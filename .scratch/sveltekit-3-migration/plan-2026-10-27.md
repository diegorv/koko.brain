# SvelteKit 3 migration

Move `@sveltejs/kit` from `^2.70.3` (`package.json:82`) to 3.x and `@sveltejs/adapter-static` from `^3.0.10` (`package.json:81`) to `^4.0.0`. The bump closes GHSA-pfhg-q3qv-9q6r and GHSA-27mw-82g8-phjj (both list 3.0.0 as first patched), plus the repo-only advisories GHSA-prjg-x2qj-wj3g and GHSA-xgrj-p7pg-6vm3. The app is a Tauri SPA (`src/routes/+layout.ts` `ssr = false`, adapter-static `fallback: "index.html"`) and imports no `$app/*`, `$env/*`, `$service-worker` or `@sveltejs/kit` runtime API anywhere in `src` or `e2e` (grep, 0 hits). The real work is config relocation, tsconfig, and the `$lib` alias (554 files under `src`).

Strategy: do the kit-2-compatible prep first (config already movable to `vite.config.js` since kit 2.62, per kit 3 source `src/exports/vite/index.js:163`), then the bump with a temporary deprecated `$lib` alias, then the `#lib` codemod as separate commits. Each step is green on its own and individually revertable.

### `#lib` specifier convention (ticket 05, 2026-10-27)
Decided for 06-11: write `#lib/...` with `.js` endings, exactly as `sv migrate` emits: `#lib/x.js` for a `.ts` module, `#lib/x.store.svelte.js` for a `.svelte.ts` store, `#lib/dir/index.js` for a barrel, `#lib/x/Comp.svelte` for a component. package.json `imports` has only `"#lib/*": "./src/lib/*"`; vitest needs no `#lib` alias (vite resolves subpath imports and maps `.js` to `.ts`). Probe matrix (kit 3.1.0, tsconfig extends `$app/tsconfig` with `moduleResolution: bundler` + `allowImportingTsExtensions`):

| Spelling | vite build | svelte-check | vitest |
|---|---|---|---|
| `.js` (plain, `.svelte.js`, `/index.js`) | ok | ok | ok |
| `.ts` (plain, `.svelte.ts`, `/index.ts`) | ok | ok | ok |
| none (`#lib/x`, `#lib/dir`) | not run | FAIL: "Cannot find module '#lib/utils/fuzzy-match'"; `.store.svelte` matched the `*.svelte` ambient module | ok (vitest is lenient, so it cannot be the gate) |
| `.svelte` component | ok | ok | ok |

Extensionless is invalid: subpath imports do no extension probing for tsc. `.ts` works but is rejected to match codemod output and the guide example. Permanent proof: `src/tests/lib/lib-subpath-import.test.ts`.

Review probes (2026-10-27): `vi.mock('#lib/utils/fuzzy-match.js')` replaced the module for both a `$lib/utils/fuzzy-match` and a `#lib/...js` import in the same file, and `vi.mock('$lib/utils/fuzzy-match')` replaced a `#lib/...js` import: vitest keys mocks by resolved file id, so ticket 11 may mix spellings. Build: with `backlinks.service.ts` temporarily importing the store via `#lib/...store.svelte.js` (static and dynamic `import()`) while other modules kept `$lib`, `pnpm build` emitted exactly one store definition (one chunk). The `.js` -> `.ts` mapping is vite's own resolver behaviour for TS importers, not a tsconfig flag.

tsconfig `paths` requirement (ticket 11, 2026-10-27): svelte-check resolved `#lib/X.svelte` (package.json `imports`) to the ambient `declare module '*.svelte'`, so `#lib` component props were silently untyped since ticket 06. `tsconfig.json` `compilerOptions.paths` now maps `"#lib/*": ["./src/lib/*"]` (plus `$lib`/`$lib/*`, because a local `paths` replaces the inherited one); with it, pnpm check surfaced 0 new errors. Side effect: TS now also accepts extensionless `#lib/x`, which fails at runtime in Node/Vite, so `src/tests/lib/lib-specifier-convention.test.ts` scans `src` and fails on any extensionless `#lib` specifier; its `@ts-expect-error` on a `#lib` component's props makes pnpm check fail if the paths entry is dropped.
