## Findings

1. **minor** `src/tests/lib/core/markdown-editor/EditorTabs.test.ts:771`. The text/plain test fires `dragover` without starting a tab drag first, so `dragFrom` is null and `handleDragOver` (`EditorTabs.svelte:130`) returns before it reaches `isTabDrag`. If the `!isTabDrag(event)` check were deleted from `handleDragOver`, the dragover half of the test would still pass; only the drop half (`handleDrop` checks the type alone) would catch it. Fix: call `startDrag(0)` first, then fire `dragover` and `drop` with a separate `fakeDataTransfer(['text/plain'])`, so the type gate is the only thing that stops them.
2. **nit** `src/lib/core/markdown-editor/EditorTabs.svelte:232`. Adding `flex-1` to the label span is outside the Issue's list: it moves every unpinned tab's close button to the tab's right end. The reason holds up: with shorter labels, a click on a tab's centre landed on its close button (the collection-block E2E caught it). It matches the prototype, and `tabs.spec.ts:152` covers it. Accept it, but name it in the squash commit's Behavior section.
3. **nit** `src/lib/core/markdown-editor/EditorTabs.svelte:117-156`. The drag has been tested only in Chromium. Two WebKit behaviours are unverified in the real Tauri window. (a) Whether `dataTransfer.types` lists the custom type during `dragover`; the precedent `RailPropertiesPicker` suggests it does. (b) Whether `dragleave` carries a `relatedTarget`. If WebKit sends null, `handleDragLeave` clears the marker each time the pointer crosses a tab boundary. The next `dragover` restores it, so the cost is a flicker, not a lost drop. Fix: check by hand in `pnpm tauri dev` before release; no code change needed unless it flickers.
