## P103. The macOS menu bar holds almost nothing

**Still real: yes.** Verified: three top-level menus (`lib.rs:212-247`), no `File`, nothing about vaults; no palette command about vaults (`commands.ts` has none); the only UI that opens a vault is the picker page that `AppShell.svelte:184` hides while a vault is open; `vaultStore.close()` has no production caller (and does not need one: `switchVault` goes straight from vault A to B).

Current behaviour: to change vaults the owner must quit and relaunch (the picker is the first screen), or use a deep link. The review's "no way to switch vaults from inside an open vault" is exact. The capability is not missing, only its entry points: `openVaultDialog` and `openRecentVault` already do the whole switch.

What the prototype wants:
- A new `File` menu between KokoBrain and Edit with `Open Vault...` and an `Open Recent` submenu (three hard-coded vaults, current one checked). Clicking the current one toasts "already open"; another one toasts "Closing the current vault, opening X".
- Palette: query "switch" lists `Switch vault` (category Vault), `Open vault...` (Vault) and `Open Settings`. `Switch vault` replaces the list with the recents (current marked "Current", title "Select a vault...").
- The "After" caption says "the app asks to close the current one first". Real flow does not ask: it saves every dirty tab, drains writes and opens, and prompts only when a save failed (`vault.service.ts:22-27`). Keep the real flow; do not add a confirm.
- Review text: "Full View, Go and Note menus are polish" (not required).

Design points a ticket must settle:
1. **`Cmd+O` is taken.** `quick-switcher:open` is `Cmd+O` (`global-keybindings.ts:70`). A native accelerator is delivered to the app menu before the webview, so a File > Open Vault... on `Cmd+O` would silently kill the quick switcher. `Cmd+Shift+O` is free (grep of `key: 'o'` finds only the switcher). Recommended: `Cmd+Shift+O`, or no accelerator at first. Settings (`Cmd+,`) is the precedent for an accelerator declared both in `build_menu` and `global-keybindings.ts`.
2. **The palette has no second-step picker** (`AppCommand` is a flat list; the rs-links-toc scout confirms). The prototype's two-stage "Switch vault" is a prototype construct. `MAX_RECENT_VAULTS = 3` (`vault.logic.ts:13`), so after dropping the current vault there are at most two others. Recommended: one palette command per other recent vault, built per call like `railGoToCommands`: `vault:open-recent:<path>` "Open Vault: <name>" (category "Vault"), plus one `vault:open` "Open Vault..." that calls `openVaultDialog`. No new dialog, store or component. The current vault is excluded (choosing it would do nothing).
3. **Native Open Recent is the expensive half.** The recent list lives in the frontend (localStorage), the menu is built once in Rust. A native submenu needs a `set_recent_vaults` IPC (DTO with `#[ts(export)]`, so the "Both" gate and regenerated bindings), a rebuild on every `vaultStore.recentVaults` change (`Submenu::append/remove/remove_at/insert` exist in Tauri 2, docs.rs `tauri::menu::Submenu`; repo locks 2.12.5), a stale-entry story (the menu cannot check `exists`; `openRecentVault` already does and removes the entry), and a `menu:open-recent` event with a path payload. Recommended: split it out as an optional follow-up (candidate T3). The File menu without a submenu plus the palette commands already make switching possible.
4. **Menu event routing.** One new unit event `menu:open-vault` (const in `events.rs`, entry in `EVENT_NAMES` and `EventMap` as `null`, listener beside `registerMenuSettingsListener`, mounted in `(app)/+layout.svelte`). The listener calls `openVaultDialog()`; it must catch and `error('LISTENERS', ...)` like the settings listener, and not toast on cancel (`openVaultDialog` returns false on cancel).
5. **Testing the menu.** `build_menu` takes `&tauri::App` and no mock runtime is enabled (`Cargo.toml:22` has no `test` feature; no `mock_app` in `src-tauri`), so the menu itself cannot be built in a test. Put the id-to-event decision in a pure function in `src-tauri/src/commands/` (the `app_exit.rs` + `tests/commands/app_exit_test.rs` pattern: `exit_decision` is pure and tested through `kokobrain_lib::commands::...`), and keep `on_menu_event` a thin match. `core_tauri_free_test.rs` only polices `vault/db/search/semantic/utils`, so `commands/` is allowed to import tauri.
6. **Quit path must survive.** `build_menu` also holds the Quit item whose custom id exists so the exit flush runs (`lib.rs:177-185`, `on_exit_requested`). Adding a File menu must not touch it; open-itens 090 edits the same function (see Overlaps).
7. **Out-of-scope vault folders.** Exposing "Open Vault..." everywhere makes open-itens 083 (a folder outside `~/Documents/kokobrain-vaults` and `~/kokobrain-vaults` is refused with a message) more reachable. 083 is ready-for-agent with an owner decision already recorded. The new entry points call the same `openVaultDialog`, so they inherit 083's fix when it lands; no extra work here, but order matters for the owner.
8. **Menu on the picker page.** On the picker page (no vault) the File item must still work (it does, the listener is in the layout). A vault switch while one is open reruns `initializeVault`; there is no "closing vault" state to show, same as deep links.

## P104. Sidebar panels and feature settings only through the Settings sheet

**Still real: partial.** The core holds for Properties, Backlinks and Outgoing links: no palette command, keybinding or header control toggles them; their only switches are `LayoutSection.svelte:127-151` (the review's path omits the `rail-shell` folder, and `commands.ts` is in `app/`, not `core/`). Three parts of the proposal's premise are off:
- Table of contents already has a palette toggle (`commands.ts:330-336`, `layout:toggle-table-of-contents`), which is the pattern to copy.
- `open(section)` does have a production caller (`SearchPanel.svelte:190`, `settingsPanelStore.open('search')`, from finders-ux 04, resolved). That is the precedent for "Configure..." links, not a gap.
- There is no "header menu" to extend: `SidebarSection.svelte:34-47` is a bare button or div. The header menu is new UI.

What the prototype wants: four panels (Properties, Table of contents, Backlinks, Outgoing links), each header with chevron, title and an ellipsis `aria-label="<name> menu"` button that is invisible until header hover, focus-visible or open (`.more { opacity: 0 }`, :300-301), opening a 200 px popover: `Hide panel`, for Properties also `Configure types...` (toasts "Opens Settings > Types"), and the footer note "Settings > Layout still works". Hiding removes the panel and toasts "<name> panel hidden (palette: Toggle to bring it back)". With every panel hidden the sidebar shows "All panels are hidden. Show them again from the palette." Palette: "Toggle Properties Panel", "Toggle Backlinks Panel", "Toggle Outgoing links Panel", "Toggle Table of Contents" (category Layout, status Shown/Hidden).

Design points:
1. **Two independent halves.** The palette toggles are three tiny commands (plus the existing TOC one) with no UI; the header menu is a `SidebarSection` change that collides with another cluster. They split cleanly (candidates T1 and T4).
2. **Properties hides Info too.** `AppShell.svelte:289-291` gates `NoteInfo` by `propertiesVisible`, and `AppShell.test.ts:221-255` asserts it. Keep it. The palette label can stay "Toggle Properties Panel"; the help text should say Info goes with it. `NoteInfo` gets no menu of its own (no flag).
3. **A toggle on a hidden sidebar does nothing visible.** Default `rightSidebarVisible: false` (`settings.store.svelte.ts:62`), and `toggleRightSidebar` is a no-op on tabs `hidesRightSidebar` covers. The existing TOC command flips only the flag, so today "Toggle Table of Contents" can appear to do nothing. See owner question 3.
4. **Shared helper.** One `togglePanel(key)` / `setPanelVisible(key, visible)` in `layout.service.ts` (beside `toggleRightSidebar`) used by the palette commands and later by the header menu. Test in `layout.service.test.ts` with the real `settingsStore`. The TOC command should move onto it so the four behave alike (its existing test `commands.test.ts:527-540` must stay green).
5. **Header menu structure.** A menu button cannot live inside the collapsible header `button` (nested interactive). The rs-properties-layout scout's T1 restructures the header into a `button` inside an `h2` that carries `pane-toolbar` (open-itens 210 item 3, sticky headers); the menu trigger then sits as a sibling of the inner button inside that wrapper. Build it after that ticket, not before. Use `DropdownMenu` from `#lib/components/ui/dropdown-menu` (already used by `PropertiesView.svelte:170-202`). Constraint: do not add `h-*`, `p*-*`, `gap-*`, `border-*` to the `pane-toolbar` class list (`pane-toolbar.test.ts`); put sizing on the trigger button. Offer the menu through optional `SidebarSection` props (`onHide`, optional configure item) so the four callers stay one line each; TOC is a plugin importing core `SidebarSection`, which is allowed.
6. **Configure links only where a section exists.** `SettingsSection` has `types` for Properties; Backlinks, Outgoing links and TOC have no dedicated section, only Layout. A "Configure..." that opens Settings > Layout from a menu whose other item hides the panel is circular. Recommended: `Configure types...` on Properties only (`settingsPanelStore.open('types')`), nothing on the other three. See owner question 2.
7. **All-hidden empty state.** Needs a pure helper (for example `anyRightPanelVisible(layout)` in `layout.logic.ts`, tested without mocks) and an empty block in `AppShell.svelte`. It must also count the Claude panel flag if `claude-code-integration` 03 lands first (that Issue makes the chat "the only right-sidebar section rendered"). Copy per prototype; a "Show panels" button is an optional extra.
8. **Persistence and undo.** Reusing the four existing layout flags means no new persisted state and no settings-merge change. "Settings > Layout still works" stays true because both write the same flags.
9. **E2E locators.** `e2e/specs/sidebars.spec.ts:42-43,55-56` click `locator('button', { has: h2 })`; the rs-properties-layout ticket changes them. The menu trigger must not match that locator (an `aria-label` "Backlinks menu" button outside the toggle button does not).

## P105. Trash can be browsed only from inside Settings

**Still real: yes.** `TrashSection.svelte` is reachable only through the Settings navigation (`settings.logic.ts:276-282`, `SettingsPanel.svelte:55,82`). No palette command (`grep Trash commands.ts` is empty), no rail item (`rail-items.logic.ts:37-48` ends at `archive` in the bottom group; the review cites `:46`, which is the Files line, so cite `:37-48`), and the Move to Trash confirm (`delete-note.service.ts:14-19`) never says where trashed notes go. `settingsPanelStore.open('trash')` already type-checks and `TrashSection.onMount` loads the manifest, so the command is three lines.

What the prototype wants: a palette command "Open Trash" in category Settings that opens the sheet straight on Trash. The rest of the prototype's sheet (Restore, Delete permanently, Empty trash, empty state) is a re-draw of what `TrashSection` already does; the prototype omits the native confirms and shows only the folder, not the full original path. Do not copy those differences.

Design points:
1. **Use `open('trash')`, not `toggle()`.** `settings:open` uses `toggle()` (`commands.ts:410`). A command that toggles would close the sheet when it is already open on another section.
2. **No vault open.** The palette overlays also mount on the picker page; `TrashSection` then shows "Trash is empty" because `vaultStore.path` is null (`onMount` skips `loadTrash`). Recommended default: the command still opens the sheet; it is harmless and avoids a gate. A toast is the alternative.
3. **Settings already open on Trash.** `open('trash')` changes nothing; `onMount` does not rerun. The store is kept current by `moveToTrash` and the lifecycle load, so this is fine.
4. **Focus and scrim.** Open-itens 199 (focus into the drawer) and 200 (modal scrim) change what `open(section)` does to focus. P105 (and P104's Configure link) call the same method and inherit the fix. No dependency.
5. **Out of scope.** Undo toast after Move to Trash ("Undo stays with P01"), a rail lens, a native Trash menu item. The review says "No rail lens".

Test files and seams: `src/tests/lib/app/commands.test.ts:555-562` ("settings open action toggles settings panel") is the template: real `settingsPanelStore`, `getBuiltInCommands().find(c => c.id === 'settings:open-trash')`, run it twice and assert `isOpen === true` and `activeSection === 'trash'` after each (a toggle would fail the second assertion), and with Settings open on `'editor'` first, the section switches to `'trash'`. `TrashSection.test.ts` (`:95-145`) is unchanged. E2E: `e2e/specs/settings.spec.ts` has no Trash coverage; add one case: palette "Open Trash" shows the Trash heading.

## Candidate tickets

The three palette halves (vault commands, panel toggles, Open Trash) all land in `commands.ts` and `commands.test.ts` and call existing services, so they are one ticket. The native Open Recent submenu is an independent risky part (new IPC, DTO, dynamic menu) and is split off as deferred.

## Owner questions

1. **Native Open Recent submenu and accelerator.** The File menu can ship with just `Open Vault...` (T2) while `Open Vault: <name>` palette commands (T1) cover recents, because at most three recents exist. A native Open Recent submenu (T3) needs a new IPC command, a DTO and a menu rebuild on every change. Build T3 now? Recommended: no, ship T1 and T2 and add T3 only if the palette route is not enough. Also: `Cmd+O` is the quick switcher, so should `Open Vault...` get `Cmd+Shift+O` or no accelerator? Recommended: `Cmd+Shift+O`.
2. **How far do "Configure..." links go?** Only Properties has a settings page of its own (Types). Recommended: `Configure types...` on Properties only, none on Backlinks, Outgoing links and Table of contents (their only setting is Layout, which "Hide panel" already covers).
3. **Should turning a panel on reveal a hidden right sidebar?** Default `rightSidebarVisible` is false, and the existing "Toggle Table of Contents" only flips its flag, so a toggle can look like it did nothing. Recommended: yes for all four toggles, using the same guard as `toggleRightSidebar` (not on tabs that hide the sidebar); turning off leaves the sidebar alone.
4. **Open Trash with no vault open.** Open the sheet (shows "Trash is empty") or refuse with a toast? Recommended: open the sheet, no gate.
