## Where the scout is wrong or incomplete

1. **The "default narrow sidebar of about 166 px" is not the app default.** `rightSidebarSize: 3` (`settings.store.svelte.ts:71`) is a percent (paneforge `types.d.ts:52` "The default size of the pane in percentage"), so a fresh vault opens the pane at about 3 % (tens of px) and the owner drags it. The 166 px figure is the prototype's crop of `narrow-1024x700-editor-light.png` (`right-sidebar.html:405,1006`), taken with the e2e fixture's `rightSidebarSize: 20` (`e2e/fixtures/test-vault.ts:52`). `MANIFEST.md:42` gives no width. The narrow case is still common for a different reason: `maxSize={30}` caps the pane at 30 % of the inner group, so at a 1024 px window the sidebar can never be much wider than about 250 px (class estimate from 166 px = 20 %). The e2e criteria must name the fixture width, not "near its default width".
2. **The h2/button flip (open-itens 210 item 3) has more consumers than the scout lists.** Missed: `AppShell.test.ts:390-398` (`h2.parentElement` must carry `pane-toolbar`), `TableOfContentsPanel.test.ts:133-140`, `OutgoingLinksPanel.test.ts:115-121`, `BacklinksPanel.test.ts:164-170` (each asserts `header.querySelector('h2')`), and `e2e/specs/event-calendar-focus.spec.ts:73` (`button` has `h2` "Backlinks"). `e2e/specs/table-of-contents.spec.ts:5` clicks the `h2` and keeps working if the button fills the heading.
3. **A cheaper flip structure exists, and it removes the "opaque hover" problem.** Wrap the existing `svelte:element` (button or div, still carrying `pane-toolbar` and `data-sidebar-section-header`, chevron slot still its first child) in `<h2 class="sticky top-0 z-10 bg-right-sidebar-bg ...">`, and put the title text in a `<span>`. Then `[data-sidebar-section-header]` is still the button for collapsible sections (the three panel tests' `header === querySelector('button')` and `AppShell.test.ts:282`'s first-child check stay true), `pane-toolbar.test.ts` still finds exactly one class list, and the translucent `hover:bg-right-sidebar-accent/50` paints over the h2's opaque background, so the hover needs no change. Only the `querySelector('h2')` / `parentElement` lookups and the e2e `button has h2` locators move (to `closest('h2')` / `getByRole('heading').getByRole('button')`).
4. **The sticky header would cover the scroll thumb.** The bits-ui scrollbar is `position: absolute` with no z-index and is a sibling after the viewport (`scroll-area.svelte.js:626-631`, `scroll-area-scrollbar.svelte`). A `z-10` header inside the viewport paints above it, so the thumb disappears under each pinned header's 40 px band. Any positive z on the header does this, and the header needs one: P121 makes the delete buttons `absolute`, and positioned z-auto content later in the DOM would paint over a header without z. Fix: `scrollbarYClasses="z-20"` on the right sidebar `ScrollArea` (`AppShell.svelte:277`; the prop exists in `scroll-area.svelte:12`). From CSS painting order, not rendered.
5. **Sticky does work in this ScrollArea.** The viewport is `overflow-y: scroll` with a flex-column content div that has no overflow (`scroll-area-viewport.svelte:28-32,47-54`, `scroll-area.svelte.js:73-76`). `tasks-view-ux` Issue 240:42 lists this as unverified. It is verified here (not edited there).
6. **T1 criterion 2 tests the wrong remount.** `PropertiesView` does not remount on a tab switch. It remounts when the sidebar hides and shows, or when `propertiesVisible` toggles (`AppShell.svelte:265,278`). The criterion must remount the component.
7. **T1 criterion 3 tests the `=== true` read in the wrong place.** `mergeLayout` copies saved values unvalidated (`settings.logic.ts:20-22`), so a `mergeLayout` test cannot show that a non-boolean reads as expanded. The read lives in `PropertiesView`, so that is where the test goes. The settings test only pins the default and that a saved `true` survives the merge. The new field's JSDoc must say "Loaded unvalidated, so read it only as `=== true`", like its neighbours (`settings.types.ts:87-94`).
8. **Info: the info-in-SidebarSection half belongs with P123, not with the frame ticket.** Both edit only `NoteInfo.svelte` (header `:42-47`, rows `:48-53`) and `NoteInfo.test.ts`. Same component, one context, one ticket. The frame ticket stays on `SidebarSection` and the Properties collapse.
9. **P123: the long-form tooltip is unrequested scope.** The scout calls the review's "the tooltip already holds the full value" false. With `title={row.value}`, the tooltip holds the whole visible string whenever the span truncates it, and the abbreviated month carries the same information. A second `title` field on `NoteInfoRow` adds API and breaks the exact `toEqual` shapes at `note-info.logic.test.ts:31-32,35-40` for no data gain. Keep `title={row.value}`. The test at `NoteInfo.test.ts:124-129` stays green unchanged.
10. **P123's e2e criterion would fail by design.** Playwright runs with no `locale` (`e2e/playwright.config.ts` has none), so en-US, 12-hour clock: "Nov 5, 2026, 12:00 PM" is about 22 characters, about 150 px at 14 px (`--text-row`), against about 134 px of content at the 166 px fixture width even after wrapping. "No value has `scrollWidth > clientWidth` at a narrow sidebar" would fail there. It would then tempt someone to weaken it. Split it instead: at 1024 px the value wraps under its label (value top below label bottom); at 1280 px (about 200 px of sidebar by the same 20 %) no value is clipped. Both widths are estimates the builder confirms on the first run.
11. **`sidebars.spec.ts` does not call `setViewportSize`** (the scout lists it as a precedent). The precedents are `tabs.spec.ts`, `note-action-bar.spec.ts`, `event-calendar.spec.ts` and `tasks-view.spec.ts`. `readPersistedLayout` (`sidebars.spec.ts:6`) types its key as `'rightSidebarVisible' | 'railPanelsVisible'`, so the union grows.
12. **The P121 ordering contradicts the sibling scout.** This scout says "P44 and P45 first, then P121". `scout-rs-properties-editing.md:144` says "P121 first, then T1 (P44)". P121 is the row skeleton: the grid, the icon column and the out-of-flow actions. P44's inline refusal message, P45's icon-as-menu-button (editing T3) and P122's "+ Add" chip all sit inside that skeleton. Land P121 first. The editing cluster's order then stands as written.
13. **P121 has two in-flow buttons on list rows.** Add item (`PropertyField.svelte:147-153`) and Remove (`:158-164`) both take width. The scout covers only Remove. Both leave the flow together, as one action group. Taking them out of the flow needs `relative` on the row (`div.group`, `:106`). P122 later replaces Add item with a visible chip and owns that change.
14. **Missed conflict: ADR 0026.** Its 2026-05-28 amendment (`docs/adr/0026-type-definitions-relationships-lifecycle.md:45`) records "a 'Has Many' row in the Properties panel" as part of `_has_many`'s parity. `help/documentation/25-types-and-relationships.md:542` says the same. Hiding empty groups changes that: the kind is reached through "Add relationship". The Relationships ticket adds a dated amendment line to ADR 0026 and fixes help 25:542 and 07:47.
15. **The kind step must be keyboard-usable.** P46 (rs-relationships T2) rebuilds the picker list on `Command` to fix keyboard use, and lands first (`scout-rs-relationships.md:81,112`). If the new kind step is a plain list of `mousedown` buttons, P46's fix regresses one step earlier. The kind step reuses P46's list.
16. **The scout's sticky criterion leaves out one case.** A collapsed section's header must also stay in place when it is the last section. Nothing extra is needed: with the h2 as the sticky element, a collapsed section is only its header. I checked this and found no gap.
17. **Persistence shape differs from P71's.** `scout-rs-links-toc.md:48` recommends an in-memory store boolean for Backlinks/Outgoing open state, not persisted across restart. P43 asks to "remember the state". The scout picks a persisted layout key. The two give the sidebar mixed memory rules (Properties survives restart, Backlinks does not). Owner question 1.

Checked with nothing wrong found: `SidebarSection` importers (the four panels only), `PropertiesView`/`NoteInfo` mounted only by `AppShell.svelte`, `note-info.logic.ts` and `PropertyField`/`RelationshipSearch` each with one importer. The parse effect lives in the `PropertiesView` script (`:105-119`), outside the collapsible body, so collapsing does not stop it. `Collapsible.Content` adds no forceMount. `LayoutSection.svelte:129-131` writes `propertiesVisible` only. No Rust struct mirrors layout keys (`grep` in `src-tauri/src`: none). The `pane-toolbar.test.ts` override regex (`:30`) allows `sticky`, `top-0`, `z-*` and `bg-*`. `claude-code-integration` 03 lives on `mvp-claude` (owner memory), so the `LayoutSettings` key list conflicts only textually, at merge time.

## Owner questions

1. Properties' collapsed state: persisted across restarts in settings, or in memory for the session only (as rs-links-toc recommends for Backlinks/Outgoing)? Recommended: persisted (`propertiesCollapsed`). It is a layout preference like the panel toggles. The Backlinks choice stays with P71.

5. Info dates keep the year ("Nov 10, 2026, 10:00"). Recommended: yes.
