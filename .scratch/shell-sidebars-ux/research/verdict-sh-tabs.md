## Where the scout is wrong or incomplete

1. **The flex-width plan would not make tabs shrink, and its test would pass anyway.** The strip's flex items are not the `role="tab"` divs. `ContextMenu.Trigger` with a `children` snippet renders its own `<div {...mergedProps}>` around them (`node_modules/bits-ui/dist/bits/context-menu/components/context-menu-trigger.svelte`, bits-ui 2.20.6). Putting `flex-[0_1_220px] min-w-[100px]` on the inner tab (scout design point 3, T1 criterion 4) leaves the wrapper sized to its content, so nothing shrinks, while a class assertion on `[role="tab"]` passes. The width classes go on the Trigger (`<ContextMenu.Trigger class=...>`, `restProps` reach the wrapper div), the inner tab becomes `w-full min-w-0`, and the test asserts on the scroller's direct children. A real-layout E2E has to prove the shrink.
2. **Tab drag must not carry `text/plain`.** Three drop targets act on a `text/plain` path: `FilesNavigator.svelte:279-291` MOVES the file into the folder (proven by `e2e/specs/rail-shell.spec.ts:897-905`), `CanvasInner.svelte:573-590` adds a file node, and CodeMirror inserts the text. A tab drag set up the "obvious" way (`setData('text/plain', path)`, as `NoteRow.svelte:77` does) would let a tab dropped on a folder move the note on disk. The repo already has the fix: `RailPropertiesPicker.svelte:70-73` uses a private type (`application/x-kokobrain-list-property`) for that reason. T2 uses `application/x-kokobrain-tab`, and the strip's `dragover` accepts only drags carrying that type, so a note row dragged over the strip shows no marker. The scout did not cover the payload at all.
3. **Keying the `{#each}` by path is the riskier option, not the recommended one.** In Svelte 5.57.3, a duplicate key throws in production too, not only in dev (`node_modules/svelte/src/internal/client/dom/blocks/each.js:356-363` calls `e.each_key_duplicate('', '', '')` in the non-DEV branch). Duplicate paths are reachable: `path-change.service.ts:179` re-adds closed tabs after a failed delete without dedupe, and the user can reopen that note during `await diskOp()`. Keep the each unkeyed. A reorder only needs the store order. All per-tab markup is derived from `tab`, and the drop ends the drag, so no DOM identity has to survive.
4. **The bits-ui Tooltip precedent is dead code, and `Tooltip.Root` needs a Provider.** `DailyNoteButton.svelte` has no importer in `src/` (grep for `periodic-notes/DailyNoteButton` and `./DailyNoteButton`: none). bits-ui's `TooltipRootState` calls `TooltipProviderContext.get()` (`tooltip.svelte.js:192`), and runed's `Context.get` throws `Context "Tooltip.Provider" not found` (`runed/dist/utilities/context/context.js:37-40`). The only live Provider is `EventCalendarView.svelte:237`. A bits-ui tooltip on tabs also stacks a third trigger (Tooltip) on top of ContextMenu.Trigger and `draggable`, and 012's note on the default `children` form keeping `tabindex=0` applies (bits-ui trigger props set `tabindex: -1`, `menu.svelte.js:1599`). The recommended default changes to a native multi-line `title` (owner question 2). It costs nothing during a drag, and its text is assertable by attribute. Dead `DailyNoteButton.svelte` is noted here, not deleted.
5. **Svelte's `onwheel` is not passive.** Only `touchstart`/`touchmove` are (`node_modules/svelte/src/utils.js:261`), and `wheel` is not a delegated event (`:110-134`), so `onwheel={...}` on the scroller can `preventDefault`. No manual `addEventListener` is needed.
6. **The reserve needs no new `layout.logic.ts` helper.** The condition is `!hidesRightSidebar(activeTabPath) && !settingsStore.layout.rightSidebarVisible`. A `$derived` in `EditorTabs.svelte`, covered by the component test, is enough. That also removes `layout.logic.ts`/`layout.logic.test.ts` from this ticket's files: sh-empty-zoom-status P97 rewrites `hidesRightSidebar(null)` in exactly that file.
7. **The reserve and the window drag region must be checked by geometry, not by a class.** Padding on the scroller (scroll container) only adds space at the end of the content, so a mid-scroll strip still runs under the toggle. The reserve goes on the non-scrolling wrapper. The scout's E2E check ("the toggle does not intersect the last tab's close button") passes with too few tabs to reach the edge. It must open enough tabs to overflow and assert `scroller.right <= toggle.left`, which holds at any scroll position. Also, today the empty area right of the last tab is a window drag handle because the strip itself carries `data-tauri-drag-region` (`:46`). If only the new wrapper carries it, the scroller covering that area stops dragging the window. Both elements keep the attribute.
8. **The hidden count also needs a tab-list trigger.** A `ResizeObserver` on the scroller does not fire when a tab is added or closed (the scroller's box keeps its size, only `scrollWidth` changes). Fade and count state recompute on `scroll`, on resize, and in an effect on `editorStore.tabs.length`. jsdom has no `ResizeObserver`: `EditorTabs.test.ts` needs the stub `EventCalendarView.test.ts:8-13` uses. `AppShell.test.ts`, `EditorView.test.ts`, `meta-bind-open-view.test.ts` and `canvas-tab-switch.test.ts` also mount the strip (through `EditorView`) and already stub it. The scout listed `EditorTabs.test.ts` as the strip's only test importer. They must stay green.
