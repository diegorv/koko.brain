   ```
   function isHiddenName(name: string): boolean { return name.startsWith('.'); }
   export function navigatorFolders(nodes) { return (nodes ?? []).filter((n) => n.isDirectory && !isHiddenName(n.name)); }
   ```
   Filter only, tree order kept. Used by FilesNavigator.svelte:77 and :430, and by `findNavigatorFolder` (lens.logic.ts:947).

4. Where the tree order comes from (the proposal's Evidence range fs.logic.ts:408-478 holds):
   - Rust `scan_vault` sorts with `sort_nodes` (src-tauri/src/commands/vault.rs:1784-1803): directories first, then `natural_cmp` on names.
   - `natural_cmp` (vault.rs:1809) lowercases names and compares code points. `_` is U+005F (95), lowercase letters start at 97, digits at 48. So every underscore folder sorts before every letter-initial folder. Verified by reading the comparison; not executed.
   - fs.service.ts:96-100: `call('scan_vault', { path, sortBy: 'name' })` plus `loadFolderOrder`.
   - fs.service.ts:111-115: `applyFolderOrder` runs only when `folder-order.json` has entries or `contentOrder` is non-empty. Otherwise the scan order is kept.
   - fs.logic.ts:408-496: `applyFolderOrder` and `orderLevel`. Branch structure: folder-order.json list first (444-455), then `_order` sort (457-476), otherwise `reorderedFolders = folders` at line 478 (keep incoming order). Return at 496. So with no custom order, underscore folders keep the top position from the Rust sort. This confirms "folder ordering already exists" as machinery, but the "sort after user folders" rule is not implemented anywhere.
   - fs.logic.ts:551-556 `compareTreeNodes` and :571-573 `sortLevel` (used by `insertTreeNode`, fs.logic.ts:584-620) re-create the scan order when a node is inserted at runtime. Any change to tree order must also match these, or inserted folders land in a different place than after a reload.

5. folder-notes.logic.ts:16-48 (cited range, still relevant but indirect)
   - 19-23 `buildContentOrderMap` and 31-44 `patchContentOrderMap` build the `_order` map used by `orderLevel`. 47-56 `addContentOrder`. 59+ `folderNoteDir`.
   - This is the `_order` input only. It does not reference underscore names. Consumers: app-lifecycle.service.ts:386 and tauri-listeners.service.ts:215.

6. Settings-based system folder (not used by the navigator)
   - settings.store.svelte.ts:97-100: `templates: { folder: '_system/templates', systemFolder: '_system' }`.
   - settings.types.ts:176-183: `systemFolder` doc says it is the folder excluded from the type sidebar, defaults to `_system`.
   - type-sidebar.logic.ts:65-75 `excludeSystemFolder` uses it. The Files navigator does not.
   - So the code already has a configured notion of "system folder". The proposal's hard-coded underscore prefix does not use it.

7. `_templates` is not the default
   - Default `templates.folder` is `_system/templates` (settings.store.svelte.ts:98). In a default vault the top level shows `_system` only; `_templates` appears only when the user configures it.
   - e2e/fixtures/test-vault.ts:65 and e2e/fixtures/live-preview.ts:26 set `templates: { folder: '_templates' }`, so the E2E vault has both.
   - src-tauri/src/commands/semantic.rs:1479 hard-codes `EXCLUDED_FOLDERS = ["_templates"]`. Not the same list as the settings default.
   - Result: the review's example ("_system and _templates sit at the top") holds for the E2E fixture vault and for users who set `_templates`, but not for a fresh vault with the defaults. Partial.

8. Counts
   - `countFiles` exists at fs.logic.ts:187-199 (recursive count of files, not notes). No UI caller; only fs.logic.test.ts uses it (lines 467-510). Would need a new call site and a decision whether to count files or markdown notes.

9. Existing behaviour pinned by tests

## Verdict

still_real: partial. The core problem holds: `_system` sorts above every letter-initial folder because of `natural_cmp` (vault.rs:1809) and the E2E test pins it (file-explorer.spec.ts:57-75). Partial because the review's example `_templates` is not the default template folder (`_system/templates` is, settings.store.svelte.ts:98); the "sort after user folders" rule is not implemented (fs.logic.ts:478 keeps the scan order); and the cited folder-notes range is about `_order`, not system folders.

Not confirmed in this pass: the screenshot content (only the manifest description was used), runtime behaviour (no app run, per read-only rules), and whether any user-facing feature besides the Files navigator renders folder lists from fileTree in the same order.
