## Review block

Copied from .scratch/design-review/review.md (lines 280-284):

```
#### P44. A refused property key rename or add fails silently, and the key field shows text that was never saved
- **Problem:** The key input is uncontrolled and ignores the rename result, so a duplicate or blank key is refused without a word and the field keeps the unsaved text.
- **Evidence:** PropertyField.svelte:29-33, 52-58, 113-119; PropertiesView.svelte:129-131, 144-152; properties.service.ts:159-172.
- **Proposal:** On a refused rename, restore `property.key` (with a refusal counter, as the value field does) and show an inline message with `aria-invalid`. Enter commits and Escape reverts. The add input shows the same duplicate message.
- **Impact:** A refused edit is no longer mistaken for a saved one. **Effort:** S
- **Validation:** revise. The add input already handles Enter and Escape.
```

Prototype metadata (right-sidebar.html): card at lines 455-458 (badges Moderate, Effort S); demo mount `#d44` built at lines 1169-1178.

- Add form (lines 728-732): input `aria-label="New property name"`, `placeholder="Property name..."`, error `<p class="p-err" id="add-err" role="alert">` under the input.
- Key handlers (lines ~900-935): Enter calls `commitKey`; Escape sets `el.value` back to `data-pk` and blurs; blur calls `commitKey`; `keyInput` clears the error when the user types again. Add input clears `addErr` on input.
- `commitKey` (lines 853-865): unchanged name is a no-op; blank name returns early (line ~857-859) without restoring the field text in the "after" state; duplicate check is case-insensitive (`p.key.toLowerCase()`, line 860) and in the "after" state sets `sb.err[old]` and does not restore the field (so the typed text stays, marked invalid, with the message).
- Interactions to try, per the card: rename `status` to `priority` and click away; Add property with `owner` (a duplicate in the mock).

Divergences between prototype and the proposal text (for the ticket's owner questions):
1. Proposal says "restore `property.key`" on a refused rename. The prototype keeps the typed text on a duplicate and marks it invalid, and only restores on Escape. The proposal's wording and the mock disagree.
2. Proposal says "a blank key reverts". The prototype's blank branch returns before touching `el.value` (line ~857-859), so the mock does not visibly revert a blank key on blur. Unconfirmed whether the mock intends a re-render there.
3. Prototype duplicate check is case-insensitive. Code is exact (see Current code), so `Status` and `status` are two keys in code today.

- properties.service.ts:88-95: when `detectLossyFrontmatter` is non-null, `toastFrontmatterWriteError(...)` is shown with id `frontmatter-refused:${activePath}`. So a refused rename or add caused by lossy frontmatter is NOT silent today. Only the duplicate, blank and alias-twin cases are silent.

### Canonical key comparison (affects the duplicate rule)

- src/lib/utils/frontmatter-aliases.ts:29-31: `canonicalizeKey(key) = ALIAS_MAP.get(key) ?? key`. Exact lookup, no case folding, so `Status` and `status` are different keys in code. The prototype's check (case-insensitive) does not match. Owner question for the ticket.
- src/lib/core/frontmatter/properties.logic.ts:735-741 `renamePropertyKey`: returns the list unchanged when `oldKey === newKey`; otherwise maps the matching key.

### Value and input primitives
