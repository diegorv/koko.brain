```
#### P122. List property chips cannot be edited or reordered, and add/remove are hover-only
- **Problem:** Chips are static spans, the controls sit at opacity 0, and an empty list shows only the key.
- **Evidence:** PropertyField.svelte:90-96, 147-153, 166-196.
- **Proposal:** Double-click a chip to edit it in place, and show a visible "+ Add" chip when the list is empty. Drag-to-reorder is optional.
- **Impact:** No more delete-and-retype on tags. **Effort:** M
- **Validation:** revise. Enter already keeps the add input open.
```

Enter in the add field still keeps it open." The review's Validation line is the only place "revise" is stated; the reason given is the Enter behavior, which is confirmed below.

Claim 7, "Enter already keeps the add input open" (the Validation note): HOLDS.
- Add input keydown, :192-195: `if (e.key === 'Enter') { e.preventDefault(); addListItem(); }`. `addListItem` (:90-96) does not set `isAddingListItem = false`. Only Escape (:194) and blur (:196) close it.

Additional findings relevant to the change (not in the review text):
- Refusal is ignored on the list path. `removeListItem` (:84-88) calls `onUpdate(property.key, items)` and discards the boolean. `addListItem` (:90-96) also discards it and clears `newListItem` unconditionally (:95). By contrast `commitValue` (:60-62) does `if (!onUpdate(...)) refusals++;`, which rebuilds the value control via `{#key refusals}` (opens at :122). The chip block (:168-201) sits outside `{#key refusals}`, so a refused chip edit would not reset the chip view unless the same pattern is added.
- Refusal source: `onUpdate` resolves to `handleUpdate` (PropertiesView.svelte:121-127) -> `updateProperty` (properties.service.ts:124-133) -> `commitChanges` (:83-109). `commitChanges` returns false when the note's properties do not match the active note (`propertiesMatchActiveNote`, :84) or when `detectLossyFrontmatter` flags the block (:87-95); on the lossy case it raises a toast with id `frontmatter-refused:<path>` (:92-94). So a refused chip edit would show the toast but the chip UI state would stay on the typed text unless handled.
- `handleListKeydown` at PropertyField.svelte:98-103 is defined but not referenced: the template uses an inline `onkeydown` (:192-195). Dead code, pre-existing. Not in P122's scope; mention only.
- Chip icon colour uses `getTagColor(item, settingsStore.tagColors.colors)` only when `property.key === 'tags'` (:171), importing `#lib/utils/tag-colors.js`. An in-place edit must keep the colour mapping keyed by the new text.
- Reorder: no drag code exists in the file or the properties feature (grep for drag/sortable not run exhaustively; unconfirmed beyond this file).

## Verdict

still_real: yes. Chips are static spans with no edit path (PropertyField.svelte:170-183), the add and remove controls are opacity-0 until hover (:147-153, :158-164, :175-181), and an empty list renders no chip block (:168), so only the key and a hover-only plus remain. Enter in the add field keeps it open (:192-195), as the review says. The review's "revise" validation is about that Enter behaviour, which holds.

Not checked: the prototype's CSS for the main-row plus (hover-only or visible) is unconfirmed; drag-to-reorder was not searched across the whole codebase; codemap/INDEX.md was not queried (grep only); no test was run (read-only research, as instructed). Risk to note for the ticket: a refused chip commit is ignored on the list path today, and the prototype's empty-text commit deletes the chip, which the review does not mention.
