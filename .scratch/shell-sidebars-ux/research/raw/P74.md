```
#### P74. Sidebar link rows truncate the identifying text and show raw markdown snippets
- **Problem:** Path, alias and heading share one truncated line. Snippets are raw markdown and can cut off the link itself.
- **Evidence:** OutgoingLinksPanel.svelte:65-71; LinkItem.svelte:25, 27; [right-sidebar-crop-light.png](screens/right-sidebar-crop-light.png), [right-sidebar-all-expanded-light.png](screens/right-sidebar-all-expanded-light.png).
- **Proposal:** Two-line rows: the title, then the folder or target and the heading in muted text, plus a path tooltip. Strip markdown from snippets and window them around the link with `line-clamp-2`, sharing the stripper with P158.
- **Impact:** The right note can be identified without opening it. **Effort:** M
- **Validation:** keep.
```

### 3. Snippet data path (the important finding)

- `src/lib/features/backlinks/BacklinksPanel.svelte:12, 70-75` calls `fetchBacklinksV2` unconditionally and renders `<LinkItem {entry} />`. There is no feature flag check in the panel. (The `backlinks.logic.ts` header comment at lines 9-15 still describes a "flag is on" degraded mode; the code path is unconditional now.)
- `src/lib/features/backlinks/backlinks.service.ts:131-163`: `call('get_backlinks_v2', { path })` then `entries.map(noteEntryV2ToBacklinkEntry)`.
- `src/lib/features/backlinks/backlinks.logic.ts:17-23`:
  ```ts
  export function noteEntryV2ToBacklinkEntry(entry: NoteEntryV2): BacklinkEntry {
  	return {
  		sourcePath: entry.path,
  		sourceName: entry.title,
  		snippets: entry.snippet ? [{ text: entry.snippet, linkStart: 0, linkEnd: 0 }] : [],
  	};
  }
  ```
  So `linkStart = linkEnd = 0`: the bold link span in LinkItem never renders in production. The mapping does not carry the link position at all.
- Rust side: `src-tauri/src/commands/vault.rs:486-497` `get_backlinks_v2` returns `Vec<NoteEntry>` from `idx.lookup_backlinks(&path)`. `NoteEntry.snippet` is set in `src-tauri/src/vault/entry.rs:268` from `compute_snippet(body)`.
- `src-tauri/src/vault/entry.rs:365-398` `compute_snippet`: takes the LEADING body, skips blank lines, joins non-blank trimmed lines with single spaces, truncates to `SNIPPET_MAX_LEN = 280` bytes (line 25) at a codepoint boundary. Markdown is kept verbatim on purpose (doc comment lines 369-373: "Markdown structure (headings, code fences, list markers) is preserved verbatim, the consumer's renderer decides how to display it"). The snippet is NOT positioned at any link.
- Consequences, verified in code:
  1. The snippet is the top of the note, not a window around the link. A backlink whose `[[link]]` sits beyond 280 bytes of body does not show the link at all. The Evidence sentence "can cut off the link itself" is therefore understated: the link is usually absent, not cut.
  2. The proposal's "window them around the link" needs data that does not exist today: either a Rust change (position of the first link to the target, then a window in `compute_snippet`-like code, plus a ts-rs DTO change regenerating `src/lib/contracts/generated/`) or a TS-side re-read of the note body (would need file IO per row; not a pure UI change).
  3. Stripping markdown in the UI is possible without Rust changes: `markdownToPlainText` exists (see section 6) and handles headings, lists, quotes, wikilinks (`[[Books/Dune|Dune]]` -> `Dune`), emphasis, highlights. Note: the stripper turns `[[target]]` into `target` (last path segment), which removes the brackets the proposal wants gone.
- `src-tauri/src/vault/entry.rs:25` is the constant to check if the 280-byte limit is changed.
- `e2e/mocks/vault-index.ts:89-98` `bodySnippet()` mirrors the limit (280 bytes) but only strips fenced code blocks and collapses whitespace; it does NOT strip markdown headings or links. So the E2E mock reproduces the raw-markdown look and any E2E test on snippets sees raw markdown.
