## Findings

1. minor, src/lib/utils/color.ts:28: the `!` on `parseRgba(oklabToHex(...))!` assumes oklabToHex always returns a parseable hex. A chroma of about 103 or more digits overflows the cubes in oklabToHex to opposing infinities, giving NaN channels and `#NaNNaNNaN`. parseRgba then returns null and `rgb[0]` throws `TypeError: Cannot read properties of null`. A probe confirmed the throw for `isDarkColor('oklch(0.5 1<400 zeros> 270)')`. A value like `oklch(0.5 1<103 zeros> 270)` is 119 characters, so it passes theme-validation's FUNCTION regex and its 128-character limit, and an imported or catalog theme package can make buildTheme throw instead of skipping the token. Fix: drop the assertion and return null when the round trip fails (`const rgb = parseRgba(...); if (!rgb) return null;`), with a color.test.ts case. This does not block: only a hand-crafted value triggers it.
2. nit, src/lib/utils/color.ts:126-144: `ensureContrast` on a translucent oklch foreground (`oklch(... / 0.5)`) returns an opaque hex: the probe gave #8490ad for `oklch(0.55 0.06 268 / 0.5)`. It already treats `rgba()` input the same way, and no built-in token is affected. The build report and discovery both note this. No change needed now.

## Resolution

1. Fixed. `parseRgba` drops the non-null assertion and returns null when the OKLab round trip does not parse back (color.ts:28-30). A probe put the NaN threshold at a chroma of 1 followed by 104 zeros (103 zeros still overflows to Infinity, which clamps), so the new color.test.ts case uses 110 zeros (126 characters, under the 128 limit) and asserts `isDarkColor` and `flatten` return null. It threw `TypeError: Cannot read properties of null` with the old color.ts.
2. Not changed, as the review says: translucent rgba() input already behaves the same way and no built-in token is affected.
