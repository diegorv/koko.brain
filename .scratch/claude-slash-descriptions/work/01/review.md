## Findings

1. **minor**: `src/lib/features/claude-code/ClaudePanel.svelte:98-104`. The effect depends on `vaultStore.path`, so during a vault switch it fires as soon as `switchVault` sets the new path. That happens before `initializeVault` reaches `teardownVault`/`loadSettings`. The request then starts in the new vault's cwd with the previous vault's `settingsStore.claudeCode.binaryPath`. `teardownVault` then calls `resetSettings` (so `claudeCode.enabled` and `layout.claudeVisible` fall back to `false` and the panel unmounts) and `resetClaude` (`slashFetch = null`), so that reply is always dropped. After `loadSettings`, the remount asks again with the right settings. The result is two `claude` processes per switch while the panel shows: the user's SessionStart hooks run twice in the new vault, and the first run may use the wrong binary. Discovery's premise "the panel stays mounted across a switch" does not hold, because the defaults unmount it. Fix: fetch at mount only (drop the `vaultStore.path` read and fix the comment). Alternatively, skip the call until the settings for `vaultStore.path` are loaded. The panel test "a vault switch does" would then need to model a remount instead of a bare `vaultStore.open`.
2. **minor**: `src-tauri/src/commands/claude/slash.rs:233-235`. After stdout reaches EOF (`eof = true`), the group is not killed, the run is unlisted, and `child.wait()` blocks with no deadline. A `claude` that closes stdout but keeps running would hold the `spawn_blocking` task past the 30 s deadline, which the Runner criterion says covers the exit. Because it is already unlisted, `cancel_all` at app exit would not reach it either. The build report acknowledges this. Fix: in the EOF path, poll `try_wait` until `deadline_at`, then `runs.cancel(&id)` while the run is still listed, and unlist it only after the process is reaped or killed. Add a test with a script that does `exec >&-; sleep 30`.

## Resolution

1. Fixed. `ClaudePanel.svelte` asks for the slash commands on mount only: the effect no longer reads `vaultStore.path`. On a vault switch the settings reset unmounts the panel, and the remount after `loadSettings` asks once with the new vault's binary. The panel test "asks once per vault: a remount makes no new call, the remount after a vault switch does" now asserts that a path change with the panel still mounted makes no call, then models teardown (unmount, `resetClaude`, new settings) and the remount. It fails with the old effect.
2. Fixed. In `slash.rs`, after stdout EOF the request stays listed and the runner polls `exited_unreaped` (now `pub(super)` in `shell_env.rs`, a `WNOWAIT` check that does not reap) until the deadline; past it, `runs.cancel` kills the group while it is still listed. It is unlisted and reaped only after that. New test `a_script_that_closes_stdout_and_keeps_running_is_killed_at_the_deadline` (`exec >&-; sleep 30`, 1 s deadline): it took 30 s and failed before the fix, and now returns the rows within the deadline with the group gone.
