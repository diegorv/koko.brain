## Findings

1. minor, `help/documentation/28-mods.md:378` (and `:637`): Stop now turns a `run.ui` call the mod does not await or catch (a fire-and-forget `run.ui.alert(...)`, a common "notice" pattern that used to resolve harmlessly) into an unhandled promise rejection. `sentry.service.ts` keeps the `GlobalHandlers` integration, so with Sentry on, such a rejection from a normal user Stop can reach Sentry, and it shows in the console. The docs say "Let the `AbortError` propagate" but never say a non-awaited call needs a `.catch`. Fix: add one sentence to the Stop bullet ("a `run.ui` call you do not await needs a `.catch`, or Stop leaves an unhandled rejection"), and list `run.ui` next to `ctx.ui` in the host-caught errors sentence at `:637`. Docs only; the AbortError design itself is the Issue's decision.
2. nit, `src/lib/plugins/mods/mods-host.service.ts:375` / `help/documentation/28-mods.md:379`: a `run.ui` dialog opened after its run already ended normally (code the action did not await) is never closed by the run, and at unload it resolves as cancelled via `closeForMod`, not rejected, because `end()` removed `abortOnUnload`. The Unload bullet says run dialogs "reject as under Stop" without that caveat. This is the build's stated default and outside the acceptance criteria; at most a half-sentence in the docs ("of a live run").
3. nit, `src/tests/lib/plugins/mods/ModDialogHost.test.ts:632`: "closing a pick from outside its buttons" clicks the dialog's close button, not an outside pointer interaction. The comment explains that both go through `onOpenChange(false)` and the code path for `run.ui` is identical to `ctx.ui`, so coverage of the criterion is adequate; the test name could say "close button".
