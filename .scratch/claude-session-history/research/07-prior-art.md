## 1. t3code

### 1a. Native threads: its own store is the source of truth

- Data source: SQLite event sourcing. `orchestration_v2_events` (append-only, `thread_id`, `event_type`, `payload_json`) plus projection tables, among them `orchestration_v2_projection_threads` (has `title`) and `orchestration_v2_projection_messages` (`role`, `streaming`, `payload_json`): `apps/server/src/persistence/Migrations/055_OrchestrationV2.ts:20`, `:194`.
- Chat view: read from those projections. The Claude transcript is not consulted to draw a thread.
- Resume: the Claude adapter builds `threadIdentity = input.resume ? { resume: nativeThreadId } : { sessionId: nativeThreadId }` (`apps/server/src/orchestration-v2/Adapters/ClaudeAdapterV2.ts:2194`). So t3code allocates the session id itself on the first turn (SDK `sessionId` option) and passes `resume` afterwards. It drives the Claude Agent SDK `query()` (import at `:67`), not `claude -p`.
- Before a resume it calls the worker method `getSessionMessages` to compute `resumeSessionAt` from the last message uuid (`:1457-1474`), and sets env `CLAUDE_CODE_RESUME_INTERRUPTED_TURN=1` and `CLAUDE_CODE_RESUME_REASON=user_resume` (`:1481-1485`). UNVERIFIED what these two env vars do inside the CLI.
- Resume cursor persistence: a provider-session-runtime repository stores per thread `threadId, providerName, status, lastSeenAt, resumeCursor (unknown JSON), runtimePayload` (schema at `apps/server/src/persistence/ProviderSessionRuntime.ts:26-37`; table created by migration `004_ProviderSessionRuntime.ts`).
- Title: not from Claude. A `thread-title.generate` effect in an outbox (`apps/server/src/orchestration-v2/EffectOutbox.ts:129`) calls `TextGeneration.generateThreadTitle` (`apps/server/src/textGeneration/TextGeneration.ts:206`), then a `provider-session.apply-thread-title` effect (`EffectOutbox.ts:54`) pushes it back to the provider session. UNVERIFIED: exact prompt and trigger.
- Skill and command descriptions (Feature A): slash commands come from SDK `initializationResult()` (`apps/server/src/provider/ClaudeProvider.ts:536`), mapped to `{name, description, input.hint}` (`:393-413`); skills are also read from disk, frontmatter `description` (`apps/server/src/provider/Drivers/ClaudeSkills.ts:95-99`, `:832`).

### 1b. Import of existing Claude Code CLI sessions

This is the closest prior art to "list past sessions from disk".

- Discovery: `discoverClaudeTranscripts` lists `<claude home>/projects/`, then each project dir, keeps `*.jsonl`, stats mtime, with an operation budget and a `truncated` flag (`apps/server/src/project/AgentSessionScanner.ts:1385-1430`). Home dir resolution: `resolveClaudeConfigDir`, falls back to `~/.claude` (`:1373-1382`).
- Hard limits: 200 messages kept, 100 transcripts, 100k records per file, 32 MB history bytes (`AgentSessionScanner.ts:87-91`). A long session keeps the first user message plus the latest 200 and counts the rest as `omittedMessageCount` (`createClaudeHistoryWindow`, `:718`; return value at `:674-681`).
- Which records count: only `type` `user` or `assistant`; records with `isSidechain`, `isMeta` or `isCompactSummary` are dropped (`isHiddenClaudeRecord`, `:335`; `shouldRetainDecodedRecord`, `:690-705`). Text is only `string` content or `text` blocks joined with newlines (`extractText`, `:305-315`). Tool calls and results are not imported.
- Title precedence (`:354-363`, `:674`): `customTitle` (record field, last non-empty wins, an empty one clears it) over `aiTitle` (last non-empty) over `deriveTitle(first user text)` (first line, 100 chars, `:404-410`) over the literal "Imported thread". The code comment says Claude flushes the AI title after a user rename (`:360`).
- Session id: `sessionId` field of records, falling back to the file name. The importer rejects ids that are not UUID shaped (`apps/server/src/project/AgentSessionImporter.ts:51`).
- Thread creation: id `import:<instance>:<sessionId>`, `historyOrigin: "v1_import"` (`:379`), runtime stored as `status: "stopped"` with `resumeCursor: { threadId, resume: <session id> }` and `runtimePayload.cwd` (`:305-320`). Re-import is idempotent: it compares stored messages with the transcript and only re-links when identical (`:337-358`).
- Takeaway: the view of an imported thread is lossy by design (text only, 200 messages), but the continuation still carries full context because Claude resumes from its own transcript.

## 2. claude-agent-acp (Zed's Claude adapter, now under agentclientprotocol)

- ACP protocol: `session/list` is gated by `sessionCapabilities.list`, params `cwd` and `cursor`, returns `sessionId, cwd, title, updatedAt` plus `nextCursor`, and "does not restore or modify" sessions (https://agentclientprotocol.com/protocol/session-list, fetched). `session/load` is gated by `loadSession`; the agent must replay the whole conversation as `session/update` notifications (`user_message_chunk`, `agent_message_chunk`, ...) and only then answer; `session/resume` reconnects with no replay (https://agentclientprotocol.com/protocol/session-setup, fetched).
- Data source: the Claude Agent SDK helpers `listSessions({dir, includeWorktrees:false, limit, offset})` and `getSessionMessages(sessionId)` (`src/v1/acp-agent.ts:2115-2145`, `src/resumed-session.ts:58-77`). It does not parse JSONL itself for the plain list. It does have a heavier "session index" that scans transcript head and tail (`src/session-index/transcript-scan.ts`).
- Page size 1000, cursor `offset:N` (`src/v1/acp-agent.ts:1486`, `:2145-2146`). Rows with no `cwd` are skipped (`:2135`).
- Title: SDK `summary`, sanitized. The index re-implements the SDK rule (`transcript-scan.ts:653-687`): `customTitle` (tail, then sidecar, then head), then `aiTitle`, then `lastPrompt`, then `summary`, then first prompt. First-prompt rules (`src/session-index/first-prompt.ts:1-19`): main-chain user records only; expand `<pasted_content>`; flatten to one line; a slash-command prompt (`<command-name>`) is only a fallback; text starting with another tag or `[Request interrupted` is skipped; cut at 200 chars; image-only gives "Image".
- Record types named in code: `custom-title` (field `customTitle`), `ai-title` (`aiTitle`), `lastPrompt`, `summary`, `agentName` (`transcript-scan.ts:653-687` and the `lastAgentName` helper above it).
- Why a session may have no AI title: the file header says Claude Code titles a new SDK session itself, shortly after the first prompt, as an `ai-title` entry; it does not for a resumed session or when `CLAUDE_CODE_DISABLE_NONESSENTIAL_TRAFFIC` or `CLAUDE_CODE_DISABLE_TERMINAL_TITLE` is set, and the adapter then asks with a `generate_session_title` control request (`src/session-titles.ts:2-14`).
- Chat view rebuild (`replaySessionHistory`, `src/v1/acp-agent.ts:7830`): reads messages, stitches history across compactions (`readHistoryAcrossCompactions`, `src/resumed-session.ts:102`: `compact_boundary` records restart the `parentUuid` chain, so it relinks via `logicalParentUuid`), skips synthetic login-required text and peer/channel meta user messages (`src/message-filters.ts:216-230`), strips local-command metadata, then pushes each message through the same `toAcpNotifications` converter the live path uses (`:8243-8262`, option `replay: true`). Same renderer for live and replay is the design point.
- Resume: `loadSession` at `:2088`, `resumeSession` at `:2076`; capability `loadSession: true` at `:1848`.

## 3. opcode (formerly claudia)

- Data source: plain directory walk of `~/.claude/projects` (`list_projects_blocking`, `src-tauri/src/commands/claude.rs:631`); sessions of one project are the `*.jsonl` files in it (`get_project_sessions_blocking`, `:787-860`), sorted by file creation time, newest first. Also joins `~/.claude/todos/<session>.json` (`:826-832`).
- Project path: the dir name is a lossy encoding (every non-alphanumeric char becomes `-`, `encode_project_path`, `:266-278`), so it recovers the real path from the `cwd` field of the first session records that have one, then falls back to probing the filesystem (`resolve_project_path`, `:458`, tests around `:2689`).
- Title: no title record is read at all. It shows the first user message: `extract_first_user_message` (`:500-535`) takes the first `user` record whose content is a string, skipping text containing the "Caveat: The messages below were generated by the user while running local commands" marker and text starting with `<command-name>` or `<local-command-stdout>`. The UI shows the first line, truncated to 120 chars (`src/components/SessionList.tsx:148-150`).
- Gotcha from the code: the parse struct types `content` as `Option<String>` (`claude.rs:72-76`). A record whose content is a block array fails to deserialize and is skipped. In the owner's vault dir user records are string content in 269 cases and block arrays in 781 (751 `tool_result`, 28 `text`, 2 `image,text`), so typed prompts that carry images would not be found by this approach (inference from serde semantics, not run).
- Chat view: `load_session_history` (`:1186-1222`) returns every JSONL line as `serde_json::Value`, skipping unparsable lines. The frontend maps each entry to the live message type with `type: entry.type || "assistant"` and sets the list (`src/components/ClaudeCodeSession.tsx:311-345`), so the renderer for streamed `stream-json` lines also renders transcript lines. Then `isFirstPrompt=false` so the next prompt continues.
- Resume: `resume_claude_code` runs `claude --resume <id> -p <prompt> --model ... --output-format stream-json --verbose --dangerously-skip-permissions` with cwd = project path (`:1288-1320`). It reads `session_id` from the `system/init` line (`:1556-1561`).
- Own persistence: only `localStorage` keys `opcode_session_<id>` and an index, holding `{sessionId, projectId, projectPath, lastMessageCount, scrollPosition, timestamp}` for tab restore (`src/services/sessionPersistence.ts:8-45`). Message bodies are re-read from the transcript.

## 4. Other open-source GUIs and viewers

### delexw/claude-code-trace (Tauri 2, Rust + React, MIT per the web search listing)

The best structural match for Kokobrain's stack.

- Data source: walks `~/.claude/projects` on a background thread, newest first, throttled to a 20 percent duty cycle (`src-tauri/src/indexer.rs:54`, header comment `:1-14`). Per-session metadata comes from one pass over the file (`scan_session_metadata`, `src-tauri/src/parser/session.rs:1205`). Preview scan stops after `MAX_PREVIEW_LINES` (`:1233`, used in the loop near `:1580`).
- Title: `first_message` = first real user prompt, 500 chars, newlines to spaces; skips command output and `[Request interrupted`; `<command-name>` becomes a `/command` fallback only when no real prompt exists (`session.rs:1580-1626`). It does not read `ai-title` or `custom-title`. Instead it joins a name from a second source: `~/.claude/sessions/*.json`, a pid-keyed registry written by running sessions, read keys `sessionId, name, status, statusUpdatedAt, pid, bridgeSessionId` (`session.rs:754-830`). The doc comment says an entry normally disappears when the session ends, so this is a live-session name source, not durable. UNVERIFIED on the owner's machine (not inspected).
- Chat view: shared pipeline parse, chunk, link subagents, inject orphans, convert to `DisplayMessage`, with index-range windowing for a virtualized list; the build is whole-file (`src-tauri/src/session_load.rs:1-12`).
- Also handles forks and inherited entries (`session.rs:1586`, "skip inherited entries so first_message reflects the fork's own first prompt") and compact boundaries (tests near `:3341-3481`).

### siteboon/claudecodeui (web UI over the CLI/SDK, GPL-3.0 per the search listing)

- Data source: scans `~/.claude/projects/**/*.jsonl` and upserts rows into its own SQLite table (`server/modules/providers/list/claude/claude-session-synchronizer.provider.ts:46-60`, `custom_name` column at `:154`).
- Title: `extractSessionTitle` scans forward keeping the last of each record type `custom-title` (`customTitle`), `ai-title` (`aiTitle`), `last-prompt` (`lastPrompt`), each matched on `sessionId`; precedence custom, ai, last prompt (`:183-232`). Comment explains why a reverse scan is wrong: Claude writes `custom-title` right before `ai-title`, so first hit from the end would lose a manual rename. Fallback: `~/.claude/history.jsonl` keyed `sessionId` to `display` (`:49`, `:94`). A user-set `custom_name` in its own DB beats all of these (`:154-158`).
- Chat view: `readTranscriptRows` (`claude-sessions.provider.ts:479-500`) reads rows with matching `sessionId`, then treats the file as a graph via `parentUuid` ("editing a sent message makes a second path appear", `:472-478`, abandoned-branch handling near `:604-690`), then normalizes to its message type. Hidden content: `<system-reminder>`, `Caveat:`, `[Request interrupted`, `Base directory for this skill:` (`:960-975`).
- Gotcha documented there (`:949-958`): persisted transcripts mark a skill body as `isMeta: true`, but the live stream does not, so without a content check the skill body renders live and vanishes on reload. This matters for `/skill` turns in the panel.

## 5. What this means for Kokobrain (structure only)

1. Two proven designs. (a) Own store (t3code native): persist the rendered messages yourself, keep only the session id for continuation. (b) Read-through (opcode, claude-code-trace, claudecodeui, ACP): list and rebuild from Claude's transcript each time. t3code uses (a) for its own threads and (b) only as an import path with lossy text.
2. Retention risk for (b): Claude Code keeps local transcripts 30 days by default, adjustable with `cleanupPeriodDays` (https://code.claude.com/docs/en/data-usage.md, "Local caching" bullet, fetched). On the owner's machine `~/.claude/settings.json` has no `cleanupPeriodDays` key (checked with a script, key absent) and the oldest of the 31 transcripts in the vault's session dir is about 20 days old. A resume of a deleted transcript cannot work, so a list built only from transcripts silently loses old chats while an own store would keep showing chats that can no longer be resumed.
3. Title records are in the transcript. In the vault's session dir (31 files) record types counted: `last-prompt` in 31 files, `ai-title` in 26, `custom-title` in 1. Key names: `ai-title` {`aiTitle`,`sessionId`,`type`}, `custom-title` {`customTitle`,`sessionId`,`type`}, `last-prompt` {`lastPrompt`,`leafUuid`,`sessionId`,`type`,`explicit`}. This matches claudecodeui and ACP.
4. Print-mode sessions lack `ai-title`. By the `entrypoint` field of the records, 2 sessions are `sdk-cli` (print mode, the panel's mode): both have `last-prompt` and neither has `ai-title`. The 26 titled ones are `cli` (12) or `sdk-py` (14); 2 `cli` files also lack one. Sample is tiny, cause UNVERIFIED (ACP's header suggests the CLI only titles some entrypoints). Design the title fallback as `customTitle`, `aiTitle`, `lastPrompt`, first prompt, as ACP does.
5. `~/.claude/history.jsonl` exists (22048 lines in the owner's file) with keys `display, pastedContents, timestamp, project, sessionId`. It is a prompt log, not a session list, and `display` is the user's prompt text, so reading it for titles has a privacy and size cost. claudecodeui uses it only as a last fallback.
6. Rebuild fidelity, common traps seen in all readers: the transcript mixes many record types with the turns (vault dir counts: `attachment` 2227, `assistant` 1615, `user` 1050, `api-request` 811, `system` 401, `queue-operation` 223, `file-history-snapshot` 187, and others), so a reader must select `user` and `assistant`; `isMeta`, `isSidechain`, `isCompactSummary` must be filtered; skill bodies and `<command-name>` rows need special handling; pasted content is wrapped in `<pasted_content id=...>` tags (claudecodeui `claude-sessions.provider.ts:972`); the chain is a `parentUuid` graph with branches, and `compact_boundary` restarts it.
7. Best reuse for the panel: opcode's idea (feed transcript lines into the same reducer as live `stream-json`) is cheapest if the store already consumes `assistant`/`user` events; the transcript's message objects have the same `message.content` blocks as the live `assistant` and `user` events in `turn.ndjson` (UNVERIFIED line by line, not diffed).

## Claims to verify

1. t3code drives the Agent SDK `query()` and passes `sessionId` on turn one and `resume` after (`ClaudeAdapterV2.ts:2194`), and draws threads from its own `orchestration_v2_projection_messages`, not from the Claude transcript.

6. Claude Code's default local transcript retention is 30 days (`cleanupPeriodDays`), and the owner has not overridden it.
7. claudecodeui's note that persisted transcripts tag skill bodies `isMeta: true` while the live stream does not is accurate for CLI 2.1.325 (taken from its source comment, not reproduced).
