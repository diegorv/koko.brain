## Findings

1. **major** `src/lib/features/claude-code/claude.service.ts:65` (and :78, :87). The save target's `chatId` is read after `await saveAllDirtyTabs()`, so a reset during that await (vault switch) followed by a send in the new vault gives the old send the new chat's id. Reproduced with a probe test (deleted after the run): send in `/vault-a` with `saveAllDirtyTabs` pending, `resetClaude()`, `vaultStore.open('/vault-b')`, send again (B's `claude_run_turn` starts), then let A's save resolve. Result: `claude_run_turn` is spawned for `/vault-a` after the vault closed, its run id `r-old` attaches to B's chat (`claudeStore.runId === 'r-old'`), and B's own run `r-new` is the one cancelled. B's panel then streams a turn running in vault A's cwd, and the `saveTarget` left by the late send points at vault A, so B's turn is never saved at Done. The catch at :87 has the same root cause: with `target` still null, a `saveAllDirtyTabs` rejection after a reset calls `failTurn` on the new chat. Fix: read `const chatId = claudeStore.chatId` right after `claudeStore.beginTurn(text)` (it is non-null there, so the `!` goes away), build the target from it, and after `saveAllDirtyTabs` return without calling `claude_run_turn` when `claudeStore.chatId !== chatId` or `vaultStore.path !== vaultPath`. Compare the catch against that early-captured id as well. Add a service test for this ordering (reset while `saveAllDirtyTabs` is pending, then a second send).
2. **minor** `src/lib/features/claude-code/claude.logic.ts:237` with `src/lib/app/lifecycle/app-lifecycle.service.ts:558`. A turn sent while vault B is still initializing, followed by a B -> C switch that skips `teardownVault`, survives into C: `restoreLastChat(C)` is a no-op while it runs, so after its Done the panel shows B's chat in C, and the next send writes B's chat into C's `.kokobrain/claude/chats/` and resumes B's session. The service test "a Done that arrives after a vault switch the chat survived writes nothing" pins the Done half only. The Issue asks for exactly this restore behaviour and the window is small, so this does not block. Record it in a follow-up Issue, or in claude-code-integration Issue 09 (needs-triage), which owns the reset-vs-run races.
