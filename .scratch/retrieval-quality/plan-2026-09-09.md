# Retrieval quality: hybrid candidate recall, reranker context, gap filter scaling

Fixes four verified defects in the query-time retrieval stack (`search_hybrid`,
`search_semantic`, `adaptive_filter`) and adds the eval harness needed to prove
each change improves retrieval instead of merely changing it. None of the tasks
below changes what is stored in the `chunks` table, so no `EMBED_RECIPE_VERSION`
bump and no reindex.

Status: AGREED 2026-09-09. Decisions: plan lives in `.scratch/`; Task 4 uses an absolute gap in logit space; Task 5 adds the filter to hybrid and reconciles the docs; Tasks 1-7 are all in scope. Each finished task is committed before the next starts.

| 3 | Gap filter documented for hybrid but not run | Confirmed; doc is stale | `semantic.rs:869` truncates only. The `search_hybrid` docstring (steps 1-6) never mentions a filter, so `docs/SEARCH.md` is the side that drifted. History is shallow (50 squashed commits), "lost in refactor" cannot be settled. |
| 4 | Gap threshold ill-scaled for logits | Confirmed; affects semantic mode today | `filtering.rs:43` uses `top.abs() * 0.04`; `semantic.rs:729` runs it on reranker logits whenever the reranker is loaded. |

## Acceptance (from the eval, Task 1 baseline vs post-Task 5)

- Bucket A (rare exact terms: identifiers, proper nouns, acronyms): hybrid recall@10 >= max(text, semantic) recall@10, and no query where hybrid misses a path that text mode returns in its top-10.
- Bucket B (paraphrase / semantic queries): hybrid and semantic recall@10 do not drop.
- Bucket C (queries with no relevant note): result count after the filter is lower or equal; no bucket A/B expected path is ever cut by the filter.
- Hybrid p50 latency stays under the documented ~500 ms rerank budget for a 50-pair pool.
