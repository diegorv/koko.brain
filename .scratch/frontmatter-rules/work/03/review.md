## Findings

1. **blocker**: `src/lib/features/auto-move/AutoMoveRuleRow.svelte:181-190` and `help/documentation/22-auto-move.md:145-151`. Settings can no longer create an expression row. `FilterPanel`'s "Add filter" always adds a visual row (`createEmptyFilterRow`, `filter.logic.ts:282-290`), and `FilterRow` has no way to switch a row to raw. Nothing in `src/lib` creates a row with `raw: ''`. A raw row only appears when a stored filter already holds one. On main, the user could type any expression into the field.
   - **Failure:** add a new rule and try to build `file.hasTag('archive')`, `file.inFolder('Inbox')` (PRD Decision 12 exists "so folder rules read naturally") or `(status == "done" && _type == "project") || file.hasTag("archive")`. None of them can be entered. The only way is to edit `.kokobrain/auto-move-rules.json` by hand.
   - **Docs:** the help page says "write it as an expression row", but the UI offers no way to add one. Its own examples (`file.hasTag('project')`, `file.hasTag('keep')`) cannot be built in the builder either.
   - **Spec:** this undercuts PRD Decision 1 ("`&&`, `||`, `!` and parentheses work inside it") for every new rule.
   - **Fix:** add a small "Add expression" button next to the builder, in `AutoMoveRuleRow.svelte` and not in the shared `FilterPanel`, so views stay unchanged. It appends `{ id, property: '', operator: 'is', value: '', raw: '' }` to the first group, or to a new `and` group when there is none. A blank raw row is already dropped by `filterGroupsToFilter`, so it is not saved until typed, and `FilterRow` already validates it. Add a row test that adds an expression row, types `file.hasTag('x')`, fires `change`, and asserts the save. Then make the docs say how to add the row.
2. **minor**: `src/lib/features/auto-move/auto-move.logic.ts:66-71`. In an object filter, a leaf that throws at runtime is swallowed by `evaluateFilter` (`collection.logic.ts:323-330`) and counts as false, so inside `not` it matches. `filterProblem` does not catch these, because the evaluator's `validateExpression` does not check method calls.
   - **Probe:** this review ran it against a note without `status`. `{ not: ["status.nosuch()"] }` and `{ not: ["status.lower() == 'x'"] }` both matched the note, with no `onError` report. The same leaf as a top-level string is reported and matches nothing.
   - **Impact:** a typo in a method name inside a "none" group therefore applies the rule to every note, silently. This is the same hazard Behavior 3 describes for parse errors.
   - **Fix:** this cannot be done without changing the shared engine (Decision 1), so open a follow-up Issue. For example, `evaluateFilter` could take an optional `onLeafError`. At least state the limit in the help page next to "A filter with no conditions matches no note...".
3. **nit**: `help/documentation/22-auto-move.md` (the "Saved as" column of the group table). A group with one row in "All" or "Any" is saved as a plain string, not as `"and"` / `"or"` (`filterGroupsToFilter` single-row shortcut). It then reopens as "All". The comment at `AutoMoveRuleRow.svelte:52-56` knows this; the docs could say "with two or more conditions".
4. **nit**: `src/lib/features/auto-move/auto-move.logic.ts:54-58`. `isFilterObject` repeats the private `isFilterObject` in `filter.logic.ts:320-324`, with an extra `Array.isArray` guard. Exporting one shared helper would keep the two shape checks from drifting.
5. **nit**: `src/lib/features/auto-move/AutoMoveRuleRow.svelte:62-64`. `blankValue` is a second copy of `filterProblem`'s blank-value rule (`auto-move.logic.ts:39-40`), while Behavior 3 says "the same check gives the inline error in the row". The two copies agree today, but a change to one will not reach the other.

## Resolution

1. **blocker, fixed** in 5bee61651. `AutoMoveRuleRow.svelte` has an "Add expression" button under the builder (not in the shared `FilterPanel`). It appends `createEmptyExpressionRow()` (new export in `filter.logic.ts`) to the first group, or to a new `and` group. Row tests "adds an expression row and saves what is typed in it" (types `file.hasTag('x')`, fires `change`, asserts the save) and "adds an expression row to the first group"; both failed before the change ("no button Add expression"). The help page says how to add the row.
2. **minor, fixed as asked** in 2d48e9684. Confirmed at `collection.logic.ts:325-330` (the `catch` returns false). Follow-up Issue `.scratch/frontmatter-rules/issues/13-object-filter-reports-runtime-leaf-errors.md` (needs-triage); the help page states the limit in a callout after "A filter with no conditions matches no note...". The engine is unchanged.
3. **nit, fixed** in 2d48e9684, worded more precisely than "with two or more conditions": the single-row shortcut applies only when the filter's only group holds one row (`filter.logic.ts:158`); a filter with two one-row groups still saves `and` / `or` lists. The help page says so in a sentence under the table.
4. **nit, fixed** in 5ef4868e6. `isFilterObject` is exported from `filter.logic.ts` and used by `filterProblem`; the `Array.isArray` guard stays in `filterProblem`, since the shared check accepts a list and changing it would change view behavior. New test: `filterProblem([...])` gives "Filter is not a list of conditions"; `isFilterObject` has its own tests.
5. **nit, fixed** in 5ef4868e6. `hasBlankValue(row)` in `auto-move.logic.ts` is the one predicate; `filterProblem` and the row's `blankValue` both call it. Tests in `auto-move.logic.test.ts`.
