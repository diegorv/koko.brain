## Findings

1. **blocker** — `src/lib/features/auto-organize/AutoOrganizeRuleRow.svelte:205` and `:170` (with `src/lib/features/auto-organize/auto-organize.service.ts:142-150`): amendment 8 is not met for the case it names. It asks both fields to show the loader's verdict "for a stored, hand-edited template that the loader dropped" as soon as the row renders. `renameError` and `templateInvalid` derive from `rule.rename` / `rule.createNote.template`, but the rows render `autoOrganizeStore.rules` (`AutoOrganizeSection.svelte:161`), which the loader filled after `withValidProperties` deleted the invalid `rename` (and the whole `createNote` for a bad template). The service test at `auto-organize.service.test.ts:1840-1856` proves it: after `loadAutoOrganizeConfig`, `'rename' in r` is false for the refused rules. So in the app a hand-edited `"rename": { "name": "{basename} x" }` shows an empty field and only the "does nothing" hint; the next Settings edit saves the config without it, erasing it from disk with only a log line. The two new row tests (`AutoOrganizeRuleRow.test.ts:824` and `:913`) pass a bad value straight into the row, bypassing the loader, so they pass while the reported problem stays. Fix: give the row the loader's verdict. Either keep the raw invalid `rename` / `createNote` in the store (evaluation already re-sanitizes: `sanitizeRename(r.rename)` in `evaluateAndMove`, `sanitizeCreateNote(r.createNote)` for creators, `sanitizeRename` in `doesNothing`), or record the dropped value's problem per rule in the store and show it. Then write a test that goes through `loadAutoOrganizeConfig` and renders the row from the store, so it fails today.
2. **minor** — `help/documentation/22-auto-organize.md:430` and `:440`: the headline example `{year}-{month} Meeting` is stable only within a month. `{year}` and `{month}` are the save date (`resolveDestination`, `auto-organize.logic.ts:932-933`; docs table line 218-219), so `2026-11 Meeting.md` saved in December is renamed to `2026-12 Meeting.md` (or `2026-12 Meeting N.md`), because `isAlreadyNamed` compares against the new month's name. The "Names that change on their own" bullet names only `now()` and `file.mtime`. Fix: say under the example, or in that bullet, that `{year}` and `{month}` are the month of the save, so a note saved in a later month gets that month's name; for a fixed name, use an `expr` built from a date property.
3. **nit** — `src/lib/features/auto-organize/AutoOrganizeRuleRow.svelte:199`: `renameSource` is read once from the rule (`untrack`). If the store's `rule.rename` changes from `name` to `expr` (or the reverse) while the row is mounted, for example on a config reload, the select keeps the old source and the next commit saves the text under it. Fix: reset `renameSource` when the stored rename's kind changes (an `$effect` on `rule.rename`, or derive the source from the rule while no draft is pending).
4. **nit** — `src/tests/lib/features/auto-organize/auto-organize.no-chain.test.ts:170-233`: the no-chain `rename` cases cover rename + properties only. The "rename, move and properties in one run, with no re-trigger" criterion has its move half proven only in the service test, where the after-save hook is mocked and a re-trigger cannot show. Fix: add a no-chain case with `destination: 'Archive'` plus a property, asserting the note ends at `/vault/Archive/<name>.md` with the property and `vi.getTimerCount()` is 0.
