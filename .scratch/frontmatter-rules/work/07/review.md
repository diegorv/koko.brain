## Findings

1. minor — `src/lib/features/auto-organize/AutoOrganizeRuleProperty.svelte:59` (`fitted`, the `if-missing` / `always` branch). Leaving `add to list` keeps the items array as the value. The row then shows the read-only JSON field, so the user cannot edit the value in Settings any more. With no items typed, `always` with `[]` passes the loader (`isTextOrTextList([])` is true) and writes `tags: []` over every matching note's tags. Steps: Add property, key `tags`, pick "add to list", then pick "always" before typing. A blank `always ''` also clears a key today, but that row stays editable. Fix: when the target mode is `if-missing` / `always` and the value is a list from an `add` row, turn an empty list into `''` (and possibly a one-item list into its string), and add a Settings test for add -> always.
2. minor — `src/lib/features/auto-organize/AutoOrganizeRuleProperty.svelte:204` (mode menu) together with `auto-organize.logic.ts` `sanitizeRuleProperties`. "add to list" is offered on `_organized`, `_archived`, `_favorite` and `todoist_project`, and a key rename keeps an `add` row on such a key (`commitKey` -> `fitted`). The loader then drops the row, so Settings shows an inert row that disappears on reload, with no message. The refused-key message covers `todoist_project`, but nothing covers the lifecycle keys. Fix: hide "add to list" for boolean-only keys (or show a note like the refused-key one), with a test.
3. nit — `src/lib/features/auto-organize/AutoOrganizeRuleProperty.svelte:222`: the refused-key message still reads "A rule never sets {key}", but `remove` is now refused on that key too. Fix: "A rule never sets or removes {key}".
4. nit — `src/lib/features/auto-organize/AutoOrganizeRuleProperty.svelte:213`: the X button is still titled "Remove property" next to the new "remove" mode, which means something else. The help page now calls it "deletes the row". Fix: retitle it "Delete row" (and update the test that queries it, if any).
5. nit — `src/lib/features/auto-organize/auto-organize.service.ts` `reportAddSkip`: a user-config mismatch (an `add` on a number) is logged with `error()`, which also sends a Sentry event, once per rule per session. This was a documented default in discovery and matches `reportWriteFailure`, so it is noted only: consider `debug` plus a visible Settings hint if Sentry noise matters.
