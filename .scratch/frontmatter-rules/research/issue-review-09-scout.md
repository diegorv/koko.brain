## 2. Touchpoints the Issue does not name

### Code

- **Types**: `auto-move.types.ts:26-46` (`AutoMoveRule`) gets `createNote`. No Rust mirror: nothing in `src-tauri/src` reads `auto-move-rules.json`, and the type is not ts-rs exported, so no `src/lib/contracts/generated/` change.
- **Load sanitizing**: `loadAutoMoveConfig` maps rules through `withValidProperties` (`auto-move.service.ts:81`, `:92-96`). `createNote` needs the same treatment (non-object dropped, `path` missing or not Markdown dropped, `template` not a string dropped, `open` coerced, `properties` through `sanitizeRuleProperties`, `auto-move.logic.ts:157-170`). A config read from JSON is a real boundary. `saveAutoMoveConfig` writes `autoMoveStore.rules` as is (`:109-113`).
- **Per-session log-once set**: `reportedWriteFailures` (`:49`) is keyed by rule id and cleared in `resetAutoMove` (`:350`). The cap log and any create-failure log need their own set (a shared one would let a property failure silence a create failure) and a matching `.clear()` in `resetAutoMove`.
- **Missing-template behavior**: `loadNoteTemplate` swallows a read failure and falls back to `inlineTemplate ?? ''` (`note-creator.service.ts:53-61`). A typo in `template` therefore creates a blank note silently, and the "only when missing" rule then stops it from ever being retried. The Issue is silent. Either check the template exists first and skip with a log, or state the blank-note outcome. Also the template string needs a traversal guard: a `template` such as `../../x` would be read with `readTextFile`.
- **Template syntax**: `loadNoteTemplate` expands Templater `<% %>` via `processTemplate` (`utils/template.ts:22-31`), with `title` = the new note's title. In a template, `tp.file.title` is the **new** note, not the source. This does not conflict with the `{variable}` path templates (different syntax) but the help page should say so. PRD and Issue 08 Notes warn against a third syntax; the Issue stays inside that.
- **Frontmatter merge of template + properties**: the pure route is `parseFrontmatterProperties(rendered)` then `applyPropertyWrites`/`propertiesToWrite`, then `rebuildContent(properties, extractBody(rendered), rendered)` (`properties.logic.ts:689`, `:55`, `:340`). Gate it with `detectLossyFrontmatter(rendered)` (`:405`) and the "starts with `---` but no readable block" check (`propertyWriteSkipReason`, `auto-move.logic.ts:263-265`), else a template with comments or a broken block loses data or stacks a second block. The Issue does not say which modes mean what on a new note (`if-missing`/`always` against the template's own frontmatter; Issue 07's `remove`/`add` also apply). State it.
- **Explicit organization**: every other creator of a user note applies `applyExplicitOrganization(content, settingsStore.explicitOrganization)` (`new-note.service.ts:32`, `type-definitions.service.ts:179-180` "every caller creates a user note, so the switch is applied here once"). The Issue is silent on whether a rule-created note gets `_organized: false`. If not applied, a rule-created note skips the Inbox while the setting is on. This is a product decision, not a code risk; ask or state it.
- **Gates**: the system and templates folder gate exists only inside `propertyWriteSkipReason`'s private loop (`auto-move.logic.ts:258-262`), mixed with content checks. The create gate needs a pure helper that takes the target path (extract the loop). The excluded-folder gate can reuse `isInExcludedFolder(targetPath, vaultPath, autoMoveStore.excludedFolders)` (`:275-297`); note the excluded list today only stops the **source** from being evaluated (`auto-move.service.ts:139`), so applying it to the target is a new meaning. Both compare case-insensitively.
- **The `..` guard must run on the resolved path, not the template.** `resolveDestination` substitutes `{status}` and `{type}` from the note's own frontmatter (`auto-move.logic.ts:356-357`), so `status: ../../x` gives `../../x/n.md` after resolution. It also strips a leading `/` silently (`:363`), so an absolute path in the template is re-rooted into the vault instead of leaving it. To reject "absolute paths" as the Issue says, test the raw template; to reject `..`, test every segment of the resolved result. `normalizePath`/`resolveFilePath` (`utils/path.ts:5-52`) throw on escape but also fold `a/../b.md` into `b.md` and append `.md`; they are usable but do not do what the Issue's wording says by themselves. Rust `ensure_safe_write_path` (`vault.rs:1108-1120`) rejects `..` and relative paths, but does not check the vault boundary or symlinks, so it is a backstop only.
- **Other path hazards the gate list omits**: a target inside a dot-folder (`.kokobrain/`, `.git/`) or a dot-prefixed file name; `getFileNameError` (`fs.logic.ts:133-140`) rejects those and the OS-forbidden characters `<>:"/\|?*`, and `{status}` can inject `:` or `?`. Reusing `getFileNameError` on the last segment is the cheap guard. The watcher ignores dot-directories (`indexing-watcher-rules.md` rule 5), so a note created there is never indexed by the watcher.
- **Splitting the path for `createFile`**: `createFile(parentPath, fileName, content)` takes parent and name separately. Use `getParentPath`/`getFileName` (`fs.logic.ts:42-56`). It de-dupes against a fresh `readDir`, so the final path can differ from the planned one only in the race below.
- **"Would create N notes now" (Settings)**: needs each matching record resolved through `resolveDestination`, the path built with `vaultPath`, and a check against `collectionStore.propertyIndex` (absolute keys, `collection.store.svelte.ts:29`). Count **distinct** targets, not matching notes: the hub-note use case (`hubs/{type}.md` from many sources) resolves many sources to one target. Skip sources and targets the gates refuse, or the count overstates what a save does. Index keys are case-sensitive while macOS is not, so the count can differ from the disk by case; acceptable for a Settings estimate.
- **Template picker and the layer rules**: `templatesStore` lives in `plugins/templates` (`templates.store.svelte.ts`) and is filled by `loadTemplates` (`templates.service.ts:20-48`). ## 3. What makes a Behavior harder than it looks

1. **Idempotency is not free (Behavior 2).** See fact 7: `createFile` de-dupes names, so the pre-check with `exists` is mandatory and is the whole idempotency. It is case-insensitive in `createFile` (`fs.logic.ts:238`) but follows the filesystem in `exists`.
2. **A shared target is a race (Behavior 2 with hubs).** Two sources that resolve to the same hub path, saved in the same debounce window (Todoist sync, a mod, a bulk edit), run `evaluateAndMove` concurrently (independent timers, `auto-move.service.ts:148-158`). Both can see `exists === false`. Then either the second `create_note` is refused by Rust (`vault.rs:1142`, logged as an error by `createFile`, `fs.service.ts:222-224`, which also reaches Sentry), or, if the first create lands between the second's `exists` and its `readDir`, `createFile` quietly writes `Hub 1.md`, a stray duplicate note. The Issue's own "hub note for a topic" example is the case. Cheapest fix inside the feature: a module-level set of in-flight target paths (like `writingPaths`, `:46`) checked before `exists`. The owner's memory note says not to add core write-path behavior for rare corners; this stays in the feature and the failure is a duplicate note, so it is worth one line in the Issue or a stated accepted limit.
3. **A rule can chain through user saves (outside Behavior 5).** Decision 6 and Behavior 5 stop the same run. A rule such as filter `file.inFolder("meetings")` with `{folder}/{basename} follow-up.md` also matches the created note once the user saves it, which then creates `X follow-up follow-up.md`, and so on, one per save. Nothing in Behaviors 1-9 prevents it, and "Would create N" does not show it. The help page should warn: the filter must not match the created note (a property or folder only the source has). Not scope to add; worth a sentence in Docs.
4. **The source may move in the same run.** `{folder}`, `{parent}` and `file.*` fields resolve from the record built before the move (`auto-move.service.ts:207`, `:224`). The Issue says variables refer to the source; it does not say before or after the move. Resolving from the pre-move record is what falls out of the code and matches Issue 08's "same record as the filter". Put the create step after the move and the property write, so "a failed move writes nothing" covers it, and before the `:255` early return.
5. **`file.mtime`, `file.ctime` and `file.size` are fake today** (`buildNoteRecord(filePath, content, Date.now(), Date.now())`, `auto-move.service.ts:207`; size defaults to 0, `collection.logic.ts:22-28`). Issue 08 Behavior 5 fixes it. Computed values in `createNote.properties` that use them depend on 08 landing first; the Issue is blocked by 08, so this is only a reminder.
6. **Cap semantics (Behavior 6).** Each rule has one `createNote` object, so a run can only reach 5 with 6 or more matching rules. The cap counts attempted creations; the Issue does not say whether a rule whose target already exists counts. Counting only real creations is the reading that matches "creates at most 5 notes". State it. "Logs once per rule per session" needs the new set noted above.
7. **Open in a background tab (Behavior 4)** is new code, small (fact 8). An `open` rule on a hub target does nothing on the repeat saves, because the target exists and the create step returns before opening. That is the intended reading of "only when missing" but the help page should say `open` applies only to the save that creates the note.
8. **No after-save and no file-history snapshot for the created note.** `createFile` does not fire `notifyAfterSave`, so file history, the Todoist scheduler (`todoist-sync/sync-scheduler.service.ts:90`) and mods' `onNoteSaved` see the note only at its first real save. Search is covered (`fs.service.ts:218-219` passes `vaultPath`). Acceptable, and what Behavior 5 wants.
9. **Template-provided frontmatter can already contain `_type: Type` or lifecycle flags**, which the property gates of Issue 01 would refuse on an existing note (`propertyWriteSkipReason`, `auto-move.logic.ts:266-267`). Those gates run on a note being rewritten, not on freshly rendered content. A template is user-authored, so this is the user's own doing; only worth a line if the owner wants parity.

## 4. Summary for the implementer

Must-fix in the Issue text: the `{parent}` example (fact 4), the "only when missing" mechanism (fact 7, an explicit `exists`), the missing-folder step (fact 6), the missing-template outcome, and where the `..`/absolute guard runs (resolved path versus template).
Must-know in code: `evaluateAndMove` early return at `auto-move.service.ts:255`; service test mock at `auto-move.service.test.ts:19-21`; no-chain harness needs `call('create_note')` to write; the template picker must not import `plugins/templates` (layer rules baseline is exact).
Nothing is impossible. Largest pieces are the Settings block, the pure content builder (template plus properties) and the tests with the in-memory vault.
