## 2. Touchpoints the Issue does not name

### Types and load (`auto-move.types.ts`, `auto-move.logic.ts`)
- `RuleProperty.value` becomes optional or a union. Every site that reads `value` breaks at `pnpm check`: `ruleValueEditor(key, value: RuleProperty['value'])` (`auto-move.logic.ts:137`), `isRulePropertyValue` (`:147`), `sanitizeRuleProperties` destructuring (`:161`), `sameValue` (`:199`), `propertyType` (`:221`), `applyPropertyWrites` (`:232`), `OwnedProperty extends RuleProperty` (`:173`), and `AutoMoveRuleProperty.svelte:38-48,111-139`. Issue 07 changes this type first; read its delivered shape before starting.
- Say what "present" means in "exactly one of the two": use `!== undefined`, and require a non-blank `expr`. Settings keeps an unfinished row in the live rule (`auto-move.logic.ts:184-185`), so a freshly switched row has `expr: ''`; `ownedProperties` re-sanitizes on every run, so a blank `expr` must be dropped there too, silently.
- Boolean-only keys (`_organized`, `_archived`, `_favorite`) are guarded today by value type at load (`auto-move.logic.ts:167`). An `expr` has no type at load. Without a run-time check, `_archived: status` writes the text `"done"`, which PRD Decision 10 and `auto-move.logic.ts:116-121` exist to prevent. Add: a boolean-only key writes only a real boolean result. `todoist_project` stays refused (`:166`) for `expr` too.
- Volatile detection (`now()`, `file.mtime`, `file.ctime`) has to walk the AST. There is no exported walker (`findUnknownFunction` is private, `evaluator.ts:320-338`). Shapes to cover: `call` with callee `now`; `member` of `file` with property `mtime`/`ctime`; and dotted-callee `call` nodes where the static path is flattened into a string, such as `file.mtime.format("YYYY")` (`parser.ts:141-145`, `evaluator.ts:615-617`); plus `methodCall` receivers and args. A string search for `now()` misses `now ()` and `file.mtime.format(...)`. Reuse the AST walk for the "contains now()" date-time rule in Behavior 2.
- "Dropped on load and logged": `withValidProperties` (`auto-move.service.ts:92-96`) drops silently today and `sanitizeRuleProperties` is pure (no logger). Logging needs the service to compare entries before and after, or the sanitizer to report drops through a callback, as `findMatchingRules` does with `onError`. `ownedProperties` runs the sanitizer on every run (`:190`), so it must not log.

### Service (`auto-move.service.ts`)
- Evaluate once, before `updateNoteFrontmatter`. `writeRuleProperties` calls `propertiesToWrite` twice, once on the parsed file (`:315`) and once inside `mutate` (`:318`). The frontmatter writer says `mutate` "must be pure: it runs a second time when a tab opens during the read" (doc comment of `updateNoteFrontmatter`, `frontmatter-write.service.ts:92-96`). Evaluating inside either call would make `today()` or `now()` differ between the two passes. Resolve each owned `expr` to a literal value right after `ownedProperties(matched)` (`:254`), then feed literals to the existing planner.
- Evaluate only the owner's entry. `ownedProperties` picks the first rule per key (`auto-move.logic.ts:187-196`). Resolving after ownership avoids evaluating and logging shadowed rules.
- State what a failed or null result does to ownership. The Issue says "writes nothing for that key". By the existing rule ("owns it even when its `if-missing` ends up writing nothing", `auto-move.logic.ts:181-183`) a failing owner would still block a lower rule. That is the consistent reading; say it.
- The record is built from the pre-move path and stays so. `file.folder`, `file.path`, `file.name` in an `expr` are the values before the move (`auto-move.service.ts:207` before `moveItem` `:244`). A rule that moves and also computes `area: file.folder...` sees the old folder. Document it; same for `resolveDestination` which already uses this record (`:224`).
- Log-once set: `reportedWriteFailures` is keyed by `rule.id` for write failures (`:49,325-335`). Reusing it would let an expression failure suppress a later write-failure message for that rule. Add a separate set and clear it in `resetAutoMove` (`:349-350`).
- Logger choice: `error()` also calls Sentry (`src/lib/utils/debug.ts:27-33`). A `null` result is routine (missing property), a throw is a rule bug. Pick `error` for throws and `debug` (or one `error`) for null, and state it. Test pattern to copy: `auto-move.service.test.ts:825-835`.
- Results the Issue does not cover, each needs a rule: `NaN` (`due + "7d"` on a string or missing `due` gives `NaN`, because `+` only does date math when the left side is a `Date`, `evaluator.ts:249-251,277`; `number("x")` also gives `NaN`); an `Invalid Date` (`date("junk")` returns `new Date("junk")`, `evaluator.ts:379`, and `toISOString`/formatting would throw or print `Invalid Date`); display objects (`link()`, `badge()`, `isDisplayValue`, `expression.types.ts:118-125`); plain objects (`file.properties`, `evaluator.ts:207-213`); a list of mixed items. Simplest: only string, finite number, boolean, valid Date, or a list of those; everything else is "no value" and logged once. Normalize list items to strings (`Property.value` is `string[]`, `properties.types.ts:9`; the parser maps items with `String`, `properties.logic.ts:177-181`), or `always` compares `[1,2]` with `["1","2"]` and never matches (`sameValue`, `auto-move.logic.ts:199-205`; harmless because `updateNoteFrontmatter` returns early on identical bytes, `frontmatter-write.service.ts:128-129`, but it re-plans every save).
- `add` plus `expr`: the items of the result are added, but Issue 07 allows only a string or `string[]` for `add`. A number or boolean result under `add` is undefined in both Issues. Pick "skip and log" to match 07's rule for a non-list current value.
- Date format: "the full ISO date and time" is ambiguous. `toISOString()` gives UTC with milliseconds and `Z`. The app's frontmatter date detector does not accept that (`ISO_DATE_REGEX`, `properties.logic.ts:40`, allows only `YYYY-MM-DD` with optional `THH:mm[:ss]`), so such a value reads back as text, not a date. Other writers use local `YYYY-MM-DDTHH:mm:ss` (`quick-capture/note-composer.logic.ts:57`, `one-on-one/one-on-one.logic.ts:56`). `formatDate(date, fmt)` in `src/lib/utils/date.ts:42` (dayjs) does it. The writer emits both forms unquoted (`yaml-quoting.logic.ts:99,122-127`). I recommend local `YYYY-MM-DDTHH:mm:ss` and writing the Date-only form in local time, not `toISOString().slice(0,10)` (that would be the UTC day).
- A string result that looks numeric (`file.basename` of `2024`) is quoted by the serializer (`yaml-quoting.logic.ts:90-120`), which keeps it text. A number result is written as a number. This is the right behavior; add one test.
- `always` with `today()` is allowed and flips the value at the first save of each day (only `now()`, `mtime`, `ctime` are refused). That follows from the owner's rule; the docs should say it.

### Real file stats (Behavior 5)
- "When it exists" is not enough. `updateNoteInIndex` builds a record with `existing?.mtime ?? 0`, `ctime ?? 0`, `size ?? 0` for a path not yet indexed (`collection.service.ts:154-160`), and `registerCollectionNoteChangeConsumer` calls it on every Markdown upsert (`:182-185`). A note created this session therefore has a record with `mtime 0`, `ctime 0`, `size 0` until the Rust delta lands. The delta path is the throttled `vault-index-updated` refresh (2-10 s, `vault.store.svelte.ts:31`), while the rule timer fires after `debounceMs`, default 3000 (`settings.store.svelte.ts:112`). The headline use case, `created: file.ctime` with `if-missing`, would then stamp `1970-01-01` permanently. Treat `mtime <= 0` (and `ctime <= 0`) as "no record" and fall back to now, now, content length. `size` has the same zero-record case; an empty real file is size 0 and a fallback to content length there is harmless.
- Even with a real record, stats lag the save by up to the refresh window: `updateNoteInIndex` keeps the old values while editing (`collection.service.ts:145-148` doc). `file.size` and `file.mtime` in a rule are the last indexed values, not the bytes just saved. The docs sentence "the file's real values once the note is indexed" should say "as of the last index refresh".
- Which record: look up by the pre-move `filePath`. The old record still exists at evaluation time. Only `mtime`, `ctime`, `size` come from the index; properties still come from `content` (the tab or disk), so keep `buildNoteRecord(filePath, content, mtime, ctime, size)` and change only the three arguments. This also matters for `projectDerivedProperties` parity (`collection.logic.ts:53-77`), which a swap to the index record would break.
- Put the "stats from index or fallback" choice in a pure function in `auto-move.logic.ts` (takes the index record or undefined, plus `now`), so the service and the Settings preview share it. Do not mock the store in tests (CLAUDE.md rule 1); set a real record with `collectionStore.setPropertyIndex`.

## 3. What makes a Behavior harder than it looks

1. Behavior 5 stats: zero-valued records for new notes (above) are the main trap. Without the `<= 0` fallback the "stamp a creation date once" use case writes 1970-01-01.
2. Behavior 4 in Settings: "not saved" cannot be done by the current stateless row; it needs draft state and re-checks on key and mode changes.
3. Behavior 4 volatility detection: needs a new AST walker that also understands dotted-callee `call` nodes; not a string test.
4. Behavior 2: the Date branch has no precedent in the rule writer (everything today is a literal). Invalid Date, NaN, objects, display values and mixed lists each need an explicit decision, or a result can crash `toISOString` or write `.nan`.
5. DST: `today() + "Nd"` is millisecond arithmetic in the engine. It is an engine property, shared with filters, so not fixable in this Issue without changing Collection behavior; the docs example and a test date should avoid the problem, and the limit should be stated once.
6. Behavior 6 preview: needs the active tab's content with its own record; a non-note active tab must be handled.
7. Example 3 does not run (section 1, item 9).
8. Evaluation order and ownership: values must be resolved to literals outside the `mutate` closure and only for the owning entry.
