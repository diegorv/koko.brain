# Validation 03: scout 05 (icons, colors, visual keys) and scout 06 (after-save trigger)

Adversarial pass over `scout-05-icons-colors-visual-keys.md` and `scout-06-trigger-after-save.md`. Both reports exist. Every claim below was checked by opening the cited code at HEAD `2e2cc5b60`. Read-only: nothing was run.

Verdict: both scouts are mostly right on mechanics. The serious errors are about the Properties panel write path (scout 05), alias collisions (scout 05), the Auto Move starvation reasoning (scout 06) and what the raw-write ratchet enforces (scout 06). The biggest gap in both reports: Auto Move's icon action already behaves as "always set" on every save, and it deletes colors. That makes it conflict with any new rule that writes `_color`/`_title_color`.

## 2. Confirmed key claims

Scout 05:
- Icons and colors are frontmatter-only, keys `_icon`, `_color`, `_title_color`, with aliases mirrored in Rust and TS (`src-tauri/src/vault/aliases.rs:9-27`, `src/lib/utils/frontmatter-aliases.ts:6-23`). ADR 0027 records that the sidecar JSON was dropped (`docs/adr/0027-...md:68`).
- `setFrontmatterIcon` / `setFrontmatterIconColors` overwrite, and they delete the color keys when no color is passed (`frontmatter-icon.service.ts:26-31,57-76`). Auto Move passes `rule.icon.color` / `rule.icon.textColor`, which may be undefined (`auto-move.service.ts:209`), so it removes existing colors.
- `upsertProperty` matches the exact key, and the parse canonicalizes keys (`frontmatter-icon.service.ts:20-24`, `properties.logic.ts:297`).
- `setIconForPath` handles Markdown and directories only (`file-icons.service.ts:118-145`). A directory ensures a `---\n---\n` folder note routed through `applyNoteChange` (`:98-110`). Folder notes are indexed under the directory key too (`:214-222,259-266`).
- The incremental updater pre-checks `/icon|color/` before parsing YAML (`file-icons.logic.ts:83-91`).
- Value rules: closed pack list, bare name read as lucide, colors rejected on `;` or `url(` (`file-icons.logic.ts:19-48,149-179`). `iconColorCss` maps the 9 palette names to `var(--type-*)` for `_color` only (`:219-223`).
- Resolver order: own icon first, else the type icon with own colors laid over it. Own colors alone apply only together with an icon (`icon-resolver.ts:64-77`). Every renderer except the Rail pin dot needs `resolved.icon` before it uses `color` (`EditorView.svelte:56-61`, `FilesNavigator.svelte:483-489`, `NoteRow.svelte:52-56,77-81`). The Rail pin color uses `_color` without an icon (`Rail.svelte:167`).
- The IconPicker offers hex swatches (`IconPicker.svelte:51-61`). `color-presets.ts` is a separate 7-name palette (`color-presets.ts:2-10`).
- Auto Move rule icons are stored in `.kokobrain/auto-move-rules.json` with the field `textColor`, while frontmatter uses `_title_color` (`auto-move.types.ts:2-11`).
- Auto Move's lossy pre-check and quiet skip (`auto-move.service.ts:199-207`). Icon helpers toast on `FrontmatterWriteError` (`frontmatter-icon.service.ts:38-50`).
- No `cssclasses` exists in `src/lib` or `src-tauri/src` (grep: no hits).

## 3. Missed

1. **Auto Move's icon is already an "always set" action that also deletes colors, and it fights manual edits and any second rule.** `evaluateAndMove` calls `setIconForPath` on every save of a matching note, "even if already in destination" (`auto-move.service.ts:199-214`). With `withIconColors` (`frontmatter-icon.service.ts:26-31`), this gives three consequences:
   - A user who picks a different icon or a color in the IconPicker on a note matched by an icon rule gets it reverted about `debounceMs` later. The picker writes through `setIconForPath`, then `updateNoteFrontmatter`, then `notifyAfterSave`, which re-arms Auto Move.
   - A new frontmatter rule that sets `_color` on a note also matched by an Auto Move icon rule without a color never converges. Auto Move removes `_color`, the new rule sets it again, and each cycle re-notifies. The result is a loop every few seconds, with one File History snapshot and one FTS/semantic reindex per cycle.
   - This is concrete support for the owner's one-engine preference. The Auto Move icon must become per-key actions with explicit fill/always semantics under the same conflict policy, or the two features will fight.
2. **Issue 169 (`ready-for-agent`) changes the file-icons consumer.** `.scratch/open-itens/issues/169-file-icons-read-frontmatter-only-through-rust.md` makes the Rust entries (`vault-index-updated` / `get_index_delta`) the only reader of the icon index and deletes the TS raw-text parse in `updateFrontmatterIconForFile`. Scout 05's "ready-made hook point (consumer fan-out)" therefore points at code that is planned to change. Do not hang a rule trigger on the `file-icons` consumer. Issue 169 also documents that today's two readers can disagree, so an icon can render differently at vault open than after a save.
3. **Non-Markdown saves reach the observers (Issue 054, `ready-for-agent`).** `writeTab` calls `notifyAfterSave` for any open path, including kanban and canvas (`editor.service.ts:187-196`). Auto Move filters only `.view` (`auto-move.service.ts:97`). A rule engine copying that observer must filter with `isMarkdownFile` (`fs.logic.ts:65-68`). Scout 06 section 6.5 says to skip `.view` only.
4. **Watcher gaps that affect an "external YAML edit" trigger.** Scout 06 did not read `watcher-handler.service.ts`.
   - Any changed file saved by the app within the last 15 s makes the whole batch skip (`areAllRecentSaves`, `watcher-handler.service.ts:50`; TTL `editor.hooks.ts:24`). An external edit right after an in-app save produces no `applyNoteChange` at all.
   - More than 10 Markdown changes in one batch (`INCREMENTAL_THRESHOLD = 10`, `:13,60`) take the full-rebuild branch, which calls no per-file `applyNoteChange` (`:76-83`). A consumer-based trigger therefore misses bulk external changes such as a git pull or a sync.
5. **Path-change events arrive per folder, not per note.** A folder move or rename arrives once, for the folder; descendants move implicitly (`path-change.service.ts:43-47`). A move or rename trigger must expand the descendants itself and read their content. The payload has none.
6. **The `edit` source runs the consumers on unsaved text.** The layout content effect (1 s) calls `applyNoteChange({source:'edit'})`, which also refreshes the Rust index (`index-updater.service.ts:24-40`, policy `note-change.service.ts:91`). The following save of identical bytes is a dedupe hit and skips the TS consumers (`:229-230,261`), but observers still fire. A note-change-consumer trigger would therefore act on unsaved typing and then never see the save.
7. **A per-path "own write in flight" guard can swallow a user save.** `saveFileByPath` chains behind a pending save of the same path (`editor.service.ts:171-179`). An autosave already queued for user content fires `notifyAfterSave` while the guard is set, and a path-only guard would drop it. Guard on the exact bytes the engine wrote (compare `content`), not on the path. Scout 06 section 5 proposes the path set.
8. **A newly created note is not covered by "on save" either.** A note-creator note opened in a tab is clean, and `writeTab` returns early for a clean tab (`editor.service.ts:189`). Nothing reaches the observers until the user types. Only the deep-link silent create and Quick Capture paths notify (`deep-link.service.ts:337`, `deep-link-actions.ts:216`).
9. **Stale lossy pre-check in Auto Move.** The pre-check reads the saved `content` (`auto-move.service.ts:203`), while `updateNoteFrontmatter` checks the fresh `base`. If the user adds a YAML comment during the debounce, the write throws and `setFrontmatterIcon` toasts (`frontmatter-icon.service.ts:45-48`). A rule engine must pre-check against the fresh content, or catch `FrontmatterWriteError` without toasting.
10. **Store copy cost (matters only if "apply rules to existing notes" is in scope).** `fileIconsStore.updateFrontmatterIcon` copies the whole map on every call (`file-icons.store.svelte.ts:43-51`). `setIconForPath` writes the store a second time after the consumer has already done so (`file-icons.service.ts:129-132`). A bulk pass over N notes is O(N^2) map copies through this helper.
11. **Related open Issues not cited by either scout.**
    - 170: icon write edge cases. `removeFrontmatterIcon` can report success without writing.
    - 008 / 105: a Properties panel no-op commit arms the skip flag, so the next panel edit can delete typed text. This matters for a property-change trigger that rewrites what the panel just wrote.
    - 082: a failed Auto Move should name the note.
    - 095: CRLF notes; affects the byte-equality no-op check.
12. **Not verified by me.** ADR 0027 says system (`_`) fields are excluded from the Rust properties reverse index (`docs/adr/0027-...md:115`). The on-save path evaluates `buildNoteRecord`, which keeps every parsed key, `_icon` included (`collection.logic.ts:22-43`). If any trigger evaluates from Rust-served records instead (`project_note_record`), check that `_` keys are present there before allowing conditions on `_icon` / `_color`.

## 4. Corrections a designer must know

1. **Properties panel edits are in-memory plus a 500 ms autosave** (`properties.service.ts:104`). They are not an immediate write. An "on property change" trigger built on the after-save observer fires about 500 ms after the panel edit, or after the YAML edit in CodeMirror. "Immediately" needs a new seam at `syncExternalContentToEditor` / `onContentChange` in `core/editor`, registered the same way as the other consumer registries.
2. **Two populated alias twins are refused, not merged** (R2). Treat `alias-collision` like every other `LossyFrontmatterReason`: pre-check against the fresh content and skip quietly.
3. **Fill-if-missing needs a new primitive.** The icon helpers cannot express it: they overwrite `_icon` and delete absent colors. Write a pure `Property[] -> Property[]` per action that matches the canonical key and never removes keys it does not own, and pass it to `updateNoteFrontmatter`.
4. **Auto Move's icon action must be folded into the same per-key model** (Missed 1). Otherwise any rule touching `_color` / `_title_color` on a note matched by an icon rule loops, and manual icon edits keep being reverted.
5. **Do a semantic no-op check before writing.** Compare the canonical values the action would set against the current ones, and skip the call when nothing changes. Relying on `next === base` re-serializes non-canonical notes once (R9). That costs an extra save, snapshot and reindex, and a caret jump on the active note while Issue 001 is open.
6. **Filter targets with `isMarkdownFile`**, not only `isViewFile` (Issue 054).
7. **Do not use the `file-icons` note-change consumer as a trigger** (Issue 169 will rewrite it). Avoid note-change consumers for triggers in general: they see unsaved `edit` content, skip saves on a dedupe hit, and miss watcher self-save windows and bulk rebuilds.
8. **Move and rename events are per folder, with no content.** The engine must expand descendants and read each note. Pending save-trigger timers keyed by the old path need re-keying or cancelling on `pathChanged`. Auto Move has no code for this today.
9. **An own-write guard, if needed, must match bytes, not paths** (Missed 7).
10. **The pack preload is not a risk** through `updateNoteFrontmatter` (R3). Color vocabulary still differs per key: `_color` resolves palette names to theme tokens, `_title_color` uses them as raw CSS keywords, and the picker writes hex. A rule UI must say which vocabulary applies to which key, and validate with the same `;` / `url(` rule the readers apply (`file-icons.logic.ts:162-164`).
11. **Starvation is not the timing risk for an Auto Move-style debounce; writing mid-typing is** (R4). Auto Move fires about 3 s after a forced 10 s save, so background writes to the active note while the user types are the real hazard. Until Issue 001 lands, any trigger that writes the active note shifts the caret.
