# Validation 04: scouts 07 (property-change trigger) and 08 (create / move / rename triggers)

Adversarial pass over `scout-07-trigger-property-change.md` and `scout-08-trigger-create-move-rename.md`. Both reports exist. Every load-bearing claim was checked against the code at HEAD `2e2cc5b60`. Read-only: nothing was run.

Verdict in one paragraph: the scouts' mechanics are mostly right (sync consumer registries, debounce floors, the lossy guard, the self-write echo through `notifyAfterSave`, `applyPathChange` ordering). Three claims are wrong in ways that change the design. (a) The note-change consumer does not see every property change: the watcher's full-rebuild branch, the 15 s self-save skip, `duplicateItem` and the Rust-delta patches bypass it. (b) Diffing the projected record does not leave body typing out, because `tags` is merged with inline body tags. (c) The lossy guard does not catch a missing closing fence or an empty `---\n---` block, and a write then stacks a second frontmatter block. Scout 08 also missed that Auto Move already chains moves through its own icon write.

## 1. Refuted

## 2. Confirmed key claims

Scout 07:
- No signal carries a per-key old/new value. `NoteChangeConsumer.upsert(path, content)` has no source and no previous content (`note-change.service.ts:26-33`). `UpdateResult` carries paths and a boolean (`src-tauri/src/vault/index.rs:33-54`). `VaultFilesChangedPayload` is `{ paths }` only (`src/lib/contracts/generated/VaultFilesChangedPayload.ts:7`).
- `markIndexed` runs before the fan-out (`note-change.service.ts:233` vs `:268`). `notifyAfterSave` runs `applyNoteChange` synchronously before the observers (`editor.hooks.ts:81` vs `:85-91`), so after-save observers never see the old record.
- `updateNoteInIndex` keeps only mtime, ctime and size from the existing record (`collection.service.ts:152-162`). `updateRecord` copies the map (`collection.store.svelte.ts:41-46`).
- Consumer registration order: collection, then file-icons, then the path-change consumers (`app-lifecycle.service.ts:258-261`). `fanOut` runs in registration order, synchronously, and isolates failures (`note-change.service.ts:167-179`). Option A's order dependence is real and silent.
- Panel text, number and date fields commit on every keystroke (`src/lib/features/properties/PropertyField.svelte:64-82, 135-143`). `commitChanges` refuses lossy frontmatter, arms `skipNextParseFor` and syncs with `'frontmatter'` (`src/lib/features/properties/properties.service.ts:83-109`).
- Meta-bind writes go through `dispatchMetaBindUpdate` as a CodeMirror transaction (`src/lib/core/markdown-editor/extensions/live-preview/widgets.ts:868-895`). Number and date inputs commit on blur or Enter only (`:1078-1080`).
- Timers: body 2000 ms with a 10 s maxWait, frontmatter 500 ms with no maxWait (`editor.service.ts:227, 230`). They are mutually exclusive (`:243-251`).
- The `edit` source covers only the active tab, with a 1 s debounce (`+layout.svelte:147-167`), and its dedupe guard sits in `updateIndexesForFile` (`src/lib/app/lifecycle/index-updater.service.ts:29`).
- Kanban writes no note frontmatter: no `updateNoteFrontmatter`, `writeTextFile` or `rebuildContent` anywhere in `src/lib/plugins/kanban`.
- The `updateNoteFrontmatter` contract: `mutate` must be pure, callers must serialize per path, an unchanged result is a no-op, and the tab branch saves at once and keeps body edits (`frontmatter-write.service.ts:84-163`).
- Auto Move's lossy precheck for icons (`auto-move.service.ts:201-207`) and its 3 s default debounce (`settings.store.svelte.ts:112`, per scout; not reopened).

Scout 08:
- `applyPathChange` is the one owner of path changes. Its consumers run synchronously after `diskOp` and `updateTabAfterRenameOrMove`, before the link rewrite, the tree move, `rename_note` and `rename_in_search_index` (`path-change.service.ts:162-227`). A folder is reported once (`:41-48`). Deletes arrive with `to === null`.
- The only callers of `renameItem` / `moveItem`: `FilesNavigator.svelte:176, 285`, `NoteRowMenu.svelte:135`, `type-definitions.service.ts:224`, `event-calendar.service.ts:734`, `sync-now.service.ts:960`, `mod-vault.service.ts:60, 67`, `auto-move.service.ts:190`. Trash restore uses a raw `rename` (`src/lib/core/trash/trash.service.ts:126`) and indexes with source `restore` (`:257`), not through `applyPathChange`.
- Creation paths: `create_note` callers are exactly `note-creator.service.ts:103`, `fs.service.ts:208`, `mod-vault.service.ts:103` and `closed-note-writer.service.ts:76`, with sources `create` / `fs` (`note-change.service.ts:93-94`: consumers always, no Rust IPC, no mark). ## 3. Missed

1. **Second content blocker: Issue 005 (empty `---\n---` block).** Templates and folder notes (`file-icons.service.ts:100` writes `'---\n---\n'`) produce blocks the regex cannot see, and every writer stacks a second block (R3). A create trigger applied to template output and a fill-if-missing rule hit this on every such note. Issue 005 is a blocker next to 001.
2. **Stale content in debounced evaluation.** Auto Move captures `content` at save time and evaluates it 3 s later (`auto-move.service.ts:116-119, 152-154`). `updateNoteFrontmatter` re-reads the base for the WRITE (`frontmatter-write.service.ts:116-122`), but the MATCH decision still uses the old bytes. A rule engine should rebuild the record from the current tab content, or from disk, at fire time, for every trigger. Scout 08 says this for path changes only.
3. **Auto Move filters only `.view`** (`auto-move.service.ts:97`). `.canvas` and `.kanban` saves are evaluated, and a folder-keyed rule can move them. A shared rule core must filter Markdown explicitly, and the Auto Move behaviour is a latent bug worth recording.
4. **Icon actions are not per-key fill-if-missing today.** `setFrontmatterIcon` upserts `_icon` and REMOVES `_color` / `_title_color` when no color is passed (`frontmatter-icon.service.ts:26-30, 64-66`). It also toasts on refusal (`:34-49`) and updates `fileIconsStore` directly (`file-icons.service.ts:127-133`). A rule writing `_icon`, `_color`, `_title_color` as plain properties through `updateNoteFrontmatter` gets the icon store refreshed by the file-icons consumer on the save fan-out (`file-icons.service.ts:240-257, 300-304`). So the rules feature does not need `setIconForPath`, and should not reuse it if "fill only if missing" must apply per key.
5. **Own-change marks are module-private.** `ownPathChanges` lives inside `event-calendar.service.ts`, and Todoist's rename (`sync-now.service.ts:960`) carries no mark at all. Any "ignore machine renames" policy needs a new shared marker in `core/filesystem`: a core API change, not a local pattern copy.
6. **A dirty tab plus an external edit flips the baseline.** `reloadExternallyChangedTabs` keeps the dirty tab (`editor.service.ts:422-430`), but `incrementalUpdateFiles` still upserts the DISK content into the consumers (`watcher-handler.service.ts:115-119`). The property index then holds the disk version until the next save puts the tab version back. With Option A, both transitions look like user property changes.
7. **Evaluation never needs the index.** `EvalContext` is a single record plus formulas (`src/lib/features/collection/expression/evaluator.ts:11-16`). `buildNoteRecord(path, content)` is enough for every trigger, including a path change mid-flight, where the index has no record at `to` (R4). This removes scout 08's worry about reading the index during `applyPathChange`. Only Option A's diff baseline needs the index.
8. **Auto Move's hook is dynamic.** It is registered by `toggleAutoMoveHook(true)` (`app-lifecycle.service.ts:445`), unregistered by the settings toggle and by `resetAutoMove` (`auto-move.service.ts:134-146, 218-231`). A rules feature that piggybacks on Auto Move's observer would be switched off with Auto Move. A shared core needs its own registration, or an explicit decision that the two toggles are one.
9. **Meta-bind is caret-safe, rule writes are not.** Meta-bind dispatches a mapped CodeMirror transaction (`widgets.ts:890-893`). Rule writes go through `syncExternalContentToEditor`, then the content-sync effect, then `replaceDoc(content, cursorPos)` with the old offset (`src/lib/core/markdown-editor/MarkdownEditor.svelte:625-648`). That path also sets `isExternalEdit` (`:642`), so a rule write does not re-enter `onContentChange`: no keystroke-pipeline loop, only the save echo.
10. **Creation does not imply a save.** A note from `openOrCreateNote` or `createFile` that the user never edits fires no after-save at all. Only the create upsert (`note-creator.service.ts:118`, `fs.service.ts:216`) or a pre-write transform reaches it. An "on save only" engine leaves untouched new notes unprocessed indefinitely.

## 4. Corrections a designer must know

- **Pick the trigger hook by its inputs, not by "sync vs async".** Both registries are synchronous and schedule-only. The after-save observer sees saved bytes from `notifyAfterSave` only. The note-change consumer also sees `edit` (unsaved), `watcher`, `task`, `create` / `fs` / `restore` and link rewrites, has no `source`, and misses the cases in R1. Neither sees a watcher full rebuild, and neither sees path changes (those come through `registerPathChangeConsumer`).
- **Do not diff the projected record.** Diff raw frontmatter: `parseFrontmatterProperties(content)` keyed by canonical key, or exclude `tags`, `organized`, `archived`, `favorite` and the relationship keys explicitly. Otherwise body typing of `#tags` fires property-change rules (R2).
- **The pre-write guard must be "block found AND not lossy".** `detectLossyFrontmatter(content) === null` is not enough. Content that starts with `---` but matches no block (missing closing fence, or an empty `---\n---`) must be skipped, or the engine writes a second frontmatter block (R3, Issue 005).
- **"No previous record" is not "created".** It also means moved, renamed, duplicated, or not yet indexed (R4). Create needs its own trigger: the pre-write transform in `openOrCreateNote` / `createFile`, or the `create` / `fs` upserts. Move and rename need `registerPathChangeConsumer`.
- **A rename cascades into backlink sources for any consumer-based trigger.** Their frontmatter wikilinks change (R8). A design that reacts to property changes through the consumer will evaluate notes the user never touched. Either accept that (the rules are idempotent) or skip that echo, which today needs a source / origin argument added in `core/` (`note-change.service.ts:26-33, 167-179`).
- **Write echoes already chain today** (R6). Issue 01's "chaining happens through the save" is the existing behaviour, not a new one. Any always-set action can oscillate, so an in-memory fixed point with a pass cap and one write per evaluation (scout 08 §5.1) is needed whichever hook is chosen.
- **Re-read the content at fire time** for both match and write (Missed 2). Re-resolve the path at fire time, because timers keyed by the old path go stale on move.
- **Blockers: 001 (caret) and 005 (empty block)** for any trigger that writes to an open or template-born note. A pre-write create transform avoids 001, but not 005 when the template carries an empty block.
- **Unverified here:** whether `buildPropertyIndex` can finish before the step 9 daily-note create in practice (timing only, not exercised). I also did not verify Svelte focus behaviour when a rule write re-parses the panel input the user is typing in (scout 07 §4.1).
