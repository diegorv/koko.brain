# Validation 05: scout-09 (other frontmatter writers) and scout-10 (overlapping features)

Adversarial pass, read-only, HEAD `2e2cc5b60`, 2026-11-10. Both reports exist. Each load-bearing claim was re-opened at the cited code. Nothing was run; "by reading" means traced through source, not executed.

## 1. Refuted (claim, why, correct evidence)

R1. **scout-09 H1: the Auto Move vs color loop needs a rule that "always sets" `_color`.** Wrong scope. The loop also happens with **fill-if-missing**. Auto Move's icon write *deletes* `_color` / `_title_color` whenever the rule's icon has no color (`frontmatter-icon.service.ts:26-31`, called with `rule.icon.color` / `rule.icon.textColor` at `auto-move.service.ts:209`, both optional in `auto-move.types.ts:7-10`). So after each Auto Move pass the key is missing again, and a fill-if-missing rule fills it again. Both writes change bytes, so `next === base` (`frontmatter-write.service.ts:129`) never stops it. The cycle repeats every `debounceMs` (default 3000, `settings.store.svelte.ts:112`). The same loop happens on `_icon` when a rule sets an icon that differs from the Auto Move rule's `pack:name` (`upsertProperty` at `frontmatter-icon.service.ts:65`). The semantic setting does not prevent it. Only key ownership does.

R2. **scout-09 3.1: "a note whose id is unknown is treated as new" (`projects.logic.ts:172-282`).** Not what the code does. Only notes with `projectId === null` can become new projects (`projects.logic.ts` candidates filter: `n.projectId === null && !known.has(n.relPath) && parentOf(n.relPath) === input.folder && isInSyncScope(...)`). A note with an unknown non-null `todoist_project` is never a candidate; it is just not matched to any tree project. Clearing the key on an existing project note does not re-create it either: `known` holds every live base's `relPath`, so the note is excluded, and its project becomes "named by 0 notes" and is skipped (`if (!project || notes.length !== 1) continue`). The deny-list advice for `todoist_project` still holds, because a rule changing it re-parents tasks in ways nobody traced. But the stated mechanism is wrong.

R3. **scout-09 section 5 and 3.2: `createFile` / typed-note / event creation report `applyNoteChange('create')`.** They don't. `fs.service.ts:216` uses `source: 'fs'`. Only `openOrCreateNote` (`note-creator.service.ts:118`), mod `ctx.vault.create` (`mod-vault.service.ts:107-113`) and Todoist pull (`closed-note-writer.service.ts:79`) use `'create'`. Rename, move and delete through the file explorer also use `'fs'` (`note-change.service.ts:13-14,19`). Option (a) of section 5 ("a post-create NoteChangeConsumer for source create") would miss Cmd+N, "+ New here", Quick Switcher create, typed notes and calendar events. It also cannot tell create from rename by source, and the consumer interface has no `source` field anyway (`note-change.service.ts:26-33`, confirmed).

R4. **scout-09 section 5: creation has "no choke point"; explicit organization is "copy-pasted into five builders"; option (b) means "8+ call sites".** Overstated. Explicit organization has 14 call sites in 13 files (grep of `applyExplicitOrganization|withUnorganizedFlag`). But almost all UI creation funnels through two TS primitives: `createFile` (`fs.service.ts:198`) and `openOrCreateNote` (`note-creator.service.ts:78`). Periodic notes, quick capture, templates, 1:1, deep-link non-silent and typed "New X" are among their callers. Only 4 sites call Rust `create_note` at all (`note-creator.service.ts:103`, `fs.service.ts:208`, `mod-vault.service.ts:103`, `closed-note-writer.service.ts:76`). The remaining raw creates are the deep-link overwrite, silent create and capture (`deep-link.service.ts:310,336`; `deep-link-actions.ts:215`), the folder-note placeholder (`file-icons.service.ts:103`), template scaffolding (`templates.service.ts:118`) and the watcher. The real blocker for shaping content inside those primitives is layering, not the call-site count (see C6).

R5. **scout-10 2.3: "periodic notes ... do not all go through [`openOrCreateNote`]".** Periodic notes do go through it (`periodic-notes.service.ts:5,53`; scout-10 2.7 says so itself). What actually bypasses it is `createFile` and the raw paths in R4.

R6. **scout-09 H2 is presented as a rule-engine hazard. It is an open, test-confirmed Properties panel bug.** Open Issue `.scratch/open-itens/issues/105-minor-write-races-are-closed-autosave-during.md`, section "Properties panel skip flag swallows the only re-parse after a quick frontmatter edit" (`:136-155`), has the verdict CONFIRMED_BY_TEST, severity data-loss, bucket corner. Its fix sketch is: store the content the commit produced and skip only when the parsed content equals it, or rebuild from a fresh parse of the tab. Issue 008 is the no-op-commit half. Any foreign write inside the 300 ms window already triggers it today: a lifecycle Cmd+D, Todoist `writeProjectId` on an open tab (`sync-now.service.ts:900`), or Auto Move's icon. The rule engine's property-change trigger turns it from a corner case into a routine one. The fix belongs to the panel (Issue 105), not to the rule engine, which scout-09 options 1-3 imply.

R7. **scout-10 2.7 and 4.5: the templates plugin "scans `_templates/`"; exclude `_templates`.** The folder comes from settings, `settingsStore.templates.folder`, default `_system/templates` (`settings.store.svelte.ts:98`; `templates.service.ts:24,79`). The `_templates/` text is a stale comment and an example in `22-auto-move.md:103,173`. A default exclusion must read the setting, as Todoist does (`anchor.logic.ts:104-110`), and not hard-code `_templates`.

R8. **Minor line drift (does not change any conclusion):** `requestPromptIndexRefresh` is at `lifecycle.service.ts:34,50,68`, not `:33,48,67`. `generateLifecycleRules` is called at `auto-move.service.ts:156`, not `~170-173`. The event calendar `enqueue` is at `event-calendar.service.ts:506` (`:355-398` is the queue state and comments). `setIconForPath` updates the store at `file-icons.service.ts:130`. The calendar's keys also include `end_date` (`event-calendar-event.logic.ts:50`), which scout-09 omitted.

## 2. Confirmed key claims

- `updateNoteFrontmatter` contract (`frontmatter-write.service.ts:84-163`): `mutate` must be pure and can run twice (`:95`, restart `:148`). The closed branch has no per-path serialization ("callers must serialize", `:96-97`). The open tab is patched with `syncExternalContentToEditor(..., 'none')` and saved at once through `saveFileByPath` (`:131-133`), which is serialized per path by `saveTails` (`editor.service.ts:163-179`). A closed note calls `notifyAfterSave` (`:161`). A byte-equal result returns early with no write and no observers (`:129`).
- A no-op `mutate` is NOT free: `rebuildContent` re-serializes the whole block (`properties.logic.ts:689-697`). The first write to non-canonical YAML changes bytes (`28-mods.md:180`). A rule must decide "nothing to do" before calling the writer, or accept one canonicalizing write.
- `withIconColors` removes colors that are not passed (`frontmatter-icon.service.ts:26-31`). `setIconForPath` is always-set (`file-icons.service.ts:118-133`). Auto Move applies the icon on every matching save, even when the note is already in place (`auto-move.service.ts:199-214`), and skips quietly on lossy frontmatter (`:203-207`).
- Auto Move: rule model `{id,name,expression,destination,enabled,icon?}` (`auto-move.types.ts:14-27`). First match wins (`auto-move.logic.ts:17-35`). One after-save observer, gated by `settingsStore.autoMove.enabled` (`auto-move.service.ts:96-127`). `excludedFolders` defaults to empty (`:28-31`). Only `.view` is skipped (`:97`). Lifecycle rules are appended after user rules (`:156-157`) and come from `_archive_to` (`type-lifecycle-rules.ts:20-60`).
- Properties panel: `commitChanges` rebuilds from `propertiesStore.properties` (`properties.service.ts:83-108`) and arms the skip flag (`:100`). The re-parse is debounced 300 ms and consumes the flag once (`PropertiesView.svelte:104-118`). The H2 sequence is correct: a foreign write inside 300 ms clears timer A before it consumes the flag, so timer B consumes it and skips the parse of the foreign content.
- Lifecycle writers use `updateNoteFrontmatter` and nudge the index (`lifecycle.service.ts:30-93`). The archive toggle depends on after-save so that Auto Move runs (`:87-90`).
- Todoist: `writeProjectId` writes only `todoist_project`. On an open tab it patches with `'body'` and does not save; otherwise it goes through `updateNoteFrontmatter` (`sync-now.service.ts:887-911`). Project renames go through `renameItem` (`:960`). The sync scope excludes `_system/`, `.kokobrain/`, `.view` and the templates folder (`anchor.logic.ts:104-110`). The after-save observer arms a 5 s cycle for notes with anchors (`sync-scheduler.service.ts:26,90-98`, `MIN_GAP_MS` 30 s at `:24`). Unanchored task edits locate by line number plus expected text and go stale on a shift (`task-line-edits.logic.ts:131-136`).
- Mods: `onNoteSaved` runs in `setTimeout(0)` after every save (`mods-host.service.ts:554-576`). `ctx.vault.write` refuses a dirty tab and then calls `notifyAfterSave` (`mod-vault.service.ts:118-135`). `ctx.app.updateNoteFrontmatter` is exposed (`mod-app.service.ts:53`).
- Type rename: raw rewrite of open tabs plus Rust `propagate_type_rename` (`type-definitions.service.ts:221-241`), with no `notifyAfterSave`. Rules on `_type` are not re-evaluated, and expressions that name the old type are not rewritten.
- Raw-write ratchet inventory (`src/tests/lib/raw-write-ratchet.test.ts:24-51`) is accurate for TS `writeTextFile(`. It does not cover Rust writers, CodeMirror transactions or `core/filesystem` (owner dir exempt, `:17`).
- scout-10: `TypeMetadata` has 14 fields and no property map (`type-definitions.logic.ts:6-35`). Icon resolution order: a note's own icon wins; otherwise the type icon with the note's own colors laid over it (`icon-resolver.ts:64-77`); `Type` notes are skipped (`:93-98`). Nested YAML in a definition note makes every writer refuse it (`properties.logic.ts:357-363,382`), so putting rules in type notes is not viable. `withUnorganizedFlag` is a hard-coded fill-if-missing (`explicit-organization.logic.ts:29-37`). A missing `_organized` reads as organized in Rust (`src-tauri/src/vault/entry.rs:193-195`) and in TS (`collection.logic.ts:63`). The Auto Move doc identity is "organize notes into folders" (`22-auto-move.md:3`), and the doc says the global switch also gates `_archive_to` (`:124`).

## 3. Missed

M1. **Link rewrite on rename is a frontmatter writer that neither scout listed.** `updateLinksAfterRename` (`link-updater.service.ts:35-80`) regex-replaces wikilinks across the whole file (`link-updater.logic.ts:86-116`), including frontmatter relationship values such as `_belongs_to: "[[Old]]"`. It writes raw with `writeTextFile` (`:58`) and only calls `applyNoteChange('save')` (`:71`), never `notifyAfterSave`. Consequences:
- A rule matching on `_belongs_to` / `_related_to` (which `buildNoteRecord` turns into target arrays, `collection.logic.ts:72-77`) is not re-evaluated on the notes whose links changed.
- An "on rename" trigger on the renamed note runs while these raw writes to other notes are in flight (`path-change.service.ts:176-190`), with no serialization against a rule write on those notes.
- On a dirty tab it reads `tab.content`, awaits the write, then syncs that content back (`:54-66`). A rule write to that tab between those two steps is overwritten.

M2. **File History restore vs always-set.** `restoreSnapshot` replaces the doc and saves through the normal save path (`file-history.service.ts:82-104`). An always-set rule re-applies its keys right after a restore, so "restore a version" cannot bring back an older value of a rule-owned key. Every rule write also adds a snapshot (the after-save hook is registered at `app-lifecycle.service.ts:282`).

M3. **The evaluation record is not the frontmatter.** `buildNoteRecord` injects `organized`, `archived` and `favorite` (always present), replaces `tags` with frontmatter tags merged with inline body tags, normalizes the casing of `_type`, and turns relationship keys into target arrays (`collection.logic.ts:53-78`). "Fill only if missing" must be judged on the `Property[]` that `mutate` receives, canonicalized with `canonicalizeKey`, never on `record.properties`. Otherwise:
- a `tags` fill is skipped on notes that have only inline tags;
- `organized` / `archived` / `favorite` always look present;
- a `_type` compare is case-normalized.

M4. **Meta-bind already shows how to write frontmatter without losing the caret.** `dispatchMetaBindUpdate` dispatches a CodeMirror change covering only `[0, frontmatterEnd)` plus a scroll snapshot (`widgets.ts:868-894`), so the selection maps through the change. `updateNoteFrontmatter`'s open-tab branch instead goes through `syncExternalContentToEditor` and the external-content signal, which is the full-doc-replace path that blocker 001 is about. A designer facing blocker 001 has two in-repo options: wait for the 001 fix, or route active-tab rule writes as a ranged transaction. Neither scout connected the two.

M5. **Open Issue 005 (empty frontmatter block stacking) hits rule writes.** A note whose content starts with `---\n---\n` is not matched by `FRONTMATTER_REGEX`, so `rebuildContent` prepends a second block (`.scratch/open-itens/issues/005-empty-frontmatter-block-matched-writers-never-stack.md`). The folder-note placeholder writes exactly that (`file-icons.service.ts:102`). A rule that matches folder notes, or any note with an empty block, writes a duplicate block on disk.

M6. **Auto Move does not filter to Markdown, despite its docs.** The observer skips only `.view` (`auto-move.service.ts:97`), while `22-auto-move.md:183` says only `.md` is evaluated. Canvas tabs save through `onContentChangeForPath` -> `saveDirtyTabs` -> `writeTab` -> `notifyAfterSave` (`editor.service.ts:187-204,265-268`). By reading, a `file.*` expression could move a `.canvas`; this was not executed. A shared rule core must filter `isMarkdownFile` itself, not inherit Auto Move's guard.

M7. **Watcher-delivered edits never run after-save observers.** These are edits from outside the app: git pull, sync tools, another editor. Only `applyNoteChange('watcher')` runs, so neither Auto Move nor on-save rules see them. Rules will not apply to notes edited outside Kokobrain until their next in-app save. That may be fine, but it should be documented.

M8. **Feature-cycle ratchet.** `featureCycleEdges` is empty (`src/tests/lib/architecture/feature-cycle-baseline.json`), so no feature cycle is allowed. Today `properties -> {file-history, file-icons, type-definitions}` and `type-definitions -> {collection, file-icons}`, and `collection` and `file-icons` have no outgoing feature edges. A property-change trigger fired by `properties` importing the rules feature is forbidden if the rules feature imports anything from `properties` (for example lifecycle helpers or `propertiesStore`). The trigger must go through a core hook (in the style of `addAfterSaveObserver`), or the rules feature must stay a leaf below `properties`.

M9. **Layer baseline correction for scout-10 constraint 8.** `layer-baseline.json` holds only the three `utils -> core` entries. Zero `core -> features` edges are grandfathered, so placing a shared rule core in `core/` that imports `features/collection/expression` is a hard test failure, not "debt that may only shrink". The shared core must live in `features/`, or the expression engine must move down a layer first.

## 4. Corrections a designer must know

C1. Icon and color keys need ONE owner. Per-action semantics do not stop R1. Either Auto Move's icon action moves into the shared rule core, or Auto Move's icon write stops deleting color keys it was not configured to set (`frontmatter-icon.service.ts:26-31`). Leaving both in place loops with either semantic.

C2. The property-change trigger depends on Issue 105's skip-flag fix (content-signature skip). Ship that fix first, or make the trigger fire only after the panel's 300 ms re-parse. Do not invent a rule-specific workaround.

C3. Creation hooks: there are two TS primitives (`createFile` with source `fs`, `openOrCreateNote` with source `create`), four `create_note` callers and a handful of raw creates. Note-change source alone cannot detect "created", and the consumer API has no source. A content-shaping hook inside the primitives must not import `features/` from `core/` (M9). It would need an injected callback registered by the feature, mirroring `registerTypeIconLookup` (`icon-resolver.ts:26-31`).

C4. Judge "missing" on raw canonical `Property[]`, evaluate on the record (M3). Skip the writer call entirely when no action changes anything, to avoid canonicalization writes and the self-re-trigger (`28-mods.md:180`).

C5. Default exclusions: non-Markdown files (M6), `.view`, `_system/`, `.kokobrain/`, the configured templates folder (R7), type definition notes (`isA === 'Type'`, `type-definitions.logic.ts:91-93`) and notes with lossy frontmatter (skip quietly, as at `auto-move.service.ts:203-207`). Watch out for empty-block notes (M5).

C6. Writers that never fire after-save will not trigger on-save rules: type rename, link rewrite (M1), Todoist task and project writes, watcher (M7), creates. Of these, link rewrite and type rename change frontmatter that rules may match on. Each needs an explicit decision on whether it should re-evaluate.

C7. The Todoist risk is a deny-list on `todoist_project` plus the rare closed-note lost-update race (scout-09 H4, still unproven end to end). Do not design around the refuted "unknown id becomes a new project" mechanism (R2).

C8. Rules must be all-matches for property actions while moves stay first-match. That still holds (scout-10 2.5, `auto-move.logic.ts:17-35`), and it is the main reason a shared core needs two evaluation modes.
