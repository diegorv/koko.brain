# Scout 15: project constraints and vocabulary for a "frontmatter rules" feature

Read-only research, 2026-11-10. Evidence is cited as path:line, or as ADR section names where the ADR itself has no line anchors. "Not verified" marks anything I did not confirm in code.

## 0. Headline findings

1. **`CONTEXT.md` does not exist.** `docs/agents/domain.md:5-12` points at a repo-root `CONTEXT.md` and says to proceed silently when it is absent. `git ls-files` finds no `CONTEXT.md` or glossary file anywhere. The vocabulary below is therefore reconstructed from ADRs 0026, 0027, 0029, the Auto Move help page and the code, not from a glossary. Any term this feature coins is a gap to note for `/grill-with-docs`, as `docs/agents/domain.md:17` says.
2. **The word "rule" is already overloaded** (Auto Move rule, lifecycle rule, `RESERVED_KEY_RULES`, "layer rules"). Section 2 gives the collisions and a naming recommendation.
3. **Layer and cycle gates decide the shape of any "shared rule core" option.** `feature-cycle-baseline.json` has `featureCycleEdges: []`, so there is no cycle today and any new one fails `feature-cycle.test.ts`. A feature that imports `auto-move` while `auto-move` imports it back fails. A shared core has to be a leaf that both import.
4. **Typed values matter.** Frontmatter properties carry a type (`PropertyType = 'text' | 'list' | 'number' | 'date' | 'boolean'`, `src/lib/core/frontmatter/properties.types.ts:2`). Issue 01 specs `defaultProperties` as string values only. Lifecycle flags (`_organized`, `_archived`, `_favorite`) are booleans, and a text value `"true"` would be written quoted (ADR 0029 quoting table: reserved literal `true` is quoted), which is a string, not the flag. A per-action value model must carry a type, or booleans cannot be set.
5. **Writing through the one write seam re-serializes the whole block** (ADR 0029). A rule write normalizes the matched note's other frontmatter bytes as a side effect, and refuses lossy blocks (comments, nested maps, duplicate keys, alias collisions, anchors, unparseable). Section 3.3.
6. **`_organized` has special semantics for "fill only if missing"**: a missing key already reads as organized (ADR 0026 amendment 2026-11-05). Filling `_organized: false` into a note that lacks it moves it into the Inbox. Section 3.2.

### Naming collisions and recommendation

- "rule" alone: Auto Move rules, lifecycle rules (generated), `RESERVED_KEY_RULES` (`type-sidebar.logic.ts`), architecture "layer rules". "Lifecycle" alone: the three boolean flags (ADR 0026) AND Auto Move's generated rules. Avoid both words as the new feature's name or as a bare noun.
- User-facing, the app says **Properties**, not "frontmatter" (Properties panel, `22-auto-move.md` says "frontmatter properties"). Code and ADRs say **frontmatter**. A scratch slug `frontmatter-rules` follows the code word; a user-facing label should probably follow the panel word. This is an owner naming call (open question Q7).
- "default" is taken: Issue 01 deliberately chose `defaultProperties` over `setProperties` so the name "should not suggest an overwrite". With per-action "fill only if missing" vs "always set", that name stops fitting an action that overwrites. A neutral action noun is needed (for example "action" with a `mode`), not "default" or "set".
- "type" is both the `_type` property and TS `type` fields; "icon"/"color" are both frontmatter system keys and Auto Move's `AutoMoveIcon` (`iconPack`, `iconName`, `color`, `textColor`, `auto-move.types.ts:1-10`). The feature's actions should name the real keys (`_icon`, `_color`, `_title_color`) rather than coin parallel names.
- Existing precedent for a feature folder name: `auto-move`, `file-icons`, `type-definitions`, `properties`, `collection`. A new feature folder under `features/` is kebab-case; file names per `CLAUDE.md` Conventions (`*.logic.ts`, `*.store.svelte.ts`, `*.service.ts`, PascalCase `.svelte`).

## 3. Constraints any design must respect

### 3.1 Layers and imports (ADR 0003 + enforcement tests)

- **Where it lives.** Auto Move is in `features/` (always loaded). A rules feature that edits frontmatter is "always on" in the same sense; `plugins/` would be wrong for a core data-integrity behavior and also forbids importing other plugins and features->plugins (`layer-rules.test.ts`, ADR 0003 enforcement table: `features->plugins`, `plugin->plugin`).
- **Feature -> feature imports are allowed while acyclic** (ADR 0003 amendment 2026-11-01, `feature-cycle.test.ts`, `src/tests/lib/architecture/feature-cycle-baseline.json`: `featureCycleEdges: []`). Current relevant pairs in `featurePairs`: `auto-move -> collection`, `auto-move -> file-icons`, `auto-move -> type-definitions`, `type-definitions -> collection`, `type-definitions -> file-icons`, `properties -> type-definitions`, `properties -> file-icons`, `properties -> file-history`. Consequences for the three options the owner asked about:
  - **Extend Auto Move**: no new pair, no new cycle risk.
  - **Separate feature that imports `auto-move`** (or the reverse): fine one way; a back-import fails with the cycle path. Do not make both import each other.
  - **Shared rule core**: must be a leaf both depend on (`auto-move -> core-X` and `frontmatter-rules -> core-X`, nothing back). Candidates by layer rule: `features/collection/expression/` (already shared, already imported by `auto-move.logic.ts:3-4`), a new leaf feature, or `utils/` only if it is pure with no state (utils must not import `src/lib` outside utils, `utils->non-utils`). The expression engine is not in `utils/` and not `.logic.ts`-named, but `pure-logic.test.ts` (ADR 0004 guard) walks the import graph from every `.logic.ts`, `.types.ts` and `utils` file and fails if it reaches the framework, Tauri, a component, store or service. Any shared evaluation module that a `.logic.ts` imports must stay pure.
- **`core/` cannot import `features/`.** A trigger that must live in `core/` (note creation, path changes) reaches the feature through a registration API, wired in `initializeVault` and unwound in `teardownVault` (`app/lifecycle`), and "a missing registration fails silently, so each one is pinned by a lifecycle test" (ADR 0003 Consequences; indexing rules 15). Existing registries: `addAfterSaveObserver` (`editor.hooks.ts:55`), `registerCollectionNoteChangeConsumer`, `registerFileIconsNoteChangeConsumer`, `registerPathChangeConsumer`. Do not grow a second owner of "a note's bytes changed" and do not call per-file updaters directly (indexing rule 6).
- **Settings UI**: the settings panel is in `src/lib/app/`; features expose section components and `app/` passes them in (ADR 0003 amendment 2026-11-01). Not verified where `AutoMoveSection` is mounted beyond `SettingsPanel.svelte` being cited in Issue 079.
- **IPC**: `src/lib/**` reaches Rust only through typed `call()` (`raw-invoke.test.ts`) and subscribes to events only through typed `on()` (`event-listen.test.ts`). Any new Rust command with `#[ts(export)]` DTOs is a "Both" change and regenerates `src/lib/contracts/generated/` (`CLAUDE.md` Quick Reference rule 6, `ipc-mirrors.test.ts`).
- **Persistence location**: app data inside the vault at `.kokobrain/` (ADR 0019, not re-read here; Auto Move proves it: `auto-move.service.ts:19` `CONFIG_FILE = 'auto-move-rules.json'`, help 22 "Configuration File"). A copied vault carries its rules. Mods keep data in `.kokobrain/mods/<id>/` (ADR 0036 amendment). The watcher drops dot-folder events (indexing rule 5), so saving the rules file does not trigger anything by itself.

### 3.2 Frontmatter semantics (ADR 0026, 0027)

- **System keys use the `_` prefix** and a new system key needs an `ALIAS_MAP` line in `src-tauri/src/vault/aliases.rs:11-26` if it has an alias, plus a row in the ADR 0027 key table amendment (the table says it lists "each underscore key the app reads once"). A rules feature that stores its own config in the vault file does not need a note-level key; adding one (for example a per-note opt-out) would.
- **Compare and write on the canonical key.** `organized` in an action must check and write `_organized` (Issue 01 behavior 4). "Missing" in Issue 01 means absent, `null`, `''` or an empty list. That definition becomes a per-action choice here ("fill only if missing" vs "always set"); the owner's definition of missing for booleans and numbers is open (Q3).
- **`_organized` trap**: a note with no `_organized` reads as organized in Rust, the frontend, the action bar and the Inbox (ADR 0026 amendment 2026-11-05). "Fill if missing `_organized: false`" would drop every previously fine note into the Inbox. Conversely the `explicitOrganization` setting already stamps `_organized: false` at creation for covered paths via `applyExplicitOrganization` (`src/lib/core/note-creator/explicit-organization.logic.ts`, textual insert, opt-in per call site; ADR 0026 amendment 2026-11-04). An on-create rule that fills `_organized` sees the key already present for those paths. Periodic notes, non-Markdown files and type definitions are excluded from that stamping.
- **Relationships**: values with wikilinks become relationships in Rust (`extract_all_relationships`); a wikilink value must be a quoted string (`"[[AWS]]"`); ADR 0029 quoting table quotes a leading `[`, and Issue 01 behavior 3 repeats the warning (unquoted parses as a nested list). `_belongs_to`, `_related_to`, `_has_many` are list-or-string wikilink fields.
- **Icons and colors are frontmatter keys** (`_icon`, `_color`, `_title_color`, ADR 0027). Icon format `pack:name`, bare name defaults to Lucide (`parseIconValuePermissive`, `file-icons.logic.ts:82` per ADR 0027). A type definition's icon is inherited by notes of that type (ADR 0027 table); a note's own `_icon` wins (resolver order not verified here). The existing write API is `setFrontmatterIcon`, `setFrontmatterIconColors`, `removeFrontmatterIcon` in `src/lib/features/file-icons/frontmatter-icon.service.ts` (exports at lines 57, 74, 84), which go through `updateNoteFrontmatter` (ADR 0029 amendment 2026-10-28 issue 55). `setIconForPath` (file-icons.service) additionally updates the icon store and handles folder icons by writing a folder note (open Issue 005 documents that `ensureFolderNote` writes `---\n---\n` and later writers stack a second block). For notes only, a rules feature can write `_icon` as an ordinary property and let the index pick it up. Two readers of the icon index disagree today (open Issue 169): `buildFrontmatterIconIndex` reads Rust entries, `updateFrontmatterIconForFile` re-parses raw text. A rule that writes `_icon` right after a save lands in that disagreement window.
- **Do not model icons with a parallel config shape.** `AutoMoveIcon` stores `iconPack` + `iconName` + `color` + `textColor` and calls `setIconForPath`; a frontmatter-rules action should write the real keys so Properties, Collection and QueryJS see the result (ADR 0027 context: the reason icons moved out of a sidecar JSON was visibility to frontmatter features).
- **Types are never inferred from strings**: `PropertyType` is detected from the raw YAML value (`properties.types.ts:1-3`). Actions need a declared value type or a parse step (Q3).

### 3.3 The write path and canonical form (ADR 0029, `frontmatter-write.service.ts`)

- **Single write seam: `updateNoteFrontmatter(path, mutate)`** (`src/lib/core/frontmatter/frontmatter-write.service.ts:99`). `mutate` is pure and may run twice. Open note: patches the tab content, keeps unsaved body edits, saves the tab at once (`syncExternalContentToEditor` + `saveFileByPath`). Closed note: `writeTextFile(..., { create: false })`, then `notifyAfterSave`. Returns the unchanged base and writes nothing when `rebuildContent` output equals the base (`next === base`). Doc comment: concurrent calls on one closed note race and the last write wins, so **callers must serialize writes per path** (lines 82-98). A multi-action rule must apply all its changes in ONE `mutate`, and an all-rules pass for one note must be one call, not one call per action or per rule.
- **Self-triggering and idempotence.** A rule write fires `notifyAfterSave`, so the note is evaluated again after the debounce (Issue 01 note 6, "chaining happens through the save, no extra loop needed, and none must be added"). "Always set" is idempotent only because `updateNoteFrontmatter` returns early when bytes are equal; "fill only if missing" is idempotent by construction. Two matching rules that set the same key to different values with "always set" would flip-flop on every save if they were evaluated one per pass (first-match-wins would not flip-flop but would hide the second rule). The mods guide warns about the same loop (`help/documentation/28-mods.md:180`). Rule order/conflict policy is an owner decision (Q2).
- **Lossy frontmatter is refused, not repaired** (ADR 0029 amendments 2026-10-28, 2026-11-02 issue 17): `FrontmatterWriteError` with reason, bytes unchanged. Issue 01 behavior 5 and 7 already decide the Auto Move treatment: a rule that cannot write falls through (when it has nothing else to do) and the failure is logged via `error('AUTO-MOVE', ...)`, not toasted per autosave. A comment-only frontmatter is reported as lossy (`comments`); the owner notes never have comment-only frontmatter (so no follow-up, per memory entry) but ordinary YAML comments in a note's block make every rule on that note silently skip.
- **First write normalizes the block.** ADR 0029 "Trigger window": normalization does not fire on open or save, only on UI mutations that re-serialize. A rule write is such a mutation, so the first rule write on a hand-written note rewrites its frontmatter to canonical form (flow lists `[a, b]`, alias keys such as `type:` become `_type:`, nested maps dropped but caught by the lossy check first). Exception: unquoted numbers and booleans whose value does not change keep their source spelling (ADR 0029 amendment 2026-11-02 issue 18). Key order is preserved; a new key is appended (Issue 01 behavior 3 "appends only the missing keys").
- **Values**: writer coerces list items to strings (`String(item)`); empty text is written `""`; empty list `[]` (ADR 0029 "Empty values", "Lists"). `"false"` as text is a quoted string, not a boolean. Dates: `PropertyType` has `date`; how a `date` value is serialized is not verified here.
- **CRLF**: open Issue 095 says CRLF notes are rewritten as LF on the first edit; a rule write on a CRLF note would convert it (rare, owner on macOS).
- **Write atomicity**: open Issue 076 says note writes via plugin-fs are not atomic (truncate then write). A rules feature that writes many notes in bulk (for example a "run on all notes" action) multiplies that exposure. Not verified whether a bulk run is in scope.
- **Caret blocker (open-itens 001, `ready-for-agent`)**: a frontmatter rewrite of the active note goes `syncExternalContentToEditor` -> `MarkdownEditor.svelte:627` and keeps the caret at its old numeric offset, so typing lands in the wrong place. Issue 01 of auto-move-default-properties is blocked by it. Any trigger that rewrites the open note (save, property change, create, rename) hits this. Per-action "always set" on an actively typed note makes the exposure larger than "fill if missing", which writes once.

### 3.4 Trigger plumbing (indexing-watcher-rules, editor hooks)

- **On save**: `addAfterSaveObserver` (core, `editor.hooks.ts:55`) is what Auto Move uses; observers are fire-and-forget, errors caught and logged, and receive the plaintext content (`editor.hooks.ts:5-9`). Auto Move debounces per file with `settingsStore.autoMove.debounceMs` and captures the content at save time (`auto-move.service.ts:96-126`). The writer already re-reads the tab or the file, so stale captured content is a design point (not verified how `evaluateAndMove` handles a content/disk mismatch).
- **On property change**: the Properties panel, lifecycle toggles, meta-bind and icon writers all end in `updateNoteFrontmatter` -> `notifyAfterSave` (ADR 0029 "Trigger window", amendments), so an after-save observer sees them. A YAML edit typed in the editor is saved by the autosave path: **500 ms debounce for frontmatter-only edits, 2000 ms for body text** (indexing rule 7), then `notifyAfterSave`. So "immediately" for typed YAML is bounded below by that autosave debounce plus any rules debounce. The `edit` source of `applyNoteChange` runs consumers on debounced keystrokes but skips the Rust IPC and the dedupe (rule 16); it is a possible earlier hook but is not a save, and the file on disk is not yet written. Not verified whether any existing consumer writes from the `edit` path.
- **`applyNoteChange` `save` must stay synchronous** (indexing rule 17): `notifyAfterSave` depends on the consumer fan-out finishing before `notifyContentInvalidated()`. A rule consumer that awaits a write inside the `save` fan-out would break that ordering. Auto Move avoids it by deferring through `setTimeout`. The mods host does the same (`ctx.onNoteSaved` runs through `setTimeout(0)`, `28-mods.md:172`).
- **On create / move / rename**: today only saves are observed. Issue 02 (auto-move-default-properties) is the open spec for move and rename, status `needs-triage`, with its own unresolved questions (which events count, where the safe hook is, whether to read content, watcher/external moves, whether "next save" is enough). Constraints from the docs: moves and renames go through `path-change.service::applyPathChange`, which owns ordering and calls registered path-change consumers synchronously after `diskOp` and before the link rewrite, once per change, a folder change reported once for the folder (indexing rule 6, third bullet). So a rename/move rule needs either a path-change consumer (no saved content in hand, must read the note) or a deferral like Auto Move's. Auto Move's own move goes through `moveItem` -> `applyPathChange`, so a path-change trigger would also see Auto Move's moves: Issue 02's "Auto Move's own move must not trigger another evaluation" applies. Note creation has many entry points (`applyExplicitOrganization` lists ~20 covered call sites and is opt-in per call site, "not built into `openOrCreateNote` or `createFile`"); the central seam for create is `applyNoteChange` with source `create`/`fs` (indexing rule 6 lists `note creator`, `fs.service::createFile` as callers). Whether to hook there or at each creator is open; ADR 0026 amendment 2026-11-04 shows the cost of the per-call-site approach.
- **External edits** (other editors, sync tools) reach the app only via the watcher (`watcher-handler.service.ts`, 500 ms debounce, incremental for 1-10 Markdown files, else full rebuild; rule 4). The `save` hook never fires for them. A rule feature that fires only from after-save ignores external changes; making it fire from the watcher path is a larger design and a known source of write races (open Issues 017, 019, 088).
- **Markdown only**: Auto Move's after-save observer filters only `.view` (`auto-move.service.ts:97`), so kanban and canvas saves reach `evaluateAndMove` today; open Issue 054 (`ready-for-agent`) fixes it with `isMarkdownFile`. A new feature must filter to Markdown from the start, and `.view` files are YAML-only and must be skipped (ADR 0027: `.view` frontmatter is a whole-file YAML).
- **Excluded folders / master switch**: Auto Move has `excludedFolders` and a global `enabled` default off (`settings.store.svelte.ts:110-113`). A separate feature needs its own switch and exclusion list or must share Auto Move's. Sharing Auto Move's `enabled` would make a property rule depend on a "moves notes" master switch (help 22 warns Auto Move performs real moves), which a user turning properties on does not expect. Owner call (Q4).

### 3.5 Svelte and store patterns (ADR 0034, PATTERNS.md)

- Stores expose getters; a getter may return a module-level `$derived`/`$derived.by` when caching pays off; plain getter is the default; no mass migration; **every computed getter has a test** (ADR 0034; `docs/PATTERNS.md:9-13`). `.store.svelte.ts` holds reactive state only, no business logic.
- Any `$effect` that calls a service must read its deps first and wrap the call in `untrack()` (`docs/PATTERNS.md:36-61`, ADR 0006). Relevant for a settings section or a store-driven re-evaluation.
- Pane/layout patterns in PATTERNS.md do not apply.
- Svelte cannot export a derived from a module (`derived_invalid_export`). A rules store with an `enabledRules` computed (like `autoMoveStore.enabledRules`, used at `auto-move.service.ts:101`) is a getter.

### 3.6 Failure and error-handling rules (`CLAUDE.md` Error Handling)

- Services: try/catch around Tauri calls, propagate, log before rethrow, no partial store updates on error. Components: user-facing errors by toast or inline state.
- Auto Move precedent for a background evaluation: failures are caught at the timer callback and logged with `error('AUTO-MOVE', ...)` (`auto-move.service.ts:118`); a failed move is silent to the user (open Issue 082, `ready-for-agent`, wants a toast naming the note without stacking per autosave). A new feature should decide the user-visible failure story up front rather than inherit the silent one.
- Config load failure: open Issue 031 (`ready-for-agent`, blocked by 030) says `loadAutoMoveConfig`'s catch resets to `DEFAULT_CONFIG` and `saveAutoMoveConfig` then overwrites the unparseable file; open Issue 079 says edits made just before Settings closes are dropped (`AutoMoveSection.svelte` `onDestroy` clears the timer instead of flushing). A rules store copied from Auto Move would inherit both defects; design it with a load-failed guard and flush-on-destroy from the start, or share the fixed code. (Auto Move's own code was read via the issue text; I did not re-open `auto-move.service.ts:42-88`, so treat the line numbers as the issue's.)

### 3.7 Testing rules for a new feature (`docs/TESTING.md`)

- Never mock stores or `.logic.ts`; mock only Tauri APIs, side-effect services and DOM services (TESTING.md "Allowlist/Blocklist"). So the expression engine and the rule matcher are tested for real. Assert on real store state and computed getters, never `.toHaveBeenCalled()` as the sole assertion; the 10-second litmus test applies.
- Every service/store test suite covers happy path, empty/null input, and error handling; every store has initial state, every setter, every computed getter, `reset()` (TESTING.md "What to Cover"). Orchestrator exception: a thin orchestrator that only dispatches to tested services may mock them.
- Test-first for behavior changes (global CLAUDE.md section 4): write a failing test, see it fail, then implement. A `fix:` commit needs a test or a `Test-Exempt:` trailer (`CLAUDE.md` Quick Reference rule 11).
- Tests mirror `src/lib/` under `src/tests/lib/`; Auto Move already has `AutoMoveRuleRow.test.ts`, `auto-move.logic.test.ts`, `auto-move.service.test.ts`, `auto-move.store.test.ts`, `type-lifecycle-rules.test.ts` in `src/tests/lib/features/auto-move/`. Any change to those files updates them in the same task.
- **Lifecycle registration test**: required by ADR 0003 for any register/unwire pair, because a missed registration is silent.
- **E2E**: a new user-facing feature needs at least one happy-path E2E (`docs/TESTING.md` "When to Create E2E Tests"). There is no Auto Move spec in `e2e/specs/` (listing shows `properties-cross-note.spec.ts`, `settings.spec.ts` only for related areas). ## 5. Where the three options sit against the constraints

Not a final recommendation (other scouts cover the engine and hook details); this is what the documents and gates imply.

- **Extend Auto Move** (add property actions to `AutoMoveRule`, as Issue 01 specs): no layer or cycle risk, reuses debounce, excluded folders, settings UI, expression engine, store. Costs: Auto Move's first-match-wins semantics conflict with "several property rules can apply" (Issue 01 rule 5 needs an exception), the master switch `autoMove.enabled` defaults off and is described as "moves notes", the help page and ADR-free docs frame it as moving, and the move-vs-write ordering (move first, then fill, Issue 01 rule 2) couples two effects. Per-action "always set" widens the surface of `AutoMoveRule`.
- **Separate feature that imports from `collection/expression` only** (its own store, settings, switch, file): keeps Auto Move untouched; duplicates the rule list, debounce, excluded folders, and the config load/save hygiene (031/079), which is exactly the "duplicated rule machinery" the owner wants to avoid, unless the shared pieces are extracted.
- **Shared rule core**: a leaf both import (expression parse/evaluate already shared at `features/collection/expression/`; the missing pieces to share would be: rule list store/persistence, debounce-and-evaluate scheduling, excluded-folder check, a "which rules apply to this note" selector). Must be acyclic and its `.logic.ts` parts pure (`pure-logic.test.ts`). Refactoring Auto Move onto it is an existing-code change that CLAUDE.md "Surgical Changes" and "Removing or Refactoring Code" checks apply to (trace every caller, write regression tests first); the Auto Move tests listed in 3.7 would be the safety net.

## 6. Open questions only the owner can answer

- **Q1.** Extend Auto Move vs separate feature vs shared core (the owner left it undecided). If a shared core: is it acceptable to touch Auto Move's service and store to move code out of it (existing tests as the safety net), or must Auto Move stay byte-for-byte untouched?
- **Q2.** When several rules match one note: apply all in order (later "always set" wins), or first-match-wins like Auto Move? Consider that a first-match-wins property rule hides every later rule for that note (Issue 01 rule 5), and that "always set" rules with conflicting values only stay stable if evaluated together in one write.
- **Q3.** Value model per action: only text, or typed (boolean, number, date, list, wikilink)? Lifecycle flags and `_favorite_index`-style numbers require types. What counts as "missing" for each type (absent only, or also `null`, `""`, `[]`, `false`, `0`)? For `_organized`, is an absent key "missing" (reads as organized) or only an explicit value?
- **Q4.** Separate master switch and excluded folders for property rules, or share Auto Move's `enabled`/`debounceMs`/`excludedFolders`? Default on or off for a vault that has no rules yet?
- **Q5.** Trigger scope: confirm "on property change" means any write that ends in the after-save pipeline (Properties panel, YAML typed in the editor after its 500 ms autosave, meta-bind, lifecycle toggle), and whether rules should also run for notes changed outside the app (watcher), and for a "run on all existing notes" action (bulk writes, exposure to open Issue 076 and the caret blocker 001).
- **Q6.** Notes whose frontmatter is lossy (comments, nested maps, duplicate keys): silently skip with a log, a toast once per note, or a visible state in the settings list? ADR 0029 already refuses; the UX is open.
- **Q7.** User-facing name and where it appears (Settings section next to Auto Move, a Types/Properties area, or per-type in type definitions like `_archive_to`). "Rules" vs another word given the collisions in section 2; "Properties" vs "Frontmatter" label.
- **Q8.** Per-type rules: should a type definition be able to declare actions (like `_archive_to` generates a lifecycle rule), or are all rules in the settings file? ADR 0026/0027 already use type-definition keys for behavior; the 0027 table would need new rows.
- **Q9.** Does the owner accept that the first rule write on a hand-written note normalizes the rest of that note's frontmatter bytes (ADR 0029), and refuses notes with YAML comments?
- **Q10.** Does the feature write icons/colors only as frontmatter keys on the note (recommended by ADR 0027), or should it also reach folder icons (folder notes, with open Issue 005's stacked-block bug) and type-level inheritance?
