# Validation 08: scouts 15 (docs, ADRs, constraints) and 16 (value semantics, cycles)

Adversarial pass, 2026-11-10. Both reports exist. Every claim below was checked against code at HEAD (`2e2cc5b60`) by opening the cited file. Read-only; no tests run.

Summary: both scouts are mostly right. No headline finding is wrong. One load-bearing mechanism claim in scout 15 is wrong (how the Properties panel and meta-bind writes reach after-save). Several line numbers have drifted. The two scouts missed five things a designer needs: note-change consumers receive no `source`; Auto Move's record fakes `file.mtime`, `file.ctime` and `file.size`; an empty `---`/`---` block stacks a second block on the first rule write; the Properties panel skip-flag race can revert a rule write; and two independent engines writing one closed note break the "serialize per path" contract.

## Missed

M1. **Note-change consumers have no source field and must be synchronous** (`note-change.service.ts:26-33`). This blocks "hook create at `applyNoteChange`" without a core API change. Create paths do not fire after-save: `openOrCreateNote` calls `create_note` plus `applyNoteChange({source:'create'})` (`note-creator.service.ts:103-118`), and `createFile` uses `source:'fs'` (`fs.service.ts:216`). The on-create trigger needs a new registry in `core/`, wired through `initializeVault` and pinned by a lifecycle test (ADR 0003), or per-call-site opt-in like `applyExplicitOrganization`.

M2. **Auto Move's record fakes the file stats.** `buildNoteRecord(filePath, content, Date.now(), Date.now())` sets `file.mtime == file.ctime == now` and `file.size == 0` (`auto-move.service.ts:154`; signature `collection.logic.ts:22-28`; `evaluator.ts:202-203`). A rule on `file.ctime` or `file.size` always gets the wrong answer on this path, while a Collection view built from the Rust index gets real values. A shared engine must either supply real stat values or document and validate that these fields are unavailable. `file.folder` is an absolute path (`collection.logic.ts:32-33`), so a rule such as `file.folder == "/Users/.../AWS"` breaks when the vault moves. Help 22 documents neither.

M3. **An empty `---`/`---` block stacks a second block on the first rule write.** `FRONTMATTER_REGEX` needs a line between the delimiters (`properties.logic.ts:39`), so `extractRawFrontmatter` returns null, `extractBody` returns the whole content, and `rebuildContent` prepends a new block (:689-696). `detectLossyFrontmatter` returns null for it (:406-407), so `updateNoteFrontmatter` does not refuse. Open Issue 022 (blocked by 005) fixes it. Scout 15 lists 022 but does not connect it to rules. Any rule feature that writes through `updateNoteFrontmatter` inherits the bug until 022 lands, and `ensureFolderNote` writes exactly that block (Issue 005).

M4. **The Properties panel skip-flag race can revert a rule write.** The panel re-parses 300 ms after a content change, and the timer resets on every change (`PropertiesView.svelte:102-118`). A panel commit arms `skipNextParseFor`, which skips the next parse whatever the content (`properties.service.ts:37-41`, :100). If a rule write lands within 300 ms of a panel commit, the parse that would have shown the rule's key is skipped. The panel's next commit then rebuilds from the stale store and drops that key, and a fill-only rule refills it after the next save. Documented in open Issue 105, section "Properties panel skip flag swallows the only re-parse" (:136-155), and in Issue 008. "Immediately on property change" with a short debounce makes this window likely while the user types in the panel. Not reproduced by a test.

M5. **Two engines writing one closed note race (last write wins).** The serialization contract (`frontmatter-write.service.ts:95-97`) is per caller. Auto Move's per-path debounce (`auto-move.service.ts:22`, :112-125) serializes only Auto Move. A separate rules feature with its own debounce would issue a concurrent `updateNoteFrontmatter` on the same closed note (for example Auto Move's icon write right after the move, while the rules pass writes properties), and one write is lost. The tab branch is safe, because it reads and writes `tab.content` with no `await` in between (:116-132). This is a concrete code argument for one scheduler and one write per path per trigger, which matches the owner's one-engine preference.

M6. **A textual insert for fill-only already exists and keeps bytes.** `withUnorganizedFlag` (`explicit-organization.logic.ts:21-37`) and `ensureFrontmatterLink`'s key-absent branch (`properties.logic.ts:522-533`) insert one line after the opening `---`. They keep the rest of the block byte for byte, comments included, and handle the empty block. A fill-only action that appends an absent key could use this instead of a full re-serialize. That would avoid normalizing the note (scout 15, 3.3) and the refusal on comment-bearing blocks. The cost is that `updateNoteFrontmatter` takes only a `Property[]` mutate, so a content-level variant of the write seam would be needed. A design option, not a recommendation.

M7. **Pending per-path timers do not follow renames.** Auto Move keys `debounceTimers` by path and captures `filePath` in the closure (`auto-move.service.ts:113-123`). A rename or move inside the debounce window makes the timer evaluate and move the old path. An engine that adds rename and move triggers should re-key or cancel pending work in a path-change consumer. Inferred from code; not reproduced.

M8. **Path-change consumers run in the middle of the operation.** They run synchronously after `diskOp` and before the link rewrite, the tree update and Rust `rename_note` (`path-change.service.ts:173-209`). A rename or move rule must defer its read and write until `applyPathChange` settles. Otherwise it evaluates against a Rust index and file tree still keyed at the old path. A folder move is reported once for the folder (:42-44), so the children need enumeration.

M9. **Partial YAML is evaluated while the user types.** Typing in the frontmatter source saves every 500 ms pause (`editor-extensions.ts:176-191`, `editor.service.ts:229-230`). Each save feeds the observer a half-typed value (`status: op`). With "always set", a condition can match a transient state and write mid-typing into the active note, which is the blocker 001 exposure. The debounce, not the trigger, is the only guard.

M10. **"Missing" for `_icon` is about the key, not the displayed icon.** A note of a typed class shows the type's icon with no `_icon` key (`icon-resolver.ts:67-70`). A fill-only `_icon` therefore overrides the inherited type icon on every such note. A fill-only `_color` without `_icon` colors the inherited icon (:72-76).

## Corrections a designer must know

1. Properties panel and meta-bind edits reach rules only through the 500 ms autosave of an open tab, not through `updateNoteFrontmatter`. Meta-bind keeps the caret; the panel and every `updateNoteFrontmatter` write on the active tab hit blocker 001 (R1).
2. No existing hook delivers "note created" to a feature. The note-change consumer API has no source and must stay synchronous (R2, M1). Budget a core registration API plus a lifecycle test, or accept per-call-site opt-in.
3. One scheduler and one `updateNoteFrontmatter` call per path per trigger, shared with Auto Move's move and icon, is required for correctness on closed notes, not only for style (M5). That favors the shared-core or extend-Auto-Move options over a separate engine with its own debounce.
4. Decide "missing" on `parseFrontmatterProperties` and canonical keys. Decide "match" on the record. Check "nothing to do" before calling the writer, because a no-op mutate still rewrites non-canonical notes (confirmed).
5. Until Issue 022 lands, a rule write on a `---`/`---` note stacks a second block (M3). Either sequence 022 (and 005) before this feature, or take the textual-insert path for fill-only (M6).
6. Values need a declared type. The serializer keys off `Property.type`, and a string `"true"` is a quoted string that `boolFlag` ignores (confirmed).
7. Rule authors must use `_icon`, `_color` and `_title_color` in conditions. The record gives fake `file.mtime`, `file.ctime` and `file.size` and an absolute `file.folder` on the save path (M2). Validate or document these in the rule editor.
8. The Issue 01 Notes record an earlier owner choice: extending Auto Move was "chosen over a separate per-folder-defaults feature (it reuses expressions, order, exclusions and the Settings screen)" (`.scratch/auto-move-default-properties/issues/01-...md`, Notes, Origin). Neither scout surfaced it. It does not bind the open "relation to Auto Move" decision, but the owner should see it next to that question.
9. Line references to fix when quoting: `frontmatter-write.service.ts` early return :128-129 and closed-note `notifyAfterSave` :161; the indexing-rules "15-17" are rule 6 sub-bullets (R3, R7).
