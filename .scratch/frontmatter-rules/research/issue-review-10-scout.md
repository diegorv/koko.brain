## 2. Touchpoints the Issue does not name

### Code that must change together

- **Rule type and load sanitizing.** `AutoMoveRule` (`auto-move.types.ts:27-46`) gets `runAction?: { id: string }`. `loadAutoMoveConfig` passes each rule through `withValidProperties` (`auto-move.service.ts:81,92-96`), which only sanitizes `properties`. A malformed `runAction` (non-object, non-string id) from hand-edited JSON passes through unchecked. Add a sanitizer, like `sanitizeRuleProperties` (`auto-move.logic.ts:157`). Issues 07-09 add other optional fields the same way; keep one shape.
- **Run flow.** `evaluateAndMove` (`auto-move.service.ts:206-268`):
  - The early exit `if (!rule?.icon && owned.length === 0) return;` (line 255) skips everything for a rule that only has `runAction`. It must also consider the action.
  - A failed move returns at lines 247 and 249, so the action does not run, consistent with PRD decision 9 (a failed move writes nothing).
  - `matched.length === 0` returns at 215-218.
  - Selecting "the first matching rule with `runAction`" needs a new pure helper next to `findMoveRule` (`auto-move.logic.ts:101-103`). It must pick from user rules only: `allRules` also contains generated lifecycle rules (`auto-move.service.ts:209-210`, `type-lifecycle-rules.ts:20`).
- **Per-session "log once per rule" set.** Add a Set next to `reportedWriteFailures` (`auto-move.service.ts:49`) and clear it in `resetAutoMove` (lines 349-350). Needed for three cases: not rule-enabled, missing or unloaded action, and (see section 3) action failure.
- **Store.** `autoMoveStore.updateRule` merges partial updates (`auto-move.store.svelte.ts:32-35`), so no store change is needed for the new field, but its tests list fields.
- **Settings UI.** `AutoMoveRuleRow.svelte` and `AutoMoveSection.svelte` (and the harness `src/tests/fixtures/AutoMoveRuleRowHarness.svelte`) get a "Run mod action" consequence with a select fed by the core registry list. The select must keep showing a saved id that is not in the list (mods off, mod not loaded yet, mod deleted), or saving the rule silently drops it.
- **Core registry (new file under `src/lib/core/`).** Must offer: a runner `(id, context) => Promise<void>`, a list of rule-enabled actions, and likely a way to tell "missing" from "not rule-enabled". The list has to be reactive for Settings (store with `$state.raw`, like `modCommandsStore`, `mod-commands.store.svelte.ts:14`) or Settings will not update when a mod loads later. Follow the `registerX(...) => unregister` shape of `icon-resolver.ts:26-31`.
- **Who registers.** Two options:
  1. `app/boot.ts::registerAppPorts` (`boot.ts:34-83`). It is vault-independent and idempotent, but the mod runner closes over per-mod state, so the runner would have to look the action up in a host-level map at call time.
  2. `mods-host.service.ts` registers per live mod and unregisters in `unloadMod` (`mods-host.service.ts:606-616`), which also covers reload-on-save (action disposed and re-added) and `stopModsHost` (`mods-host.service.ts:934-947`).
  Option 2 matches lifetimes. Whatever is chosen must resolve at call time (mods reload on save and re-register actions, `mods-host.service.ts:506-511`).
- **Host wrapper.** Everything the runner needs is private to `createModContext`: `actions` map (line 143), `runAction` (334-425), `openPicker` (434-449). The only externally visible hook today is `modCommandsStore.register({ run: () => void })` (`mods-host.service.ts:497-505`), which takes no arguments and returns nothing. A new path is needed that (a) accepts a context, (b) returns a promise.
- **Contract (other repo).** Edit `packages/mod-core/src/contract/mod-api.v1.ts` in `diegorv/koko.brain-mods`, plus `packages/mod-core/src/testing/fake-ctx.ts` (`addAction` stub at line 162, `labs.place` at 166-174) if a new member is added; then re-pin the SHA in `package.json:81` and `pnpm-lock.yaml:181,183,516,2607` (`docs/MOD-CORE.md:38-47`). ## 3. Things that make a Behavior impossible or much bigger than it looks

1. **Opt-in cannot live in `manifest.json` as written (Behavior 2).** See fact 2. Options for the implementer, all of which the Issue's author should pick, not the scout:
   - A new optional field on `ModActionV1` in the canonical contract (for example `ruleAction?: true`), copied in `addAction` (`mods-host.service.ts:488-494`), validated with an `invalid(...)` throw like the other fields (lines 474-485), and shown in docs 02. This needs the cross-repo contract change and a SHA re-pin.
   - An unstable placement on `ctx.labs.place` (for example `{ rule: true }`), alongside `palette` and `menu` (`mods-host.service.ts:37-50,148-185`). Labs is host-only (`ModContext`, not `ModContextV1`) and "may change without an API version bump" (`mods/02-actions-and-entry-points.md`), so no contract repo change and no re-pin, and it matches how every other entry point is opted in. The Issue's wording "additive change to the mod API ... bump the contract" would then not apply to the opt-in.
   - A manifest-level list (`ruleActions: ["id", ...]`) would work with the host's existing parser (`mods.logic.ts:183-210`) and needs no contract repo change, but it is not what "on that action" says, and the manifest of a mod switched off is parsed without loading its code (`mods-host.service.ts:735-760` area), which would even allow Settings to list actions of unloaded mods.
2. **Context argument shape (Behavior 3) is ambiguous and an equivalent already exists.** `run.target = { on: 'note', path }` already carries the matched note for note-menu runs (`mods-host.service.ts:174,386-388`, contract lines 52-58). The Issue's settled decision is a `{ notePath }` argument with an absolute path; the scout does not reopen it, but the Issue does not say WHERE it goes: a third `run(input, run, context)` parameter, or a field on `ModRunV1`. A third parameter changes the `ModActionV1.run` signature (contract line 103); function-typed members are not bivariant-checked per the header, so a mod with fewer params still type-checks (additive). Note also that `target.path` is vault-relative while the Issue wants absolute, and `onNoteSaved` hands mods vault-relative paths (`mods-host.service.ts:560`). The mod API is relative everywhere (`ctx.vault` takes vault-relative paths); an absolute `notePath` is the odd one out and a mod cannot pass it to `ctx.vault.*`. Worth a one-line confirmation, not a redesign.
3. **No programmatic invoke exists with completion.** `modCommandsStore.list[i].run()` is `() => void` and goes through `openPicker` (`mods-host.service.ts:497-505`, `434-449`), which:
   - for an action with `input` OPENS THE PICKER TEXT FIELD for the user (`mods-host.service.ts:444-449`). A rule-fired action with `input` would pop a dialog at save time. Decide: refuse such actions as rule-enabled, or call with `''`.
   - `runAction` only reveals the run view lazily for the `command` origin (`lazy=true`); with `lazy=false` the run view opens at start (`mods-host.service.ts:383`). The runner must use the lazy path, or every rule run steals focus.
   - failures toast (`mods-host.service.ts:420`) and go to the run, not to the caller. PRD decision 9 says rule errors are never toasted, but a mod failure toast is the host's standing behavior (ADR 0036 line 41: errors "go to a toast and `debug('MOD:<id>')`"). A "runner returns Promise<void>" that resolves after the run (to make "once per run" and ordering meaningful) needs `runAction` to return completion; today it already returns a promise (`async`, line 334) but it swallows errors internally and resolves on both busy-early-return and success.
   - the "missing action logs once" requirement needs the runner to distinguish "no such action" from "busy": today busy and success both resolve with no signal.
4. **writingPaths ordering trap (Behavior 4 and 6).** `writingPaths` is held across the whole write phase (`auto-move.service.ts:257-267`) and the observer drops saves for those paths (`auto-move.service.ts:128`). If the action is awaited inside that `try`, saves the mod causes on the note are silently suppressed, which would implement the loop protection the Issue says is "documented, not prevented", and the documented warning would be false. The action must run after the `finally` (line 267), and then its own saves schedule a new debounced evaluation (`auto-move.service.ts:148-158`), which is the documented loop. A test must pin this (action writes the note; a second evaluation is scheduled).
5. **Timing and availability of mods.** Mods start after vault open, off the open path (`app-lifecycle.service.ts:539-543`, `startModsHost` at `mods-host.service.ts:866-891`), and only when mods are enabled for the vault (`mods-host.service.ts:868`). A save during startup, or with mods off, hits "missing" and logs once per rule per session, then later saves are quiet even after the mod loads; acceptable but should be stated. Reload on save of `main.js` removes and re-adds actions (`mods-host.service.ts:506-511`), so the runner must not cache action objects. Listing in Settings when mods are off is empty.
6. **Run-per-action serialization.** One live run per action (`mods-host.service.ts:336-339`). Two notes saved in quick succession invoke the same action; the second is dropped (and reveals the run view) while the first runs. The Issue's "A running instance is not started twice" matches, but the practical effect is a lost invocation for the second note. It is not queued and no log says so.
7. **Cross-repo contract dependency.** Any contract-level choice (items 1 and 2) requires a commit to a private repo and a new SHA pin before the host can compile against it, plus `fake-ctx` and conformance updates there. This is the largest hidden cost. The Gate line "frontend only: `pnpm check` + `pnpm vitest run`" does not name the `pnpm build` and `pnpm install --frozen-lockfile` steps that a `package.json`/lockfile change needs (CLAUDE.md rule 6; `docs/MOD-CORE.md:44-45`).
8. **`ModRuntime.runs` and reload.** A rule-started run joins `runtime.runs` (`mods-host.service.ts:382`), so a mod reload waits for it (PRD P10); a hung action blocks reload of that mod until Stop. The rule has no UI to Stop it unless the run view is revealed. Minor.
9. **Rule filter evaluation cost is not affected,** but "Matches N notes now" (PRD decision 13) and a rule's "starts disabled" guard are the only protection against a broad rule firing a mod action on every saved note (mod actions can write, call HTTP, spawn LLM calls; ADR 0036 line 41 says mods have full trust). Worth a line in the help page; not a scope change.
10. **Lifecycle rules.** `allRules` includes generated lifecycle rules (`auto-move.service.ts:209-210`); they never have `runAction`, but the helper must not assume every matched rule has the field.

## 4. Verdict

Behaviors 1, 4 (as an order), 5 and the registry pattern are feasible as written. Behavior 2 (manifest opt-in) names a place that does not exist; Behavior 3 requires a cross-repo contract change plus a SHA re-pin and mis-states the ADR's bump rule. Behaviors 3 and 4 also need a new host entry point (argument-taking, awaited, lazy, input-less, quiet on failure) that does not exist today, and the action must run after `writingPaths` is cleared.
