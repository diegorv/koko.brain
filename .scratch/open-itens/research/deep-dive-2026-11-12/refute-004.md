# Refute: Issue 004 (canvas edit closed or renamed inside the debounce window)

Adversarial validation against HEAD `318b6e9b5` (2026-11-12). Read-only: no tests, builds or app were run. "Fact" = read in code at the cited line. "Inference" = reasoned, not executed. The dossier was written at `115d8d576`; `git diff --stat 115d8d576 HEAD` touches none of the files below (only palette/tasks/kanban CSS files and `.scratch`), so its line numbers still hold.

## Verdict

- **Close case: still present (fact).** `closeTab` (src/lib/core/editor/editor.service.ts:303-332) checks `isTabDirty` at :312 and calls `editorStore.removeTab` at :328. Nothing asks the canvas to flush before that. The canvas tab is clean inside the 300 ms debounce (src/lib/features/canvas/CanvasInner.svelte:227-241, `pendingPersist = true` at :234, timer :236-239). The keyed instance (src/lib/app/EditorView.svelte:84-86) is destroyed only after removal; its `onDestroy` (CanvasInner.svelte:246-250) runs `persistChanges` -> `onJsonChange(ownPath, json)` (:123) -> `onContentChangeForPath` (editor.service.ts:265-268) -> `updateTabContentOnly` (src/lib/core/editor/editor.store.svelte.ts:139-144), which finds no tab. The edit is dropped silently, with no prompt.
- **Rename case: present in code, but the Issue names a route that does not exist.** Tabs are re-pathed only by `updateTabAfterRenameOrMove` (src/lib/core/filesystem/link-updater.service.ts:93-109), and its only caller is `applyPathChange` (src/lib/core/filesystem/path-change.service.ts:185). The watcher (src/lib/core/filesystem/fs.watcher.ts:1-9 imports) only refreshes the tree and never touches tabs, so a "watcher-detected rename" never re-keys the canvas. The real programmatic routes are auto-organize (`moveItem`/`renameItem` at src/lib/features/auto-organize/auto-organize.service.ts:338, :473; off by default, src/lib/core/settings/settings.store.svelte.ts:111) and vault mods (`vault.rename`/`vault.move`, src/lib/plugins/mods/mod-vault.service.ts:93, :100).
- **Impact for this owner: low to medium.** Cmd+W is a global keybinding with no textarea exclusion (src/lib/app/global-keybindings.ts:80-85, and the comment at :31-38 says `registerKeybinding` fires everywhere), so Cmd+W typed straight from a card textarea reaches `closeTab`. The loss is the text typed since the last 300 ms pause: silent and unrecoverable, but usually only a few words. A tab-x click takes longer than 300 ms of mouse travel (inference). The rename leg is near zero for this owner: auto-organize is off by default, and nothing shows that the owner's mods rename an open canvas (the mods source is outside the repo and was not checked). Most of 004's queue value is that it unblocks 015 (ux/high), the kanban 006, 027 and 100.
- **Complexity S, risk low (agree with dossier).** The change adds to the only close path (`closeTab` callers: EditorTabs.svelte:89, :104; commands.ts:112 and global-keybindings.ts:84, both through `closeActiveTab` at editor.service.ts:335-339). It is a no-op when nothing is registered. ADR-0003 holds: the registry lives in `core/` and `features/canvas` registers into it; CanvasInner already imports editor.service (CanvasInner.svelte:44). Only one EditorView mounts (src/lib/app/AppShell.svelte:262) and only one CanvasView (EditorView.svelte:85), so at most one flusher per path is live. live-preview-rules do not apply (canvas is not CodeMirror). indexing-watcher-rules: a close-time save through `saveFileByPath` -> `writeTab` (editor.service.ts:171-204) keeps `notifyAfterSave` (:196), so rule 6 (`applyNoteChange` owner) is respected.
- **Can a fresh agent implement it from the text alone? Not reliably, for three reasons.** (1) Criterion 1 as written passes with a wrong fix (see M1). (2) "What to build" still offers the unsafe option 2. (3) The text never says what `closeTab` does after the flush makes the tab dirty: save, or show today's "Discard changes?" prompt. There is no open owner decision: 015's recorded owner decision (closing a dirty tab saves and closes, prompt only on save failure) settles it, but 004 does not say so.

Recommendation: **run after edits** (M1-M3).

## Must-fix edits to the Issue text

The flush makes A dirty and arms the 2 s body autosave (editor.service.ts:265-268, :227), so after "advance 3000 ms" `writeTextFile(A, ...)` has been called and the neighbour was never written. The criterion passes, but in the real app the user gets "This file has unsaved changes. Discard changes?" for text they just typed, and "Discard" loses it. It does fail on today's code (no write to A at all), so it is a valid red test. It is just too weak to prove the fix.

### M2. "What to build" must name the mechanism and drop option 2

Evidence (fact): option 2 ("have the path-scoped writer save a path with no open tab straight to disk") would, on a rename, write to the old path after `diskOp` moved the file (path-change.service.ts:174-185) and recreate it. The Issue's own second opinion says so, but the option is still listed in "What to build". Also, after a flush the tab is dirty, and today's `closeTab` prompts (:312-319). The owner decision recorded in 015 (save, then close; prompt only when the save fails) settles what should happen.

Replace the last two sentences of **What to build** ("A rename re-keys ... straight to disk.") with:

> A rename re-keys the instance and the flush targets the old path, which has no tab. Fix with a pre-close flush hook, never by writing a path that has no open tab (that would recreate a renamed-away file). In src/lib/core/editor/editor.service.ts add `registerPendingEditFlusher(path: string, flush: () => boolean): () => void` (the returned unregister removes only that function) and `flushPendingEdits(path: string): boolean`. A flusher writes its view's pending edit into the tab of `path` and returns true when it wrote something. A throwing flusher is logged with `error('EDITOR', ...)` and does not stop the close, as `notifyTabClosed` does (:37-46). In `closeTab`, after the pinned check and only for a non-virtual tab, call `flushPendingEdits(tabPath)`; when it returns true, `await saveFileByPath(tabPath)` before the existing dirty check, so a successful save closes with no prompt. A failed save leaves the tab dirty and the existing prompt is the fallback. This matches the owner decision recorded in Issue 015, which later replaces the prompt wording. CanvasInner.svelte registers a flusher for `ownPath` on mount (`if (!pendingPersist) return false; clearTimeout(nodesChangeTimer); persistChanges(nodes, edges); pendingPersist = false; return true`) and unregisters it on destroy. `onDestroy` keeps its flush for tab switch and source-mode toggle. The API is generic so KanbanView (Issue 006) can register through it.

### M3. Criterion 2 names a non-existent route and the wrong mechanism

Evidence (fact): the watcher does not re-path tabs (fs.watcher.ts imports `refreshTree` and `fsStore` only; `updateTabAfterRenameOrMove` has one caller, path-change.service.ts:185). A rename never calls `closeTab`, so "through the same pre-close flush" cannot work unless `updateTabAfterRenameOrMove` calls the flusher itself. The routes that do reach it are auto-organize (auto-organize.service.ts:338, :473) and vault mods (mod-vault.service.ts:93, :100).

Replace the second checkbox with:

> - [ ] A programmatic rename or move of the open canvas inside the debounce window (auto-organize, or a vault mod's `vault.rename` / `vault.move`; a user rename takes longer than 300 ms, and the watcher never re-paths tabs) keeps the typed text in the renamed file. `updateTabAfterRenameOrMove` (src/lib/core/filesystem/link-updater.service.ts:93-109) calls `flushPendingEdits` for each tab it re-paths, before `editorStore.updateTabPath`, so the edit lands in the tab while it still has the old path and the body autosave then writes the new path. Test: in canvas-tab-switch.test.ts type into A, advance 100 ms, call `updateTabAfterRenameOrMove(A, A2)`, `flushSync()`, advance 3000 ms: `writeTextFile` was called with A2 and the typed text, and never with A.
