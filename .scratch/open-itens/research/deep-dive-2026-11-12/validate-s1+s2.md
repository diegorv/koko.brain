## Rejected additions

- **007 (meta-bind paste, cut, copy).** The bug is confirmed (F). `CONTROL_EVENT_TYPES` has no clipboard events (`core/form-control-events.ts:2-11`). The widgets answer `ignoreEvent` with `isFormControlInputEvent` (`widgets.ts:415,816,961,1003`). CodeMirror 6.43.15 `eventBelongsToEditor` (`node_modules/@codemirror/view/dist/index.js:4921-4931`) then routes the event to `handlers.paste`, which inserts at the editor selection and returns true (`:5192-5204`). `runHandlers` calls `preventDefault` (`:4621-4624`), so the input never receives the paste. Cut with an empty editor selection deletes the cursor line (`copiedRange` `:5223-5243`, cut dispatch `:5258-5262`). For cut and copy, the `hasSelection` check at `:5253` passing while focus sits in an `<input>` inside contentDOM in WKWebView is (I). Reason for rejection: the owner's brief defers "meta-bind bugs". The sweep recommended adding it without naming that deferral. Re-ask: it is S and low risk, and it is the one meta-bind bug that writes into the note text. If the owner un-defers it, it runs after 062 (widgets.ts series, `priority-2026-11-08.md` "Run in series").
- **026 (clearing a canvas node color or link title).** The bug is confirmed (F). `flowNodeToCanvasNode` spreads `originalNode` and copies `label` and `color` only when they are `!== undefined` (`src/lib/features/canvas/canvas.logic.ts:193-209`). The clear paths send `undefined`: `handleSetNodeColor` (`CanvasInner.svelte:411-415`) and the link title (`LinkNode.svelte:56`). The base is `lastSyncedData` (`CanvasInner.svelte:119-122`), which still holds the old value, so the old value is written back. Edges handle this correctly (`canvas.logic.ts:243-249`). Reason for rejection: canvas bugs other than 004 are deferred by the owner. Re-ask it next to 038 and 039 (see below), all S.

## Spot-checks of low-impact ratings (missed bugs)

- **008 (low, agreed).** (F) `commitChanges` arms `skipNextParseFor` with no `newContent === content` guard (`properties.service.ts:97-106`). Any content change consumes the flag (`PropertiesView.svelte:103-119`, `consumeSkipNextParse` `:113`). So the loss needs a no-op commit, then a hand edit of the frontmatter as the very next content change, then a panel edit. Body typing in between disarms the flag harmlessly. `PropertyField` commits on `onchange` (`PropertyField.svelte:128`), which a browser fires only on a real change, so no-op commits are rare (I). The loss is a typed line with no undo. Rare, so low stands.
- **023 (medium-low, agreed).** (F) Both openers pass `editorStore.activeTabPath` (`commands.ts:390-392`, `global-keybindings.ts:173-174`), so the dialog always starts on the active note. Writing into the wrong note needs a tab change while the dialog is open (`file-history.service.ts:82-100` uses the shared `editorView`). Whether Cmd+W reaches the app through the modal dialog was not checked.
- **005 (medium-low, agreed).** (F) The `'---\n---\n'` placeholder (`file-icons.service.ts:102`) fails `FRONTMATTER_REGEX` (`properties.logic.ts:39`), so the icon writer prepends a real block. The icon is still read from that first block. The leftover is two `---` lines in the folder note body. Cosmetic, no loss.
- **025 (low-medium, conditional).** (F) `updateMetadata` writes through `view` (`meta-bind-button-widget.ts:98-101`), and the app shares one EditorView across tabs (`MarkdownEditor.svelte:142,146` `setState`). This is a silent frontmatter write into the wrong note in a daily feature, but only for a button that puts `open` or `createNote` before `updateMetadata`. The repo's example vault has no such button (`help/examples/markdown-editor-vault/19-meta-bind.md`). The owner's vault is outside the repo and was not checked. If any owner button chains these actions, this is the highest-impact meta-bind bug in range. Worth one question to the owner. It stays deferred with meta-bind otherwise.
