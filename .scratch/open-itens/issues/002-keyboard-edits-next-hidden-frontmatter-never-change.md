# 002: Keyboard edits next to the hidden frontmatter never change its fences

**Origin:** `audit-2026-11-05` Issue 02, moved here on 2026-11-08. Its PRD, raw evidence and closed siblings stay in `.scratch/archived/audit-2026-11-05/`. Bare Issue numbers in the text below use that feature's numbering; `priority-2026-11-08.md` in this folder maps them to the numbers here. The regression-risk deep dive behind this text is in `research/deep-dive-002/` (SUMMARY.md, critique.md).

**What to build:** The frontmatter lines are hidden with per-line `Decoration.replace({})` plus a display:none line class (src/lib/core/markdown-editor/extensions/live-preview/core/hide-lines.ts:14-20, called from plugins/frontmatter-field.ts `computeFrontmatter`). Only the mouse path is guarded: `frontmatterClick` remaps a press in the top padding to the first body line, and its own doc comment says keyboard moves are not changed (frontmatter-field.ts:86). Nothing under src/lib defines atomicRanges, a transactionFilter or a changeFilter, so keyboard commands act on the hidden fence. Cmd+Up puts the selection at 0, and Enter or Delete there edits the opening `---`. Backspace at the start of the first body line deletes the line break after the closing fence (`---First line`), and further Backspaces delete fence characters. Alt+ArrowUp (`moveLine`, userEvent `move.line`) on the first body line moves the closing fence below it, so the YAML block swallows that line. After any of these, `findFrontmatterBlock` (parsers/frontmatter.ts) no longer finds the block, or it closes the block at a later `---` horizontal rule.

Notation used below: `B` is `bodyStart`, the start of the first line after the closing fence; `F1 = B - 1` is the end of the closing fence line (the position of its line break). All paths below are relative to src/lib/core/markdown-editor/extensions/live-preview/ unless they start with src/, e2e/ or docs/.

Fix direction (variant B, owner decision 2026-11-12): add one exported extension `frontmatterGuard` in plugins/frontmatter-field.ts and register it in `BLOCK_EXTENSIONS.frontmatter` at live-preview.ts:47 beside `frontmatterField`, `frontmatterGutter` and `frontmatterClick`. The decorator kill switch and source mode then remove it with the rest (the `BLOCK_DECORATOR_NAMES` loop in `livePreviewExtensions` and the `livePreview` compartment). It is two pure filters: no StateField, decoration, effect, dispatch or `view` access, and neither reads `tr.state`. Both check the userEvent first and only then compute `B = bodyStart(tr.startState)` with the existing private helper in the same file. When `B` is null they do nothing.

Why only `delete*` and `move*` are change-filtered: once the selection clamp (item 2) keeps every keyboard selection at or after `B`, no keyboard `input.*` command edits below `B`. Typing and dead-key composition are bounded by the edited DOM line. `insertNewlineAndIndent` moves `from` back at most to the start of the caret's line. `insertNewlineContinueMarkup` (lang-markdown's Enter) can edit or read the line above (its blockquote and list branches), but at `B` the line above is exactly `---`: its quote regex cannot match, `resolveInner(B, -1)` finds no list or quote context, so it returns false and Enter falls through to `insertNewlineAndIndent`. This holds only while the line above `B` is exactly `---`; it is not a general rule, and a later markdown-keymap change could break it. From a visible caret the keyboard crosses `B` only through deletions (`delete.*` at `B` deletes `F1`) and moves (`move.line`, `move.character`, `move.drop`). Leaving `input.*` out keeps typing, dead keys, paste, autocomplete and search replace exactly as today.

1. **Change filter** (`EditorState.changeFilter`). Evaluate in this order:
   1. Return `true` unless `tr.docChanged` and `tr.isUserEvent('delete') || tr.isUserEvent('move')` (`isUserEvent` matches by prefix, so it covers `delete.backward`, `delete.forward`, `delete.selection`, `delete.cut`, `delete.line`, the bare `delete` of lang-markdown's Backspace, `move.line`, `move.character` and `move.drop`). Then compute `B`; return `true` if it is null.
   2. Collect the changes with `fromA < B` (`tr.changes.iterChanges`). If there are none, return `true` (strict: an edit at exactly `B` passes, so Delete at `B` and Enter at `B` work).
   3. `move*`: return `false`. All or nothing, never narrowed, and the line-break exception in step 4 does not apply. Narrowing would apply half of `moveLine` and write a second `---` under the first body line.
   4. `delete*` line-break exception: return `true` when exactly one change has `fromA < B`, it inserts nothing, its `fromA === B - 1`, its `toA < tr.startState.doc.length`, and the character at `toA` is `\n`. The fence line stays exactly `---` followed by a line break, so CodeMirror's own result is safe. This keeps Backspace on a blank first body line and Cmd+Shift+K (`deleteLine`, which always deletes the line break before the line when `from > 0`) on the first body line working as today.
   5. `delete*` where a change with `fromA < B` inserts text: return `false`.
   6. Any other `delete*`: return `[0, B]`. A straddling deletion keeps its body part, and one wholly below `B` is suppressed.
2. **Selection clamp** (`EditorState.transactionFilter`).
   - It runs for userEvent `select` and its subtypes, except `select.pointer` (owned by `frontmatterClick`, which keeps the selection on purpose when the first body line is a block widget) and except exactly `select.search` (Find Next and Find Previous; compare `tr.annotation(Transaction.userEvent) === 'select.search'`, because `isUserEvent('select.search')` also matches `select.search.matches`, which is clamped). It also runs for every `delete*` and `move*` transaction; transaction filters receive the transaction after the change filters ran. For any other transaction, or when `B` is null, return `tr`.
   - Base selection: `tr.startState.selection` for a `delete*` or `move*` transaction that ends with no doc change (the change filter blocked it, so the caret stays where it was: Alt+ArrowUp at column 5 stays at column 5), else `tr.newSelection`. CodeMirror maps a blocked change's explicit selection back through its inverse (`@codemirror/state` `filterTransaction`), and `deleteBy` sends an explicit cursor at `F1`, so without this a blocked Backspace leaves the caret on the hidden closing fence and the next keystrokes vanish.
   - Pass path: if the base is `tr.newSelection` and no range has `from < B`, return `tr` itself. Every body keystroke and every selection next to a composition takes this path; nothing is rebuilt.
   - Rewrite: drop ranges with `to < B`; turn each other range into `EditorSelection.range(Math.max(anchor, B), Math.max(head, B))` (a range ending at `B` becomes a cursor there); if none remains, use one cursor at `B`. Keep the old main range as main if it survived, else index 0. `EditorSelection.create` throws on an empty array and does not validate `mainIndex`, so never pass either.
   - Return `[tr, { selection, sequential: true }]`, the idiom `indentOnInput` uses (`@codemirror/language`). Do not return `{ changes: tr.changes, selection, effects: tr.effects, annotations: tr.annotations, ... }`: `Transaction` does not declare `annotations` in its typings, so that fails `pnpm check`, and the usual workaround (`userEvent: tr.annotation(Transaction.userEvent)` or a cast) drops the other annotations, including `fromHistory` on `select.undo` and `addToHistory`. The sequential form keeps every annotation, effect and the scroll flag, and maps the new selection through an empty change set. `B` from `tr.startState` is also the body start in the new doc: the change filter lets no change below `B` through except the step-4 exception, after which the first body line still starts at `B`.
   - Coverage: Cmd+Up, Mod+Home, ArrowUp, ArrowLeft, PageUp, their shift-extends, select-all-matches, Cmd+Alt+ArrowUp (`addCursorAbove`, whose new range is the main one), `undoSelection` (`select.undo`), the caret after a blocked key, and Cmd+A, the context-menu Select All (`handleSelectAll` in src/lib/core/markdown-editor/MarkdownEditor.svelte calls `selectAll`) and the Edit menu Select All (native `.select_all()` in src-tauri/src/lib.rs, which reaches CodeMirror as a DOM selection change with userEvent `select`; that WebKit's native Select All spans the content is inference, covered by the manual checks). In live preview they select the body only, so copy and cut leave out the hidden frontmatter (owner decision 2026-11-12; source mode is unchanged).

Do not use `atomicRanges` (`deleteBy`'s `skipAtomic` would make Backspace at `B` delete the whole frontmatter), do not filter `input.*`, do not add a keymap that swallows Backspace or Alt+ArrowUp, and do not add `Prec` (it would flip the order against `indentOnInput`, which is registered before `livePreview` in src/lib/core/markdown-editor/setup/editor-extensions.ts and so runs after the guard). Undo and redo dispatch with `filter: false` (`@codemirror/commands` `HistoryState.pop`), so neither filter sees them and Cmd+Z still restores any edit that is in history. Programmatic writes carry no userEvent and pass untouched: the Properties panel and tab sync go through `replaceDoc` in MarkdownEditor.svelte (which also sets `Transaction.addToHistory.of(false)`, so those writes are never in history), meta-bind writes go through `dispatchMetaBindUpdate` (widgets.ts; in history), and tab loads and setState carry none either. Update the stale "Keyboard moves (ArrowUp into the frontmatter) are not changed" line in the `frontmatterClick` doc comment (frontmatter-field.ts:86) and the same sentence in docs/LIVE-PREVIEW.md:36. The e2e at e2e/specs/live-preview/click-reveal/frontmatter.spec.ts:53-65 pins today's ArrowUp behavior (the cursor lands on the first hidden line). That test only recorded the current behavior (Issue 03 Notes); change it to expect the first body line, and say so in the commit.

## Notes

- **Priority:** content safety (bucket 1-content). Upheld content/medium. Cmd+Up+Enter, Alt+ArrowUp or a held Backspace breaks the hidden fence on any note with properties, and autosave writes broken frontmatter. It is visible at once and Cmd+Z restores it, so it is wrong data, not silent loss. The e2e at frontmatter.spec.ts:53-65 pins today's cursor landing (Issue 03 Notes), so this Issue changes it.
- **Risk:** medium, reduced by scope. The change filter sees only `delete*` and `move*`; typing, composition, paste and every programmatic write never reach it. Every pass path returns `true` or the same `tr` object, never a rebuilt spec, and no path may throw (pure arithmetic, no try/catch). Check the userEvent before calling `bodyStart`. The policy comes from reading `@codemirror/state` 6.7.6 and from state-only `node -e` experiments in the deep dive (research/deep-dive-002/scout-s02-codemirror-filters.md section 3), not from a running editor. Write the jsdom cases first and see each fail for the stated reason; if a case behaves differently from this text, stop and report instead of bending the guard or the test.
- **Owner-visible changes (commit message):** Cmd+A and both menu Select All entries select the body only, so Cmd+A, Cmd+C copies no properties, and Cmd+A, Cmd+V of text that has its own `---` block keeps the current properties and puts that block in the body as visible text. Alt+ArrowUp on the first body line does nothing. Backspace at the start of a non-empty first body line does nothing. After a blocked key the next Cmd+Z undoes a smaller step: the blocked key records a selection-only history entry, so the next edit starts a new undo group (harmless, no test).
- **Out of scope (pre-existing, not keyboard edits next to the frontmatter; do not widen the fix for any of these):**
  - An edit typed at a caret that a non-keyboard path left in the hidden lines (a right-click in the top padding, the source to live preview toggle, the first property added to a note whose caret was at 0, a legacy search jump into a property, a Find match in the YAML) still edits the hidden YAML as today. Backspace and Delete there are blocked and move the caret to the body start.
  - `gotoLine` (Mod-Alt-g, installed through `searchKeymap`) sets a selection with no userEvent and is not clamped, so go to line 1 to 3 leaves the caret in the hidden lines, and typing or Enter there edits them as today. A text search found no app binding that overrides Mod-Alt-g.
  - A deletion the browser performs itself during or right after a dead key (CodeMirror leaves keys to the browser while composing, and in Safari and WKWebView also the first key within 100 ms after `compositionend`) arrives as `input.type` and is not filtered. Whether WebKit deletes across the hidden line there at all is unknown; see the manual checks.
  - Starting an accent over a pointer selection that reaches 0 deletes the frontmatter, as today: CodeMirror first deletes a multi-line selection with userEvent `input` when composition starts.
  - A pointer drag from the body into the top padding still selects from 0, so typing over it replaces the frontmatter as today. An `input.drop` into the top padding inserts before the opening fence, as today.
  - Search replace and replace-all still replace frontmatter matches.
  - A note with no line after the closing fence keeps `bodyStart` null (frontmatter-field.ts `bodyStart`) and the guard off, as the mouse path does (frontmatter-field-click.test.ts:150-155). Such a note opens with the caret at the end of the closing fence (`getPositionAfterFrontmatter`, src/lib/core/editor/editor.logic.ts), so typing there still appends to `---`.
- **Accepted:** Ctrl-T at the first body line start does nothing. A multi-cursor deletion that reaches the hidden lines applies only its body part. ArrowUp and Cmd+Up land at column 0 of the first body line (goal column reset). A first body line that is a block widget (table, code, math, queryjs, meta-bind button) shows its source after Cmd+Up, ArrowUp or Cmd+A, as it already does when the note opens. A frontmatter-only note with a trailing newline (what the Properties writer emits) has `bodyStart === doc.length`: typing at the end works, Backspace there does nothing, Cmd+A selects nothing.
- **Vault mods:** a mod dispatch with a `delete*` or `move*` userEvent that touches the hidden frontmatter is narrowed or dropped in live preview. `input*` and dispatches without a userEvent are untouched. The mods source is outside this repo; the owner checks it for such dispatches before launch.
- **Manual checks (owner, real app after delivery; WKWebView is not automatable, Playwright runs Chromium; not a build or review criterion):** after Cmd+Up, dead-key accents (`´` + `a`, `~` + `a`, `^` + `o`) at column 0 of an empty and of a non-empty first body line; a dead key, then Backspace twice fast, at column 0 of a non-empty first body line (the frontmatter must stay hidden and intact); held Backspace at the first body line; Cmd+A, Cmd+C; Edit > Select All from the menu bar with the mouse, then Cmd+C; a meta-bind button with the caret on the first body line, then Cmd+Z; a Properties edit with the caret on the first body line (no Cmd+Z: Properties writes are not in history, so Cmd+Z would undo the previous body edit).
- **Library facts (read in node_modules, not run):** `@codemirror/state` 6.7.6: `filterTransaction` runs change filters first, maps a blocked or narrowed transaction's selection back through the inverse, then runs transaction filters last-registered first on the filtered transaction; `ChangeSet.filter` filters change by change and lets a pure insertion at a range start through; `mergeTransaction` in sequential mode maps the second spec's selection through an empty change set; `EditorSelection.create` throws on an empty array and does not check `mainIndex`; the `Transaction` typings have no `annotations` field; `isUserEvent` matches by prefix. `@codemirror/commands` 6.11.1: `deleteBy` dispatches an explicit cursor at the deletion start; `deleteLine` does `if (from > 0) from--`;
