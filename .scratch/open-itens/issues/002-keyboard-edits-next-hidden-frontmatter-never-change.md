# 002: Keyboard edits next to the hidden frontmatter never change its fences

**Origin:** `audit-2026-11-05` Issue 02, moved here on 2026-11-08. Its PRD, raw evidence and closed siblings stay in `.scratch/archived/audit-2026-11-05/`. Bare Issue numbers in the text below use that feature's numbering; `priority-2026-11-08.md` in this folder maps them to the numbers here.

**What to build:** The frontmatter lines are hidden with per-line `Decoration.replace({})` plus a display:none line class (src/lib/core/markdown-editor/extensions/live-preview/core/hide-lines.ts:14-20, called from plugins/frontmatter-field.ts:23). Only the mouse path is guarded: `frontmatterClick` (plugins/frontmatter-field.ts:88) remaps a press in the top padding to the first body line, and its own doc comment says keyboard moves are not changed (:79, :86). Nothing under src/lib defines atomicRanges, a transactionFilter or a changeFilter, so keyboard commands act on the hidden fence. Cmd+Up puts the selection at 0, and Enter or Delete there edits the opening `---`. Backspace at the start of the first body line deletes the line break after the closing fence (`---First line`), and further Backspaces delete fence characters. Alt+ArrowUp (`moveLine`, userEvent `move.line`) on the first body line moves the closing fence below it, so the YAML block swallows that line. After any of these, `findFrontmatterBlock` (parsers/frontmatter.ts:17-30) no longer finds the block, or it closes the block at a later `---` horizontal rule.

Fix direction: add one exported guard extension in plugins/frontmatter-field.ts and register it in `BLOCK_EXTENSIONS.frontmatter` at live-preview.ts:47 beside `frontmatterField`, `frontmatterGutter` and `frontmatterClick`. The decorator kill switch and source mode then remove it with the rest (live-preview.ts:90-92, 109-111). Compute the hidden range from `tr.startState` with the existing `frontmatterEnd` / `bodyStart` helpers (:53, :62); when `bodyStart` is null the guard does nothing. It acts only on user transactions:

1. **Selection clamp** (`EditorState.transactionFilter`): a transaction with no doc change whose userEvent is `select` (any subtype except `select.pointer`) and that puts a selection range inside the hidden range is rewritten. Ranges with both ends below `bodyStart` are removed (a cursor at `bodyStart` itself stays), ranges that straddle it get their lower end clamped to `bodyStart`, and if no range remains, one cursor sits at `bodyStart`. Return a spec with the new selection plus the transaction's effects, annotations and scrollIntoView. This covers Cmd+Up, Mod+Home, ArrowUp, PageUp, their shift-extends, search's select-all-matches, and Cmd+A and the menu Select All: in live preview they select the body only, so copy and cut leave out the hidden frontmatter (owner decision 2026-11-12; source mode is unchanged). Leave `select.pointer` to `frontmatterClick`, which keeps the selection on purpose when the first body line is a block widget (:82-85, :93); clamping pointer selections would reveal that widget's source.
2. **Change narrowing** (`EditorState.changeFilter`): in a transaction whose userEvent is `input`, `delete` or `move` (`tr.isUserEvent(...)`, which also matches subtypes such as `move.line`, `move.drop` and `input.replace.all`), return the range `[0, bodyStart]`. Changes inside the hidden lines and the line break after the closing fence are suppressed and the rest apply, so a search replace-all still replaces its body matches and Backspace at the start of the first body line does nothing to the fence. A changeFilter range lets a pure insertion at position 0 through (`ChangeSet.filter`), and a programmatic caret can still reach 0 (a right-click in the top padding, MarkdownEditor.svelte:308, then menu Paste as `input.paste`), so a transaction that inserts at 0 returns `false` instead. An insertion at exactly `bodyStart` passes, so Enter at the body start works. Undo and redo (`undo` / `redo` userEvents) pass unchanged, so Cmd+Z still restores a frontmatter write.

Do not make the whole range atomic: CodeMirror's deleteCharBackward deletes an atomic range whole, so Backspace at the first body line would remove the entire frontmatter. Programmatic writes must pass unchanged: the Properties panel, meta-bind writers (`dispatchMetaBindUpdate`, widgets.ts:885-896), tab content sync (MarkdownEditor.svelte:190-194), tab loads and setState carry no userEvent. Update the stale "Keyboard moves (ArrowUp into the frontmatter) are not changed" line in the `frontmatterClick` doc comment (:86). The e2e at e2e/specs/live-preview/click-reveal/frontmatter.spec.ts:53-65 pins today's ArrowUp behavior (the cursor lands on the first hidden line). That test only recorded the current behavior (Issue 03 Notes); change it to expect the first body line, and say so in the commit.

## Notes

- **Priority:** content safety (bucket 1-content). Upheld content/medium. Cmd+Up+Enter, Alt+ArrowUp or a held Backspace breaks the hidden fence on any note with properties, and autosave writes broken frontmatter. It is visible at once and Cmd+Z restores it, so it is wrong data, not silent loss. The e2e at frontmatter.spec.ts:53-65 pins today's cursor landing (Issue 03 Notes), so this Issue changes it.
- **Risk:** medium. The filters run on every user transaction in every note with hidden frontmatter, and a bug there drops user typing. Keep both filters a strict no-op when `bodyStart` is null, the userEvent is not one listed above, or every change and range is at or after `bodyStart`.
- **Owner-visible change:** Cmd+A and menu Select All in live preview select the body only; say it in the commit message.
- **Out of scope:** a note with no line after the closing fence. `bodyStart` is null there (frontmatter-field.ts:62-65), so the guard stays off, as the mouse path does (frontmatter-field-click.test.ts:150-155). Such a note opens with the caret at the end of the closing fence (editor.logic.ts:110-123), so typing there still appends to `---`. Do not widen the fix for it. A multi-cursor edit that straddles the fence is narrowed to its body part, which is accepted.
- **Library facts (read, not run):** `@codemirror/state` 6.7.6 `filterTransaction` and `ChangeSet.filter`; `@codemirror/commands` 6.11.1 `cursorDocStart` and `selectAll` dispatch `select`, `moveLine` dispatches `move.line`, `Mod-Home` is bound on every platform and `Cmd-ArrowUp` only on macOS; `@codemirror/search` 6.7.2 `replaceAll` dispatches all matches in one `input.replace.all` transaction. Details in `research/deep-dive-2026-11-12/refute-002.md`.
- **Files:** plugins/frontmatter-field.ts, live-preview.ts:47, the new test file and e2e/specs/live-preview/click-reveal/frontmatter.spec.ts. It touches neither properties.logic.ts nor properties.service.ts, so its line in `priority-2026-11-08.md` belongs with live-preview frontmatter, not the properties group. It shares no file with 062 and may run beside it (one E2E per checkout).
- **Trigger:** A note with frontmatter (properties, _type, meta-bind) is open in live preview. The user presses Cmd+Up (or ArrowUp from the first body line) and then Enter to make room at the top. Or the user deletes the first body line with Backspace held down, and the key repeat runs past the start of the line. Nothing visible happens on the hidden lines. The fence breaks, the raw YAML appears as body text (the closing `---` turns `status: todo` into a setext heading), and autosave writes it.
- **Evidence (verified by reading code at `5f8003d67`):** src/lib/core/markdown-editor/extensions/live-preview/core/hide-lines.ts:14-20 hides each line with a plain replace and covers no line break; plugins/frontmatter-field.ts:23 hides lines openIdx..closeIdx; plugins/frontmatter-field.ts:76-88 handles the mouse only, and :86 says keyboard moves are not changed; `rg atomicRanges|transactionFilter|changeFilter src/lib` returns nothing; e2e/specs/live-preview/click-reveal/frontmatter.spec.ts:53-65 pins ArrowUp onto the first hidden line; the Issue 03 note (commit 1d58399ad) records it as today's behavior, not a requirement; parsers/frontmatter.ts:10,24-30 needs line 0 and the closing line to match /^---\s*$/ exactly. Re-checked by the 2026-11-12 deep dive at `318b6e9b5`: still present.
- **Second opinion:** upheld (content, medium). The frontmatter is always hidden with per-line replace decorations (hide-lines.ts:14-20), and it is not revealed when the cursor enters it. rg finds no atomicRanges, transactionFilter or changeFilter under src/lib. frontmatterClick only handles the mouse, and its comment says keyboard moves are not changed. The e2e at frontmatter.spec.ts:53-65 shows ArrowUp lands on a hidden line. Backspace at the start of a non-empty first body line merges it with the closing `---`. Enter after Cmd+Up splits the opening fence. Either way findFrontmatterBlock stops matching and autosave writes broken frontmatter. Nothing guards this path.
- **Source:** audit 2026-11-05, domain `live-preview`, finding `N-live-preview-01` (from live-preview-content-1). Size S to M.
