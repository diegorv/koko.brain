# 108: The Tasks list stays mounted, and the rule explains itself

**Origin:** `tasks-view` Issue 04, moved here on 2026-11-08 and rewritten on 2026-11-12 from the Tasks view UX research (`.scratch/tasks-view-ux/research/`) and its review, then corrected by the deep dive (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md`, `dossier-108.md`, `refute-108.md`). Its PRD stays in `.scratch/archived/tasks-view/`. Issue numbers in this text are open-itens numbers. Line numbers are left out on purpose: the view file has changed since the first draft.

**What to build:** The Tasks view (Cmd+Shift+T, "Toggle Tasks View") looks empty and jumpy. This Issue fixes three things without changing what it lists or what a row looks like. The default section tag stays `#to-list`.

1. **The list stays mounted during a refetch.** `buildTaskIndex` (`tasks.service.ts`) sets the loading flag on every call, and the view swaps the whole list for "Indexing tasks..." whenever it is set. A refetch runs on mount, on every index version bump and after every toggle, so focus and scroll are lost.
   - The Tasks store (`tasks.store.svelte.ts`) gains a `hasLoaded` flag with a getter and `setHasLoaded(loaded: boolean)`. It is false at start and after `reset()`. `buildTaskIndex` calls `tasksStore.setHasLoaded(true)` in its `finally`, under the same `request === latestTaskIndexRequest` guard as `setLoading(false)`, so it is set on success and on failure. A call superseded by a newer call or by `resetTasks` never sets it: after a vault switch the new vault shows "Indexing tasks..." until its own first fetch settles. Update the `buildTaskIndex` JSDoc.
   - "Indexing tasks..." shows only while `!tasksStore.hasLoaded`. A list that is legitimately empty stays an empty state during later refetches instead of flashing the loading text.
   - Otherwise the list stays, and while `tasksStore.hasLoaded && tasksStore.isLoading` a `<Loader2 class="size-3.5 animate-spin text-muted-foreground" />` (imported from `@lucide/svelte/icons/loader-2`, as `SearchPanel.svelte` does) inside a `<span role="status" aria-label="Refreshing tasks">` shows at the end of the toolbar. It is absent, not hidden, when idle, and it does not show during the first load (the loading text covers that). Do not add height, padding, gap or wrap classes to the toolbar, and do not put `pane-toolbar` on the span (`src/tests/lib/pane-toolbar.test.ts` allows one `pane-toolbar` class list and forbids overrides on it).
   - The store keeps its groups across a remount (`fileTaskGroups` is module state that only `reset()` clears), so returning to the Tasks tab shows the previous list at once. `EditorView.svelte` unmounts the view on every tab switch, so this is the common path.
   - Keep the row keys (`group.filePath`, `task.lineNumber`) and do not wrap the list in a `{#key}`: focus survives a refetch because the keyed `{#each}` reuses the nodes.
2. **A rule sentence above the list.** A pure `describeTaskRule({ sectionTag, hideCompleted, dateFilter })` in `tasks.logic.ts` builds the sentence from three parts, with no trailing period:
   - `Open tasks` when `hideCompleted`, else `All tasks`;
   - ` under headings containing <tag>` when the trimmed `sectionTag` is not empty, else ` from every note`. The tag is shown trimmed, with a leading `#` added when it is missing, as the Rust match adds one. A whitespace-only tag counts as empty. One private helper in `tasks.logic.ts` does this display for both functions;
   - `, in notes edited in the last 7 days` for `last7days`, `, in notes edited in the last 30 days` for `last30days`, nothing for `all`.

   For example "Open tasks under headings containing #to-list" or "All tasks from every note, in notes edited in the last 7 days". It renders as a `<p>` above the count, and stays visible in the empty state but not while "Indexing tasks..." is shown. The sentence, its button and the empty state read `tasksStore.sectionTag` (the applied tag), not the textbox's pending `sectionTagInput`. When the section tag is set and the list is not empty, a "Clear tag" button (text content `Clear tag`, no `aria-label`) follows the sentence, in a wrapper next to the `<p>`, not inside it. It clears the pending debounce timer, empties the textbox (`sectionTagInput = ''`) and calls `updateSectionTagFilter('')`. In the empty state the sentence shows no button; the empty state's own action does it.
3. **An empty state that names the cause.** A pure `explainEmptyTasks({ groups, sectionTag, hideCompleted, dateFilter })` in `tasks.logic.ts`, where `groups` is the unfiltered `tasksStore.fileTaskGroups` (already limited by the section tag on the Rust side). The view calls it only when the filtered list is empty. It takes no clock: it picks wording, it does not filter again. It returns `{ message: string; action?: { kind: 'clearTag' | 'showCompleted' | 'allTime'; label: string } }` for the first stage that empties the list, in this order:
   1. No group in `groups` holds a task (count tasks, not groups): with a section tag, "No task sits under a heading containing <tag>" (tag displayed as in the sentence) with `{ kind: 'clearTag', label: 'Clear tag' }`; without one, "No tasks in this vault yet" and no action.
   2. With hide-completed on, every task in `groups` has `checked` true, the predicate `filterCompleted` uses: "All N tasks are completed" (N is the number of tasks in `groups`; "The only task is completed" when N is 1) with `{ kind: 'showCompleted', label: 'Show completed' }`.
   3. Otherwise the date filter. With hide-completed on: "No open task is in a note edited in the last 7 days" (or 30); with it off: "No note with tasks was edited in the last 7 days" (or 30). Both with `{ kind: 'allTime', label: 'All time' }`. The view filters by date before it hides completed tasks, so stage 2 can pass while every open task sits in an old note; the first wording covers that case.
   4. With `dateFilter: 'all'` stage 3 cannot be reached from the view (stages 1 and 2 passing leave an unchecked task, which `filterCompleted` keeps). Return `{ message: 'No tasks found' }` with no action, with a comment saying why.

   Its result replaces the bare "No tasks found" in the view. The message renders as a `<p>` and the action as a button that runs the Clear handler above, `tasksStore.setHideCompleted(false)` or `tasksStore.setDateFilter('all')`.
