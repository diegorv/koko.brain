# 233: An Auto Organize move into a folder that already has the name lands the note as `<name> 2`

**What to build:** when a rule moves a note and the destination already holds a file with the same name, the note moves under the first free numbered name (`<name> 2`, `<name> 3`, ...) in one path change, the rest of the run applies at the new path, and an info toast says so.

Today the move fails and the run stops. `moveItem` throws `targetExistsError` when `<dest>/<same name>` exists (`src/lib/core/filesystem/fs.service.ts:307-327`, check at `:312`, message at `:272-274`) and logs through `error()` (`:324`, console and Sentry). `evaluateAndMove` swallows it with a bare `catch { return; }` (`src/lib/features/auto-organize/auto-organize.service.ts:337-342`), which skips the legacy icon, every matched rule's properties, every `createNote` and the mod action (`:348-371`). A lifecycle-archived note keeps `_archived: true` in its old folder, the generated rule keeps matching (`type-lifecycle-rules.ts:41-48`), and every later save fails again in silence.

Rules with a `rename` already pick a free name (`applyRename`, `auto-organize.service.ts:420-478`; loop `:462-477`; `numberedName` and `isAlreadyNamed` in `auto-organize.logic.ts:679-692`), but they rename and then move in two path changes. When another `<name> 2` exists anywhere in the vault, the rename writes the fallback link `[[A/<name> 2.md]]` from its intermediate path (`link-updater.logic.ts:102-104`), the pure move then rewrites nothing (`link-updater.service.ts:39`), and the link silently resolves by basename to that other note. This Issue makes both cases one path change.

## Behavior

1. **One path change.** `moveItem(sourcePath, targetDirPath, fileName?)` gains an optional target file name (`fs.service.ts:307`), default `getFileName(sourcePath)`, so every existing caller (`auto-organize.service.ts:338`, `mod-vault.service.ts:100`, `FilesNavigator.svelte:288`) is unchanged and its `toHaveBeenCalledWith(path, dir)` assertions keep holding. Auto Organize passes it only when it numbers the note. One `applyPathChange` re-paths tabs, tree, the Rust index, search, semantic keys and the mods' `settled` step, so a mod's `onNoteMoved` fires once with the final path. Links to the note are rewritten once, against the final path.
2. **The free name.** A shared, service-private helper picks the name from the loop `applyRename` uses today, probing with `exists()` only (never a folder listing compared as a set; that was Issue 029's bug), checking the destination resolved per candidate (`finalFolder`, `auto-organize.service.ts:455-460`) and, when the note moves, the current folder. It numbers from the full basename and never strips a trailing number: `Chapter 2` becomes `Chapter 2 2`. The loop has an upper bound, so an `exists` that always answers true cannot hang it; past the bound the note stays put, as a refusal (Behavior 4).
3. **Rename rules use it too.** When a rule both renames and moves, `applyRename` picks the name and the move step carries it out in the same single `moveItem` call, instead of `renameItem` then `moveItem`. A rename without a move still goes through `renameItem`.
4. **Notes that are never numbered** stay where they are, exactly as today: not Markdown, inside the system or templates folder, a type definition (all through `propertyWriteSkipReason`, `auto-organize.logic.ts:851-873`), and a Todoist project note (`isRefusedKey`, `auto-organize.service.ts:430-432`). One helper holds these checks for both the collision and `applyRename`, so they cannot drift. For these notes the run checks the target before calling `moveItem`, so it no longer sends `error('FS')` to Sentry on every save; telling the user about them is Issue 082.
5. **Not a collision with itself.** Before treating `<dest>/<name>` as taken, compare `stat` `dev` and `ino` of the source and the target (`stat` from `@tauri-apps/plugin-fs`, already allowed by `fs:allow-stat` and used in `mod-vault.service.ts:107`). The same file means the note is already in its destination: no rename, no move, and the write phase runs. This covers a destination spelled with a different Unicode form (NFC vs NFD) or case than the folder on disk, and a destination such as `./Archive` (`resolveDestination` keeps `.` segments, `auto-organize.logic.ts:961-962`). `isAlreadyInDestination` (`:903-916`) also compares paths with `normalize('NFC').toLowerCase()`.
6. **The rest of the run follows.** The icon, properties, `createNote` and the mod action apply at the numbered path in the same run. The next save of the numbered note does nothing (`isAlreadyInDestination`).
7. **Info toast**, once per numbered move: `Auto Organize moved "<old name>" to <destination> as "<new name>": a note with that name was already there.` No dedupe set is needed: after the move the note is in its destination, so the next save does not move it.

## Notes

- **Owner decisions (2026-11-11):** one path change through an optional `fileName` on core `moveItem` (chosen over rename-then-move inside Auto Organize, which keeps the stale-link bug above and gives mods two `onNoteMoved` events); an info toast on a numbered move; `Chapter 2` becomes `Chapter 2 2`; the never-numbered list in Behavior 4; the `stat` identity check; the test fixture changes in Acceptance. **The in-app overwrite race is accepted, not fixed here:** plugin-fs 2.7.1 `rename` calls `std::fs::rename`, which replaces an existing target, and `moveItem` checks then acts, so two same-name notes moved to one folder in the same burst (a mod writing many notes) can still pick the same name and one can overwrite the other. That race exists today without a collision.
- **Research:** seven scouts and three validators, reports in `/tmp/ao-collision/` (not kept). Line numbers are from `8ed1a8033`; locate each edit by the quoted code after other Issues land.
- **Related, kept separate:** 082 (tell the user about a move that fails: a refused note or a disk error); 054 (moves should be Markdown only); 096 (a root destination builds `vault//`, the move at `auto-organize.service.ts:323`; build the target the way `finalFolder` does); 052 (kanban card links on rename); 100 (canvas file nodes); 044 (File History across moves). Not filed yet: a lifecycle `archiveTo` with `{year}` or `{month}` moves an already archived note again at its first save in a new period (`type-lifecycle-rules.ts:15-17,36-45`, `auto-organize.logic.ts:951`).
- **Known limits, documented, not fixed:** links with a folder prefix keep the old folder (`[[A/Note]]` becomes `[[A/Note 2]]`, resolved through the basename fallback); kanban card links are never rewritten (Rust does not index `.kanban`, `src-tauri/src/utils/fs.rs:143-146`); while both notes share a name, a `[[Note]]` that the TypeScript tree and the Rust index resolve differently is not rewritten (`link-updater.service.ts:29-33`).
- **Not on the never-numbered list, on purpose:** periodic notes and person notes (a move already breaks their canonical path, and the periodic detector lives in `plugins/`, which `features/` may not import); a tab with unsaved edits (the single path change re-paths the dirty buffer).
