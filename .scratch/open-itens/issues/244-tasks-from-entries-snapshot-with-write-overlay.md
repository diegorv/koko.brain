# 244: Tasks come from the entries snapshot, with an overlay for the view's own writes

**Origin:** split out of Issue 115 (`tasks-view` Issue 12) by the 2026-11-12 deep dive (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md` section 4 and the 115 list, `dossier-115.md`, `refute-115.md`, `cross-state-chain.md` H1 to H3, M10, L1, `cross-rust-ipc.md` F11). This is 115b, the fetch half; Issue 115 (115a) builds the heading rule it calls. The PRD and raw evidence stay in `.scratch/archived/tasks-view/` (PRD "Task model", "Freshness after the view's own writes", decision B6). Issue numbers in this text are open-itens numbers.

**What to build:** Source rules need note fields (type, tags, lifecycle, frontmatter) that `get_all_tasks_v2` does not carry. The memoized entries snapshot does (`getVaultEntries()` in `src/lib/core/vault/vault-entries.service.ts`, shared with QueryJS). Move the Tasks view onto it, run the section tags through Issue 115's heading rule, and add an overlay so the view's own writes show at once although the snapshot lags. After this Issue nothing in `src/lib` calls `get_tasks_in_section_v2`; Issue 121 removes it.

**Fetch**
- `buildTaskIndex` (`tasks.service.ts`) reads `vaultStore.vaultIndexVersion` and calls `getVaultEntries()` in the same synchronous turn, before the `await`: that is the version the returned snapshot was read or patched at. It no longer calls `get_all_tasks_v2`, `get_tasks_in_section_v2` or `setFileTaskGroups`. Inside the existing `latestTaskIndexRequest` guard it drops overlay entries (below), then sets `tasksStore.setRows(buildTaskRows(entries, vaultStore.path, parseSectionTags(tasksStore.sectionTag), overlay))`. Keep Issue 108's `setHasLoaded` in `finally` under the guard, Issue 234's `setError` handling (a failed latest request sets the fixed message and leaves the rows untouched; a success clears it; a superseded request touches neither) and the `debug('TASKS', ...)` count line.
- `get_all_tasks_v2` stays: the event calendar and the Todoist scan call it.
- The section filter runs here, so `tasksStore.rows` stays limited by the section tags, as the Rust command left it. Issue 108's empty-state stage 1, Issue 111's `noteTaskCount`/`noteOpenCount` and Issue 236's "N of M open" rely on that. A tag change refetches through `updateSectionTagFilter` as today; the read is the memo, not an IPC.
- Two overlapping `buildTaskIndex()` calls at one version now share one IPC (`versionGated` in `src/lib/utils/inflight.ts` hands out the cached Promise per version).

**Rows**
- In `task-query.logic.ts`, `buildTaskRows` replaces Issue 111's group input:
  `buildTaskRows(entries: readonly NoteEntryV2[], vaultPath: string | null, sectionTags: readonly string[], overlay: TaskOverlay): TaskRow[]`
- For each entry, each task's `headings` is `headingChains(entry.taskHeadings ?? [])[task.heading]`, or `[]` without a heading (Issue 115). A task is kept when `matchesHeading(headings, sectionTags, 'tag')`. The overlay applies to kept tasks; then `checked` (`status !== 'todo'`) and `open` (`isTaskOpen(status)`, Issue 110) are recomputed from the overlaid status. An entry with no kept task gives no row.
- Every `TaskRow` field is filled. Issue 111's fields: the `TaskItem` fields, `filePath` = `entry.path`, `relPath` and `folder` as Issue 111 computes them (`vaultRelativeKey`, Issue 236's `noteFolder`), `noteTitle` = `entry.title`, `open`, `modifiedAt` = `entry.modifiedAt * 1000` (the snapshot is in seconds), `noteTaskCount` and `noteOpenCount` from Issue 236's `noteTaskCounts` over the note's kept, overlaid tasks (after the heading filter, as Rust's section result was), and `parentLine` over the kept tasks. New required fields: `noteType: string | null` = `entry.isA`, `noteTags: string[]` = `entry.tags` (without `#`), `archived`, `organized`, `favorite` (from the entry), `properties` = `entry.frontmatter` (by reference, never mutated) and `headings: string[]`. No `key` field and no flattened metadata.
- Notes come out sorted by `filePath` with `compareTaskPaths` (Issue 234, `tasks.logic.ts`), tasks in document order. Sort a filtered copy: never sort, push into or edit the shared snapshot array, its entries, their `tasks` or their `frontmatter` (QueryJS and the listener read the same objects). Issue 234's group sort in the service goes, since groups no longer exist.
- `fromV2`, the hand-written `FileTaskGroup` type and `tasksStore.fileTaskGroups` with `setFileTaskGroups` are left unreferenced on purpose: Issue 121 deletes them with the Rust command. Reviewers do not flag them. `TaskItem` stays: `TaskRow` extends it and `setTaskStatus` takes it.

**Freshness after the view's own writes**
- The memo is only as fresh as the last version bump, throttled to 2 s and up to 10 s in a burst (`REFRESH_DELAY_MS`, `REFRESH_MIN_INTERVAL_MS` in `src/lib/app/tauri-listeners.service.ts`, indexing rule 12). The direct refetch in `afterTaskWrite` would return the same stale snapshot.
- **Prompt refresh.** `setTaskStatus` (Issue 241, which `toggleTask` calls) calls `vaultStore.requestPromptIndexRefresh()` right before `call('toggle_task_status', ...)`, after the dirty-buffer preflight: the preflight save emits its own `vault-index-updated`, which would consume a flag set before it. Not in `afterTaskWrite`: the command emits `vault-index-updated` before it returns, so the flag must be set before the call. When the call throws, returns `stale`, or returns `updateResult.changed: false`, Rust emits nothing: clear the flag with `vaultStore.takePromptIndexRefresh()`, or the next unrelated event skips the throttle. Issue 246's Due and Priority write follows the same placement when it lands.
- **Overlay.** A module-level `Map` in `tasks.service.ts`, keyed `${filePath}:${lineNumber}`. It is not store state: nothing renders it, and the store holds reactive state only. Its types live in `task-query.logic.ts`:
  `interface TaskOverlayEntry { text: string; status: TaskStatus; version: number }` and `type TaskOverlay = ReadonlyMap<string, TaskOverlayEntry>`.
  `afterTaskWrite(path, updatedContent, written: { lineNumber: number; text: string; status: TaskStatus; version: number })` calls `settleTaskWrite`, records the entry, then refetches. `setTaskStatus` passes the line, the text, the target status and `result.updateResult.version`. Keep the overlay in the tasks feature, not in `core/filesystem/task-write.service.ts`, which the Todoist sync shares.
- **Drop rule.** `buildTaskIndex` deletes the entries whose `version` is at or below the version it read before the `await`. `refresh()` in `tauri-listeners.service.ts` bumps the version, then patches the memo in the same synchronous turn, so a snapshot read at that version already holds the write.
- **Refusals read a fresh snapshot.** The two refusals that refresh the list, `stale` from `toggle_task_status` and the dirty-buffer "line moved" check, call `invalidateVaultEntries()` right before their `buildTaskIndex()` and delete the overlay entry for that key. Without it the refetch returns the snapshot that just proved stale, and a retry is refused again for 2 to 10 s although the message says the list was refreshed. This costs one whole-vault `get_all_vault_entries_v2` per refusal; refusals are rare and user-initiated, and every other reader shares the fresh snapshot afterwards. A changed write does not invalidate: the overlay covers it.
- `resetTasks()` clears the overlay next to the request-counter bump.
- The circle (Issue 021) and the row status menu (Issue 241) read `expectedText`/`expectedStatus` from the overlaid row. Issue 241's Undo keeps the values it captured at write time, which match it; do not rewrite it.

**Behavior changes the user sees** (Issue 115's rule, now live). Update the Section filter part of `help/documentation/10-tasks-and-todoist.md`: case is ignored (`#To-List` matches); a tag matches only as a whole tag, so `#to-listing` no longer matches `#to-list`, while a nested `#to-list/today` still does; a tag right after `(` or another non-space character no longer matches; a task under `### C` below `## A #to-list` / `### B #to-list` is now kept. It still works with several tags, any of them.
