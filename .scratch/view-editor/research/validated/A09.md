## Facts most useful for the agent reference

**Confirmed:**
- **Mounting and source mode:** a `.view` opens as `fileType: 'collection'` (editor.service.ts:137-139). EditorView.svelte:86-90 mounts one CollectionView per path. Source mode is local state (:30) and resets on every tab switch (:47-52). The toggle is at :122-134.
- **Parser errors:** the messages listed in the report are correct (yaml-parser.ts:18-112). `sort[].property` is accepted as an alias of `column` (:71-74). `direction` must be exactly `ASC` or `DESC`. `limit` must be a number >= 1.
- **Top-level `filters`:** not validated at parse time (:101-103). It is checked at query time (collection.logic.ts:136-141, :232-250).
- **Filter semantics:** an object holding `and`, `or` and `not` together requires all three to hold (collection.logic.ts:364-372). An expression that throws while evaluating excludes that record (:356-358).
- **Tab writes:**
  - `renameView` trims the name and silently refuses an empty name, its own name or a duplicate (yaml-parser.ts:388-407).
  - `addView` always appends a table view named `Untitled` (:344-356, CollectionView.svelte:429).
  - `setViewType` keeps the calendar keys (:416-430).
  - `removeView` refuses to remove the last view (:375).
- **What tab rename and delete leave alone:** neither touches `_rail_view`. Only `updateViewEditYaml` syncs it, and only when `_rail_view` already named a view (:298, :319).
- **How `_rail_view` resolves:** exact match, case-sensitive, untrimmed (`" board"` is kept as written, yaml-parser.test.ts:509-510). The first match wins, else `views[0]` (yaml-parser.ts:142-143).
- **The editor never reads `_rail_view`:** yaml-parser.ts:136-141, also documented at help/documentation/12-collection.md:157. On first open in a session it shows `views[0]`. After that it shows the last-used tab, which is kept in memory only (collection.store.svelte.ts:25, CollectionView.svelte:142-148).
- **No UI sets `_rail_view`:** a grep finds no writer except the dialog's sync (yaml-parser.ts:319). It is authored by hand or by an agent.
- **Toolbar writes:** each one writes a single `EDITOR_KEYS` key (key-edit.logic.ts:23), checked for conflicts against the view's name plus the key's value (:47-51).
  - The file is re-serialized and saved at once (type-definitions.service.ts:328-390), so comments are lost.
  - Empty values delete the key (yaml-parser.ts:184-257).
- **Row set in the editor:** it follows the rail's rule (lens.logic.ts:704-721):
  - system-folder notes, type definitions and `.view` files are dropped;
  - archived notes are dropped unless a filter cites `archived` or `_archived`;
  - without a view `sort`, `_sort` order and `_order` pins apply (type-note-list.logic.ts:96-98). The report did not mention the pins;
  - `limit` is applied last;
  - a record with no entry is dropped.
- **Columns:** with `order`, those keys are used, labelled by `properties.<key>.displayName`, else the raw key (collection.logic.ts:454-461). Without `order`, the columns are `file.name` plus every key in the matched records (:463-477).
- **Display names are read-only:** read at PropertiesPanel.svelte:56 and SortPanel.svelte:48, never written. This settles the report's open question.
- **No UI for:** `limit`, `columnSize` (parsed only), `_sort`, `_order`, `_sidebar_label`, `_rail_view`, `properties`.
- **Table rendering:** the table shows 200 rows, then "Show more" adds 200 (CollectionTableView.svelte:20, :85-95). Its only empty text is "No results match the current filters" (:34-37). The cell rules at :62-78 and `formatCellValue` at collection.logic.ts:381-403 are as reported.
- **Calendar picker:** the date property list is every known property, not only dates (CalendarConfigPanel.svelte:59-63). This settles another open question.
- **Calendar empty state:** a grep found no empty-state text in either calendar component (only the placeholders for a missing `dateProperty`, CollectionView.svelte:702-720). `MAX_EVENTS_PER_CELL = 3` (CollectionCalendarView.svelte:36).

**Corrected:**
- **`railViewIgnored`:** the report says any non-null value other than a non-blank string goes there. In fact only non-string non-null values do. A blank string is dropped silently (yaml-parser.ts:118-120, :126-127, test :518).
- **Line folding:** the default width is 80 (node_modules/yaml/dist/options.js:20). The folding is cosmetic: a folded plain or double-quoted scalar parses back to the same value (from memory of yaml v2, not run). `lineWidth: 0` is about readability. The real loss on every write is comments.
- **Filter errors in the editor:** the check runs on the toolbar's round-tripped filters (`filterGroupsToFilter(parseFilterToGroups(...))`, CollectionView.svelte:258-261), not on the raw YAML. Malformed shapes become JSON rows so the error still surfaces (filter.logic.ts:106-110, :133-137). `rowToItem` was not read, so that it round-trips exactly is not verified.
- **Inferred columns:** they always include the derived `organized`, `archived`, `favorite` and `tags` keys, plus every `_*` frontmatter key such as `_type` (collection.logic.ts:63-69, :468-475). A view without `order` is very wide, so agents should always write `order`.
- **`file.name`:** it includes the extension. Use `file.basename` to drop it (collection.logic.ts:29-31, :409-410).

## Implications for the dialog

- Move the `_rail_view` sync into `renameView` and `removeView`, or warn in the editor. Keep the duplicate-name rule the same on both rename paths.
- Show which view the dialog edits: `views[railViewIndex]`.
- The fields to add are `limit`, column order with display names, `_sort`/`_order`, a `_rail_view` picker, plus an `order` default for new views.
- Tell the user that comments are lost on save.
