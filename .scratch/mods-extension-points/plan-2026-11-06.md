# Mod entry points: which Issues, in which order

Goal: the easier mods are to evolve, the more the owner can test in the app without large core changes.

Shorthand: `host` = `src/lib/plugins/mods/mods-host.service.ts`, `contract` = `src/lib/plugins/mods/contract/mod-api.v1.ts`, `MOD_APP` = `src/lib/plugins/mods/mod-app.service.ts:23-53`, `mods:` = `/Users/diegorv/kokobrain-vaults/kokobrain-mods-src`. Other paths are under `src/lib` unless they start with a repo folder. `EP-NN` = Issues proposed here (not created yet). `VM-NN` = the existing `.scratch/vault-mods` Issues. Nothing was built or run: runtime claims are "read, not run".

The first six brain Issues edit no file under `core/`, and `layer-baseline.json` stays at 3 entries. A `core/` store, or a prop passed down from `app/`, is needed only for surfaces core renders (`EditorTabs.svelte`, `MarkdownEditor.svelte`), and those are not scheduled: `app/` may import anything (`scripts/import-graph.mjs`, `if (f.layer === 'app') return null`), so `app/` reads a store owned by `plugins/mods`.

Run brain Issues one at a time with explicit numbers. Each edits `host` and `28-mods.md`, so parallel relay gains nothing. A relay Issue cost 25 to 44 minutes here (`.scratch/vault-mods/ledger.md` Log); a mod change costs seconds. So a brain Issue is judged by how many later experiments stop needing one.

## 2. The principle behind the order

Spend core cost only where a mod cannot get there alone, and try everything else first as a raw spike or in `mods:shared/`. Three tensions, and the choice taken:

- **Stable contract vs raw freedom: raw first, then an unstable per-mod tier, then the contract.** `ctx.app` and `ctx.kb` are already outside the freeze (`host:30-46`, `src/tests/lib/plugins/mods/mod-api-contract.test.ts:62-63`). New surfaces land on `ctx.labs`, promoted to `ModContextV1` when two mods keep using a member. **Cost:** mods hand-type these members (`mods:shared/types.ts:1-4`), and an app change can break them. One author fixes that with `tsc`, so the cost is real but small. See decision 1.
- **Declarative vs render functions: plain data everywhere, with `mount(el)` in exactly one slot.** Palette rows, menu items and pick lists are data the host renders. Mod code runs on an event only, never in a `$derived`, template or list build: `provider.resolve` has no try/catch (`features/rail-shell/lens.logic.ts:434`) and runs in `$derived.by` (`features/rail-shell/RailNoteList.svelte:177-190`). A sync loop there cannot be stopped (`help/documentation/28-mods.md` Limits). The sidebar gets a host-owned `mount` because a panel cannot be data. No widget DSL. **Cost:** no `when`, so an item can show where it will fail softly, and mod DOM gets no style isolation.
- **One generic mechanism vs one per surface: one action with many origins, and a small registry per surface inside the host.** PRD P5 already says later entry points "reuse the same actions" (`.scratch/vault-mods/PRD.md:49`), and rail buttons already reference action ids (`contract:94-95`). No `ctx.contribute(surface, spec)`: that is a union of unrelated shapes. **Cost:** each new surface still needs a small host edit and a render edit.

### EP-01. Raw pack on `ctx.app`

- **API:**

- **Unlocks:** every experiment in section 7's second list, with no further brain Issue.
- **Risk and bound:**
  - `read` runs in an effect. Reading `activeTab.content` re-runs per keystroke (`core/editor/editor.store.svelte.ts:84-86`). Reading `activeTabPath` does not (`:39`), since a keystroke mutates `content` in place. The docs say so, with the one safe example.
  - A handler that reads pages through `ctx.kb()` rebuilds every page per index bump (`plugins/queryjs/kb-api.ts:432-471`), because `patchVaultEntries` makes a new array (`core/vault/vault-entries.service.ts:73-83`). QueryJS blocks pay the same, so the docs state it as a bound: coalesce, or refresh only when the result is on screen.
  - A save observer runs in the sync loop of `notifyAfterSave`, each in its own try/catch, after `applyNoteChange` and invalidation (`core/editor/editor.hooks.ts:81-91`), so Indexing rule 6's ordering holds. Built-ins register first at vault open (`app/lifecycle/app-lifecycle.service.ts:276,435`; mods start at `:535`). One registered later, such as `features/search/SemanticIndexStatus.svelte:23` on mount, runs after a mod's. A handler can only delay the rest, and `on-save.ts` defers.
  - Loops: `updateNoteFrontmatter` writes nothing when unchanged (`core/frontmatter/frontmatter-write.service.ts:129`), so an idempotent handler ends. `ctx.vault.write` has no equality guard (`plugins/mods/mod-vault.service.ts:103-111`), so a handler using it can loop; it is async, so the Labs switch stops it.
  - A thrown observer goes through `error()` (`editor.hooks.ts:89`), hence Sentry, against P9. `on-save.ts` catches first; the owner is the sole recipient.
  - Path calls go through `applyPathChange` (rule 6), no new write path.
- **Test:** new `src/tests/lib/plugins/mods/mod-app.service.test.ts`. Each member is the real object. `watch` fires on change, not at subscribe, not when `updateContent` runs with `read` on `activeTabPath`, not when another tab closes and the active path stays, survives a throw in `read` or `onChange`, stops after dispose. Host test: a mod's observer sees a save and is gone after unload.
- **Blocked by:** none.
- **Trade-off:** C's alternative was to ban the observer and poll `vaultIndexVersion`. Polling gives no path and lags 2 to 10 s (Indexing rule 12), and C's reasons for the ban do not hold given the lines above.

## 6. What NOT to do

- **Generic `ctx.contribute(surface, spec)`:** a union of unrelated shapes loses type help and the per-member freeze. Place on actions; mount in one slot.
- **`when`, `appliesTo` or any callback in a list build, row or render:** puts mod code where a sync loop or throw hurts the whole app, for cosmetic gain.
- **Any new behavior in core write paths for mods:** before-save hook, write pacing, batch writes, adding `notifyAfterSave` to `create`. Indexing rule 6 keeps `save` synchronous with one owner, and the owner rejects this for rare failures.
- **Deep links or meta-bind buttons to mod actions:** `PRD.md:90` says no: outside content must not run vault code.
- **Rebinding UI:** built and removed once. The mod holds its own bindings.
- **Crash guard or safe mode:** renaming the mod's folder recovers (`28-mods.md` Limits). Rare, and it is core startup code.
- **Moving built-in menu items into a registry:** rewrites tested menus for no mod gain. Mods only append.
- **A contract for CodeMirror or fences now:** each reconfigure rebuilds block decorators, and Live Preview invariants would become an API.
- **Migrating every mod to new APIs in the same relay Issue:** migration is a direct commit in `mods:` after each delivery.
- **Long rare-case lists in Issues:** rare, visible and recoverable cases (a row picked during a reload, a menu open during unload) get no guard.
