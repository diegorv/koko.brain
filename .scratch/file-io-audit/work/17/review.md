## Findings

1. major — `src/lib/features/properties/properties.service.ts:90` (`commitChanges`), reached from `PropertyField.svelte:125` (`oninput={handleValueChange}`). A text, number or date property in the panel commits on every keystroke. Typing in one on a note whose frontmatter has a comment, a nested map or a duplicate key now shows a new error toast for every character: `svelte-sonner` gives each call a new id from `toastsCounter`, so the toasts stack. Before this change the edit went through (with the data loss). The refused input also keeps showing the typed text, which was never written. Meta-bind avoids both: it commits on blur or Enter and resets the control. This is not a data-loss risk (the refusal is right), so it does not block. Fix: show the panel refusal toast with a stable id (e.g. `toast.error(msg, { id: \`frontmatter-refused:${path}\` })`, or an optional id on `toastFrontmatterWriteError`) so repeats replace one toast, and re-sync the panel from the note after a refusal (`parseAndSetProperties`, or a key bump on the field) so the input shows the stored value again. Add a test that types two characters on a commented note and asserts one visible toast.
2. minor — `src/tests/lib/features/properties/properties.service.test.ts:409-422`. The test "still adds to a comment-only frontmatter block" (added by architecture-stability Issue 41) was turned into its opposite: a comment-only block such as `---\n# nothing yet\n---` now refuses every panel add. This follows the Issue's rule ("a note with a comment" refuses) and matches `updateNoteFrontmatter`. But a template that writes a placeholder comment block now leaves the note's properties uneditable from the panel until the user removes the comment by hand. That is a visible behavior change the owner should know about; the build report flags it. Nothing pins the neighbouring case any more: an empty block `---\n---` still accepts a panel add. Fix: add a `properties.service.test.ts` case for the empty block, and confirm with the owner that refusing on a comment-only block is wanted (the alternative is to let `detectLossyFrontmatter` ignore a block whose only content is comments, at the cost of dropping that comment).
3. minor — `src/lib/core/frontmatter/properties.logic.ts:360`. `isFrontmatterUnparseable` has no production caller left (the diff removed both callers; only `properties.logic.test.ts` uses it), and the `UNPARSEABLE` sentinel's comment at `:252-256` describes it as the guard's support. Fix: remove the export and its tests in this Issue, or leave it with a follow-up note. Either way, say which.
4. nit — `src/lib/app/deep-link-actions.ts:189`. The capture toast reads `<file>.md: The note's frontmatter could not be parsed; fix it in the note` (or `...has comments; it cannot be rewritten...`). It does not say that the link title and tags were left out, so the user does not learn that the capture is missing its tags. Fix: add a capture-specific suffix, e.g. `; title and tags were not added`.
5. nit — `src/lib/core/markdown-editor/extensions/live-preview/widgets.ts:762`. The meta-bind toast now reads `Cannot set status: The note's frontmatter ...` with a capital `T` after the colon (it was lowercase before), because the shared table is written for the `<file>: <Message>` form. Cosmetic only. Fix: lowercase the first letter in the meta-bind template, or leave it.

## Resolution
