## Findings

1. **major** `src/tests/lib/features/event-calendar/event-calendar.model.test.ts:460` (also :20-21, :193, :242-244) — the new generator limit (`.filter((name) => name !== run.outside)`) hides a fixture bug, not the `followPathChange` limitation the header claims. Seed 103 without it crashes with `TypeError: Cannot read properties of undefined (reading 'match')` in `rustFrontmatter` (fixtures/event-notes.fixture.ts:63). Ops #40 `outsideDelete Standup` then #72 `edit Standup title "Daily sync"` while that delete is in flight: the fixture's calendar `renameItem` (`src/tests/fixtures/calendar-vault.fixture.ts:169`, `disk.set(to, disk.get(from)!)`) writes `undefined` to disk for a missing source, where the real `renameItem` (and the fixture's own `rename` mock at :149-150) throws `No such file`. Probe: with the fixture's `renameItem` throwing `No such file: ${from}` when `!disk.has(from)` and the `run.outside` filter removed, the whole model file passes (22 tests, all 300 seeds). Fix: add that one-line throw to the fixture's `renameItem`, and drop `Run.outside`, its bookkeeping in `fire`, the filter, and the header clause "and no field write targets a note while an outside change of it runs (the limitation `followPathChange` documents)" (and the matching words in the `randomStep` comment and discovery.md's build findings). That way the random runs keep covering a field write during an outside change of the same note.
2. **minor** `src/lib/features/event-calendar/event-calendar.service.ts:651` — the title is planned (`readDir` + `planTitleChange`, :640-643) before `joinPath` waits on the new path's queue, so the plan can be stale when the rename runs. Example: a restore queued on `Y` lands the note at `Y` while the edit waits, and the edit then fails with "Could not rename the note to "Y": a note with that name may already exist". On main the two raced instead. The error is visible and recoverable, and `duplicateEvent` has the same plan-then-join order (but `createFile` re-picks the name there). Fix (optional): re-plan after the join and continue only if the planned path is unchanged, or leave it and add a sentence to the `writeEvent` comment.
3. **minor** `src/lib/features/event-calendar/event-calendar.service.ts:651` — this is a second cross-path wait (with `duplicateEvent` :928), so two tasks can now wait on each other: a rename X -> Y running on X's queue joins Y while an earlier task on Y's queue (an edit or undo renaming Y -> X) joins X. The two `joinPath` calls then wait on each other forever, and `drainEventCalendarWrites` (vault switch, window close) hangs. This can only happen when both X and Y are gone from disk while the store still shows them (each plan needs the other's file to be missing), so the risk is low. Fix: none required. Consider a sentence on the `joinPath` JSDoc noting it must not be taken across a cycle.
