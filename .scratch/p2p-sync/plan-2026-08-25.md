# P2P Vault Sync

Sync a Kokobrain vault between two computers on the same LAN. No server, no cloud account,
no third-party service holding the notes.

## Decisions

| Topic | Decision |
|---|---|
| Network scope | Same LAN. No NAT traversal, no relay, no internet path. |
| Peers | Exactly two machines, both macOS. |
| Transport | `rsync` over `ssh`, both preinstalled on macOS. Nothing hand-rolled. |
| Pairing | An ssh keypair, generated once, public key copied to the peer. |
| Discovery | `<hostname>.local` over Bonjour. No IP is ever typed. |
| Granularity | One folder per side, vault-relative. Empty means the whole vault. |
| Timing | Manual. A button. No background sync, no scheduler. |
| Direction | Pull only. The button writes to the local vault and never to the peer. |
| Deletions | Never propagated. Sync is create and update only. |
| Conflicts | Local wins. The remote version is preserved as a conflict copy. |

## Design principles

Three principles decide every trade-off below. They are the reason the architecture is shaped
the way it is.

**1. The network phase must not be able to lose a note.** A transfer that is interrupted,
truncated, or hostile writes into a disposable staging area, never into the vault. This is
cheaper and more absolute than making the writer defensive: there is a point in the run where
zero vault bytes have changed and the entire payload is already on local disk.

**2. The filesystem is the authority on path identity, not our in-memory model.** APFS folds
case by default. Two machines can disagree about whether `README.md` and `readme.md` are the
same file. Any design that decides "does this file exist locally?" by looking something up in
a map we built earlier is wrong twice over: wrong about case, and stale by the time it writes.
We ask the filesystem, at the moment we write.

**3. Every line of budget goes to the code that writes.** Transport, encryption, framing,
resume, and delta are solved problems available as a binary. Merge semantics on a specific
user's vault are not. The test suite is weighted the same way.

## Architecture

Three layers. Only the third can modify the vault.

### Layer 1 - Transport

`rsync` over `ssh`, invoked from Rust with `std::process::Command`.

sshd is the listener. ssh keys are the pairing. Encryption, authentication, resume, and delta
transfer come from the OS. The app ships no protocol, no framing, no handshake, no listen
port, no accept loop, and no crypto dependency.

macOS advertises the machine's hostname over Bonjour, so the peer is addressed as
`<hostname>.local` and the address survives DHCP lease changes. Resolution is a query, not an
advertisement: the app announces nothing about itself on the network.

The peer must have Remote Login enabled. That is the entire setup on the serving side.

### Layer 2 - Staging mirror

```
rsync -a --delete --exclude <dot-dirs> <peer>:<peer_vault>/<folder>/ <vault>/.kokobrain/sync-staging/<peer>/
```

- `--delete` applies only to the staging mirror, which the app computes and owns. The
  destination is never a user-typed path. Task 3 asserts this before the process is spawned.
- Dot-directories are excluded. `<vault>/.kokobrain/` holds a live SQLite database with an open
  WAL and the ONNX model blobs. Copying a live database file corrupts it silently, and a
  corrupted index is worse than a lost note: notes have conflict copies and file history, the
  index has neither. The exclusion pattern must be verified to apply recursively, not only at
  the top level (Task 3).
- When this layer returns, the vault is byte-for-byte unchanged and the full payload is on
  local disk.

Cost: staging holds a copy of the synced folder. For a markdown vault this is megabytes.
`ponytail: full staging mirror, revisit with --link-dest or a hash-only listing if a vault with
large attachments makes the disk cost real.`

### Layer 3 - Merge

Walk the staging tree. For each file, decide, then write. This is the only code in the feature
that can modify the vault.

**State:** `<vault>/.kokobrain/sync-state.json`, shaped
`{ "<peer>": { "<rel_path>": "<sha256 of the last content both sides agreed on>" } }`.
One hash per entry.

**Decision table, evaluated per file at write time:**

| # | Condition | Action |
|---|---|---|
| 1 | `fs::read(dest)` returns `ErrorKind::NotFound` | Write it. `agreed = remote_hash` |
| 2 | `local_hash == remote_hash` | No write. `agreed = remote_hash` |
| 3 | `local_hash == agreed` (only the remote moved) | Write it. `agreed = remote_hash` |
| 4 | Anything else (both moved, or no baseline) | **Local wins.** Write the remote content to `<stem> (conflict <peer> <remote_hash[..8]>).<ext>`. Leave `agreed` unchanged. |

Two consequences worth stating explicitly, because they are what keep this table at four rows:

- **The local hash is read from disk at write time, not collected up front.** Principle 2. A
  case-folded name is found rather than overwritten, and a local save that lands during the run
  is seen rather than clobbered. There is no local-state data structure to build or invalidate.
- **The conflict copy's filename carries the remote hash, so writing it twice is a no-op.**
  Idempotence is a property of the name, not of a "have I seen this remote version" field. That
  field does not need to exist, and repeated syncs cannot pile up copies or overwrite a copy the
  user has since edited.

**The most dangerous line in the feature** is row 1. It must match `ErrorKind::NotFound` and
nothing else. An `EACCES` or `EIO` treated as "no local file" reads as permission to overwrite.
This gets a dedicated test.

### Path safety

One function, `resolve_dest(vault, rel) -> Result<PathBuf>`, and one call site, because there
is one writer.

1. Reject absolute paths, any `..` component, any dot-prefixed component, and `:`.
2. `create_dir_all` the parent, then `canonicalize` **the parent** and assert it
   `starts_with` the canonicalized vault root. Canonicalizing a path whose leaf does not exist
   yet cannot detect a symlinked intermediate directory, which is the case that lets a write
   escape the vault.

The same rules run on the names coming out of staging and on anything we generate. A rule
applied on one side only produces files that are advertised and then permanently refused.

## Out of scope

| Not built | Why |
|---|---|
| Per-folder expose/subscribe negotiation | One person, two personal machines, one vault. A single folder path per side covers it. Revisit only if a machine must be prevented from receiving specific folders. |
| Deletion propagation | Additive sync cannot destroy a file it was never allowed to remove. Reconciling deletes manually is the cheaper failure mode. |
| Background or scheduled sync | If a manual button turns out not to get pressed, that is a verdict on the feature, not a reason to add a scheduler. |
| More than one peer | Two machines. |
| Content-hash transfer decisions | rsync decides what to move by size and mtime; the merge still decides by SHA-256. Ceiling: badly skewed clocks can skip a changed file of identical size. `ponytail: mtime-based transfer skip, add rsync -c if clock skew ever produces a missed update.` |
| A status pane, progress bar, or per-file log | A summary line after the run. |

## Settings surface

- **Peer host** - e.g. `macbook.local`
- **Peer vault path** - absolute path on the peer
- **Folder to sync** - vault-relative, empty for the whole vault

Plus a **Pull from peer** button and the last result: `downloaded / conflicts / skipped /
errors`.

The button is labelled "Pull from peer", not "Sync now". The design is one-directional, which
means the button lives on the machine that lacks the data. A full exchange is one press on each
machine and the label should say so rather than imply otherwise.

## Testing rules

1. **Every guard that prevents data loss names the test that fails when the guard is deleted.**
   Not "there is a test nearby". Delete the guard, the named test goes red. The guards: the
   `NotFound` discrimination, the parent-canonicalize containment check, each path rejection
   rule, the staging-path assertion before `--delete`, and the `local_hash == agreed`
   comparison.
2. **The merge is testable without rsync.** Layer 3 takes a staging directory as input; merge
   tests build it by hand with `tempfile`. Only Task 3 needs a subprocess.
3. Per project rule, every computed getter in the store has a test, and every suite covers
   happy path, empty input, and error handling.

## Prerequisites

Two existing bugs on `main`. Sync is the first feature that rewrites many vault files at once,
so both fire on the first real run and both land before Layer 3 does. Neither is sync-specific:
`git pull`, Dropbox, and any external editor hit them identically.

## Notes

**Target size:** roughly 400-500 Rust LOC and 200 TS LOC, with the test weight concentrated on
`merge.rs`, `decision.rs`, and `paths.rs`.

**Ordering constraint:** Layers 1 and 2 are inert without Layer 3 and safe to land first. The
feature is not enable-able until Task 8 is complete and its guard tests are proven to fail when
their guards are removed.

**If Remote Login on the peer is unacceptable**, Layer 1 does not exist and the app has to carry
its own authenticated encrypted transport. That is a different and considerably larger plan.
Layers 2 and 3 are unchanged by it: the staging barrier and the four-row merge do not care how
the bytes arrived.
