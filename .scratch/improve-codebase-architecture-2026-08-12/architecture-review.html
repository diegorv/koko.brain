1 · Give “a note changed” one owning module

Strong in-process

Three explorers reached this independently — from the Rust seam, from lifecycle orchestration, and from filesystem operations. It is the same missing module seen from three sides.

Problem

Mutating a note has no module. The caller must know a five-step ordered protocol — markRecentSave → write bytes → update_note_in_index → syncExternalContentToEditor → clearIndexedEntry for path changes — and the 15+ call sites each implement a different subset.

Solution

One module owning “a note changed on disk”: writeNote(path, content) and forgetNote(path), with the per-source policy (save / edit / watcher) as its implementation rather than as four hand-rolled fan-out lists.

Deletion test

Delete the module and the five-step protocol reappears at 15+ sites in five distinct subsets — which is exactly today's state. Complexity concentrates. The sibling shape already exists: notifyAfterSave is this module for “content changed at P”, and nothing downstream re-assembles it.

Live divergence found during verification

Commit 473146f fixed “absolute path used as an FTS/semantic key” in watcher-handler.service.ts:117. The identical derivation in search.service.ts:316-318 still falls back to the absolute path — doing exactly what the other copy's comment forbids. One copy was fixed; its twin was not, and no task file tracks it. Separately, collection.service.ts:108 removeNoteFromIndex has zero production callers, so deleted notes linger as phantom pages (tracked as M08).

What the merge must not flatten

  • The typing path's omission of invalidateQueryjsCache and the FTS/semantic IPCs is deliberate — running ONNX inference on a 1 s typing pause is a regression. Keep it as explicit per-source policy.
  • The bare-write sites currently rely on the Rust watcher picking them up. Adding markRecentSave suppresses the watcher, making the explicit notify load-bearing — a behaviour change needing the trace-before-remove ritual.
  • closeTabsForDeletedPath must stay before the disk op (commit 7070e56), so the path side needs a before/after pair, not one trailing call.

Contradicts ADR-0008 — worth an amendment, not a reopening

The parameter set must be re-derived from those two genuinely different variations. Also: the settings toggle list needs a names-only export, or it drags katex, mermaid and DOMPurify into its import graph.

3 · Make persistence a property of the settings module

Strong in-process

Problem

Changing a setting is a two-step contract every caller must remember — mutate the store, then separately trigger a save — repeated across 58 onchange() calls in 17 files plus 14 external saveSettings sites in 9 modules, with nothing checking step two happened.

Solution

One persistence owner: a single $effect reading settingsStore.settings and calling one debounced save under untrack(), so mutating the store is persisting it.

Before — two arrows per site, four debounce policies

After — one arrow per site, one policy

Wins

  • Interface shrinks: sections take zero props
  • One seam owns persistence
  • 72 call sites lose a duty
  • Locality: one debounce policy, not four
  • Tests hit one interface, not seventeen

Deletion test

Delete the onchange prop and the 13 non-panel saveSettings imports: every site reduces to a bare settingsStore.updateX(...). Nothing is pushed back onto callers. The store's setters fail the same test in the opposite direction — deleting those spreads spread-merge logic across 92 sites — so they earn their keep.

The two-step contract has already been forgotten, on main

AppShell.svelte:102 and :109 call updateLayout({leftSidebarVisible: …}) with no save, while the identical toggles at global-keybindings.ts:109-120 and command-palette.service.ts:163-183 do persist. Toggling a sidebar with the button is forgotten across restarts; toggling it with ⌘B is not. That is exactly the silent regression the two-step contract predicts.

Under-costed by the proposal

Three suppressions are needed, all internal to the settings module, so the depth win holds: (a) resetSettings() during teardown (app-lifecycle.service.ts:421) would otherwise schedule a write of DEFAULT_SETTINGS; (b) the effect's first run happens over un-hydrated defaults and needs a hydration gate or it clobbers settings.json; (c) two await saveSettings(...)-before-toast sites become fire-and-forget.

Test impact

Nothing in src/tests/lib/core/settings/ asserts that a mutation reaches disk — the store suite checks spread merges, the service suite calls save/load directly, and no sections/*.svelte test exists. Verifying today's shape honestly would need ~17 component files asserting 58 handlers each remembered a second call — tests at the wrong granularity. After: one test (mutate, advance timers, assert the written value) covers all 72 sites.

6 · Give the VaultIndex snapshot one reader

Worth exploring in-process

Problem

Ten call sites each invoke get_all_vault_entries_v2 and keep their own copy of the result; vault.rs:478 clones and sorts every NoteEntry per call. Three of them then hand-roll a different version-gate spelling on top.

Solution

One version-keyed snapshot memo behind an entries() interface. Scope it to the snapshot only — not to a general subscribe protocol.

Five test suites test the same three describe-blocks against five different implementations. tags.service.ts:103 exports flushScheduledTagIndexRebuild, marked “test-only”, purely so a test can observe private module state — a test reaching past the interface.

Half of this candidate was refuted — read before acting

The tempting framing (“one reader owning version gate + in-flight + latest-wins for everyone”) is a category error. The version-gate owners read targeted commands (get_backlinks_v2, get_outgoing_links_v2, get_all_tags_v2) and never touch the snapshot; the snapshot readers own no version gate. Only two consumers are in both sets. Burst collapse is already centralized — tauri-listeners.service.ts:104 bumps the version inside a 300 ms debounce, so the missing guards in tasks.service.ts and GraphView are covered. And subscribe(fetch, apply) cannot express the real variation, so it would ship a shallow module. What survives is the narrow, real win: a version-keyed memo for the ten snapshot call sites.

Wins

  • Snapshot fetched once per version, not ten times
  • Drops a per-render full-vault fetch in queryjs
  • Removes the “pass entries down if you have them” hack
  • Leverage: one interface, ten call sites

Deletion test

initializeVault has exactly one production caller, and that caller shrinks from a 38-line then/catch/else block to two calls. Merging in this direction concentrates; merging in the other spreads eight ordered steps into a component.

Defect found during verification, not claimed by the explorer

initializeVault early-returns — and therefore resolves — at six points (:133, :160, :163, :192, :207, :224). The +layout .then tail fires autoOpenDailyNote and maybeAutoCheckForUpdates anyway — including when open_vault_db failed or a rapid vault switch invalidated the init. Moving the tail inside makes that guard automatic.

Scope it down

Do not move the listener registrations. They are app-mount scope, not vault scope: registerDeepLinkListener must be live before any vault is open — deep-link.service.ts:130-139 stores a pending action and calls vaultStore.open() precisely because the listener caught a URL with no vault open. Same for the close handler, the menu listener and quick-capture.

Test impact

No test directory covers src/routes at all. Nothing anywhere asserts that opening a vault opens the daily note, that the update check runs after settings load, or that a vault switch saves dirty tabs before teardown. The existing suite even asserts the daily-note step is not part of the interface. After the merge, those three become plain assertions in the existing suite with the same Tauri-only mock set.

Checked and rejected

Six candidates did not survive verification. Recorded so they are not re-proposed.

  • Merge the two note-creation modules. Their contracts differ (“collision-free name in folder F” vs “open path P, create from template”). Merging yields an options bag with mutually-exclusive mode flags — a shallow module. The real defect is narrower: createFile hardcodes empty content, so five callers write real content afterwards while markRecentSave has already suppressed the watcher.
  • One hub for the external-note-write protocol. The writer inventory was wrong in both directions; two of the eight claimed writers do not write. Superseded by candidate 1.
  • Resolve a sidebar selection in one module. The eight switch sites dispatch on genuinely different concerns; collapsing them moves complexity rather than concentrating it.
  • One registered discipline for the five widget render caches. The caches store different things on purpose (live DOM, sanitized HTML string, SVG markup, query data) — CLAUDE.md documents why. One adapter each, no real seam.
  • Collapse the .collection YAML write paths · make the filter-row mapping one table. Both are local tidy-ups, not depth changes. The two query languages are also genuinely justified — merging them would need a JS-chain→AST translator and would grow complexity.

Top recommendation

Give “a note changed” one owning module

Three explorers reached it independently from three different subsystems, which is the strongest structural signal in this review. It is the only candidate whose absence is already producing shipped defects rather than predicted ones: an active ADR-0009 violation in renameItem and moveItem, a bug fixed in one copy of the vault-relative path rule and left standing in its twin, and a removal function with zero callers leaving phantom pages behind. Every other candidate improves code that currently works.

It is also the largest, so start with the forgetNote half — three call sites, two of them already wrong, and an ADR that already specifies the correct behaviour. That lands the seam and the test surface before the fifteen-writer side needs touching.

Runner-up: candidate 2 — the cheapest Strong result here. Eleven verbatim copies, a factory shape already proven in this repo for the inline track, and no behaviour change beyond deleting eleven provably dead guards.
