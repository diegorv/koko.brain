## Findings

1. **major** `src/lib/plugins/mods/mods-host.service.ts:439` and `:446-453`: a mod loads twice when a watcher batch for it arrives while `startModsHost` is still in `exists(modsPath)` / `readDir`. The listener is registered before those awaits; `requestReload` bumps the folder epoch and its `reloadFolder` starts; then `startModsHost` calls `loadMod`, which captures the already-bumped epoch, so neither load is superseded. Both `onload`s run and `liveMods` holds two instances of the mod (reproduced by the probe above; self-heals at the next reload or stop). This breaks the Issue's "drop a load that finishes after a newer one started". `rediscoverMods` racing the start has the same cause. Fix: after `readDir`, have `startModsHost` skip every folder that already has an entry in `reloadRunners` (only this generation's listener can have created one, since the stop at the top clears the map), or route the start's loads through `requestReload`; add a host test that emits a batch between calling `startModsHost` and awaiting it and asserts one `load` event.
2. **minor** `src/lib/plugins/mods/mods-host.service.ts:380`: the serialized runner awaits `loadMod`, which awaits the mod's `onload`. A reloaded mod whose `onload` never settles holds the runner forever, so every later save of that mod only sets `dirty` and the fixed code never loads until the mod is switched off and on or the app restarts. Fix: since `reloadFolder` already unloads an instance still in `onload`, let the runner not wait on `onload` (or record this explicitly as Issue 06 scope in its Notes).
3. **minor** `src/lib/plugins/mods/mods-host.service.ts:368-372`: `reloadFolder` unloads the mod before `exists(.../manifest.json)`. If `exists` rejects, the mod is gone but its row still says `loaded`, and the failure only reaches `error('MODS')`. Fix: on a failure after the unload, upsert the row as `error` with the message (or check `exists` before unloading).
4. **nit** `src/lib/plugins/mods/mods-host.service.ts:374-377`: a `manifest.json` deleted while the folder stays drops the row, but a restart lists that same folder as `error` ("cannot read manifest.json"). Within the Issue's "unload only", so acceptable; note it in the discovery defaults or match the restart's row.
5. **nit** `src/lib/plugins/mods/mods.logic.ts:37`: a mod folder whose name has a `.` is loaded (as an error row) at start, but its deletion reported as the folder alone is ignored, so the stale error row stays until a restart or rediscover. Fix: drop the single-segment `.` rule, or document it.

## Resolution

1. Fixed. `startModsHost` skips every folder that already has a reload runner after `readDir` (only this start's listener can have made one, since the stop at its top clears the map). Test: "a batch that arrives before the start lists the mods folder loads the mod once" (failed with two loads before the fix).
2. Fixed. `loadMod` takes `waitForOnload` (default true); `reloadFolder` passes false, so the runner resolves once `onload` is called. A newer reload still unloads an instance whose `onload` runs, and that `onload`'s result is dropped. Test: "a reloaded mod whose onload never settles does not block the next save".
3. Fixed by checking `exists(manifest.json)` before unloading: a rejected check leaves the running mod and its `loaded` row, and goes to `error('MODS')`. Test: "a failed check for manifest.json keeps the running mod and its row".
4. Kept, as the Issue's "unload only" asks; the difference from a restart's error row is now in `reloadFolder`'s JSDoc.
5. Kept the single-segment `.` rule (the Issue lists a README directly in the mods folder as ignored); the stale row for a deleted dotted folder is now in `mapModChanges`'s JSDoc.
