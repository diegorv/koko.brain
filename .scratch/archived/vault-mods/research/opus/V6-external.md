### Web (primary sources)

- **Obsidian** (https://obsidian.md/help/plugin-security, no page date): S26's quotes on Restricted Mode, "cannot reliably restrict plugins to specific permissions", the three capability lines, and the automated scan and scorecard all match verbatim.
- **Obsidian PluginManifest** (https://docs.obsidian.md/Reference/TypeScript+API/PluginManifest): `id`, `name`, `version`, `minAppVersion`, `description`, `author`, `authorUrl?`, `isDesktopOnly?` and `dir?`. There is no permissions field.
- **QuickAdd** (https://quickadd.obsidian.guide/docs/UserScripts/): S26's claims match, including the `params` contents, no hidden folders, `.js` or an md js block only (2.30.0 stops the macro), the `require()` warning about full Node/Electron access, and secrets local to the app profile.
- **Elastic, PHANTOMPULSE** (https://www.elastic.co/security-labs/threat-command/phantom-in-the-vault, 2026-04-14): Shell Commands plus Hider (v1.6.1). The victim had to turn on "Active community plugin list" and "Installed community plugins" in Sync, both off by default and local to the device. Quote: "an attacker cannot remotely force the installation or enablement of a community plugin via vault sync alone." Payloads are PowerShell on Windows and `osascript` plus a LaunchAgent on macOS.
- **Tauri iframe IPC.** CVE-2024-35222 / GHSA-57fm-592m-34r7 (2024-05-23, fixed in 2.0.0-beta.20) stopped injecting IPC into iframes on macOS and added an invoke key. Invoke stays reachable from an iframe "on Windows when the origin of the Tauri window and the origin of the iFrame are the same." wry PR #1874 (https://github.com/tauri-apps/wry/pull/1874, opened 2026-10-04, **open, unmerged**) reports that on Windows (WebView2) and Android, Tauri's main-frame-only init scripts, `__TAURI_INTERNALS__` and the invoke key included, are injected into **every** frame, sandboxed `srcdoc` included. A tester found `data:`, sandboxed `srcdoc` and cross-origin frames could invoke commands on Android, and called it a regression of the CVE. The same PR reports macOS, Linux and iOS as unaffected.
- **MCP spec**: the latest revision is **2026-07-28** (https://modelcontextprotocol.io/specification/latest, schema `schema/2026-07-28/schema.ts`). Its standard transports are stdio ("newline-delimited messages over the standard streams of a client-launched subprocess") and Streamable HTTP (https://modelcontextprotocol.io/specification/2026-07-28/basic/transports). The changelog (https://modelcontextprotocol.io/specification/2026-07-28/changelog) says the revision removes protocol sessions and `Mcp-Session-Id`, removes the `initialize` handshake (every request carries version and capabilities in `_meta`), adds a mandatory `server/discover`, replaces the GET stream with `subscriptions/listen`, and removes SSE resumability. Server-initiated requests are replaced by Multi Round-Trip Requests (`InputRequiredResult`). Roots, Sampling and Logging are deprecated. HTTP+SSE, deprecated since 2025-03-26, is reclassified as Deprecated under the new lifecycle policy, which has a 12-month minimum window.
- **The previous revision**, 2025-11-25 (https://modelcontextprotocol.io/specification/2025-11-25/basic/transports), still had `MCP-Session-Id`, an `MCP-Protocol-Version` header, and the Origin-validation and localhost-binding MUSTs and SHOULDs for servers.
- **MCP TypeScript SDK v2** (https://github.com/modelcontextprotocol/typescript-sdk, `packages/client/package.json`) ships `@modelcontextprotocol/client` 2.4.0. It is split from `@modelcontextprotocol/server`, v2 was released 2026-07-27, and it implements 2026-07-28. v1 lives on as `@modelcontextprotocol/sdk`. The client exports are `.`, `./stdio`, `./ext/skills` and `./validators/*`, and a `./_shims` subpath has a `browser` condition. The v2 docs (https://ts.sdk.modelcontextprotocol.io/v2/llms-full.txt) say the root `Client` "Runs anywhere: browsers, Workers, Node" and that `StdioClientTransport` "spawns the server as a child process, so it is exported from `./stdio`", which is Node-only. The dependencies include `cross-spawn` and `eventsource`.
- **Anthropic Messages API from a browser** (https://platform.claude.com/docs/en/manage-claude/authentication#browser-based-applications): a cross-origin request is accepted only with `anthropic-dangerous-direct-browser-access: true`, which the TS SDK sends when `dangerouslyAllowBrowser: true`. ZDR or Compliance-API organizations get a 401 (`CORS requests are not allowed for this Organization`). The restriction applies only to requests that carry an `Origin` header. The TS SDK (`@anthropic-ai/sdk` 1.6.0, API version `2026-10-21`; https://platform.claude.com/docs/en/cli-sdks-libraries/sdks/typescript) accepts a custom `fetch` in its constructor (`new Anthropic({ fetch })`).
- **Claude Agent SDK, TypeScript** (https://code.claude.com/docs/en/agent-sdk/typescript): `@anthropic-ai/claude-agent-sdk` "bundles a native Claude Code binary for your platform" and spawns it as a subprocess (`spawnClaudeCodeProcess`, and `close()` "terminate[s] the underlying process"). Its runtime option is `'bun' | 'deno' | 'node'`. It cannot run inside a webview. Its options include `model`, `agents: Record<string, AgentDefinition>` with a per-agent `model` (`'haiku'`, `'opus'`, ...), `maxBudgetUsd`, `permissionMode`, `cwd` and `mcpServers`.
- **`claude -p`** (https://code.claude.com/docs/en/headless and https://code.claude.com/docs/en/cli-reference):
  - Flags: `--output-format text|json|stream-json`, `--json-schema`, `--model`, `--agents <json-or-file>`, `--max-budget-usd` (print mode, covers subagent spend, client-side estimate), `--max-turns`, `--mcp-config` / `--strict-mcp-config`, `--permission-mode`, `--allowedTools`, `--add-dir`, `--no-session-persistence` and `--bare`.
  - `--bare` "never reads OAuth credentials or the system keychain" and needs `ANTHROPIC_API_KEY` or an `apiKeyHelper`. The docs say it "will become the default for `-p` in a future release".
  - Without `--bare`, a `-p` run "runs the hooks in a project's `.claude/settings.json` and connects the servers in its `.mcp.json`, even in a folder you've never trusted", with no trust dialog.
  - `--output-format json` reports `total_cost_usd`.
- **VS Code**:
  - Manifest (https://code.visualstudio.com/api/references/extension-manifest): requires `name`, `version`, `publisher` and `engines`; also has `main`, `browser`, `activationEvents`, `contributes` and `capabilities`. **There is no permissions field.**
  - Activation events (https://code.visualstudio.com/api/references/activation-events): since 1.74, contributed commands and views no longer need `onCommand` or `onView`. `*` is discouraged in favour of `onStartupFinished`.
  - Contribution points (https://code.visualstudio.com/api/references/contribution-points): `contributes.commands` (command, title, icon, category, `enablement`), `contributes.menus` (`when`, `commandPalette`), `contributes.viewsContainers.activitybar` (id, title, icon; the analogue of a rail button), and `contributes.configuration`.
  - Workspace Trust (https://code.visualstudio.com/api/extension-guides/workspace-trust): `capabilities.untrustedWorkspaces.supported: true | false | 'limited'` (default `false`, which keeps the extension disabled until the workspace is trusted), a required `description`, `restrictedConfigurations`, `workspace.isTrusted` and `onDidGrantWorkspaceTrust`.

## Refuted or corrected claims

1. **S29, "CSP at `tauri.conf.json:28`."** The CSP is at line 29. Line 28 is `"security": {`. S26 had it right.
2. **S29, "only window labelled `main` (line 16 title)."** There is no `label` key. Line 16 is the title. `main` is the implicit default label (`app_exit.rs:16`). S29 also missed the runtime `composer` window (`lib.rs:135-153`).
3. **S29, "Per-window capabilities can keep privileged Rust commands away from a mod surface."** For this repo that is false. Capabilities do not gate app commands at all, because `build.rs:23` defines no `AppManifest::commands`, and Tauri allows every registered command in every window and webview by default. A dedicated mod window or webview with an empty capability could still call `create_note`, `rename_note`, `read_files_batch` and the other 61 commands. Option (b) in S29 implication 4 only works after an `AppManifest` is added and every existing window gets explicit command permissions. That is a cross-cutting change.
4. **S29, "on Linux and Android Tauri cannot distinguish an iframe from its window."** Incomplete and partly inverted for the current threat. The primary-source picture as of 2026-10 is this. On **Windows and Android**, sandboxed `srcdoc` frames receive `__TAURI_INTERNALS__` and the invoke key and can invoke (wry PR #1874, unmerged). On **macOS and Linux**, subframes do not get the bridge. The capabilities-doc warning is about telling requests apart. The bigger gap is that Windows and Android inject the bridge into the frame. So S29 open question 2 has a provisional answer: on Windows, yes, a sandboxed mod iframe can likely call `invoke` directly. That is unverified in this app and must be spiked.
5. **S29, "Node removed its experimental [ShadowRealm] support in 2026."** False. nodejs/node#65650 is **open and unmerged** (opened 2026-08-29, held for the Sep 29 to Oct 1 TC39 meeting). The rest stands: Stage 2.7, no browser implementation, WPT tests dropped (wpt#59794).
6. **S26, "No consent step found" for QueryJS.** Incomplete. The `autoRunQueries` policy exists (`settings.types.ts:273-281`), but its default `'first-open'` (`settings.store.svelte.ts:141`) **auto-executes** vault code when a note opens. So QueryJS is not only unconsented. It is a standing auto-run path for vault-delivered code with full main-frame IPC (all app commands plus the fs and http plugin scopes). Any mod trust model that leaves QueryJS as it is guards only the smaller door.
7. **S26, "fs read/write scoped to `$DOCUMENT/kokobrain-vaults/**` and `.kokobrain` (around lines 37-46)."** Incomplete. `$HOME/kokobrain-vaults/**` is granted too, `$APPLOG` gets write, mkdir and exists, and the grants span `:36-222`. More importantly, the fs-plugin scope is not the whole file-access surface: the Rust app commands (`read_files_batch`, `create_note`, `rename_note`, and others) are not ACL-scoped (see 3).
8. **S26, "a mod in the same context can call `invoke()` on any allowed Tauri command."** Understated. It can call every registered app command (no allowlist exists) plus the plugin commands granted to `main`. INFERRED: code inside `new Function` in the main frame can reach `window.__TAURI_INTERNALS__.invoke`, because Tauri injects it into the main frame. Not executed in this session.
9. **S29, "Remote URLs can be granted capabilities via `remote.urls`; `withGlobalTauri` defaults false."** True but irrelevant to the threat. `withGlobalTauri: false` only hides `window.__TAURI__`. `window.__TAURI_INTERNALS__` is still present in the main frame (Tauri issue #12404 and discussion #11586 both show it in use). INFERRED from those sources; not tested here.
10. **S26 on CustomJS** used only secondary sources. I did not re-verify it. Treat it as unverified and non-load-bearing.

## Answers to the scouts' open questions

- **S27, MCP spec version and transports.** The latest revision is 2026-07-28. Its transports are stdio and Streamable HTTP. HTTP+SSE has been deprecated since 2025-03-26 and is formally "Deprecated" in 2026-07-28. The 2026-07-28 revision is stateless: no `initialize`, no sessions, a mandatory `server/discover`. Servers on 2025-11-25 or earlier still use the `initialize` handshake and `MCP-Session-Id`. A client that wants to talk to both must implement the version detection in https://modelcontextprotocol.io/specification/2026-07-28/basic/versioning.md (not fetched; gap).
- **S27, can the TS SDK run in a webview?** The v2 client root is runtime-neutral ("browsers, Workers, Node"), with a `browser` shim. Streamable HTTP from a webview still hits two walls in this app:
  - CSP `connect-src` (`tauri.conf.json:29`) blocks any MCP host not listed.
  - The server's CORS policy applies to an Origin-bearing webview request.

  Routing through `@tauri-apps/plugin-http` avoids CORS (precedent: `tauri-fetch-adapter.ts:1-26`), but each host must then be granted in `http:allow-fetch*` (`default.json:223-266`). Whether the v2 `StreamableHTTPClientTransport` accepts a custom `fetch` is NOT verified.
- **S27, what does a stdio server need?** The client must spawn and own the server process (spec: "client-launched subprocess"). The SDK's `./stdio` is Node-only (`cross-spawn`). In Tauri this means either a Rust command that spawns the process and pipes newline-delimited JSON-RPC over events or channels, or `tauri-plugin-shell` with a scoped sidecar or command allowlist. Neither exists today (`Cargo.toml:21-72`, the `lib.rs:325-389` handler list). Spawning a user-named command is arbitrary code execution, so the executable and arguments must come from a consented manifest, not from mod code at runtime.
- **S28, which path fits "30 haiku + 10 opus write a PRD into the vault"?** Compare the three options:
  - **(a) The Messages API from the webview** requires the CORS header, adding `api.anthropic.com` to CSP or to plugin-http scope, and storing an API key in the app. It gives no agent loop, no tools and no file writes; Kokobrain would have to write the orchestrator itself. It also fails for ZDR or Compliance-API organizations if sent with an Origin. Routing via plugin-http (Rust reqwest) probably sends no browser Origin (INFERRED; plugin-http header behaviour not verified).
  - **(b) The Agent SDK** needs a Node, Bun or Deno host process. It cannot run in the webview, so it would mean shipping a JS sidecar. It does have exactly the right knobs: `agents` with per-agent `model`, `maxBudgetUsd`, `cwd` = vault, and `mcpServers`.
  - **(c) `claude -p`** spawned from Rust with `--agents` (per-agent `model: haiku|opus`), `--output-format stream-json`, `--max-budget-usd`, `--permission-mode`, `--allowedTools`, `--add-dir <vault>` and `--no-session-persistence`. It needs the `claude` CLI installed and either the user's login (non-bare) or `ANTHROPIC_API_KEY` (`--bare`).
  - **Verdict, INFERRED:** (c) is the cheapest MVP, because one Rust "run agent job" broker command reuses Claude Code's orchestration, subagents and budget cap, and keeps keys out of mod code. (b) is the same engine with more packaging cost. (a) means building an agent runtime.
  - **Two hazards for (c).** First, a non-bare run with `cwd` set to the vault auto-loads any `.claude/settings.json` hooks and `.mcp.json` inside the vault with no trust dialog. A shared vault could plant those, which is the same delivery chain as PHANTOMPULSE. So use `--bare` plus explicit `--mcp-config` / `--agents`, or run with a cwd outside the vault and `--add-dir`. Second, whether one `-p` run will actually fan out to 40 concurrent subagents, and with what concurrency limit, is not documented on the pages read.
- **S30, minimal manifest shape.** None of VS Code, Raycast or Obsidian has a permission field. VS Code's nearest concept is workspace-level trust (`capabilities.untrustedWorkspaces`). A vault-mods manifest therefore has no direct prior art for declared permissions. If permissions are added, they are Kokobrain's own invention and are only as strong as the broker that enforces them. A shape grounded in the sources (INFERRED synthesis):
  - from Obsidian and VS Code: `id`, `name`, `version`, `minAppVersion` (like Obsidian `minAppVersion` and VS Code `engines`) and `description`;
  - `entry` (a `.js` file, like Obsidian `main.js` and QuickAdd user scripts);
  - `contributes.rail[]` with `id`, `title` and `icon` (like `viewsContainers.activitybar`), and `actions[]` with `id`, `title` and `description` (like Raycast commands and VS Code `contributes.commands`);
  - `preferences[]` with `type` including `password` (Raycast);
  - and `permissions[]` such as `vault:read`, `vault:write`, `http:<origin>`, `mcp:<server-id>` and `agents:claude` with a budget, enforced in the broker.

  Activation should be lazy, on click (VS Code ≥1.74 style), not `*`.
- **S29 Q2, can a sandboxed `srcdoc` frame call `__TAURI_INTERNALS__.invoke`?** Per the wry PR: no on macOS and Linux, yes on Windows and Android until PR #1874 lands. This still needs an in-app spike on each target OS.
- **S29 Q3, multiwebview.** Not answered here. Note that even with a child webview, finding 3 applies: app commands are open to it unless an `AppManifest` is added.
- **S26, provenance.** The only prior art found is an Obsidian forum feature request (not shipped). No primary-source signing scheme for user scripts was found in Obsidian, Templater or QuickAdd.

## Constraints the vault-mods design must respect

1. **Capabilities are not a command boundary in this repo.** Because `build.rs:23` uses no `AppManifest`, every one of the 64 app commands (`lib.rs:325-389`) is callable from any webview or window. A mod surface can only be isolated from them in one of two ways. Either it gets no IPC bridge at all (an opaque sandboxed iframe on macOS or Linux, with the Windows exception below), or the PRD adds `AppManifest::commands` and explicit per-window command permissions for `main` and `composer` first.
2. **Windows (and Android) iframes get the IPC bridge**, sandboxed ones included, until wry #1874 or an equivalent lands. On those platforms a sandboxed iframe is not a boundary. The PRD must either scope the MVP to macOS (and Linux), or isolate with a separate webview plus an AppManifest, or accept full trust. `bundle.targets` is `"all"` (`tauri.conf.json:63`).
3. **The trust model is the security boundary, per all prior art.** Obsidian, Templater, QuickAdd, VS Code and Raycast give extension code full host power. None has enforced per-extension permissions. Declared permissions are only real if a broker the mod cannot bypass enforces them.
4. **Consent must be keyed to vault content, and re-asked on change.** PHANTOMPULSE shows that a shared or synced vault delivers code plus config. A new or changed mod file (hash) must not run without a fresh consent. The consent record must live outside the synced vault, or it syncs along with the payload (INFERRED).
5. **QueryJS already auto-runs vault JS** in the main frame by default (`settings.store.svelte.ts:141`, `kb-api.ts:413,552`). The mod trust story is incomplete unless the PRD at least states this. Whether to bring QueryJS under the same consent is an owner decision.
6. **Network egress needs explicit grants.** CSP `connect-src` (`tauri.conf.json:29`) and `http:allow-fetch*` (`default.json:223-266`) allow only fixed hosts. "Call any HTTP API" from a mod needs either a broker in Rust (reqwest exists, `Cargo.toml:65`) or widening plugin-http scope. Widening it applies to all main-frame code, QueryJS included.
7. **stdio MCP and agent CLIs require process spawning in Rust.** None exists today. The executable and arguments must come from consented configuration, not mod runtime strings.
8. **Agent orchestration belongs host-side.** Use `claude -p --bare` (or the Agent SDK in a sidecar) with explicit `--agents`, `--mcp-config`, `--max-budget-usd` and `--permission-mode`. Do not run a non-bare `claude -p` with cwd set to the vault: it would execute vault-planted `.claude/settings.json` hooks and `.mcp.json` servers with no trust dialog.
9. **Target the current MCP revision with fallback.** 2026-07-28 is stateless (no `initialize`, no `Mcp-Session-Id`, `server/discover` required). Older servers still need the handshake. HTTP+SSE should not be implemented.
10. **Do not plan on ShadowRealm.** SES is the only language-level sandbox, and it does not isolate the DOM or bound resources.
