This scout returned its answer without writing the report file. The validator for its theme (research/opus/V*.md) answered the question from the code; trust that over this summary.

## Summary

The templates plugin runs no user code. Its "Templater-compatible" `<% %>` handling is a regex replace plus a hand-written string parser (src/lib/utils/template.ts:28 and 188-216) that knows only tp.file.title, tp.date.now(...), "+" concatenation, string literals and custom variables, and returns unknown expressions as literal text. The only places user-authored code runs are the two QueryJS sites, both via `new Function`: src/lib/plugins/queryjs/kb-api.ts:413 (`kb.view()` scripts read from the vault by queryjs.service.ts:4-6) and kb-api.ts:552 (fenced ```queryjs blocks, called from queryjs-block-widget.ts:256). There is no sandbox, Worker or iframe for either path (ADR-0010 rejected a Web Worker sandbox, docs/adr/0010-queryjs-kb-api-caching.md:71), and the default policy `autoRunQueries: 'first-open'` (settings.store.svelte.ts:141) runs blocks without a click (queryjs-block-widget.ts:136-147). Vault mods would therefore have no existing sandbox to reuse; the only precedent is in-renderer `new Function` with full `kb`/`dv` access, and the templates parser cannot serve as an expression engine.

- Templates flow: TemplatePicker.svelte:15 filters templatesStore; templates.service.ts:20-48 loadTemplates reads _templates/*.md via readDir; templates.service.ts:55-69 createFileFromTemplate calls openOrCreateNote; note-creator.service.ts:49-64 loadNoteTemplate reads the file and calls processTemplate; note-creator.service.ts:100 renders before create_note writes the file. Nothing is executed as code.
- processTemplate is also used by deep-link-actions.ts:188 and by quick-capture note-composer.service.ts:38-46. These are substitution-only as well, with the same parser.
- Trust-boundary check for QueryJS script paths is a plain substring test: kb-api.ts:534-536 rejects any path containing '..' and does not canonicalize. That is weaker than ADR-0020 (docs/adr/0020-path-security-absolute-canonicalize.md), which applies to Rust commands. The frontend readTextFile in queryjs.service.ts:5 is not checked against any Tauri fs scope in this read.
- Rust side: no JS engine or eval-like crate was found in src-tauri (grep for eval, Function, vm, rquickjs, boa, deno, v8). The only process spawn is osascript at src-tauri/src/quick_capture/source.rs:244.
- Tests use new Function in src/tests/lib/plugins/queryjs/kb-api-contract.test.ts:197 and src/tests/help/queryjs-features-scoping.test.ts:160, which mirror the runtime pattern.
- Open question: what Tauri fs scope and capabilities (src-tauri/capabilities, not read here) allow readTextFile to reach outside the vault, and whether a vault script can reach Tauri globals or invoke commands from inside new Function. INFERRED: the function body sees window globals, so it can, but this was not verified.
- Open question for vault mods: the QueryJS kb API is the closest prior art for a plugin-like surface (kb-api.ts:52-90 class KBAPI, kb-ui.ts for DOM). A mod API would need a decision on sandboxing (Worker/iframe with postMessage, as ADR-0010 rejected for DOM reasons), on whether 'first-open' auto-run applies to mods, and on a permission model for MCP, HTTP and LLM calls. None of these exist today.
- Limitation: the dynamic `import()` sweep was run once across src with quoting, and it found only chunk and module loading (widgets.ts:613, kb-ui.ts:919, file-icons.icon-data.ts:85), none of it fed by vault content.
