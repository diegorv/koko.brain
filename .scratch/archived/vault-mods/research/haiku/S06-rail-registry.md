## Summary

Rail buttons are not a free-form registry. railItems() (rail-items.logic.ts:30-60) builds the rail from hardcoded built-ins (Search, Inbox, Today, Favorites at :36-41; Types, Files at :42-46; Archive at :47), the navigators in railRegistryStore (registered at runtime, :41-46 of rail-registry.store.svelte.ts), and pins derived from vault files (:57). The only runtime-registrable button shape is a RailNavigator {id, label, icon, component, lens} (rail-shell.types.ts:175-186), and its component renders in the navigator pane, not a modal (AppShell.svelte:215). Registration is hardcoded at vault open (app-lifecycle.service.ts:257-263) and unregistered at teardown (:571-572); no loader lets vault-authored JS call registerNavigator. Items have no handler field: a click goes to selectRailItem (rail-navigation.ts:14-22), which sets layout.railItem. Layout keys (railItem, railHidden, railOrder, railInboxBadge) persist in .kokobrain/settings.json; pins persist as `_rail: true` in the .view or type-definition frontmatter, not in settings. Pin order comes from `_order` or TypeMetadata.order, not railOrder. A modal-action button therefore needs a new item kind or a new API surface, which is a design decision for the PRD.

- Item fields (rail-items.logic.ts:8-19): key, label, group ('top' | 'navigator' | 'pinned' | 'bottom'), optional navigator, optional pin. There is no icon field on RailItem (icons come from navigator.icon, BUILT_IN_ICONS in Rail.svelte:47-55, or resolveIconForPath for pins at Rail.svelte:141), no handler, and no order field on the item itself.
- Navigator registration replaces by id (rail-registry.store.svelte.ts:42) and unregister matches by identity (:44). Built-in keys are not checked: a navigator with id 'inbox' would collide with the built-in Inbox key. restoreRailItem checks RAIL_ITEM_LENSES first (lens.logic.ts:199-202), so the built-in would win (INFERRED from reading that order; not run).
- Pins cannot be hidden (lens.logic.ts:183-186) and are not affected by railOrder (rail-items.logic.ts:4, 27-29; LayoutSection.svelte:35 passes [] for pins). Pin keys are absolute paths (`view:<abs path>`, rail-pin.logic.ts:4-18), so moving a .view file changes its key and triggers staleRailPinFix at AppShell.svelte:177 (lens.logic.ts:246-249), which falls back to Today.
- railRegistryStore.reset() (rail-registry.store.svelte.ts:73-78) has no caller in src/lib; only tests reference it (not verified).
- Existing precedent for vault-authored JS: the QueryJS engine runs user code through new Function (src/lib/plugins/queryjs/kb-api.ts:413, :552) behind a versioned contract (queryjs/contract/kb-api.v1.ts). I did not check whether QueryJS can reach railRegistryStore.
- ADR-0003 applies: features/ may not import plugins/, so plugin contributions are wired by app-lifecycle.service.ts. Vault mods would need a separate registration surface, for example an object passed in at vault open (INFERRED, not researched further).
- Implications for the PRD: (1) a modal action button needs a new RailItem kind with a click handler, since a navigator always renders a pane; (2) the mod's button key must be stable because railHidden and railOrder are key-based; (3) mod keys need a namespace to avoid built-in collisions; (4) pins are a vault-file mechanism, so a mod-declared pin would need its own persistence, not layout.railItem.
- Open questions: whether the modal button should be a new item kind or a navigator with an inert lens (hacky); where mod buttons sit in group order; whether mod entry points persist in the vault or in settings.json; how mods reach the registry without importing internals (a sandbox or API boundary decision).
