## Summary

A vault .js file cannot be loaded as an ES module today. The CSP at src-tauri/tauri.conf.json:29 sets script-src to 'self' 'unsafe-eval' with no asset:, http://asset.localhost or blob: source, so import() of an asset:// or blob: URL is blocked. The only working path is the one the codebase already uses for QueryJS: read the file with the fs plugin (src/lib/plugins/queryjs/queryjs.service.ts:4-5) and run it through new Function (src/lib/plugins/queryjs/kb-api.ts:413, 552), which 'unsafe-eval' permits. That path runs classic script bodies with injected parameters, not ES modules, so import/export statements and relative imports between mod files are unavailable unless the mod loader provides its own resolver. The fs read scope only covers $DOCUMENT/kokobrain-vaults and $HOME/kokobrain-vaults (src-tauri/capabilities/default.json:36-82), so a vault at any other path cannot be read, and the owner needs to decide how that scope is widened.

- Config: assetProtocol is enabled (tauri.conf.json:30-43) and the protocol-asset feature is on (src-tauri/Cargo.toml:22). The asset scope includes $DOCUMENT/** and $HOME/kokobrain-vault/** (singular), while the fs read scope uses kokobrain-vaults (plural). The two scopes do not match and should be reconciled.
- convertFileSrc is used in one place, src/lib/app/editor-host.ts:1 and :113 (assetUrl for images). No code path uses it to load scripts. Dynamic import() appears only with literal specifiers (about 35 occurrences in src excluding tests; the one in the runtime path is kb-ui.ts:919 import('chart.js/auto')). Nothing imports a dynamic or vault-relative path.
- Security: unsafe-eval is already in script-src, so new Function and eval are already available to any code the webview runs. Adding blob: or asset: to script-src would add little extra execution power. The real exposure is privilege: vault mod code runs in the main webview, which holds the main capability (default.json, including fs read/write scoped to kokobrain-vaults, opener, dialog and http:allow-fetch for api.todoist.com and raw.githubusercontent.com). Any mod gets those permissions, and a real sandbox would need an iframe with an opaque origin plus a postMessage bridge (INFERRED from general web platform behavior, not verified in this repo).
- HTTP for MCP/API actions: tauri-plugin-http is registered (src-tauri/src/lib.rs:313) and the frontend adapter uses it (src/lib/features/tasks/tauri-fetch-adapter.ts). The request runs in Rust, so the webview CSP connect-src (tauri.conf.json:29) does not limit it; only the http capability URL allowlist does (default.json ~line 224). Whether that governs the mod case is INFERRED and not verified.
- Versions: tauri 2.12.5 and tauri-plugin-fs 2.7.1 from src-tauri/Cargo.lock:5372-5373 and :5558-5559. CSP behavior described above is from reading the config. I did not check Tauri's docs for how the asset protocol and CSP interact, so that part is from memory.

How a user-chosen vault outside kokobrain-vaults would reach the fs plugin is an open question. Grep for kokobrain-vaults in src and docs found only one file, src/routes/(app)/+page.svelte. The default vault location is not confirmed.
- Options for the owner: (a) keep the QueryJS pattern, read via fs and run with new Function, wrapped in an async IIFE, and build a small require-style resolver for multiple files; (b) add blob: to script-src and import() blob URLs, which gives real ES module semantics at little extra risk given unsafe-eval; (c) run mods in a sandboxed iframe with a message bridge, which isolates them but is the most work. Option (b) is the smallest change to get true modules.
