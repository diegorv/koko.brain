## Findings

1. minor — `src/lib/core/filesystem/fs.logic.ts:577` (`insertTreeNode`): no check for dot-prefixed segments. `scan_dir` skips every dot-prefixed name (`vault.rs:146`), and the Rust watcher drops any path with a dot segment (`watcher.rs:71-79`). An app create of a hidden name therefore now appears in the explorer, and no watcher event ever removes it; only the next full load does. Two paths I traced: QuickSwitcher "create" on a query `.x` calls `createFile(vault, '.x.md')`, which bypasses `getFileNameError`, and a deep-link `new` with a dot-prefixed `file`. Before this branch, the `refreshTree` rescan hid these at once. Fix: return `tree` unchanged when any segment of the vault-relative path starts with `.` (for `moveTreeNode`, apply the removal only), plus a `fs.logic.test.ts` case.
2. nit — `src/lib/core/filesystem/fs.service.ts:148` (`addToTree`), app-lifecycle step 4: a create made while the initial `loadDirectoryTree` is in flight can be overwritten when that load lands. The build report's "the create's own watcher event puts it back" does not hold in this window: `startWatching` runs only at step 7 (`app-lifecycle.service.ts:500`), after the event already happened. Before, `refreshTree` bumped `treeLoadGeneration` and superseded the initial load. The window is rare and fixes itself on the next full load. If it is worth closing: have `addToTree` bump `treeLoadGeneration`, or re-apply pending inserts when a load lands. Otherwise, add it to the Issue's known limits.
3. nit — `src/lib/core/filesystem/fs.service.ts:132` (`currentTreeOrder`): app changes now read `fsStore.folderOrder` from memory. Before, each change went through `loadDirectoryTree`, which re-read `.kokobrain/folder-order.json`. The watcher ignores `.kokobrain/`, so an outside edit to that file now applies only on the next full load, not on the next create or rename. That looks acceptable; I record it so it is a known change, not a surprise.
