## Findings

1. minor — docs/adr/0029-frontmatter-yaml-canonical-form.md (Trigger window / amendments): `serializeProperties` no longer writes only from the value. When it rewrites an existing note, an unchanged unquoted number or boolean keeps its source token, so `True`, `0x1F` and `1e3` are no longer normalized on a UI write. ADR-0029, the canonical-form contract that external producers follow, says nothing about this. Fix: add a short dated amendment saying that number and boolean scalars keep their source spelling unless the write changes their value, and pointing to `plainScalarsByKey` / `SOURCE_TOKEN_TAG` in properties.logic.ts.
2. nit — src/lib/core/frontmatter/properties.logic.ts:616: `source.value === p.value` is false for NaN, so an untouched `x: .NaN` (or `.NAN`) is still rewritten as `.nan`. It is outside the Issue's list and harmless in practice. Fix: compare with `Object.is(source.value, p.value)`, which also keeps `-0` and `0` apart.
3. nit — src/tests/lib/features/properties/frontmatter-number-spelling.test.ts:122: `expect(lineFor(after, 'done')).not.toBe('done: True')` would also pass if the toggle deleted the line or wrote garbage. Fix: assert the exact line the toggle writes (`done: "false"`, the behavior noted in the build report).

2. Fixed: the guard in `serializeProperties` compares with `Object.is(source.value, p.value)`; a new properties.logic.test.ts case (`x: .NaN` round-trips) failed before the change and passes after.
