## Findings

1. minor — `src/lib/app/tauri-listeners.service.ts:81`: when `prepareForExit` rejects (for example a calendar drain fails), the error only goes through `error()`. To the user, Cmd+Q does nothing, with no message. CLAUDE.md § Error Handling says user-facing errors should be shown via toast. Fix: in the catch, `toast.error(...)` with a message saying the app could not finish saving before quitting and that the user can try again. Assert the toast in the "logs and stays open when the exit flush fails" test. This can go in a follow-up Issue.
2. nit — `src/lib/app/tauri-listeners.service.ts:76` / `src-tauri/src/lib.rs:168`: every Cmd+Q re-emits `app:exit-requested`, and the listener has no in-flight guard. A second Cmd+Q while a flush or the discard prompt is pending starts a second `prepareForExit`: a second save pass and possibly a second "Failed to save" prompt. Fix: ignore the event while a run is in progress (a module-level `exitInFlight` flag, reset in `finally`), with a test that fires the handler twice.
3. nit — `src-tauri/src/lib.rs:163-170`: the build report already states that Quit has no escape when the main webview never answers (the layout is not mounted yet, the webview hung, or a flush promise never settles). Dock Quit and Force Quit still work, and a timeout would kill the app while the discard prompt is open, so I accept the trade-off. Record it in Issue 44 so the owner's Cmd+Q check also covers a Cmd+Q right after launch.

## Resolution

1. Fixed. The `app:exit-requested` handler's catch now calls `toast.error('Kokobrain could not finish saving before quitting. Try quitting again.')`; the "logs and stays open when the exit flush fails" test asserts the toast, and a new test asserts no toast when the exit goes on.
2. Fixed. A per-listener `exitInFlight` flag, reset in `finally`, makes a request that arrives during a running flush or discard prompt a no-op. Tests: two requests fired back to back run one flush and one `confirm_exit`; a request after a cancelled one runs the flush again.
3. Recorded, no code change (the trade-off is accepted). Issue 44 has a Notes entry on the unanswered-webview case with the Cmd+Q-right-after-launch manual check, and Issue 01's Notes add that case to the owner's manual check.
