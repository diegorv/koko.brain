## Findings

1. minor, `src/lib/features/collection/CollectionView.svelte:365-370` (with the sync effect at `:242-253`): adding or removing a formula on a view with an explicit `order` now never persists the matching `formula.<name>` column. The sync effect changes `localColumns` only locally, and only `handleColumnsChange` writes `viewOrder`. Before, the next Sort or filter edit wrote `viewOrder: localColumns` and carried the column along. `resolveColumns` (`collection.logic.ts:459`) shows only `order` when it is set, so after a reopen a new formula column is gone and a deleted formula's column stays in `order`. The discovery's default ("A formula change writes `formulas` only") says the old formula write missed this as well, but it leaves out that later edits used to fix it. Fix: when a confirmed formula change makes the sync effect change `localColumns` and the view has an `order`, also `persistKey('viewOrder', ...)` with the synced list. Or record it as an accepted gap in the Issue or a follow-up. It does not block this Issue's criteria.
2. nit, `src/lib/features/collection/CollectionView.svelte:312-320`: the `run` transform passed to `rewriteView` has side effects (`selfYaml`, `onApply`, `written`), but `rewriteViewFile` documents that `transform` must be pure because it can run twice (`type-definitions.service.ts:345-348`, and the redo at `:409` when the tab closes before its save). In `EditorView` the tab is always open at the start, so only the tab-closed redo can hit this, after the component is destroyed. A second `onApply` there only touches dead state, so this is harmless today. A one-line comment saying this is safe would stop the next writer from relying on a single run.
3. nit, `src/lib/features/collection/CollectionView.svelte:172,345-350`: if the user switches view tabs while a root-key write (`filters`, `formulas`) is still in flight, the seed effect rebuilds `toolbarBase` from `yamlContent`, which does not hold that write yet. A second edit of the same root key before the first write settles is then refused with a spurious "This view changed" toast. The end-of-write re-seed then restores the right state, so nothing is lost. This needs an edit, a tab switch and a second edit inside one read+save, so no change is asked for.
