## Findings

1. minor — src/lib/core/markdown-editor/extensions/live-preview/parsers/fenced-code-block.ts:139-144 — Inside a container, an opening fence indented past the container column is accepted, but CodeText does not strip the fence's own indentation the way CommonMark requires (content lines lose up to the fence's indent). Probe: `>  ```demo\n>  a\n>   b\n>  ```` gives `" a\n  b"` instead of `"a\n b"`. The same happens for `- item\n\n   ```demo\n   a\n    b\n   ```` (fence 1 column past the list content). A tab in list-item content is also stripped whole (`  a\n\tb` gives `"a\nb"`). This is also inconsistent with the top level, where the same indented fence is rejected (line 141) and stays raw. The impact is low because YAML, JS and mermaid tolerate a uniform extra indent. Fix: either reject a container fence whose `fence.from` is past the container's content column, mirroring the top-level rule, or strip up to that many leading spaces from each content line. Add a parser test for the chosen behavior.
2. nit — src/lib/core/markdown-editor/extensions/live-preview/parsers/fenced-code-block.ts:142-144 — A top-level block whose body is only blank lines now yields one extra newline. Probe: ```` ```demo\n\n``` ```` gives `"\n"`, where the old line slice gave `""`. The fix commit claims top-level blocks are unchanged. The consumer impact is negligible (an empty YAML or mermaid source renders the same error or empty state). Fix: drop a trailing `\n` that the last CodeText carries when it ends at the closing fence line, or accept the change and document it in the `content` JSDoc. A one-line parser test either way.
3. nit — src/lib/core/markdown-editor/extensions/live-preview/parsers/fenced-code-block.ts:62-65 (pre-existing, outside this diff) — `findAllFencedCodeBlocks` keeps only the last CodeText as `contentFrom/contentTo`. So a plain ```` ```js ```` block in a blockquote or callout shows only its last line in CodeBlockWidget. My probe: `> ```js\n> a = 1\n> b = 2\n> ```` gives the content `"b = 2"`. The Issue's premise that plain blocks "render" in containers holds only for single-line bodies. The fix is not in scope here; it is recorded in work/03/discovery.md. Fix: open a follow-up `.scratch` Issue that reuses the CodeText join from `findSpecialFenceBlocks` for the generic code-block path.

## Resolution

1. Fixed. `findSpecialFenceBlocks` now rejects a fence that starts past its container's content column (`startsAtContentColumn` in parsers/fenced-code-block.ts): right after the line's quote marker and one optional space in a blockquote, and at the list content column the marker line sets in a list item. This mirrors the top-level rule (column 0, now in the same helper), so the block falls back to a plain code block. Parser tests: "skips a fence indented past the content column of its container" (`>  `, `> >  `, a list fence one column past content, an ordered list) and "accepts a fence at the list content column the marker line sets", plus a list inside a quote. The tab sub-case is not fixed: a fence indented with a tab is now rejected (columns count characters), but a tab inside a content line is still stripped whole by Lezer's `CodeText`; matching CommonMark's partial-tab expansion needs column-aware re-expansion for a case YAML forbids and JS / mermaid tolerate.
2. Fixed. `content` is now built per line between the fences (one entry per line, filled from the `CodeText` slices on it, blank when it has none) and joined by `\n`, so a blank-only body gives what the old line slice gave: one blank line `''`, two `'\n'`, in a quote and a list item too. Parser test "gives one content line per line between the fences when the body is blank".
3. Out of scope, as the finding says: opened `.scratch/live-preview-audit/issues/07-plain-code-block-in-container-shows-last-line.md` (needs-triage).
