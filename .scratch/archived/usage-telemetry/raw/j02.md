## Summary

- **Pre-vault errors are never reported.** Sentry (JS and Rust) is only initialized after `initializeVault` loads that vault's settings. Boot, the vault picker, and any error during the settings load are lost. This follows from per-vault consent, so it is a design limit, not a bug. It matters for a daily-use owner, because crashes at launch are invisible.
- **Real vault-switch leak, JS side.** On a switch, the old JS client keeps capturing for up to 2 s (the flush timeout) before `activeDsn` is cleared. Errors from the new vault's settings load can go to the old vault's DSN in that window.
- **Real vault-switch leak, Rust side.** The Rust client is reconfigured after the JS flush, so Rust panics during that window also go to the old DSN.
- **Ordering is otherwise sound.** Every path closes JS before reconfiguring Rust, and enabling configures Rust before starting JS. Superseded inits return before configuring Sentry, and the config queue serializes operations.
- **Tests do not cover the window.** `configureSentry` is mocked in the lifecycle test, so the timing hazards are not exercised.

## Findings

**F1. medium. Errors before a vault's settings load are never captured (JS and Rust).**
- Claim: No error is reported at boot, on the vault picker, or during `loadSettings`. JS capture is a no-op until a client exists, and no client exists until `configureSentry` runs.
- Evidence: `src/lib/core/settings/sentry.service.ts:112-113` (`if (activeDsn === null) return;`). `src/lib/app/lifecycle/app-lifecycle.service.ts:199` (`loadSettings`) then `:203` (`configureSentry`). `src/routes/(app)/+layout.svelte:81` is the only `initializeVault` caller, and it runs only when a vault is open. On the Rust side, `src-tauri/src/lib.rs:321` only calls `.manage(SentryState::default())`, and the client is created only by the `configure_sentry` command (`src-tauri/src/commands/sentry.rs:7-13`, `error_monitoring.rs:49-55`). Boot panics go unreported, for example the `expect` at `lib.rs:261` or the `register_multiple` call at `lib.rs:300`.
- Fix: Accept and document the gap in PRIVACY.md and the Sentry section, or add a separate, explicit app-level opt-in for boot errors. Per-vault consent cannot cover boot, because no vault is known yet.

**F2. medium. JS old-DSN window during a vault switch.**
- Claim: Errors from the new vault can reach the old DSN for up to 2 s after a switch.
- Evidence: `vault.service.ts:25` (`vaultStore.open`) triggers the effect at `+layout.svelte:81`, which calls `initializeVault`. `app-lifecycle.service.ts:154` queues `disableSentry()`. `sentry.service.ts:45-47` awaits `Sentry.close(2000)` and sets `activeDsn = null` only after it returns. `captureSentryException` checks `activeDsn` synchronously (`:113`), so during the flush it still sends. In `@sentry/core` 11.9.0, `close()` flushes first and clears the scope client only after the flush (`node_modules/.pnpm/@sentry+core@11.9.0/node_modules/@sentry/core/build/esm/exports.js:58-66`). New-vault calls to `error()` in that window include `loadSettings` failures (`settings.service.ts:43`). The new vault's `loadSettings` starts only after the awaited `saveAllDirtyTabs` and `drainEventCalendarWrites` (`app-lifecycle.service.ts:181-187`), which can run while the flush is pending.
- Fix: Clear `activeDsn` before awaiting the flush, or make `captureSentryException` drop events while a configuration is queued or in progress. Keep the flush for the old client's events, but do not route new events to it.

**F3. medium. Rust old-DSN window during a switch or disable.**
- Claim: Rust keeps the old DSN enabled until the JS flush finishes, so Rust panics in that window go to the old project.
- Evidence: `sentry.service.ts:45-50`: JS close is awaited, then `call('configure_sentry')` runs. Rust disables or replaces its client only inside that call (`error_monitoring.rs:36-40`). Rust's own close timeout is 200 ms (`error_monitoring.rs:39`), while the JS flush is 2000 ms.
- Fix: Send the Rust `configure_sentry` call first, or run both concurrently. Then the Rust client stops before JS starts flushing. Align the two timeouts.

**F4. low. Fire-and-forget disables swallow failures.**
- Claim: `void disableSentry()` discards rejections. If the IPC call fails on the disable path, Rust stays enabled with no log.
- Evidence: `app-lifecycle.service.ts:25`, `:154`, `:585` (`teardownVault`). `sentry.service.ts:46` sets `activeDsn = null` only after the close succeeds, and `:50` makes the IPC call. A failure there rejects into a discarded promise. The Rust failure modes are limited to a poisoned lock (`error_monitoring.rs:32`).
- Fix: Attach a `.catch` that calls `error('LIFECYCLE', ...)`. Per the project's error rules, do not leave it unhandled.

**F5. info. Order of reconfiguration is correct.**
- Claim: JS is closed before Rust is reconfigured, and Rust is configured before JS is initialized. This avoids JS events going out while Rust is off, and the reverse.
- Evidence: `sentry.service.ts:45-58` (close → `configure_sentry` → `Sentry.init`). Rust unbinds the hub before closing the old client (`error_monitoring.rs:36-40`). Invalid DSNs fail before `Sentry.init` (`:46-48`, and `sentry.service.ts:50` throws before `:58`).

**F6. info. Failed loads fail closed.**
- Claim: If `initializeVault` for the new vault is superseded, or `loadSettings` throws, monitoring stays off for the new vault.
- Evidence: `app-lifecycle.service.ts:25` disables first. `:201` returns before `configureSentry` if superseded. `settings.service.ts:42-48` falls back to default settings (`enabled: false`) on read errors.

**F7. info. Rust events are not scrubbed like JS events.**
- Claim: JS strips breadcrumbs, extra, request and user data in `beforeSend`. The Rust client sets `send_default_pii(false)` and `max_breadcrumbs(0)` but has no `before_send`.
- Evidence: `sentry.service.ts:28-36` and `:84` (JS scrubbing). `error_monitoring.rs:49-55` (Rust options).

**F8. low. Lifecycle test does not exercise the real ordering.**
- Claim: The order assertion runs against a mocked `configureSentry`, so the flush window and the Rust/JS interleaving are not covered.
- Evidence: `src/tests/lib/app/lifecycle/app-lifecycle.service.test.ts:107` (mock), `:324-326` (order assertion against the mock). The queue itself is tested in `src/tests/lib/core/settings/sentry.service.test.ts:116-147`.
- Fix: Add a test that holds `Sentry.close` open and checks that a new-vault `captureSentryException` does not reach the old client.
