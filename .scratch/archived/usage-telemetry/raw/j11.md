## Summary

- The feature surface is 22 `features/`, 10 `plugins/`, and 13 `core/` folders. The palette registry is `src/lib/app/commands.ts`, and the global shortcuts are in `src/lib/app/global-keybindings.ts`.
- Settings has 18 section IDs (`settings.types.ts:331`), listed in the nav at `settings.logic.ts:221-261` and rendered by `SettingsPanel.svelte:68`.
- Recommended design: one generic `command.run` event carrying the registry `id`, plus a few feature events for things that never go through the palette (note list, calendar, settings sections).
- Privacy risk: palette IDs are not always content-free. `rail:open-view:${view.path}` (`commands.ts:79-82`) embeds a vault path. `one-on-one:create` and periodic/template actions must send only the action, never the person name, note title or path.
- Not written to disk. This subagent's rules forbid writing report `.md` files, so the Markdown is returned here instead of `.scratch/usage-telemetry/raw/s11-feature-inventory.md`.

| Section ID | Proposed event |

Settings changes should not be sent as values. Only the section ID and the act of changing it (`settings.change`, no key or value) are needed.

## Open questions

1. Should `command.run` send the full registry `id`? It is fine for fixed IDs, but the `rail:open-view:` IDs need sanitizing first. Confirm that the allowlist of IDs is acceptable.
2. Per-session counts or per-day counts? This affects whether the events need a timestamp bucket.
3. Several entry points are marked UNVERIFIED: backlinks panel trigger, word-count UI, calendar rail navigator, QueryJS block call site. A follow-up read of the Svelte components is needed before those rows are final.
4. Confirm that rare actions (1:1 creation, Sentry section, Todoist, trash) should be measured at all. They are sensitive as well as rare.
