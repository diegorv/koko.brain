# Scout s19: supply-chain fit for usage telemetry candidates

## Summary
- **Nothing in the current build sends usage data.** `src/lib` has no `Sentry.logger` or `enableLogs` call (grep found none), so Sentry Logs would add no traffic until someone adds one.
- **The privacy CI scanner cannot see a new analytics package.** Its patterns name only `@sentry/browser` and `@doist/todoist-api-typescript` (`.github/workflows/privacy.yml:56,79`). Neither `posthog-js` nor `@aptabase/tauri` is matched by name, and the Rust scan never reads `Cargo.toml` dependencies. Aptabase's network calls run inside its Rust crate (reqwest), so the scan and the webview CSP both miss them.
- **PostHog and Aptabase break PRIVACY.md's headline promise** ("No analytics, no tracking", `PRIVACY.md` line 1 section). Both need a rewritten promise, new CSP hosts and new table rows. Sentry Logs needs a narrower change: the same DSN and existing CSP hosts, but a PRIVACY.md row that currently says logs are disabled.
- **A self-hosted Umami or Plausible endpoint is the hardest fit.** The CSP `connect-src` is static (`src-tauri/tauri.conf.json:29`), so a host the user types cannot be listed. Widening it to `https:` removes the guard for the whole app.
- **Supply-chain friction is low for all four.** Each package passes the install-script checks I could verify. The 5-day quarantine (`pnpm-workspace.yaml:7`, `minimumReleaseAge: 7200`) applies to each new version, and PostHog's latest version was published very recently (see F7).

## Findings

**F1. [high] Privacy scanner would not flag a new analytics package by name.**
- Claim: adding `posthog-js` or `@aptabase/tauri` passes `privacy.yml` unless the source has a `fetch(`, `https?://` literal or similar.
- Evidence: TS patterns and known list at `.github/workflows/privacy.yml` (patterns block, `@sentry/browser` at lines 56 and 79, `ingest(\.us|\.de)?\.sentry\.io` at line 80). No `posthog` or `aptabase` string appears in `.github/workflows/privacy.yml`, `.github/workflows/pr.yml`, or `PRIVACY.md`. The scan action only greps `src` and `src-tauri/src` (`.github/actions/scan-external-calls/action.yml`); `node_modules` is in skip.
- Fix: add explicit package-name patterns for every new analytics package, and for any new crate under `Cargo.toml` (for example `tauri-plugin-aptabase`), so the scan notices when one is imported.

**F2. [high] Aptabase's network call is in Rust, outside both the scan and the CSP.**
- Claim: `tauri-plugin-aptabase` 1.3.0 depends on `reqwest ^0.13.4`, `tokio`, `tauri`, `os_info`, `sys-locale`. Its HTTP traffic is made by the Rust crate, so the webview CSP does not apply, and the Rust scan does not read the dependency tree.
- Evidence: crates.io dependency list for `tauri-plugin-aptabase` 1.3.0 (`https://crates.io/api/v1/crates/tauri-plugin-aptabase/1.3.0/dependencies`). Published 2026-10-16, MIT, `rust_version` 1.85.0 (`https://crates.io/api/v1/crates/tauri-plugin-aptabase/1.3.0`). Current Rust HTTP usage is `tauri-plugin-http` (`src-tauri/Cargo.toml:68`, `src-tauri/src/lib.rs:313`), which is scoped by `src-tauri/capabilities/*.json` lines 235-274.
- Fix: if this route is taken, it needs its own privacy-scan pattern (`tauri_plugin_aptabase` in the Rust list) and a PRIVACY.md row. Whether the plugin needs a capability permission is UNVERIFIED.

**F3. [high] A self-hosted Umami or Plausible endpoint cannot be expressed in the static CSP.**
- Claim: the host is user-configured per vault, but `connect-src` and the `http:allow-fetch` capability scopes are fixed JSON. Listing an arbitrary host requires `https:` or `https://*`, which is a broad regression.
- Evidence: `src-tauri/tauri.conf.json:29` (`connect-src ipc: ... https://*.ingest.sentry.io ...`), `src-tauri/capabilities/*.json:235-274` (explicit host list for `http:allow-fetch`). Umami send API: `POST /api/send` on the user's own host, JSON with `payload.website`, `payload.name`, `payload.url`, `payload.hostname`, `payload.screen`, `payload.language`, `payload.referrer`, and `type: "event"`, no auth token, requires a `User-Agent` header (`https://docs.umami.is/docs/api/sending-stats`). Umami docs do not say whether cookies or IP are stored; that is UNVERIFIED.
- Fix: keep the endpoint in Rust with a validated, user-supplied host and a capability scope built at runtime, or do not add this route. Either way, the scan needs a known entry that does not pass arbitrary `fetch` calls.

**F4. [high] The plain-fetch route silently passes the scan through existing escape hatches.**
- Claim: a new `fetch(` in `src` is caught, but the fix people usually reach for, a `known` entry or a `// privacy-ok` comment, is broad. The `skip` list drops any line containing `privacy-ok` without a report.
- Evidence: `.github/actions/scan-external-calls/action.yml` (skip lines are dropped silently; `known` lines only emit `::notice::`). `privacy-ok` appears 12 times across `src` and `src-tauri/src` (grep count). Examples: `src/lib/utils/sanitize.ts`, `src-tauri/src/quick_capture/kind_detect.rs`.
- Fix: a telemetry module should not use the `privacy-ok` marker. If it must be exempt, a single named `known` entry for one file path is safer than a generic `fetch` allowance.

**F5. [high] PostHog's defaults send data to a third party and capture page content.**
- Claim: with defaults, `posthog-js` captures pageviews, autocaptures clicks, and persists IDs. Its cloud host is US.
- Evidence: PostHog config defaults: `autocapture` true, `capture_pageview` true (`history_change` from defaults `2025-05-24`), `persistence` `localStorage+cookie`, `api_host` `https://us.i.posthog.com` (`https://posthog.com/docs/libraries/js/config`). Dependencies of `posthog-js` 1.447.1: `fflate`, `preact`, `core-js`, `dompurify`, `web-vitals`, `@posthog/core`, `@posthog/types`, `@posthog/browser-common`, `query-selector-shadow-dom` (`https://registry.npmjs.org/posthog-js/latest`). Unpacked size is about 28 MB, which is the registry's `dist.unpackedSize`. Autocapture reads DOM text, which for a notes app would include note content unless disabled.
- Fix: if used, set `autocapture: false`, `capture_pageview: false`, `disable_session_recording: true`, `persistence: 'memory'`, a self-hosted `api_host`, and add that host to CSP. Each of these changes needs a test per CLAUDE.md. Even so, the package is large for a usage counter.

**F6. [medium] Sentry Logs: no new dependency, but it changes a documented promise.**
- Claim: Sentry Logs uses the existing `@sentry/browser` (installed 11.9.0, `package.json:46` `^11.9.0`, lock entries `pnpm-lock.yaml:695,2854`). It is enabled through `enableLogs`, and the SDK sends logs only when the app calls `Sentry.logger`.
- Evidence: `https://docs.sentry.io/platforms/javascript/logs/`: option `enableLogs`; logs default on from 10.71.0 (our 11.9.0 is above that); no separate package; `beforeSendLog` filters; automatic attributes include `user.id`, `user.name`, `user.email` if set, plus browser and release. `src/lib/core/settings/sentry.service.ts:58-84` filters integrations to a fixed list and uses `beforeSend: removeSensitiveEventData`, but does not mention `beforeSendLog`. `PRIVACY.md` table row for Sentry says logs are disabled. CSP already allows `*.ingest.sentry.io` (`tauri.conf.json:29`), and the scan already knows the ingest host (`privacy.yml:80`).
- Fix: the cheapest path, if usage data is wanted, but it still sends usage to a third-party cloud. Needs: `enableLogs: true` only when the per-vault opt-in is on, `beforeSendLog` that drops everything except an allowlist, a PRIVACY.md change, and a test in the sentry test suite. The `sentry.service.ts` integration filter does not apply to logs and must be checked separately (UNVERIFIED).

**F7. [medium] Quarantine and dependency policy.**
- Claim: any new npm or crate version must be 5 days old (`minimumReleaseAge: 7200`), and `trustPolicy: no-downgrade` applies to npm packages. Neither `posthog-js` nor `@aptabase/tauri` has install hooks.
- Evidence: `pnpm-workspace.yaml:7` (7200), `:34-36` (`blockExoticSubdeps`, `strictDepBuilds`, `trustPolicy`), `docs/adr/0014-supply-chain-pnpm-quarantine.md` amendment 2026-10-29 (5 days). `posthog-js` 1.447.1 time stamp is `2026-11-06T00:07:01Z` in the registry (`https://registry.npmjs.org/posthog-js`). That is after today's date (2026-11-05), so it needs checking; in any case it stays inside the window until about 2026-11-11 UTC. `@aptabase/tauri` 0.7.0 has only `build`, `watch`, `pretest`, `prepublishOnly` scripts (no install hook). Its `repository` points at a git URL but it is published to the registry. `tauri-plugin-aptabase` 1.3.0 published 2026-10-16, which clears the window. `trustPolicy` provenance for these packages is UNVERIFIED.
- Fix: pin a version older than the window if adopting now, and record the decision in the ADR.

**F8. [medium] Documentation and policy changes needed for any third-party route.**
- Claim: `PRIVACY.md` opens with "No analytics, no tracking" and a closing table of every external call. Any new service needs both changed, and the scan's known list needs the same host.
- Evidence: `PRIVACY.md` (headline bullet and the table of external calls). `.github/workflows/privacy.yml` runs on push to `main` and on `workflow_call` from `pr.yml:78-88`, not on every PR as `PRIVACY.md` implies. The `paths` filter includes `PRIVACY.md`, so a doc-only PR still runs it.
- Fix: write the PRIVACY.md change in the same PR as the code, so the policy and the scan agree.

**F9. [info] Aptabase data scope and hosts.**
- Claim: Aptabase sends an event name and custom properties (strings and numbers), app version and build, OS, device model, locale, a random short-lived session ID, and timestamps. The server derives country from IP and does not store the IP. Default hosts are `eu.aptabase.com` (keys `A-EU-`) and `us.aptabase.com` (keys `A-US-`). The docs do not describe self-hosting, so a self-hosted option is UNVERIFIED.
- Evidence: `https://aptabase.com/docs` (fetched 2026-11-05).
- Fix: none needed unless adopted. Note that notes do not go in these fields, but it is still third-party analytics.

**F10. [info] Lowest-friction option that needs no new package or policy change.**
- Claim: local-only counters (for example, feature-use counts written to the existing local log through `appendLog` in `src/lib/utils/log.service.ts`, or a local table) answer "which features do I use" with no network call, no CSP change, no scan change and no PRIVACY.md change. This is a suggestion outside the scope of the questions, not verified against the code.
- Evidence: ADR-0015 describes `appendLog` as the file writer that runs whenever a session is active (`docs/adr/0015-dual-logging-frontend-rust.md:20`).
