# s10: Known Sentry issues and decisions (as of 2026-11-05, main at 47ecf60ef)

Written to `/Users/diegorv/Dev/pet-projects/koko/brain/.scratch/usage-telemetry/raw/s10-known-issues.md`.

## Summary

- Sentry is opt-in per vault and off by default. The privacy controls are in place: CSP limited to Sentry ingest, browser integrations filtered, `beforeSend` scrubbing, Rust `send_default_pii(false)`. Do not re-report these as missing.
- Sentry was moved under Settings > Advanced (ux-polish Issue 32, commit a6b28484d). That placement is settled.
- Still open: `error()` forwards a non-Error string argument to Sentry unchanged (a path leak channel). Rust `configure_sentry` tears down the live client before validating the DSN. The DSN field reconfigures Sentry on every keystroke.
- The Rust `sentry` bump to 0.49.5 (commit 7fee3cbac, 2026-11-05) is not on HEAD. `Cargo.lock` still pins 0.49.3.
- No automated test covers the open items. The Sentry E2E case in `e2e/specs/settings.spec.ts` was reviewed but not run.

## Findings

**F1. medium. open. Privacy: `error()` sends a string argument to Sentry as the exception**
- `src/lib/utils/debug.ts:31` uses `args.find(instanceof Error) ?? args.at(-1)`. A string last argument goes to `captureSentryException` (`sentry.service.ts:112-117`).
- `removeSensitiveEventData` (`sentry.service.ts:28-36`) strips breadcrumbs, extra, request and user, not the exception value.
- String-only call sites: `src/lib/core/vault/vault.service.ts:44` (a path) and `src/lib/core/trash/trash.service.ts:167` (`restorePath`).
- Audit: `.scratch/audit-2026-11-04/findings.md:494`. The `debug.test.ts:140` case covers only an Error.
- Fix: send only `Error` instances, or scrub string exception values in `beforeSend`. Add a string-last-argument test.

**F2. low. open. Rust `configure_sentry` closes the live client before validating the DSN**
- `src-tauri/src/error_monitoring.rs:36-40` unbinds and closes the existing client. The DSN parse is at `:46-48`.
- Reachability is low: the frontend gates with `isValidSentryDsn` (`sentry.service.ts:41`, `:52`), so only a direct IPC call reaches this path.
- The doc comment at `:23-25` is true only for the new client.
- `src-tauri/tests/error_monitoring_test.rs:4-11` covers only the no-prior-client case.
- Audit: `.scratch/audit-2026-11-04/findings.md:353` (confirmed).
- Fix: parse the DSN before unbinding, and test that an active client survives a malformed configure.

**F3. low. open. DSN field reconfigures Sentry on every keystroke**
- `src/lib/core/settings/sections/SentrySection.svelte:64-67` calls `updateSentry` per `oninput`. Each change runs `Sentry.close(2000)`, an IPC call and a re-init (`sentry.service.ts:39-48`). Calls are serialized (`:94-99`), so there is no race, only churn.
- The invalid-DSN message shows while typing (`SentrySection.svelte:17-19`).
- Audit: `.scratch/audit-2026-11-04/findings.md:440`.
- Fix: update on `onchange` or `onblur`, or debounce.

**F4. low. open. Auto-move error reporting on every save (caller UNVERIFIED)**

- UNVERIFIED: which caller passes `onError`. `auto-move.service.ts` does not pass it in the lines I searched.
- Audit: `.scratch/audit-2026-11-04/findings.md:146`.
