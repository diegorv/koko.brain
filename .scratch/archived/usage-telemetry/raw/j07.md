# S02: Rust Sentry client audit

Written to `/Users/diegorv/Dev/pet-projects/koko/brain/.scratch/usage-telemetry/raw/s02-rust-client.md`.

## Summary

- Panic capture is installed by default (default integrations on, `panic` feature enabled). The hook is process-wide and captures only panics. No Rust `Result` error is ever sent.
- Real leak: the `contexts` feature is enabled, and `ContextIntegration` sets `server_name` to the machine hostname on every client init. `configure_sentry` never overrides it, and `send_default_pii(false)` does not gate it.
- No `before_send` on the Rust client, so panic message text goes out verbatim. The frontend scrubber does not cover this path.
- Good: `send_default_pii(false)`, `max_breadcrumbs(0)`, debug images off, release-health/logs/metrics off, invalid DSN rejected before init, and the disable path unbinds and closes the transport.
- One reconfigure gap: threads that touched the hub before a reconfigure keep the old client, so panics on those threads are dropped after switching clients. Only panics are sent, so impact is low to medium.

## Findings

**S02-F1, high.** Every Rust event carries the hostname as `server_name`. `ContextIntegration` fills it when options leave it unset, and `configure_sentry` never sets it. `send_default_pii(false)` does not prevent this.
- Evidence: `src-tauri/Cargo.toml:72` (`contexts` feature); `src-tauri/src/error_monitoring.rs:49-54` (no `server_name`); `sentry-contexts-0.49.3/src/integration.rs:74-77` (`if options.server_name.is_none() { options.server_name = server_name()... }`); `sentry-contexts-0.49.3/src/utils.rs:112-115` (`hostname::get()`); `sentry-core-0.49.3/src/client/mod.rs:186-188, 360-362` (setup runs at construction; `event.server_name` copied from options).
- docs.rs `ClientOptions` (0.49.3): `send_default_pii` covers HTTP headers and user IPs, not `server_name`. The hostname fill-in is documented only in the crate source.
- Fix: set `server_name` explicitly to a fixed non-identifying value, so `setup` skips the fill-in. Alternatively drop the `contexts` feature. Verify with a test asserting the built client's `server_name` is not the hostname.

**S02-F2, medium.** No `before_send` on the Rust client. Panic messages go out verbatim (`sentry-panic-0.49.3/src/lib.rs`, `value: Some(msg.to_string())`). The frontend `removeSensitiveEventData` (`src/lib/core/settings/sentry.service.ts:28-36`) clears breadcrumbs, extra, request and user, not `server_name` or exception values, and it does not run on the Rust path.
- Fix: add `before_send` to redact exception values and home-directory paths, and clear `server_name`. Audit panic message sites (see open questions).

**S02-F3, info (positive).** Panic integration is installed. `default_integrations: true` plus the `panic` feature (`Cargo.toml:72`) causes `defaults.rs:51-70` to add `PanicIntegration`. Its `setup` installs the hook once via `Once`. `panic_handler` calls `capture_event` then `client.flush(None)`, so panic events flush synchronously.

**S02-F4, info (gap).** Rust `Result` errors are never captured. `grep` for `capture_error|capture_message|capture_event` in `src-tauri/src` and `src-tauri/tests` finds nothing. The doc comments at `error_monitoring.rs:23-25` and `commands/sentry.rs:5` say "error and panic reporting", which overstates it. Fix: correct the comments, or decide explicitly whether to add error capture, since that increases what leaves the machine.

**S02-F5, low (positive).** Constrained defaults: `send_default_pii(false)` (`error_monitoring.rs:53`), `max_breadcrumbs(0)` (`:54`), `debug-images` not enabled because of `default-features = false` (`Cargo.toml:72`), and release-health/logs/metrics off. These would return if the dependency line moved to default features.

**S02-F6, medium.** Reconfigure does not reach threads that already resolved their thread-local hub. Each non-initial thread snapshots the process hub via `Hub::new_from_top` at first access (`sentry-core-0.49.3/src/hub_impl.rs:22-26`). `configure_sentry` rebinds only `Hub::main()` and the calling thread (`error_monitoring.rs:36-37`). The comment at `:60-63` ("new Rust threads inherit the active client") is true only for threads whose first hub access comes after the bind. The old client is closed, so stale threads send nothing (`client/mod.rs:520-528`, `envelope_sender.rs:209-216`). The disable path is effective; enable-after-reconfigure loses panics on pre-existing threads.
- Fix: keep one client and gate sending with an `AtomicBool` in `before_send`, or document the limitation. Add a test that reconfigures and then panics on a pre-existing thread.

**S02-F7, low.** No flush on app exit. `SentryState` is managed state and is not dropped on exit (`lib.rs:321`, no exit flush in `lib.rs:392-396`). The reconfigure close waits only 200 ms (`error_monitoring.rs:38-40`). Panics are unaffected because they flush synchronously.

**S02-F8, info.** Release is `kokobrain@<version>` from `__BUILD_INFO__` (`sentry.service.ts:19-22`, passed at `:50-60`). Environment is not set, so the SDK default applies: `development` in debug builds and `production` in release, unless `SENTRY_ENVIRONMENT` is set (`defaults.rs:86-100`). Fix: set it explicitly.

**S02-F9, info, UNVERIFIED.** Stack frame `abs_path` comes from debug info (`sentry-backtrace-0.49.3/src/process.rs:89`). Release builds use `strip = true` (`Cargo.toml:88`), so shipped frames may lack paths. Dev builds carry `/Users/...` paths. Needs a release build to confirm.

**S02-F10, low.** Test coverage is thin. `src-tauri/tests/error_monitoring_test.rs` covers only invalid DSN and disabled startup. Nothing covers the enabled path, `server_name`, `before_send`, panic capture, or reconfigure. The `test` feature (`TestTransport`) is not enabled, so testing needs a feature change (how it is exposed in 0.49.3 is UNVERIFIED).

**S02-F11, info.** `Cargo.toml` requires `0.49.2`; `Cargo.lock` resolves `0.49.3` (`Cargo.lock:4702-4704`). The local registry source matches the lock, so the audit reads the exact resolved code.

3. Do shipped release frames contain paths (S02-F9)? Needs a build.
4. Is `server_name = Some("")` safe at ingest, or should a fixed constant be used? UNVERIFIED.
