## Summary

- **DSN storage:** the DSN is plain JSON in `<vault>/.kokobrain/settings.json`, so it is per-vault. Anything that syncs or commits the vault (git, iCloud, Dropbox) will carry it. Sentry's docs describe a DSN as public (submit-only), so the exposure is quota abuse and spam, not data read access.
- **Defaults and opt-in are correct:** monitoring is off by default, and nothing initializes without `enabled` and a valid DSN.
- **Test-event button overclaims:** it reports "Test event sent" whenever the SDK queue drains, which includes HTTP 401/403, 429, and offline failures. Only a timeout yields "pending". I confirmed this from SDK 11.9.0 source, not from a live run.
- **Usable as a template, with caveats:** the toggle, field, and status pattern is reusable, but `parseSettings` hand-builds the `sentry` object, so new fields are silently dropped on load unless added there too. Usage analytics also collides with PRIVACY.md. A local counter in the vault or the app DB needs no third-party service at all.

I did not write a report file, because this thread's instructions say to return findings directly.

## Findings

**F1. Medium. DSN is stored in the vault's plain-text settings file.**
- Claim: the DSN lives at `<vault>/.kokobrain/settings.json`, unencrypted, and is written by the shared settings writer.
- Evidence: `src/lib/core/settings/settings.service.ts:13-18` (`SETTINGS_DIR='.kokobrain'`, `settings.json`); `settings.service.ts:250-273` (single write site); `settings.types.ts:361` (documents the path); `sentry` persisted at `settings.service.ts:164-167`. A grep of the repo found no `.gitignore` entry or vault-level exclusion for `.kokobrain`. `src/lib/utils/path.ts:77` only mentions `.gitignore` in a doc example.
- Sentry docs: "DSNs are safe to keep public because they only allow submission of new events ... they do not allow read access" (https://docs.sentry.io/concepts/key-terms/dsn-explainer/). The risk is abuse of the project quota and spam, not read access.
- Suggested fix: document that `.kokobrain/` travels with the vault. Optionally add `.kokobrain/settings.json` to the vault's ignore guidance, or move the DSN to app-level config outside the vault. The per-vault design is intentional, so the cheaper route is documentation.

**F2. Info. Disabled by default and opt-in is enforced.**
- Evidence: `src/lib/core/settings/settings.store.svelte.ts:126-129` (`enabled: false, dsn: ''`); `settings.service.ts:165` (`parsed.sentry?.enabled === true`, so non-boolean values are not consent; tested at `src/tests/lib/core/settings/settings.service.test.ts:233-245`); `sentry.service.ts:41` (`shouldEnable = settings.enabled && isValidSentryDsn(dsn)`); `sentry.service.ts:58` (`Sentry.init` only after that check).
- Evidence (Rust side): `src-tauri/src/error_monitoring.rs:42-44` returns early when disabled.

**F3. Info. Persistence is correct.**
- The section never saves directly. `updateSentry` changes the store (`SentrySection.svelte:13-14`), and the persistence effect writes after a 500 ms debounce (`src/lib/core/settings/settings-persistence.svelte.ts:10, 53-63`). Each vault's settings are reset on teardown (`app-lifecycle.service.ts:585-586`).

**F4. High. The test-event button reports "sent" when delivery is not confirmed.**
- Claim: `sendSentryTestEvent` returns `'sent'` whenever `Sentry.flush` resolves `true`. That happens after any queue drain, including HTTP error responses and network failures.
- Evidence (app): `src/lib/core/settings/sentry.service.ts:133` (`await Sentry.flush(2000) ? 'sent' : 'pending'`); `SentrySection.svelte:31-35` shows "Test event sent. Check Sentry Issues in a few moments."
- Evidence (SDK 11.9.0, from `node_modules/.pnpm/@sentry+core@11.9.0/node_modules/@sentry/core/build/esm/`):
  - `client.js:257-266`: `flush` returns `clientFinished && transportFlushed`.
  - `promisebuffer.js:25-29`: `drain` is `Promise.allSettled(...).then(() => true)`, so it resolves `true` even when tasks fail.
  - `transports/base.js:25-60`: a 4xx response resolves with its status, and a network error is recorded as lost and rethrown. Both settle the task, so `drain` still returns `true`.
- Failure scenario: a wrong project key (401/403), an offline machine, or a rate limit all show "Test event sent" and never reach the Issues page. Only a flush timeout shows "pending".
- Suggested fix: reword the success message to "accepted by the SDK queue, check Sentry Issues", or verify delivery with a direct request whose HTTP status is inspected. The first fix is small. Reserve "sent" for confirmed delivery.

**F5. Medium. The test path is only partly covered.**
- Evidence: unit tests at `src/tests/lib/core/settings/sentry.service.test.ts:124-143` cover the synthetic event and the pending case. The E2E test (`e2e/specs/settings.spec.ts:46-60`) checks only the invalid-DSN alert and the "Sentry is not active" status. No test covers `SentrySection.svelte` itself, and no test covers a real-DSN success or failure message.
- Suggested fix: add a component test for the three result strings, and an E2E case for the "sent" path with a mocked transport.

**F6. Medium. Invalid-DSN feedback is incomplete.**
- The message is generic: "Enter a valid Sentry Cloud DSN to start error monitoring." (`SentrySection.svelte:17-19`). `isValidSentryDsn` checks five separate things (https, ingest host, public key, one path segment) at `src/lib/core/settings/sentry.logic.ts:13-27`, and the user is not told which one failed.
- `configurationError` starts empty (`SentrySection.svelte:9`), so a saved bad DSN gives no alert when settings are reopened. The alert appears only after an input or toggle.
- The startup call ignores the result: `src/lib/app/lifecycle/app-lifecycle.service.ts:203` runs `await configureSentry(settingsStore.sentry)` without reading `'invalid-dsn'`.
- Suggested fix: name the specific failing rule, and run the validation once when the section mounts.

**F7. Low. Each keystroke sends an IPC call.**
- Claim: every DSN keystroke calls `updateSentry`, which calls `configureSentry`, which calls `call('configure_sentry')`. Partial DSNs send `enabled:false` every time.
- Evidence: `SentrySection.svelte:13-24, 67`; `sentry.service.ts:50-54`. The queue at `sentry.service.ts:94-99` serializes the calls.
- Suggested fix: debounce the DSN input, or apply on blur.

**F8. Medium. The settings parser hand-builds the Sentry object, which is a trap when copying the pattern.**
- Evidence: `settings.service.ts:164-167` builds `sentry` from two fields instead of spreading defaults. `normalizeSettings` in `settings.logic.ts` does not reference Sentry (grep). Any new field added to `SentrySettings` is dropped on load unless this line is also changed.
- Suggested fix: when copying this pattern, spread `DEFAULT_SETTINGS.sentry` and the parsed object, as the other sections do.

**F9. Low. Copy says "unhandled errors", but handled errors are sent too.**
- Evidence: the description at `SentrySection.svelte:50` says "unhandled errors". `sentry.service.ts:112-118` (`captureSentryException`) sends handled errors as well.
- Suggested fix: change the copy to "errors" or "errors and exceptions".

**F10. Info. Template suitability and the privacy conflict for usage analytics.**
- Reusable parts: the toggle and field layout, the status-message pattern, the serialized configure queue (`sentry.service.ts:94-99`), and the per-vault lifecycle hooks (`app-lifecycle.service.ts:154, 203, 585`).
- Caveats:
  - PRIVACY.md says "No analytics, no tracking" and names Sentry as the only exception (`PRIVACY.md:8`, table row at line 18). A usage section that sends data would require changing that promise and the table.
  - A third-party usage service would send feature-usage data off the machine. The usage data has to stay local.
  - A local feature counter needs no new service. The app already has a per-vault SQLite DB at `.kokobrain/kokobrain.db` (`src-tauri/src/db/mod.rs:25`), or a counter could live in the settings file. Either route keeps the data on disk in the vault. Settings are stored per vault, so a counter in them gets the same sync exposure as F1.
- Also check `.github/workflows/privacy.yml` before adding any new network target. I did not read it, so what it enforces is UNVERIFIED.
