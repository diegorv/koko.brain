## Findings the scouts missed

- **M1 (low-medium). Dev and stable events cannot be told apart.** JS `environment` is always "production" (`prepareEvent.js:83`), and a stable-channel dev build has the same release string. The owner likely runs `pnpm tauri dev` against the real opted-in vault, so dev noise lands in the production issue stream. Fix: pass `environment: import.meta.env.DEV ? 'development' : __APP_CHANNEL__` to `Sentry.init` and to `configure_sentry`. The Rust crate's default environment differs from JS (it is build-profile based, from memory, UNVERIFIED), so the two sides may already disagree.
- **M2 (low). Settings edits reinitialize the client on every keystroke.** `SentrySection.svelte:67` calls `configureSentry` on every `oninput`. Each valid-to-different-valid edit does `close(2000)` + IPC + `init` (`sentry.service.ts:43-58`). The queue keeps this correct, but each re-init leaks one more GlobalHandlers closure (handlers are added, never removed; they only bail at `globalhandlers.js:35,58`). Negligible in practice.
- **M3 (low). The serialization queue has no test.** `sentry.service.test.ts:144-153` awaits every call in turn, so a `configureSentry` that dropped the `configurationQueue.then` chaining would still pass. Add a test that fires enable, disable and enable without awaiting, holds `close` open, and asserts the final `isSentryActive()` and the `init`/`close` order.
- **M4 (low). The "Send test event" flush does not tell you whether the server accepted the event.** `sendSentryTestEvent` (`sentry.service.ts:133`) returns `'sent'` when `flush` resolves true. `flush` only says whether the transport queue drained in time, not whether ingest accepted the event (from SDK semantics; I did not trace the transport). A wrong project id in a well-formed DSN would still show "Test event sent".
- **M5 (info). `isSentryActive` has no production caller.** `git grep` shows it is used only by tests. Mentioned only, not a defect.
- **M6 (info). Non-Error objects are handled safely.** For plain objects, the browser builder puts the serialized value in `extra.__serialized__` (`eventbuilder.js:159-165`), and `beforeSend` strips `extra`. Only the key list reaches the message. This part of the scrubbing does work.

## Verdict for this area

The init/config is correct for SDK 11.9.0: every option exists, the integration whitelist is enforced by a test against the real defaults, and PII/request/breadcrumb collection is off. What is not "well configured":

1. **Unreadable stack traces.** There are no source maps and no upload step. This is the biggest usefulness gap.
2. **Unscrubbed messages.** Message and exception text go out unscrubbed, including at least one absolute vault path (`vault.service.ts:44`). This is disclosed in the Settings copy.
3. **No environment and no build sha.** Dev and prod events cannot be told apart.
4. **Capture blind spots.** There is no capture before a vault's settings load, Rust `Err` values are never reported, and there is no Svelte error boundary.

The lifecycle ordering is sound. The vault-switch leak windows are real but short and low-impact for a single-owner setup. The tests check gates and options as literals, but because the SDK is mocked they cannot show that scrubbing runs in the real pipeline.

UNVERIFIED: s4-F1, F3, F4 and part of F5 (I did not reread those sites), the Rust default environment, whether Svelte 5 errors reach `window.onerror` in the Tauri WebView, and M4's transport semantics.
