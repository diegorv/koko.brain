# s4: Sentry capture coverage (what reaches Sentry)

Written to: /Users/diegorv/Dev/pet-projects/koko/brain/.scratch/usage-telemetry/raw/s04-capture-coverage.md

## Summary

- The working capture path is `error()` in `/Users/diegorv/Dev/pet-projects/koko/brain/src/lib/utils/debug.ts:27-33`. It calls `captureSentryException` synchronously (`sentry.service.ts:112-118`) before `console.error`. `GlobalHandlers` is kept (`sentry.service.ts:67`), so uncaught errors and unhandled rejections are captured while a vault has opted in. Rust panics are captured through the `panic` feature (`src-tauri/Cargo.toml:72`, `src-tauri/src/error_monitoring.rs:62-63`).
- About 162 `error(` calls (38 `.ts`, 9 `.svelte` files) feed Sentry. About 13 `console.error` sites in `src/lib` bypass it. About 20 `.catch(() => {})` or empty `catch` sites swallow errors silently.
- Biggest blind spots: CodeMirror live-preview failures go through `reportError`/`editorLog` and never reach Sentry. Rust `Err(String)` command results are never reported, only panics are. There is no `svelte:boundary` and no client error hook.
- Capture only runs for a vault that opted in and after `configureSentry` (`app-lifecycle.service.ts:203`). Errors before that, on the welcome screen, and in the vault-switch gap are dropped.
- Privacy: when the last argument to `error()` is a string, Sentry uses it verbatim as the event message (`debug.ts:31`, `@sentry/core@11.9.0` `eventbuilder.js:82`). `beforeSend` strips only breadcrumbs, extra, request and user.

## Findings

### F1: CodeMirror live-preview errors never reach Sentry
- **Severity:** high
- **Claim:** Live-preview decoration, click and wikilink failures are logged to the console and a local log port only.
- **Evidence:**
  - `src/lib/core/markdown-editor/extensions/live-preview/core/profiling.ts:36-39`: `reportError` calls `console.error` and `port.log`, never `error()` or Sentry.
  - `.../live-preview/inline/inline-formatting-plugin.ts:83-91`: the `try { decorate() } catch` writes `editorLog('LP-INLINE', ...)` and does not rethrow.
  - `.../live-preview/wikilink-navigation.ts:33-34, 63-64`, `.../live-preview/click-handler.ts:38`, `src/lib/core/markdown-editor/extensions/wikilink/completion.ts:20-21`: all use `reportError`.
  - `.../live-preview/widgets/mermaid-widget.ts:113-116` and `widgets/math-widget.ts:62-65`: render failures are shown in the DOM and logged nowhere.
- **Suggested fix:** Make `reportError` call `error()`. Add `captureSentryException` in the `inline-formatting-plugin.ts` catch, keeping the once-per-handler throttle. Decide whether mermaid and math failures should be reported, since they depend on note content and may be noisy.

### F2: Rust command errors are never reported; only panics are
- **Severity:** high
- **Claim:** Commands returning `Err(String)` reach the frontend as rejected `invoke` promises. They are reported only if a caller calls `error()`, and many do not.
- **Evidence:**
  - `src-tauri/Cargo.toml:72`: `sentry` with `default-features = false` and `features = ["backtrace", "contexts", "panic", "transport"]`. Per docs.rs for 0.49.2 (https://docs.rs/crate/sentry/0.49.2/features), `panic` enables `sentry-panic` and `transport` enables `reqwest` plus `native-tls`.
  - `src-tauri/src/error_monitoring.rs:26-66`: the only capture mechanism is the panic integration, inherited through the bound hub (lines 60-63). No capture call exists for `Err` values.
  - `src-tauri/src/commands/` has about 82 matching lines (`async fn` or `#[tauri::command]`, grep count, approximate).
  - `src-tauri/src/lib.rs:66, 85` and `src-tauri/src/utils/logger.rs:62`: `eprintln!` only.
  - `src/lib/contracts/ipc.ts:21-27`: `call()` is a bare `invoke` wrapper with no logging or capture.
  - `src-tauri/Cargo.toml:84-98` sets no `panic = "abort"`, so unwinding is the default and the panic hook runs. Panic capture should work, but this was not run (UNVERIFIED at runtime).
- **Suggested fix:** Report command rejections once in `call()`, with the command name as a tag. Keep the message generic, since Rust strings may contain paths. On the Rust side, explicitly capture `Err` from high-value commands (DB open, save, index build), or document the gap.

### F3: Silent swallows of fire-and-forget promises
- **Severity:** high
- **Claim:** About 10 `.catch(() => {})` sites discard rejections with no log and no capture. Several are on user-visible paths.
- **Evidence:**
  - `src/lib/core/filesystem/fs.service.ts:169`: `loadDirectoryTree(vaultPath).catch(() => {});`
  - `src/lib/features/backlinks/BacklinksPanel.svelte:28-29`: two fetches with `.catch(() => {})`.
  - `src/lib/features/outgoing-links/OutgoingLinksPanel.svelte:27`: `fetchOutgoingLinksV2(...).catch(() => {})`.
  - `src/lib/features/canvas/FileNode.svelte:45`, `ImageNode.svelte:35`, `src/lib/features/search/SemanticIndexStatus.svelte:48`: `.catch(() => {` with bodies not read (UNVERIFIED beyond the first line).
  - Likely intentional, not bugs: `event-calendar.service.ts:1311` and `type-definitions.service.ts:358` (queue tails), `inflight.ts:136-138` (cache eviction), and `.catch(() => true)` existence probes at `frontmatter-write.service.ts:155` and `widgets.ts:689`.
- **Suggested fix:** Replace `() => {}` in the panel fetches and the file tree load with `(err) => error('TAG', 'msg:', err)`. Leave the queue tails and existence probes.

### F4: Empty or silent `catch {}` blocks on data paths
- **Severity:** medium
- **Claim:** Several `catch {}` blocks return a default without logging. Most are benign, but some sit on data paths.
- **Evidence:**
  - `src/lib/features/type-definitions/type-definitions.service.ts:71, 151, 194, 225`. Benign status UNVERIFIED for 71 and 151.
  - `src/lib/features/type-definitions/type-sidebar.logic.ts:536, 557`.
  - `src/lib/core/markdown-editor/extensions/live-preview/meta-bind-button.logic.ts:150, 164`.
  - `widgets.ts:117, 125` (URL parsing helpers, benign) and `theme.service.ts:83` (localStorage mirror, benign).
- **Suggested fix:** Review the type-definitions and type-sidebar blocks first. Route real failures through `error()`.

### F5: Direct `console.error` bypasses Sentry
- **Severity:** medium
- **Claim:** About 13 `console.error` sites do not call `error()` and are never captured.
- **Evidence:**
  - `src/lib/features/command-palette/CommandPalette.svelte:34` (command failed).
  - `src/lib/features/tasks/TasksView.svelte:89` (Todoist sync failed).
  - `src/lib/plugins/calendar/CalendarNavigator.svelte:70` and `:81`.
  - `src/lib/plugins/one-on-one/OneOnOnePicker.svelte:32` (create 1:1 failed).
  - `src/lib/plugins/templates/TemplatePicker.svelte:43` (create from template failed).
  - Leave as-is (reporting them would be circular): `src/lib/utils/log.service.ts:72, 105, 177` and `SentrySection.svelte:22, 38`.
- **Suggested fix:** Convert the five user-facing sites to `error()`.

### F6: No Svelte error boundary and no client error hook
- **Severity:** high
- **Claim:** There is no `svelte:boundary` and no `handleError` hook. Render and effect errors go to the global path, and the UI may unmount.
- **Evidence:**
  - `git grep svelte:boundary -- src`: 0 matches. `handleError`: 0 matches. `src/hooks.client.ts` does not exist (only `src/app.d.ts`).
  - `GlobalHandlers` (`sentry.service.ts:63-70`) still captures uncaught errors and unhandled rejections when a vault has opted in.
  - Whether an uncaught error unmounts the whole Svelte 5 tree, and whether it reaches `window.onerror` in the Tauri WebView, is UNVERIFIED. Not run.
- **Suggested fix:** Add a root `svelte:boundary` that calls `error()` and shows a recoverable message. Verify unmount behavior with a deliberate throw in a dev build.

### F7: Capture gated to an opted-in vault; early and between-vault errors lost
- **Severity:** medium
- **Claim:** Nothing is sent until `configureSentry` runs in `initializeVault`.
- **Evidence:**
  - `sentry.service.ts:113`: `captureSentryException` returns when `activeDsn === null`.
  - `src/lib/app/lifecycle/app-lifecycle.service.ts:199`: `await loadSettings(vaultPath)` is not wrapped. A throw rejects `initializeVault` and is not captured. `configureSentry` runs at line 203.
  - `app-lifecycle.service.ts:154` and `:585`: `void disableSentry()` runs at the start and end of the vault lifecycle.
  - `app-lifecycle.service.ts:236-239` (DB open failure) is captured, because configure has already run.
- **Suggested fix:** Confirm the per-vault gate is intended, and document it in PRIVACY.md or the Sentry section. Wrap `loadSettings` the same way as the surrounding steps.

### F8: A string last argument becomes the message and loses context
- **Severity:** medium
- **Claim:** `captureSentryException(tag, args.find(Error) ?? args.at(-1))` sends a non-Error last argument as the message. Earlier descriptive text is dropped, and no arguments yields the literal message `"undefined"`.
- **Evidence:**
  - `src/lib/utils/debug.ts:31`.
  - `node_modules/.pnpm/@sentry+core@11.9.0/node_modules/@sentry/core/build/esm/utils/eventbuilder.js:82`: `ex.message = \`${exception}\`` for non-Error values.
  - Rust `Err(String)` values arrive as strings. Example: `app-lifecycle.service.ts:236` produces an event whose message is the raw Rust string.
- **Suggested fix:** Build the event from the tag and the joined arguments, for example `captureException(new Error(\`${tag}: ${joined}\`))` with the `source` tag, and keep the original Error as `cause` when there is one.

### F9: Privacy: string arguments reach Sentry verbatim
- **Severity:** medium
- **Claim:** `beforeSend` strips breadcrumbs, extra, request and user, but not the exception message or stack. Paths or note text in an error message are sent.
- **Evidence:**
  - `sentry.service.ts:28-36` (`removeSensitiveEventData`).
  - F8 shows string arguments become the message.
  - `src-tauri/src/error_monitoring.rs:53-54`: `send_default_pii(false)` and `max_breadcrumbs(0)` are set, which is good. Whether Rust panic messages contain paths is UNVERIFIED.
- **Suggested fix:** Scrub absolute paths in `removeSensitiveEventData`, and have F8's fix stop passing raw strings through.

### F10: Events in flight at quit may be lost
- **Severity:** low
- **Claim:** The only `Sentry.flush` in `src` is in `sendSentryTestEvent`. The exit path does not flush Sentry.
- **Evidence:**
  - `sentry.service.ts:133`.
  - `src-tauri/src/commands/app_exit.rs` and `src/lib/app/tauri-listeners.service.ts:71-74` flush saves on exit, not Sentry.
  - Impact (events lost, and whether the WebView dies before transport sends) is UNVERIFIED.
- **Suggested fix:** Add `Sentry.flush(2000)` to the exit sequence, and close the Rust client with a short timeout on `RunEvent::ExitRequested`.

### F11: Positive: the capture path is synchronous, tagged and deduped
- **Severity:** info
- **Claim:** `error()` captures before logging, sets a `source` tag, and keeps `Dedupe` and `LinkedErrors`. This is sound for the paths it covers.
- **Evidence:** `debug.ts:31`; `sentry.service.ts:114-116`; `sentry.service.ts:63-70`.
- **Suggested fix:** None.

## Open questions

1. Does an uncaught error in a Svelte 5 component tree unmount the app, and does it reach `window.onerror` in the Tauri WebView? Needs a dev-build test (F6).
2. Is pre-vault and between-vault capture (F7) intended? If the owner wants crash reports before a vault opens, the gate needs redesign.
3. Which Rust commands should report `Err` values (F2)? Vault open, save and index build are the likely candidates.
4. Do Rust panic messages contain vault paths in practice? If so, F9 extends to the Rust side.
