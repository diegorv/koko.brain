## Summary

- **Autocapture is the main privacy risk, and it is on by default.** It records clicks on `a`, `button`, `input`, `textarea`, `label` and similar elements, and element text appears in event names (for example "clicked span with text ..."). In an editor-heavy UI that text can be note content. `autocapture: false` plus `capture_pageview: false` and `capture_pageleave: false` is the minimum.
- **Session replay must be off.** Web replay does not mask general text by default, and only inputs are masked. Replay is controlled by `disable_session_recording: true` and must not be enabled for this app.
- **Tauri support is shaky.** The one related posthog-js issue (#1760) reports that events silently never send from a packaged Tauri v2 app. It was closed by the reporter with no maintainer reply and no fix. Third-party workarounds route events through Rust.
- **Runtime key and host are supported.** `posthog.init(token, { api_host })` takes both, so a user-supplied project token and host are feasible. The CSP in `src-tauri/tauri.conf.json` currently allows no PostHog host, so it would need an update.
- **Free tier and pricing figures are unverified.** Only third-party sites report them (1M events, 5K web recordings, 1M flag requests per month). The official pricing page did not render in the fetch.

## Findings

**F1. [high] Autocapture captures element text and is on by default.**
- Claim: the default `autocapture: true` captures clicks on interactive elements, and element text goes into event names. `mask_all_text` defaults to `false`.
- Evidence: [posthog-js config](https://posthog.com/docs/libraries/js/config) (`autocapture` default `true`, `mask_all_text` default `false`, `capture_copied_text` default `false`). [Autocapture docs](https://posthog.com/docs/product-analytics/autocapture): "clicked span with text ..." naming, element text property, and the list of autocaptured tags.
- Fix: `autocapture: false`, `mask_all_text: true` as a belt-and-braces setting, `capture_copied_text: false` (already the default). Also set `capture_dead_clicks: false`, `rageclick: false`, and `capture_heatmaps`/`capture_performance`/`capture_exceptions: false` (listed on the config page as disable toggles).

**F2. [high] Session replay must be disabled and cannot be relied on to mask note content.**
- Claim: general text is not masked on web. Inputs are masked by default. The only blocking class documented on the page is `ph-no-capture`.
- Evidence: [Session replay privacy](https://posthog.com/docs/session-replay/privacy): "General text is not masked by default." Also `ph-no-capture` and `maskTextSelector: "*"`. The config page: `disable_session_recording` default `false`.
- Fix: `disable_session_recording: true` and `disable_surveys: true`. Do not rely on masking classes for a note editor.

**F3. [high] Auto-collected properties need guarding even in manual mode.**
- Claim: beyond the event name, posthog-js attaches page URL, pathname and similar properties to every event. This matters because Kokobrain's Tauri origin is `tauri://localhost`, so the URL is not sensitive, but any `capture` call that includes a note title or path would leak content.
- Evidence: the config page documents `property_denylist` (default `[]`, "A list of properties that should never be sent with capture calls") and `before_send` for changing or dropping data. The full list of default properties was **not** verified.
- Fix: enforce a typed allowlist of event names and property keys in one wrapper module. Use `before_send` to reject any event that is not on the list. Mark the default-property list UNVERIFIED until checked in the SDK source.

**F4. [high] Persistent `distinct_id` is stored by default.**
- Claim: default persistence is `localStorage+cookie`. That keeps a stable ID across sessions. The page also documents `disable_persistence` and `cookieless_mode`.
- Evidence: [config page](https://posthog.com/docs/libraries/js/config): `persistence` default `localStorage+cookie`; `cookieless_mode` `always` or `on_reject`, which "sets no cookies and uses no session or local storage" and "must be enabled in project settings, otherwise cookieless events are ignored."
- Fix: `persistence: 'memory'` for a non-persistent ID, or `cookieless_mode: 'always'` with the project setting enabled. Choose based on whether the owner wants usage over time (which needs a stable ID) or wants no identifier at all. This is a design decision, see Open questions.

**F5. [medium] posthog-js does not document a manual-only mode.**
- Claim: no single master switch exists. Stopping all capture takes `opt_out_capturing_by_default: true`, which requires `posthog.opt_in_capturing()` before anything sends. `advanced_disable_flags: true` disables flag-dependent features.
- Evidence: [JS library overview](https://posthog.com/docs/libraries/js) has no manual-only section. Config page: `opt_out_capturing_by_default` text quoted above.
- Fix: combine `opt_out_capturing_by_default: true` (opt-in only after the Settings toggle), and the per-feature disables from F1 and F2. Do not use the slim bundle as the privacy control. Its effect on capture is UNVERIFIED.

**F6. [high] Reports of posthog-js not sending from a packaged Tauri v2 app.**
- Claim: issue #1760 reports that events worked in Safari against the Vite server but were never sent in the packaged Tauri v2 app, with no error logs. It was closed by the reporter on 2025-02-23. No maintainer replied and there is no fix PR.
- Evidence: [posthog-js #1760](https://github.com/PostHog/posthog-js/issues/1760). Reported version 1.222.0. Also reported: the origin is `tauri://localhost` (or `http://tauri.localhost` on Windows), per [openframe PR #769](https://github.com/flamingo-stack/openframe-oss-frontend/pull/769), which also notes that `tauri://` is not a special scheme.
- Fix: before adopting posthog-js, build the release app and confirm one test event reaches the PostHog project. Treat that as a gate, not an assumption. Workarounds exist (see F7).

**F7. [medium] Third-party Tauri plugins route PostHog events through Rust.**
- Claim: `tauri-plugin-better-posthog` keeps posthog-js and sends via a Rust `captureEvent`, with a `before_send` hook. `tauri-plugin-posthog` (crates.io) replaces the JS client with its own API.
- Evidence: [tauri_plugin_better_posthog docs](https://docs.rs/tauri-plugin-better-posthog), [lib.rs listing](https://lib.rs/crates/tauri-plugin-better-posthog), [tauri-plugin-posthog on crates.io](https://crates.io/crates/tauri-plugin-posthog). Maintenance, license and downloads were NOT verified (crates.io did not render).
- Fix: if posthog-js fails the F6 gate, use a plugin only after checking its source and maintenance status. Alternative: a small custom `reqwest` POST from Rust to the PostHog capture API, with the same allowlist.

**F8. [high] CSP blocks PostHog hosts today.**
- Claim: `connect-src` in the Tauri CSP lists Todoist, Hugging Face, GitHub and Sentry ingest hosts, but no PostHog host. Any PostHog request would be blocked until one is added.
- Evidence: `src-tauri/tauri.conf.json:29`, the `csp` value. Hosts to add if used: `https://us.i.posthog.com` or `https://eu.i.posthog.com` (plus the assets host from the snippet, if that is used). Host names: [config page](https://posthog.com/docs/libraries/js/config) gives `api_host` default `https://us.i.posthog.com` and EU projects `https://eu.i.posthog.com`.
- Fix: add only the one chosen host to `connect-src` when the feature is enabled. Prefer the EU host if the owner wants EU residency. Note: CSP changes in the Tauri config affect the whole app. Verify the change with a real release build.

**F9. [medium] EU residency.**
- Claim: PostHog Cloud EU is hosted in Frankfurt. US and EU projects use different ingest hosts.
- Evidence: [Data storage docs](https://posthog.com/docs/privacy/data-storage): "hosted on servers based in Frankfurt." The page did not give the ingest URLs, but the config page gives `eu.i.posthog.com` as the EU host. US-cloud hosting location was not stated.
- Fix: if residency matters, create an EU project and set `api_host` to the EU host. Use the EU project key.

**F10. [medium] Free tier and paid pricing unverified.**
- Claim: multiple third-party pricing sites say the free tier is 1M product analytics events, 5,000 session recordings and 1M feature flag requests per month. Above that, events cost about $0.00005 each and recordings about $0.005.
- Evidence: [usercall pricing post](https://www.usercall.co/post/posthog-pricing), [getpricepulse](https://www.getpricepulse.com/companies/posthog-pricing.html). The official [pricing page](https://posthog.com/pricing) returned only navigation text (UNVERIFIED). Sources disagree on survey responses and AI credits. Treat all numbers as UNVERIFIED until checked on posthog.com.
- Fix: check the official pricing page before the owner commits. For a single desktop user, the free allotment is likely more than enough if only a few manual events are sent. This is UNVERIFIED.

**F11. [low] Bundle size.**
- Claim: posthog-js v1.445.1 is 333.4 kB minified, 112.7 kB gzipped. The page did not say whether that version is current.
- Evidence: [Bundlephobia](https://bundlephobia.com/package/posthog-js). npm page returned HTTP 403, so latest version is UNVERIFIED.
- Fix: the cost is acceptable for a desktop app, but a manual-only client could be lighter if the slim bundle is verified to exclude the analytics extension. Verify the size with the project's own build before deciding.

**F12. [info] posthog-rs.**
- Claim: crate `posthog-rs`, shown as version 0.14 in the docs. Async client is the default. A blocking client is enabled by `default-features = false`. `capture` is non-blocking and hands events to a background worker, so `flush()` or `shutdown()` is needed before exit.
- Evidence: [posthog-rs docs](https://posthog.com/docs/libraries/rust) (fetched). Maintainer status is inferred from PostHog hosting the docs, not stated. crates.io metadata NOT verified (page did not render). Check [the crate page](https://crates.io/crates/posthog-rs) or `https://crates.io/api/v1/crates/posthog-rs` before pinning.
- Fix: if Rust-side capture is needed (F6 fallback), use it with an explicit allowlist. Rust-only capture is a simpler privacy surface than the JS SDK.

**F13. [info] Runtime key and host.**
- Claim: the project key and API host can be supplied at runtime because `posthog.init` takes both. The host defaults to the US cloud. A self-hosted instance works if it is reachable.
- Evidence: config page `api_host` and the [JS install page](https://posthog.com/docs/libraries/js). Whether the project key is safe to expose is UNVERIFIED; it is normally embedded in client bundles, which suggests it is a write-only public token, but I did not confirm this in the docs.
- Fix: follow the Sentry pattern: store the key in settings, default off, initialize only when the owner opts in. Do not hardcode the key.

**F14. [medium] Self-hosting is unsupported and cloud-only for paid features.**
- Claim: Docker Compose hobby deploy is MIT-licensed. PostHog says self-hosted deployments are "officially unsupported," with no guarantees. New Kubernetes deployments are no longer supported. Minimum is a 4 vCPU, 16 GB RAM, 30 GB+ VM. "All paid-plan features are Cloud-only."
- Evidence: [self-host docs](https://posthog.com/docs/self-host) (fetched via the summarized page; the `/docs/advanced/self-host` path returned 404).
- Fix: for a privacy-first app with no backend, self-hosting adds a server to run and maintain. Cloud with a minimal event set is simpler. Decide after the owner answers Open question 1.

## Open questions

1. Does the owner want a stable identifier across sessions (needs `localStorage`/cookie persistence) or none at all (`memory` or cookieless)? This changes F4.
2. Should the app ever send anything without an explicit opt-in per vault, matching Sentry? I assumed yes, per the request.
3. Is EU residency required? If yes, the EU project and host change (F9).
4. Is a self-hosted PostHog acceptable given its unsupported status (F14), or should the owner use Cloud?
5. What exact event list is wanted? Usage "over time" for feature counts needs only event names and a feature key, which fits the allowlist approach.
