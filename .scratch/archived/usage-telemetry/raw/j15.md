## Summary

- Sentry can answer "which features do I use most" without a new vendor. The most fitting primitive is Application Metrics (a counter per feature, trace-connected). Sentry Logs with a `feature` attribute also works, and Explore can chart either.
- The Developer (free) plan is thin for "over time" questions. Lookback is 30 days on the pricing page but 7 days on the Explore and Logs docs, a conflict I could not resolve. Team ($26/mo annual) gives 90 days.
- Volume is not the constraint. Feature-usage events are tiny next to the 5M spans and 5GB logs included in the free tier (my estimate, not a Sentry figure).
- Privacy is the constraint. Usage events are analytics, PRIVACY.md promises none, and a per-feature counter sent to Sentry is a new data flow. It needs its own opt-in toggle, separate from error reporting, and a PRIVACY.md update if enabled.
- I did not read the local Sentry files; this scout covered web facts only. I also did not write the output file, because the agent rules say not to write report .md files, so this Markdown is the return value.

## Findings

**F1. Sentry Logs is GA and has a JavaScript API.** Severity: info.
- Claim: Logs went GA on 2025-09-03. The browser SDK supports logs from 9.41.0, and they are enabled by default from 10.71.0. The API is `Sentry.logger.{trace,debug,info,warn,error,fatal}(msg, attrs)`. Attributes become searchable columns.
- Evidence: https://www.businesswire.com/news/home/20250903036545/en/Sentry-Structured-Logs-Now-Available-to-All ; https://github.com/getsentry/sentry/discussions/86804 ; https://docs.sentry.io/platforms/javascript/logs/ (fetched; the page was summarized by a model, so verify the exact quote). `beforeSendLog` can filter logs before they are sent.
- Suggested fix: For a feature-usage event, use `Sentry.logger.info('feature.used', { feature: 'kanban' })`. Set `enableLogs: true` explicitly so behavior does not depend on SDK version.

**F2. Application Metrics is the current custom-metrics product. The old beta is gone.** Severity: info.
- Claim: Counters, gauges and distributions, each event trace-connected. Aggregations include `sum` and `per_minute` for counters. `beforeSendMetric` exists. Metrics are counted separately from errors and do not group into issues. The page does not state retention or quota.
- Evidence: https://docs.sentry.io/product/metrics/ (fetched) ; https://docs.sentry.io/platforms/javascript/tracing/span-metrics/ (search result only) ; https://docs.sentry.io/product/accounts/quotas/ (fetched via /pricing/quotas/, which confirms "Logs and Application Metrics are counted individually").
- Suggested fix: A counter named `feature.used` with a `feature` attribute group-by fits "most used" queries. Confirm the JS API method name in the JS Application Metrics setup page before coding (UNVERIFIED here: the JS method signature was not fetched).

**F3. Custom spans are the wrong tool for usage counting.** Severity: low.
- Claim: Spans are billed as a unit (Developer includes 5M). Spans are subject to sample rate, so usage counts would be sampled. The docs point to Application Metrics for counts that sampling should not affect.
- Evidence: https://docs.sentry.io/pricing/quotas/ (fetched); https://docs.sentry.io/platforms/javascript/tracing/span-metrics/ (search only). Span attribute API details are UNVERIFIED.
- Suggested fix: Use metrics or logs for counts. Use spans only if you want latency per feature.

**F4. Explore can query and chart all of it, with saved queries and dashboard widgets.** Severity: info.
- Claim: Explore covers Traces, Logs, Metrics and Errors. Saved queries can go to a dashboard widget or a monitor. The plan's lookback limits each query window: "Developer, 7 days | Team, 14 days | Business, 30 days." Export is capped at 10,000 log lines (CSV or JSONL).
- Evidence: https://docs.sentry.io/product/explore/ (fetched) ; https://docs.sentry.io/product/explore/logs/ (fetched).
- Suggested fix: For a "top features" view, group logs or metrics by `feature`. Accept the lookback limit or move to Team.

**F5. Free-tier quotas and lookback.** Severity: medium.
- Claim: Developer includes 5k errors, 5M spans, 5GB logs, 50 replays, 1GB attachments, 1 cron, 1 uptime monitor, and a "30-day lookback". Team is $29/mo monthly or $26/mo annual, with "Up to 90-day lookback". Business is $89/mo or $80/mo annual, with 90-day lookback.
- Evidence: https://sentry.io/pricing/ (fetched). Also https://docs.sentry.io/pricing/ (fetched; it gives no base prices or lookback and redirects to sentry.io/pricing). Conflict: Explore and Logs docs give "Developer, 7 days" for the query window.
- Suggested fix: Treat Developer lookback as 7 to 30 days until the in-app Settings page shows the real figure. Confirm in the Sentry account.

**F6. Pay-as-you-go on the free Developer plan is unresolved.** Severity: medium.
- Claim: Pricing page shows "No" for Developer on spend notifications and maximum spend threshold, and ties PAYG to paid tiers. Third-party sources say Developer cannot buy PAYG. Logs overage is $0.50/GB, from third-party sources only. A free account over quota drops data.
- Evidence: https://sentry.io/pricing/ (fetched; table shows "No"); https://docs.sentry.io/pricing/quotas/ (fetched; the Developer question came back UNVERIFIED); https://maple.dev/guides/sentry-pricing/ (search only, secondary). Official log overage rate: UNVERIFIED.
- Suggested fix: Assume usage events are dropped when over the 5GB log quota. At personal scale that will not happen, but check the usage stats page after a week.

**F7. Retention beyond lookback is not documented.** Severity: medium.
- Claim: I could not find a retention table. The URL I guessed (docs.sentry.io/organization/data-retention/) returns 404. The lookback numbers above are query windows, not storage retention.
- Evidence: https://docs.sentry.io/organization/data-retention/ (404, fetched). No other source found; retention per category is UNVERIFIED.
- Suggested fix: Do not promise the owner year-long history from Sentry. For long-term usage, either keep a local count (see F9) or use Team for 90 days.

**F8. Some search-result claims are unverified and conflict with each other.** Severity: low.
- Claim: Developer error quota is listed as 5k by most sources and 50k by ReviewCost. Business error quota is 50k or 100k depending on source. Sources were not checked against sentry.io/pricing for these points.
- Evidence: sentry.io/pricing (fetched) matches 5k for Developer. The Business figure was not confirmed.
- Suggested fix: Do not rely on secondary pricing summaries. Use sentry.io/pricing.

**F9. Privacy: usage events are analytics.** Severity: high (to the privacy promise, if shipped on by default).
- Claim: PRIVACY.md promises no analytics and notes never leave the machine. Sending feature-name events to Sentry is analytics leaving the machine. Feature names alone are not note content, but any attribute carrying note titles, paths or tags would breach the promise.
- Evidence: PRIVACY.md and the Sentry wiring were not read in this scout (out of scope for the web task). The Sentry docs confirm `user.id`, `user.email` and `user.name` are attached automatically when set in scope (https://docs.sentry.io/platforms/javascript/logs/), which must be stripped from usage events.
- Suggested fix: If built, add a separate per-vault toggle (off by default), an allowlist of feature names only, `beforeSendMetric`/`beforeSendLog` that drops any attribute outside the allowlist, and a PRIVACY.md update. Alternatively, keep a local counter in the vault and never send it.

**F10. A local counter may beat Sentry for this question.** Severity: info.
- Claim: The owner asked "which features do I use most over time". A local count (per-feature integer in the app data folder, shown in Settings) answers that with no network traffic, no lookback limit, no quota and no privacy surface.
- Evidence: The lookback and retention limits in F4, F5 and F7 are the reason. This is reasoning from those findings, not a Sentry source.
- Suggested fix: Consider a local counter first. Use Sentry only if the owner wants cross-device aggregation, and then only as opt-in.
