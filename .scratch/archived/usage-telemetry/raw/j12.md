# Aptabase for Kokobrain (scout s14)

## Summary
- `tauri-plugin-aptabase` 1.3.0 targets Tauri 2 (`tauri = "2.11.5"`) and was released 2026-10-16. The JS package `@aptabase/tauri` 0.7.0 was released the same day. Before that, there was a gap from 2023 to 2025.
- Each event carries a session id that lives only in memory, OS name and version, locale, app version, engine name and version, and the SDK version. The source has no device id, device model, or CPU architecture. The docs page says "Device model" is collected, which conflicts with the source.
- Self-hosting is supported. The server runs on Docker with Postgres and ClickHouse, and the plugin takes a `SH` key plus a host. The docs site does not mention self-hosting.
- The app key is a compile-time-style string passed to `Builder::new` during app setup, so a user-supplied runtime key is only feasible if Rust reads it at startup before the plugin is registered. Switching keys means restarting the app.
- Any use of this plugin, even opt-in, would contradict the current PRIVACY.md wording ("No analytics, no tracking") and would need a privacy-text update and a per-vault opt-in gate.

## Findings

**A1. Plugin version and Tauri 2 support** (severity: info)
- Claim: the current Rust crate is 1.3.0 and targets Tauri 2. The older 0.1.5 on docs.rs is Tauri 1.
- Evidence: [crates.io API](https://crates.io/api/v1/crates/tauri-plugin-aptabase) shows 1.3.0 created 2026-10-16, with 1.0.0 on 2025-03-27 and 0.5.1 on 2024-02-04. [Cargo.toml on main](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/Cargo.toml) shows `version = "1.3.0"`, `tauri = "2.11.5"`, `rust-version = "1.85.0"`. The [docs.rs 0.1.5 page](https://docs.rs/crate/tauri-plugin-aptabase/0.1.5) is Tauri 1. The [npm registry](https://registry.npmjs.org/@aptabase/tauri) shows `@aptabase/tauri` 0.7.0 on 2026-10-16, with 0.6.0+ depending on `@tauri-apps/api ^2.10.1`.
- Suggested fix: pin `tauri-plugin-aptabase = "1.3.0"` and `@aptabase/tauri = "0.7.0"` if adopted. Note the Rust MSRV bump to 1.85.0 against the repo's CI pin of 1.98.0 (fine).
- Maintenance note: 1.x publisher is a single maintainer. The 0.x line had a three-year gap. Activity is recent but bursty.

**A2. Per-event data** (severity: high, privacy-relevant)
- Claim: each event sends `timestamp`, `sessionId`, `eventName`, `systemProps`, `props`. `systemProps` holds `isDebug`, `osName`, `osVersion`, `locale`, `engineName`, `engineVersion`, `appVersion`, `sdkVersion`. Custom props must be a JSON object of strings or numbers.
- Evidence: [client.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/client.rs) (payload keys, session id); [sys.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/sys.rs) (six `SystemProperties` fields: `is_debug`, `os_name`, `os_version`, `locale`, `engine_name`, `engine_version`; locale from `sys_locale`); README per the [GitHub page](https://github.com/aptabase/tauri-plugin-aptabase) for the string/number prop rule.
- Suggested fix: if adopted, never pass note titles, paths, or content as props. Event names only.

**A3. Device identifier and session persistence** (severity: medium)
- Claim: no device id is generated. The session id is `unix_seconds * 1e8 + random(0..1e8)`, held only in memory, and rotates after 4 h of inactivity. It is regenerated on every launch, so it is not a persistent user id.
- Evidence: [client.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/client.rs) (session field is `SyncMutex<TrackingSession>`, `SESSION_TIMEOUT` 4 h, nothing written to disk). [lib.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/lib.rs) shows no device id at setup.
- Conflict: the [Aptabase docs](https://aptabase.com/docs) say "Device: Device model is collected." The source has no device-model field, and the docs say "Device IDs ... never collected." Treat the source as authoritative for the 1.3.0 code, but flag the docs claim to the vendor. Confirmed by reading the code only, not by inspecting network traffic.
- Suggested fix: before any adoption, capture one real request body with a proxy to confirm the field set.

**A4. Self-hosting** (severity: medium, an option)
- Claim: the server can be self-hosted with Docker Compose (Postgres + ClickHouse, port 8000). The plugin's `SH` key type requires a `host` option; without it, tracking is disabled.
- Evidence: [aptabase/self-hosting](https://github.com/aptabase/self-hosting) (compose, port 8000, no default login, activation link in container logs). Search results for the image `ghcr.io/aptabase/aptabase:main` and AGPL-3.0 licensing come from a search snippet, not a fetched source. [config.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/config.rs) shows the `SH` branch and `InitOptions.host`.
- Caveat: the self-hosting repo does not show a license. The main repo's LICENSE URL returned 404. AGPL is UNVERIFIED from a primary source.
- Suggested fix: if self-hosted, the server would be on the owner's own machine or server, which fits "notes never leave the machine" only if the owner hosts it at home. Otherwise events go to Aptabase.

**A5. Pricing and EU hosting** (severity: low)
- Claim: free tier of 20,000 events/month. Paid from $10/month (200k events) up to $450/month (50M). No overage fees; analytics pause when the quota is exceeded. EU host is `https://eu.aptabase.com` (Germany); keys look like `A-EU-...` and `A-US-...`.
- Evidence: [Aptabase docs](https://aptabase.com/docs) (Limits & pricing, Hosting regions). Region mapping in [config.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/config.rs): middle segment `EU`, `US`, `DEV`, `SH`; base URLs `https://eu.aptabase.com` and `https://us.aptabase.com`; ingest at `/api/v0/events`.
- Suggested fix: n/a unless adopted. For a single-owner app the free tier is ample.

**A6. App key: compile-time or runtime?** (severity: high, design-blocking)
- Claim: `Builder::new(app_key: &str)` takes the key at plugin construction, and it moves into the config during setup. Nothing reads an environment variable. A user-supplied key is therefore feasible only if Rust code reads it at startup before `.plugin(...)` runs, and it is fixed for the process lifetime. Changing it requires a restart.
- Evidence: [lib.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/lib.rs) (`pub fn new(app_key: &str)`, `Config::new(self.app_key, self.options)` at setup). [config.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/config.rs) (no env var reads). The README's `dotenv!` example is compile-time.
- Inference (not tested): a Kokobrain Rust module could read a per-vault setting file before `tauri::Builder` is built. The frontend settings store (`settings.store.svelte.ts`) lives in the webview and cannot feed the plugin builder. This means the key-entry UI and the opt-in flag need a Rust-side persistence path.
- Suggested fix: if pursued, store the key in a Rust-readable settings file and register the plugin with it. Document the restart requirement in the Settings UI.

**A7. Delivery behavior** (severity: low)
- Claim: events queue in memory only, flush every 60 s in release (2 s in debug), up to 25 per request. Retries only for network and 5xx errors. The queue is not saved to disk, so unflushed events are lost on crash or quit. Events drop silently if the key is invalid.
- Evidence: [config.rs](https://raw.githubusercontent.com/aptabase/tauri-plugin-aptabase/main/src/config.rs) (flush intervals); the [GitHub README](https://github.com/aptabase/tauri-plugin-aptabase) (batching, retries, no disk queue).
- Suggested fix: n/a for usage stats; acceptable loss, but the owner should know counts can be undercounted on crash.

**A8. Conflict with repo privacy promises** (severity: high)
- Claim: PRIVACY.md currently says "No analytics, no tracking, no accounts, no sign-up. Sentry error reporting is the sole optional exception." ADR-0015 says cloud telemetry "could be added as an optional, opt-in layer later." Adopting Aptabase would make it a second exception and require updating PRIVACY.md and possibly ADR-0015.
- Evidence: [PRIVACY.md:8](/Users/diegorv/Dev/pet-projects/koko/brain/PRIVACY.md) and [docs/adr/0015-dual-logging-frontend-rust.md:71](/Users/diegorv/Dev/pet-projects/koko/brain/docs/adr/0015-dual-logging-frontend-rust.md). Also [docs/adr/0001-tauri-svelte-sveltekit-stack.md:22](/Users/diegorv/Dev/pet-projects/koko/brain/docs/adr/0001-tauri-svelte-sveltekit-stack.md) says telemetry must not require an internet round-trip. The plugin sends events online with no offline fallback.
- Suggested fix: any adoption must be off by default, per-vault opt-in, use the owner's own key or self-hosted server, and update PRIVACY.md before shipping.
