## Findings

1. **nit** `src/lib/plugins/mods/ModsStatusList.svelte:57-59` — A read issued when a reload replaces the entry can resolve after a newer commit and overwrite that commit's optimistic value. The row then shows the older value while the newer one is pending, and `commitSetting`'s unchanged check (`:75`) compares against it, so setting the field back to the value shown is skipped and the pending value is written. The window is one `read_mod_data` IPC after a reload finishes, and the next reload's re-read corrects the display. Fix (optional): count commits per folder and drop a read result that started before the latest commit.
2. **nit** `src/lib/plugins/mods/mods.logic.ts:243` — Inside `parseModManifest`, `const fields: ModSettingField[]` shadows the outer `fields` (the raw manifest record, `:205`). It is correct but easy to misread. Fix: rename the inner one, for example `parsedFields`.
3. **nit** `src/lib/plugins/mods/mods-host.service.ts:940` — The drain awaits only the instances this pass unloads (`running`). A write still in flight from an instance unloaded earlier, for example by `disableMod` just before a re-enable and an immediate edit, is not awaited. The build report names this gap. It needs a toggle-off-on and an edit within one IPC, and Behavior 7 asks only for "the old instance". No change needed; mention it in the delivery notes.
