## Findings

1. **blocker** `src/lib/features/todoist-sync/sections.logic.ts:389` (with `:382`). A link with no `local_base.location` loses its brain heading. This covers every link made before this Issue and every link paired in rebuild mode (design rule 1).
   - What happens: a user line under a brain `##` heading that has no Todoist section goes out as `section_add`. The next cycle pulls the line back out of that heading, to above the sections, and leaves the new Todoist section empty. In cycle 1 the line is skipped (`sectionId === undefined`, `:382`), so its location is never set. In cycle 2 `local.location === undefined` takes the "Todoist wins" branch, and the line moves to Todoist's place.
   - Reproduced with a probe (not committed): after a first sync, drop `location` from every `local_base` and put `td-w1` under a new `## Today`. Cycle 1 sends `section_add Today`. Cycle 2 sends no `item_move`, rewrites `Todoist/Work.md` to `...td-w2\n- [ ] Plan ... td-w1\n\n## Today\n`, and leaves `w1` at `section_id: null`.
   - This goes against the Issue's "a new `##` heading with tasks becomes a section", on the store-loss path and on the first cycle after upgrade.
   - Fix: when a link has no location and its line sits under a heading whose place is not known yet (`:382`), store `location` as Todoist's current place, or otherwise mark the brain as the side that placed it. Once the heading is linked, the line then pushes `item_move` instead of being pulled out. Add a sync-now test for a link with no location under a new brain heading, and one for the rebuild-then-normal sequence.
2. **minor** `src/lib/features/todoist-sync/task-line-edits.logic.ts:152` and `src-tauri/src/vault/task_lines.rs:340`, against `sections.logic.ts:175`. The planner counts only `##` headings, but the writer's `afterHeading` and `renameHeadings` match a heading of any level.
   - What happens: a project note with a `### Next` (or `# Next`) and a Todoist section `Next` gets a `## Next` appended, and the batch then goes stale as `headingDuplicated` on every cycle. That blocks every other write to the note: a new no-section task `w4` was never inserted, the message said "nothing new", and only a `stale` log row was written (probe, not committed).
   - Fix: give section inserts and renames a level-2 match in both writers (or count every level in `noteOutline` when deciding to append, pair or rename), and add a test.
3. **minor** `src/lib/features/todoist-sync/sections.logic.ts:226-234`.
   - A `## ` heading with empty text that has a task line under it goes out as `section_add` with `name: ""`. `headingText` guards only the Todoist side.
   - A refused `section_add` (documented default) is retried and logged as `command-error` every cycle, which fills the 1000-row log.
   - Lines under a heading whose text is duplicated in the note, or whose linked section is archived or deleted, never move and never go to `section_id: null`. The criterion says a line under no linked heading has `section_id: null`.
   - Fix: skip empty heading texts in `noteOutline` or `planSections`. Consider keeping refused heading texts (as `projects` keeps `refused`), and say in discovery.md that lines under unlinkable headings stay in place indefinitely.
4. **nit** `src-tauri/tests/todoist_state_test.rs`, `src-tauri/tests/vault_task_lines_test.rs`. The build report says the Rust tests were written in the same step as the code and never seen failing, which falls short of "Failing tests first". They do pass and assert real behavior. No change needed beyond noting it.
5. **nit** `src-tauri/src/db/todoist_repo.rs:79`. `delete_section_ids` / `deleteSectionIds` is never sent by the engine (only the tests and the vault fake use it). It mirrors `deleteAnchors`, which is also unused. Speculative, but small. Keep it or drop it.

Both failed first (`w1` stayed at `section_id: null`). There is also a unit case in `sections.logic.test.ts`.
2. **Fixed** in bb15f480a. `unique_heading` (`task_lines.rs:340-343`) and `uniqueHeading` (`task-line-edits.logic.ts:151-153`) match only level-2 headings, so `afterHeading` and `renameHeadings` name the same headings `noteOutline` counts. The Todoist sync's section edits are the only callers of either. Rust and TS writer tests cover insert and rename, and a sync-now test covers a `### Next` heading next to a section `Next`, where a later new task is still inserted and no `stale` row is logged. Each was seen failing first. The doc comments changed, so the ts-rs bindings were regenerated and committed.
3. **Fixed** in dbf1177c7. `planSections` skips a `##` heading with no text (`sections.logic.ts:234-235`). A terminal `section_add` refusal is logged only on manual cycles (`pushSections`, `sync-now.service.ts:770`), as the skipped-creates log is. It is still resent every cycle, and is not remembered, which would need new persisted state. The fake gets `refuseSectionAdds()`, and the sync-now test "logs a refused section_add on a manual cycle only" failed first with 3 log rows. `discovery.md` now says lines under a heading that can never be linked stay in place indefinitely and keep their Todoist section: an empty heading, a duplicated heading, a heading whose section is archived or deleted, or a heading whose `section_add` is refused. Remaining: when the refused heading is a brain rename, its `section-renamed` log row (`sync-now.service.ts:457`) is still written on every cycle that sends the add, including automatic ones.
4. **No change**, as the finding says. The Rust tests added in this round (`insert_after_a_heading_matches_only_a_level_two_heading`, `a_rename_matches_only_a_level_two_heading`) were run against the unfixed `task_lines.rs` and failed first (2 failed), then passed.
