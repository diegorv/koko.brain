## Findings

1. **major** `src/lib/features/todoist-sync/pull.logic.ts:431` — The signifier skip keys on `task.contentProblem === 'signifier'`, but `contentRoundTripProblem` (`task-line.logic.ts:324-330`) returns only the first problem, checked in the order newline, empty, hash, signifier. Content with a `#` or a line break before the signifier check is inserted as-is. Probe run through `planPull` (test file written and removed during the review): `Fix #12 📅 2020-01-01` became `- [ ] Fix #12 📅 2020-01-01 🆔 td-a`, and `Line one\n⛔ blocked` became `- [ ] Line one ⛔ blocked 🆔 td-b`, each logged only as `content-roundtrip`. The parser then reads a `📅 2020-01-01` that Todoist does not have, while `local_base.dueDate` is null, so the field sync (Issue 09) would see a local due change and push it. `🆔` is still caught by the `readAnchor` backstop, so the anchor stays safe; the gap is the "any other signifier" half of the criterion. Fix: test for a signifier on its own (export a `hasSignifier`/`SIGNIFIER` regex from `task-line.logic.ts`, or check it before `contentRoundTripProblem`'s ordering applies), and add failing tests for `Fix #12 📅 2020-01-01` and `A\n⛔ b`.
2. **minor** `src/lib/features/todoist-sync/completion.logic.ts:172` — The close is dropped whenever the remote due day moved, recurring or not. Example: a non-recurring task rescheduled in Todoist since the last sync, then checked in the brain. The brain close is discarded and the line is reopened with the new date (logged `close-dropped`), so the user's check silently undoes itself. This follows design rule 6's literal text ("if remote `due` moved since the base, drop the pending close"), and the criterion says the same. The rationale (a close acting on a stale occurrence) only applies to recurring items. Fix: either limit the drop to `remoteBase.due?.isRecurring || item.due?.isRecurring` with a test for the non-recurring case, or keep it and have the owner confirm the behavior in the Issue Notes.
3. **nit** `src/lib/features/todoist-sync/completion.logic.ts:185` — A stored `pending_cmd` that is no longer wanted (for example a close whose send failed, then the line was reopened before the next run) is cleared with no log entry. `discovery.md` says "otherwise cleared (logged when dropped)". If Todoist did apply the lost close, the next cycle closes the line again with no trace in the sync log. Fix: push a `pending-dropped` log entry when `pending !== null && push !== pending.type`, or correct `discovery.md`.
4. **nit** `src/lib/features/todoist-sync/completion.logic.ts:282` — `planAck` moves `remote_base.due` to the ack pull's due even for a non-recurring item, where no `📅` is written. If someone else changed that due between the cycle pull and the ack pull, the change is absorbed into the base and never reaches the line. This is a narrow race and only matters once the field sync (Issue 09) lands. Fix: move `due` only when the `📅` is written, as `planCompletion` does (`:198`).

1. **Fixed** in 5064e771f. `task-line.logic.ts` exports `hasSignifier` (the signifier regex on its own; `contentRoundTripProblem` uses it), and `planPull` skips on `hasSignifier(item.content)` instead of `contentProblem === 'signifier'`. 2. **Rejected, owner call.** The current behavior is what the Issue's criterion ("A pending close is dropped when the remote `due` moved since the base") and design rule 6 (`research/design.md:16`, "if remote `due` moved since the base, drop the pending close") both state, with no recurring qualifier. Limiting the drop to recurring items changes what the user sees against the written criterion, and this step cannot get the owner's confirmation. The reviewer's case (a non-recurring task rescheduled in Todoist, then checked in the brain, gets unchecked again with a `close-dropped` log entry) is real and is recorded here for the owner: if they choose the recurring-only rule, the change is the `dueMoved` condition at `completion.logic.ts:172` plus one test.
3. **Fixed** in 8f4cbe4cd. `planCompletion` logs `pending-dropped` when a stored pending command is cleared without being replaced, unless Todoist already shows its effect (e.g. both sides closed: the lost close was applied) or the close is already logged as `close-dropped`. Test: "logs a pending command cleared because the line no longer wants it". The discovery's "logged when dropped" now holds.
4. **Fixed** in 8f4cbe4cd. `planAck` moves `remote_base.due` only when it writes a `📅`, as `planCompletion` does. Test: "leaves the remote due base alone when no 📅 is written".
