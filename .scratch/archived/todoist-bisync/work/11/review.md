## Findings

1. major — src/lib/features/todoist-sync/sync-now.service.ts:644 — `writeProjectId` writes `todoist_project` through `updateNoteFrontmatter`. When the note is open in a tab, that function patches the tab and then calls `saveFileByPath` right away (`core/frontmatter/frontmatter-write.service.ts:131-140`). This breaks design rule 12 ("the background job never saves the user's tab") and the engine's own contract in `note-writer.service.ts:31` ("A tab is never saved or reloaded from here"). This is the common case, not a corner case: a note the user just created in the sync folder is usually still open when the cycle acknowledges its `project_add`, so a background or automatic cycle saves the user's tab and runs the after-save hooks the user did not trigger. Fix: for a note with a tab, put the new frontmatter into the tab content without saving (the same `syncExternalContentToEditor` content-only path the note-writer uses for background tabs, so autosave persists it), and keep `updateNoteFrontmatter` for closed notes only. Add a service test with the note open in a tab that asserts the tab content carries the id and no save ran.
2. minor — src/lib/features/todoist-sync/projects.logic.ts:193,238 — `taken` includes the renamed note's own path in lower case. A case-only Todoist rename therefore collides with itself and gets a suffix. Probe: base `{name:'Acme', relPath:'Todoist/Acme.md'}` with Todoist name `acme` plans `to: 'Todoist/acme 2.md'`. Fix: leave `note.relPath` out of the collision check for its own rename (macOS is case-insensitive, so `renameItem`'s `exists` check would also refuse the case-only target; route that case through a two-step rename or keep the current path and just move the base name), and add a case to "renames the note after a Todoist rename".
3. minor — src/tests/lib/features/todoist-sync/sync-now.service.test.ts — the cross-request temp-id resolution added to `sendCommands` (`sync-now.service.ts:735`, `withRealProject` with `resolved` and `known`) has no test. Two paths are uncovered: a brain-born project whose `project_add` lands in one 100-command request and whose `item_add`s land in the next, and a line resend that names the temp id of a project acknowledged in an earlier cycle (`known` from `base.tempId`). Removing that mapping would leave every current test green, and both failures would detach the lines for good (404 terminal). Fix: add a service test with more than 100 commands in one cycle, the `project_add` near the end of the first request and its lines in the second, and one where the line's `item_add` gets a non-terminal status while the project is acknowledged, then succeeds on the next cycle.
4. minor — src/lib/features/todoist-sync/projects.logic.ts:271 — when a brain-born note is renamed while its `project_add` is unacknowledged (lost response), the pending add is dropped and a new add goes out under the new name. That makes a second Todoist project if the first was applied. The note's anchored lines keep `pending_cmd` naming the dropped temp id. Nothing resolves it, so the resend gets a 404 and those lines are detached for good. The build report lists the first half but not the line detach. This is a rare race (lost response, then a rename before the next cycle), so it needs no code under the owner's rules. Record it in the follow-up Issue: the cheapest fix would be to match a pending add whose note moved by the anchors of its lines rather than by path.
5. nit — src/lib/features/todoist-sync/sync-now.service.ts:216 — `treeIds` comes from the full pull only, while `planPull` builds its tree from the merged full and incremental rows. Suppose a project is deleted between the two pulls of one cycle. The incremental row shows the deletion and `planDetach` detaches its links, but `planProjects` skips the base because the full-pull `treeIds` still contain the id. The token then moves past the deletion, so the base never detaches. The effect is harmless (nothing syncs into a deleted project), but computing `treeIds` from the merged `projects` would make the two consistent.
6. nit — src/lib/features/todoist-sync/projects.logic.ts:40,43,50,57,60,66,67,92,95,96 — several exported interface fields have no JSDoc (`PendingProject.uuid` is documented but `args` is not; also `ProjectState.pending`, `PlannedNoteRename.projectId/from/to`, `PlannedProjectUpdate.projectId/uuid`, `ProjectInput.state/newUuid/newTempId`). CLAUDE.md Conventions requires JSDoc on interface fields. Add one line each.
7. nit — .scratch/todoist-bisync/work/11/discovery.md:29 — it says "Rebuild mode: bases adopted, no add, no rename", but the code (`sync-now.service.ts` `allowAdds: plan.mode === 'normal'`) only stops adds; renames and `project_update`s still run in rebuild mode, as the build report says. Rule 1 only forbids creates, so the code is acceptable. Correct the discovery line so later agents do not rely on it.
