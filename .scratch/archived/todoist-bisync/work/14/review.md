## Findings

1. **major** `src/lib/features/todoist-sync/sync-scheduler.service.ts:165` A queued manual follow-up ignores the 429 wait. When "Sync now" is pressed during an automatic cycle and that cycle gets a 429, `handleOutcome` sets `blockedUntil`, then `runCycle` starts the queued manual cycle at once and sends another `/sync` inside the `retry_after` window. That breaks the criterion ("wait ... before the next cycle"), design rule 13, and the service's own doc ("during a 429 wait it sends nothing"). Probe (fake 429 with `retry_after: 90`, requests held, `syncNowFromUi()` pressed, then released): Todoist received 2 requests. Fix: before running the queued manual follow-up, apply the same `blockedUntil` check as `requestManualCycle` and resolve its waiters with the rate-limit refusal message; add that case to `sync-scheduler.service.test.ts`.
2. **minor** `src/lib/app/lifecycle/app-lifecycle.service.ts:672` with `src/lib/features/todoist-sync/sync-now.service.ts:85` After a vault switch during a cycle, `teardownVault` resets `todoistSyncStore`. Then the old cycle's `assertVault` fails and `todoistSyncStore.fail(VAULT_SWITCHED)` puts the store back in `error`. The next vault's status bar then shows "Todoist sync error" ("The vault changed during the Todoist sync") until its own first cycle succeeds. Probe: stop, reset, `vaultStore.open('/other-vault')`, release; the store ended in `status: 'error'` with that message. Fix: on `vault-switched`, leave the store alone (the store now belongs to the next vault), and add a test.
3. **minor** `src/lib/features/todoist-sync/sync-scheduler.service.ts:155` An automatic cycle checks `first_run_done` for `s.vaultPath`, but `syncNow` then reads `vaultStore.path` fresh. If the vault switches while `todoist_read_kv` is pending and the new vault's index is already ready, the automatic cycle runs on the new vault without checking that vault's `first_run_done` (rule 9). The window is narrow. Fix: after the await, return `SKIPPED` unless `s === session && vaultStore.path === s.vaultPath`.
4. **nit** `src/lib/features/todoist-sync/sync-scheduler.service.ts:67` The after-save observer runs `hasAnchoredLine` (a full `extractTaskLines` parse) on every saved note of every vault, including while `syncEnabled` is off, which is the default. Fix: return early when `!settingsStore.todoist.syncEnabled`.

## Resolution

All four findings fixed, each test-first (the new tests failed before the fix, then passed).

1. Fixed in f386d619c. `rateLimitRefusal()` is shared by `requestManualCycle` and the queued manual follow-up in `runCycle`; a queued "Sync now" after a 429 resolves with the wait message and sends nothing. Test: "refuses a "Sync now" queued during the cycle that gets a 429, without calling Todoist" (1 request, toast "Try again in 90 seconds").
2. Fixed in 0620ee951. `syncNow` no longer calls `todoistSyncStore.fail` for the `vault-switched` failure; the outcome keeps its message and kind. The store is left to `teardownVault`, which runs on the only path that changes `vaultStore.path` (`switchVault` -> `initializeVault`). Tests: "leaves the store reset by the vault teardown alone when the old run stops" (idle, no error), and the existing mid-cycle switch test now expects the store untouched.
3. Fixed in 1b29f8b02. `autoCycleAllowed()` reads `first_run_done`, then returns false unless `s === session && vaultStore.path === s.vaultPath`; the cycle ends as `SKIPPED`. Test: "skips a cycle whose vault switches while its first_run_done is read" (0 requests, no writes to the new vault).
4. Fixed in 2e291abd0. The after-save observer returns before `hasAnchoredLine` while `syncEnabled` is off. Test: "schedules nothing for a save made while sync is off".
