## Findings

1. **minor** `src/lib/app/tauri-listeners.service.ts:189` / `:226`: the property index can now stay stale for longer than before. Two cases:
   (a) A whole-vault `get_all_property_records` read (from `fullRefresh`, the watcher's full rebuild, or vault open) is issued before a later per-path delta. That read can land after the delta, since the Issue measured whole-vault payloads arriving 0.65-1.1 s late. It then overwrites the delta's newer record with the older one.
   (b) `buildPropertyIndex` fails during a full rescan refresh. It logs and leaves the store alone, and `isIndexReady` stays true, so later refreshes only patch per path. The rest of the rescan never reaches the property index.
   Before this branch, the next event of any note re-read everything and healed both cases. Now a stale record heals only when its own path is touched again or at the next full read. The listener JSDoc documents (a); (b) is not documented. Concrete trigger for (a): a favorite toggle within about 1 s of a watcher full rebuild. The collection views then show the old `favorite` value for that note.
   Fix (a follow-up is fine): give `buildPropertyIndex` a start sequence, and have `applyPropertyDelta` remember the paths it patched after that start. When the whole read lands, apply its snapshot and then re-apply those paths, or drop the whole read when a delta landed after it began. For (b), reset `isIndexReady` (or force a full refresh on the next window) when a whole read fails.
2. **minor** Acceptance criterion 4 (Heartbeat `[HB] stall` on a favorite toggle, 10k notes) is unverified. The owner has to measure it before the Issue is marked resolved. One reason to measure rather than assume: `typeDefinitionsStore.patchEntries` still replaces `entries` and bumps `entriesVersion`, so every `$derived` / effect downstream of the type-definition entries still recomputes over the whole array. The Issue's measured `setEntries` cost of 23-28 ms with a forced `flushSync` may be mostly that downstream work. Only the payload deserialization, the main stall, is gone for sure.
3. **nit** `src/lib/features/type-definitions/type-definitions.store.svelte.ts:13`, `:15`, `:26`: the comments "Rebuilt on every setEntries" and "Always rebuilt together with `entries` in setEntries/reset" are now incomplete, because `patchEntries` also writes `entriesByPath` (patched, not rebuilt) and conditionally rebuilds `typeDefinitionPaths`. Fix: name `patchEntries` in all three comments.
4. **nit** `src/lib/app/tauri-listeners.service.ts:145-147`: the JSDoc narrates history ("A one-note save used to cost two whole-vault payloads ... (308-369 ms on a 10,628-note vault, Issue 65)"). The comment rules ask code comments to describe the code as it is, with counts and measurements kept in the commit message. Fix: keep a short "why" with the Issue link and drop the "used to cost" measurement.
5. **nit** `src/lib/core/vault/vault-entries.logic.ts:30`: the sorted merge uses UTF-16 order while Rust sorts by bytes. The two orders differ only between astral-plane characters and U+E000-U+FFFF, but `buildTypeDefinitionPaths` is first-match-wins in snapshot order. So in that case, two Type notes with the same title could resolve to a different winner after a patch than after a full read. This is documented, the case is vanishingly rare, and no change is needed beyond knowing it.
