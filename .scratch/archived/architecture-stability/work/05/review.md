## Findings

1. **major** `src/tests/lib/architecture/feature-cycle.test.ts:62-64` — "there is exactly one cycle, made of the features featureCycleEdges names" fails once the cycle is fully broken or splits into two, which is where this ratchet is supposed to lead. Probe: an acyclic graph with an emptied baseline gives `checkFeatureCycles` `{unlisted: [], stale: []}` but `stronglyConnected` returns `[]` against an expected `[[]]`. Two cycles `a<->b`, `c<->d` with all four pairs baselined give `[["a","b"],["c","d"]]` against `[["a","b","c","d"]]`. Someone who follows the stale instruction all the way then gets a red test, and the only way out is to edit the test. Fix: compare the members, not the component shape, e.g. `expect(stronglyConnected(pairs).flat().sort()).toEqual(members(baseline.featureCycleEdges))` (unlisted/stale already cover the rest). Add synthetic cases for "cycle fully broken, empty baseline" and "cycle split in two" that go through this same assertion.
2. **minor** `src/tests/lib/architecture/feature-cycle.test.ts:75-79` — "featurePairs records every directed feature pair" can never fail: it reads back the file the module wrote a moment earlier (lines 41-44). It reads as a check but proves nothing, and in CI a stale `featurePairs` passes without a word. Fix: drop the test, or rename it so it does not claim to check anything. If owner review of new acyclic pairs should also hold in CI, make a drift fail there (e.g. when `process.env.CI` is set) and keep the rewrite for local runs.
3. **minor** `src/tests/lib/architecture/feature-cycle-baseline.json:2-35` — the baseline adopts a bigger cycle than the Issue describes. 2 features and 9 pairs joined after the Issue was written: `search -> rail-shell` comes from `src/lib/features/search/open-search.service.ts:2`, and rail-shell landed with sidebar work (8484df17). The Notes allow regenerating the counts, and nothing in the repo can remove these pairs within this Issue's scope. But "adding a pair needs owner sign-off" is the rule this baseline sets up, and these 9 pairs get in without it. Fix: no code change. Record the 10->12 / 24->33 growth in the delivery commit and the ledger so the owner sees it, or open a follow-up to take `search -> rail-shell` out of the cycle.
4. **nit** `src/tests/lib/architecture/feature-cycle.test.ts:41-44` — the module-level `writeFileSync` runs on every `vitest run`, the deliver full suite included, so whenever the graph drifts a tracked file ends up modified. Fix: deliver should check `git status` after the full suite. No code change needed if the owner accepts the defaults in discovery.md.
