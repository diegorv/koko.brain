## Findings

1. minor — src/lib/core/filesystem/path-change.service.ts:51-52 and CLAUDE.md:285. The `registerPathChangeConsumer` JSDoc still says "`app-lifecycle` calls it during vault teardown". The Indexing item 6 "Consumers register" bullet still names only the vault-lifetime wiring in `initializeVault`. Neither is true for the two app-lifetime consumers `registerAppPorts()` now registers: those are never unregistered. A later reader could "fix" them into the vault-lifetime list, which Hazard 1 forbids. Fix: say in both places that consumers are either vault-lifetime (wired by `initializeVault`, unwound in teardown) or app-lifetime (wired once by `app/boot.ts::registerAppPorts`, never unwound).
2. nit — CLAUDE.md:287. The "`save` must stay synchronous" bullet still says `notifyAfterSave` depends on the consumer fan-out finishing "before `invalidateQueryjsCache()`". That call now happens inside the queryjs listener of `notifyContentInvalidated()`. The bullet is still true but names the old call site. Fix: "before `notifyContentInvalidated()` (whose queryjs listener clears the cache)".
3. nit — src/lib/core/filesystem/path-change.service.ts:133-139. The view-cache eviction used to run at the end of `applyPathChange`. It now runs right after `diskOp`, before the `updateLinksAfterRename` / `refreshTree` / `rename_note` awaits. A `refreshViewDefinition(from)` started before the rename and resolving during those awaits can now re-insert a stale entry; before, the late eviction would have dropped it. The old code had the same window after its own eviction, the race is rare, and the entry is for a path that no longer exists. No change requested; noted for the post-delivery review (Hazard 3).
