## Findings

1. minor — src/lib/core/frontmatter/frontmatter-write.service.ts:149 — Scope: the fix changes the core writer, which is outside the Issue's Files line (`src/lib/features/event-calendar/`). Every caller (lifecycle, file-icons, bookmark migration) now gets `missing` where a note vanishes mid-write, instead of a recreated file. That is the only atomic place for the refusal, it matches the function's own doc ("never re-creates a note that vanished"), and the build report says so. No change is needed; the main session should know the blast radius when it reads the ledger.
2. minor — src/lib/features/event-calendar/event-calendar.service.ts:607 — The new doc sentence says a refused write "leaves the tombstone in place". For an outside rename that is only half the story. `remapPath` (store :211) has already copied the in-flight overlay's `after` state into a settled `create` at `to`, with a version clock. After the write is refused, the calendar shows the renamed note at the never-written position for up to two bumps, while the disk keeps the old fields. This is no regression: before the fix the same overlay showed, and the write also recreated a duplicate note at `from`. The model generator still excludes this case for renames. Fix: mention it under "Known limitations", or file a follow-up (an outside rename racing a field write, where the moved `create` carries the refused state).
3. minor — src/tests/lib/features/event-calendar/event-calendar.service.test.ts — No service-level test checks that the calendar write rejects with `reason: 'missing'` (the user's "moved or deleted" toast) when an outside delete races it. The writer test checks the writer, and the rename variant (:2437) checks the rename path; the delete named sequence checks the store, the disk and the history but not the rejection. Fix: add a service test (hold the write, `moveEvent`, `deleteItem`, release) asserting `rejects.toMatchObject({ reason: 'missing' })`, that the note is still hidden and that the history is empty.
4. nit — src/lib/core/frontmatter/frontmatter-write.service.ts:150-153 — When the vault switches during a write that is then refused, the catch throws `missing` before `assertVault` runs, so the caller sees `missing` rather than `vault-changed`. This is harmless (nothing was written, and the calendar drops stale results through `isCurrent`), but the order differs from the success path.
