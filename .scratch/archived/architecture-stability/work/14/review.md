## Findings

1. **major**, `src/tests/lib/features/event-calendar/event-calendar.model.test.ts:353`: The random run caught none of the four reverted fixes. With each of abeec4ee, d57c0ff9, b9c9eb90 and 471978db reverse-applied, `-t 'random interleavings'` still passed all 300 seeds; only the named sequences failed. The two-bump end check is close to tautological for clocked overlays: `prunePending` drops any settled, clocked write once `version >= settledAtVersion + 2`, whatever its state. So the end check can only catch unsettled writes, unclocked overlays and pure projection errors. In a probe, I bumped once when the run's log had no `outside*` op and twice otherwise (`await vault.refresh(run.log.some((o) => o.op.startsWith('outside')) ? 2 : 1)`). It passed all 300 seeds on the current code and, with abeec4ee reverted, failed at seed 150 ("no pending write outlives ...", a settled update overlay at version 4 with settledAtVersion 3). Fix: use the one-bump horizon for runs with no outside change (or no outside change racing a calendar write), keeping two bumps only where the race is legitimate. That makes the random run detect at least one real regression class.
2. **major**, `.scratch/architecture-stability/work/14/discovery.md:56-67`: Five real races the unrestricted runs found are recorded only in the work notes, the build report and a short paragraph in the test header. The work notes are cleaned up at close, and the commit message points at "the build report", which is not in the repo. I reproduced race 4 with a probe sequence (move, settle, hold, move, flush, undo, release, settle): the undo returns `refused` ("#5 undo Move event"), so Cmd+Z during an in-flight drag write is silently dropped. Race 1 can clobber a later write, which is data the user typed. Fix: before closing Issue 14, file each race as a `.scratch/architecture-stability/issues/` follow-up (needs-triage) and point the model test's header at them. The generator limits that exclude them can then be lifted per fix.
3. **minor**, `src/tests/lib/features/event-calendar/event-calendar.model.test.ts:390-391`: Rethrowing as `new Error(message)` drops the assertion's `actual` / `expected` diff. A `check` failure reads only `expected [ { …(8) }, …(1) ] to deeply equal [ { …(8) }, …(1) ]` (seen in the abeec4ee mutation run), so the failing field is not visible. Fix: pass `{ cause: err }` and append the AssertionError's `actual` / `expected` (JSON) to the message.
4. **minor**, `src/tests/lib/features/event-calendar/event-calendar.model.test.ts:372-376`: The "every write is indexed in its vault" check compares counts per path (`indexed >= written`), not order. An `update_note_in_index` from another source (create, restore) can stand in for a missing one, and "followed by" is not checked. Fix: match each write to a later `update_note_in_index` on the same path in `VAULT` (consume the matches in order).
5. **minor**, `src/tests/lib/features/event-calendar/event-calendar.model.test.ts:669-676`: A failing seed prints its number, but there is no way to replay that one seed short of editing the loop. Between seeds only `setUp` runs; `settingsStore` / `editorStore` / localStorage are reset only per `it`, so seed N run alone is not guaranteed to match seed N inside the loop. Fix: read an optional `MODEL_SEED` env var to run a single seed, and reset the same stores per seed that `beforeEach` resets.
