# P2P Vault Sync

Sync a Kokobrain vault between two computers on the same LAN. No server, no cloud account,
no third-party service holding the notes.

## Decisions

| Topic | Decision |
|---|---|
| Network scope | Same LAN. No NAT traversal, no relay, no internet path. |
| Peers | Exactly two machines, both macOS. |
| Transport | `rsync` over `ssh`, both preinstalled on macOS. Nothing hand-rolled. |
| Pairing | An ssh keypair, generated once, public key copied to the peer. |
| Addressing | `<hostname>.local`, typed once into settings. There is no discovery; the app announces nothing about itself. |
| Peer identity | A UUID generated once and stored in settings on both sides. **Not** the hostname. |
| Granularity | One folder per side, vault-relative. Empty means the whole vault. |
| Timing | Manual. A button. No background sync, no scheduler. |
| Direction | Pull only. The button writes to the local vault and never to the peer. |
| Deletions | Never propagated, in either direction. A file deleted locally is not re-created; a file deleted on the peer is not removed locally. |
| Conflicts | Local wins. The remote version is preserved as a conflict copy. |

Addressing and identity are deliberately separate. `LocalHostName` is a network address: it
changes when the Mac is renamed and macOS auto-appends `-2`/`-3` on mDNS name collision. Keying
sync state on it means one rename silently invalidates every baseline in the state file, which
drops every differing file into the conflict row and produces a conflict copy for the entire
vault in a single press.

## Design principles

Three principles decide every trade-off below.

**1. The network phase must not be able to lose a note.** A transfer that is interrupted,
truncated, or hostile writes into a disposable staging area, never into the vault. There is a
point in the run where zero vault bytes have changed and the entire payload is already on local
disk.

**2. The filesystem is the authority on path identity, not our in-memory model.** APFS folds
case by default (verified: writing `readme.md` next to `README.md` yields one file, one inode,
the original name preserved). Any design that decides "does this file exist locally?" from a map
built earlier is wrong twice: wrong about case, and stale by the time it writes. We ask the
filesystem, at the moment we write.

**3. Every line of budget goes to the code that writes.** Transport, encryption, framing,
resume, and delta are solved problems available as a binary. Merge semantics on a user's vault
are not. The test suite is weighted the same way.

## Architecture

Three layers. Only the third can modify the vault.

### Layer 1 - Transport

`rsync` over `ssh`, invoked from Rust with `std::process::Command`.

sshd is the listener and an ssh keypair is the pairing, so the app ships no protocol, no
framing, no handshake, no listen port and no crypto dependency. The peer must have Remote Login
enabled, which is off by default on macOS. That is the whole setup on the serving side.

**Non-interactive or it hangs.** The first connection to a new host hits
`StrictHostKeyChecking=ask`, which writes a prompt to a stdin that `std::process::Command` never
attaches to a terminal, and the child blocks forever. A passphrased key with no agent does the
same. Every invocation therefore carries:

```
-e 'ssh -o BatchMode=yes -o ConnectTimeout=10'  --contimeout=10  --timeout=60
```

plus a wall-clock kill on the child. A pairing problem must surface as a typed error, never as a
button that spins forever.

`<hostname>.local` resolution is free over Bonjour and the *name* survives DHCP lease changes,
but the address does not: `dns-sd -G v4` on this machine returns six A records including
loopback and four VPN/tunnel addresses. ssh tries them in order, which is the second reason
`ConnectTimeout` is mandatory rather than nice to have.

Note that enabling Remote Login registers `_ssh._tcp` over Bonjour. The *app* announces nothing;
the prerequisite does.

### Layer 2 - Staging mirror

```
rsync -a --delete --exclude '.*' \
      --contimeout=10 --timeout=60 \
      -e 'ssh -o BatchMode=yes -o ConnectTimeout=10' \
      <peer_host>:<peer_vault>/<folder>/ <cache>/sync-staging/<peer_id>/
```

**Staging lives in the OS application cache directory, not inside the vault.** It is disposable,
it is not the user's data, and putting it under `<vault>/.kokobrain/` would double the vault's
size inside whatever the user already backs the vault up with (git, iCloud, Dropbox) and would
aim a high-rate write workload at the directory the vault watcher works hardest to ignore. The
merge reads and writes rather than renaming, so there is no same-filesystem atomicity argument
for co-locating it.

`--delete` applies only to this mirror, whose path the app computes from the peer id and the user
never types. Task 6 asserts that before spawning anything carrying the flag.

`--exclude '.*'` was verified empirically on the rsync actually installed here, in both local and
remote-shell mode: it matches the basename at any depth, so `.kokobrain` nested anywhere is
excluded. Two near-misses to avoid: `--exclude '.*/'` still copies dotfiles, and
`--exclude '.kokobrain'` alone still copies `.git`, `.obsidian` and `.DS_Store`. The pattern is
applied by the *sender*, so the peer's rsync governs it, not ours.

The exclusion is a bandwidth and disk decision, not a corruption barrier. `<vault>/.kokobrain/`
holds a live WAL SQLite database (`db/mod.rs:37`, two connections, plus `-wal`/`-shm` sidecars)
and hundreds of MB of re-downloadable ONNX weights (`semantic/model.rs:65`). Per
sqlite.org/howtocorrupt.html §1.2, copying an open database yields a corrupt **copy**; the
original is unharmed, and `resolve_dest` would refuse to write a dot-path into the vault anyway.

**The barrier holds only on exit 0.** `--delete` defaults to `--delete-before`, so rsync empties
the stale mirror before it transfers. A run that dies mid-transfer leaves staging nearly empty,
and merging that would read as a mass peer-side deletion. A non-zero exit aborts before Layer 3
runs. Do not build an exit-code table: the man page documents 0/1/2 and the binary was observed
returning 23 for a missing source. Treat any non-zero as failure and surface stderr verbatim.

Ceiling worth knowing: `-a` on the rsync installed here expands to `-Dgloprt`, which includes
owner and group (meaningless across machines, warning-prone as non-root) and does **not** include
`-E`, so extended attributes, resource forks and Finder tags on attachments are dropped.
`ponytail: -a without --numeric-ids or -E, revisit if attachment xattrs or Finder tags turn out
to matter.`

### Layer 3 - Merge

Walk the staging tree. For each file, decide, then write. This is the only code in the feature
that can modify the vault.

**State:** one file, keyed by peer id, shaped
`{ "<peer_id>": { "<rel_path>": "<sha256 of the last content both sides agreed on>" } }`.
Keys are normalized (NFC, case-folded) before lookup, because the key space is case-sensitive
strings and the filesystem underneath is not.

**Decision table, evaluated per file at write time:**

| # | Condition | Action |
|---|---|---|
| 1a | `fs::read(dest)` is `NotFound` **and** no `agreed` entry | Write it. `agreed = remote` |
| 1b | `NotFound` **and** `agreed == remote` | **Skip.** We synced this before and the user deleted it since. Leave `agreed` unchanged. |
| 1c | `NotFound` **and** `agreed` exists but `!= remote` | Write it. Deleted locally, edited remotely. `agreed = remote` |
| 2 | `local == remote` | No write. `agreed = remote` |
| 3 | `local == agreed` (only the remote moved) | Snapshot the local content, then write. `agreed = remote` |
| 4 | Anything else (both moved, or no baseline) | **Local wins.** Write the remote content to `<stem> (conflict <peer> <remote_hash[..8]>).<ext>`. Leave `agreed` unchanged. |

Four things this table encodes, each of which is a hole if you drop it:

- **Row 1 must consult `agreed`, or sync resurrects deletions forever.** A single `NotFound`
  row rewrites every file the user ever deleted locally, on every press, with no way to stop it
  short of deleting the file on the peer too. That directly contradicts the deletions decision.
- **Row 3 must snapshot before overwriting.** It is an unconditional overwrite and it writes no
  conflict copy, so a file truncated on the peer while rsync read it replaces a good local note
  with a fragment. File history does **not** cover this: snapshots are produced only by the
  in-app after-save observer (`file-history.service.ts:190`), which a Rust-side write bypasses
  entirely. Either call the snapshot path before every row-3 write, or the feature has no
  recovery story and the plan must stop claiming one.
- **The local hash is read from disk at write time, not collected up front.** Principle 2. A
  case-folded name is found rather than overwritten, and a local save landing during the run is
  seen rather than clobbered. There is no local snapshot structure to build or invalidate.
- **The conflict copy's filename carries the remote hash.** Writing the same remote version
  twice is a no-op, so idempotence needs no "already seen this version" state field. It is
  idempotence per version, not in general: each distinct peer-side edit of a conflicted file
  produces one more copy, and sweeping them is manual.

**The most dangerous line in the feature** is the `NotFound` match. It must match
`ErrorKind::NotFound` and nothing else. An `EACCES` or `EIO` treated as "no local file" reads as
permission to overwrite. Dedicated test.

### Path safety

Validation runs on **both** ends of the pipe.

`resolve_dest(vault, rel) -> Result<PathBuf>` guards every write, at one call site because there
is one writer:

1. Reject absolute paths, any `..` component, any dot-prefixed component, and `:`.
2. `create_dir_all` the parent, then `canonicalize` **the parent** and assert it `starts_with`
   the canonicalized vault root. Canonicalizing a path whose leaf does not exist yet cannot
   detect a symlinked intermediate directory, which is the case that lets a write escape.

A second validator guards `peer_vault_path` and `folder` **before they enter argv**. `rsync`
hands the remote path to the peer's login shell, and `std::process::Command` prevents local
shell injection while doing nothing about the remote side. The installed rsync's man page is
explicit that it makes no attempt to deal with escape sequences. Reject shell metacharacters,
newlines, `..`, and a leading `-` (which would be read as a flag). A `folder` value of
`x; rm -rf ~` runs on the peer otherwise.

## Out of scope

| Not built | Why |
|---|---|
| Rename detection | A peer-side rename arrives as a create, and the old local file is never visited because the merge only walks staging. Both files remain; the user reconciles. Detecting it means diffing against the previous run's file list, which is a second state machine. |
| Per-folder expose/subscribe negotiation | One person, two personal machines, one vault. A single folder path per side covers it. |
| Deletion propagation | Additive sync cannot destroy a file it was never allowed to remove. |
| Background or scheduled sync | If a manual button turns out not to get pressed, that is a verdict on the feature, not a reason to add a scheduler. |
| More than one peer | Two machines. |
| Extended attributes and Finder tags | `-a` does not include `-E`. See the Layer 2 ceiling. |
| Content-hash transfer decisions | rsync decides what to move by size and mtime; the merge still decides by SHA-256. Ceiling: badly skewed clocks can skip a changed file of identical size. `ponytail: mtime-based transfer skip, add rsync -c if clock skew ever produces a missed update.` |
| A status pane, progress bar, or per-file log | A summary line after the run. |

## Settings surface

- **Peer host** - e.g. `macbook.local`
- **Peer vault path** - absolute path on the peer
- **Folder to sync** - vault-relative, empty for the whole vault

Plus a **Pull from peer** button and the last result: `downloaded / conflicts / skipped /
errors`. The peer id is generated on first use and never shown.

The button is labelled "Pull from peer", not "Sync now". The design is one-directional, so the
button lives on the machine that lacks the data. A full exchange is one press on each machine and
the label should say so rather than imply otherwise.

## Testing rules

1. **Every guard that prevents data loss names the test that fails when the guard is deleted.**
   Not "there is a test nearby". Delete the guard, the named test goes red. The guards: the
   `NotFound` discrimination, the `agreed` consultation in rows 1a/1b/1c, the pre-write snapshot
   in row 3, the parent-canonicalize containment check, each local and remote path rejection
   rule, the staging-path assertion before `--delete`, the exit-0 gate before Layer 3, and the
   `local == agreed` comparison.
2. **The merge is testable without rsync.** Layer 3 takes a staging directory as input; merge
   tests build it by hand with `tempfile`. Only Task 6 needs a subprocess.
3. Per project rule, every computed getter in the store has a test, and every suite covers happy
   path, empty input, and error handling.

## Notes

**Verified on this machine (macOS 26.5.2), and worth re-verifying on the peer:** `/usr/bin/rsync`
is openrsync, protocol 29, rsync-2.6.9 compatible - **not** GNU rsync, which macOS 14 and earlier
shipped. It supports `-a`, `--delete`, `--exclude`, `-e`, `--contimeout` and `--timeout`.
`--exclude '.*'` matches the basename at any depth in local and remote-shell mode. `-a` expands
to `-Dgloprt`. A missing source exits 23, not the documented 1. `/usr/bin/ssh` is OpenSSH_10.2p1.
Remote Login is off by default. `std::process::Command` is unblocked: there is no entitlements
file, no `bundle.macOS` key, no App Sandbox and no hardened runtime, and Tauri capabilities gate
the webview's IPC surface rather than Rust. It currently has exactly one call site in the repo
(`quick_capture/source.rs:244`).

**Target size:** roughly 500-600 Rust LOC and 200 TS LOC, with the test weight concentrated on
`merge.rs`, `decision.rs`, and `paths.rs`.

**Ordering constraint:** Layers 1 and 2 are inert without Layer 3 and safe to land first. The
feature is not enable-able until Task 9 is complete and its guard tests are proven to fail when
their guards are removed.

**If Remote Login on the peer is unacceptable**, Layer 1 does not exist and the app has to carry
its own authenticated encrypted transport. That is a different and considerably larger plan.
Layers 2 and 3 are unchanged by it: the staging barrier and the merge table do not care how the
bytes arrived.
