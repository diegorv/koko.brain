## Findings

1. **Low**, `src/lib/features/type-definitions/type-definitions.service.ts:112`. The `invoke('create_folder', ...)` rejection reaches the caller raw. Rust `create_folder` returns `Result<(), String>` (`src-tauri/src/commands/vault.rs:863-867`), so the rejection is a bare string with no `.message`, and nothing logs it first. That contradicts the docblock at `:101-107`, which lists only three outcomes. It also slips past Task 27's mapping, which turns only `Error('create-failed')` into `EventCalendarError('create-failed')`, so a mkdir failure or an `ensure_safe_write_path` refusal would skip the calendar's error toast. Fix: wrap the call in try/catch, `error('TYPE-DEF', 'createTypedNote: create_folder failed:', err)`, and throw `new Error('create-failed')`. Then add a test where `invoke` rejects on `create_folder`: it throws `create-failed` and `createFile` is never called. The ticket's error list does not include this case, so it does not block.
2. **Low**, `src/lib/features/type-definitions/type-definitions.service.ts:118-120`. `buildContent` gets the name from the dedupe in `resolveTypedNoteTarget`, but `createFile` dedupes again against a fresh `readDir` (`fs.service.ts:119-121`). If a file with that name appears between the two reads (watcher, sync, or a second rapid create), the note lands as `Standup 2.md` while its content was built for `Standup 1`. Task 27's `event_title` would then be wrong. The window is small and the discovery notes the risk. A cheap guard is to throw `create-failed` when `path` does not end in `/${target.fileName}`. Otherwise, add a note to the docblock. Not blocking.
3. **Nit**, `src/tests/lib/features/type-definitions/type-definitions.service.test.ts:328-444`. No test pins the order the AC specifies (`create_folder`, then the template read, then `createFile`), and the throwing-`buildContent` case does not show that `create_folder` already ran. Optional: compare `vi.mocked(invoke).mock.invocationCallOrder[0]` against `vi.mocked(createFile).mock.invocationCallOrder[0]` in the first case.
4. **Nit**, commit 0f584fd6, Files section. `type-definitions.service.ts:30-122` should be `:30-123`, because `createTypedNote` closes at `:123`. Fix it only if the commit is rewritten anyway. Do not amend just for this.

## Resolution

1. Fixed. `createTypedNote` wraps `create_folder` in try/catch, logs with `error('TYPE-DEF', ...)` and throws `Error('create-failed')`; the docblock lists the case. New test: `create_folder` rejects with a bare string, the call throws `create-failed`, no template read, no `createFile`.
2. Documented, not guarded. By the time `createFile` returns a different name the note already exists on disk, so throwing `create-failed` would report a failure for a note that was created (an orphan the caller never learns about). The docblock now names the window and accepts it, matching the existing `createView` precedent.
3. Fixed. The first case asserts `create_folder` runs before `createFile`, and a new case pins `create_folder` < template read < `createFile` via `invocationCallOrder`.
4. Rejected. 0f584fd6 is not rewritten (no amend), as the finding itself allows.
