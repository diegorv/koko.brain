1. **major**, `src/lib/core/markdown-editor/extensions/live-preview/styles.ts:77-81`: `backgroundColor: 'transparent !important'` on every `.cm-activeLine` also clears the background that live preview's own line decorations give that same element. Failure scenario: in live preview, put the cursor on any line of a callout or a blockquote. That line loses the tint, so an untinted stripe cuts through the box while the left border still runs past it. On main, the same line showed the active-line fill instead, because a theme beats a base theme at equal specificity (`@codemirror/view` `index.cjs:8849` `Prec.lowest` base theme, mount order at `:8388`). The tint was already lost on main, but now the line is a bare gap. The discovery's risk note ("no live-preview rule wants an active-line fill") misses this. The owner uses callouts, so this shows up in normal use. Fix: in `livePreviewActiveLineTheme`, set the tint again for those lines with higher specificity and `!important`. For example, `'.cm-activeLine.cm-lp-blockquote': { backgroundColor: 'var(--lp-blockquote-bg) !important' }`, the same for `-2` and `-3`, and `'.cm-activeLine.cm-lp-callout': { backgroundColor: 'color-mix(in srgb, var(--callout-note) 7%, transparent) !important' }`. Use the `backgroundColor` longhand: my probe showed that jsdom does not compute the `background: var(...)` shorthand (non-active blockquote lines read `rgba(0, 0, 0, 0)`), so a test can only assert on the longhand. Excluding those lines with `:not(...)` alone is not enough, because the `editor-theme.ts` fill would then win over the base-theme tint again and bring the slab back. Add a failing test first: in live preview, with the cursor inside a blockquote and inside a callout, the active line's computed `backgroundColor` is the tint.
