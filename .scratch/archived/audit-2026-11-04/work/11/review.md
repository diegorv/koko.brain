## Findings

1. minor - src-tauri/src/db/fts_repo.rs:188 (and the chunk/mtime UPDATEs in src-tauri/src/db/semantic_repo.rs:276). A row that already sits at a destination key makes the UPDATE hit `UNIQUE(path)` / the chunk or `semantic_meta` PK, and the one transaction rolls back every child. For a folder that means one colliding child puts the whole folder back on the old path, and the `forgetNote` sweep then drops all of them, which is the bug this Issue fixes. Today the window is small: the new path can only be written between `diskOp` and the re-key, by an autosave whose tab has already moved to the new path (`updateTabAfterRenameOrMove`), by a watcher upsert, or by a stale row. For a single note `updateLinksAfterRename` widens the window, but a collision there touches only that note, and the row the colliding writer left is correct. Fix (follow-up, not blocking): skip each row whose destination key already exists, or drop the row being moved, because the destination row is newer. Then one collision costs only that note, not the folder.
2. nit - src-tauri/src/commands/search_index.rs:279. No test checks that `invalidate_search_cache()` runs after chunks move. If it were dropped, semantic results would keep returning the old `source_path` until the next cache reload. The build report says this is left untested. Fix: a Rust test that fills `SEARCH_CACHE` (or reads it through a test-visible getter), runs the re-key and asserts the cache is empty.

## Resolution

1. Fixed. The row already at the destination wins, since it is newer: `fts_repo::rename_entries` drops the moving row (from `notes_fts` and `notes_content`) when its new path is taken, and `semantic_repo::rename_paths` deletes the moving chunks and `mtime:` keys whose destination already exists before the UPDATEs. `rename_paths` now returns moved + dropped chunk rows, so a drop-only rename still invalidates the cache. `rename_in_search_index_inner` returns early when `from == to`, because the shadow check would otherwise treat every row as colliding with itself. Tests: `a_row_already_at_the_destination_wins_and_the_other_children_still_move` (red before the fix with the UNIQUE error) and `rename_onto_itself_keeps_every_row` in src-tauri/tests/search_rekey_test.rs. docs/SEARCH.md got a sentence on this.
2. Fixed. `search_rename_that_moves_chunks_clears_the_search_cache` in the `commands::semantic` unit tests (the only module that can see the private `SEARCH_CACHE`) fills the cache, runs the re-key over a seeded chunk and asserts the cache is empty.
