## Findings

1. **major**, src/lib/core/filesystem/link-updater.logic.ts:104 (comment at :78-80). A note at the vault root renamed into a stem that a nested note already owns still ends up pointing at the other note. Probe: `buildRenameResolution('/v/Old.md', '/v/Other.md', ['/v/B/Other.md', '/v/Old.md'], '/v')` plus `replaceWikilinks('[[Old]]', ...)` writes `[[Other.md]]`, and `resolveWikilinkCached('Other.md', after, '/v')` returns `/v/B/Other.md`. The path form of a root note has no `/`, so `findExactFile` (wikilink-resolution.logic.ts:31-38) and Rust `find_exact_file` (index.rs:118-119) both take the first `by_file_name` candidate. After `rename_note` the renamed note is pushed last, so B/Other.md wins. The fallback is never re-verified, and the doc comment's claim that the path form is "the one form both resolvers map exactly" is false for root notes. This is not a regression (main writes `[[Other]]`, which is equally wrong), and no form reaches the root note without a resolver change, which D4 (a) ruled out. Fix: correct the comment to name the root-level limit, add a logic test that pins today's output for this case, and open a follow-up `.scratch` Issue asking the owner for a decision (for example, a root-anchored form such as `[[/Other.md]]` in both resolvers).
2. **minor**, src/lib/core/filesystem/link-updater.service.ts:37. The "before" resolution is judged against `fsStore.fileTree` order, which follows the user's folder/content order (`fsStore.folderOrder` / `contentOrder`). Rust's `by_path` winner for a duplicated stem follows scan order, and after a removal it follows HashMap iteration (index.rs:1172-1182). With two notes that share the OLD stem, a bare `[[Old]]` that Rust resolves to the renamed note can be judged as B/Old and skipped. After the rename it then silently resolves to the namesake, where main would have rewritten it. This is reachable only with a duplicated old stem, which discovery.md already notes as a risk, and the Issue allowed the tree as the source. Fix: state the order dependence in the service doc comment (two lines). Optionally, when a source returned by `get_backlinks_v2(oldPath)` ends up with no rewritten link at all, log it through `debug('FS', ...)` so the case can be diagnosed.
