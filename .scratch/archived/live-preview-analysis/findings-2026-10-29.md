## Lead suspect for the bullet <-> H1 glitch (unverified)

`src/lib/core/markdown-editor/extensions/live-preview/styles.ts:47-56`:

```ts
'.cm-formatting-block': { fontSize: '0.01em', opacity: '0', transition: 'font-size 0.2s ease, opacity 0.2s ease' },
'.cm-formatting-block-visible': { fontSize: '1em', opacity: '0.6' },
```

Used by `inline/handlers/heading-handler.ts` for the `# ` HeaderMark (and by list marks).
Arrowing from a bullet line to an H1 flips two lines at once: the bullet marker shrinks and the
`# ` grows over 200 ms. Glyph advance width animates, so the heading text slides sideways while
CodeMirror measures coordinates and the vertical-motion goal column. Inside a large heading the
em size compounds with the heading font size.

Checked by hand: the CSS above, `heading-handler.ts` (line deco `cm-lp-h{N}` is applied
regardless of cursor, so line height is stable; only width changes). No `atomicRanges`,
`goalColumn` or `moveVertically` anywhere in live-preview or setup.

Proposed first check: remove `font-size` from the `transition` (keep opacity if desired) and
reproduce the bullet/H1 arrow movement. If the glitch persists, next candidates below.

## Origin of our design

Our live preview mirrors `blueberrycongee/codemirror-live-markdown` (same names:
`shouldShowSource`, `checkUpdateAction`, `mouseSelecting`, `cm-formatting-block`/`-visible`,
same `0.01em` + `font-size` transition in `src/theme/default.ts:72-84`). That project has no
arrow-key tests or fixes. We added the `lastCursorLine` gate, which none of the six reference
projects have (they rebuild on every `selectionSet`); it is the only cross-update state and
should be tested for staleness on bullet <-> heading moves.

## What the reference projects do

- **SilverBullet** (MIT, mature): reveal per node by selection overlap (`util.ts:219`
  `isCursorInRange`); hides with `Decoration.replace({})`, no transition. Heading markers on
  the cursor line hang into the margin via negative `text-indent` (`editor.scss:250-290`) so
  text does not move; CHANGELOG.md:134 records the "headings jump sideways" fix.
  `withCollapsedBlockSnap` (`client/editor_commands.ts:60-160`) saves the goal column before
  ArrowUp/Down and replays `moveVertically` if the motion lands wrong.
- **atomic-editor** (MIT): per-line reveal, `Decoration.replace`, heading size on a line class
  independent of cursor; bullets always replaced by widget. No arrow handling.
- **Zettlr** (GPL-3.0, ideas only): per-node reveal (`util/range-in-selection.ts`),
  `Decoration.replace`, heading font on the line class.
- **ink-mde** (MIT): never hides `#`; bullets replaced by widget AND added to
  `EditorView.atomicRanges` (only project of the six that does).
- **HyperMD** (CM5, archived): `font-size: 0` without transition, but a 100 ms debounce on
  reveal causes its own stale window. Do not copy.
- **Tolaria**: not comparable; BlockNote/TipTap WYSIWYG with a separate CodeMirror raw mode
  (no syntax hiding). One lesson: ADR-0037 replaced regex heading decoration with the Lezer
  parser after a heading/frontmatter overlap bug.

Consensus: do not animate width of hidden syntax; keep line height independent of the cursor;
optionally make hidden markers atomic; optionally snap vertical motion to the saved goal column.

## Candidate fixes, in order

1. Drop `font-size` from `.cm-formatting-block` transition.
2. Test `checkUpdateAction` + `lastCursorLine` for stale reveal across bullet <-> heading moves.
3. Hang the heading marker into the margin (SilverBullet) so reveal does not shift text.
4. `EditorView.atomicRanges` for hidden markers / goal-column snap for ArrowUp/Down.

## Prior decisions in this repo (must be revisited, not ignored)

- `docs/adr/0008-codemirror-live-preview-architecture.md:23,53,68`: `Decoration.replace({})` for
  inline formatting was tried early and rejected because it pops in/out with no animation;
  "Use `Decoration.replace` everywhere" is listed as a rejected alternative. Switching back needs
  an ADR amendment stating the new evidence (animated width breaks arrow-key navigation; all six
  reference projects swap instantly).
- `c4298609` (2026-04-07): moved HR, UL marker and hard break from replace widgets to
  `Decoration.mark` + `font-size:0` + `::before/::after`, for scroll reflow. Profiling showed JS
  at ~1 ms per plugin; the lag was in browser rendering.
- `a404aebb` (2026-04-08): that migration duplicated bullets (3-5 per item) because overlapping
  `expandedVisibleRanges` produce nested mark spans; fixed with a visited-node Set.
- `b4aa9028` (2026-04-29): `font-size:0` mark on a BulletList `ListMark` froze the editor (a
  CodeMirror measure/layout loop); bullets went back to `Decoration.replace({ widget })`.
- `ffb60d55`: deleted dead live-preview decorations and CSS.

Pattern: every move from replace to mark+font-size has produced a bug in this codebase.

## Decision (2026-10-29, user)

The user accepts challenging ADR 0008: even with the mark + animated CSS rule, live preview still
has visual and UX bugs. The plan will amend ADR 0008 (new evidence: animated width breaks
arrow-key navigation, three bugs of the same family, all six reference projects swap instantly)
and move hidden syntax toward instant swaps.

Still open: reveal granularity (whole cursor line, as today, vs only the node under the cursor,
as SilverBullet/Zettlr), and whether to keep an opacity-only fade.

Animation: resolved. The user wants it removed 100%; instant swaps only, no fade.

Reveal granularity: resolved. The user tried both and chose the option with the fewest failure
points and side effects. That is option A applied uniformly: reveal the whole line(s) touched by
the selection, one shared predicate for every handler and block, rebuild on every selectionSet
with no lastCursorLine gate (no cross-update state). Per-node reveal (B) is out: it adds boundary
and nesting edge cases (cursor adjacent to `**`, link inside bold) that the user does not want.

## Issue 06 measurement: rebuild cost per selection change (2026-10-29)

Question: what does a full live-preview rebuild cost, i.e. what every intra-line cursor move
would pay once the `lastCursorLine` gate is gone (line-crossing moves and every typed character
already pay it today).

Method: `work/06/lp-profile-measure.ts.txt`. Full `livePreviewExtensions()` stack mounted in a
jsdom `EditorView` (vitest, Node 26.12.1, macOS 26.6.2, Apple Silicon), main at `4f358626`.
`profileStart`/`profileEnd` replaced by a recorder with no 0.5 ms threshold, so every label is
the same LP-PROFILE bracket the app logs. 200 line-crossing cursor moves spread over the note.
Synthetic note: repeated sections with headings, bullets, tasks, inline marks, links, wikilinks,
a table, a fenced code block, a callout, inline math, a footnote ref. Caveats: JS cost only
(no WebKit layout); jsdom reports a 642-char viewport, close to the app's, but the inline
pipeline also scans `expandedVisibleRanges` (+2000 chars), measured separately below.

Mean ms per rebuild (p95 in parentheses):

| Note | 11 block decorators (sum) | inline-formatting | 4 inline plugins (sum) | JS total | `dispatch()` total |
|------|------|------|------|------|------|
| 1008 lines / 16 KB | 1.75 | 0.76 (1.65) | 0.39 | ~2.9 | 5.8 (7.7) |
| 2016 lines / 33 KB | 3.67 | 0.87 (1.69) | 0.45 | ~5.0 | 8.1 (11.5) |
| 6000 lines / 100 KB | 10.84 | 0.94 (1.55) | 0.50 | ~12.3 | 15.4 (18.5) |

Largest block decorators at 6000 lines: code-block 2.07 (2.90), block-comment 1.51, table 1.21,
callout 1.05; the other seven 0.57-0.83 each. The block decorators are full-document scans, so
they grow linearly with note size; the inline pipeline is viewport-bounded and stays ~0.6-0.9 ms
(0.73 ms mean when run directly over a 60-line viewport + 2000 chars each side).

Verdict against the Issue's stop rule ("order of a few ms"): small for notes up to ~2000 lines,
not small on a large note (~12 ms JS, ~15 ms per dispatch at 6000 lines, most of a 16.7 ms
frame). Issue 06 stopped before removing the gate; decision handed to the user.
