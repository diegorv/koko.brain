## Findings

1. **blocker** `src/lib/core/settings/theme-package.logic.ts:151` (rendered at `src/lib/core/settings/sections/AppearanceSection.svelte:247`). `parseThemeCatalog` does not reject duplicate ids. Two entries with the same `id` (two packages, or a package and a too-new entry) both reach the keyed `{#each}`, which throws `each_key_duplicate` in dev and in production. The catalog then never renders, and the error escapes the section instead of becoming the error state. A copied theme file with an unchanged id in the generated index is enough to break Settings > Appearance for every user, against "an invalid entry is skipped ... the rest of the catalog still shows". Fix: in `parseThemeCatalog`, keep the first entry for each id and push a skip reason such as `<id>: duplicate id` for later ones. Add a `theme-package.logic.test.ts` case and a catalog-service or component case where a duplicate-id entry is skipped and the others still render.
2. **minor** `src/lib/core/settings/theme-catalog.service.ts:18`. `tauriFetch` runs with no timeout (the plugin's `connectTimeout` is unset). On a stalled connection the catalog stays on "Loading the theme catalog..." forever, with no error state, toast or Retry. Fix: pass a `connectTimeout`, or use an `AbortSignal` with a timeout, and test that a timeout reaches the error state.
3. **minor** `src/lib/core/settings/theme-catalog.service.ts:22` and `src/lib/core/settings/sections/AppearanceSection.svelte:45`. Skipped entries and load failures are logged with `error()`, which also reports to Sentry. Discovery (`work/03/discovery.md`, "Defaults taken") chose `debug()` so third-party data stays out of Sentry. As built, every offline opening of Appearance and every bad entry on every opening sends a Sentry event. Fix: log skipped entries with `debug()`, or keep one `error()` per load rather than one per entry. Also decide whether an expected network failure belongs in Sentry; the toast already tells the user.
4. **minor** `src/lib/core/settings/theme-package.logic.ts:185-189`. Install also writes the ~150 expanded tokens into `themes`, so `settings.json` carries each installed theme twice, and the criterion says "source, not expanded colors". Load ignores the copy, so behavior is correct, and ADR-0035 Consequences records the choice. Still, the copy contradicts the ADR's own Context, which names settings-file growth as a motivation. Optional: leave installed themes out of `themes` when saving, or accept the trade-off and keep it documented.
5. **nit** `src/lib/core/settings/sections/AppearanceSection.svelte:33`. `catalogEntries` has no JSDoc, although `catalogStatus` and `catalogPreviews` next to it do (CLAUDE.md: JSDoc on state variables).
6. **nit** `docs/adr/0035-remote-theme-catalog.md:16`. The Decision says "Besides the built-ins" without naming the two that stay (`KokoBrain Default`, `Lavender Haze`). The criterion asks for "themes besides the two built-ins". Name them, so the ADR still reads correctly after Issue 05.

## Resolution

1. **Fixed** in `97d57dbf` (fix(settings): skip catalog entries that repeat an earlier id). `parseThemeCatalog` keeps the first entry per id (package or too-new) and skips later ones with `<id>: duplicate id`. Tests: `theme-package.logic.test.ts` "keeps the first entry of an id and skips later ones, too-new entries included"; `AppearanceSection.test.ts` "skips an entry that repeats an id and still renders the rest". Both failed before the fix (the component one with `each_key_duplicate`).
2. **Fixed** in `f2208896` (fix(settings): time out a stalled theme catalog request). `fetchThemeCatalog` passes an `AbortSignal` to the plugin and races the request, body read included, against `THEME_CATALOG_TIMEOUT_MS` (15 s). On expiry it aborts the signal, so the plugin cancels on the Rust side, and rejects with "Theme catalog request timed out", which the existing catch in `AppearanceSection.svelte` turns into the error state with Retry. `connectTimeout` alone was not used because it covers only the connect phase, not a stalled response or body. Tests: `theme-catalog.service.test.ts` "rejects and aborts the request when it stalls past the timeout" and "times out a response body that stalls after the headers".
3. **Fixed** in `cf721b92` (fix(settings): keep theme catalog failures out of Sentry). Skipped entries and catalog load failures both go through `debug()`. Decision: an expected network failure does not belong in Sentry, because the toast and the error state already tell the user, and a bad entry is third-party data. Tests: the service test asserts the skipped reason reaches `debug` with `captureSentryException` and `console.error` not called; the component error-state test asserts `console.error` (always called by `error()`) is not called.
4. **Rejected (kept and documented)**, ADR wording in `77e96348`. The expanded copy in `themes` is load-bearing: `loadAppearance` (`theme-package.logic.ts:231-244`, JSDoc at 224-230) keeps an installed theme's list position through `base.themes.map(...)`, and when a saved package no longer validates (for example, after a future validator tightening) it drops the package but keeps the saved colors as a user theme, so the user's theme does not disappear. Leaving installed themes out of `themes` on save would lose both, and would make installed themes the only kind not in the list the store holds (built-ins are saved expanded too and ignored on load). The growth this saves is one copy per theme the user installed, against the 24 expanded built-ins saved today, which Issue 05 removes. ADR-0035 Consequences now gives this reason.
5. **Fixed** in `77e96348`: JSDoc on `catalogEntries`.
6. **Fixed** in `77e96348`: the Decision names `KokoBrain Default` and `Lavender Haze`.
