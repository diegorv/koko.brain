## Findings

1. **blocker**, `src/lib/core/settings/theme.logic.ts:303` (`DEFAULT_APPEARANCE`) and `src/lib/core/settings/settings.service.ts:35-52` (fresh and fallback branches of `loadSettings`). The migration is not gated for a vault created after the upgrade. `DEFAULT_APPEARANCE` has no `exBuiltinsMigrated`, and the no-file, empty-file and catch branches of `loadSettings` save `DEFAULT_SETTINGS` without running `loadAppearance`. Now that the catalog offers the 22 for install, this path is easy to reach. Reproduction (a probe on this branch; I deleted it afterwards):
   1. Start from `structuredClone(DEFAULT_SETTINGS).appearance`.
   2. `installThemePackage` Sakura 1.0.3 and Sepia 1.0.0, then set `activeTheme: 'Sakura'`.
   3. Round-trip it through JSON and call `loadAppearance`.

   Result: `installed` is `[['sakura','1.0.3'], ['sepia','1.0.0'], ['sakura','1.0.0']]`. The migration appended a second package with id `sakura`, rebuilt from the saved colors. In the `built` name map the later 1.0.0 copy wins, so the duplicate id is saved for good, and update and uninstall then act on two entries. Any installed ex-built-in that is not active is also dropped from `themes` and then appended back at the end, so it loses its place in the list. Fix: put `builtinsFromCode: true, exBuiltinsMigrated: true` in `DEFAULT_APPEARANCE` (or route the fresh and fallback branches through `loadAppearance({})`). Then add a `settings.service.test.ts` case: load with no settings file, install and activate an ex-built-in, `saveAndReload`, and expect exactly one package with that id, unchanged.
2. **minor**, `src/lib/core/settings/theme-package.logic.ts:339-355` (`migrateExBuiltins`). A save from before `builtinsFromCode` loses user edits to `Sakura` and `Twilight Violet`; the presets were exempt from edit detection anyway. If the edited theme is not active, it is dropped. If it is active, it becomes an installed `sakura` 1.0.0 that cannot be edited in place, and "Update to 1.0.1" would overwrite the edit. Before this branch, `normalizeAppearance` turned it into a "Sakura (edited)" user theme. `discovery.md` accepts this because "the flag shipped long before", but `builtinsFromCode` landed in f9aca6d9 on 2026-10-30, four days before this branch. The plan says to drop the others, so this needs an owner decision. Either accept it and say so in the ADR consequence, or, when `!raw.builtinsFromCode`, keep a saved Sakura or Twilight Violet that differs from the fixture-era colors as an "(edited)" user theme.
3. **nit**, `src/tests/lib/core/settings/settings.service.test.ts:919`. "installs an active ex-built-in ... once" cannot show that the flag survives a save. If the flag were not saved, the reload would re-run the migration on the same input and still give an equal result. Assert `exBuiltinsMigrated: true` in the JSON passed to `writeTextFile`, or reload after installing a different ex-built-in, as in finding 1.
4. **nit**, `help/documentation/26-theming.md:67`. "The other 21 leave your theme list" is only true when one of the 22 was active. When the active theme was KokoBrain Default, Lavender Haze or a user theme, all 22 leave. Suggested wording: "The others leave your theme list."

## Resolution

1. **Fixed** in 2b251869. `DEFAULT_APPEARANCE` (`theme.logic.ts:302-313`) now sets `builtinsFromCode: true` and `exBuiltinsMigrated: true`, so the no-file, empty-file and catch branches of `loadSettings` save a vault that never runs the migration. New `settings.service.test.ts` cases (one per branch: no file, empty file, unreadable file) install Sakura 1.0.3, activate it, `saveAndReload`, and expect `installed` to be exactly that one package; all three failed first with a second `sakura` package, and pass now. `theme.logic.test.ts` asserts both flags on `DEFAULT_APPEARANCE`.
2. **Accepted and recorded** in 20bf2aa0 (ADR-0035 Consequences). Keeping such an edit as "(edited)" needs Sakura's and Twilight Violet's colors in app code to tell an edit apart, which criterion 4 removes (the fixture lives under `src/tests/`). Treating every pre-flag saved Sakura as edited would instead create a spurious copy in every unedited vault. The window is narrow: on main, `normalizeAppearance` already split an edited Sakura / Twilight Violet into "(edited)" on any load since f9aca6d9 (they were not in `PRESET_THEMES`, `main:theme.logic.ts:530`), so only a vault not opened since 2026-10-30 is affected. The discovery note's "shipped long before" is wrong on the date; the ADR now carries the correct one. Owner can still ask for the other option.
3. **Fixed** in 2b251869: the reload test parses the last `writeTextFile` payload and asserts `appearance.exBuiltinsMigrated === true`; the finding-1 cases also cover "reload after installing a different ex-built-in".
4. **Fixed** in 20bf2aa0: "The others leave your theme list."
