- [met] The host accepts a write when the SHA-256 of the disk text, decoded the way the frontend decodes it (UTF-8 with replacement, BOM stripped), equals the SHA-256 of the base, or equals the SHA-256 of the new content (a retry of a write that already landed). A write to an existing file with no base is refused — `write.rs::write_checked` uses `disk_text` (`from_utf8_lossy` plus a BOM strip) and compares `sha256` against the text and the base. Otherwise it returns a `Conflict: ` error, which `rpc.rs` sends as `-32001`. An existing file with no base is refused. Covered by `remote_write_test.rs` (`a_write_on_the_base_lands`, `a_retry_after_a_landed_write_is_accepted`, `a_write_to_an_existing_file_with_no_base_is_refused`, `the_base_is_compared_with_the_disk_text_as_the_frontend_decodes_it`).

## Findings

1. major (process, blocks the merge rather than the code) — `/Users/diegorv/Dev/pet-projects/koko/brain/.claude/worktrees/ios-poc/src/lib/core/editor/note-write.port.ts`, an untracked file in the main checkout (feature/ios-poc). It is an earlier draft of the branch's port, and its comments differ from the branch's. A merge of this branch into the main checkout fails with "untracked working tree files would be overwritten by merge". Fix: before merging, delete that untracked file from the main checkout. It is not part of the branch.
2. minor — `src/lib/core/editor/editor.service.ts:226-235` (`saveDirtyTabs`) with `:208-214`. After the one conflict toast, every later autosave of that tab is skipped with no message. Nothing persistent marks the tab as conflicted. If the owner misses the transient toast and keeps typing, nothing more is saved and nothing says so: closing Safari loses all of it. The same holds when the tab is undone back to clean and then edited again: no reload clears `conflictedPaths` (the 07 refresh skipped it while it was dirty), so autosave stays silently off. The criterion's wording is met. Fix (follow-up): a persistent conflicted indicator on the tab or in the status bar, or re-show the toast when a skipped autosave finds unsaved typing.
3. minor — `src/lib/core/filesystem/fs.service.ts:246` with `src/lib/features/auto-move/auto-move.service.ts:174-191`. In the browser, auto-move now really creates the destination folder on the Mac (`plugin:fs|mkdir` is a Write), and only then `moveItem` refuses. `refuseInBrowser()` runs outside the `try`, so nothing is logged, and auto-move's catch says "`moveItem` already logged the cause". The result is an empty folder created on the Mac with no trace. Fix: skip auto-move in the browser (`isRemoteBrowser()`), or refuse before the mkdir.
4. nit — `src-tauri/src/remote/dispatch.rs` (`write`, `plugin:fs|write_text_file` arm). The plugin-fs `options` header (`create: false`, `append`, `createNew`) is ignored. `frontmatter-write.service.ts` relies on `create: false` so that a note deleted after its check is not recreated. In the browser, a no-base write to a missing file creates it. This flow is mostly moot in the browser, because a no-base write to an existing note is refused. Fix: refuse `create: false` and `append: true` when the file is missing, or document that the host ignores them.
5. nit — `src-tauri/src/remote/write.rs:116-119`. The accepted write is truncate-then-write on the live file, which is not atomic. The Mac's watcher (500 ms debounce) could read a half-written note, and a crash mid-write truncates it. This matches plugin-fs's own write, so it is not a regression. Fix (follow-up): write a temp file in the same folder, `fsync`, then `rename` over the target, keeping the O_NOFOLLOW check on the target.
