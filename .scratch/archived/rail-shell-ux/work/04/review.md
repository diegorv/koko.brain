## Findings

1. **major**, `src/lib/features/collection/toolbar/filter.logic.ts:282` / `:301-305`: `filterToExpression` assumes every non-string list item is an object, and a `null` item makes it throw. YAML turns an empty list entry into `null`, and `parseCollectionYaml` casts `filters` without validating it (`yaml-parser.ts:95-96`). Here is a probe I ran and then deleted. `filters:\n  and:\n    - "status == 'open'"\n    -\n` parses to `{"and":["status == 'open'",null]}`. `parseFilterToGroups` then throws `TypeError: Cannot read properties of null (reading 'and')`. On main, `itemToRow` turned that item into the raw text `null`, which never crashed and simply matched nothing. In `CollectionView`, `parseFilterToGroups` runs at component init (`seedFromDefinition()`, `CollectionView.svelte:137`) and in an `$effect`. `EditorView.svelte:85` mounts it with no `<svelte:boundary>` anywhere in `src/lib` or `src/routes`. A user who leaves a half-typed `-` entry in collection source mode and toggles back to the visual view now hits an uncaught error instead of an empty table. The rail's `loadView` and `countViewNotes` catch the error, so there it degrades to "load failed". Fix: in `itemToRow`, keep the object path only for a non-null object (`item !== null && typeof item === 'object'`) and fall back to the old JSON-text raw row otherwise. Give `filterToExpression`'s `wrap` the same guard for a `null` nested two levels down. Add a `filter-logic.test.ts` case where `{ and: ["x == 1", null] }` and `{ and: [{ or: [null] }] }` parse without throwing.
2. **nit**, `src/lib/features/collection/toolbar/filter.logic.ts:302`: the expression text and the evaluator handle errors differently. `evaluateFilter` catches a parse or eval error per item, but the joined expression fails as a whole. Probe: `{ or: ['nope(', 'true'] }` shows as `(nope() || (true)`. The object matches every note, but the text, once edited, matches nothing. An unedited row runs on the object, so query results are right. Only the shown text and an edited row differ, and the build report already lists this as a risk. No change needed beyond being aware of it. Optionally, mention it in the `filterToExpression` JSDoc.
3. **nit**, `src/tests/lib/features/collection/CollectionView.test.ts` ('keeps both nested objects...'): the filter edit is followed by a restore, and nothing asserts that the intermediate edit reached `getYaml()`. If the `input` event stopped reaching `FilterRow`, the test would still pass. The criterion's final deep-equality still holds. Optional fix: assert `getYaml()` contains `opened` after the first edit.
