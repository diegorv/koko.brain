## Findings

1. minor — `src/lib/features/collection/toolbar/filter.logic.ts:286` (`itemToRow` → `jsonRow(null)`): a null list item (an empty YAML `-` entry, e.g. `filters: { and: [~] }`) is reported only by the inline block. A probe shows `executeQuery` on the raw definition returns `Invalid filter item: null is not an expression`. Through the toolbar round-trip, which the editor and `queryViewLens` both use, the item becomes the raw text `null`. That text parses, so `queryViewLens(...).filterError` is `undefined` and the list is silently empty: the "looks like no data" symptom this Issue removes. FilterRow does not mark the row either. No criterion names the null item, so this is not a blocker. Fix: make the JSON-text row of a non-object item fail `validateExpression`, or flag a `jsonRow` built from null so FilterRow and the query report it. Alternatively, record that a null item is out of scope.
2. minor — `src/lib/features/collection/toolbar/filter.logic.ts:105-109` (`parseFilterToGroups` JSON fallback): users see a malformed `and` / `or` / `not` through the editor and the rail, and both go through the toolbar. There the message is a lexer error on the JSON text, not `executeQuery`'s `"or" must be a list`. Probe: `queryViewLens({ filters: { or: 'x' } ...})` gives `Invalid filter "{"or":"x"}": Unexpected character: '{' at position 0`. The key is "named" only because it appears inside the quoted JSON, and the `toContain('"or"')` assertions in filter-logic.test.ts and lens.logic.test.ts would pass for any message that quotes the JSON. The criterion holds in its letter. Fix, optional: give a JSON-text row a clearer reason (e.g. detect a leading `{` / `[` in `validateExpression` callers and say "not an expression: a filter object with a malformed key"). Alternatively, accept the wording and note it for Issue 10's rendering.
3. nit — `src/lib/features/collection/collection.types.ts:31`: `CollectionViewDef.type` is still the hand-written union `'table' | 'calendar' | 'linear-calendar'`. The Issue asks for one constant shared with `ViewType`; `ViewType` is derived from `VIEW_TYPES`, but this union duplicates it and can drift. Fix: `type: ViewType`. Either import the type, or move `VIEW_TYPES` next to the types so the import keeps the current direction.
4. nit — `src/lib/features/collection/toolbar/toolbar.types.ts:105` / `formula.logic.ts:88`: `FormulaEntry.error` is still computed by `updateFormulaEntry`, but `FormulaRow` was its only reader and now derives the error itself. The field is now dead data (discovery records it as kept on purpose). Fix: remove it in a follow-up, or leave a note.
5. nit — `src/lib/features/collection/collection.logic.ts:210-233` (`findItemError`): a top-level `filters:` written as a YAML list (`filters: ['a == 1', 'b = 2']`) is treated as an object with none of the keys. The bad `b = 2` is never reported, and no `filterError` comes back (probe). This is outside the criteria, and the behavior predates this branch. Fix, optional: report an array at the top level, or an object with none of `and` / `or` / `not`, as a malformed filter.
