## Findings

1. **blocker** — `src/lib/features/collection/yaml-parser.ts:306-307`. Edit view always writes the dialog label as the edited view's `name` and, when `_rail_view` named it, as `_rail_view`. When that label equals the `name` of an earlier view in the same file, `_rail_view` now resolves (first match) to the earlier view, so the save moves the rail to a different view than the one it just edited. This happens on the normal path: New view writes `_sidebar_label: X` and `views[0].name: X`; the user adds a `Board` tab in the editor and sets `_rail_view: Board`; Edit view prefills the label `X`, so a filter-only save writes `views[1].name: X`, `_rail_view: X`. Probe (temporary test, deleted afterwards) on `_sidebar_label: Projects, _rail_view: Board, views: [Projects, Board]` with `updateViewEditYaml(yaml, { label: 'Projects', viewFilters: "status == 'done'" })`: `railViewIndex` is 1 before the save and 0 after. The new filter sits on `views[1]`, which the rail no longer runs, the rule line changes from `view "Board"` to `view "Projects"`, and the row shows no note because the name now resolves. Fix: have `updateViewEditYaml` refuse (`{ ok: false, error: 'Another view in this file is named "<label>"' }`, which the dialog already shows as its submit error) when the label equals the `name` of another view than the edited one, and add a yaml-parser logic test for that case. If the owner would rather keep the view name when only the label is unchanged, that is a spec change and needs their decision. Either way the save must not silently switch the view the rail runs.
2. **minor** — `src/lib/features/type-definitions/type-sidebar.logic.ts:412-418` (applied through `src/lib/features/rail-shell/lens.logic.ts:463`). The `_rail_view` rule also runs on a type definition's frontmatter, which has no `views`. A `_rail_view` key in a type note therefore gets `"X" names no view; the first view runs`, which says nothing useful about a type. The build report notes this too. Fix: run the `_rail_view` rule only when the record has a `views` array (for example `check: (v, fm) => !Array.isArray(fm.views) || ...`), or record the owner's acceptance in the Issue Notes.
3. **nit** — `src/lib/features/rail-shell/RailNoteList.svelte:130`. `viewRunIndex` is set only when a query returns a result (`if (result)`) and is never reset when the picked path changes. A load that fails for a new path keeps the previous view's index. That index is only read by `persistViewState`, and the toolbar does not write after a failed load, so this is not reachable today. Resetting it to 0 at the start of a load would make the invariant explicit.

## Resolution

1. **blocker, fixed** in `5a4a8d2fa` (fix(collection): Edit view refuses a label another view is named). `updateViewEditYaml` (`src/lib/features/collection/yaml-parser.ts`) returns `{ ok: false, error: 'Another view in this file is named "<label>"' }` when any view other than the edited one carries the label as its `name`, with or without `_rail_view`; the dialog shows it as its submit error. Keeping the edited view's own name still saves. Logic tests in `yaml-parser.test.ts` ("with _rail_view": the reviewer's New view plus second tab case, the no-`_rail_view` case, and the unchanged label still running `views[1]`). Help 25's Edit view bullet names the refusal (docs commit below).
2. **minor, fixed** in `dffe03f76` (fix(type-definitions): report _rail_view only on a record with views). The `_rail_view` rule in `RESERVED_KEY_RULES` (`type-sidebar.logic.ts`) accepts any value when the record has no `views` array, so a type row shows no `_rail_view` note; a `.view` without `views` fails its parse anyway. The former assertion that a record without views gets the note became the opposite test in `type-sidebar.logic.test.ts`. Help 25's `_rail_view` row says type definitions are not marked.
3. **nit, fixed** in `cb6e320cb` (refactor(rail-shell): reset the view-run index when the picked view changes). `RailNoteList.svelte` resets `viewRunIndex` to 0 when a load starts for another path than the one loaded, and sets it to `result?.viewIndex ?? 0`. It is not reset on every load: a reload of the same view (after our own write, or a content change) keeps `viewLoaded` and so the toolbar usable, and an unconditional reset would let a toolbar edit during that reload write to `views[0]`.
