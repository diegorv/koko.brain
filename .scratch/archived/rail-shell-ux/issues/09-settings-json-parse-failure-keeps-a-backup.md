# 09: A broken settings.json is backed up and reported, not silently replaced by defaults

**What to build:** When `.kokobrain/settings.json` exists but does not parse to a JSON object, the app copies it byte for byte to `.kokobrain/settings.broken-<YYYYMMDD-HHmmss>.json` before anything writes `settings.json`, runs on the defaults, and shows a toast that names the backup file and says the settings were reset. When the file exists but cannot be read, the app runs on the defaults in memory, does not write `settings.json` during load, and shows a toast. Help 19 gains a note on editing settings.json safely (quit the app first, because the app rewrites the file from memory on the next settings change and drops unknown keys) and names the backup file.

## Notes

- **Cause (traced):** in `core/settings/settings.service.ts` the `try` opens at `:33` and covers `exists` (`:34`), `readTextFile` (`:44`), `JSON.parse` (`:54`), the merge (`:55-162`) and the write-back `saveSettings` (`:164`); the `catch` (`:167-179`) stores `DEFAULT_SETTINGS` and calls `saveSettings` for every one of those failures, so themes, periodic formats, Todoist, Sentry, Auto Move and the rail layout are lost. `error()` (`utils/debug.ts:27-33`) only logs and reports to Sentry, so the user sees nothing. `JSON.parse('null')` succeeds and then `parsed.periodicNotes` throws inside the merge; `[]` merges silently into defaults.
- **Owner decision (2026-11-04):** only the load-time backup and toast; suspending saves for the session and skipping `cleanup_history` after a failed load stay out (the latter remains `file-io-audit/10`).
- **Main-session decisions (owner accepted 2026-11-04):** a timestamped backup per failure (no rotation; failures are rare and the files are small); no file watcher for external edits (documented instead).
- **Backup mechanism (main-session decision):** `copyFile` from `@tauri-apps/plugin-fs`, which copies bytes. Do not use `readTextFile` + `writeTextFile`: `readTextFile` decodes with `TextDecoder` (`node_modules/@tauri-apps/plugin-fs/dist-js/index.js:489-498`), so a BOM or invalid UTF-8 would not survive, and a second `writeTextFile(` in `settings.service.ts` would also fail the raw-write ratchet (`src/tests/lib/raw-write-ratchet.test.ts:30` allows one). `fs:allow-copy-file` already covers `.kokobrain/**` in both vault roots (`src-tauri/capabilities/default.json:172-187`), so no capability change is needed. `fs.service.ts:1,339,357` uses the same import.
- **Branches (main-session decision):** parse failure = `JSON.parse` throws or the parsed value is not a plain object; read error = `exists` or `readTextFile` throws; a write-back failure after a good parse is neither and keeps the parsed settings (log it with `error()`, as `saveSettings` failures are logged today). Restructure the `try` so only the read and parse sit inside the branch that falls back to defaults.
- **Stamp:** local time, `YYYYMMDD-HHmmss`. Two failed loads in the same second overwrite one backup; accepted, since `loadSettings` runs once per vault open (`app/lifecycle/app-lifecycle.service.ts:198`). The test pins the clock with `vi.useFakeTimers({ toFake: ['Date'] })` + `vi.setSystemTime` so the promise chain is not frozen.
- **Toast:** `toast` from `svelte-sonner`, imported directly as `core/settings/update-check.service.ts:1` does (there is no shared toast helper). `settings.service.test.ts` does not mock `svelte-sonner` today; add the mock the way `update-check.service.test.ts:10` does.
- **Scope of the guarantee:** this Issue protects `settings.json` during load. `startSettingsPersistence` (`app-lifecycle.service.ts:210`, `settings-persistence.svelte.ts:46-66`) takes the in-memory defaults as its baseline, so after a read error or a failed backup the first in-app settings change still rewrites the file from memory. Changing that is not part of this Issue.
- **Overlap:** `.scratch/file-io-audit/issues/10-settings-load-failure-defaults.md` (needs-triage) covers the same catch. This Issue covers its backup, read-error and write-back-failure legs. Not covered here: skipping `cleanup_history` after a failed load (`app-lifecycle.service.ts:273-277` runs it with the default retention of 7), and atomic settings writes.
