# 17: New view asks for a name and creates the view under that name

**What to build:** The `+` next to Views in the Types navigator opens a "New view" dialog instead of writing `Untitled.view` at once. The user types a name and presses Enter or Create. A `.view` file named after the typed name is created at the vault root, with that name as its label (`_sidebar_label`) and as its table view's name, no filters and the default `_sort: title`. The new view becomes the note list's lens and its row is highlighted. Cancel or Escape writes nothing. If creation fails, the dialog stays open, keeps the typed name and shows the reason inline; it cannot be closed while a create is in flight.

Prefactor first, in its own commit: the view-creation service takes the name, builds the YAML from a pure builder using the YAML serializer (today it pastes the title into a template string, which is safe only because the title is always `Untitled N`: a typed `#tag`, `123`, `true` or `- x` would write a broken `.view`), and rejects on failure instead of returning null (today a failed create is silent):

```ts
createView(name: string): Promise<string> // resolves to the new path; rejects with no vault, or when the folder cannot be read or the file cannot be created
```

The builder is `buildNewViewYaml(name: string): string` in `src/lib/features/type-definitions/type-sidebar.logic.ts` (that module already imports `yaml` and holds `getViewLabel` and `updateViewIconYaml`). It serializes `{ _sidebar_label: name, _sort: 'title', views: [{ type: 'table', name }] }` with the `yaml` package's `stringify(value, { lineWidth: 0 })`, the same `lineWidth: 0` that `src/lib/core/frontmatter/properties.logic.ts:623` passes to `doc.toString`; the default line width (80) folds long plain scalars at spaces. The name check is `validateViewName(name: string, existingLabels: string[]): string | null` in `src/lib/features/type-definitions/type-definitions.logic.ts`, next to `validateTypeName`; Issue 19 reuses it with the edited view's own label left out of `existingLabels`.

## Notes

- **Owner decisions (2026-11-04):** filename is the name as typed, deduped the way notes are (`Name 1.view`), no slug; file goes to the vault root, as today; a name an existing view already shows is refused; no `_order` is written, so the new view sorts by name among the default order; no success toast (as New type); failures show inline with the dialog kept open.
- **Reference:** modelled on Tolaria's Create View dialog (name + filters, inline save error, icon and color set later from the row menu). These Notes are the complete decision record; the scout's design files outside the repo are not inputs.
- **Dialog shell:** a new component, mounted next to the New type dialog in the Types navigator; Issue 18 adds the filter section to it and Issue 19 reuses it for Edit view. Do not reuse or change `TypeNameDialog`: its `confirm()` sets `open = false` before awaiting `onConfirm`, so it cannot keep the dialog open on a failure, and it has no close guard. Take from it the validation derived from the value and Enter on the input; take from the event form (`src/lib/features/event-calendar/EventForm.svelte:47-58`) the submit model: a `saving` flag, the rejection caught into an inline `role="alert"` message. Close only after `createView` resolves. While `saving`, every close request (Cancel, Escape, outside click, the content's close button) is ignored.
- **No `<form>` wrapper.** Issue 18 puts the filter panel in this dialog; its dropdown triggers contain a typeless `<button>`, which inside a form submits on a mouse click. Submit via Enter on the name input and an `onclick` on Create.
- **Main-session decision (dedupe):** the content no longer embeds the deduped filename, so `createView` drops its own vault-root `readDir` and the comment that justified it; `createFile` already dedupes with `generateUniqueName` (case-insensitive, so `Foo` next to `foo.view` becomes `Foo 1.view`; not `generateCopyName`, which compares exact case, see `file-io-audit/19`) and rejects when it cannot read the root.
- **E2E mock gap:** the E2E vault-index mock indexes only `.md` files with `---` frontmatter, so in E2E a `.view` row always shows its filename. With the filename equal to the name this still matches; the label itself is proven in unit tests. Extending the mock is out of scope.
- **Known, out of scope:** an unfiltered view lists every note; Issue 01 keeps `.view` files (the new view included) out of that list, and this Issue does not depend on it. A name containing ` #word` or `[[x]]` gives the `.view` a tag or an outgoing link, because Rust extracts both from the raw content; accepted.
- **Not handled (rare race):** delete `Foo.view` in Finder, then create "Foo" in the dialog: the view parse cache can serve the deleted file's filters for one refresh. The root cause, the watcher never evicting a `.view` parse-cache entry on an external delete, is `cross-audit-plan-2026-08-12/issues/62`; in-app deletes and renames already evict through the path-change consumer in `src/lib/app/boot.ts`. Not fixed here.
- **Shared function with Issue 16:** Issue 16 wraps the content inside `createTypedNote`'s body; this Issue only removes the `(as in \`createView\`)` reference from its JSDoc. Touch nothing else in `createTypedNote`, so the two edits merge cleanly whichever lands first.
- **Leftover kept:** `createView` also sets a type-definitions selection of kind `view` that nothing reads; its existing test asserts it. Leave it.
- **Help overlap:** Issue 26 re-reads the same help page after the delivery; this Issue only changes "Creating a View".
- **Size:** M.
- **Type scale (typography-hierarchy, done 2026-11-04):** the chrome uses the text-role tokens in `src/app.css` (`text-label` 11px, `text-meta` 12px, `text-row` 14px, `text-title` 15px semibold, and the `section-label` utility for section headers, sentence case).
