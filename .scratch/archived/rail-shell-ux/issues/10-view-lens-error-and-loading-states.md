# 10: A broken or loading `.view` says so in the note list and the navigator

**What to build:** When the picked view lens cannot be shown, the note list says why instead of "No notes here". Cases: the `.view` does not parse (show the parser message; a missing or empty `views` is a parser message too, `yaml-parser.ts:27-37`), cannot be read (show the read error), its filter does not parse (Issue 06's query error), no longer exists, or the index is still loading (show a Loading state, not an empty list). The error state offers "Open view", which opens the `.view` in the editor so the user can fix it. The view's row in the Types navigator shows an error mark (icon with a tooltip carrying the message) instead of silently dropping its count. While a count is pending, the badge slot keeps its width so rows do not shift. A non-number `_order` (`"1"`) or a non-boolean `_open_in_editor` (`"true"`) is reported in the same tooltip as "ignored key", through a reserved-key table that later Issues extend.

- **Today (traced):** `features/rail-shell/RailNoteList.svelte:127,131-134,160-191,375,446,480-483` hides Sort, Filter and New here and shows "No notes here" in every failure case: `loadView` passes `null` to `resolveViewLens` for a parse failure (165-168), for an index that is not ready (178-185) and for a read failure (186-190), and `resolveViewLens` turns `null` into an empty list (`lens.logic.ts:570-573`). - **Main-session decisions:** keep the Sort and Filter buttons hidden in the error state (the fix path is "Open view"); a missing `.view` shows "This view no longer exists" and the same Open button is hidden.
- **Main-session decision (precedence and signals):** the view lens resolves in this order: Loading while `collectionStore.isIndexReady` is false; missing when `findNodeByPath(fsStore.fileTree, viewPath)` (`core/filesystem/fs.logic.ts:9`) finds nothing; error when the read throws or the parse fails; then the query runs (`ran`). The file tree is loaded before the property index is marked ready (`app/lifecycle/app-lifecycle.service.ts:316` before the property build at 412), so the tree check is reliable once Loading ends. The tree is the missing signal, not the read: `getCachedViewDefinition` serves a cached parse without disk I/O (`view-parse-cache.ts:58-62`), and a delete outside the app does not clear that cache (only the in-app path-change consumer does, `app/boot.ts:40-43`), while the watcher does refresh the tree (`core/filesystem/fs.watcher.ts:200`). The view lens effect must therefore react to tree changes for the picked view. The missing decision lives in `RailNoteList`, not in `resolveViewLens`: `countViewNotes` builds its context with an untracked tree (`TypesNavigator.svelte:82-83`) and re-reads every `.view` from disk, so a missing file there is a read error.
- **Main-session decision (navigator):** counts keep their index gate and 1000 ms debounce (`TypesNavigator.svelte:66-72,86-90`), so the error mark appears with the first count pass. The mark replaces the count for an errored view; a view with only ignored-key notes keeps its count and shows the mark next to it. The tooltip lists the error first, then the ignored-key notes. Reuse the existing `getViewOpensInEditor` rule (only YAML `true` is on, `type-sidebar.logic.ts:327-329`); the ignored-key check only reports, it does not change which values work.
- **Main-session decision (reserved-key table):** Issues 13 (`_sort`), 20 (`_visible`) and 21 (`_rail`, on view and type rows) add rows to this table, and Issue 22 (`_rail_view`) reports through the same notes, so the helper takes a frontmatter record, not a view entry, and adding a key is one table row.
