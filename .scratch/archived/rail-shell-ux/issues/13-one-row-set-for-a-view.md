# 13: A `.view` lists the same rows, in the same order, in the editor and in the rail

**What to build:** One function owns the row set of a `.view` view. It takes the records the view's query matched (filters and the view's own `sort` applied, `limit` not yet applied) and drops what the rail never lists: archived notes, notes under the system folder, and the type definitions and `.view` files that Issues 01 and 12 keep out of view results (reuse their predicate). It then orders them: with the view's own `sort` it keeps the query order; without one it orders by the top-level `_sort`, else the default (modified, newest first), with `_order` pins on top (`resolveViewListSort` and `getNotesForViewPaths`, as the rail does today). Last it applies `limit`. The collection editor (table and calendars, for the active tab of a `.view`), the rail's view lens and the navigator count all use it, so "N results" in the editor for the first view equals the count badge in the navigator. `.collection` files and ```` ```collection ```` fences in notes keep `executeQuery` exactly as today. The Sort popover shows the effective sort (for example "Sorted by `_sort: modified`") instead of "No sorts applied" when no sort of the view's own orders the list, in the rail and in the editor for a `.view`. An unknown `_sort` value is reported through Issue 10's ignored-key table instead of silently meaning title. The rule line under the label says "first view" when the `.view` has more than one view.

## Notes

- **Owner decision (2026-11-04):** the rail's rule wins in both surfaces (no archived, no system folder, `_sort` applied, one function).
- **Today (traced):** the editor runs `executeQuery` directly (`features/collection/CollectionView.svelte:207-221`; "N results" at 467) and keeps archived, system-folder, type-definition and `.view` rows in query order. The rail drops archived and system-folder notes in `resolveViewLens` (`features/rail-shell/lens.logic.ts:570-582`) and, only when the view has no sort of its own, orders by `_sort` with `_order` pins (`type-note-list.logic.ts:94-96`; `features/type-definitions/type-sidebar.logic.ts:98-116,193-213,338-341`); with its own sort the rail keeps the query order and applies no pins. On both surfaces `executeQuery` applies `limit` after the view's own sort but before any exclusion and before `_sort` ordering (`collection.logic.ts:170-188`), so a `limit: 3` view with no sort shows the first three in index order, minus the excluded ones. The rail runs only `views[0]` (`lens.logic.ts:550-556`). `getViewSort` turns a non-string `_sort` into `modified` (`type-sidebar.logic.ts:338-341`), while an unknown string falls to the title comparator (`type-sidebar.logic.ts:209-211`). The rail's Sort popover renders the shared `SortPanel`, whose empty state is "No sorts applied" (`features/collection/toolbar/SortPanel.svelte:135-137`; used at `RailNoteList.svelte:390-396` and `CollectionView.svelte:511`).
- **Main-session decision (where the function lives):** `features/collection` must not import `rail-shell` or `type-definitions`: `rail-shell -> collection` and `type-definitions -> collection` already exist and the feature-cycle ratchet allows no cycle (`src/tests/lib/architecture/feature-cycle.test.ts`, `FEATURE_CYCLE_EDGES_SIZE = 0`). So the row-set function lives on the rail side (next to `queryViewLens` in `features/rail-shell/lens.logic.ts`) and reads `NoteEntryV2` entries (`typeDefinitionsStore.entries`, `vaultStore.path`, `settingsStore.templates.systemFolder`) for archived, title, dates and `_order`. The editor reaches it through a port in `features/collection` that `registerAppPorts()` in `app/boot.ts` fills, the way `registerTypeIconLookup` (`features/file-icons/icon-resolver.ts:26`) is filled there. The port also supplies the effective-sort label for the editor's Sort panel. `CollectionView` uses the port only when `isViewFile(path)` (`core/filesystem/fs.logic.js`; `editor.service.ts:137` maps `.view` and `.collection` to the same file type, so the path is the only signal); with no port registered it keeps today's query.
- **Main-session decision (shape):** the editor needs whole records (formula values, columns), the rail needs paths. One low-risk shape: an optional fourth argument of `executeQuery` that, when given, replaces its `limit` step with the row-set function and resolves the columns from the rows it returns (`resolveColumns` reads the rows it is given, `collection.logic.ts:190-191`, so a dropped note adds no column). Without it `executeQuery` behaves exactly as today, which keeps `.collection`, the fences (`collection-block-widget.ts:116`) and their tests unchanged. `queryViewLens` then takes the row context too; its callers change with it: `RailNoteList.svelte` `loadView`, `view-lens.service.ts:24`, and the tests in `lens.logic.test.ts`, `view-lens.service.test.ts` and `TypesNavigator.test.ts`. Use Issue 10's `resolveViewLens` load-state input, not the old `ViewQueryResult | null`.
- **Owner decision (2026-11-04):** the editor's Sort panel for a `.view` shows the effective `_sort` too, not only the rail's.
- **Main-session decision (unknown `_sort` (owner accepted 2026-11-04)):** "ignored" means the default applies (modified, newest first), the same as `getViewSort` already does for a non-string. This changes the order of a view whose `_sort` is an unknown string from title to the default; the ignored-key note says why.
- **Main-session decision (`_order` pins):** pins apply only when `_sort` or the default orders the list, as the rail does today. A view with its own sort keeps the query order on both surfaces.
- **Consequence of the owner decision:** a `.view` whose own filter selects archived notes (for example `_archived == true`) now lists nothing in the editor either, as it already does in the rail. The rail's Archive lens is the place for archived notes.
- **Row cap:** `CollectionTableView` draws at most 200 rows and says "Showing N of M" (`CollectionTableView.svelte:20-23,87`). The "N results" compared here is the row-set length (`queryResult.records.length`), not the drawn rows.
