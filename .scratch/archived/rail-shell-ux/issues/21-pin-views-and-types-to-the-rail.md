# 21: `_rail: true` pins a view or a type to the rail

**What to build:** A `.view` or a type definition with `_rail: true` (YAML boolean) becomes an item on the rail. Pinned items sit in their own group under the navigator items (Types, Calendar, Files), separated by a divider that renders only when there is a pin, above the bottom Archive. They are ordered by `_order` (a view's default is 50, as `getViewOrder`; a type uses `TypeMetadata.order`), then label. A pin shows what its Types row shows: the label is the view's `getViewLabel` or the type's `sidebarLabel`, used as tooltip and accessible name; the icon is `resolveIconForPath` of the `.view` path or the definition path, rendered through `IconRenderer` with its colour, else the row's fallback glyph (`Table` for a view, `FileText` for a type, as in `TypesNavigator.svelte:221-225,249-253`). Clicking a pinned view picks the view lens, or, when it has `_open_in_editor: true`, opens the `.view` in the editor and leaves `layout.railItem` unchanged, matching its Views row. Clicking a pinned type picks that type's lens. Neither opens a navigator pane, like Inbox. The pick persists in `layout.railItem` as `view:<absolute path>` or `type:<TypeMetadata.name>` (the name the type row's lens targets). A saved pin that is no longer pinned (file gone, key removed) falls back to Today once per vault open, in the same check that drops a stale Types pick, so the pin is kept while the index loads. A pinned view moved to Trash from the app falls back to Today at once, through Issue 20's path-change consumer. The view row and type row menus get "Pin to rail" / "Unpin from rail", which write or remove the key and ask for a prompt index refresh. When the rail is too short, the pinned group scrolls and the rest of the rail stays fixed.

## Notes

- **Owner decisions (2026-11-04):** pins are a `_rail: true` key in the file, plus a menu item that writes it; the same key works on `.view` files and type definitions.
- **Main-session decisions (owner accepted 2026-11-04):** pinned group below the navigator items and above Archive; no pin limit (the group scrolls); the pin keeps the item's `_order`, it has no separate rail order; Settings > Rail (Issue 24) orders built-in items only.
- **Main-session decisions (scope of a pin, owner accepted 2026-11-04):**
  - Pins follow the Types navigator, which lists views and type definitions wherever they live (`collectViewFiles` walks the whole tree, `buildTypeMetadataMap` reads every entry), so the builder does not apply `excludeSystemFolder`.
  - `_rail` and `_visible` are independent: a pinned view hidden from Views by Issue 20's `_visible: false`, or a pinned type with `_visible: false`, still shows on the rail. With no Types row, it is unpinned by editing the file.
  - Only the canonical `_rail` spelling is read (no `ALIAS_MAP` entry), like `_open_in_editor` (ADR 0027 amendment 2026-11-03).
  - The stale fallback runs once per vault open, not live, for the reason `staleTypesPickFix` gives (the refresh is throttled, and the entries snapshot lands after `indexReady`). During a session, a pinned view moved to Trash from the app resets the rail to Today at once (owner decision 2026-11-04, same as Issue 20's Types pick); one deleted outside the app (Finder, git) shows Issue 10's "This view no longer exists" until the next vault open; an active pin that is unpinned keeps its lens with no highlighted rail item until another item is picked or the vault reopens. A moved or renamed `.view` is not followed (the Types pick of a view is not either); it falls back at the next vault open.
- **Which view runs:** a pinned view runs the same lens as its Views row: `views[0]` today, the `_rail_view` view once Issue 22 lands. Nothing here changes that.
- **Why the blockers:** 02 gives the `.view` writers the write step the Pin item reuses; 10 adds the reserved-key table and the view lens states; 12 keeps type definitions and `.view` files out of the lenses a pin can show; 20 changes `viewNavigatorRows` and the view row menu first (the review's recommended path, section 5: structure inside Views, then pins) and adds `_visible`.
- **Today (traced):** the built-in rail items are constants and the navigator items come from `railRegistryStore` (`features/rail-shell/Rail.svelte:40-53`); `restoreRailItem` resolves only built-ins and registered navigators (`lens.logic.ts:159-172`); `RailNoteList` already treats any `kind: 'view'` lens as a view (`RailNoteList.svelte:107`), and type lenses already resolve, so the note list needs no change.
- **Owner decision (2026-11-04, accepted limit):** the `.view` YAML writers re-serialise the whole file, so Pin and Unpin on a `.view` drop its comments and formatting, like Change icon (review F13, listed as a risk of option A; fixed by review I15 / `file-io-audit/32`, not here). A type definition goes through `updateNoteFrontmatter`, which keeps the body and unsaved tab edits.
