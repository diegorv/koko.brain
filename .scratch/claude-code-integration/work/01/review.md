## Findings

1. **blocker** src/lib/features/claude-code/ClaudeCodeSection.svelte:64-67 — The switch shows ON while the feature is OFF after the consent notice opens or is cancelled. The shadcn `Switch` binds `checked` internally (`bind:checked` in src/lib/components/ui/switch/switch.svelte), so the click flips its own state to `true`; `setEnabled` returns early without changing the store, so the `checked={settingsStore.claudeCode.enabled}` prop never changes and never re-syncs it. Probe (temporary jsdom test, deleted after): aria-checked was `false` before, `true` while the notice was open, still `true` after Cancel with `claudeCode.enabled === false`; the next click turned the switch visually off, called `setEnabled(false)`, and showed no notice, so the user must click twice to see the notice again. On the consent control for a full-permissions feature, the toggle must not display a state it does not have. Fix: drive the prop from both values, e.g. `checked={settingsStore.claudeCode.enabled || confirmingEnable}`, so Cancel changes the prop from `true` to `false` and resets the switch (or use a Svelte function binding that re-reads the store). Add assertions on `aria-checked` after Cancel and after Enable to `Cancel leaves the feature off and the notice unacknowledged`; the existing test checks only the store, which is why it passes.
2. **minor** src/lib/core/settings/settings.service.ts:172-177 and ClaudeCodeSection.svelte:38-40 — `claudeCode` (including `binaryPath` and `privacyAcknowledged`) lives in the vault's `.kokobrain/settings.json`, and the section runs `claude_status` with that override on mount, so a copied vault can make Settings execute a script it ships. Out of scope for Issue 01 (its criterion says "persist through the settings store"), and mvp-claude already tracks it: b3d086c72 (Issue 02, override must canonicalize to an executable named `claude`) and 810cc135d (Issue 04, machine-wide storage, refuse in-vault paths). No change here; make sure Issue 04 lands before the feature is used with a vault from someone else.
3. **minor** src-tauri/src/commands/claude.rs:174-178 — `run_with_timeout` calls `wait_with_output` after the child exits, which reads stdout/stderr to EOF. If a login rc file starts a background process that inherits the pipe, that read blocks without any bound (not just past 5 s), leaving the section at "Checking..." with "Check again" disabled until the grandchild exits. The build report names this as a known limit. Rare; acceptable for v1, but worth a one-line comment at the function or a follow-up if it ever shows up.
4. **minor** help/documentation/19-settings.md:9 — The Settings help still lists "**Integrations** (Todoist)" and has no Claude Code section. Add Claude Code to the group list and a short table (`claudeCode.enabled`, `claudeCode.binaryPath`), or defer it to Issue 04, which changes where these values are stored.
5. **nit** src-tauri/src/commands/claude.rs:55-60 — `login_shell()` (the `$SHELL` read and the `/bin/zsh` fallback) has no test. It reads process env, so a test would need a pure helper that takes the env value; optional.
