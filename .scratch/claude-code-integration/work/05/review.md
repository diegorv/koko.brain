## Findings

1. major, src-tauri/tests/commands/claude_turn_test.rs:306-313 (and src-tauri/src/commands/claude/turn.rs:306-312): the branch rewrites Issue 02's `sleeping_run_cancelled_mid_run_ends_in_done` so the grandchild is forked before Init, which avoids a real cancel bug instead of exposing it. The probe shows the original script fails deterministically (Done after 30 s, 3 of 3) once the child env has a short PATH: `sh` forks `sleep` while `killpg` runs, the new child misses SIGKILL and holds stdout. In production a cancel that lands while `claude` forks a tool hits the same path. The new test still proves group kill, so keeping it is fine, but the bug must not disappear with it. Fix: open a follow-up `.scratch` Issue for Issue 02's cancel (for example a second `killpg` after the leader is reaped, or `killpg` until ESRCH), with the original script as its failing test; reference it in the test comment.
2. minor, src-tauri/tests/commands/claude_shell_env_test.rs (no test): nothing covers the AC's "After END: `try_wait` up to 1 s, then `killpg(SIGKILL)` and reap" path. Every fake shell that prints END also exits right away, so `reap`'s grace-then-kill branch (shell_env.rs:333-345) never runs in the suite. The probe shows it works today (1.54 s, shell killed and reaped). Fix: add a fake-shell test that prints the env and then `sleep 30` without `exec`, asserting the capture returns in about 1-2 s, the vars are parsed, and the shell pid is gone.
3. minor, src-tauri/src/commands/claude/shell_env.rs:333-345: when the shell exits within the grace, its session is not `killpg`ed, so background jobs started by rc files keep running after every capture (probe: still alive 1.5 s later). The AC and validation 05 say "then `killpg(SIGKILL)` and reap" without that exception; discovery recorded the narrower reading as a default. Those survivors also make report item 2 worse (a job that inherited a turn's pipe would outlive the capture). Fix: either `killpg` the session after a clean exit too (the group id stays reserved while a member lives), or record the decision in the Issue's Notes so the owner accepts it.
4. nit, src-tauri/src/commands/claude/shell_env.rs:247-257: `refresh` gives up on `try_lock` failure, which also happens while a `get` holds the lock for the microseconds it takes to clone a cached result, so a "Check again" can be skipped without a capture running. Rare and recoverable; fix only if cheap (for example a `capturing` flag instead of lock contention).
5. nit, src-tauri/tests/commands/claude_shell_env_test.rs:320: `background_job_holding_stdout_does_not_hold_the_capture` asserts the whole capture takes under 4 s, looser than the AC's "within about 1 s of END". It still proves the capture does not wait for the 8 s job. Fix: optional, measure from the shell's start (a timestamp file) rather than from the spawn.
6. nit, src-tauri/src/commands/claude/shell_env.rs:42-43: two blank lines in a row after `EXIT_GRACE`. Fix: delete one.

## Resolution

1. Fixed: follow-up Issue `.scratch/claude-code-integration/issues/07-cancel-misses-a-child-forked-during-killpg.md` (needs-triage) records the cancel race with Issue 02's original script as its failing test; the comment on `sleeping_run_cancelled_mid_run_ends_in_done` points to it.
2. Fixed: `shell_that_lingers_after_the_end_marker_is_killed_after_the_grace` (fake shell prints the env, then `sleep 30` without `exec`): asserts a return under 4 s, parsed vars, and the shell pid gone (no zombie).
3. Fixed: `reap` now kills the session after a clean exit too. It polls with `waitid(WEXITED | WNOHANG | WNOWAIT)`, so the exited shell stays unreaped and its group id reserved until `killpg` has run, then `kill_session` reaps it. Test `background_job_of_a_shell_that_exits_is_killed` failed before the change (job alive past 5 s) and passes after.
4. Fixed: `ShellEnv` has a `capturing` flag set only while the capture function runs; `refresh` skips when it is set and otherwise waits for the lock, so a `get` cloning the cached result no longer drops a "Check again". No new test: the window is microseconds and a test for it would be timing-dependent; the existing cache tests (including `refresh_while_a_capture_runs_is_skipped`) pass.
5. Rejected (optional nit): measuring from the shell's start needs a timestamp file and adds little; the test still proves the capture does not wait for the 8 s job, and the new grace test covers the post-END timing.
6. Fixed: blank line removed.
