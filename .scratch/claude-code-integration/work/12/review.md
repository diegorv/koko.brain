## Findings

1. major (plausible, not verified in WKWebView), `src/lib/features/claude-code/ClaudePanel.svelte:99-102`: slow scrolling up during a streamed reply can be undone by the next delta. Each `text_delta` is its own store event (`src-tauri/src/commands/claude/stream.rs:144`, `--include-partial-messages`), and the effect calls `scrollTop = scrollHeight` whenever `following` is true. A slow trackpad scroll moves the list a few px per frame, so every scroll event lands within 32 px and keeps `following` true, and the next delta snaps the list back to the bottom. A delta can also arrive between the user's scroll and its scroll event, while `following` is still true. Either way, the user cannot scroll away from a streaming reply unless one frame jumps more than 32 px. Fix: treat upward movement as leaving the bottom. Record the `scrollTop` the effect set. In `onMessagesScroll`, set `following = false` when `scrollTop` is lower than both the last recorded position and the bottom, and set it to true only when the list is within the threshold and not moving up. A `wheel` listener with `deltaY < 0` is an alternative. Add a test in which a scroll event 10 px above the bottom, after an auto-follow, is followed by a TextDelta and the list stays put.
2. nit, `src/tests/lib/features/claude-code/ClaudePanel.test.ts` (`fakeMessageListLayout` and the follow tests): each test sets `content.height` before it emits the event, so a version that reads `scrollHeight` synchronously, without `tick()`, would also pass. The `tick()` requirement is met in the code but not pinned by a test. Fix: derive the fake `scrollHeight` from the number of rendered `[data-claude-message]` and `[data-claude-tool]` nodes, or from their text length, so the value changes only once the DOM updates.
3. nit, `src/lib/features/claude-code/ClaudePanel.svelte:94`: the refocus runs only when `document.activeElement` is the body or null. Under the HTML focus fixup rule, a disabled field loses focus, which the test models. If a WebKit build kept `activeElement` on the textarea once it was disabled, the code would never call `focus()`. Adding `|| active === promptEl` to the condition costs nothing and covers that case.

## Resolution

1. Fixed. `ClaudePanel.svelte` keeps `lastScrollTop`, the `scrollTop` of the last scroll event or follow. `onMessagesScroll` sets `following` only when the list is within the threshold and did not move up from that position, so a small scroll up during a streamed reply stops the follow. New test `stops following on a small scroll up during a streamed reply`: 10 px up after an auto-follow, then a TextDelta, leaves the list there. It fails against the reviewed panel.
2. Fixed. `fakeMessageListLayout` derives `scrollHeight` from the text length of the rendered `[data-claude-message]` and `[data-claude-tool]` nodes, so it grows only once the DOM updates, and the follow tests assert against the rendered bottom. Probe: a follow that measures in `$effect.pre` (before the DOM update) fails 3 tests. A synchronous read in `$effect` without `tick()` still passes, because Svelte 5 runs `$effect` after the DOM update of the same flush; no jsdom test can tell that apart, and `tick()` stays as the pattern docs/PATTERNS.md asks for.
3. Fixed. The refocus condition also accepts `active === promptEl`. New test `focuses the prompt again when the engine kept focus on it while disabled` (jsdom keeps focus on the disabled textarea) checks that `focus()` is called; it fails against the reviewed panel.
