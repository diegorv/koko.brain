# 06: A filter that does not parse shows an error instead of an empty (or full) list

**What to build:** A filter expression that fails to parse (`status = 'active'` with a single `=`, an unclosed quote) or calls an unknown function (`foo(1)`) is reported, not evaluated as false. The collection editor and the inline collection block show a short error naming the bad expression; the rail's view lens result carries the same error, which Issue 10 shows in the note list. The filter row in the toolbar marks its input as invalid while the text does not parse. A parse failure inside a NOT group no longer turns into "every note matches". Two smaller cases in the same area: a formula with a parse error or an invalid name cannot be confirmed, and an unknown view `type` is a parse error naming the three accepted values.

## Notes

- **Cause (traced):** filter strings are parsed at evaluation time, per record, and a parse failure returns `false`: `evaluateFilterCached` (`features/collection/collection.logic.ts:229-256`, called from `executeQuery` at lines 141 and 144); `evaluateFilter` (lines 199-221, used only by tests) has the same catch. A NOT around it inverts that to `true`. An unknown function parses (`expression/parser.ts:117-128`) and throws only when evaluated (`expression/evaluator.ts:403-404`), into the same catch. `yaml-parser.ts:95-96` keeps filter strings unvalidated; `FilterRow.svelte:89-91` writes every keystroke. Formula: `toolbar/FormulaRow.svelte:34-58`, `formula.logic.ts:15-25` (`formulasToEntries` sets no `error`), `formula.logic.ts:79-110`. View type: `yaml-parser.ts:47-49`, `help/documentation/12-collection.md:35`.
- **Main-session decision:** an expression that does not parse makes the whole query report the error (no partial result), so a typo never looks like "no data".
- **Main-session decision (mechanism):** `executeQuery` checks every filter string of the global and view filters, recursively through `and` / `or` / `not`, before the record loop, with one exported validator (parse plus the unknown-function check) that `FilterRow` also uses, so the row and the query agree. The first failure returns `records: []` and `filterError` (an optional `filterError?: string` on `QueryResult` in `collection.types.ts`, and the same field on `ViewQueryResult` in `lens.logic.ts`). The unknown-function check walks the AST for `call` nodes whose callee has no `.` and compares them with a list of the plain functions handled in `evaluateCall`'s `switch` (`evaluator.ts:290-406`), kept next to it. Runtime throws (an unknown file method, a circular formula) keep today's per-record `false` and are out of scope, so the per-record catch stays and the existing `collection-logic.test.ts` test 'handles invalid expressions gracefully' is unchanged.
- **Main-session decision (where):** `parseCollectionYaml` does not reject bad filter strings. Rejecting them there would replace the editor with the Parse Error banner and hide the toolbar on the keystroke that broke the filter, so the user could not fix it where they typed it.
- **Main-session decision (blank):** a blank raw row is unfinished, not invalid: `filterGroupsToFilter` drops it and `FilterRow` does not mark it. A blank item written by hand in the YAML (`and: ['  ']`) is reported like any other expression that does not parse.
- **Main-session decision (formula):** Check uses the `nameError` that `PropertiesPanel` already passes (`validateFormulaName`: blank, spaces, dots, duplicate) and derives the expression error from `entry.expression` with `validateFormulaExpression`, not from `entry.error`, so a formula loaded with a broken expression shows its error once opened. A blank expression also disables Check (`validateFormulaExpression` treats blank as valid, so check it separately).
- **Main-session decision (view type):** review F91 left "default or reword" open; reword. A missing `type` stays a parse error (no behaviour change for existing files) and help 12 stops saying `table` is the default. Derive the accepted list and the message from one constant shared with `ViewType` (`yaml-parser.ts:235`).
- **After Issue 04:** a nested filter object loads as a raw row whose text is an equivalent expression, so it validates like any other raw row and is not marked invalid.
- **Known effect, not fixed here:** a visual row on a property whose name has a space (`due date`) serializes to `due date == '...'`, which does not parse (`filter.logic.ts:44-55`, no quoting; the expression language has no syntax for such names). Today that row matches nothing; after this Issue the query reports the error naming that expression. Making such properties filterable is out of scope.
- **Until Issue 10 lands:** the navigator count for a `.view` with a bad filter reads 0 (`view-lens.service.ts:24` counts `notes.length`), and the rail note list shows "No notes here". Issue 10 renders `filterError`.
