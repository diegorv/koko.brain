## Findings

1. **blocker** `src/lib/features/type-definitions/type-definitions.service.ts:25-26`: the two new imports add the feature pairs `type-definitions -> properties` and `type-definitions -> rail-shell`. With the existing `properties -> type-definitions` and `rail-shell -> type-definitions` they form feature cycles, and `src/tests/lib/architecture/feature-cycle.test.ts` (ADR-0003, `FEATURE_CYCLE_EDGES_SIZE = 0`) fails: 4 tests, 9 pairs reported inside a cycle (`type-definitions -> rail-shell -> type-definitions`, `type-definitions -> properties -> type-definitions`, and the longer ones through event-calendar and note-list). The test also rewrites `feature-cycle-baseline.json` with the two new pairs when it runs. The full suite will fail at deliver. Fix: (a) `setTypeRailPin` should not import `features/properties`. Either move `setTypeRailPin` into `features/properties/lifecycle.service.ts` next to `toggleFavoriteForPath`, or into `features/rail-shell` (TypesNavigator is its only caller; `rail-shell -> properties` is acyclic), or move `setBooleanFlag` down to `core/frontmatter/properties.logic.ts`. (b) `renameType` should not import `features/rail-shell`. Move the pin-key prefixes and `viewPinKey` / `typePinKey` into a module both features can import (`utils/` or a `core/` settings helper), or have the rail shell move the `railItem` after a rename instead. Do not add baseline entries. Then re-run `feature-cycle.test.ts` and restore the baseline JSON if the test touched it.
2. **minor** `src/lib/features/rail-shell/TypesNavigator.svelte:375`: the type-row pin calls `setTypeRailPin(path, pinned)` without a catch. `updateNoteFrontmatter` passes read errors through as-is ("Read errors propagate as-is"), so a definition that cannot be read gives an unhandled promise rejection and no feedback. The view row routes through `handleViewRailPin`, which logs and toasts. Fix: wrap the call the same way, in a handler that shows a toast on failure.
3. **minor** `src/lib/features/type-definitions/type-definitions.service.ts:309,317`: when the `.view` YAML does not parse, `setViewRailPin` returns silently. The user clicks Pin to rail and nothing happens, with no toast. The JSDoc also says it "writes nothing when the file already says so", but `updateViewRailYaml` re-serialises the file. In practice `updated === content` holds only for YAML that does not parse, or a file already in `stringifyYaml`'s exact form. Fix: on YAML that does not parse, throw so the menu shows its toast (or report it some other way), and correct the comment.
4. **nit** `src/lib/features/rail-shell/TypesNavigator.svelte:26,398`: the new module-level `error` import (debug logger) is shadowed by `{@const error = ...}` in the `viewRow` snippet. It works, but it is easy to misread. Fix: rename the import (`error as logError`) or the snippet const.
