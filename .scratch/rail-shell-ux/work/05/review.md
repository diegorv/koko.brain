## Findings

1. **minor**: `src/lib/features/collection/expression/evaluator.ts:613`. In `dateOperandTime`, a string that is not `YYYY-MM-DD` falls back to `new Date(val)`, and V8 parses many plain words that way. Probes: `new Date('Phase 2')` gives 2001-02-01, `'Week 3'` gives 2001-03-01, `'1/2'` gives 2001-01-02 and `'5'` gives 2001-05-01. So a text property such as `due: "Week 3"` matches "before 2026-03-01" and "on or before 2026-03-01", which is the false positive this Issue removes for `''`/null. The Issue's Fix direction prescribes `new Date(str)`, and the listed criterion (`abc`) holds, so this does not block. Fix (follow-up): before falling back to `new Date`, require an ISO date prefix (`/^\d{4}-\d{2}-\d{2}([T ]|$)/`) and return NaN for anything else. Add a test with `'Week 3'`.
2. **minor**: `src/lib/features/collection/expression/evaluator.ts:613`. A Date against a numeric string changed from `Number(str)` to `new Date(str)`. `file.mtime > '0'` now compares against 2000-01-01 local, and `'2026'` against 2026-01-01 UTC. Before, both were milliseconds. The toolbar never writes this, because `quoteUnlessNumber` leaves numbers unquoted, and no test covers it, so the effect is limited to hand-written filters. Fix: keep it, and cover it with the ISO-prefix check from finding 1 (a non-ISO string then gives NaN). Or, if the old behaviour is wanted, keep `toNumber` for an all-digit string.
3. **nit**: `help/documentation/12-collection.md:281`. The `date(string)` row still says only "Parse a date from a string". A user cannot see that a `YYYY-MM-DD` argument is now local midnight with day precision. That changes hand-written filters: `file.mtime > date('2024-01-01')` now starts on 2024-01-02, and `==` matches the whole day. Fix: add one sentence to that row, or a follow-up docs Issue.
