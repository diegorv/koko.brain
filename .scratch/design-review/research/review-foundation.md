# Design review: Design tokens, theming, UI primitives

Area: src/app.css, src/lib/features/canvas/canvas-markdown.css, src/lib/components/ui, theme application (ADR-0035) and theme settings components, components.json (no tailwind.config; Tailwind v4 via vite plugin).
Evidence: inventory-foundation.md, screenshots (settings-appearance-light/dark, settings-update-light, settings-editor-light, file-history-light, editor-live-preview-light, kanban-board-dark, rail-favorites-light, collection-and-queryjs-block-light), code read, and contrast ratios computed from the literal token values in theme.logic.ts (WCAG 2.x formula). Run-time behavior was not exercised; items that depend on it say so.

Overlap note: review-settings.md (#9, #10, #17) already covers hover-only theme actions, theme editor basics and the settings sheet. Items here are the root causes at token/primitive level or new facts.

## Clear

1. Control boundaries fail non-text contrast (switch off-state, input and select edges) (accessibility, M)
- READABILITY_PAIRS (theme-builder.logic.ts:105-155) checks only text and accent pairs. No pair covers a control against the surface it sits on, so the settings toggle track and input border are near invisible. Computed from theme.logic.ts: Lavender Haze switch track #D2CCE0 (:286) on setting item #DDD8E8 (:284) is 1.12:1, off thumb on track 1.38:1, input border #D5D0E2 on the item 1.08:1. KokoBrain Default track #444660 (:177) on #20212d (:174) is 1.74:1, input border #242835 1.09:1. WCAG 1.4.11 asks 3:1. Visible in settings-update-light.png (Auto-check on launch toggle at about 1367,486 reads as a smudge).
- Proposal: add control-boundary pairs to READABILITY_PAIRS (switch track, input border, select border against settingItemBg, card, popover, editorBg) at 3:1 and let the final pass lift `switchUncheckedBg` and `input`. Give the off switch a 1px border in the lifted color. Because `Input` also uses `bg-input-bg` and `Select` trigger is transparent (select-trigger.svelte:22), make both use the same surface and border tokens.

2. Error and destructive text is held to only 3:1 and never checked on the surfaces it is drawn on (accessibility, M)
- `text-destructive` appears 59 times, 31 on 11-12px text. The core error color is lifted to 3:1 against the editor background only (theme-builder.logic.ts:187), and READABILITY_PAIRS has no destructive-as-text entry (only destructiveForeground on destructive, :122). Computed: Lavender #C83848 is 4.53:1 on the editor but 3.66:1 on the settings item (the catalog error in settings-appearance-light.png) and 4.16:1 on the right sidebar #EAE6F2; Default #f3333b on editor #2a2e3d is 3.44:1. The same gap applies to muted text on `settingsHoverBg` (Lavender #645c74 on #D2CCE0 is 4.05:1) and on the selected row accent.
- Proposal: derive a dedicated text-safe error token (lifted to 4.5:1 on editorBg, card, rightSidebarBg, settingItemBg, fileExplorerBg) and use it for every `text-destructive` text; keep `destructive` for fills. Add muted-on-hover/selected pairs. Button `destructive` uses a literal `text-white` (button.svelte:12); switch it to `text-destructive-foreground` so the checked pair applies.

3. Toasts ignore the theme and errors disappear after 4 seconds (feedback-states, M)
- AppOverlays.svelte:16 renders `<Toaster richColors>`: colors come from the library, not tokens (pink/red in Lavender, red text on near-black red in KokoBrain Default, see settings-appearance-dark.png). 103 `toast.error` calls use svelte-sonner's 4000 ms default (Toast.svelte TOAST_LIFETIME); only three sites override (settings.service.ts:210, sync-scheduler.service.ts:261, :275). There is no close button, action or details on the default path, and the toast text is not selectable (see 4).
- Proposal: one token-styled toast (popover surface, 1px divider border, 3px left accent in destructive/warning/success, text in foreground). Errors stay until dismissed or 10 s with pause on hover, show a close button, and offer "Copy details" for long messages. Reversible deletes use an "Undo" action instead of a confirm. Put the severity-to-duration rule in one helper so call sites stop choosing.

4. Icon-only controls have no enforced name, tooltip or size (accessibility, M)
- 35 `size="icon*"` buttons: 11 have neither `aria-label` nor `title` (CollectionView.svelte:595, 622, 645, 668; FormulaRow.svelte:57; FilterRow.svelte:101, 184; SortPanel.svelte:126; AutoOrganizeRuleRow.svelte:298, 307, 316) and 4 more have title only; a scan of the 206 raw `<button>` elements finds about 16 more icon-only ones with no name (CalendarConfigPanel 4, TasksView 2, NoteActionBar, SearchResult, LinkItem and others). 133 `title=` attributes carry the tooltips: unstyled, delayed by the OS, never shown on keyboard focus, and shortcuts are written as "Cmd+D" (NoteActionBar.svelte:148-175). Only 3 files use the styled Tooltip primitive. 18 of 35 icon buttons are resized by the caller with `size-5/6/7` because Button only offers 32/36/40px.
- Proposal: an `IconButton` in components/ui that requires a `label` prop (renders aria-label and the styled Tooltip with an optional shortcut chip using the Mac glyphs), with `xs` 24, `sm` 28, `md` 32 sizes. Migrate the 27 unnamed ones first. One Tooltip.Provider at the app root with a 400 ms delay (today only EventCalendarView.svelte:237 has one).

5. No shared empty, loading and error components: about 25 variants of the same three states (information-architecture, M)
- inventory section 2/3: "No files found", "No results found", "Nothing here", "No notes here", "No backlinks found", "Indexing vault...", "Indexing tags...", "Loading..." and so on, each its own markup. The same sentence is drawn with `text-xs`, `text-meta` or the default size, with `py-4` or `py-8`, in three different muted colors (SearchPanel.svelte:116-120, TagsView.svelte:80-82, BacklinksPanel.svelte:58-64). Most give no next step: rail-favorites-light.png shows a bare "No notes here" while Favorites is a lens the user fills with the star in the action bar. `animate-spin` is hand-placed in 11 files, and no skeleton exists.
- Proposal: `EmptyState` (optional icon, one-line title, one-line hint, optional action), `InlineStatus` (spinner plus label, or error plus Retry) and a copy rule: "No <things> yet" with a hint that says how to get one; one ellipsis character; "Indexing" for background work, "Loading" for fetches. Migrate the high-traffic lists first: note list, search, backlinks, tags, kanban empty lane.

## Moderate

6. Selection is disabled app-wide with no opt-in (interaction, S)
- app.css:498 sets `user-select: none` on body, and `select-text` or `user-select: text` appears nowhere in src/lib (only the editor opts in, editor-theme.ts:40). Error messages, file paths, the build string in Update (settings-update-light.png "4.9.1 (f2cd7f97b) (2026-11-17T09:11:08)"), properties Info values and toast text cannot be selected or copied, which matters most when reporting a failure.
- Proposal: keep `none` on chrome (buttons, tabs, rows, rail), and add a `selectable` utility applied to settings content, toasts, dialogs, error blocks, tooltips, the Info rows and backlink snippets. Alternatively invert: allow text selection by default and mark interactive chrome `select-none` once in the base layer.

7. Primitive gaps make every feature hand-roll controls (consistency, L)
- 206 raw `<button>` elements against 97 `Button` uses. No Tabs or segmented control: ThemeEditor.svelte:176-183 hand-builds tabs without role or aria-selected, while search, calendar D/W/M and kanban view toggles each have their own. No Checkbox: 7 native `input type=checkbox` styled with `accent-primary` (PropertiesPanel.svelte:80, 98, 127; EventDialog.svelte:202; PropertyField.svelte:126; RailPropertiesPicker.svelte:149). Native `<select>` in KanbanView.svelte:488 and GraphControls.svelte:100, 113 although `Select` is used in 7 files (macOS chrome visible in kanban-board-dark.png). No Badge/Chip, Textarea or Spinner.
- Proposal: add Tabs (bits-ui), SegmentedControl, Checkbox, Badge, Textarea, Spinner; replace the three native selects and the theme editor tabs. Keep it incremental: new primitive first, then migrate the surfaces that other reviews already flag.

8. Base layer has no focus or reduced-motion rules, so each primitive improvises (accessibility, S)
- Focus treatments: Button and Input `ring-[3px] ring-ring/50` (button.svelte:7, input.svelte:44), resizable handle `ring-1 ring-offset-1` (resizable-handle.svelte:24), scroll area `ring-4` (scroll-area.svelte:32), dialog close `ring-2 ring-offset-2` (dialog-content.svelte:38), meta-bind `box-shadow` 1px at 30% (styles.ts:712). The global rule only tints the outline (app.css:486). The dialog close uses `focus:` not `focus-visible:`, and bits-ui focuses it when the dialog opens, so every dialog shows a heavy ring on the X on open (file-history-light.png).
- Motion: `prefers-reduced-motion` appears once in src (EventCalendarView.svelte:284). Every overlay uses tw-animate-css `animate-in`, the settings sheet flies in, `animate-spin` and `transition-all` are everywhere.
- Proposal: one `--focus-ring` token and a `focus-ring` utility, a base `:focus-visible` rule so raw buttons get the same ring, and the dialog close switched to focus-visible. Add one `@media (prefers-reduced-motion: reduce)` block in `@layer base` that shortens transitions and animations to near zero.

9. Keyboard activation on a theme row's action buttons also selects the theme (interaction, S)
- AppearanceSection.svelte:172-178: the row is `div role="button"` with `onkeydown` for Enter/Space calling `selectTheme`; the nested Edit, Duplicate and Uninstall/Delete buttons (:192-239) only stop propagation in their click handlers (:82, 93, 112, 119). A keydown on a focused nested button bubbles to the row, switches and persists the active theme (selectTheme :87-90), then the click runs. Pressing Enter on Edit leaves the edited theme active; Cancel calls `applyActiveTheme` (:140-143), which now applies that theme instead of the previous one. Not exercised at runtime; traced from code.
- Proposal: make the row a real button for selection (or a radio group) with the actions as sibling buttons, not children. At minimum ignore keydown whose target is not the row. Add a visible focus ring to the row.

10. Theme editor exposes 128 raw tokens although a derivation exists (information-architecture, L)
- UIColors 59, SyntaxColors 19, PreviewColors 39, Wikilink 5, Callout 6. Meanwhile `buildTheme` expands about 28 core colors (CorePalette, theme-builder.logic.ts:19) and lifts text to the READABILITY_PAIRS contrast; `coreFromColors` reads a core back out. The editor never uses either: values are saved as typed (ThemeEditor.svelte:80-83), so a user can set muted text equal to its background with no signal. ThemePreview is only used on the list.
- Proposal: open on a "Simple" tab with about 12 core colors (editor bg, panel bg, text, muted, border, primary, link, heading, error, success, warning, code) that regenerates the rest through `buildTheme`; keep the five tabs as "Advanced" overrides, with a reset-to-derived per row. Show a pass/fail contrast chip on every token that appears in READABILITY_PAIRS, and a live ThemePreview in the header.

11. Appearance has no light/dark pairing or "match system" (interaction, M)
- Active theme is a single name (AppearanceSection.svelte:87-90), mode is derived from editor background (theme.service.ts:27-35), and `prefers-color-scheme` appears nowhere in src. The two built-ins are one dark (default) and one light (Lavender Haze), so a macOS user on automatic appearance has to open Settings twice a day.
- Proposal: add "Light theme", "Dark theme" and "Match system" next to the list; listen to `matchMedia('(prefers-color-scheme: dark)')` and apply the paired theme; the list keeps the "Active" marker on whichever is in use.

12. Theme catalog reports the same failure twice and does not finish the install (feedback-states, S)
- Opening Appearance always fetches (:56-58) and on failure shows both a toast (:52) and the inline error with Retry (:260-268); both visible in settings-appearance-light/dark.png, where the toast covers the Heading rows in the Editor section behind it. Offline use is normal for a local-first app. After "Install" (:286-289) the toast says Installed (:67) but the theme is not applied; the user must scroll up to the list and click it.
- Proposal: drop the toast and keep the inline state with a "last checked" hint and the offline cache; toast only on an explicit Retry. Offer "Install" and "Install and apply" (or an "Apply" action on the success toast).

13. QueryJS UI helpers hard-code dark-theme colors (color-theming, M)
- kb-ui.ts defaults: tag chip text `rgba(186,197,238,0.9)` (:297), badge text `#fff` on the 40% status color (:72-75, :346), zebra `rgba(255,255,255,0.03)` (:419), list border `rgb(61,61,61)` (:788, :881). Computed on Lavender Haze: tag chip 1.2:1, status badges 1.53 to 1.65:1, zebra rows invisible. Fine on KokoBrain Default (6.1:1 chip). The app already solved this for events and code blocks with `color-mix` on `--editor-bg/--editor-fg` (app.css:402-415).
- Proposal: express these defaults with theme tokens (`--editor-fg`, `--lp-collection-*`, `--type-*`) and `color-mix`, and add the new pairs to the contrast test in both built-in themes.

14. Meta-bind inline controls are three shapes and the number field is stretched (consistency, S)
- editor-live-preview-light.png: Status is a pill select with a caret, Rating is a box about 190px wide holding "4", Due is the native date field with its own glyph. Select and text/number/date inputs share colors (styles.ts:690-715, 783-794) but the input has no width, so the number and date inputs keep native widths (widgets.ts:1047-1060). The date input color is forced for all date inputs with `!important` at 70% (app.css:473-482), which lowers its contrast.
- Proposal: one control base (height 1.6em, radius, padding, font) for select, number, text and date; set number width from `min`/`max`/value length in `ch`; style the date indicator with the same tokens and scope the date color rule to inputs that need it.

## Polish

15. Token and type-scale hygiene (consistency, S)
- app.css `.dark` (:215-361) is a hand-copied second source of truth for KokoBrain Default and has already drifted: `--input-bg: #3d4058` (:266) vs `inputBg '#333544'` (theme.logic.ts:177 area), `--border` oklch vs `#242835`. Inline theme vars override it after startup, so it only shows before the first apply. Ten `--lp-*`/`--bracket-*` tokens are referenced with fallbacks only and are not themeable (`--lp-comment`, `--lp-hard-break`, `--lp-table-add-*`, `--bracket-match-*`), `--card-foreground` has no Tailwind mapping, and there is no z-index scale (dialogs, kanban popovers and canvas pickers all use 50).
- Proposal: generate the fallback block from `KOKOBRAIN_DEFAULT_THEME` in a test (or delete the duplicated values), add the missing tokens to the theme or drop the vars, and define `--z-*` steps (shell, popover, dialog, toast).
- Type roles: `text-xs` 166 and `text-sm` 110 against `text-meta` 138 and `text-row` 46; 22 `text-[11px]`, 4 `text-[13px]`, 2 `text-[14px]`; primitives hard-code `text-xs`/`text-sm`. Sizes match today (12 and 14 px), so users see no difference; the roles will not hold if a size changes. Proposal: map the primitives to role names and add a lint test next to `text-roles.ts` that fails new `text-[Npx]`.
