## Findings

1. minor — `docs/REMOTE-ACCESS.md:33` (and `src-tauri/src/remote/server.rs:427-454`, the Issue's note): "Video plays but may not seek (no Range support yet)" is probably wrong for Safari. Apple's Safari Web Content Guide says "HTTP servers hosting media files for iOS must support byte-range requests" (https://developer.apple.com/library/archive/documentation/AppleApplications/Reference/SafariWebContent/CreatingVideoforSafarioniPhone/CreatingVideoforSafarioniPhone.html). Several reports describe iOS and Mac Safari refusing to play at all when a server answers `Range` with a 200 and the whole file. The current code does not hit this yet: `MediaWidget` takes its raw src and never goes through `convertFileSrc` (desktop gap X4), so no editor path loads a vault video from `/v1/asset/`. When X4 lands, though, the video in the owner check may not play on the iPad. Fix: change the sentence to say video may not play in Safari or iOS until Range support lands, and raise the priority of the Range item in `research/next-phases.md`. A minimal `Accept-Ranges: bytes` / 206 answer is the real fix, in a follow-up.
2. nit — `src-tauri/src/remote/dispatch.rs:139-153`: `asset_path` copies the body of `require_vault_path` (`dispatch.rs:116-132`). The only differences are the root allowance and returning the canonical path. If one rule changes, the other can drift. Fix: one private helper that returns the canonical path and takes an `allow_root` flag, used by both.
3. nit — `src-tauri/src/remote/server.rs:440`: a `HEAD` request reads the whole file into memory only to report `Content-Length`. Fix: on HEAD, take the length from `fs::metadata`. Not urgent, since the Issue already accepts whole-file reads for GET.
4. nit — `src/lib/app/remote/tauri-bridge-stand-in.ts:13`: this line of the edited doc comment was not rewrapped and runs past the width of the lines around it. Fix: rewrap the paragraph.
