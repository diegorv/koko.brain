2. minor — `src-tauri/src/commands/history.rs:61-90`. Now that `save_snapshot` runs on the blocking pool, two saves of one file can reach `DB.lock()` in either order. Before, the main thread ran them one at a time, in order. The window is exactly the case this Issue targets: during a multi-second cache load, every save queues on the `DB` mutex, and `std::sync::Mutex` does not wake waiters in FIFO order. Plain reordering is harmless, because `created_at` is taken before the lock and `find_latest_hash` orders by it. An A-B-A sequence is not. Scenario: the latest snapshot is X, the user saves v2 and then reverts to X, and both saves wait on the lock. If the second save wakes first, its dedupe compares X with the latest snapshot X and skips. Then v2 is inserted. History now ends at v2 while the file on disk is X. The editor does not save unchanged content again, so the gap lasts until the next edit. Nothing is lost (X is still in history as an older row), but the newest entry is wrong. Fix (optional, owner's call): dedupe against the latest snapshot with `created_at <= own created_at`, then insert. Or accept it and note it in the Issue. Both build and discovery already flagged the risk, but neither described this case.
3. nit — `src/lib/features/search/search.service.ts:354`. With `fetchStats: false`, startup stats now come only from `buildSemanticIndex()`. If that build rejects (logged, never surfaced), `semanticStats` stays null for the session, so `SearchStatus.svelte:19`, `SearchPanel.svelte:100` and `SearchSection.svelte:124` show no chunk count until Settings re-runs init. Before, the init read filled them in. This only affects display, and discovery already lists it. No change requested.
4. nit — `src-tauri/src/commands/semantic.rs:1164-1165`. The comment says the `DB` mutex "is held for a whole search-cache load". It is only held while a load runs. `history.rs:57-59` says it more precisely ("can be held"). Fix: write "can be held" here too.
