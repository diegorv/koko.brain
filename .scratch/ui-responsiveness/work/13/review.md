## Findings

1. minor — `src/lib/plugins/queryjs/kb-api.ts:401-437`: `ensureCache` re-reads the module slot on every call and keeps no per-instance reference to the set it got. If a block that runs across an await (`await kb.view(...)`, the external script load) is overtaken by a block at a newer key that replaces the slot, its next `pages()` / `page()` / `current()` call rebuilds the set from its own snapshot. Within one block run, `kb.page(x)` then returns a different object than before the await, and fields a `mutate` wrote earlier in that run are gone. On main one block always saw one stable set (ADR 0010: "lives for the duration of one widget execution"). The same gap causes the alternating-key thrash the build report names. Fix: keep the result on the instance (`this._pageSet ??= <slot hit or build>`) so each block keeps the set it first got and still shares on a hit. Add a test that interleaves two keys and asserts `a.page(p)` keeps its identity.
2. minor — `help/documentation/13-queryjs.md:338`: the user-facing `mutate` example (`p.computed = p.priority * 10`, "Modify in place") does not say that the write is now seen by every later block at the same index state. A block that assigns a frontmatter key such as `p.status` changes what other blocks filter on. The ADR and the Issue Notes record this, but a script author reads only the help page. Fix: add one sentence there, or have `mutate` users write to a copy.
3. nit — `src/lib/plugins/queryjs/kb-api.ts:30`: the single slot keeps the closed vault's whole page set (about 10k `KBPage` objects on the owner's vault) alive after `teardownVault`, until the next build replaces it. The cost is memory only, and the next vault's first block replaces it. If wanted, a `resetSharedPageSet()` export called next to `queryjsSessionStore.reset()` drops it. The build report states this choice.
4. nit — `src/lib/plugins/queryjs/kb-api.ts:16-19,30`: the `PageSet` fields (`list`, `byPath`) and the inline slot type fields have no JSDoc. CLAUDE.md asks for JSDoc on interface fields.
5. nit — `src/tests/lib/plugins/queryjs/kb-api.test.ts` (list-isolation test): `listB.mutate(() => {})` is a no-op, and `mutate` never reorders or resizes its list. The `_values` reverse and push lines are what exercise the copy. No test pins the documented behavior that a field B's `mutate` writes is visible to A (shared page objects). One assertion there would stop a later deep copy from changing that behavior silently.

## Resolution

1. Fixed. `KBAPI` holds the set it got on its first read in a private `_pageSet` (`kb-api.ts`); `ensureCache` returns it before looking at the slot, so a block that awaits keeps one set. New test "a block keeps the page set it first got when a block at a newer index state runs in between" (red before the fix: `a.page(alpha)` was a rebuilt object); `kb-api-contract.test.ts` lists `_pageSet` as internal. ADR 0010 amendment says so.
2. Fixed. `help/documentation/13-queryjs.md` Mutation section says page objects are shared until the index changes and to write a field of your own, not a frontmatter key.
3. Rejected (optional nit). The cost is memory only, bounded to one set, and the next vault's first block replaces it; `teardownVault` already changes the key through `invalidateVaultEntries()`. A reset export would add a second teardown hook for this module with no visible behavior to test.
4. Fixed. One-line JSDoc on the `PageSet` fields and the slot fields.
5. Fixed. The list-isolation test's `mutate` assigns `computed`, and the test asserts block A's page sees it.
