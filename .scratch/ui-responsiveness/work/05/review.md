## Findings

1. minor — `src-tauri/src/utils/main_heartbeat.rs:102-105` — The test poster runs even the `Duration::ZERO` closures on a freshly spawned thread, so a thread spawn plus schedule over 50 ms (a loaded CI box during the parallel `cargo test` run) produces an extra report and fails `reports.len() == 1` / `reports.is_empty()`. Fix: run zero-delay tasks inline (`if delay.is_zero() { task() } else { spawn }`), keeping the spawned thread only for the late one.
2. minor — `src/lib/contracts/ipc.ts:41-71` — FIFO pairing drifts once a recorded invoke never gets an `enter` (a traced command whose args fail to deserialize, or Rust debug turned off while the JS listener stays on): every later `[IPC-QUEUE]` line for that command pairs with an older invoke and over-reports until 32 more invokes push it out. Bounded and debug-only. Fix (optional): drop pending invokes older than a few seconds when pairing, or note the caveat in the `takeQueueWait` JSDoc.
3. nit — `src/lib/utils/log.service.ts:83-88` — With the 250 ms window, the last lines before a permanent webview hang or a force quit are never written; before, they were at least queued as IPCs right away. The Issue asks for this design and the build report notes it. Possible follow-up: flush on `pagehide` / `beforeunload`.
4. nit — `src-tauri/src/utils/main_heartbeat.rs:57-80` — `set_enabled` (start/stop/idempotence, spawn failure) has no test; only the pure loop does. Low risk thin glue. Also, if `run_heartbeat` returns because the poster failed, `RUNNING` stays `Some`, so a later enable does nothing until a disable. That only happens when the event loop is gone.
5. nit — `e2e/mocks/tauri-core.ts:486` — `set_main_thread_heartbeat` reuses `handleSetTauriDebugMode`; it behaves the same (returns null) but the name is misleading. A shared `handleNull` or a dedicated handler reads better.

## Resolution

1. Fixed: the test poster in `main_heartbeat.rs` runs zero-delay closures inline and spawns a thread only for a late one.
2. Fixed (documented): the `takeQueueWait` JSDoc names the FIFO drift and its bound (`MAX_PENDING_PER_COMMAND`). Not dropping stale entries by age: the lines are debug-only and bounded, and an age cutoff would also drop real long waits, which are what this line exists to show.
3. Rejected for this Issue: the 250 ms buffer is the design the Issue asks for. A `pagehide` / `beforeunload` flush is a possible follow-up for the owner.
4. Rejected: `set_enabled` is thin glue around a real thread and `debug_log`; a test would need the global `RUNNING` state and real sleeps. The stale `RUNNING` after a poster failure happens only once the event loop is gone (app shutting down), when no later enable can follow.
5. Fixed: `set_main_thread_heartbeat` has its own `handleSetMainThreadHeartbeat` in `e2e/mocks/tauri-core.ts`.
