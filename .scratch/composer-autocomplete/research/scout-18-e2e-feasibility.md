# Scout 18: E2E feasibility for composer #tag / [[wikilink]] autocomplete

Read-only research. Nothing was run (no vitest, cargo, build, or Playwright). All paths are relative to the repo root.

## Verdict

An E2E spec for the composer is feasible and cheap. The `/composer` route can be opened directly in the Playwright Chromium page, the Tauri mock layer already serves the vault data the completion sources need, and the editor's `wikilink-completion.spec.ts` is a direct template. Three things need care: (1) the composer page runs with its own empty mock state, so a spec must seed it; (2) the mock has no way to observe what `submit_composer_capture` received; (3) the real production risks (separate webview, capability, window clipping, Esc propagation) cannot be reproduced fully in the browser.

## 1. How E2E runs

- `scripts/e2e.sh:89` starts `PLAYWRIGHT=true pnpm dev` in the background, `:46` waits up to 30 s for `/`, `:116` runs `pnpm exec playwright test --config e2e/playwright.config.ts -x "$@"`. Extra args (spec paths, `--shard`) are forwarded. Port: `E2E_PORT` env, 1421 in main checkout, 1422-1499 hash in worktrees (`scripts/e2e.sh:40`, default_port above it).
- `e2e/playwright.config.ts`: `testDir ./specs`, 30 s test timeout, 5 s expect timeout, fullyParallel, 4 workers locally, 1 retry locally and 2 in CI, single `chromium` project, `baseURL http://localhost:${E2E_PORT}` (lines 5-23). Playwright `^1.64.1` (`package.json:84`).
- CI: `.github/workflows/e2e.yml` runs 4 shards through `bash scripts/e2e.sh --shard=N/4`. A new spec is picked up automatically by the testDir glob.
- `docs/TESTING.md:168-171` requires at least one E2E happy-path test for a new user-facing feature; `:173-177` requires asserting rendered content, one behavior per test. Per-area run table is at `:146-164` (no row for the composer or `routes/`).
- Existing unit coverage of the composer route: `src/tests/routes/composer-page.test.ts` (459 lines, jsdom, mocks `#lib/contracts/ipc.js` `call`/`on`, lines 5-8). There is NO E2E spec that touches the composer (grep over `e2e/` finds "composer" only in `e2e/mocks/tauri-core.ts` and a template path string in `e2e/specs/deep-link.spec.ts:8`).

## 2. How Tauri is mocked in E2E

- `vite.config.js:55-67` lists `playwrightMocks`; `:135` applies them as `resolve.alias` only when `PLAYWRIGHT` is set. Aliased: `@tauri-apps/api/core`, `plugin-fs`, `plugin-dialog`, `api/event`, `plugin-opener`, `plugin-http`, `plugin-deep-link`, `api/window`, `api/webviewWindow`. `:116-129` excludes them from dep optimization so there is a single module instance.
- The composer imports `call` and `on` from `#lib/contracts/ipc.js` (`src/routes/composer/+page.svelte:5`), and `ipc.ts:1-2` imports `invoke` and `listen` from the aliased modules. So the composer page in E2E uses the same mocks as the main app with no extra wiring.
- `e2e/mocks/tauri-core.ts`:
  - `HANDLERS` is a type-exhaustive map over `CommandMap` (`:470-566`). A new Rust command added to `src/lib/contracts/commands.ts` fails `pnpm check` until a handler is added here (`:569-575` compile-time guards). `invoke` returns the handler result and logs `[e2e mock] Unknown invoke command` for unknown names (`:577-586`).
  - Quick-capture commands are all no-ops: `open_composer`, `dismiss_composer`, `submit_composer_capture`, `report_composer_capture_result` -> `handleQuickCaptureNoop` (`:556-561`, handler at `:453`).
  - Data commands the completion sources need already exist and return real mock data: `get_all_tags_v2` (`:155`, handler wired `:491`), `get_all_vault_entries_v2` (`:127`, wired `:485`), `scan_vault` (`:66`, wired `:474`), `read_files_batch` (`:70`).
- `e2e/fixtures/console-guard.ts:21-37`: an auto fixture fails any spec whose page logs an unknown-command warning (allowlist is empty). So a composer spec built on `test-vault.ts` base fails loudly if the composer calls a command with no mock handler.
- Event bus: `e2e/mocks/tauri-event.ts` keeps an in-page `listeners` map; `emit()` from app code is a no-op (`:20-22`); specs deliver Rust events with `window.__e2e.events.emit(name, payload)` (`:29-36`, `:44-47`). Typed against `EventMap`. Events are per page: there is no cross-page delivery.
- State: `e2e/mocks/virtual-fs.ts` (in-memory Map, `populate()` at `:101-123`) and `e2e/mocks/vault-index.ts` (`rebuildAll()` `:366`; `virtualFS.subscribe({onPopulate: rebuildAll ...})` `:672-676`; `getAllTags()` `:499`; `getAll()` `:425`). Both register on `window.__e2e` at import (`virtual-fs.ts` bottom; `vault-index.ts:690-694`). Because the composer page imports the core mock through `ipc.js`, `window.__e2e.fs` and `window.__e2e.events` exist on a bare `/composer` load.
- `e2e/mocks/tauri-window.ts` and `tauri-webview-window.ts` (`getCurrentWebviewWindow` reports label `main`, `:48-52`) are not used by the composer today.

## 3. Can `/composer` be opened and driven?

Yes, by reading the code. UNVERIFIED by execution (not allowed to run Playwright).

- `src/routes/+layout.svelte` only imports `app.css` and renders children (lines 1-7); `src/routes/+layout.ts:5` sets `ssr = false`. The vault-boot logic lives in `src/routes/(app)/+layout.svelte`, so `/composer` boots without a vault, without `Open Vault`, and without the app shell. `page.goto('/composer')` on the dev server should render the textarea (`+page.svelte:204-212`).
- Every existing spec uses `page.goto('/')` through the `vaultPage` fixture (`e2e/fixtures/test-vault.ts:140-158`, `:174-180`). No spec navigates to another route or opens a second page (`grep newPage|goto(` finds only `goto('/'`). So a composer spec would be the first non-root route spec; it needs its own small fixture or inline setup.
- The composer page holds a brand-new mock state (empty `virtualFS`, empty `vaultIndex`). Seeding recipe, all with existing APIs: `goto('/composer')`, `waitForFunction(() => window.__e2e?.fs)` (as `test-vault.ts:140-145`), `page.evaluate(files => window.__e2e.fs.populate(files), TEST_FILES)` (`populate` auto-rebuilds the index, `vault-index.ts:673-675`). `TEST_FILES` is exported from `e2e/fixtures/test-vault.ts:126`; it already has tags `intro` (Welcome.md), `plan`/`project` (Roadmap.md frontmatter and inline), and notes Welcome, Inbox, Projects/Roadmap, Projects/2026-Q2, Projects/archive/2025-Q4, Daily/2026-05-01. No fixture change needed for tag or wikilink completion cases.
- Showing the composer: the route focuses its textarea on mount (`+page.svelte:175`). A summon is simulated with `window.__e2e.events.emit('qc:open-composer', '')` (`QC_OPEN_COMPOSER`, `events.ts:24`/`:54`), which runs `resetForShow` (`+page.svelte:146-159`). Typed text persists to `localStorage` key `kokobrain:composer-draft` (`+page.svelte:12`, `:34`, `:46-53`); Playwright gives each test a fresh context, so drafts do not leak between tests.
- Save flow in E2E: `Meta+Enter` or `Control+Enter` triggers `handleSave` (`+page.svelte:167-170`). `submit_composer_capture` is a no-op in the mock (`tauri-core.ts:560`), so `waitForResult` ends unconfirmed after 3 s (`RESULT_TIMEOUT_MS`, `+page.svelte:10`) unless the spec emits `qc:composer-capture-result` with the matching `requestId`. The `requestId` is a `crypto.randomUUID()` the spec cannot see, because nothing records `invoke` args. To assert "the submitted text contained `[[Welcome]]`", the mock needs a recorder (e.g. push `args` into a `window.__e2e` array in `handleQuickCaptureNoop`-style handler for `submit_composer_capture`, and an auto-reply emit). That is a small, test-infra-only change under `e2e/mocks/` (allowed by the owner's constraint, which only forbids editor behavior changes), but it is scope the owner may not want; the autocomplete cases (tooltip visible, filtered, accept inserts text) do not need it.
- Viewport: Playwright default is 1280x720. The real window is 600x240 (`src-tauri/src/lib.rs:131-143`, `.inner_size(600.0, 240.0)`). A spec that cares about the tooltip fitting should call `page.setViewportSize({ width: 600, height: 240 })`.

## 4. Existing editor completion E2E (mirror candidates)

- `e2e/specs/wikilink-completion.spec.ts` (50 lines) has three tests: `[[` opens `.cm-tooltip-autocomplete` with a `.cm-completionLabel` (lines 5-17); `[[Wel` narrows to a label matching `/Welcome/i` (19-29); `[[Welc` + `Enter` inserts and `.cm-content` contains `Welcome` (31-49). It drives the real editor through `vaultPage` + `openFile(page, 'Inbox.md')` (helpers `e2e/fixtures/helpers.ts:82-90`). These map one-to-one to composer cases if the composer renders a CodeMirror tooltip with the same classes.
- There is NO tag-completion E2E: `grep` for `cm-tooltip-autocomplete|completionLabel` finds only `wikilink-completion.spec.ts`. The tag source (`extensions/tag/completion.ts`) is only unit tested. A composer spec for `#pl` -> `plan` would be new, but the fixture data for it exists (see section 3). Because tag labels are `type: 'keyword'`, `filter: false` (`tag/completion.ts:43-46`), the spec should assert on `.cm-completionLabel` text for `plan` and `project`.
- Selectors the composer spec can reuse if CodeMirror is the implementation: `.cm-tooltip-autocomplete`, `.cm-completionLabel`, `.cm-content`. If the composer instead builds its own dropdown on the textarea, there is no E2E precedent and new `data-*` hooks are needed.
- Editor wiring for reference (not E2E): one `autocompletion({override:[wikilinkCompletionSource, dateShortcutCompletionSource, tagCompletionSource]})` at `src/lib/core/markdown-editor/setup/editor-extensions.ts:142-143`. Data through `appEditorHost` (`src/lib/app/editor-host.ts:123-198`): `listLinkCandidates` reads `fsStore.fileTree` via `treeLinkIndex()` (`:76-85`, main-window store) plus `get_all_vault_entries_v2`; `listTags` calls `get_all_tags_v2` keyed by `vaultStore.path` and `vaultIndexVersion` (`:100-110`). Both stores exist only in the main window, which is the core cost for the composer, and relevant to E2E because the composer spec would exercise whichever IPC the new host uses.

## 5. Reuse opportunities for the test

- Spec skeleton: copy `wikilink-completion.spec.ts` assertions; replace `vaultPage` + `openFile` with the composer setup above.
- Data: `TEST_FILES`/`TEST_VAULT_PATH` exports from `e2e/fixtures/test-vault.ts:21,126`; `vaultFiles` option (`:173`) if a case needs extra notes.
- Base `test` from `console-guard.ts` gives free detection of any composer IPC that lacks a mock handler.
- If the composer uses only existing commands (`get_all_tags_v2`, `get_all_vault_entries_v2`, `scan_vault`), no mock change is needed. If it adds a new command, `tauri-core.ts` needs a handler (forced by the exhaustive `Handlers` type, `:470`), plus `COMMAND_ARGS` and Rust entries (`src/tests/lib/contracts/ipc-parity.test.ts` checks parity with `generate_handler!`).

## 6. Risks and gaps E2E cannot cover (browser mock vs real Tauri)

1. Cross-webview data path. E2E has one page with its own `virtualFS`; it will happily pass with data seeded in the composer page even if, in the real app, the composer webview's IPC cannot see the vault. The mock does not model `vaultStore.path`, per-window capabilities, or which Rust state the composer's `invoke` reaches. UNVERIFIED in real Tauri: whether the composer window (capability `src-tauri/capabilities/composer.json`: `core:default`, `core:window:allow-hide`, `core:window:allow-set-focus`) may call app commands such as `get_all_tags_v2`. `src-tauri/build.rs` has no `AppManifest`/command restriction (lines 1-40 read), which suggests app commands are not per-capability gated, but this was not confirmed against Tauri docs. The composer.json description says "no other IPC", so a doc/comment update may be expected. Needs a manual run in the packaged app; E2E cannot prove it.
2. Vault path in the composer. `resolveLink`/`createNote` and `treeLinkIndex` need `vaultStore.path`/file tree; the composer has neither (ADR 0028 line 47 and 63). Whatever the composer uses to enumerate notes in production (Rust IPC) is mocked in E2E from the seeded `virtualFS`, so a wrong production source would not fail E2E.
3. Window clipping. Real window is 600x240 and `html, body { overflow: hidden; height: 100% }` (`+page.svelte:223-229`). CodeMirror tooltips default to `position: fixed` with `tooltipSpace` = `documentElement.clientHeight` (`node_modules/@codemirror/view/dist/index.js:10403`, `:10395-10398`), so they are limited by the window, not by the overflow rule. With a short window the popup can be tiny or flip above. A spec with `setViewportSize(600,240)` can assert the tooltip bounding box stays inside the viewport. The transparent, frameless macOS webview is not reproduced.
4. Esc and Mod+Enter propagation. The composer handles keys on `<svelte:window on:keydown>` (`+page.svelte:202`) and does not check `defaultPrevented` (`onKeyDown` `:161-171`). In CodeMirror, `closeCompletion` is bound to Escape (`node_modules/@codemirror/autocomplete/dist/index.js:2067`) with no `stopPropagation` (view only stops propagation when a binding sets it, `view/dist/index.js:9262-9275`), so with a CM-based composer, Esc to close the popup would also reach the window handler and dismiss the whole composer. Likewise `defaultKeymap` binds `Mod-Enter` to `insertBlankLine` (`node_modules/@codemirror/commands/dist/index.js:1806`), which would insert a blank line and still bubble to `handleSave`. This only applies if the textarea is swapped for CodeMirror; it is testable in E2E (press Escape with the tooltip open, assert the `dismiss_composer` effect), but requires the invoke recorder from section 3. This is the highest-value E2E case after the happy path.
5. Tab/Enter accept behavior of a textarea-based dropdown is not covered by any precedent; the editor spec only presses `Enter`.
6. The save round trip (composer -> Rust -> main window `handleDetectedCapture` -> `qc:composer-capture-result`) spans two webviews and cannot run in one Playwright page. The existing `e2e/specs/deep-link.spec.ts` covers the capture writer on the main page. Do not expect an E2E that goes from composer text to a written note.
7. Dev server only. E2E runs `vite dev`; `pnpm build` (adapter-static with `fallback: index.html`, `vite.config.js:80-82`) is not exercised by E2E but is what Tauri serves at `WebviewUrl::App("/composer")`. CI `pnpm build` covers prerender failures (`CLAUDE.md` rule 6).
8. Timing: CM `autocompletion` defaults (activateOnTyping, debounce) behave the same in the composer. The editor spec waits `toBeVisible({ timeout: 3_000 })`; reuse that margin because the tag source awaits an IPC promise (`tag/completion.ts:25-31`).
9. Parallelism: `fullyParallel` with 4 workers; the composer draft key uses per-context `localStorage`, so no cross-test leakage. The first-load of `/composer` on a cold dev server may take longer than `/` because Vite transforms `@codemirror/*` for this route (UNVERIFIED; the main page already imports them).

## 7. Open questions

- Which implementation will the composer use (CodeMirror vs a textarea overlay)? Decides which selectors, which Esc/Mod+Enter issues, and whether the editor spec can be mirrored literally.
- Which IPC will feed the composer (existing `get_all_tags_v2` / `get_all_vault_entries_v2`, or a new command)? A new command adds work in `commands.ts`, `COMMAND_ARGS`, Rust, ts-rs bindings, `tauri-core.ts` HANDLERS, and (if needed) `composer.json`.
- Is adding a recorder for `submit_composer_capture` args to `e2e/mocks/tauri-core.ts` acceptable? It is not an editor file, but it is beyond a pure completion test. Without it the Esc/dismiss and "submitted text" assertions are not possible (the unit test `src/tests/routes/composer-page.test.ts` can cover them instead, with `call` mocked).
- Is the packaged-app behavior (capability, vault path) to be verified manually? E2E cannot.
