## Verdict summary

The three reports are accurate on the core facts. Most line references check out. The errors are a few wrong line numbers, one misleading bundle claim, one overstated "no test" claim, and gaps in the headless-reuse plan (Option A in scout 01). Those gaps matter for the design.

## Refuted or corrected claims

1. **Scout 01 §1.3 / §4.4: the `.view` filter is at `src/lib/app/editor-host.ts:72`.** Wrong line. Line 72 is a doc comment. The filter `flattenFileTree(tree).filter((f) => isLinkTargetFile(f.path))` is at `src/lib/app/editor-host.ts:80`. The scout also misses that the notes get the same filter: `(await getVaultEntries()).filter((e) => isLinkTargetFile(e.path))` at line 131.
2. **Scout 01 §4.2: "only `@codemirror/state` is needed at runtime".** Misleading. The `import type` lines are type-only (`wikilink/completion.ts:1`, `tag/completion.ts:1`). But to call a source, the composer has to pass a `CompletionContext`, and the real class is a runtime export of `@codemirror/autocomplete` (`node_modules/@codemirror/autocomplete/dist/index.js:2125`). There are two ways to do it. One is to ship autocomplete at runtime. The other is to pass a cast object `{ state, pos, explicit }`, as `src/tests/lib/app/lifecycle/app-lifecycle.service.test.ts:1137-1146` does. That cast is fragile, and the scouts call it fragile themselves.
3. **Scout 01 §4.2: "On accept, call `option.apply(shimView, ...)`".** Incomplete. Tag options have no `apply` (`tag/completion.ts:38`). CodeMirror applies them through `applyCompletion` (`autocomplete/dist/index.js:1053-1066`), which reads `view.state.field(completionState)` and calls `insertCompletionText(view.state, ...)` (lines 188-204). A textarea shim cannot run that path. It has to do the default "replace `from..to` with `label`" itself for tags. That is a few lines, but it is new code, and it sits next to the reused wikilink `apply` closures.
4. **Scout 17 §1: "Nothing asserts the wikilink `apply()` behavior".** True only at unit level. `e2e/specs/wikilink-completion.spec.ts:31-48` accepts a suggestion with Enter in the real editor. It asserts only that `Welcome` is rendered, not the `]]` rule or the alias form.
5. **Scout 17 §4: `<svelte:window on:keydown>` at `+page.svelte:~185`.** Wrong line. It is at `src/routes/composer/+page.svelte:202`. The focus line `~158` is correct (line 158).
6. **Scout 17 §6.1: "About 20 call sites use `textarea().value`".** The scout lists 13 sites, and 13 is the right count (`composer-page.test.ts:199, 213, 234, 254, 256, 267, 277, 309, 372, 419, 429, 438, 457`).
7. **Scout 17 §6.7 / §8 and scout 02 §7.8: the layer rules on `src/routes` are left UNVERIFIED.** Now resolved. `scanLib` walks only `LIB = 'src/lib'` (`scripts/import-graph.mjs:29, 249-255`). So neither `layer-rules.test.ts` nor `markdown-editor-imports.test.ts` sees a route importing editor internals. `raw-invoke.test.ts:11` and `event-listen.test.ts:13` do scan `src/routes`, so any new composer IPC must go through `call()` / `on()` from `#lib/contracts/ipc.js`.
8. **Scout 02 §2: per-keystroke re-query is marked "Not verified in source".** Now VERIFIED. `ActiveResult.updateFor` (`autocomplete/dist/index.js:1004-1022`) keeps a result only when `checkValid(result.validFor, ...)` passes, and `checkValid` returns false without `validFor` (lines 1036-1038). Neither source sets `update`, so the state goes back to Pending and the source re-runs on every typed character.
9. Minor: scout 02 cites `fuzzy-match.ts:8-38`, but the function ends at line 41. Scout 02 also calls the length term a "shorter-name bonus". It is a length penalty (`score += target.length - query.length`, line 38), which ranks the same way.

## Gaps the scouts missed

1. **`resolveLink` is synchronous** (`editor-host.ts:46`). A composer host cannot do a sync IPC. Heading and block-id modes (`[[Note#`) need two things in the composer. First, a preloaded list of file paths with a resolution index built by the pure `buildResolutionCache` / `resolveWikilinkCached` (`core/filesystem/wikilink-resolution.logic.ts:109, 128`) plus the vault root. Second, a `readNote` that works. The capability rules out filesystem access, so that means either a new command or relaxing the capability. Without both, `NOOP_HOST.resolveLink` returns null and those modes go silent (`completion.ts:16-17`). Scout 17 §7 notices the silent result but not the sync constraint.
2. **The `boost` value on aliases has no effect in the editor.** With `filter: false`, CodeMirror ignores `boost` and scores each option `1e9 - index` (`autocomplete/dist/index.js:787-790`). The editor therefore lists the options in array order: files (fuzzy-ranked), then aliases in note order. If a custom composer dropdown sorted by `boost`, it would differ from the editor. CM also drops an option whose label, detail, type, apply and boost all match the previous one (lines 826-831). The wikilink closures are distinct, so this never fires for them.
3. **The wikilink source does not catch a rejection from `listLinkCandidates`** (`completion.ts:68`). Inside CodeMirror the library logs it. A headless shim has to catch it itself, or an IPC failure becomes an unhandled rejection. Scout 17 §6.3 sees this only through the test mock.
4. **Async ordering in a headless shim.** CM discards stale async results itself (the `running` queries, `autocomplete/dist/index.js:1181-1196`). A textarea shim that re-runs the source on every `input` must drop results that resolve out of order. Scout 01 notes the stale `state` captured by `apply`, but not the race between in-flight queries.
5. **The look of the dropdown lives in the editor theme.** The autocomplete tooltip CSS is in `buildEditorTheme` (`setup/editor-theme.ts:69-78`, tested in `editor-theme.test.ts:105-121`). A CodeMirror swap has to import `buildEditorTheme` to match it (reuse, zero edits). A custom dropdown has to copy the styles.
6. **Render cap.** The editor renders at most `maxRenderedOptions: 100` (`autocomplete/dist/index.js:383`). The sources themselves are uncapped, as scout 01 says. A custom dropdown needs its own cap.
7. **Where the file list comes from.** The app's `files` come from `fsStore.fileTree` (`app/editor-host.ts:77-80`), so they include attachments. `get_all_vault_entries_v2` feeds only `notes`. Whether it includes non-markdown files is UNVERIFIED, so for parity on attachments the composer may need the scanned tree, not the vault entries. This is detail for scout 04/06.
8. **Placement of a composer host.** `markdown-editor-imports.test.ts:15-23` bans stores, services, Tauri, features and plugins in `src/lib/core/markdown-editor/*.ts`, and its doc (lines 5-9) says the editor reaches the app only through the facet. A composer `EditorHost` that calls IPC should therefore live outside the editor folder (for example `plugins/quick-capture/` or the route). That also follows the constraint of zero editor edits.
9. **Test-mock interplay, scout 17.** If the composer calls IPC for tags or link candidates on mount or at summon, the exact-list `commands()` asserts break (`composer-page.test.ts:201, 214, 224, 355, 373`). A lazy fetch on the first `#` or `[[` avoids this, and it also matches the app's laziness (`listLinkCandidates(false)` returns no notes, `app/editor-host.ts:131`).

## Feasibility conclusions (validated)

- Reusing both real sources with zero editor edits is feasible. It works through a CodeMirror state, either inside a CodeMirror view or headless over the textarea. The direct-call tests prove both sources run with only `editorHost.of(host)` and no language (`tag/completion.test.ts:29-37`, `editor-host.test.ts:219-254`).
- Headless over the textarea, beyond what scout 01 lists, the composer must still write: default insertion for tags, rejection handling, stale-result dropping, keyboard handling, a dropdown and a sync `resolveLink`.
- With a CodeMirror swap, CM supplies apply, ordering, races and the keymap, but the textarea-bound draft, focus and test helpers have to be rewired, and the Escape collision has to be handled in the page.
