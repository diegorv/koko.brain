# Scout 10: theme and tooltip rendering for composer autocomplete

Scope: how the editor styles the completion tooltip, which CSS variables the composer webview has, and whether the CodeMirror tooltip renders correctly inside the 600x240 transparent frameless composer window. Read-only research. Library versions read from node_modules: `@codemirror/view` 6.43.15, `@codemirror/autocomplete` 6.20.4 (package.json line 3 of each).

Bottom line: styling and tooltip placement are NOT blockers. A CodeMirror instance in the composer picks up the app theme through the same CSS variables the editor tooltip already uses, and CodeMirror's default fixed positioning works in a 240px viewport (it flips above/below and shrinks the list). The only reuse problem is that the tooltip CSS lives inside `buildEditorTheme`, which also styles the whole editor surface (see Reuse).

## 1. How the editor styles the completion tooltip

- All tooltip styling is one `EditorView.theme(...)` call inside `buildEditorTheme` in `src/lib/core/markdown-editor/setup/editor-theme.ts:12-93`. There is no global CSS for it: grep for `cm-tooltip` over `src/` finds only `editor-theme.ts` and its test; `src/app.css` has no `cm-` selectors (grep of `cm-` found only `@layer base` at app.css:484, unrelated).
- `.cm-tooltip` (editor-theme.ts:69-75): `background var(--popover)`, `color var(--popover-foreground)`, `1px solid var(--border)`, `border-radius var(--radius-md)`, `box-shadow var(--shadow-md)`.
- `.cm-tooltip.cm-tooltip-autocomplete` (editor-theme.ts:76-89, selector deliberately equal to the autocomplete base theme selector so it beats `padding: 0`, see autocomplete index.js:1310-1313): list `padding 4px`, rows `border-radius var(--radius-sm)`, selected row `background var(--accent)` and `color var(--accent-foreground)`.
- Everything else comes from the CodeMirror base themes and is not overridden by the app: list font is `monospace`, `max-height 10em`, `min-width 250px`, `max-width min(700px, 95vw)`, row padding `1px 3px`, line-height 1.2 (autocomplete index.js:1309-1338); `overflow hidden auto` on the `ul` so it scrolls. Icons come from `.cm-completionIcon-*` base rules (index.js:1390+, `keyword` at 1423-1425; the tag source uses `type: 'keyword'`, tag/completion.ts:38; wikilink uses `type: 'file'`, wikilink/completion.ts:73). I did not read whether a `file` icon rule exists: UNVERIFIED.
- The `dark` flag passed as the second arg of `EditorView.theme` (editor-theme.ts:91) selects the CodeMirror light/dark base theme for any rule the app theme does not override (selected row base colors, etc.).
- Tests that pin this: `src/tests/lib/core/markdown-editor/setup/editor-theme.test.ts:103-125` (tooltip chrome, list padding selector, selected row accent). These test `buildEditorTheme`'s output, so any reuse that leaves that function untouched keeps them green.
- No `tooltips({...})` config anywhere in the repo (grep `tooltips(` over `src/` returned nothing), so the editor uses CodeMirror defaults. Autocompletion config is just `override: [...]` plus `activateOnTyping: true` (editor-extensions.ts:142-145); `aboveCursor`, `tooltipClass`, `closeOnBlur` all default (autocomplete index.js:382-401: `closeOnBlur: true`, `tooltipClass: () => ""`, `aboveCursor: false`).
- The editor theme is applied through a compartment and rebuilt when settings or `appliedThemeStore.isDark` change (MarkdownEditor.svelte:702-715; initial value via `createExtensions`, editor-extensions.ts:169).

## 2. CSS variables available in the composer webview

- The composer route is wrapped by `src/routes/+layout.svelte:2`, which imports `../app.css`, so the composer has the full stylesheet: `:root` defaults (app.css:155-210, e.g. `--popover` 160, `--popover-foreground` 161, `--accent` 168, `--accent-foreground` 169, `--border` 172, `--radius` 210) and the `.dark` block (215+).
- `--radius-xs..xl` and `--shadow-xs..xl` are declared with `@theme static`, specifically so CodeMirror themes can use `var(--radius-md)` and `var(--shadow-md)` (app.css:105-130). `--elev-*` fallbacks exist on `:root` (app.css:205-209, dark 279), so `--shadow-md` resolves even before a theme is applied.
- `applyStoredTheme()` (theme.service.ts:54-68) reads `kokobrain:theme-vars` from localStorage and sets every `--*` string var on `document.documentElement` (setRootVars, 16-21), then `applyMode` toggles `html.dark`, `color-scheme` and `appliedThemeStore.setDark` (30-37). The composer calls it in `onMount` (+page.svelte:174), on `storage` events for that key (142-144) and on every summon (`resetForShow`, 146-150).
- The mirrored var map is produced by `themeColorsToCssVars` (theme.logic.ts:60-75): every `UIColors` token (including `popover`, `popoverForeground`, `accent`, `accentForeground`, `border`, theme.types.ts:12-36) plus the derived `--elev-*` vars. The main window writes it in `applyActiveTheme` (theme.service.ts:76-87).
- Because the vars live on `<html>` and the tooltip DOM is inside the page, `var(--popover)`, `var(--border)`, `var(--accent)`, `var(--radius-md)`, `var(--shadow-md)` resolve in the composer exactly as in the main window. No new variables are needed.
- `dark` for `buildEditorTheme` can come from `appliedThemeStore.isDark`: the composer's own module instance is updated by its own `applyStoredTheme()` call (theme.service.ts:35). That store is also what the editor uses (MarkdownEditor.svelte:119, 704). Caveat: `applyMode` bumps `appliedThemeStore.revision` and sets `isDark` on every summon, so a compartment reconfigure on `isDark` change would work, but the composer currently has no CodeMirror instance to reconfigure. Not verified by running anything.
- Staleness risk (pre-existing, same for textarea today): theme changes made in the main window while the composer is hidden are picked up on the next summon via `resetForShow` (+page.svelte:146-150), so the tooltip colors follow.
- Composer root styling: `.composer-root` uses `color-mix(in srgb, var(--popover) 92%, transparent)` as background with `backdrop-filter: blur(20px)` and `border-radius: 12px` (+page.svelte:238-241). The tooltip background is the same `--popover` but fully opaque, so the tooltip separates from the panel only by its 1px `--border` and `--shadow-md` ring. Cosmetic: low contrast edge in some themes. UNVERIFIED visually (no app run allowed).

## 3. Will the tooltip render correctly in a 600x240 transparent window?

Window facts: `inner_size(600.0, 240.0)`, `decorations(false)`, `transparent(true)`, `resizable(false)`, `shadow(true)` (src-tauri/src/lib.rs:135-154). `html, body` have `overflow: hidden; height: 100%` (+page.svelte:223-229) and `.composer-root` is `100vw x 100vh` with padding 14px 16px 10px (231-237). So the webview viewport is exactly 600x240 and nothing can paint outside it.

Tooltip mechanics (read from `@codemirror/view` dist/index.js):

- Defaults when no `tooltips()` config: `position: "fixed"` (non-iOS), `parent: null`, `tooltipSpace: windowSpace` (index.js:10399-10408). `windowSpace` is `{top:0, left:0 (or gutter), right: clientWidth, bottom: documentElement.clientHeight}` (10383-10398), i.e. the whole 600x240 viewport.
- With `parent: null` the tooltip is appended inside `view.dom` (the `.cm-editor` element) (10440-10450, 10506). It is `position: fixed`, so it is not clipped by the editor's or `.composer-root`'s box. The root has no `overflow` set.
- Horizontal: left is clamped into `[space.left, space.right - width]` (10600-10603). Autocomplete list `max-width: min(700px, 95vw)` = 570px max at 600px wide, `min-width: 250px`. So it always fits horizontally.
- Vertical: starts below the caret (`aboveCursor` false); if it does not fit below it flips above when more room is there (10604-10609). If neither side fits fully and the tooltip does not set `resize: false`, CodeMirror sets an explicit `height` equal to the available space (10610-10618); the autocomplete `ul` has `height: 100%` and `overflow: hidden auto` so it becomes a scrollable list. I found no `resize` property in `@codemirror/autocomplete` dist (grep returned none), so the default (resizable) applies. If available space is smaller than `defaultLineHeight`, the tooltip is hidden (10612-10615).
- Rough numbers (my estimate, UNVERIFIED by measurement): list is capped at 10em of the inherited font size plus 4px padding on each side and a 1px border, roughly 170px at 16px font; the textarea area is about 197px tall (240 minus 14 top padding, 10 bottom padding, hint row about 19px). A full 170px list fits below the caret only on roughly the first 2 lines and above it only from around line 9; on lines in between CodeMirror shows the larger side with a shortened scrollable list (about 4 to 6 rows). Usable, not clipped.
- Hidden-by-visibility rule: a tooltip is hidden if its anchor position lies outside the editor's `scrollDOM` rect or the tooltip space (10589-10595). With a long note the caret stays in view because CodeMirror scrolls it, so no issue.
- Info side panel (`.cm-completionInfo`, positioned in `CompletionTooltip.positioned`, autocomplete index.js:591+): only created for options with an `info` field. The wikilink and tag completion sources set no `info` (grep for `info` in both completion.ts files: none), so no side panel to fit in 600px.
- backdrop-filter ancestor: `.composer-root` has `backdrop-filter: blur(20px)` (+page.svelte:239-240), and a `backdrop-filter` ancestor can become the containing block for `position: fixed` descendants in engines that follow the Filter Effects spec. Whether WKWebView does this: UNVERIFIED. It is harmless here for two reasons: (1) CodeMirror detects a non-body offsetParent (non-Safari, index.js:10537-10541) or uses a kludge on Safari (10530-10536) and switches to absolute coordinates relative to `view.dom` (10575-10582, 10628-10631); (2) `.composer-root` sits at (0,0) filling the viewport with body `overflow: hidden`, so root-relative and viewport-relative coordinates are numerically identical even if the Safari kludge (which only compares against the -10000 offset) does not trigger. Risk only appears if someone later offsets or scrolls `.composer-root`.
- Rounded corners and shadow: the tooltip is rectangular and opaque and can overlap the 12px rounded corner region of the transparent window only if it reaches the window edges; horizontal position follows the caret (at least the 16px left padding), so a corner overlap is unlikely but possible at the bottom edge when shrunk to fit. `--shadow-md` (4px/12px blur) is clipped by the window edge when the tooltip touches it. Cosmetic only.
- `body { user-select: none }` (app.css:493-499): the editor re-enables selection on `.cm-content` (editor-theme.ts:40). The tooltip rows do not need selection. Not an issue for tooltips; relevant only for a future CodeMirror content element, owned by another scout.

Conclusion: no `tooltips()` configuration is needed. Keep defaults so behavior matches the editor.

## 4. Reuse opportunities

1. Call `buildEditorTheme(fontFamily, fontSize, lineHeight, contentWidth, paragraphSpacing, dark)` from the composer unchanged (it is exported via `setup/index.ts:1` and has 3 existing callers). It gives the identical tooltip chrome with zero edits to editor files. Cost: it also applies editor surface rules that the composer would have to neutralize or accept: `&` background `var(--editor-bg)` and `height: 100%` (editor-theme.ts:22-27), `.cm-content` padding `16px clamp(24px, 5vw, 80px)` (37-46), `.cm-scroller` font family and size (31-36), `.cm-activeLine` background (55-57), `.cm-gutters` colors (61-65). Passing `contentWidth 0` and `paragraphSpacing 0` removes max-width and line padding. The editor padding and background would need a second composer-specific `EditorView.theme` to override. Which of two themes wins when both define the same selector at equal specificity: UNVERIFIED (style-mod mount order not traced).
2. Alternative without touching editor files: a small composer-local `EditorView.theme` that repeats the `.cm-tooltip` and `.cm-tooltip.cm-tooltip-autocomplete` rules. This duplicates about 20 lines and drifts if the editor's tooltip style changes, which conflicts with the owner's reuse constraint, but it is the least invasive for editor behavior.
3. A strict refactor would extract the tooltip rules (editor-theme.ts:69-89) into an exported `tooltipTheme(dark)` used by `buildEditorTheme`. Output would be byte-identical, but it edits an editor file. The owner prefers zero edits to editor files, so this is a fallback only if option 1 proves too noisy; the existing test (editor-theme.test.ts:103-125) would still cover it through `buildEditorTheme`.
4. `dark` source: `appliedThemeStore.isDark` (applied-theme.store.svelte.ts:16), already maintained by `applyStoredTheme` in the composer.
5. The composer's `layer rules` (CLAUDE.md layer table): importing `#lib/core/markdown-editor/setup` from `routes/composer` is a route importing core, which is allowed; checking the architecture baseline test is another scout's topic.

## 5. Risks

- Font mismatch: the tooltip list inherits font size from `.cm-editor` ancestors (the editor sets font size only on `.cm-scroller`, editor-theme.ts:31-36), so in both editor and composer it is the page's inherited size in monospace (list `fontFamily: monospace`, autocomplete index.js:1312). The composer text is 14px sans (+page.svelte:256-258). Identical to editor behavior; just visually different from the composer text. The actual inherited size is UNVERIFIED (body has no explicit font-size at app.css:493-499).
- Short windows lose rows: on lines 3 to 8 of the textarea the list is shortened to what fits and scrolls. Acceptable, but a long wikilink result list will show about 4 to 6 rows there.
- Same-color tooltip over `--popover` panel gives low edge contrast in some themes (see section 2).
- `closeOnBlur: true` (default) closes the list on editor blur. If the composer window loses focus (summon/dismiss), the list closes, which is desired.
- Out of my topic but noticed: the composer binds Esc and Cmd+Enter on `<svelte:window on:keydown>` (+page.svelte:161-171, 202). When a CodeMirror completion list is open, `Escape` is handled by `completionKeymap` first, but the window listener would still see the event if CodeMirror does not stop propagation, which would dismiss the whole composer instead of just the list. Whether CodeMirror's key handling calls `stopPropagation`: UNVERIFIED (not read). Flag to the keyboard-focused scout.
