## Findings

1. **major** `src/lib/core/layout/AppShell.svelte:126-140`: the once-per-vault-open stale-pick check is keyed on `vaultStore.path` plus `entriesVersion > 0`, and neither is scoped to the vault being opened.
   - Scenario A, the check is skipped. On a switch from vault A to vault B in the rail shell, `vaultStore.open(B)` sets the path synchronously. The effect then runs in the same flush, while `typeDefinitionsStore` still holds A's entries (`entriesVersion > 0`; `typeDefinitionsStore.reset()` only runs in `teardownVault`, after `initializeVault` awaits `saveAllDirtyTabs`). `settingsStore` still holds A's layout. So it checks A's pick against A's rows and sets `typesPickCheckedFor = B`. B's own saved pick is never checked: a type deleted in B shows as an empty list under its stale label until the next restart.
   - Scenario B, a wrong fallback. `app-lifecycle.service.ts:329-333` documents that a tail `vault-index-updated` from the old vault can refill the type-definitions store after teardown. In that window the check can run B's valid pick against A's rows, clear it and send the rail to Inbox.
   - Fix: arm the check only once THIS vault's index is ready. Run it on the first entries snapshot whose version is above the one recorded when `vaultStore.indexReady` turned true, or reset `typesPickCheckedFor` whenever `entriesVersion` returns to 0 and also require `vaultStore.indexReady`. Add a regression test, for example by extracting the gate into a small pure function in `lens.logic.ts` and testing it. The discovery already flags this effect as E2E-only.
2. **minor** `src/lib/features/rail-shell/lens.logic.ts:182-193` and `TypesNavigator.svelte`: a type deleted mid-session leaves the pick in place. The note list keeps the deleted type's label with an empty list, and no row is highlighted until the next vault open. This was chosen on purpose (to avoid bouncing during the throttle window) and is recoverable, but the criterion reads "a type that no longer exists falls back". Accept it as a documented default, or also run the fix once a later snapshot confirms the type is gone, for example when the pick is missing from two consecutive snapshots after the refresh that follows the change.
3. **minor** `src/lib/features/rail-shell/lens.logic.ts:188-190`: the Untyped row shows even at 0 notes. The classic sidebar shows it only when `untypedCount > 0 && showUntypedNotes` (`TypeSidebar.svelte:296`). This is a documented default and the Issue's wording allows it, but it differs from the classic list the PRD mirrors. The owner should confirm.
4. **minor** `e2e/specs/rail-shell.spec.ts:361-385`: "its size persists" is checked only on the write side: the saved `navigatorSize` grows. No test restarts and asserts that the pane opens at the saved size, so a regression in `defaultSize={settingsStore.layout.navigatorSize}` would pass. Fix: after the drag, restart with the saved settings and compare the navigator width with the width before the restart.
5. **nit** `src/tests/lib/features/rail-shell/TypesNavigator.test.ts:180-218`: the menu tests ("New Project", "Open type definition", "Reveal in Finder", "Create type definition", Rename) assert only `toHaveBeenCalledWith` on mocked services. That is acceptable for service seams, but TESTING.md discourages call assertions as the only check. The menu label assertions partly offset it.
6. **nit** `src/lib/features/rail-shell/TypesNavigator.svelte:99`: the New type button's hover pair (`hover:bg-file-explorer-accent hover:text-tab-text-active` on the tab-bar header) is not in `READABILITY_PAIRS`. The New here button already uses the same pair. Pin it, or note it in the theme follow-up.

## Resolution

1. **Fixed** in `d94d631c`. The gate is now the pure `stepTypesPickCheck` (`lens.logic.ts:242-280`), used by the AppShell effect (`AppShell.svelte:126-143`). It re-arms on every path change and only after it sees the vault's index not ready (`initializeVault` calls `vaultStore.resetIndexReady()` at entry, `app-lifecycle.service.ts:140`, and readiness stays suppressed until `markIndexReady()` at :316). It records `entriesVersion` when `indexReady` turns true and runs once on the first snapshot above it. So A's entries still in the store (scenario A) and a tail refresh from A after teardown (scenario B, which also lands before ready or is the snapshot already there at ready) never trigger it. A due check waits while the classic shell is on (its rows are empty) and runs when the rail shell comes on. Regression tests in `lens.logic.test.ts:366-473` cover first open, once per open, no vault, the switch, the tail refresh, the disabled shell and a reopen. The E2E fallback test still passes. Known limit: if the post-scan refresh (2 s after `scan_vault_v2`'s event) lands before `markIndexReady`, the check waits for the next snapshot instead of using that one.
2. **Rejected, kept as the documented default** (discovery "Defaults taken"). The criterion "a type that no longer exists falls back" is met on the next vault open (`staleTypesPickFix` tests, E2E "a saved type that no longer exists falls back"). Mid-session the state is visible and recoverable: one click on any row or rail item. A "missing from two consecutive snapshots" rule adds state tied to the throttled refresh timing (`tauri-listeners.service.ts:84-87`) for a rare case; the owner can ask for it.
3. **No change; owner to confirm.** The Issue text says "then Untyped when `showUntypedNotes` is on", with no count condition, and the discovery records the default. Hiding it at 0 would be a one-line change in `typeNavigatorRows` (`lens.logic.ts:190`) if the owner wants the classic rule.
4. **Fixed** in `50729edf`. The E2E now restarts with the saved settings after the drag and asserts the navigator opens within 3 px of the resized width (`e2e/specs/rail-shell.spec.ts:387-392`). A pane that ignored the saved size would open at the 18 % starting width, more than 60 px narrower.
5. **Fixed** in `708084e4`. Each menu-action test also asserts the menu is closed after the click. The mocked services are side-effect seams that TESTING.md allows mocking. The rename test keeps its rendered "This will update 2 notes" assertion. The dialog's closed state is not asserted because it does not leave the jsdom DOM after a submit.
6. **Rejected, deferred** (same as Issue 08, `work/08/review-2.md:37`). Adding `['ui', 'tabTextActive', 'ui', 'fileExplorerAccent', 4.5]` to `READABILITY_PAIRS` is not test-only: `withReadableContrast` (`theme-builder.logic.ts:147-163`) moves every failing foreground in the list, so in a custom theme it would recolour `tabTextActive` across the whole tab bar.
