## Findings

1. **major**, `src/lib/utils/note-date.ts:24`. `parseDateKey` gives a day to values that are not dates instead of letting them fall through. `dayjs(value)` falls back to V8's lenient `Date` parsing and rolls invalid days forward. So `date: 2026-02-30` files the note on 2026-03-02, `date: Meeting 12` on 2001-12-01, `date: tbd 2026` on 2026-01-01 and `date: 2026` (a YAML number) on 1969-12-31 in UTC-3, even when the note has a valid `created`. Before this branch `date` was ignored, so these notes now land on wrong days. The same `date` key also diverges from the Calendar tab: `isValidDayKey` (`event-calendar-dates.logic.ts:76-78`) rejects `2026-02-30` and non-strings as "not-a-day", while the sidebar calendar shows a dot for them. A falsy `created: 0` also changed: the old scan skipped it (`if (created)`), but now it lands on 1969-12-31. Fix: make the string path strict. Require a leading `YYYY-MM-DD` that round-trips (the same check as `isValidDayKey`, rewritten in `utils/` because `utils/` cannot import `features/`), optionally followed by a time part, and return null for anything else. Either drop bare numbers, or accept them only when they look like a ms timestamp. Add the probe values above to `note-date.test.ts` as fall-through cases. Before tightening, check whether real imported `created` values use other formats (for example `March 5, 2024`). If they do, decide on them on purpose instead of dropping them silently.
2. **nit**, `src/lib/plugins/calendar/calendar.service.ts:84`. Disk times only come from the last full scan. A note created (or renamed or moved: forget plus upsert) after the scan with no frontmatter `date` / `created` gets `diskCreatedAt: null` and stays off the calendar until the next scan. The old `fileFilesystemKeys` had the same gap, so this is not a regression. It matters once the Day and Today lenses reuse this rule with live data. Fix: none in this Issue. Note it for the lens Issue.

## Resolution

1. **major, fixed in `149b657a`.** `parseDateKey` (`src/lib/utils/note-date.ts:17-41`) now takes a string only when it is `YYYY-MM-DD` with a day that exists (checked by a local `Date` round-trip, the same check `isValidDayKey` makes), optionally followed by a `T`/space `HH:mm[:ss[.SSS]]` time and a `Z`/`+-HH:mm` offset. Without an offset the written day is the key. With an offset, it is the local day of that instant. Numbers are no longer frontmatter dates, so `2026` and `created: 0` fall through. The disk time is read as ms directly in `noteDateKey`. Valid Date objects are still accepted. Fall-through tests in `src/tests/lib/utils/note-date.test.ts` cover every probe value (`2026-02-30`, `2026-13-01`, `Meeting 12`, `tbd 2026`, `Oct 27`, `2026-10-27T25:00`, numeric `2026`, `created: 0`), along with `March 5, 2024` and `2026-10-27 notes`. They pass under `TZ=America/Sao_Paulo` and `TZ=Asia/Tokyo`. Formats checked before tightening: the app's own writers produce `YYYY-MM-DDTHH:mm:ss` (`note-composer.logic.ts:59`, `one-on-one.logic.ts:52`), and the help vault uses `YYYY-MM-DD`. Both still parse. Space-separated `YYYY-MM-DD HH:mm` (a common Obsidian template output) also parses. Prose dates such as `March 5, 2024` now fall through on purpose. Accepting them would mean going back to V8's lenient parser, and the Calendar tab rejects them too.
2. **nit, no change.** As the review says, this is not a regression: disk times come only from the last full scan. Left for the Day/Today lens Issue.
