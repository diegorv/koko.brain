## Findings

1. minor — `src/lib/features/rail-shell/RailNoteList.svelte:87` — `shownLens` builds a new `todayLens(...)` object every time `nowMs` changes. That happens on every 30 s clock tick and every window focus, so `resolved` re-runs `resolveLens` over the whole vault (two `listEntries` passes with note-date parsing and sorting), and `groupedItems` and the VList data are rebuilt even when the day did not change. The probe confirmed it: two same-day ticks gave two extra resolves. Fix: derive the day key string first (`let todayKey = $derived(eventCalendarViewStore.todayKey)`), then `shownLens = $derived(isToday ? todayLens(todayKey) : lens)`. String equality then stops the chain until the day actually changes.
2. nit — `src/lib/features/rail-shell/RailNoteList.svelte:347` — a note that is both a favorite and dated today renders two `NoteRow`s with the same path. F2 or menu Rename then shows two inline inputs that share `menu.rename.input` and value. Focus goes to whichever copy mounted last (the Today group's), not to the row the user acted on, and clicking the other copy's input blurs the first one and commits early. The dual listing is a documented default and follows the prototype, so this is an edge case. Fix: accept it and note it, or render the rename input only in the first occurrence of a path.
3. nit — `src/lib/features/rail-shell/lens.logic.ts:399` with `RailNoteList.svelte:244` — New here dates the note with `dayjs()` at click time, but the list's day comes from the 30 s clock. In the up-to-30 s window after midnight, New here writes the new day while the list still shows the old one, so the created note is missing from the list until the next tick. Fix (optional): prefer `lens.target` when it is a valid day key and fall back to `ctx.now`, as the Day lens rule does.
4. nit — theme check — the new markup reuses the note list's region tokens and a test pins the header class, but nobody checked the Today list by eye in each built-in theme. Leave it to the deliver step or a human pass.

## Resolution

1. Fixed. `RailNoteList.svelte` derives the `todayKey` string first and builds `shownLens` from it, so a same-day tick or window focus stops at string equality. Test: RailNoteList "does not re-resolve the lens on a clock tick that stays on the same day" (spies on the real `typeDefinitionsStore.entries` getter; failed before the fix with 1 read, passes after).
2. Rejected (accepted as is). Listing a pinned note that is dated today in both groups is the documented default and follows the prototype; the shared rename input is a rare, visible and recoverable glitch (the rename still commits the typed name). Rendering the input only on the first occurrence adds per-path bookkeeping to the grouped list for that edge case.
3. Fixed. `newNoteRule` for Today writes the lens's day when it is a valid `YYYY-MM-DD` key and falls back to `ctx.now` (shared `todayLensDay` helper, also used by `resolveTodayLens`). Tests: lens.logic "dates the note by the lens's day when it has one" (failed before the fix) and "falls back to the creation instant when the lens day is not a valid day key".
4. Not done in this step. The deliver step runs headless and did not open the app in each built-in theme; the markup uses only the note list's existing region tokens. A human pass by eye is still open.
