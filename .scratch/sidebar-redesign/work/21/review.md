## Findings

1. minor — `src/lib/features/search/SearchPanel.svelte:22-25`: the input focuses on every mount, and in the rail shell the panel mounts on actions that are not Search requests: Cmd+2 / Cmd+Shift+B (the `railPanelsVisible` `{#if}` in `AppShell.svelte:212`), app start / vault open with a saved `railItem: "search"`, and switching the layout to Rail. In each case focus moves from the editor to the search input, so the next keystrokes go into the query. (Classic has the same thing on Cmd+Shift+B while SearchPanel is open, so this is not new behavior, but the rail mounts the panel much more often.) Fix: in rail mode focus only when there is a request the panel has not handled yet (e.g. keep the last handled `focusRequest` in the store, or a `pendingFocus` flag that `openSearch` sets and the panel clears), and keep focus-on-mount for classic.
2. minor — `help/documentation/20-keyboard-shortcuts.md`, `help/documentation/06-search-and-navigation.md`: the new "/" shortcut and the rail behavior of Cmd+Shift+F (opens and stays open, no toggle) are not documented. Issue 10 added Cmd+1/Cmd+2 to the same help page. Fix: add a `/` row ("Rail layout: open Search") and a note on Cmd+Shift+F in the Rail layout.
3. nit — `src/lib/features/search/SearchPanel.svelte:73-82`: the PRD Lenses table gives the Search lens a rule text ("the query"), and this lens has no rule line. The build's own default is that the input already shows the query. The Issue's criteria do not require one, so this is just a recorded difference from the PRD. Fix: none required; if the PRD row should hold, render the query as the rule line the way `RailNoteList.svelte:446` does.
4. nit — `src/lib/core/keybindings/global-keybindings.ts:11`: `core/` now imports one more `features/` module (`event-calendar-keys.logic.js`) to get the generic `isTypingTarget`. The file already imports several features, so this adds to an existing ADR-0003 exception. Fix (optional): move `isTypingTarget` to `utils/` in a later cleanup.
5. nit — `src/lib/core/keybindings/global-keybindings.ts:60-69`: "/" also fires while a non-input element inside a modal has focus (e.g. a switch in the Settings panel). It then changes the rail item behind the dialog, and the focus trap keeps the input from taking focus. The change is visible and easy to undo. Fix (optional): skip while a dialog is open (`[role="dialog"]` contains `e.target`).
