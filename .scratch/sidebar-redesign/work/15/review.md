## Findings

1. minor — `src/lib/features/rail-shell/FilesNavigator.svelte:280-291` — Reveal in Finder and Copy path fail silently: `revealInSystemExplorer` logs and swallows (`fs.service.ts:292-298`) and `navigator.clipboard.writeText` is not caught, so a rejection is an unhandled promise with no toast. The Issue's "Every failure tells the user with a toast" covers them, though the acceptance criteria list only rename, invalid name, delete and create, and the classic tree has the same gap. Fix: wrap both in `runOrToast` (reveal would need `revealInSystemExplorer` to rethrow, or a local try/catch around `revealItemInDir`), or record the parity decision in the Issue.
2. minor — `src/lib/features/rail-shell/files-navigator.service.ts:11-20` — the build report says this covers Issue 14's deferred gap "a picked folder deleted mid-session", but only for in-app deletes and renames (`applyPathChange`). A folder deleted or renamed outside the app reaches the watcher's deletion branch (`forgetNote`), not the path-change consumers, so the pick stays on a missing folder until the next vault open's `staleFolderPickFix`. Fix: state the scope in the Issue/ledger, or open a follow-up for watcher-side folder removals.
3. minor — `src/tests/lib/features/rail-shell/FilesNavigator.menu.test.ts` — the no-hard-coded-colors assertion (`FilesNavigator.test.ts:125`) does not cover the rename input or the portalled menu, and no one checked the menu and input by eye in the built-in themes. The tokens are the classic tree's, so the risk is low. Fix: add the same `innerHTML` regex assertion with the rename input open, and eyeball one light and one dark theme before the Issue closes.
4. minor — `src/tests/lib/features/rail-shell/FilesNavigator.menu.test.ts:397-401` — "Change icon" is tested only as "a dialog opens"; nothing asserts that picking or removing an icon reaches `setIconForPath` / `removeIconForPath` with `isDirectory: true` for the folder. Fix: select an icon in the picker (or call the `onSelect` path) and assert the resulting `fileIconsStore` state for the folder.
5. nit — `src/lib/features/rail-shell/FilesNavigator.svelte:157` — the known glitch: the consumer points the pick at the new path before `refreshTree()` has it, so the note list can be empty for one refresh after a rename. Visible, recoverable, documented in discovery.md; no change needed unless it shows in use.
6. nit — `src/lib/features/rail-shell/FilesNavigator.svelte:67-72,258` — the local `Creator` interface repeats `RailFolderCreator` minus `id`, and the `{#each}` keys on `creator.label`, so a plugin registering a label equal to a built-in one ("New note") would throw Svelte's duplicate-key error. Fix: type it `Omit<RailFolderCreator, 'id'> & { id: string }` with built-in ids and key on `id`.

## Resolution

1. Partly fixed. Copy absolute / relative path now run through `runOrToast` (`copyPath` in `FilesNavigator.svelte`), so a clipboard refusal toasts `Could not copy the path of "<name>": <reason>`; test "toasts when the clipboard refuses the path". Reveal in Finder is left as is: `revealInSystemExplorer` logs and swallows on purpose and has six callers (classic tree, note list, Types navigator, Type sidebar, file history) plus a test pinning that it resolves on error; making it rethrow is a shared-service change outside this Issue. Parity with the classic tree is the recorded decision; a follow-up can make reveal toast everywhere at once.
2. Accepted as scope, no code change. The path-change consumer follows in-app renames and deletes (`applyPathChange`) only; a folder removed or renamed outside the app goes through the watcher's `forgetNote` path, and the pick is repaired at the next vault open by `staleFolderPickFix`. Recorded in the Issue's Comments.
3. Partly fixed. Test "keeps the rename input on the region tokens, with no hard-coded colors" opens the rename input and runs the same `innerHTML` color regex. The portalled menu is the shared shadcn `context-menu` already used by the classic tree, so it carries no new styling. Not checked by eye in a light and a dark theme: this deliver step has no app window; that look stays open for the owner.
4. Fixed. Test "sets the picked icon on the folder through its folder note, then removes it" picks an icon in the real `IconPicker`, asserts `fileIconsStore.getFrontmatterIcon(folder)` and the `_icon` written to the folder note, then removes it and asserts the store entry and the frontmatter key are gone.
5. No change, as the review says.
6. Fixed. The local `Creator` interface is gone: the built-in items are `RailFolderCreator`s with `builtin:` ids and the `{#each}` keys on `id`. Test "a plugin creator labelled like a built-in one renders next to it" fails with `each_key_duplicate` on the old label key.
