## Findings

1. **minor** — `src/lib/features/properties/bookmark-migration.service.ts:61-74`: if the vault switches between two bookmarks (not during one write), the next `updateNoteFrontmatter` captures the NEW vault as its baseline, so `vault-changed` never fires: the old vault's note is written and `notifyAfterSave` / `update_note_in_index` run for a path outside the now-open vault, the old vault's bookmarks file is deleted, and the "bookmarks were removed" toast can show over the new vault. The fix report names this gap itself. Fix: at the top of each loop iteration (and before `remove` / the toasts) return when `vaultStore.path !== vaultPath`, with a test that switches the vault between two bookmarks. Rare (needs a vault switch during the first open's migration), so not blocking.
2. **nit** — `src/lib/features/properties/bookmark-migration.service.ts:64`: `startsWith(`${vaultPath}/`)` is a string-prefix check, so a stored path like `${vault}/../other/Note.md` would pass. The app always wrote absolute normalized paths, and the copied-vault case the blocker described is covered, so this is defensive only; normalizing the path first would close it.
3. **nit** — `src/lib/features/properties/bookmark-migration.service.ts:40`: the reflowed JSDoc line is much longer than its neighbours; rewrap.
