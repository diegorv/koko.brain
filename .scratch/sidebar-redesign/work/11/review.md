## Findings

1. minor — `src/lib/features/rail-shell/lens.logic.ts:21-25` vs `src/lib/features/rail-shell/Rail.svelte:37-42`, `src/lib/core/layout/AppShell.svelte:128`. The map from item key to lens now lives in two places: `Rail.svelte`'s `items` / `bottomItems` and the new `RAIL_ITEM_LENSES`. `AppShell` drops the `lens` argument that `Rail` still passes to `onSelect`. Failure: a later ticket adds a rail item to `Rail.svelte` but not to `RAIL_ITEM_LENSES`. Clicking it then saves the key, but `restoreRailItem` maps it straight to Inbox, so the click looks like it does nothing and no test fails. Fix: build `Rail.svelte`'s items from one source shared with `restoreRailItem`, or at least add a test (in `Rail.test.ts`) that every rendered `data-rail-item` key restores to itself. Then drop the unused `lens` parameter from `Rail`'s `onSelect`.
2. nit — `src/lib/core/settings/settings.types.ts:64`. `railItem` is typed `string`, but the loader passes any JSON value through unchecked: the branch's own test loads `42`. That is safe today, because the only reader, `restoreRailItem`, takes `unknown`. But a future reader that trusts the type (for example `railItem.startsWith(...)`) would throw on a hand-edited file. Fix (optional): leave as is, or add to the field's JSDoc that the value is unvalidated and must go through `restoreRailItem`.

## Resolution

1. Fixed. `Rail.svelte` items no longer carry a lens, and `onSelect` takes only the item key, so `restoreRailItem` in `lens.logic.ts` is the one key-to-lens map. `Rail.test.ts` now checks that every rendered `data-rail-item` key restores to itself with its lens, so an item added to the rail but not to `RAIL_ITEM_LENSES` fails a test. The click test asserts `onSelect` gets only the key.
2. Fixed. The `railItem` JSDoc in `settings.types.ts` says the value is loaded unvalidated and must be read through `restoreRailItem`.
