## Findings

1. **minor** `src/lib/features/rail-shell/RailNoteList.svelte:158`: after its `await`, `persistViewState` reloads the view it started on, even when the lens has moved to another view by then. `TypeNoteList.loadViewNotes` has a guard for this (`sel.path !== viewPath` returns); the rail copy lost it. I reproduced it with a throwaway component probe (since deleted). Change view A's sort while `updateViewQuery` is pending, pick view B (its rows render: `["alpha","gamma","person"]`), then let the save resolve: B's list goes blank (`[]`) and its Sort and Filter buttons disappear. That happens because A's reload takes the newest generation, re-seeds the toolbar with A's state and sets `viewLoaded.path = A`. It recovers only on the next `entriesVersion` bump (the watcher's full rebuild for the `.view` write). Fix: after the `await`, return when `viewPath !== path` (or check `path === viewPath` inside `loadView` after the generation check), and add a component test with a pending `updateViewQuery` and a lens switch.
2. **minor** `src/lib/features/rail-shell/lens.logic.ts:418`: `viewNoteType` matches only the bare `_type` / `type` properties. The engine also treats `note._type`, `note.type`, `property._type` and `property.type` as the type field (`collection/expression/evaluator.ts` `isTypeIdentifier`). Probe: `parseFilterToGroups("note._type == 'Project'")` gives the row `{property:'note._type', operator:'is', value:'Project'}`, and `viewNoteType` returns null for it. So a view that filters exactly one type through `note._type` gets a plain note from New here, which breaks the PRD rule. Fix: strip a leading `note.` / `property.` before the key check, and add a logic test.
3. **minor** `src/lib/features/rail-shell/lens.logic.ts:406`: the PRD Lenses table gives the View rule text as "the view's label", and Terms calls a rule "plain-language". Instead the rule line shows the raw filter expressions plus ", not archived" (e.g. `_type == 'Project', not archived`; `!isEmpty(status)` or `contains(tags, 'x')` would appear verbatim). `work/13/discovery.md` records this as a default, but it departs from a written spec decision. Fix: get the owner's call, then either follow the PRD or record the choice in the PRD decisions log.
4. **nit** `src/lib/features/rail-shell/RailNoteList.svelte:147-158`: when the save fails, `persistViewState` toasts and still re-runs the query with the unsaved toolbar state. The list then shows a sort or filter the `.view` does not have, and the next refresh keeps it, because the content hash did not change. Fix: on failure, re-seed from the file (clear `seededViewHash` before the reload), or keep this behavior on purpose and assert it in the save-failure test.
5. **nit** `e2e/specs/rail-shell.spec.ts:442`: the restart half of this test would pass even if the saved pick were ignored, because the only view is also `rows[0]`, which the shell picks when nothing is saved. The deleted-view half does prove that the pick was saved and parsed. Fix: give the vault two views and pick the second one, then assert it is still highlighted after the restart.
6. **nit** `src/tests/lib/features/rail-shell/RailNoteList.view.test.ts:71`: the test mocks `view-parse-cache.js` and `updateViewQuery` instead of only `@tauri-apps/plugin-fs`. So the persistence check only asserts the arguments passed to `updateViewQuery`, and the real YAML round trip is checked only by the E2E. Fix: mock `readTextFile` / `writeTextFile` and assert the written YAML, as `view-lens.service.test.ts` does for reads.
