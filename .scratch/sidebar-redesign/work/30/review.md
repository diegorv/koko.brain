## Findings

1. **blocker** src-tauri/src/vault/parsing.rs:698 (`Anchors::resolve`), with :590 and :777 — the Issue's threat (a crafted note overflows the stack and aborts the app on every vault open) is still reachable through aliases. `MAX_YAML_NESTING_DEPTH` bounds the event depth only; a resolved alias splices a whole `Shared` subtree into the tree, so `project_value` and the `YamlNode` / `Rc` drop recurse over the projected depth, which an alias chain multiplies. Reproduced with a temporary probe (removed afterwards): a 3.4 KB block `a0: &a0 x` then, for i = 1..13, `a{i}: &a{i} ` + 126 `[` + `*a{i-1}` + 126 `]` stays within both limits (event depth 128, alias budget 9 841 of 10 000) and projects to depth 1 636. `parse_frontmatter` on it aborts a 2 MiB thread ("has overflowed its stack, fatal runtime error: stack overflow, aborting", debug test profile) and passes on 8 MiB. The scan runs on `tokio::task::spawn_blocking` (commands/vault.rs:1111), whose threads have tokio's 2 MiB default, so `pnpm tauri dev` crashes on that note; release builds were not checked. The build report's risk note ("about 1,600 levels, handled on a normal stack") is wrong for a 2 MiB thread. Fix: also store the subtree height in `Shared` (computed once in `register`, like the size), pass the current depth into `build_node`, and reject the block (an `Err` into the same fallback and one log) or resolve the alias to null when height + current depth goes past `MAX_YAML_NESTING_DEPTH`. Add a test with the 13-anchor chain above in a 256 KiB thread, and update the `MAX_YAML_NESTING_DEPTH` doc comment and the ADR line so they cover aliases. (Bounding the projected depth also keeps the `NoteEntry` snapshot under rmp-serde's default decode depth of 1 024, rmp-serde 1.3.1 decode.rs:213. I did not check that round trip because the probe overflowed first.)
2. **minor** src-tauri/src/vault/parsing.rs:3356 — `.expect("parser thread did not overflow")` reads as if `join()` catches a stack overflow. It does not: the overflow aborts the whole test process, and `join` only returns `Err` on a panic. The test is still valid, because an abort fails the run. Fix: reword the message (for example "parser thread panicked") or add a comment saying that an overflow aborts the binary.

## Resolution

1. **Fixed** in 8d807206 (blocker, alias chain). `YamlNode::Shared` and `Anchors::nodes` store the subtree height next to the size, both computed once in `register`. `build_node` now takes the number of open collections, and `Anchors::resolve(id, depth)` returns null when `depth + height > MAX_YAML_NESTING_DEPTH`. I picked null over rejecting the block because it is how an alias past the alias budget already behaves, and `build_node` has no error path into the fallback. Every alias obeys the bound and every stored height already counts the aliases inside it, so no projected value can nest past 128. New test `alias_chain_cannot_nest_past_the_depth_limit` uses the 13-anchor chain from the finding. It checks that `a1` (126 sequences around `*a0`) still resolves, and that every projected value nests less than 128 deep. One deviation: the test runs on a **1 MiB** stack, not 256 KiB. In the debug profile a legitimate 128-level tree needs more than 256 KiB: with the fix in, the test overflowed at 256 KiB and passed at 512 KiB. 1 MiB is half of tokio's 2 MiB `spawn_blocking` default. With the depth check turned off for a moment (`depth + height` condition forced true), the test aborts the 1 MiB thread with a stack overflow; with the check, it passes. The `MAX_YAML_NESTING_DEPTH` doc comment and the ADR 0029 line now cover aliases. I did not check the rmp-serde round trip separately: projected depth is now at most 128, below its decode limit of 1 024.
2. **Fixed** in 8d807206 (minor). The message now reads `.expect("parser thread panicked")`, with a comment that an overflow aborts the binary, which `join` cannot catch. The new test uses the same wording.
