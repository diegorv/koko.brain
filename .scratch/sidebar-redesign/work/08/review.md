## Findings

1. **major** `src/lib/features/rail-shell/RailNoteList.svelte:100`: the button uses file-explorer tokens on the tab-bar surface (the header is `bg-tab-bar`). `fileExplorerMutedFg` is only pinned against `fileExplorerBg` in `READABILITY_PAIRS` (`theme-builder.logic.ts:106`). On `tabBar` it measures 4.00:1 in Lavender Haze, so the "reads correctly in every built-in theme" criterion fails. Fix: use the tab-bar region tokens, which are pinned at 4.5:1 against `tabBar` (`text-tab-text-inactive`, `hover:text-tab-text-active`; Lavender Haze inactive measures 7.15:1, as `NoteActionBar` does). Alternatively, add a `fileExplorerMutedFg@tabBar` readability pair and fix the theme. The header's count span from Issue 07 has the same pairing; fixing it is optional and outside this Issue.
2. **minor** `src/lib/features/rail-shell/RailNoteList.svelte:59-68`: the handler has no in-flight guard. A fast double click runs two `createNoteHere` calls that read the same siblings, and both pick `Untitled.md`. Rust `create_note` refuses the second (`File already exists`), so the user sees "Could not create the note" right after a note was created and opened. Fix: ignore clicks while a creation is pending (a local `creating` flag), with a component test that clicks twice.
3. **minor** `src/lib/features/rail-shell/new-note.service.ts:19`: `createFile` can reject after `create_note` wrote the note. `refreshTree` → `loadDirectoryTree` rethrows. In that case the toast says creation failed while the note is on disk and not opened. This matches `createTypedNote` and is not new. Fix: either document it in the service JSDoc ("a rejection after the write leaves the note on disk"), or have `createFile` treat the tree refresh as non-fatal. That change touches core, so it is not for this Issue. The build report's claim that an open failure still toasts is wrong: `openFileInEditor` catches, shows its own toast and does not rethrow (`editor.service.ts:116-119`), so `createNoteHere` resolves.
4. **minor** `src/lib/features/rail-shell/rail-shell.types.ts:47-53`: `NewNoteRule` can express only a folder and frontmatter. The PRD's Type lens ("from the type's template, today's `createNoteOfType` path") and ADR 0033 ("folder, type, date, ...") will need a template or a delegate. That is fine for this Issue, but the JSDoc calls it "the one lens-to-new-note rule", so the Type-lens ticket should extend this type rather than add a second path. Fix: none needed now. Note it in the Type-lens Issue.
5. **nit** `src/lib/features/rail-shell/lens.logic.ts:89`: `newNoteContent` writes values without YAML quoting. Today's booleans and ISO dates are safe, but a later string value containing `: `, `#` or a leading `[`/`{` would produce broken frontmatter. Fix: quote strings when a later lens needs them (e.g. `JSON.stringify` for non-trivial strings), with a test.
6. **nit** `src/lib/features/rail-shell/RailNoteList.svelte:100`: `cursor-pointer` while the sibling rail items (`Rail.svelte:41`), note rows (`NoteRow.svelte:56`) and the Types note list's create button use `cursor-default`. Fix: `cursor-default` for consistency.
