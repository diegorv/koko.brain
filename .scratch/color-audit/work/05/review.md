## Findings

1. minor — `src/lib/core/settings/theme-builder.logic.ts:373` (and `withReadableContrast`, :254). The 90% hover headroom for the primary button label is enforced only in `readableCore`, on the core `p.primary`. When a theme sets `ui.primary` (or `ui.primaryForeground`) as an override, a user theme edited in the theme editor or a catalog theme with a `ui.primary` override, it skips `labelOnFill`: only the `primaryForeground on primary` pair runs. So the label can pass at rest and fall under 4.5:1 or Lc 45 on `hover:bg-primary/90`, and the theme editor never warns, because the pair list cannot express a tint. The Issue says "Hover fills derived from primary keep the pair" and the owner decision covers user themes. discovery.md records this limit as a decision. Fix: in `withReadableContrast`, after the `primaryForeground` pair, also lift `primaryForeground` (or the fill) on `tint(primary, 0.9, surface)` for the plain surfaces. If that is not wanted, record the limit in the Issue's Notes so the owner sees it. This does not block: every built-in and fixture theme passes "keeps the primary button label readable at rest and on hover" (:475), and my 400 random core palettes (seeded) all built pure black or white labels that pass on every hover tint.
