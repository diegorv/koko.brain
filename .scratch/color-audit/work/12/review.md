## Findings

1. **minor** `src/lib/core/settings/theme-builder.logic.ts:229` `readabilityFailures` measures every pair on the user's own colors, but the lift measures label-on-fill pairs on the already lifted fill. A label token that passes on the typed fill is then changed by the app with no warning. Probe: Lavender Haze with `primary: '#b09ad8'`, `primaryForeground: '#000000'`: the app shows primary `#5f5276` and primaryForeground `#cecece`, while the editor warns only on Primary. Item 2 says the editor marks each token the app shows lifted. Fix: also report a token whose `withReadableContrast` value differs from the typed one, e.g. walk the pairs on a running lifted copy, as `withReadableContrast` does, and measure each fg on that copy's bg. Add a test with this primary/primaryForeground case.
2. **minor** `src/lib/core/settings/theme-builder.logic.ts:129` Item 3 and the audit finding (`theme-builder.logic.ts:105` in `research/workflow-result.json`) name `primary` on `settingItemBg` **and** `settingsDialogBg`. Only hover and item got a pair, so a user theme whose primary fails on the dialog is neither lifted nor warned about. `readableCore` does not lift primary on `dialog` either. The finding also lists `success` on the Settings surfaces. Fix: add `['ui', 'primary', 'ui', 'settingsDialogBg', 4.5]` before the `primaryForeground` pair, and the same surface in `readableCore`'s primary lift. Add `success` if Issue 05 does not take it.
3. **minor** `src/lib/core/settings/theme-builder.logic.ts:265` The 4.5:1 Settings lift sits on `error` in `readableCore`, so it moves every token derived from `error`, not only the destructive text. On KokoBrain Default, `typeRed` goes from #f3333b to #fd746e, `typeOrange` from #fb8336 to #fd9b56 and `typePink` from #d16fa2 to #d386b9. Destructive buttons go from #171717 on #f3333b to #363635 on #fd746e, which measures 4.55:1. On Lavender Haze, error, the callout caution, collection and embed errors, and the type red and pink all darken. This matches the existing invariant that `typeRed` equals the lifted error (`theme-builder.logic.test.ts:65`) and the owner's "lift every theme" decision, and the build report discloses it. Still, the default theme's categorical red is now visibly salmon in the rail, tags and type colors. Fix: none is required for this Issue. The owner should confirm the new Default red before delivery. Otherwise, derive `typeRed`, `typeOrange` and `typePink` from the 3:1 error and leave the 4.5:1 lift to `destructive` and the error text tokens.
4. **nit** `src/lib/utils/color.ts:9` `SEP` is matched per channel, so the parser accepts strings that CSS rejects: `rgb(255, 0 0)`, `rgb(255 0 0, 0.5)` and `rgb(255,0,0/0.5)` all parse (probe: `#ff0000`, `#ff8080`, `#ff8080`). A token typed like that is measured and treated as a real color, but the browser drops the variable. Fix: use one alternation for the whole legacy comma form and one for the modern space form with an optional `/` alpha. Add a null test for the mixed forms.
5. **nit** `src/lib/core/settings/sections/ThemeColorRow.svelte:92` The warning `<p>` is not tied to the hex input or swatch (no `aria-describedby`), so a screen reader on the input never hears it. Fix: give the `<p>` an id and point the input's `aria-describedby` at it.
6. **nit** `src/lib/core/settings/theme-builder.logic.ts:232` `readabilityFailures` copies `colors[group]` and `colors[bgGroup]` on every pair (`{ ...colors[group] }`) only to widen the type. A cast (`colors[group] as Record<string, string>`) does the same without the allocations. The editor runs this function on every draft change.
7. **nit** `src/lib/core/settings/sections/ThemePreview.svelte:21` The theme list's preview cards still paint the typed, unlifted colors, while the app shows them lifted. This is outside the Issue's items, so it is a follow-up at most.
