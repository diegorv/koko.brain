## Findings

1. **minor**, `src/lib/features/tasks/TasksView.svelte:460`: `handleRowMenuCloseFocus` now treats focus inside any `[role="dialog"]` as free, where it only needs to cover this view's due date dialog. The Command Palette and the Quick Switcher are also bits-ui Dialogs (`features/command-palette/CommandPalette.svelte`, `features/quick-switcher/QuickSwitcher.svelte`). Scenario: a row menu is open and a global shortcut opens the palette. The menu closes on the focus move, the handler finds the palette's input inside `[role="dialog"]`, calls the focus "free", and focuses the task row. Before this change that focus was left alone, because it was outside the view and not in a menu. The palette's focus trap may pull focus back, but nothing tests that, and the rule is wider than its stated purpose. Fix: add a marker to the due dialog's `Dialog.Content` (for example `data-task-due-dialog`) and match only `[role="menu"], [data-task-due-dialog]`. Verdict: PLAUSIBLE, not reproduced in a real app run.
2. **nit**, `src/lib/features/tasks/tasks.service.ts` `updateTask`: the outside-vault check (`vaultRelativeKey` null) runs after `preflightTaskWrite`. For a note outside the open vault, a dirty tab of that note is saved before the write is refused. This is harmless (the save is the user's own typing), and Tasks rows only come from the vault, but checking `relPath` before the preflight is cheaper and matches "nothing is sent".
