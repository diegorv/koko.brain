## Findings

1. minor — `src/lib/features/tasks/tasks.service.ts:268`. Two overlapping menu writes leave the first Undo toast live. `setTaskStatus` dismisses the held id at the start of the write, but `setTaskStatusFromMenu` assigns the new id only after `afterTaskWrite` resolves, and that includes a full `buildTaskIndex`. If write 1 (row A) and write 2 (row B) are both in flight, write 2 dismisses nothing (no id yet), write 1 then sets id1, and write 2 overwrites it with id2 without dismissing id1. Toast 1 stays on screen, and its Undo performs a real write on row A, which breaks "Only the last menu write can be undone" and outlives later circle clicks. This is not the race the Issue accepts (the in-flight circle click, whose Undo meets `stale`): here the Undo succeeds. Fix: call `dismissStatusUndo()` just before `statusUndoToastId = toast(...)`, and add a test in `tasks.service.test.ts` with two deferred writes that checks `toast.dismiss` is called with the first id.
2. nit — `src/tests/lib/features/tasks/tasks.service.test.ts:945`. The title "calls toast.dismiss with no id held: not after the toast was dismissed, not on resetTasks" says the opposite of what it asserts (`dismiss` is never called). Rename it to "never calls toast.dismiss with no id held: ...".
3. nit — `src/lib/features/tasks/TasksView.svelte:496`. The close-focus guard treats focus inside any `[role="menu"]` as free, but the Issue says "outside the closing menu". In practice only one bits-ui menu is open at a time, so this changes nothing today. Narrowing it to the closing content (for example `e.currentTarget`, or the content ref) would match the Issue's wording if Issue 246 ever adds a submenu.

No scope creep. The discovery's defaults (opening a menu makes its row current, the `getClientRects` layout stub, the two extra focus tests) all serve the Focus bullet. The help text stays on the Issue's topics.
