## Findings

1. minor, src/lib/features/tasks/TasksView.svelte:409: after a mouse collapse, a later refetch moves focus by code into the list.
   - Cause: the focus-follow `chosen === current` branch now focuses `tabStopRow(rendered, next, current)`; before this change it focused `rowElement(current)`. That branch exists to refocus a current row that was recreated in another group.
   - When a mouse click collapses the group that holds the focused row, WebKit leaves focus on `<body>` and `lastFocusedRowEl` is disconnected. The next refetch that keeps the same rows then focuses the next shown row and makes it current, with no `preventScroll`. A mouse click on a checkbox under the All filter is such a refetch.
   - Probe 2 reproduced this. Focus b1 (blur it or not), click `Collapse B`, then `buildTaskIndex()` with the same rows: `document.activeElement` ends on c1, not `<body>`. On main, `rowElement(b1)` returns undefined and nothing moves.
   - This conflicts with "Collapsing never moves focus by code" and "on `<body>` when a mouse click collapsed the group", and the current row b1 is lost.
   - Fix: keep `rowElement(current)` in that branch, or focus only when `current` is in `rendered`. Add a collapse test: focus a row, blur, click the chevron, refetch with the same rows, expect `<body>` and current row unchanged.
2. nit, src/tests/lib/features/tasks/TasksView.collapse.test.ts (the Open filter case): this test passes with main's `tabStopRow` as well. It pins the switch from `next` to `rendered` in the view, not the new fallback. Cases (a) to (c) cover the fallback, so no change is needed.
