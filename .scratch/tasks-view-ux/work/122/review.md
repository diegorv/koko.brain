## Findings

1. minor, `src/lib/utils/task-tokens.ts:704-715` (`insertToken` block-id branch) and `src/tests/fixtures/task-line-edits.fixture.json`: on a recurring task that ends in a block id, inserting before the block id changes the parsed recurrence. I probed `parse_task_metadata`: `water 🔁 every week ^abc` gives recurrence `"every week ^abc"`, and after `setDueToken(..., '2026-11-20')` the result `water 🔁 every week 📅 2026-11-20 ^abc` gives `"every week  ^abc"` (two spaces). The parity test would flag this, but the fixture has no recurrence-plus-block-id case, so nothing pins it. Before the block-id rule, the due went after `^abc` and the recurrence stayed the same. The Issue Notes expect the RECURRENCE_RE swallow to stay; they do not mention the extra space. Fix: add a fixture case for it, then decide whether that case keeps the old placement (append when a `🔁` precedes the block id) or the Rust side trims the recurrence text. Either way, record the choice in the Issue or in Issue 246.
2. nit, `e2e/mocks/vault-index.ts:47` (`TASK_LINE_RE`, used by `writeTaskText` at `:640`): the mock matches only `-`/`*` markers and no ordered or `+` lines, and JS `.` stops at `\r`. So the mock reports `stale` where Rust writes (a `+ [ ]` or `3. [ ]` line, a CRLF line). `toggleTaskStatus` has the same gap and no spec drives it yet, so it does not block. When Issue 246 adds an e2e spec, keep its fixtures to `-`/`*` LF lines or widen the regex.
3. nit, `src-tauri/tests/vault_task_text_test.rs` / `src/tests/lib/utils/task-tokens.test.ts`: red-first cannot be verified from the history, because each test lands in the same commit as the code it tests (fe2332b23, 9ecd94aad). The build report says both failed first. Nothing to change.
