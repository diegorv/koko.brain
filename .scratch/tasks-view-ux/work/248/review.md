## Findings

1. **blocker** `src/lib/features/todoist-sync/fields.logic.ts:313-314,394` (made reachable by `src/lib/features/todoist-sync/task-line.logic.ts:230`). Links recorded under the old rule now lose labels on the Todoist side. Release 4.4.0 ships the ASCII `TAG_NAME` (checked with `git show 4.4.0:src/lib/features/todoist-sync/task-line.logic.ts`), so every 4.4.0 link that carries a label like `café`, `über`, `revisão` or `area/home` stored it in `remoteBase.unmappedLabels`, kept it off the line and kept it out of `localBase.tags`. After this branch, `mappedLabels` reads such a label as mapped. Then `before` and `tags` both hold it, so `tagsChanged` is false and the label is never written to the line. On the first brain-side tag edit (adding or removing any tag), line 394 keeps only unmapped labels and line tags, so the label is dropped from the push. Probe (a temporary `planFields` test, since removed): remoteBase `labels: ['deep','Work','café'], unmappedLabels: ['Work','café']`, line tags `['deep','next']`, Todoist unchanged. The pushed `item_update` is `labels: ["deep","Work","next"]`, so `café` is deleted in Todoist. This is the Todoist label loss the Issue exists to prevent, and it reaches every 4.4.0 user with an accented or nested label. **Fix:** treat a label that the stored base holds as unmapped, but that is mappable now, as added by Todoist. For example, compute `before` from `remoteBase.labels` minus `remoteBase.unmappedLabels`, so the next cycle writes `#café` to the line once and the bases record it. As a smaller fix, line 394 could also keep every label that is not in `localBase.tags`. Pin it with a `fields.logic.test.ts` case seeded with a 4.4.0-style base: the label is kept (or written to the line), and a brain tag edit never pushes a label list without it.
2. **minor** `src/lib/features/todoist-sync/task-line.logic.ts:240-243`. `tagMatches` scans the raw task text, but Rust `parse_task_metadata` (`parsing.rs:1940`) scans after it strips the signifiers. So a tag glued to a signifier (`Plan 🔺#shop`, or `📅 2026-11-13#shop`) is read by Rust but missed by `addTag`/`removeTag`. The old rule had no left boundary and found it. If Todoist removes the label, `removeTag` is a no-op, the line keeps `#shop`, and the next cycle pushes the label back. Lines written by the sync always put a space before tags, so this needs a hand-typed edge case. **Fix:** either accept it and document it in the `tagMatches` JSDoc, or add a test that pins the chosen behavior.
3. **minor** `src/lib/utils/tag-extraction.ts:7` and `src/lib/features/todoist-sync/completion.logic.ts:342`. TS `\p{L}` and Rust `is_alphabetic()` disagree on more than "rare combining marks": Devanagari and other Indic vowel signs (U+093F, U+0902, `Other_Alphabetic`) fail `\p{L}`. I checked this: `/^\p{L}+$/u.test('हिंदी')` is false. When Rust reads `#हिंदी` and fields planning puts it in `removeTags` (`fields.logic.ts:324`), `removeTag` → `assertTagName` throws during `applyLineChange`. The gap predates this branch (on main it threw for any non-ASCII tag), so the branch narrows it. **Fix:** file a follow-up to align `INLINE_TAG_NAME_SOURCE` with Rust (`[\p{Alphabetic}_][\p{Alphabetic}\d_/-]*`) or make the sync skip, not throw, on a Rust tag that TS rejects. Out of scope here.
4. **nit** `src/tests/lib/features/todoist-sync/task-line.logic.test.ts:219-229`. The table's JSDoc says it checks "the description where Rust asserts one", but the `file #work/ now` case leaves out Rust's asserted `file / now`. `removeTag` yields `file/ now`: `removeSpan` eats the space before the tag and keeps the trailing `/`. This is the same as main. **Fix:** say in the comment that this case's description is left out and why, or make `removeSpan` keep the left gap when the char after the span is not whitespace.
