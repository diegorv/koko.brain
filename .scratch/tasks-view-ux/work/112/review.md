## Findings

1. **minor** `src/lib/features/tasks/TasksView.svelte:373`: the focus-follow branch runs on every recompute of `groups`, not only when the current row changed group. `order` is a new array on each recompute (a refetch that changed nothing, a settings write, which re-runs the derived through `timeSync`'s `debug()`), so with a current row and focus on `<body>`, focus jumps into the list and `focus()` (no `preventScroll`) scrolls the viewport back to that row. Confirmed by the probe above; on main, Issue 113's effect returned early here. Scenario: the user clicks a blank area (focus to body), scrolls the list with the wheel, then any settings write scrolls it back and moves focus. Fix: refocus only when the current row's element was replaced, for example keep the row element that last held focus (from `handleListFocusin`) and refocus only when it is no longer `isConnected`; add a test in `TasksView.grouping.test.ts` that a recompute with the same rows leaves focus on `<body>`.
2. **nit** `help/documentation/10-tasks-and-todoist.md:13`: "Ticking a task does not move its note." is true for the Note grouping, but under Display > Status a ticked task moves to the Done group and under Due/Priority a group can disappear. Fix: scope the sentence ("Under the Note grouping, ticking a task does not move its note") or add that a ticked task moves to its new group under Status.
3. **nit** criterion 1 (test first): tests and implementation landed in one commit (ddbe9dd8e), so the red step is only the builder's claim. No change needed; noted for the record.
