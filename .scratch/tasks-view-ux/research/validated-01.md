# Validated 01: adversarial check of scout-01 (UI audit) and scout-02 (data model)

Method: every factual claim and path:line in `scout-01-current-ui-audit.md` and `scout-02-data-model-unused.md` was opened in code. Read-only; nothing was run, rendered or tested, so visual effects (flash, glue, jump) are derived from code paths, not observed. Facts carry path:line; opinions are labeled.

Verdict in one line: both scouts are substantially right on facts. Scout-01 has several wrong line numbers and one wrong peer-comparison (Kanban input chrome) and understates the status problem. Scout-02 is more precise but its top recommendation (render `metadata.description`) is unsafe as written because the Rust description is lossy for links. Both missed that a toggle makes the clicked file jump to the top of the list and triggers two refetch flashes.

## Refuted or corrected

Scout-01
1. "filterByDate, lines 90-103" and "computeTaskStats ... tasks.logic.ts:106-124": wrong. `filterByDate` is tasks.logic.ts:76-88, `computeTaskStats` is 91-113.
2. "Other toolbar inputs use `h-7 rounded-xs border-border bg-background` (GraphControls.svelte:81, Kanban 489/501)": half wrong. GraphControls matches (src/lib/plugins/graph-view/GraphControls.svelte:81). Kanban has no `h-7` anywhere in src/lib/plugins/kanban/; KanbanView.svelte:489 is a `<select>` and 501 an input, both `rounded-xs border border-border bg-background px-2 py-0.5 text-xs`. There is no single toolbar-input convention to copy. There is also a shared `Input` component (src/lib/components/ui/input/input.svelte) that neither scout mentions, but it is `h-9 text-sm` form chrome, too tall for a `h-10` pane toolbar.
3. Store default line refs "tasks.store.svelte.ts:9, 11, 29-31": off by one, actual 8, 10, 30-31. "`--primary` ... src/app.css:158": actual 159. "fromV2 ... tasks.service.ts:19-23": the conversion is at 24.
4. "`text-purple-400` is near-duplicate of `text-primary`": only true in light (`oklch(0.734 0.16 300)`, app.css:159). Dark primary is `oklch(0.73 0.08 278)` (app.css:220), a muted lavender, so in dark the hardcoded purple diverges more from the theme, which strengthens the point.
5. "in-progress, question, forwarded, important, cancelled ... are indistinguishable from todo/done": understated. The icon follows `toggleTarget` while the text follows `checked`, so `[/] [?] [>] [!]` render an open circle (like todo) next to struck-through text (like done): a contradictory mixed state, not just a lost distinction. Cancelled renders exactly like done.
6. "the scroll position resets (the `ScrollArea` content is rebuilt)": mechanism imprecise. `ScrollArea` (137) stays mounted; only its child block switches. The scroll is lost because the content collapses to one line, which clamps scrollTop to 0. Net effect claimed is right.
7. "Groups are ordered ... (commands/vault.rs:648-649, 735+)": 648-649 is a doc comment. The sort for the default path is src-tauri/src/vault/index.rs:1082.

Scout-02
8. Recommendation 1 "show `metadata.description` (still through `parseTaskTextSegments`)" is unsafe as written. `TASK_TAG_RE` (parsing.rs:1579-1580) has no word boundary and runs over the whole text (1865, 1873), so `[[Note#Heading]]` becomes `[[Note]]` with a bogus tag `Heading`, and a URL fragment `https://x/y#frag` loses `#frag`. Digits are allowed as the first tag char, so `#123` becomes a tag too. `RECURRENCE_RE` takes `.+?` up to the next signifier, a `#`, or end of line (1532-1548), so `🔁 every week [[Meeting]]` puts the wikilink inside `recurrence.text` and drops it from the description. Description can also be empty for a signifier-only line (Calendar falls back to `text` for that reason). ADR-0037 records the same fact: "the parser strips signifiers, collapses spaces and drops `#tags` from the description, so ... the projection is lossy" (docs/adr/0037-todoist-two-way-sync.md:15). Correct approach: strip signifier tokens from the text segments of `parseTaskTextSegments(task.text)` on the frontend, leaving wikilinks and links intact, or a Rust parser change (owner decision, touches Todoist field merge).
9. "Another write command exists, `write_task_lines` ... only frontend consumer is Todoist sync (`todoist-sync/sync-now.service.ts:1028-1115`)": the consumer is right, the citation is not. sync-now builds edits (around 1111); the IPC is called in src/lib/features/todoist-sync/closed-note-writer.service.ts:43-46, and open tabs are written by note-writer.service.ts without the IPC. Any quick-add from the Tasks view must handle the open-tab case the same way.
10. "Calendar already treats only `done` and `cancelled` as closing (event-calendar-tasks.logic.ts:21)": line 21 is a doc comment. The code is EventTaskChip.svelte:18.
11. "`none` in the type, see F6": there is no F6 in the report; dangling reference.
12. P7 / Q3 (stamp `✅`, regenerate recurring tasks on completion): not wrong as an owner question, but it collides with ADR-0037. For synced lines Todoist owns the recurrence rule and the completion sync rewrites `📅` on close (docs/adr/0037-todoist-two-way-sync.md:47; src/lib/features/todoist-sync/completion.logic.ts:1-6). A local roll would double-advance or duplicate synced recurring tasks. Also a core write-path change, which the owner has refused for corner cases before. Treat as out of scope for this ticket set.

## Missed by scouts

1. Toggle makes the file jump to the top (fact). `toggle_task_status_inner` writes the file, reads the new mtime and re-indexes with it (src-tauri/src/commands/vault.rs:802-804; `update_note_in_index_inner` at vault.rs:324 builds the entry with that `mtime`). Groups sort by `modified_at` desc (index.rs:1082). So ticking a task in the fifth file moves that whole file to position one after the refetch, and pulls it into "Last 7 days". Combined with the scroll reset, the user loses their place on every click. Any "stable order" fix must sort on something other than mtime or keep a client-side order across refetches.
2. Two refetch flashes per toggle (fact from code, not observed). `afterTaskWrite` refetches at once (tasks.service.ts:176-179), and `toggle_task_status` also emits `vault-index-updated`, so the throttled `vaultIndexVersion` bump (about 2 s, up to 10 s in a burst; tasks.service.ts:114-116 and docs/agents/indexing-watcher-rules.md rule 2) refetches again via the effect at TasksView.svelte:73-78. Each call sets `isLoading` true.
3. Remount on every tab switch (fact). `TasksView` is rendered only while the Tasks tab is active (src/lib/app/EditorView.svelte:40, 71-72), so returning to the tab refetches, flashes and starts at scroll 0. A "keep stale list" fix covers this case for free because the store is module-level.
4. Minimal fix for the flash needs no new store field (opinion): render the loading text only when `isLoading && fileTaskGroups.length === 0`. Rule-wise this is a view change plus a TasksView test; no store getter added, so no ADR-0034 getter test is triggered.
5. Test selectors are position-sensitive (fact). TasksView.test.ts uses `[data-task-row] span` (96), the first `[data-task-row] button` (133) and `[data-task-row] a` (232). Adding a chip `<span>` before the text, or a status-menu button before the toggle, breaks these silently or makes them hit the wrong element. Slices that change the row must update these selectors (prefer `data-*` hooks) in the same commit.
6. `isValidDayKey` and `resolveIconForPath` are importable from features/tasks without breaking layer rules: feature-to-feature imports are allowed while acyclic (src/tests/lib/architecture/feature-cycle.test.ts header; ADR-0003), nothing in src/lib/features or plugins imports features/tasks today, and event-calendar-dates.logic.ts has no imports, so a `.logic.ts` may import it. The new pairs will show up in `feature-cycle-baseline.json` (the test rewrites `featurePairs`), which a ticket must commit.
7. Section tag details (fact): Rust prepends `#` when missing (parsing.rs:1725-1729), and the match is a substring, so `#to-list` also matches `#to-listing`. Typing then closing the tab within 400 ms drops the change because `onDestroy` clears the timer (TasksView.svelte:42-44) while the input showed the new value.
8. Indentation is absolute document indent (fact): with a section filter or `hideCompleted`, a child can appear indented with no visible parent, because indent comes from leading whitespace (parsing.rs:1620-1631) and filtering only keeps checked parents with open descendants (tasks.logic.ts:17-52).
9. Todoist anchors (`🆔 td-...`) and user `🆔` both live in `metadata.id` (ADR-0037:27, 39). A chip for `id` must not expose anchors as user ids; hiding the `🆔` token in the row is safe because Todoist matches on its own scan, not on the view.
10. A status menu writing `[/] [?] [>] [!]` is compatible with Todoist sync: its `setTaskStatus` keeps those chars when opening and maps closing to `x` (task-line.logic.ts:123-125).
11. Calendar overlap (opinion): the Calendar already places dated tasks by `dueDate` with the closed rule. Date buckets in the Tasks view should reuse `isValidDayKey` and the same closed rule so the two views never disagree.

## Net recommendations that survive

Ordered as candidate vertical slices. Each is frontend-only unless stated, and each must ship with tests per CLAUDE.md rules 6, 11 and the Task Completion Gate (real stores, no store or `.logic.ts` mocks).

1. Stable list on refetch: keep groups mounted while refetching (loading text only when there is no data), preserve order across a toggle so the clicked file does not jump (missed item 1), and keep scroll. Touches TasksView and possibly a small sort in `tasks.logic.ts`; no Rust change. Check docs/agents/indexing-watcher-rules.md rule 2 (the `vaultIndexVersion` effect must stay; do not remove the immediate refetch in `afterTaskWrite` without tracing it, CLAUDE.md "Removing code").
2. Status correctness: add an `isTaskClosed(status)` helper in task-status.logic.ts (done or cancelled, matching `toggleTarget`, EventTaskChip and Todoist) and use it for strike-through, `filterCompletedTasks`/`hasUncheckedDescendants`, and stats. Update tasks.logic.test.ts, which asserts `checked` semantics. Do not change Rust `checked` (it is the checkbox fact, documented in task.rs:25 and consumed elsewhere).
3. Status glyphs for all 7 statuses with a larger hit target and focus ring; optional status menu through `toggle_task_status` `target` (needs a `setTaskStatus` service function; Todoist-compatible per missed item 10). Update the position-sensitive selectors (missed item 5).
4. Clean row text: strip signifier tokens and the `🆔` token from text segments of the raw `task.text`, keeping wikilinks and links; render due date, priority, recurrence and tags as chips using theme tokens. Do not render `metadata.description` directly (refuted item 8).
5. Token and header polish: replace `text-purple-400`, raw `text-xs/text-sm` with role tokens, show `done/total` per file, folder path as subtitle or title, `truncate`, locale-aware dates. Opinion on `titleColor`: optional, adds a features/file-icons pair.
6. Toolbar rework: labeled "Show completed" control, a clear section-source chip with reset, `aria-pressed` and focus-visible states. Input chrome should follow GraphControls (`h-7 rounded-xs border-border bg-background`) since no wider convention exists (refuted item 2).
7. Honest empty and error states: distinct copy for no tasks, all closed, filters hiding N, and a visible error for a failed fetch (CLAUDE.md Error Handling: user-facing errors must be inline or toast).
8. Due-date buckets and grouping modes (Overdue / Today / Upcoming / No date) in a new `.logic.ts` with injectable `now`, validated by `isValidDayKey`. Needs owner answers on due vs scheduled and on the default grouping. Must decide child-task handling when grouping across files.
9. Keyboard navigation (arrows, Enter opens, Space toggles).

Dropped or deferred: done-date stamping and recurrence roll on completion (conflicts with ADR-0037 and is a core write-path change); dependency/blocked state (needs vault-wide id lookup and collides with Todoist `🆔` anchors); quick-add via `write_task_lines` (must replicate Todoist's open-tab path, owner decision).

Owner questions that still gate slices: keep `#to-list` and `hideCompleted` as defaults; which signifiers are actually written; due-only or due-then-scheduled for buckets; whether `[/] [?] [>] [!]` count as open (the code elsewhere says yes).

Not verified: nothing was rendered, so the flash, the jump and spacing remain code-derived. I did not check how live preview renders `[/] [?] [>] [!]` in the editor, which matters for cross-view consistency (scout-17's angle).
