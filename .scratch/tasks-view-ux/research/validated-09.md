# Validated 09: scouts 17 (other task renderers) and 18 (theming tokens)

Adversarial check of `scout-17-other-task-renderers.md` and `scout-18-theming-tokens.md`. Every claim below was opened in code. Read-only: nothing was built, tested or run. Contrast figures are computed by hand from palette hex values with the WCAG formula, not measured in the app.

## Confirmed (claim + evidence)

### Scout 17

- `get_all_tasks_v2` at `src-tauri/src/commands/vault.rs:652` returns `lookup_all_tasks` (`src-tauri/src/vault/index.rs:1070-1084`): files with no tasks dropped, sorted by `modified_at` desc. `get_tasks_in_section_v2` (`vault.rs:742-760`) re-reads every note that has tasks from disk on a blocking thread.

- Event Calendar: `tasksFromGroups` keeps tasks with a valid `dueDate` and uses `metadata.description || text` (`event-calendar-tasks.logic.ts:49-66`). - Todoist: `get_all_tasks_v2` at `vault-scan.service.ts:57`, hand-kept `STATUS_CHAR` at `:19-27`, `fieldsOf` at `:29-37`, regex mirrors in `task-line.logic.ts:36-39` and `:48`.

## Refuted or corrected (claim + why + correct fact)

### Scout 17

1. **"Version bump contract ... `indexing-watcher-rules.md` item 5."** Item 5 is the hidden-directory filter. The `vaultIndexVersion` consumer pattern is **item 2** (`docs/agents/indexing-watcher-rules.md:5`).
2. **"Live preview checkbox ... `[/]`, `[-]` etc. toggle to `x` or blank here."** Wrong. The editor uses stock Lezer GFM (`core/markdown-editor/highlight-styles.ts:87`). Its TaskList parser only matches `/^\[[ xX]\][ \t]/` (`node_modules/@lezer/markdown/dist/index.js:2223`), so a `[/]`, `[-]`, `[?]`, `[>]` or `[!]` line produces no `TaskMarker`. `taskMarkerHandler` (`live-preview/inline/handlers/simple-widget-handlers.ts:19-31`) never builds a widget for those lines, and they show as a list item with literal `[/]` text. Correct fact: the editor has no checkbox for the extended statuses at all. The Tasks view is the only UI that toggles them.
3. **"`task-line-edits.logic.ts` (`extractTaskLines`)."** `extractTaskLines` is in `features/todoist-sync/pull.logic.ts:278`. `task-line-edits.logic.ts` exports `applyTaskLineEdits`, `codeFence`, `headingIndexes`.
4. **"`STATUS_CHAR` (mirror of Rust `status_to_char`, `parsing.rs:1604`)."** No `status_to_char` exists. The Rust function is `status_checkbox_char` at `parsing.rs:1606`. The TS comment at `vault-scan.service.ts:18` names a function that does not exist (stale comment, not a UX issue).
5. **"`DUE_RE`, `PRIORITY_RE` at `task-line.logic.ts:27-45`."** They are at `:51` and `:54`. Only `TASK_LINE_RES` falls in that range.
6. **"A Tasks view and an open Calendar tab both refetch on the same bump."** This cannot happen. `AppShell.svelte:262` mounts one `EditorView`, and `EditorView.svelte:72-77` renders only the active tab's view (`{#if isTasksTab} ... {:else if isEventCalendarTab}`). Only one of the two is mounted at a time. Problem 4 and recommendation 5 lose their main premise. The Todoist scan can still overlap, but on its own schedule.
7. **"Calendar importing from `features/tasks` would be a feature-to-feature import, check `layer-baseline.json` ... if that is a new violation, move `toggleTask` ... into `core/`."** Overstated. The ADR-0003 amendment of 2026-11-01 allows feature-to-feature imports while they form no cycle (`docs/adr/0003-four-layer-source-taxonomy.md:37`, `:91`). `layer-baseline.json` lists only three `utils/` edges and does not track feature pairs. The guard is `feature-cycle.test.ts` with `feature-cycle-baseline.json`, where `featureCycleEdges` is empty and the test rewrites `featurePairs`. `features/tasks` is a leaf: it imports no feature, and no feature imports it (grep). A new `event-calendar -> tasks` edge is acyclic and allowed. It adds one line to `featurePairs` for review, and nothing needs to move to `core/`.
8. **Recommendation 3, "Render `metadata.description` instead of raw `text`."** Unsafe as stated, see Missed 2: `description` is lossy and corrupts `[[Note#Heading]]` links and URL fragments.
9. Minor line drift: `get_tasks_in_section_v2` is at `vault.rs:742-760` (doc comment from `:732`), not `:733-749`. The `ModContext.kb` declaration is at `mods-host.service.ts:74-81`.

### Scout 18

1. **"`warning` (4.5 on fileExplorerBg/editorBg)"** (Problem 7). Only `fileExplorerBg` at 4.5 and `fileExplorerAccent` at 3 are pairs (`theme-builder.logic.ts:124-125`). On editorBg, `warning` gets only the 3:1 core `yellow` lift (`:205`). Correct fact: `text-warning` is not guaranteed at 4.5 on the editor surface or on card.
2. **"`type-yellow == warning`, `type-green == success` in builder themes."** That holds only before the final pass. `withReadableContrast` (`:158-175`, applied at `:293`) lifts `warning` and `success` to 4.5 but type colors only to 3, so they can diverge. Lavender Haze also overrides `typeYellow: '#907900'` (`theme.logic.ts:242`).
3. **"`typeRed..typeGray` are held only to 3:1 on fileExplorerBg."** Incomplete. `readableCore` also lifts the core `blue`, `green`, `purple` and `yellow` to 3:1 on editorBg (`:202-205`) before derivation. The mixed hues (`typeOrange`, `typeTeal`, `typePink`) and any override get no editorBg guarantee.
4. **"In most themes `card = panelBg` differs from `editorBg`."** Unverified, and false for the default. KokoBrain Default has `editorBg` and `panelBg` both `#2a2e3d` (`theme.logic.ts:118,120`). Of the built-ins, only Lavender Haze differs (editor `#F3F0F8`, panel `#EAE6F2`, `:233,235`). The catalog was not inspected. Correct fact: the `bg-card` vs `bg-editor-bg` mismatch is invisible in the default theme and shows only in the shipped light theme.
5. **Contrast of `text-purple-400`.** The direction holds, the numbers shift. Computed from Tailwind's oklch value (`node_modules/tailwindcss/theme.css:170`): about 2.3:1 on Lavender Haze card, about 2.5:1 on its editor background, about 2.8:1 on white, and about 4.8:1 (not 5.1) on the default card. On the one light theme that ships, it fails even the 3:1 large-text threshold.
6. **Inline `padding-left` at line 173.** It is at `TasksView.svelte:175`.
7. **"Adding a key to `ThemeColors` would have to flow through ... the catalog schema in the themes repo and `isThemeColorValue`."** Overstated. A key derived in `buildTheme` needs no catalog change unless themes must be able to override it. The real costs are user and duplicated themes stored as expanded tokens, which `mergeThemeWithDefaults` fills (`theme.logic.ts:98,107,382`), and the theme editor. The recommendation to prefer a CSS `color-mix` derived variable still stands.
8. **NoteRow chip as precedent.** It uses `text-[11px]` (`NoteRow.svelte:103,114,124`), the arbitrary size `app.css:78` tells authors to avoid. Copy its shape with `text-label`, not its classes verbatim. Scout 18's own chip recipe already does this, but it presents NoteRow as the precedent without flagging the difference.

## Missed by scouts

1. **The text strike-through also keys off `checked`** (`TasksView.svelte:191`). With hide-completed off, an in-progress or important task shows an open circle (it "completes" on click) next to struck-through, muted text. That is a third disagreement on the same row, beside the filter and the icon. The current hiding is documented and pinned: `TasksView.test.ts:139` says "Hide completed hides every checked row, `[!]` included". Changing it changes that behavior, so it is an owner decision, not a bug fix.
2. **`metadata.description` is lossy and can corrupt links.** `parse_task_metadata` strips tags with `TASK_TAG_RE.replace_all` (`parsing.rs:1873`). The regex is `#([A-Za-z0-9_][A-Za-z0-9_-]*)` with no word boundary (`:1579-1580`). Consequences, verified by reading the regex (no Rust test covers them; inputs at `:3102-3242`):
   - `[[Note#Heading]]` becomes `[[Note]]`, and `[[Note#Heading|alias]]` becomes `[[Note|alias]]`.
   - `https://x.com/p#frag` loses `#frag`.
   - Mid-sentence tags vanish: "Call #mom today" becomes "Call today".
   - The removed fragments also land in `metadata.tags` (for example `Heading`).

   Rendering `description` through `parseTaskTextSegments` would break heading wikilinks that work today on raw `text` (`tasks.logic.ts:123`). For display, either strip only the emoji signifiers TS-side from `text`, or fix the Rust tag regex in its own ticket (Rust tests, IPC unchanged).
3. **The toggle must keep sending the raw text.** `toggleTask` passes `expectedText: task.text` (`tasks.service.ts:150`), and Rust compares it with the line. Any display text change must leave `task.text` intact on the item.
4. **The view remounts on every tab activation.** It is unmounted when inactive (`EditorView.svelte:72`). Its `vaultIndexVersion` effect runs on mount (`TasksView.svelte:73-78`), so every switch back to Tasks refetches, by default through the disk-reading `get_tasks_in_section_v2`, because `#to-list` is non-empty. `onDestroy` clears the 400 ms debounce (`:42-44`), so a section-tag edit made just before switching tabs is lost. The input shows the typed value only until remount, then reverts to `tasksStore.sectionTag`.
5. **There is a due-proximity helper, but `features/` cannot import it.** `getDateProximity` (`overdue / today / tomorrow / upcoming / future / none`) is at `plugins/kanban/kanban.logic.ts:687-702`. `features->plugins` is a forbidden direction (`layer-rules.test.ts`, ADR-0003 table at `:28`). A Tasks due chip needs its own helper in `features/tasks/*.logic.ts` (or `utils/`). Kanban can later import it (plugin to feature is allowed), which is the only legal direction for scout 18's "shared due-date chip" idea.
6. **The editor-parity checkbox ring has low contrast in the shipped light theme.** `taskBorder = faintFg`, and Lavender Haze has `faintFg: '#C0B8D0'` (`theme.logic.ts:242`). That is about 1.55:1 on its card and about 1.7:1 on its editor background, under the 3:1 non-text guideline. It is equally weak in the editor today. Copying `--lp-task-border` into Tasks inherits the weakness. A `text-muted-foreground` ring (guaranteed 4.5 on card) is the safe idle state.
7. **Both questionable classes date to the initial commit.** `bg-card` and `text-purple-400` were introduced in `b7358e712` ("chore: initial project setup") and never touched since (`git log -S`). No recorded design decision backs either, which answers scout 18 open question 1 for practical purposes.
8. **The test selectors are positional.** `[data-task-row] span` picks the first span (`TasksView.test.ts:96`), and `circleButton()` picks the first button in the row (`:133`). A chip or status span placed before the text, or any button before the toggle, breaks these tests. The done state is asserted to have no `<circle>` (`:157`), so a done icon that draws one (for example lucide `circle-check`) would fail too.
9. **TagsView puts a panel title in its toolbar** (`TagsView.svelte:51`, `text-primary`). TasksView has none. This is a sibling-consistency point for the header slice.

## Net recommendations that survive

1. **One closed predicate.** `isTaskClosed(status)` (`done || cancelled`) next to `toggleTarget` in `task-status.logic.ts`, used by `filterCompletedTasks`, `computeTaskStats`, the row strike-through (`TasksView.svelte:191`) and `EventTaskChip.svelte:18`. This needs an owner decision first (scout 17 Q1), because it changes pinned behavior (`TasksView.test.ts:139`). Test-first in `tasks.logic.test.ts` with `[/]` and `[!]` fixtures.
2. **Shared presentational `TaskStatusIcon`** in `features/tasks/` (props only, no store). `EventTaskChip` imports it directly: an allowed acyclic feature edge, with no move to `core/`. Its size only shrinks if the owner does not use the extended statuses (scout 17 Q6).
3. **Show metadata as chips, but do not render `metadata.description` as the text** until the tag-regex loss is fixed. For the text, strip only date, priority and recurrence signifiers on the TS side, or keep `text`. Show tags as chips only if the text no longer shows them. Keep `task.text` on the item for the toggle.
4. **Due-date chip.** New `features/tasks` logic for due proximity (do not import Kanban's). Use `text-warning` for due today and `text-destructive` for overdue, on an icon, border or tint, with `text-foreground` text when contrast is not guaranteed. Neither `warning` nor `destructive` is a verified text pair on card or editor (`warning` 4.5 only on fileExplorerBg, `destructive` 3:1).
5. **Replace `text-purple-400`** with `text-foreground font-medium` or `text-primary` (4.5 guaranteed on editorBg only). Use `text-meta text-muted-foreground tabular-nums` for date and count. Settle the root surface on `bg-editor-bg` like TagsView. If grouped cards are wanted, give the cards `bg-card`. The difference only shows in light themes, so check Lavender Haze.
6. **Adopt the chrome type roles** (`text-label` for chips, `text-meta` for counts, `text-row` for rows). Keep `pane-toolbar`. Pair any `group-hover:opacity-100` with `group-focus-within:opacity-100` (guard test).
7. **Status icon colors on the icon only** (`text-type-blue`, `text-type-purple`, `text-type-teal`, `text-warning`, `text-muted-foreground`). That is enough for non-text 3:1 on the core hues. Teal is a mix with no editorBg guarantee.
8. **For any new color, use a derived `color-mix` variable in `app.css`**, not a new `ThemeColors` key.
9. **Add a scoped raw-palette guard test for `src/lib/features/tasks/`** (cheap, passes after the purple fix).
10. **Out of the UX slices:** no shared task fetch cache (the premise is refuted, and indexing rule 1 says no mirror). No `KBTaskV1` change (contract, item 12). No change to Kanban or the editor checkbox. Fixing `TASK_TAG_RE` boundaries and the stale `status_to_char` comment belong in their own tickets.
11. **Update tests** whenever the row markup changes: the positional selectors and the `<circle>` assertions in `TasksView.test.ts`.
