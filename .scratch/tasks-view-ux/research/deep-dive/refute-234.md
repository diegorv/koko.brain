# Refutation: Issue 234, the Tasks list keeps your place, and a failed refresh says so

Ticket: `.scratch/open-itens/issues/234-tasks-groups-keep-their-place.md`. Dossier: `dossier-234.md`. HEAD `d2304ac9e`. "Verified" means read in code at HEAD or in `node_modules`; "Inference" means reasoning, not run (no tests or app run, per the task rules).

## Verdict

**Confidence: medium.** The sort, the error field, the alert and the debounce flush are specified well enough, and most factual claims check out (list below). Three points would make a fresh agent build the wrong thing or stop to ask:

1. **The scroll save mechanism doesn't work in the app.** The ticket says "On destroy it saves the viewport's `scrollTop`". In Svelte 5.57.3 the `{#if}` branch's DOM is removed before the child component's teardowns run (`node_modules/svelte/src/internal/client/reactivity/effects.js:518-542`: `remove_effect_dom` at :521-528, then `destroy_effect_children` at :531, then `execute_effect_teardown` at :542; `onDestroy` is `onMount(() => () => untrack(fn))`, `node_modules/svelte/src/index-client.js:115-121`). A detached element has no layout box, and CSSOM View says `scrollTop` is then 0. Worse, the bits-ui viewport ref is cleared when its node disconnects (`svelte-toolbelt@0.9.3 dist/utils/attach-ref.js`: the teardown sets the ref to null when `!node.isConnected`). So `viewportRef` is probably already null when `onDestroy` runs (inference from the effect order). The ticket's own test ("set the viewport's `scrollTop`, unmount, mount again") can still pass in jsdom if the element is captured in a closure, because jsdom stores `scrollTop` as a plain field (`node_modules/jsdom/lib/jsdom/living/nodes/Element-impl.js:44`). That gives a green test while the app always restores 0.
2. **Two storage options, one of which fails the ticket's own tests.** The ticket offers `tab-view-state.ts` as an option, but its own acceptance criteria (`tasks.store.test.ts`: "`reset()` clearing the scroll offset") and Issue 115 (`115-fetch-from-entries-snapshot.md:26`: "`tasksStore.reset()` still clears every field the view added (... scroll offset, error ...)") need a store field.
3. **"With no list loaded yet" is undefined after Issue 108.** In Issue 108, `hasLoaded` becomes true when the first fetch finishes, "success or failure" (`108-mounted-list-and-rule-sentence.md:8`). So `!hasLoaded` can never select the failed-first-fetch case. The agent has to guess what the condition is.

Everything else is wording or test-tightening. With the must-fix edits below applied, I would put confidence at high.

### Claims that are wrong or imprecise

- "on a vault switch the editor reset unmounts the view and `resetTasks()` runs after it". `teardownVault` calls `resetEditor()` (`src/lib/app/lifecycle/app-lifecycle.service.ts:651`) and then `resetTasks()` (:664) with no `await` between them. `resetEditor` only resets the store (`src/lib/core/editor/editor.service.ts:460-465`), so the unmount and `onDestroy` happen at the next Svelte flush, after `resetTasks()` (inference: no `flushSync` on that path). The guard the ticket asks for is still right, and the ticket's test order (type, `resetTasks()`, unmount) matches the real order. Only the sentence is backwards.
- "On destroy it saves the viewport's `scrollTop`": see Verdict 1.

Do not read `scrollTop` in `onDestroy`: Svelte removes the `{#if}` branch's DOM before the component's teardowns run, a detached element reports `scrollTop` 0, and the bits-ui ref is already null by then. The field is not reactive state any component renders, so scrolling causes no reactive churn."

2. **Name the generation export.** Issue 241 calls it from service code (`241-tasks-row-status-menu-with-undo.md:13`: "Issue 234's reset generation"). ## Dossier errors

1. **§4.2, reason against `tab-view-state.ts`.** It says Cmd+Shift+T "closes the active Tasks tab" and so loses the place through `closeTab`'s `deleteTabViewState`. Wrong for that path: `toggleTasksTab` calls `editorStore.removeTab` directly (`tasks.service.ts:216`), and only `closeTab` deletes view state (`editor.service.ts:328-329`), which is the tab's close button. The conclusion (use a store field) still holds, for the reasons in must-fix 3.
2. **AC4, "`vi.waitFor` polls on timers and can hang under fake timers".** Wrong for vitest 5.1.0: `waitFor` uses the safe real timers and calls `vi.advanceTimersByTime(interval)` on each check when fake timers are on (`node_modules/vitest/dist/chunks/index.CZzC1gGg.js:6973-6994`). The real hazard is the opposite: it advances the clock and can fire the 400 ms debounce before the unmount (should-fix 8).
3. **§0.1 is right but incomplete.** Besides `scrollTop` being 0 on a detached node, the bound `viewportRef` is probably already null in `onDestroy`: the svelte-toolbelt attachment teardown nulls it when the node is disconnected, and that child effect is torn down before the component's `onDestroy` effect, which is created after the template (inference from Svelte's effect order). So a destroy-time read through `viewportRef` likely fails even in jsdom, unless the node is captured in a closure, in which case the test passes falsely.
4. **§0.2 and §5.9: "the unmount most likely lands after `resetTasks()`".** Stated as inference. `resetEditor` only calls `editorStore.reset()` and `clearAllTabViewStates()` (`editor.service.ts:460-465`), with no `flushSync`, which supports it. The dossier's conclusion holds.
5. **§1.2, "Existing tests already use alphabetical paths, so none changes".** Correct for `tasks.service.test.ts` (`:150-186` use `/vault/new.md` alone). `TasksView.test.ts` uses a single note (`NOTE`, `:32`), so no existing component test depends on order either. No error, but the dossier gives evidence only for the service file.
6. **§4.4, tie-break called optional.** For an Issue whose goal is "keeps your place", a tie that can reorder on every refetch defeats the goal for case-variant or accent-variant names. It should be required (should-fix 9), not left to the reviewer.
