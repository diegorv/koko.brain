## 0. Findings that change the plan (read first)

1. (F) `parseSettings` rebuilds the settings object key by key (`src/lib/core/settings/settings.service.ts:82-198`) and `loadSettings` writes the result straight back to disk after a successful parse (`:68-74`). A key that `parseSettings` does not name is erased at the next load. So `tasksView` must be added to `parseSettings`, and passed through verbatim (no spread, no default): the `todoist` model at `:160-163` is wrong for an opaque value, because `{ ...undefined, ...42 }` silently turns `42` into `{}`, and the load write-back would then already "overwrite" an invalid `tasksView: 42`. This is the single point where the ticket's pointer ("the per-section merge in `settings.service.ts`, as `todoist` does") misleads.
2. (F) The seam for "when the vault's settings have loaded" does not exist. `loadSettings` is called from one place only, `initializeVault` (`src/lib/app/lifecycle/app-lifecycle.service.ts:210`, grep over `src/lib` shows no other caller). `core/settings` cannot call into `features/tasks` (layer rules). So the load must be a function exported by `features/tasks/tasks.service.ts` and called from `initializeVault` after `loadSettings` and the `initVersion` check (`:212`). `app/lifecycle` already imports from `features/tasks` (`:57`), so no layer edge is new.
3. (F) `src/tests/lib/app/lifecycle/app-lifecycle.service.test.ts:189-192` mocks `#lib/features/tasks/tasks.service.js` with a factory that exposes only `buildTaskIndex` and `resetTasks`. A new export called from `initializeVault` and missing from that factory makes vitest throw on access, which breaks EVERY `initializeVault` test in the file. The factory must gain the new function in the same commit.
4. (F) "Not written until the user changes the field" cannot mean "`writeTextFile` is never called after load": `loadSettings` always writes the merged settings back after a good parse (`settings.service.ts:69-74`). It means the invalid `tasksView` value stays byte-identical on disk until the next change (through the pass-through in finding 1), and that nothing in the load path or the persistence effect rewrites it. The red test must assert that, not "no write at all".
5. (F) `tasksStore.reset()` already restores `#to-list` (`src/lib/features/tasks/tasks.store.svelte.ts:30`) and `resetTasks()` runs inside `teardownVault` (`app-lifecycle.service.ts:664`) before the next `loadSettings`. The ticket's "reset still restores `#to-list`" line is already true and tested (`src/tests/lib/features/tasks/tasks.store.test.ts:46-55`). The new load must nevertheless SET `#to-list` explicitly for a vault with no key, not skip: the double-switch window skips `teardownVault` (comment at `app-lifecycle.service.ts:142-147`, branch at `:177`), so the store can still hold the previous vault's tag when the next `loadSettings` returns.
6. (F) No Rust, IPC, e2e-mock or ts-rs change. Nothing in `src-tauri/src` reads the Tasks keys of `settings.json` (grep `settings.json` in `src-tauri/src` only hits a watcher test). Gate is frontend only, as the ticket says.
7. (F) Cross-ticket shape, for the reader of 116/123: Issue 116 removes the textbox and `tasksStore.sectionTag` and repoints the load site; 123 extends the same key. Keep the load in ONE exported function with one call site so 116 repoints it (see 1.3).

## 4. Ambiguities and the most likely reading

- A1. Where the load is called. The ticket says "when the vault's settings have loaded" and names no function. Reading: a function in `features/tasks/tasks.service.ts` called from `initializeVault` right after `loadSettings` (finding 2). Rejected alternatives: an `$effect` in `TasksView` (runs only when the tab is open, and races the first fetch); a settings-loaded hook in core (new mechanism, nobody asked).
- A2. What counts as an "invalid value". The ticket gives `42`. Reading: valid = absent, or a plain object whose `sectionTag` is absent or a string; invalid = `null`, array, string, number, boolean, or `sectionTag` of another type. `version` is not checked on read (a newer build may write `version: 2`; rejecting it would make a downgrade lose the tag and toast every start). On save, an existing numeric `version` is kept, else `1`.
- A3. Empty string. Ticket: "A missing key or a missing `sectionTag` gives `#to-list`." Reading: a saved `sectionTag: ''` loads as `''` (every task), because Clear tag and an emptied box write `''` and the owner asked for the field to be remembered as typed. This sits beside the owner's "the view never defaults to every task" rule, which concerns the default only. Issue 116's dossier (A7) reads an empty list as `#to-list` for the card model; that is 116's decision, not 243's. State it once in the report; a test pins `''`.
- A4. "As typed": the raw text, untrimmed, un-normalized (`'#a, b '` saved verbatim). Reading: yes, no `parseSectionTags` on write.
- A5. Which writes count. "A change that `updateSectionTagFilter` applies". Reading: only that function writes (`TasksView` debounce and Clear tag both go through it). Mounting the view or loading never writes; a textbox value equal to the saved one produces a write attempt that the persistence effect skips because the serialized text is unchanged (`settings-persistence.svelte.ts:57`).
