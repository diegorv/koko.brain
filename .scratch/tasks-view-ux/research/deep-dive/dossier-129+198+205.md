## 4. Ambiguities (implementer would have to guess)

1. **The error rule is not implementable as written.** "The newest sync log entry for the anchor is a terminal command error or a field that could not be pushed, newer than the link's last successful cycle". Facts: the link has no timestamp; `cycle` rows have `anchor: null` (`cycle-log.logic.ts:101`); and within one cycle the error rows are appended BEFORE that cycle's `cycle` row (`sync-now.service.ts:578` vs `:252`), and a cycle with command errors still ends `ok`. So "newer than the last successful cycle" is false for the very cycle that logged the error. Most likely intended reading, and what to build: the newest log row for the anchor (any kind) decides; it is an error if its kind is one of the three. It clears when any later anchor-bearing row appears (a `written`, `applied`, `stale`, `frozen`, `conflict` row and so on) or when the link detaches. Known consequence: an error persists until another row for that anchor is logged or the 1000-row log trims it (quiet cycles fold into one row and add none). The ticket marks this rule as a proposal needing owner confirmation before launch (`## Notes`, Triage); do not launch before that.
2. **Precedence** when several states apply (a frozen link with an old error row, a pending frozen link). The ticket lists them as separate states. Recommended: frozen, error, pending, linked.
3. **Pending**: "attached link whose `todoist_id` is still null". Also `pendingUuid` is normally set. The link field is the only input needed; no use of `pendingUuid`.
4. **Fixed message per kind**: wording is not given. Proposal: linked "Synced with Todoist"; pending "Waiting to be created in Todoist"; frozen "Frozen: this anchor is on more than one line" (given in the ticket); error per kind: "Todoist refused the last change to this task" (`command-error`), "The task text was not sent to Todoist" (`content-not-pushed`), "The due date removal was not sent to Todoist" (`due-not-pushed`).
5. **Which rows show state when `syncEnabled` is false.** The filter is shown only while it is on; the icons are not addressed. Recommended: no fetch and no icons while sync is off (the links would be stale). If a persisted or earlier `quick.todoist` is non-`any` when sync is turned off, the list empties silently except for the rule sentence, the "Reset Todoist filter" empty-state action and Reset filters. Alternative: ignore `quick.todoist` in the view when sync is off. Pick one and test it.
6. **"Refetch when `todoistSyncStore` reports a finished cycle"**: which signal. Recommended: `status` leaving `'syncing'` (covers success and failure), not `lastResult` alone (a failed cycle may already have committed link and log rows).
7. **"Open in Todoist" on which rows.** Ticket: linked rows. Recommended: any row whose info has a non-null `todoistId` (linked, frozen, error); pending has none.
8. **Where "Open in Todoist" sits** relies on 241's menu structure (a `DropdownMenu` on the button plus one list-level `ContextMenu`). If 241 shares the items through a snippet, add the item once; if it duplicates, add to both. Test the dropdown and the context menu.
9. **Name of the query type**: the ticket says `TaskQuery`; at this point the type is whatever 111 named the `quick` object (the PRD's `TaskQuery` arrives with 123). Use the existing type and name the new union `TodoistFilter`.
10. **`applyQuickFilters` parameter shape**: the ticket says "the state map passed in". After 238 the signature is `(rows, quick, today, now)`. Recommended: add the map as the fifth parameter. `explainEmptyTasks` needs it too.
11. **Wording of the filter's rule-sentence clauses** beyond the one example ("synced with Todoist and frozen"). Proposal in step 3.

## 5. Risks and contradictions

- Contradiction: acceptance criterion 4 (`isQueryModified`) cannot be done in this ticket (see section 2).
- Contradiction (minor): the ticket says the map is "dropped on `teardownVault`". There is no separate teardown hook to add; `resetTasks()` at `app-lifecycle.service.ts:664` already clears the store and covers it. A second place (`todoistSyncStore.reset()` at `:673`) belongs to todoist-sync and must not touch the Tasks store (`todoist-sync` must not import `tasks`).
- `todoist-sync` must not import `features/tasks`: keep the state function free of any `TaskRow` type; it takes `string | undefined`.
- `visibleRows` is a module-level `$derived` (ADR-0034, `docs/adr/0034-derived-allowed-behind-store-getters.md`): it must read `todoistStates`, and the getter needs a test that a map change recomputes it.
- Reading 1000 log rows (cycle rows carry JSON) once per cycle end is cheap, but do not call it per row or per tasks refetch. Do not refetch the map on every `vaultIndexVersion` bump; a cycle writes notes, so the version bumps during it, and the map refresh after the cycle ends is what matters. A brain-born line gains its anchor in a note write, so for a moment the row shows nothing until the map refreshes after the cycle.
- Race: the map read can resolve after a vault switch. The counter plus `vaultStore.path` check handles it. `todoist_*` commands refuse a path that is not the open vault, so a late call errors rather than leaking; the catch must not toast.
- Indexing rules (`docs/agents/indexing-watcher-rules.md`): this ticket does not write notes or touch `applyNoteChange`, the index or the watcher. Rule 6 mentions `task-write.service::settleTaskWrite` for the Todoist sync's `write_task_lines`; not affected.
- Layer rules: `features/tasks` -> `core/settings` and `core/vault` are allowed. `settingsStore` access from the view is fine (`TodoistSyncStatus.svelte:2` does the same).
- e2e: none of the existing selectors in `e2e/specs/tasks-view.spec.ts` can see the new icon or filter (sync is off in the mock vault). A new icon in each row changes no accessible name of the circle button.
- `menu-item-anatomy.test.ts`, `chrome-type-scale.test.ts`, `chrome-state-styles.test.ts`, `pane-toolbar.test.ts` scan `TasksView.svelte` by source: no `mr-*` on menu items, no `text-xs` label in a menu item, no `text-[10px]`, no `transition-all`, no overrides on the one `pane-toolbar` element.
