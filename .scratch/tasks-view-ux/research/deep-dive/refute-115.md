# Refutation: Issue 115, Tasks come from the entries snapshot, and the heading rule runs in TS

Ticket: `.scratch/open-itens/issues/115-fetch-from-entries-snapshot.md` (cited as `115:N`). Dossier: `dossier-115.md`. Code cited at HEAD `d2304ac9e`. (F) = verified in code at HEAD; (I) = inference, mostly about what predecessors leave behind. Nothing was run (read-only task): no vitest, check, cargo or e2e.

## Verdict

**Confidence: low** that a fresh agent implements it right from the ticket text alone.

The core facts hold. The memo and its throttle are as described (F: `vault-entries.service.ts:26-38`, `tauri-listeners.service.ts:106-109,276-305`). `toggle_task_status` emits `vault-index-updated` with the same `UpdateResult` it returns, before it returns (F: `src-tauri/src/commands/vault.rs:853-864`). `bumpVaultIndexVersion` assigns the Rust version (F: `vault.store.svelte.ts:108-111`). The entries snapshot carries `isA`, `tags`, lifecycle flags and `frontmatter`, and `FileTaskGroup` does not (F: `NoteEntry.ts:34-98`, `vault.rs:652-660`, `index.rs:1070-1084`). The A/B/C difference is real (F: `parsing.rs:1749-1758`). The overlay drop rule is sound: `refresh()` bumps first and patches the memo in the same synchronous turn (F: `tauri-listeners.service.ts:267-275`, `inflight.ts:133-153`).

Nine gaps would make an agent guess, ship a regression, or stop:

1. The failing-first test (`115:38`) cannot pass on a correct implementation as written. It combines a snapshot that never changes, "the index refresh runs", and "mocking only invoke". The refresh only runs through the real listener, which needs `@tauri-apps/api/event` mocked. Once the refresh runs, the version reaches the write's version and the overlay is dropped, so a snapshot that never changes shows `todo` again.
2. The stale and line-moved refusals still "refresh the list" (`tasks.service.ts:141-145,154-157`). On the memo they get back the snapshot that just proved stale, so a retry is refused again for 2 to 10 s. The old test at `tasks.service.test.ts:296-317` encodes the fresh refetch, and `115:42` says to rewrite it without saying to what.
3. "whole tag token" (`115:12`) is undefined. The plausible readings differ on `(#to-list)`, `#to-list.` and `#to-list/today`, and two of those match today. The help text and tests pin only three changes (`115:14`, `:40`).
4. "The section tag textbox and the rule sentence (Issue 108) use it" (`115:13`) does not say where rows are filtered. 108's empty state requires `rows` to be section-limited already (`108:17`).
5. The new `TaskRow` field names are not pinned. `115:41` says "type, tags, archived, frontmatter", while 116 reads `row.noteType`, `row.noteTags` and `row.archived` (`116:9-15`) and the PRD names `properties` (`PRD.md:252-255`).
6. The ticket does not say where the overlay lives or that a reset clears it. If it is a module Map, `tasksStore.reset()` in the existing `beforeEach`s does not clear it (`tasks.service.test.ts:215-219`), so entries leak between tests.
7. `115:25` asserts that 243's saved tags load, but 243 is not a blocker (`115:28`), and 243 waits on 030, which is still `ready-for-agent` (`030:15`).
8. `115:9` says `TaskItem` "stops being used". It stays in use: `TaskRow` extends it (`111:14`), `toggleTask(filePath, task: TaskItem)` takes it (`tasks.service.ts:130`), and 121 keeps it (`121:10`).
9. The e2e test that writes a note inside the test and then opens Tasks (`e2e/specs/tasks-view.spec.ts:89-102`) used to read a live index. On the snapshot it waits for a throttled bump of up to 10 s, against a 5 s expect timeout (`e2e/playwright.config.ts:8`). 242's new two-tag e2e test uses the same pattern (refute-242 M3).
