## 0. Findings that change the plan

1. **Re-choosing the checked radio item still fires `onValueChange`** (verified, `node_modules/bits-ui/dist/bits/menu/components/menu-radio-group.svelte:20-27`: the box setter assigns `value = v; onValueChange(v)` unconditionally). The ticket says "Choosing the current status writes nothing". Rust does no-op (`toggle_task_status_inner`, `src-tauri/src/commands/vault.rs:788-798`, `updated == original`), but before that IPC the TS protocol would save a dirty open tab. So the guard `target === task.status` must be client-side, before the dirty-buffer save.
2. **Close-autofocus runs late and can lose to the refetch** (inference from verified bits-ui code, `node_modules/bits-ui/dist/bits/utilities/focus-scope/focus-scope.svelte.js:56-62,86-107`: `onCloseAutoFocus` fires on focus-scope unmount, after the exit animation). With a fast IPC the row can be removed (Done under Open) before the menu unmounts. Then 113's "focus follows" check sees `document.activeElement` inside the portaled menu (outside the view), does nothing, and the menu later unmounts to `<body>`. So the `onCloseAutoFocus` handler itself must fall back to the current row when the opened-from row is gone. See step 7.
3. **The default close-autofocus target is wrong on WebKit**: bits-ui returns focus to the trigger only if it is tabbable (`menu.svelte.js:830-842`), else to the pre-open focus memory. The row's actions button has `tabindex="-1"` in every non-current row (ticket 113), and Tauri macOS WebKit does not focus a button on click. So both menus need an explicit `onCloseAutoFocus` that does `e.preventDefault()` and focuses the row. Precedent in repo: `src/lib/features/event-calendar/EventPopover.svelte:88,159` (a Popover, with jsdom tests `EventPopover.test.ts:271`). Whether the same fires for a Menu under jsdom is NOT verified (see Risk R3).
4. **The "Copy task text" stripping is not available to reuse as written.** Ticket 109's `taskDisplayText` returns `metadata.description` by default and strips the id and anchor only as a final step; its regexes are planned as private constants (`dossier-109.md:126`). 241 needs the stripped RAW `task.text` (the test expects `Call Ana` from `Call Ana 🆔 td-123 ^abc`). So 241 must export a small helper from `tasks.logic.ts` (for example `stripTrailingTaskIds(text)`, block id first, then anchor), and ideally 109's `taskDisplayText` calls the same one. If 109 shipped the regexes private, 241 extracts them (a refactor of 109's code, covered by 109's tests).
5. **Todoist claim verified**: `isClosedStatus` is `x`, `X`, `-` only (`src/lib/features/todoist-sync/task-line.logic.ts:119-121`); a local change is detected as `lineClosed !== isClosedStatus(localBase.status)` and pushes `item_close` / `item_uncomplete` (`completion.logic.ts:170-171,198-199`). Matches `help/documentation/29-todoist-sync.md:263-275`. Open-to-open and closed-to-closed send nothing. No code needed. Two details for the help text: a Tasks-view write is not a note save, so it does not start the after-save sync (`help/documentation/10-tasks-and-todoist.md:111` already says this for the circle), and the line "stays as you left it" until Todoist confirms (doc 29:275).
6. **Ticket claim that holds**: `toggle_task_status` accepts any target (`status_checkbox_char`, `src-tauri/src/vault/parsing.rs:1606-1616`, all seven statuses) and writes only the checkbox char (`set_task_status_in_content`, `parsing.rs:1887-1915`), so there is no done-date stamp and no text change. Hence Undo's `expectedText` equals the original `task.text`. The e2e mock does the same (`e2e/mocks/vault-index.ts:502-529`). No Rust or contract change: Gate is frontend only.
