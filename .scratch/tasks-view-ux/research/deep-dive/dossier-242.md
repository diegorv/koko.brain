## 0. Findings that change the plan (read first)

1. (F) The e2e mock does not implement the heading rule. `e2e/mocks/vault-index.ts:489-495` (`getTasksInSection`) lowercases the tag and matches NOTE tags (`entry.tags.some(t => t.toLowerCase() === target)`). Note tags are stored WITHOUT `#` (`src/lib/utils/tag-extraction.ts`: `.replace(/^#/, '')`, inline tags exclude the `#`, `findInlineTags` returns `tag` without `#`), and the target keeps the `#`. So today the mock returns `[]` for every tag that starts with `#`. The default `#to-list` therefore shows nothing in e2e, which is what the spec comment at `e2e/specs/tasks-view.spec.ts:17-19` relies on. The ticket's e2e criterion ("types two tags and sees tasks from both sections") cannot pass by only changing the arg name. The mock needs a TS port of the Rust heading-section rule that reads file content from `virtualFS`.
2. (F) A single-pass "any of the tags" scan with ONE shared `in_matching_section` / `section_level` state is NOT the union of the per-tag results. The Rust scanner resets `section_level` whenever a heading contains the tag (`src-tauri/src/vault/parsing.rs:1749-1759`). Example: `# A #to-list`, `## B #work`, `- t1`, `## C`, `- t2`. Tag `#to-list` alone keeps t1 and t2 (level 2 > 1). Tag `#work` alone keeps t1. A shared state sets `section_level = 2` at B and drops t2, so it loses a task that the `#to-list` filter listed before the change. The ticket says "keeps a task when its heading section matches any of the tags" and "each tag matches with today's rule", so the faithful implementation keeps one (active, level) state PER TAG and keeps a line when any tag is active. Issue 115 later keeps "the any-of-several-tags rule", so this is the semantic to lock in with a test.
3. (F) The existing Rust section tests call `tasks_in_section(candidates, "#to-list", ...)` with a `&str` (`src-tauri/tests/commands/vault_test.rs:1075, 1094, 1102, 1133`). A `&[String]` parameter cannot accept that, so "the existing section tests pass unchanged" can only mean their assertions are unchanged; the four call sites need a mechanical edit (`&["#to-list".to_string()]`). No generic bound avoids this.
4. (F) The Rust red test is compile-red, not assertion-red (a slice where `&str` is expected). That is still a valid "fails today". The TS tests are assertion-red.
5. (F) Predecessor 108 is the reason the placeholder change is safe: the e2e spec finds the box by `getByRole('textbox', { name: /section tag/i })` (`e2e/specs/tasks-view.spec.ts:20, 31, 42, 69, 99`), and today the accessible name comes from the placeholder `section tag` (`TasksView.svelte:130`; there is no `aria-label` at HEAD). 108 adds `aria-label="Section tag"`. Before editing the placeholder, confirm the `aria-label` is in the view; if not, the whole e2e spec loses its locator.

## 4. Ambiguities and the most likely reading

- A1. Per-tag state vs shared state in Rust. Ticket: "keeps a task when its heading section matches any of the tags. Each tag matches with today's rule." Reading: per-tag state, i.e. the union of single-tag results (finding 2). A shared scan is simpler but regresses the nested case and changes the 1-tag behavior in no test; only the new nested test catches it.
- A2. Signature of `describeTaskRule` / `explainEmptyTasks`. Ticket says they say "#to-list or #work" but not how the tags arrive. Reading: keep `sectionTag: string` (108's contract and tests; 111/238/243 reference it) and call `parseSectionTags` inside.
- A3. Joining three or more tags. The ticket shows only two (`#to-list or #work`). Reading: `join(' or ')` for any N ("#a or #b or #c"); no Oxford comma or commas, to stay literal.
- A4. Bare `#` token and trailing separators while typing. Ticket: "drops empty tokens", "adds a leading `#` to a token that lacks one". A lone `#` is not empty, so it stays `#` and matches any heading that contains a `#`; the Rust side already behaves that way for a lone `#` today. While a user types `#to-list #` the 400 ms debounce can fire and run the disk scan with a very broad extra tag. Reading: follow the ticket literally and do not special-case; mention this in the report. (Dropping a bare `#` would be a defensible one-line improvement but is a behavior the owner did not ask for.)
- A5. "Tag is set" for the Clear tag button and the empty-state action (108 text: "when the section tag is set"). With several tags, text such as `,` is a non-empty string but an empty tag list. Reading: "set" means `parseSectionTags(...).length > 0`; consistent with the service, which would call `get_all_tasks_v2` for `,`.
- A6. Textbox width. The input is `w-28` (7rem, with `pl-5 pr-2`, about 84px of text area) at `TasksView.svelte:131`. `#to-list #work` at `text-xs` is about 14 characters and probably does not fit; three tags certainly do not. The ticket changes only placeholder and name. Reading: widen modestly (for example `w-44`) as part of the textbox change; unverified visually because I did not run the app. It is a class change on the input, not on the toolbar element, so `pane-toolbar.test.ts` is not affected.
- A7. Case sensitivity in dedupe. Matching stays case-sensitive (ticket note), so `#Work` and `#work` are different tags and both are kept. Reading: dedupe is exact-string after `#` normalization.
- A8. Rust handling of an empty or all-blank list. The TS side never sends one. Reading: keep the existing fall-through (`extract_tasks`, all tasks) so the command is total and consistent with today's empty-string behavior; cover it with a unit test.
- A9. E2E fixture. The ticket says "add a second tagged heading to the fixture vault if none exists". None exists, but editing shared fixtures leaks `#work`/`#to-list` into tag, search and count assertions of other specs (risk R4). Reading: create the notes inside the test via `__e2e.fs.writeFile` + `vaultIndex.update`, which meets the intent without the cross-spec risk.
- A10. Mock fidelity. The ticket asks only to "update" the mock. Reading: the mock must gain the heading rule (finding 1); matching note tags cannot satisfy the new e2e test. Keep it minimal (one pass, per-tag state, fences by the same `^\s*```` test the mock's `parseTasks` already uses).
- A11. Ticket text says the rule lives in "`tasks_in_section`, `extract_tasks_from_section` in `src-tauri/src`". Correct locations are `src-tauri/src/commands/vault.rs:694` and `src-tauri/src/vault/parsing.rs:1721`.
