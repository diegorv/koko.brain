## 4. Ambiguities (where an implementer must guess) and the most likely reading

- **A1. `rowsByNote(rows: VisibleRow[])` cannot return the unfiltered `total`.** The ticket gives the one-argument signature and says `total` is "the note's task count before any filter". But `applyQuickFilters` drops failing rows that have no passing descendant (that is the whole filter), so the visible input no longer contains them. The ticket's own test line ("`rowsByNote`'s `total` counts every task of the note") is unsatisfiable as written. Likely intent: a second parameter with the unfiltered rows (`rowsByNote(visible, allRows)`), computing `total` per `filePath` from `allRows`. Alternatives: store a `noteTotal` on each row (adds a field the ticket's `TaskRow` list does not have) or compute totals in the store. I would take the second parameter; it keeps `TaskRow` as specified and matches Issue 112's later `groupTaskRows`.
- **A2. Where "before any filter" counts from.** Rows come from the section-tag-limited fetch, so `total` counts tasks Rust returned for that note, not every task in the note on disk. This matches 236's wording ("from the unfiltered `tasksStore.fileTaskGroups`", which is also tag-limited). Take it as intended.
- **A3. Order of the date cutoff and the quick filter.** Today the date filter runs first (group-level), then hide-completed (`TasksView.svelte:47-49`), and 108 relies on that for its stage 3 wording. Keep: cutoff first, then `applyQuickFilters`. A parent row in a note outside the date window never appears.
- **A4. What N in the header's "N of M open" counts after 111.** 236 defines N as the note's open tasks among the listed ones, M as the unfiltered total. Now that dimmed rows are listed, N could mean open rows in `note.rows` (dimmed included) or open and not dimmed. Likely reading: `note.rows.filter(r => r.open).length` regardless of `dimmed`, because "open" is a task property and 236's example ("2 of 3 open" with hide-closed on and off) never meant "matching the filter". Under Status: Closed it would read "0 of 3 open" with only closed rows listed. The toolbar count, by contrast, is explicitly non-dimmed only.
- **A5. Fate of `filterByDate`.** The ticket's delete list names four functions and not `filterByDate`, but after 111 nothing calls it (the view moves to `applyEditedCutoff`; `tasks.service.ts:16-18` only mentions it in a comment). CLAUDE.md says remove what your change orphans. Likely intent: either keep it until 238 (which "replaces" the date pills) or delete it with its three test cases, moving them to `applyEditedCutoff`. I recommend deleting it and porting its tests, and saying so in the commit; if the owner wants it kept, leave it and its tests untouched.
- **A6. `rows` as deep `$state` or `$state.raw`.** The ticket only says "store ... `rows`". Rows are replaced wholesale and never mutated, so `$state.raw` avoids deep proxying thousands of rows and keeps `Object` identity for the derived. `fileTaskGroups` (deep `$state`, `tasks.store.svelte.ts:4`) is the precedent for the opposite. Both satisfy the ticket; `$state.raw` is the cheaper, but pick one and say why. If `$state.raw` is chosen, `toBe` identity assertions in tests become possible.
- **A7. The status list and its order.** The menu needs the seven statuses in a fixed order; no such constant exists in the repo (`grep` for `'in-progress'` finds only `todoist-sync/vault-scan.service.ts:23`). 110 may or may not export one. Likely: a `TASK_STATUSES: TaskStatus[]` in `task-status.logic.ts` in 110's table order (todo, in-progress, done, cancelled, question, important, forwarded), with `statusGlyph(s).word` as the label. Check the branch first.
- **A8. Word versus raw value in the trigger and the sentence.** "the chosen statuses joined with `, `" and "`Tasks that are <statuses joined with ' or '>`". Likely the `statusGlyph(...).word` ("in progress", not "in-progress"), since the checkbox labels are those words. Also the array order: canonical order (stable label, stable `toEqual` in tests) rather than click order; toggle inserts in canonical order.
- **A9. Pieces the ticket requires but does not name.** (a) A pure toolbar count (`{ tasks, notes }` from `VisibleRow[]`: tasks = not dimmed rows, notes = distinct `filePath` among them) and its label ("N open in M notes" vs "N tasks in M notes", singular forms); the view test pins the strings, so unit-test the helper. (b) The trigger label (`open`/`closed`/`all`/statuses). (c) Whether the count renders while the list is empty or loading. Likely: render the count whenever `hasLoaded` (so "0 open in 0 notes" is visible with the empty state's explanation), hidden before first load; TagsView hides its count only while loading (`TagsView.svelte:52`). The ticket moved the count "from the list body", where it was inside the non-empty branch (`TasksView.svelte:139-146`), so keeping it non-empty-only is also defensible. Choose, and add a test either way.
- **A10. Which radio is checked while `statuses` is non-empty.** "A non-empty `statuses` wins over `show`" but says nothing about the radio group. Likely: none checked (`value=''`), so the menu does not claim a mode the filter is ignoring. `show` is kept in state and returns when the user picks a radio (which clears `statuses`).
- **A11. Does Status: Closed make sense with the empty-state wording "No task has the chosen status".** The ticket's wording applies to every case other than "show open and all closed". With `show:'closed'` and no closed tasks it reads slightly off ("chosen status" for a mode). Follow the ticket literally; flag it to the owner as a copy nit. Also unspecified: whether the `Show all` action attaches to both status-stage messages. Likely yes (the ticket gives one action for the stage).
- **A12. Date-stage wording for non-open `show`.** 108's stage 3 has two texts keyed on hide-completed (open vs not). With `show:'closed'` or `statuses` there is no spec. Likely: "No open task is in a note edited in the last N days" when `show==='open'` and no statuses, else the generic "No note with tasks was edited in the last N days". Acceptable, a "closed" variant would be an extension.
- **A13. `folder` for a path outside the vault and for a null vault path.** Ticket: `folder` = part of `relPath` before the last `/`. But 236 says a path that stays absolute gets no subtitle. If `buildTaskRows` follows the ticket literally, an outside-vault note's `folder` is its absolute directory and the header (now reading `note.folder`) would show it, contradicting 236. - **A14. `modifiedAt` on every row.** Copied from the group (ms), so every row of a note carries the same value. `rowsByNote` takes `modifiedAt` from the note's first row. Intended.
- **A15. `quick.statuses` empty array versus `undefined`.** `statuses?: TaskStatus[]`. Treat both as "no status set" in `applyQuickFilters` and in labels. `setQuick({ show, statuses: undefined })` leaves an own key with value `undefined`; `toEqual` treats it like a missing key, `toStrictEqual` does not. Use `toEqual`, or have `setQuick` drop undefined keys.
- **A16. Rule sentence when both `show` and `statuses` are set.** `statuses` wins: "Tasks that are done or cancelled". - **A17. `today` for 109's chips.** 109 says the view reads `today` "when the rows are rebuilt". Rows do not exist until 111. Likely 109 computes it in the view from the groups; 111 should leave that code alone (do not move chip computation into `buildTaskRows`).
- **A18. Dimmed rows and 110's styling.** A dimmed row is a closed (or non-matching) row; 110 strikes closed rows through. Under `Status: Closed`, an open parent above a closed child is dimmed but must not be struck through (it is open). ## 5. Risks

**R1. Contradiction in the ticket (A1).** The `rowsByNote` signature versus the `total` requirement. Resolve before writing the test; otherwise the "failing test first" for criterion 4 is not writable.

**R2. First module-level `$derived` in any store.** No precedent in `src/lib` (grep). ADR-0034 permits it and two probe tests pin the behavior (`src/tests/lib/svelte-derived-sync.test.ts`, `.client.test.ts`, fixture `src/tests/fixtures/derived-sync.svelte.ts`). Under vitest's node environment the derived re-runs on every read (no caching), so the store test pins values only; a caching assertion would need jsdom. In the app (client runtime) it is memoized. `Date.now()` inside the derived is not a dependency, so a view left open across the 7-day boundary does not refresh until another dependency changes; acceptable, mention in a JSDoc line. Do not export the derived directly (`derived_invalid_export`).

**R3. Row identity and `{#each}` keys.** `visibleRows` returns new objects on every recompute (`{...row, dimmed}`), so each change re-creates row objects. Keyed `{#each ... (row.lineNumber)}` inside a note keeps DOM nodes, but inline handlers close over the new `row`; `toggleTask` reads `task.text`/`task.status`/`task.lineNumber` at click time so it always sees the current row. Do not cache `row` in non-reactive variables. Performance: a recompute is O(rows); ticks of the section tag textbox (400 ms debounce) are not a concern.

**R4. Reactivity gap between `setFileTaskGroups` and `setRows`.** Both writes are in the same sync block after the `await`, so effects batch; the view no longer renders from `fileTaskGroups` but 108's empty-state `explainEmptyTasks` now reads `rows`. If an implementer leaves any read of `fileTaskGroups` in the view (236's header `total`, 108's `groups`) the two stores could be momentarily inconsistent in tests that write only one. Make the view read `rows` only; the ticket says "after this Issue nothing renders from it".

**R5. `relativePath('', filePath)` strips the leading slash.** `relativePath` tests `filePath.startsWith(vaultPath + '/')` (`path.ts:99`); with the ticket's `vaultStore.path ?? ''` fallback an absolute path matches and loses its first slash, giving `relPath` `vault/Projects/x.md` and `folder` `vault/Projects`. The first describe of `TasksView.test.ts` never opens the vault (`vaultStore` is only `open('/vault')` in the second describe, :203), so a header-subtitle assertion there would see a fake folder. In production the vault is open whenever tasks load (`resetTasks` and `initializeVault` ordering unchecked by me). Mitigation: tests that assert folder/subtitle open the vault (236's tests already do per its AC); consider `vaultPath ? relativePath(...) : filePath` in `buildTaskRows` (also fixes A13).

**R6. Predecessor tests are the larger part of the TasksView.test.ts churn.** 108, 110, 234, 236 and 109 add many component tests, several of them calling `setHideCompleted`. The 111 agent starts in a fresh context and must grep `setHideCompleted` / `hideCompleted` / `Show completed` / `showCompleted` / `completed` across `src/tests/lib/features/tasks/` and rewrite each, including text assertions that say "completed". Missing one fails `pnpm check` (`setHideCompleted` removed) so the type check is the safety net, but string assertions like "Show completed" fail only at runtime.

**R7. bits-ui menu behavior to verify rather than assume.** Verified in `node_modules/bits-ui` 2.20.4: `closeOnSelect` exists on item, checkbox-item and radio-item (`types.d.ts:69,104,199`; honored at `menu.svelte.js:1094`); `role="menuitemradio"` (:1437) and `menuitemcheckbox` (:1304); the dropdown trigger opens on pointerdown (button 0) and on a click with `detail === 0` (:1455-1480). Real-browser e2e: Playwright's click sends pointerdown (opens) and a click with `detail 1` (ignored), so no double toggle. The shadcn checkbox wrapper declares `checked = $bindable(false)`; pass `checked={...}` from the store and update the store in `onCheckedChange`, never bind to local state. If the radio group is controlled with `value=''` while `statuses` is set, the radio `isChecked` derived (`menu.svelte.js:1424`) is false for all three: OK.

**R8. `pane-toolbar.test.ts` and `menu-item-anatomy.test.ts`.** The toolbar test needs exactly one class list with `pane-toolbar` and none of the override classes. The filter row's class list is a different list, but a careless `class="pane-toolbar ..."` copy would break it. The toolbar test regex reads only static `class="..."` attributes (`pane-toolbar.test.ts:41`), so do not build the toolbar class dynamically. The anatomy test fails on `ml-2`/`mr-1` and `text-xs` inside any `DropdownMenu*Item`/`RadioItem`/`CheckboxItem` element, including an icon inside it.

**R9. Architecture tests (verified by reading the tests, not run).**
- `pure-logic.test.ts`: `task-query.logic.ts` may import only pure files; it must not import the store, `vaultStore` or any `.svelte`. `buildTaskRows` takes `vaultPath` as a parameter for that reason. `tasks.logic.ts` is already imported by logic; the new file importing it (for `parseSectionTags`) is allowed (`.logic` -> `.logic`).
