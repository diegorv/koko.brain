## 4. Ambiguities (where the implementer would have to guess)

- **A1. What is a "whole tag token"?** The ticket says: appears as a whole tag token, case-insensitive, in any ancestor heading. It does not define the boundary. Likely intended: the tag is a whitespace-delimited word of the heading, so `#to-list` matches `Inbox #to-list` and `Inbox (#to-list)`, not `#to-listing`, not `#to-list/sub` (nested tag is a different token), not `x#to-list`. Pick the tokenize-and-compare approach: no regex escaping and no lookbehind (WebKit lookbehind support is recent; avoid depending on it). Not in the ticket: whether `#to-list,` or `#to-list.` count (the trim set above says yes), and whether a nested `#to-list/sub` should satisfy `#to-list` (the note-tag rule of 239/116 does prefix-match; the ticket for headings says whole token, so no). State the choice in the commit and pin it in a test. A lone `#` tag (user typed `#`): `parseSectionTags` (242) keeps it as `#`; `matchesHeading` should treat it as matching a bare `#` token only; low value, do not special-case.
- **A2. Where the section filter runs.** The ticket says "the section tag textbox and the rule sentence use it" and "an empty list keeps every row" but never says whether `tasksStore.rows` is already section-limited. Reading used here: **limited in `buildTaskIndex`** (rows = built rows `.filter(matchesHeading)`), which keeps every predecessor contract intact: 108/111's empty state stage 1 ("No task sits under a heading containing ..." is decided from `tasksStore.rows` being already section-limited, as the Rust side did), 236's "N of M open" total (before quick filters, after the section), 242's `updateSectionTagFilter -> buildTaskIndex` refetch, 234's textbox debounce. The alternative (store holds all tasks, a `visibleRows` stage applies the tag) is what 116 will build ("heading source cards" over `row.headings`), and then the empty-state stage and the total change; do not do it in 115. Consequence to note: a section-tag change re-runs `buildTaskRows` over the whole snapshot (cheap, no IPC).
- **A3. Where the overlay lives.** Ticket: "`afterTaskWrite` records ... in an overlay". Candidates: module-level Map in `tasks.service.ts` (recommended: the store is "reactive state only", and a plain Map in it contradicts CLAUDE.md "Stores"), or a `tasksStore` field. The cost of the service-level Map is test hygiene: `tasksStore.reset()` in `beforeEach` does not clear it (only `resetTasks()` does), so a leftover entry keyed `/vault/a.md:1` with `version: 1` while `vaultIndexVersion` is `0` in tests would leak into the next test (R2). Either clear it via `resetTasks()` in each `beforeEach` or export a tiny test-only reset; the store variant would be cleared by the existing `tasksStore.reset()` calls for free. Pick one and put it in the commit; the dossier recommends the Map in the service plus `resetTasks()` in the test `beforeEach`s.
- **A4. Overlay entry shape and guard.** The ticket says text, status, version. A status write leaves the text unchanged, so `text` is the row's own text. If a later write (122, not in the chain) changes the text, the overlay would patch `text` but not `metadata` (chips, `description` stay old for up to 10 s; dossier-122 A5). Not 115's problem, but do not claim more in the docs. Guard against a shifted line: the overlay is keyed by line number, so an edit that moves lines inside the 10 s window would paint the overlay on another task. Ticket says nothing; the version drop bounds the exposure. Most likely intended: no extra guard. Cheap optional guard: also store the pre-write `text` and apply only while the snapshot row's text equals it (one comparison). Avoid unless you hit a case; "no code for rare races".
- **A5. The stale-refusal refetch.** *(Gap, not in the ticket.)* `setTaskStatus` on `stale` (and the dirty-buffer "line moved" path, `tasks.service.ts:141-145`) calls `buildTaskIndex()` to "refresh the list", then toasts "...so the list was refreshed. Try again." After 115 that call returns the memoized snapshot, which is the very snapshot that just proved stale, until the next version bump (2 s, 10 s in a burst). The user retries and is refused again. At HEAD the same call read the live Rust index, so this is a regression. Readings: (i) call `invalidateVaultEntries()` right before the stale/line-moved `buildTaskIndex()` so it reads a fresh whole snapshot (one multi-MB IPC, user-initiated and rare, shared by every consumer afterwards); (ii) leave it and accept the retry loop (contradicts the toast's promise). Recommended: (i), plus delete the overlay entry for that key on stale, and tell the owner. It stays inside the Tasks service and uses an existing core export (`vault-entries.service.ts:45`). Note it only helps when Rust's index already holds the newer disk state; for an external edit not yet picked up by the watcher the index is stale too and the next event fixes it. The same ticket text reasons about the `afterTaskWrite` direct refetch and does not mention this path. Test shape if (i): prime the memo with a stale entry, fake Rust says stale, the next `get_all_vault_entries_v2` returns the fresh entry, assert `rows` shows it and `invoke` saw a second entries read. The old test "refetches ... when the line is stale" encodes exactly this and cannot be re-pointed without choosing.

Then every hand-built `TaskRow` in tests from 111 to 241 needs the seven fields, so rely on the shared builder with defaults. ## 5. Risks

- **R1. The memo makes tests share state (highest test risk).** `vaultEntriesMemo` (`vault-entries.service.ts:26-29`) is module state keyed on `vaultStore.vaultIndexVersion`, which is `0` in every test unless a test bumps it (`_reset` sets 0, `vault.store.svelte.ts:153`). Test 2 in a file reuses test 1's cached Promise: `mockResolvedValueOnce` values never get consumed and rows leak across tests. Every tasks test `beforeEach` must call `invalidateVaultEntries()`. Also the same applies to `TasksView.test.ts` and the dirty-buffer file.
- **R2. Concurrency semantics changed for the seq-guard tests.** `get()` shares one Promise per version (`inflight.ts:146`), so two overlapping `buildTaskIndex()` calls at one version issue **one** IPC. The existing "older call resolves last" and "stays loading while a newer call is in flight" tests rely on two distinct IPCs. To rebuild them: bump the version between the calls, or `invalidateVaultEntries()` between them, and resolve two deferred promises. Also the overlay Map leaks between tests (A3): use `resetTasks()`.
- **R3. Never mutate the shared snapshot.** `getVaultEntries()` hands the same array and entry objects to QueryJS, wikilink completion and the listener (`vault-entries.service.ts:36`; `patchEntriesSnapshot` relies on identity of untouched entries). In `buildTaskRows`, do not `entries.sort(...)` (use filter then sort the filtered copy), do not push into `entry.tasks`, and do not edit `entry.frontmatter` (rows hold it by reference as `properties`). Spread each task into a new row object. Add a test asserting the input is deep-equal and in the same order after the call.
- **R4. Staleness gaps the ticket does not cover.** (a) Stale-refusal refetch returns the stale snapshot (A5). (b) Mounting the Tasks tab right after saving a note in the editor now shows the previous snapshot for up to 2 s (10 s in a burst): `get_all_tasks_v2` at mount read the live index. The ticket accepts snapshot freshness (PRD B6 (a)); it only repairs the view's own writes. Flag once, do not fix (memory: no core changes for corner cases). (c) The Todoist sync's `write_task_lines` goes through `settleTaskWrite` without a prompt refresh, so the view lags as it did before. (d) A failed `get_index_delta` patch rejects the memo promise (`tauri-listeners.service.ts:256-265` then `invalidateVaultEntries()` + `fullRefresh()`): a `buildTaskIndex` that joined the failing promise sets `tasksStore.error` (234), the Retry button recovers.
- **R5. Overlay drop rule is sound, but only with the real ordering; verified.** In `refresh()` (`tauri-listeners.service.ts:267-275`) `bumpVaultIndexVersion(latestVersion)` runs first, then `incrementalRefresh` calls `patchVaultEntries` synchronously, and `install()` stamps the patched Promise with the **new** version. The Tasks effect on `vaultIndexVersion` runs afterwards in a microtask, so its `getVaultEntries()` receives the patched (or freshly fetched, on `fullRefresh`) Promise, which includes the write because `get_index_delta` runs after the write. So `vaultIndexVersion >= write.version` implies the snapshot read at that version includes the write. Edge cases checked: the bump arriving before `afterTaskWrite` records the entry (the entry is pruned on its first `buildTaskIndex`, the read is already post-write); a prompt-flag consumed by an earlier unrelated event (the write's own event is then throttled to 2 s; the overlay carries the row meanwhile); a no-op/stale command leaves `promptIndexRefresh` set because Rust emits nothing (`toggle_task_status` emits only when `changed`), so the next unrelated event refreshes at once, harmless. Read `vaultIndexVersion` **before** the await in `buildTaskIndex` (R5 depends on it); reading it after the await could prune an entry using a version the fetched snapshot never reached.
- **R6. `TaskRow` literal fan-out.** New required fields (A6) break `pnpm check` in every hand-built row across `task-query.logic.test.ts` (111 to 239, 112 groups) and `TasksView.test.ts`. Mitigate with one builder with defaults; expect a long type-error list on the first `pnpm check`.
- **R7. `$state` deep proxy over rows holding frontmatter.** If 111's store declared `rows` with `$state` (not `$state.raw`), the whole row list including each note's `properties` object becomes a lazily proxied tree. The repo precedent is `$state.raw` for big replaced-wholesale arrays (`fs.store.svelte.ts:8-11`, 40k nodes). Check the landed store; if it is `$state`, consider `$state.raw` for `rows` (rows are replaced, never mutated). Not verified for the owner's vault size; not required by the ticket. Do not store a derived copy of the snapshot elsewhere.
- **R8. ADR-0034 getters.** No new getter is added by 115. The existing `visibleRows`/`groups` deriveds recompute on each `setRows` (every refetch, as before). Their tests (111, 112) keep passing as long as rows keep the same shape. If the overlay moved into the store (A3) it would need a getter and a test.
- **R9. Layer and cycle tests.** `features/tasks -> core/vault/vault-entries.service` and `-> core/vault/vault.store` are features -> core: allowed (`layer-rules.test.ts`). `task-query.logic.ts` must stay free of `.service.ts`/store imports (`pure-logic.test.ts` walks the graph; `vault-v2.types.ts` is a `.types.ts`, whose edges are not followed).
