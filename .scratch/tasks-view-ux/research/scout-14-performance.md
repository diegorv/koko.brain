# Scout 14: Performance of the Tasks view

Read-only research. Nothing was measured or run; every cost below is derived from reading code and is labeled as an estimate where it is one. Paths are relative to the repo root.

## Summary

The Tasks view fetches the whole task set over IPC, converts it, filters it and renders it as one flat DOM tree with no windowing. Every `vaultIndexVersion` bump, every toggle and every section-tag keystroke (after 400 ms) triggers a full refetch, and the default `#to-list` tag makes each refetch re-read from disk every note in the vault that has tasks. During each refetch the whole list is replaced by an "Indexing tasks..." message, so the list is destroyed and rebuilt and the scroll position is lost. The app already ships `virtua` (`VList`) and uses it in the note list, so windowing is a known, available pattern; the redesign should flatten groups into one row array and render it through `VList`, keep the previous data visible while refetching, and move date/hide-completed filtering to a place that does not pay for a full re-read.

## Facts (verified in code)

### Data path

- F1. `TasksView` fetches on mount and on every `vaultStore.vaultIndexVersion` change through one `$effect` that calls `buildTaskIndex()` inside `untrack`: `src/lib/features/tasks/TasksView.svelte:71-78`.
- F2. `TasksView` is only mounted while the Tasks tab is active (`{#if isTasksTab}` in `src/lib/app/EditorView.svelte:72-73`), so every return to the tab runs a fresh fetch (mount effect) and the effect stops when the tab is not active. Task index is deliberately not built at vault init: `src/lib/app/lifecycle/app-lifecycle.service.ts:407-410`.
- F3. `buildTaskIndex` sets `isLoading` true at the start of every call (`tasks.service.ts:67`), calls `get_tasks_in_section_v2` when the trimmed tag is non-empty, else `get_all_tasks_v2` (`tasks.service.ts:70-73`), maps every group and every task through `fromV2` (`tasks.service.ts:20-48,75`), writes the store, then loops again over all groups to count tasks for a debug line (`tasks.service.ts:76-79`). A latest-wins sequence guard exists (`tasks.service.ts:55,66,74`).
- F4. `fromV2` copies every task and re-copies all 14 metadata fields field by field, so every refetch allocates a fresh object graph: `tasks.service.ts:25-45`. The result replaces `fileTaskGroups` wholesale (`tasks.store.svelte.ts:21`), so every row gets a new `task` object identity on every refetch.
- F5. The store default `sectionTag` is `#to-list` (`tasks.store.svelte.ts:8`, reset at `:30`), so by default the section command runs, not the index command. The field is not persisted (open issue `.scratch/open-itens/issues/227-tasks-help-says-default-view-lists-only.md`).
- F6. `get_tasks_in_section_v2` (`src-tauri/src/commands/vault.rs:741-758`): copies the candidate paths (entries with at least one task) under a read lock (`:747-752`), then on a blocking thread calls `std::fs::read_to_string` for each one and runs `extract_tasks_from_section` (a line-by-line scan with a heading regex and fence tracking, `src-tauri/src/vault/parsing.rs:1721-1761`) (`vault.rs:694-730`). The cost is O(notes with tasks) file reads plus O(total lines) scanning, on every call, with no caching. The code's own doc comment says so: `tasks.service.ts:88-95`.
- F7. `get_all_tasks_v2` is a plain `#[tauri::command] pub fn` (not `async`) that clones every entry's `tasks` under a read lock and sorts: `src-tauri/src/commands/vault.rs:651-660`, `src-tauri/src/vault/index.rs:1070-1084`. The repo's own comment treats non-async commands as main-thread (`vault.rs:737-738`: "Async so Tauri runs it off the app main thread"). `get_tasks_in_section_v2` is async and avoids that; `get_all_tasks_v2` does not. The `VaultIndex` does not store headings, which is why the section path must read disk (`vault.rs:732-735`).
- F8. Each task crosses IPC as JSON with `text` plus a `metadata` object that also carries `description` (the same text with signifiers stripped) and optional dates, priority, recurrence, id, dependsOn, onCompletion, tags: `src-tauri/src/vault/task.rs:22-35,81-126`. The view uses only `text`, `checked`, `indent`, `lineNumber`, `status` today (`TasksView.svelte:169-194`). `metadata` is shipped but never read by the view. No payload was measured; a rough estimate of a few hundred bytes per task means a few MB of JSON for ~10k tasks (opinion/estimate).
- F9. Result ordering is `modifiedAt` descending, done in Rust (`vault.rs:728`, `index.rs:1082`). The view does no re-sorting.

### Refetch triggers

- F10. The version bump is throttled in `src/lib/app/tauri-listeners.service.ts`: first refresh `REFRESH_DELAY_MS = 2000` after an event, at most once per `REFRESH_MIN_INTERVAL_MS = 10_000` in a burst (`:105-109`, scheduling at `:277-288`). Because `vaultIndexVersion` is vault-wide, ANY note save anywhere in the vault bumps it, and with the Tasks tab open each bump causes a full task refetch even when no task changed. The listener's own doc comment names TasksView as a consumer (`:135`).
- F11. `toggleTask` calls `toggle_task_status`, then `afterTaskWrite` runs `settleTaskWrite` then `buildTaskIndex()` immediately (`tasks.service.ts:147-179`). Rust also emits `vault-index-updated` for the toggle (indexing rules, rule 2, `docs/agents/indexing-watcher-rules.md:5`), so the throttled bump arrives 2 s later and triggers a SECOND full refetch (and a second loading flash). Both fetches are necessary under today's design; the second is redundant for a toggle.
- F12. The section-tag input debounces 400 ms then calls `updateSectionTagFilter`, which refetches (`TasksView.svelte:31-40`, `tasks.service.ts:96-99`). Each fetch re-reads the vault's task notes from disk (F6); typing `#to-list` slowly can issue several scans, only the latest writes the store (F3 guard) but the earlier ones still run to completion in Rust.
- F13. The date filter and hide-completed are pure client-side derivations over the full fetched set (`TasksView.svelte:46-54`, `tasks.logic.ts:59-88`), so changing them costs no IPC. Good.

### Render cost

- F14. Nothing is virtualized. The whole content is `{#each filteredGroups}` containing `{#each group.tasks}` inside a bits-ui `ScrollArea`: `TasksView.svelte:137-222`. Each task row renders a wrapper div, a button with an icon component (`Circle` or `CircleCheckBig`), and a span with an inner `{#each parseTaskTextSegments(task.text)}` (unkeyed) producing text nodes, wikilink buttons or anchors: `:169-215`. That is roughly 4-6 DOM nodes plus an SVG per task, before any link segments (estimate from the template).
- F15. `parseTaskTextSegments` is a regex `matchAll` over the text per row (`tasks.logic.ts:123-161`). It runs inside the template expression, so it re-runs for a row whenever that row's block re-evaluates: once on first render, and again after each refetch because `task` is a new object (F4) and `task.text` is read from it. There is no memoization. For a few thousand short strings this is cheap CPU (opinion), but it is pure repeated work and also creates the per-row array garbage.
- F16. `{#each group.tasks as task (task.lineNumber)}` and `{#each filteredGroups as group (group.filePath)}` are keyed (`TasksView.svelte:149,169`), so a refetch that returns the same keys updates in place rather than recreating nodes, IF the list stays mounted. It does not stay mounted: see F17.
- F17. `{#if tasksStore.isLoading}` shows "Indexing tasks..." INSTEAD of the list (`TasksView.svelte:139-140`), and `buildTaskIndex` sets `isLoading` on every call (F3). So every toggle, every version bump while the tab is open, and every tag change tears down the entire list DOM and rebuilds it from scratch once the fetch resolves. The `ScrollArea` stays but its content collapses, so the scroll position is lost (the scroll container's content height drops to the message height). With the section command taking disk reads (F6) this flash lasts as long as the scan. This is the most user-visible performance defect and is a design issue, not a micro-optimization.
- F18. `filterCompleted` and `filterByDate` allocate new group objects (`{ ...group, tasks }`) each time the derived runs (`tasks.logic.ts:59-70`); `computeTaskStats` is a second full pass (`:91-113`). `hasUncheckedDescendants` rescans descendants per completed task, O(n * depth-run) worst case within one file (`:17-26`). All of these are in-memory O(total tasks) per change; not a bottleneck next to the DOM cost (opinion).
- F19. Side observation relevant to correctness of hide-completed: Rust `checked` is true for any status other than `todo` (`task.rs:25-26`), and `filterCompletedTasks` keys on `checked` (`tasks.logic.ts:40`), so in-progress or important tasks are treated as completed by "hide completed". The view's own comment acknowledges `[/]` and `[!]` are checked (`TasksView.svelte:170`). Not a performance item; flagged for whichever scout owns semantics.

### Windowing patterns already in the app

- F20. `virtua` is a dependency (`package.json`: `"virtua": "^0.54.1"`, installed version 0.54.1). The only use is `VList` in `src/lib/features/rail-shell/RailNoteList.svelte:4` (import), `:834-859` (grouped list: a flat array of header / note / empty items with `getKey`) and `:899-906` (plain list). The grouped list is directly analogous to the Tasks view: it already renders group headers and rows as one flattened `GroupedItem[]` (`:683`).
- F21. `NoteRowMenu.svelte:199-200` documents that "List virtualizers wrap every row in positioning divs", so context-menu logic uses `closest('[data-note-row]')`. Any redesign that adds a row context menu or event delegation over a `VList` must do the same. The Tasks row already carries `data-task-row` (`TasksView.svelte:173`).
- F22. `virtua`'s Svelte `VList` props include `data`, `getKey`, `bufferSize`, `itemSize`, `ssrCount`, `shift`, `keepMounted`, `cache`, `onscroll` (`node_modules/virtua/lib/svelte/VList.type.d.ts:6`); `Virtualizer` adds `scrollRef` and `scrollToIndex` (`Virtualizer.type.d.ts:44,134`). There is no sticky-header prop in these types; sticky group headers over `VList` were not verified and need a prototype or the virtua docs before promising them. `VList` owns its scroll element, so it replaces the bits-ui `ScrollArea` rather than nesting inside it (nesting would need `Virtualizer` with `scrollRef`; not verified to work with the bits-ui viewport).
- F23. No `content-visibility`, `IntersectionObserver` windowing or other virtualization exists in `src/lib` (grep over svelte/ts/css). Other scrolling lists (Tags, Backlinks) were not audited by me; only the note list is windowed.

### Indexing rules that apply (`docs/agents/indexing-watcher-rules.md`)

- R1. Rule 1: all vault metadata lives in the Rust `VaultIndex`; TS reads through `*_v2` commands and does not mirror it (`:3`). A Tasks-side TS cache of the whole vault would be a mirror and conflicts with the rule's intent; local per-panel result storage is what rule 2 allows (`:5`: "Panels store the result locally; no central TS-side mirror").
- R2. Rule 2: the reactive consumer pattern is exactly the `$effect` on `vaultIndexVersion` that TasksView uses (`:5`).
- R3. Rule 6: toggles go through `task-write.service::settleTaskWrite` into `applyNoteChange` (`:13`); that is the single owner of "bytes changed". A redesign must keep toggles on `toggleTask` and not add a second writer. Any new write action (bulk complete, edit text, reschedule) must follow the same path.
- R4. Rule 12: `getVaultEntries()` memoizes `get_all_vault_entries_v2` per version and patches by `get_index_delta` on a bump instead of refetching (`:31`). Tasks do not use this today; `NoteEntryV2.tasks` already exists in that snapshot (`buildKBPage` reads `entry.tasks`, `:31`). That is a precedent for an incremental, delta-patched consumer. It does not carry headings, so the section filter cannot be computed from it (F6).
- R5. The throttle (rule 12 text, `:31`, and `tauri-listeners.service.ts:105-109`) means Tasks can lag up to 10 s behind external changes during a burst; this is accepted as the design for panels.
- R6. `vault-index-updated` payload (`UpdateResult`) lists `upserted` and `removed` paths (`:31`; `tauri-listeners.service.ts:285-287`). That information is not exposed to `vaultIndexVersion` consumers, only to the listener.

## Problems and opportunities

1. P1 (high, user-visible): loading state replaces the list (F17). Fix is purely front-end: show the previous data while `isLoading`, use an inline spinner or subtle indicator, and only show the full-page loading text when there is no data yet (initial mount). This also keeps scroll position and stops DOM teardown.
2. P2 (high at scale): no windowing (F14). Thousands of tasks mean tens of thousands of nodes and SVGs. `virtua` `VList` over a flattened `[header, task, task, header, ...]` array is the proven in-repo pattern (F20).
3. P3 (medium): every vault-wide save refetches all tasks (F10), and with the default tag each refetch does O(notes with tasks) disk reads (F6). Options, cheapest first: (a) skip the refetch when the bump carried no task-relevant change (needs the listener to expose upserted paths, or a cheap `tasksVersion`/hash from Rust); (b) cache the section-scan per file keyed by `modified_at` on the Rust side; (c) make the section filter index-side by storing the heading (or a `section` string per task) in `Task` at parse time, removing the disk read entirely and making `get_all_tasks_v2` the only command. (c) is the structural fix but is a Rust and DTO change (ts-rs bindings, `src/lib/contracts/generated/`) and changes `extract_tasks` behavior, which is a core parsing path.
4. P4 (medium): a toggle causes two refetches (F11). The immediate one is needed for responsiveness; an optimistic local patch of the toggled task (flip its status in the store from the `toggle_task_status` result) plus letting the throttled bump reconcile would avoid the first refetch and the flash. This touches `tasks.service.ts` semantics and its stale-result handling, so it needs tests first.
5. P5 (medium): `get_all_tasks_v2` is a sync command and clones all tasks under the lock on the main thread (F7). At scale that blocks the UI thread for the clone and sort. Making it `async` or `#[tauri::command(async)]` (`vault.rs:1210` shows that form is already used) is a small Rust change; verify with the `CmdTrace` timings before committing to it.
6. P6 (medium): the redesign will likely want more than five fields. Today `metadata` is shipped but unused (F8). If due date, priority and tags are to be shown, the payload is already paying for them. If not, dropping `description` (duplicate of `text`) or serializing only displayed fields would cut IPC size, but that is a DTO change.
7. P7 (low): `fromV2` deep-copies for no reason beyond the ms conversion of `modifiedAt` and the loop to count (F4). It could mutate in place or convert lazily. The cost is small next to IPC and DOM; do it only if profiling shows it.
8. P8 (low): `parseTaskTextSegments` per render (F15). With windowing the number of rendered rows is bounded (tens), so memoization is unnecessary. Without windowing, memoize per task via a derived/`Map` keyed by `text`. Prefer windowing.
9. P9 (low): in-memory derivations (`filterByDate`, `filterCompleted`, `computeTaskStats`) allocate new group objects per change (F18). If the redesign adds search text filtering, status/priority/tag facets and grouping modes, fold them into one pass that produces the flat row array, so the pipeline is one O(n) pass and the stats come from the same loop.
10. P10 (design hazard): adding a client-side text search box means filtering thousands of tasks per keystroke. With a single pass over the fetched array plus `VList` this is fine; do not issue an IPC per keystroke and do not re-read the disk (the section tag input already shows the cost of that, F12).
11. P11: the 400 ms section-tag debounce plus a disk-reading command (F12) is a smell for a better design: either make the section filter index-side (P3c) so it is instant, or apply it client-side on a `section` field.

## Recommendations for the redesign

Ordered by cost and independence, written so each can be its own vertical slice:

1. Keep stale data on screen while refetching (P1). Show the loading state only when there is no data. Add a store test that asserts the groups remain readable while `isLoading` is true. Smallest, highest-value slice and prerequisite for scroll-preserving toggles.
2. Introduce a pure `.logic.ts` function that turns filtered groups into one flat row array with stable keys (header rows and task rows, plus a count per header) and render it through `VList`, as `RailNoteList.svelte:834-859` does (P2). Keep `data-task-row` on rows and use `closest()` delegation (F21). Replace the `ScrollArea` for this view. Verify sticky headers, `shift`, and `scrollToIndex` against the virtua docs before promising them (F22).
3. Reduce refetch churn (P3, P4): at least stop the double fetch after a toggle, and decide whether bumps unrelated to tasks may be ignored. A cheap, honest first step is an equality check on the fetched result (same file paths, same `modifiedAt`, same task list) before writing the store, so an unchanged refetch causes no re-render at all. Keep the existing latest-wins guard.
4. Remove the disk read from the default path (P3c/P11) only if the owner wants the section filter to stay as a first-class concept; this is the one change with real blast radius (Rust parser, DTO, bindings, two commands). Treat it as a separate, later ticket behind the UX slices, per the project's rule against core changes for corner cases.
5. If new filters and grouping are added (status, priority, due date, tag, text search, group by file/date/section), compute them in one derived pass in `tasks.logic.ts` and test the logic without mocks, per the repo testing rules.
6. Pick the fields the new UI shows and decide whether `metadata` stays in the payload (P6).
7. Make `get_all_tasks_v2` async if the unfiltered path becomes the default (P5), since it is the path a redesign without the default `#to-list` filter would hit.
8. Add timing visibility before and after: `buildTaskIndex` already logs `buildTaskIndex completed in Xms` and `Tasks: N files, M tasks` through `debug('TASKS', ...)` (`tasks.service.ts:69,79`), and `CmdTrace` wraps both commands (`vault.rs:655,746`). Use the session log to get real numbers on the owner's vault before sizing the work.

## Open questions for the owner

1. How many tasks and how many notes with tasks are in your real vault, and how long does `buildTaskIndex completed in ...ms` say a refetch takes (log in `~/Library/Logs/com.diegorv.kokobrain/` with debug logging to file on)? Without this, windowing is justified by design (no upper bound on DOM) but not yet by a measured problem.
2. Is the `#to-list` section default intentional for your workflow, or an accident of the old design (open issue 227 documents it as surprising)? The answer decides whether the section scan stays and so whether P3c is worth doing.
3. Do you accept the list showing slightly stale data for up to 10 s during bursts (existing throttle), or must the Tasks view refresh faster than other panels?
4. Should "hide completed" treat in-progress and important tasks as not completed (F19)? It changes both filtering and the counts.
5. Do you want sticky file headers while scrolling, collapsible file groups, or a flat list with a file label per row? Sticky headers over `VList` are unverified and collapsing groups changes the flat-array logic.
6. Are you willing to accept a Rust and DTO change (section stored per task, or fewer metadata fields) as a separate later slice, or should all slices stay front-end only?
