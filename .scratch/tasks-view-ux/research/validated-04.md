## Missed by both scouts

1. **The view unmounts on every tab switch, not only on close.** `EditorView.svelte:72-73` renders `TasksView` only while it is the active tab. Switching to a note and back remounts it: the version `$effect` runs again (`TasksView.svelte:73-78`), so each return pays the full disk re-read (with the default tag) and the "Indexing tasks..." flash, scroll is lost, and a pending debounced tag is dropped on a plain tab switch. Issue 108's "list stays mounted" covers refetches, not remounts: on remount `fileTaskGroups` is still populated, so 108's `isLoading && groups.length === 0` rule already avoids the flash there, but scroll position and any component-local state (`sectionTagInput`, future selection or keyboard cursor) still reset. Any new local UI state (expanded groups, selected row) must live in the store or it resets on every tab switch.
2. **The e2e mock implements a different filter from Rust.** `e2e/mocks/vault-index.ts:489-495` matches note-level tags (`entry.tags`) by exact case-insensitive equality, and the mock's tags have no `#` (`src/lib/utils/tag-extraction.ts:131-146`), so `#to-list` never matches in e2e and headings are never consulted. No e2e test can exercise the heading rule today, and a slice that adds e2e coverage for the rule sentence or a non-empty tag gets results unrelated to the app. Issue 074 already plans a mock-parity fixture for headings.
3. **Existing Issue 198 owns the colour cleanup.** `198-status-colors-use-theme-tokens-test-forbids.md` (`ready-for-agent`) replaces `text-purple-400` with tokens and adds `src/tests/lib/architecture/palette-classes.test.ts`; it is in the TasksView run-in-series group. Scout 07's recommendation 7 duplicates it. Its line refs (`TasksView.svelte:184/192/252/261`, `text-green-400`) are stale: today it is `:154`, and the green icon is gone.
4. **Open Issue texts cite stale lines.** 108 cites `TasksView.svelte:154-163`, `:169-176` and `tasks.service.ts:65` (today `:124-133`, `:139-146`, `:67`); 227 cites `tasks.service.ts:68-71`; 074 and 115 cite `parsing.rs:1700-1750` and `vault.rs:736-753` (today `:1721-1768`, `:741-758`). The file shrank after the Todoist button left. New or reused tickets need refreshed references, or relay discovery spends time re-locating them.
5. **Accessibility gaps in the current toolbar.** The date pills and eye toggle carry no `aria-pressed` (`TasksView.svelte:95-121`); the eye toggle has only a `title`. Relevant if the toolbar is rebuilt (scout 12 territory, flagged here because both toolbar recommendations keep these controls).
6. **A comment goes stale when the default changes.** `app-lifecycle.service.ts:407-409` justifies not prebuilding the task index by "the default section tag makes `get_tasks_in_section_v2` read every note with tasks from disk". Flipping the default (scout 08 recommendation 2) or removing the command makes it wrong; CLAUDE.md section 8 requires updating it in the same change. Same for `tasks.service.ts:88-95` and `indexing-watcher-rules.md` rule 1, which lists `get_tasks_in_section_v2` among the `*_v2` reads.
7. **A built-in `RailAction` crosses a feature boundary.** Registering one from `features/tasks` imports `features/rail-shell`'s registry; `src/tests/lib/architecture/feature-cycle.test.ts` and its baseline guard feature cycles. Wiring it from `src/lib/app/` (as other cross-feature wiring is) avoids the question. The `RailAction` doc names mods as the example user (`rail-shell.types.ts:195-198`), so a built-in one is a design change that needs an owner decision, as scout 07 says.
8. **Tab restore across restarts.** No tab-restore code turned up for `openTabs`, `restoreTabs` or `lastOpen` in `src/lib` or the lifecycle service. If virtual tabs are not restored, filter state only needs to survive inside a session (the store already does) until the owner asks for more. Still unverified; a session-restore check belongs to scout 15.

## Net recommendations that survive

1. Keep Tasks as the singleton editor tab. No rail lens or navigator for the list. Any rail entry point (a `RailAction`) is an owner question, wired from `src/lib/app/`.
2. Keep exactly one literal `class="pane-toolbar"` in `TasksView.svelte` with no `h-*`, `p*-*`, `gap-*`, non-`b` `border-*` or `flex-wrap`. Layout goes on children (`min-w-0 flex-1`, `ml-auto`, `overflow-x-auto`). Toolbar content: title plus count, the primary controls, one trailing menu. If the toolbar moves to its own file, move its `TOOLBARS` entry in the same commit (moving the entry does not weaken the test).
3. Put the rule sentence, chips and quick filters in a plain second row below the toolbar. Fold it under a width threshold with `@container`. Check it at narrow widths with an e2e viewport test, not vitest.
4. Replace `bg-card` on the root with `bg-editor-bg` (or drop it and let the wrapper paint). Theme-builder themes can make the two differ.
5. Reuse the open chain instead of writing parallel tickets: 108 (mounted list, rule sentence, Clear, cause-naming empty states), 198 (colour tokens), 227 (help text), then 074 → 115 → 116/121, with 123/124 behind owner triage. Refresh their stale line references when they are picked up.
6. Retire the free-text section tag box only once the TS heading rule (115, which needs 074) exists. Until then, restyle nothing; give it `aria-label="Section tag"` as 108 already specifies, so the e2e role query stops relying on the placeholder.
7. Fix the match semantics in TS as 115 pins them (case-insensitive, whole-token, nested fix). Do not patch `parsing.rs` for it, since 121 deletes the command afterwards.
8. Any new view-local state (selection, expanded groups, scroll anchor) lives in `tasksStore`, because the component remounts on every tab switch.
9. Fix or replace the e2e mock's `getTasksInSection` before adding any e2e test that relies on a non-empty tag; the e2e rewrite ships in the same Issue that changes the textbox.
10. Owner decisions still open (do not decide in tickets): B1 default (recorded as (a) on 2026-11-06, scout 08 asks to reconfirm), whether Calendar follows the view's rule, whether Cmd+Shift+T keeps closing the tab, a rail entry point, and any change to `pane-toolbar.test.ts`.
