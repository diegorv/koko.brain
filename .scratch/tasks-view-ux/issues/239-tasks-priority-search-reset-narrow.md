# 239: Tasks priority and tag filters, search, Reset and a narrow-pane fold

**Origin:** Tasks view UX research, 2026-11-12 (`.scratch/tasks-view-ux/research/`) and its review. The last part of Issue 111's first draft, split out as `critique.md` D4 asked. **What to build:** Finish the quick filters: filter by priority and by task tag, search the list, reset every quick filter at once, and keep the filter row usable in a narrow pane.

- **Defaults.** `TaskQuickFilters` (Issue 111, `task-query.logic.ts`) gains `priorities?: TaskPriority[]`, `tags?: string[]` and `search?: string`. Issue 111's `isQuickFieldDefault(quick, field)` is the one test for "at its default", extended here: `QuickFilterField` gains `'priority' | 'tag' | 'search'` (the names Issue 111 reserved; the field names, not the `quick` keys), default when `priorities` and `tags` are absent or empty and `search` is absent or blank after `trim()`. Every setter writes `undefined` for an empty list (a menu that unchecks its last item) and for an empty search box, never `[]` or `''` (Issue 111's rule). Reset filters visibility, the `Filters (n)` count, `describeTaskRule` and the predicates in `applyQuickFilters` all go through `isQuickFieldDefault` or the same normalization, so typing a letter and deleting it leaves no trace.
- **Priority menu** in the filter row (trigger `Priority` when empty, `Priority: <words>` otherwise, words joined with `, `): one checkbox item per level, in the order highest, high, medium, no priority, low, lowest (the order of the generated `TaskPriority`), each with `closeOnSelect={false}`. Item labels and trigger words are `highest`, `high`, `medium`, `no priority`, `low`, `lowest`. Chosen values are stored and shown in menu order, not click order. Empty means any. A task with no priority signifier arrives with `metadata.priority` absent: Rust never emits `'none'` (no emoji maps to it). The `no priority` item therefore matches an absent priority as well as `'none'` (`row.metadata.priority ?? 'none'` in the chosen set).
- **Tag menu** in the filter row (trigger `Tag` when empty, `Tag: #a, #b` otherwise, in option order): one checkbox item per tag present in `tasksStore.rows` before the quick filters (so choosing one tag does not hide the others), from a pure `taskTagOptions(rows: TaskRow[]): string[]` in `task-query.logic.ts`. It returns tags without `#` (the stored form), de-duplicated case-insensitively (first spelling wins) and sorted case-insensitively; the view adds the `#` to the label. Each item has `closeOnSelect={false}`. A chosen tag that is no longer in `rows` stays in the options, checked, so it can be unchecked. With no tag in `rows` the menu holds one disabled item `No tags in these tasks`. Empty means any. `tags` is stored without `#`, as Rust emits them.
- **Tag match.** A task passes when it carries any chosen tag; a chosen tag `work` matches a task tag `work` or one starting with `work/` (nested prefix), case-insensitively, and a leading `#` on the chosen tag is ignored. Export the matcher as `matchesNestedTag(chosen, tag)` from `task-query.logic.ts` so Issue 116's note tag clause reuses it. Today's task tag regex never emits a `/`, so the nested case shows only once Issue 075 lands; the logic covers it now. The options come from `metadata.tags` as Rust emits them, including tags taken from inside links (`Chapter` from `[[Book#Chapter 2]]`, `b` from `https://example.com/a#b`) that Issue 109 hides from chips. That is accepted until Issue 075; do not add a second tag source.
- **Search:** an `<input type="search" placeholder="Search tasks" aria-label="Search tasks">` in the pane toolbar, after the title, count and spinner, with `w-40 min-w-0 shrink` plus the section textbox's token classes. Its `value` is `tasksStore.quick.search ?? ''` and its `oninput` calls `tasksStore.setQuick({ search })` with `undefined` for an empty box. Do not use `bind:value` on the store's object and do not keep a local copy. Typing sets it on every input (no debounce; it filters in memory), and a reset empties the box. It matches, case-insensitively as a trimmed substring, the row's `taskDisplayText` (Issue 109, what the row shows) or `noteTitle`. Tags, dates and other chips are not searched: on the usual path `taskDisplayText` returns the description, from which Rust strips them. Use the Tag menu for tags.
- **Reset filters** (a text button at the end of the filter row) shows when status, due, priority, tag or search is off its default (`isQuickFieldDefault`), and restores all five with `resetQuick()`. Its text never contains "Due", so it cannot be confused with Issue 238's "Reset Due filter".
- **Narrow pane:** below 560 px container width (`@max-[560px]:`; the root is `@container` since Issue 109) the Status, Due, Priority and Tag menus fold into one `Filters (n)` dropdown, where n counts those of the four not at their default and is always shown, `Filters (0)` included. The folded menu is flat: a `DropdownMenuLabel` (`Status`, `Due`, `Priority`, `Tag`) and a separator before each group, no sub-menus, so `menuitemradio` "All" is clickable without hovering. The fold is CSS only: both the menus and the `Filters (n)` trigger are rendered, and literal container-query classes in the `.svelte` source hide one of them. No resize observer, so jsdom tests keep seeing the menus. To render each group's items in both places, move them into Svelte snippets (or a `TasksFilterRow.svelte` in the same folder if `TasksView.svelte` grows too large), keeping the existing Status and Due menus' labels and behavior. The section tag textbox stays visible, the note headers hide their folder subtitle (`@max-[560px]:hidden`), the filter row (never the `pane-toolbar` element, which `pane-toolbar.test.ts` forbids to wrap) wraps with `flex-wrap`, and in the toolbar the count carries `@max-[420px]:hidden` and the search box shrinks below that.
- `describeTaskRule` adds, after Issue 238's due part, `, priority <words joined with ' or '>` (for example `, priority high or no priority`), then `, tagged #a or #b` (option order), then `, matching "<trimmed search>"` when set. `explainEmptyTasks` checks, after due: priority, then tag, then search. Each stage is cumulative like 238's Due stage (the filters up to and including that field leave no row), with "No task matches the <Priority|Tag|Search> filter" and a `{ kind: 'resetQuick', field: 'priorities' | 'tags' | 'search', label: 'Reset Priority filter' | 'Reset Tag filter' | 'Reset Search filter' }` action (`field` is the `quick` key, as 238's `field: 'due'`). Issue 238's `runEmptyAction` branch, `setQuick({ [action.field]: undefined })`, resets only that field.
