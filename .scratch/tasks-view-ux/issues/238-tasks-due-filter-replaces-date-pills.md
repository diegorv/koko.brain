# 238: A Due menu replaces the Tasks date pills

**Origin:** Tasks view UX research, 2026-11-12 (`.scratch/tasks-view-ux/research/`) and its review. The Due part of Issue 111's first draft, split out as `critique.md` D4 and D13 asked. Revised the same day from the deep dive (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md`, `dossier-238.md`, `refute-238.md`). Issue numbers in this text keep the open-itens numbering: the Tasks view Issues live in `.scratch/tasks-view-ux/issues/`, the others (030, 085, 151, 198, 204, 205 and the rest) in `.scratch/open-itens/issues/`.

**What to build:** The three date pills (All time, Last 7 days, Last 30 days) filter on the note file's modification time, not on any task date, so "Last 7 days" lists every task of any note edited this week. Replace them with a Due menu on the task's due date (PRD A2). The note-edited filter survives as two options in the same menu.

- **Due menu** in the filter row, right after the Status menu where the pills were. Trigger `Due: <value>`, the value being `any`, `overdue`, `today`, `next 7 days`, `no date`, `note edited 7 days` or `note edited 30 days`. The content is one `DropdownMenuRadioGroup` holding all seven items, so exactly one is checked: Any (default), Overdue, Today, Next 7 days, No date; a `DropdownMenuSeparator`; Note edited in the last 7 days, Note edited in the last 30 days. Copy the markup of Issue 111's Status menu. bits-ui's `MenuRadioGroup` accepts a separator child. Its `onValueChange` hands back a plain `string` and fires again when the checked item is picked a second time, so the handler maps `'any'` to `undefined`, casts the rest to `DueRange` and calls `tasksStore.setQuick({ due })`.
- `TaskQuickFilters` (Issue 111, `task-query.logic.ts`) gains `due?: DueRange`, with `type DueRange = 'any' | 'overdue' | 'today' | 'next7' | 'none' | 'edited7' | 'edited30'` exported from `task-query.logic.ts` beside it. `tasks.types.ts` only loses `TaskDateFilter`. Unset means `any`; choosing Any stores `undefined`, so `quick` after a reset equals Issue 111's `DEFAULT_QUICK`. Issue 111's `isQuickFieldDefault(quick, field)` gains `due`: absent or `'any'` is the default.
- Meanings, with `today` as `YYYY-MM-DD` and the due date read from `metadata.dueDate` (absent, never `null` or `''`, when the task has none):
  - overdue: a due date before today. No status clause: Status is a separate filter.
  - today: a due date equal to today.
  - next 7 days: a due date from today through today + 7 days, both ends included (eight calendar days; Issue 112's "This week" relies on this window). Compute the end once per call with `formatDateWithOffset(today, 'YYYY-MM-DD', 'YYYY-MM-DD', 7)` from `#lib/utils/date.js`, which parses the key as a local date. Never `new Date(today)` (a date-only string parses as UTC midnight) and never string arithmetic on the day field. Do not import `addDays` from `event-calendar`: it adds a `tasks -> event-calendar` feature pair.
  - no date: `metadata.dueDate` absent.
  - the two edited options: `row.modifiedAt >= now - days * 86_400_000`, the cutoff of Issue 111's `applyEditedCutoff`. They ignore task dates.
  Plain string comparison on the keys is correct; Rust emits `\d{4}-\d{2}-\d{2}` without a calendar check, and a bad date still sorts consistently.
- `applyQuickFilters(rows, quick, today, now)` applies it. The due clause joins the same per-row predicate as the status clause, so the dimmed-parent rule covers it. The edited options fold into that predicate too: every row of a note shares `modifiedAt`, so the subtree rule can never keep a failing row dimmed, and the result is the same as dropping. `applyEditedCutoff` and its separate pre-step in the store go. Every existing two-argument `applyQuickFilters` call (the store's derived and Issue 111's tests) passes `today` and `now`; vitest ignores missing arguments and only `pnpm check` catches them.
- `today` and `now` are read (`formatNow('YYYY-MM-DD')`, `Date.now()`) when the store's `visibleRows` derived runs, so no `.logic.ts` reads the clock. A pane left open past midnight updates on the next refetch.
- `describeTaskRule` and `explainEmptyTasks` drop the `dateFilter` parameter; `explainEmptyTasks` takes `today` and `now`, which the view reads at the call. After the heading part, the sentence adds `, overdue` / `, due today` / `, due in the next 7 days` / `, with no due date` / `, in notes edited in the last 7 days` / `, in notes edited in the last 30 days` when set, and nothing for `any` or unset.
- The empty state's date stage becomes the Due stage: "No task matches the Due filter" with `{ kind: 'resetQuick', field: 'due', label: 'Reset Due filter' }`. It is cumulative: reached when the status stage did not fire and no row passes both the status and the Due filter (`applyQuickFilters` with `show`, `statuses` and `due`). A stage that checks `due` alone would miss a list emptied by an open undated task plus a done overdue task, and Issue 239 appends stages after this one, so Due is no longer the catch-all. The label names the field so it never clashes with the filter row's "Reset filters" button (Issue 239).
- "Reset Due filter" resets only `due`: `runEmptyAction` gains a `resetQuick` branch that calls `tasksStore.setQuick({ [action.field]: undefined })`, here `setQuick({ due: undefined })`. `resetQuick()` keeps resetting every quick filter (Issue 239's Reset filters relies on that). The `allTime` action kind (Issue 108) leaves the action type, and `runEmptyAction` drops its `setDateFilter('all')` branch.
- Remove `dateFilter`, `setDateFilter`, the `TaskDateFilter` type, the view's pill constant and markup, `applyEditedCutoff` and the `allTime` kind once nothing calls them. Issue 111 already deleted `filterByDate` and ported its cases to `applyEditedCutoff`; those cases are migrated to `quick.due` on purpose, not dropped. Grep the branch for `dateFilter|DateFilter|filterByDate|applyEditedCutoff|allTime` first and end every hit deleted, migrated or justified (CLAUDE.md "Removing or Refactoring Code"). Issue 111 rewords the `fromV2` doc comment in `tasks.service.ts`; if it still names `applyEditedCutoff`, point it at `applyQuickFilters`' edited options and keep the seconds-to-ms reason.

**Tests that change on purpose** (name them in the commit): the `applyEditedCutoff` cases in `task-query.logic.test.ts` (ported from `filterByDate` by Issue 111), whose fixtures (notes 1, 10 and 60 days old) become `due: 'edited7'` and `due: 'edited30'` cases of `applyQuickFilters`; the `dateFilter` and `setDateFilter` cases of `tasks.store.test.ts`, including Issue 111's "`visibleRows` follows a `setDateFilter` change", which becomes a `quick.due` case; Issue 108's `describeTaskRule` rows for `last7days` and `last30days` and its date-stage `explainEmptyTasks` cases (all wordings), which become Due cases; the `allTime` action test; every two-argument `applyQuickFilters` call; and Issue 111's view case "Last 7 days still drops a row from a note edited 10 days ago", which becomes Due > Note edited in the last 7 days with the same fixture.
