# 241: Change a task's status from its row, with Undo

**Origin:** Tasks view UX research, 2026-11-12 (`.scratch/tasks-view-ux/research/`, `synthesis.md` T09, `critique.md` D10 and D15) and its review, then corrected by the deep dive (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md`, `refute-241.md`, `dossier-241.md`, `cross-state-chain.md` M5-M7). The status part of Issue 122, carved out because it needs no Rust change. Issue numbers in this text keep the open-itens numbering: the Tasks view Issues live in `.scratch/tasks-view-ux/issues/`, the others (030, 085, 151, 198, 204, 205 and the rest) in `.scratch/open-itens/issues/`.

**What to build:** The circle only flips between open and done. Each row gets a menu that sets any of the common statuses, opens the note at the task, or copies the task text, and a status change from the menu can be undone from a toast.

- **Row action button.** Each row ends with an always-visible button (the `Ellipsis` icon from `@lucide/svelte/icons/ellipsis`, of which `MoreHorizontal` is an alias; `aria-label="Task actions"`, `data-task-actions`, never `opacity-0` or a hover-only opacity). It follows Issue 113's rule for controls inside a row: `tabindex="0"` only in the tab-stop row, `-1` elsewhere. It opens a `DropdownMenu` from `#lib/components/ui/dropdown-menu/`, one `Root` per row (bits-ui renders no content until open).
- **Right click.** One `ContextMenu` around Issue 113's list container, not one menu instance per row, following `NoteRowMenu.svelte` and `NoteRow.svelte`: each row's own `oncontextmenu` sets the context row (no store lookup, no data attributes), and the container's handler, in the trigger's `child` snippet, suppresses the menu when `e.target.closest('[data-task-row]')` is null (a header, the gap between groups) and otherwise forwards to the trigger's `oncontextmenu`. The trigger props spread `tabindex="-1"` and `data-state` onto that container; keep Issue 113's `keydown` and `focusin` handlers and its `svelte-ignore` comments working with them, and ignore any new warning by the name `pnpm check` reports.
- **Keyboard.** `resolveTaskKey` (Issue 113, `tasks-keys.logic.ts`) gains `{ kind: 'menu' }` in two cases: `key === 'F10'` with `shift` and no Meta, Ctrl or Alt, and `key === 'ContextMenu'` with no modifier. Both apply only when `onRow` is true and `count > 0`. Shift+F10 is the one exception to Issue 113's "Shift gives `null`" rule: every other key keeps it, and Issue 113's test cases for it keep their keys. F10 without Shift, and either key with Meta, Ctrl or Alt, give `null`. On `{ kind: 'menu' }` the list handler calls `preventDefault()` and then `click()` on that row's `[data-task-actions]` button, which opens its DropdownMenu anchored at the button (a click with `detail === 0` toggles a bits-ui menu). Do not dispatch a synthetic `contextmenu` event: the ContextMenu anchors at pointer coordinates.
- **Menu items**, the same list in both menus. Write the list once (a snippet or a small component), because Issue 246 (due and priority) and Issue 129 (Open in Todoist) add items to both menus; if a shared form does not compile, write two literal blocks and add a test that both menus list the same labels. `menu-item-anatomy.test.ts` scans only literal `DropdownMenu.`/`ContextMenu.` tags, so keep the items free of side margins and `text-xs` either way.
  - Open at line: `openNoteAt(filePath, { kind: 'line', line })`, as a click on the text does.
  - Copy task text: `navigator.clipboard.writeText(stripTaskTrailers(task.text))`. `stripTaskTrailers(text)` is defined by Issue 109 in `tasks.logic.ts` (trim, a trailing block id `^[\w-]+`, then a trailing Todoist anchor). The copied text is the raw text, so it keeps dates, priority and tags. Pasting a synced line does not duplicate its anchor: the sync writes the anchor last, before a block id (ADR-0037 freezes a link whose anchor sits on two lines). Text a user typed after the anchor keeps it. Success shows nothing; a rejected `writeText` shows `toast.error('Could not copy the task text.')`.
  - Status: a radio group of Todo, In progress, Done, Cancelled, in `TASK_STATUSES` order (Issue 110), labelled with `statusGlyph(status).word` (Issue 110) with its first letter capitalized. The row's current status is checked. A row whose status is question, important or forwarded shows no item checked.
- **The write.** `setTaskStatus` in `tasks.service.ts`:

  ```ts
  export async function setTaskStatus(
  	filePath: string,
  	task: Pick<TaskItem, 'text' | 'status' | 'lineNumber'>,
  	target: TaskStatus
  ): Promise<boolean>; // true only when the line was rewritten
  ```

  - It returns `false` before doing anything when `target === task.status`: no dirty-tab save, no IPC, no Undo dismissal. Do not rely on Rust for this: Rust rewrites `[X]` to `[x]` for target `done` and an unknown box (parsed as `todo`) to `[ ]` for target `todo`, and bits-ui calls the radio group's `onValueChange` again when the checked item is picked.
  - Otherwise it runs the protocol `toggleTask` runs today: save a dirty open tab first and refuse when the line moved; call `toggle_task_status` with `expectedText`, `expectedStatus` and `target` (the command accepts any target status); on `stale`, refetch and show the stale message below, writing nothing; on success, `afterTaskWrite`.
  - `toggleTask(filePath, task)` becomes `setTaskStatus(filePath, task, toggleTarget(task.status))`, so the two paths cannot drift. Its signature stays.
  - The two refusal messages become `The note changed, so the list was refreshed. Try again.` (line moved after the dirty-tab save) and `The task changed on disk, so the list was refreshed. Try again.` (`stale`). `Task not changed: the note could not be saved.` and `Failed to save task change.` stay. The assertions that pin the old copy change on purpose: one in `tasks.service.test.ts` and two in `task-toggle-dirty-buffer.test.ts` (`grep -rn "Click it again\|Click the task again" src/tests`).
- **Undo, menu writes only.**
  - The menu calls `setTaskStatusFromMenu(filePath, task, target): Promise<void>` in `tasks.service.ts`. It reads the reset generation (`getTasksResetGeneration()`, defined by Issue 234; code inside `tasks.service.ts` may read the counter directly) before it calls `setTaskStatus`. When the write returns `false`, or the generation changed while it was awaited (a vault switch), no toast is shown.
  - Otherwise it shows `toast('Task marked <Label>', { description: taskDisplayText(task), action: { label: 'Undo', onClick }, onDismiss, onAutoClose })`, with `<Label>` the menu label and `taskDisplayText` from Issue 109, following `deleteEventFromUi` in `event-calendar.service.ts`. The service keeps one module-level toast id, not store state; `onDismiss` and `onAutoClose` forget it.
  - Undo's `onClick` returns without writing when the captured generation is no longer current (`toggle_task_status` writes any absolute path, so a late Undo would otherwise write into the previous vault). Else it calls `setTaskStatus(filePath, { text: task.text, lineNumber: task.lineNumber, status: target }, task.status)`: the expected text is unchanged because the command only rewrites the box character. Undo goes through `setTaskStatus`, not the menu wrapper, so it shows no second toast.
  - Only the last menu write can be undone. `dismissStatusUndo()` calls `toast.dismiss(id)` only while an id is held, so the existing `svelte-sonner` mocks without `dismiss` stay valid. `setTaskStatus` calls it at the start of every real write (after the equal-status return), so any newer write from the menu, the circle or Space retires the toast, and `resetTasks()` calls it on a vault switch.
  - Undo restores the previous status, whatever it was: a `[X]` line comes back as `[x]`, and an unknown box comes back as `[ ]`.
  - The circle and Space stay without a toast (owner decision below).
- **Focus.** Both menus' `Content` gets an `onCloseAutoFocus` handler that calls `e.preventDefault()` and focuses, with `{ preventScroll: true }`, the row the menu was opened from when that row is still rendered, else the row `tabStopRow` (Issue 113, refined by Issue 240) gives for the current row. It does nothing when `document.activeElement` is outside the view and outside the closing menu. The bits-ui default is not enough: it returns focus to the trigger when the trigger is tabbable (the actions button of the tab-stop row, not the row), else to the element focused before opening, which may be a row the refetch removed. While the menu is still mounted, focus sits inside the portaled menu, so Issue 113's focus-follow does not move it; this handler closes that gap. After a menu write or an Undo removes the row (Done or Cancelled under the Open filter), Issue 113's `nextCurrentRow` picks the next row and its focus-follow rule applies unchanged: this Issue does not widen that guard.
- **Todoist.** On a line with a Todoist anchor, a change between an open status (todo, in progress) and a closed one (done, cancelled) reaches Todoist on the next sync as a close or reopen. An Undo before the next sync leaves the line as it was at the last sync, so nothing is sent; an Undo after a sync sends the opposite change. A change between two open or two closed statuses does not reach Todoist (`isClosedStatus` in `todoist-sync`). A Tasks view write is not a note save, so it does not start the after-save sync. This needs no code. The help page says it.
