# 113: Keyboard navigation and accessible rows in the Tasks view

**Origin:** `tasks-view` Issue 10, moved here on 2026-11-08 and rewritten on 2026-11-12 from the Tasks view UX research (`.scratch/tasks-view-ux/research/`, `critique.md` D9, D10 and D17) and its review, then corrected by the deep dive (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md`, `refute-113.md`, `cross-state-chain.md` M6). It runs before grouping (Issue 112). Its PRD stays in `.scratch/archived/tasks-view/`. Issue numbers in this text keep the open-itens numbering: the Tasks view Issues live in `.scratch/tasks-view-ux/issues/`, the others (030, 085, 151, 198, 204, 205 and the rest) in `.scratch/open-itens/issues/`.

**What to build:** The task list has no keyboard model beyond tabbing through every circle and link, and the task text is a static element with a click handler (a `svelte-ignore` comment silences the a11y warnings). Make the list keyboard-first (PRD A8): one tab stop for the rows, arrows to move, Space to toggle, Enter to open the note at the task's line, with the place kept across refreshes and tab switches.

**Row keys.** Every rule below identifies a row by the string `<filePath>:<lineNumber>`, the key Issue 112 also uses for its each-blocks. Each row element carries it as `data-task-key`, next to `data-task-row`.

- **Roving focus over rows.** Each row element is the focus stop: `tabindex="0"` on the tab-stop row and `tabindex="-1"` on the others. The tab-stop row is `tabStopRow(...)` (below): the current row when it is rendered, else the first rendered row, else none. The controls inside a row (the circle, wikilink buttons, URL links, and later Issue 241's actions button) get `tabindex="0"` only in the tab-stop row and `tabindex="-1"` in every other row, so Tab from that row walks its own controls and then moves on to the next note's header buttons. Group header buttons (the title button, Issue 236's header, later Issue 240's chevron) keep their normal tab stop: they are the keyboard route to opening a note without a line. Only rows and the controls inside rows rove. Mouse clicks on any control still work. In-app roving examples: `EventCalendarHeader.svelte` and `EventColorSwatches.svelte`. Focus rings follow `NoteRow.svelte` (`focus-visible:ring-*`), with no `transition-all` and no `hover:scale` (`chrome-state-styles.test.ts`).
- **Pure key logic** in a new `src/lib/features/tasks/tasks-keys.logic.ts` (no imports):
  - `resolveTaskKey(input: TaskKeyInput): TaskKeyAction | null`, with `TaskKeyInput = { key: string; repeat: boolean; onRow: boolean; meta: boolean; ctrl: boolean; alt: boolean; shift: boolean; index: number; count: number }` and `TaskKeyAction = { kind: 'focus'; index: number } | { kind: 'toggle' } | { kind: 'open' }`. `key` is `KeyboardEvent.key`, so Space is `' '`.
    - ArrowDown and ArrowUp move by one. At the last row ArrowDown returns `{ kind: 'focus', index: count - 1 }`, and at the first row ArrowUp returns `{ kind: 'focus', index: 0 }`, so the handler still calls `preventDefault()` and the scroll viewport does not scroll under the focused row. Home and End go to index 0 and `count - 1`.
    - Space toggles, Enter opens the note at the task's line (as a click on the text does).
    - With `repeat` true (`KeyboardEvent.repeat`), Space and Enter return `null`; arrows, Home and End still move. Holding Space would otherwise toggle the row that slides under focus after each refetch, writing the note each time.
    - It returns `null` when `onRow` is false (the key landed on a control inside the row, so Space or Enter on the circle or a wikilink keeps its native click and does not run twice), when Meta, Ctrl, Alt or Shift is held, when `count` is 0, and for every other key. Issue 241 adds one exception (Shift+F10) and the ContextMenu key; keep the `shift` field even though it only yields `null` here.
  - `nextCurrentRow(order: string[], prevOrder: string[], current: string | null): string | null`: the current row after the list changed. `current` when it is still in `order`; else the first key after it in `prevOrder` that is in `order`; else the nearest key before it in `prevOrder` that is in `order`; else `null`. `null` when `current` is `null` or not in `prevOrder`.
  - `tabStopRow(rendered: string[], order: string[], current: string | null): string | null`: `current` when it is in `rendered`; else the first key of `rendered`; else `null`. `order` is unused in this Issue: Issue 240 changes the fallback to "the first rendered row after it in `order`, else the last rendered row", so the roving `tabindex`, focus on open and the focus-follow below must all read this one function.
  - `order` is every row in display order: `tasksStore.visibleRows` order in this Issue, and from Issue 112 on the flattened `tasksStore.groups` rows. `rendered` is the rows in the DOM, which equals `order` until Issue 240 adds collapsed groups and the row cap.
- **The key handler.** One `keydown` handler on the list container (one plain `<div>` around all note groups, inside the scroll area, outside the toolbar and filter row) calls `resolveTaskKey` with `onRow` true when `e.target` has `data-task-row`, `repeat: e.repeat`, and `index`/`count` taken from `querySelectorAll('[data-task-row]')` in DOM order across groups. On a non-null action it calls `preventDefault()`. `focus` calls plain `focus()` on that row, so the browser scrolls it into view. `toggle` and `open` look the row up by its `data-task-key` (not by index into a data array: dimmed rows and later groupings make the orders differ) and call the view's existing toggle path and `openNoteAt(filePath, { kind: 'line', line })`. A dimmed row (Issue 111) is a row like any other: Space toggles it. The search box, the filter row and the menus (portals) sit outside the list container, so their keys never reach this handler, and no typing-target check is needed.
- **The current row is kept.** The Tasks store holds the current row as `TaskRowRef = { filePath: string; lineNumber: number }` (in `tasks.types.ts`) or `null`, with a `currentRow` getter and `setCurrentRow(row: TaskRowRef | null)`, which copies the two fields and does nothing when they are equal. `tasksStore.reset()` clears it. A `focusin` handler on the list container sets it from `closest('[data-task-row]')`, so focus on a control inside a row also updates it.
- **When the current row leaves the list.** When `order` changes (a refetch, a quick filter change), the view computes `nextCurrentRow(order, prevOrder, current)` against the previous `order` it kept, and writes the result with `setCurrentRow` when it differs. Focus moves to the new current row only when the current row changed and, after the DOM update, `document.activeElement` is `<body>` (the focused row was removed) or inside the list container. A filter typed in the search box therefore never moves focus. Store reads and writes in that effect go inside `untrack()` (`docs/PATTERNS.md`).
- **Focus on open.** Focus goes to `tabStopRow(...)` (the current row, or the first row when there is none; owner decision below), with `focus({ preventScroll: true })`, so its order relative to Issue 234's scroll restore does not matter. The attempt is made once per mount: the first time the rendered row count is above zero during that mount, whether or not the guard lets it move. A later refetch or filter change never pulls focus. The guard: the move happens only while `document.activeElement` is `<body>`, the view root itself, or an element inside the list container. It never moves focus out of a text field (the section tag textbox, the search box) or from anywhere outside the view (the palette, a dialog, another pane, the tab bar). With no rows, nothing is focused. Opening the tab by clicking it leaves focus on the tab element (`EditorTabs.svelte` tabs are focusable), so focus stays there, and the palette path may do the same; that is accepted, do not widen the guard to `[role="tab"]`. Cmd+Shift+T from the editor lands on `<body>` and focuses the row.
- **Roles and names.** Each note group's row container has `role="list"` and an `aria-label` set to the note title; each row has `role="listitem"`. The circle's label already reads `Mark task as done: <text> (<word>)` (Issues 110 and 109). The rows (`role="listitem"` with a dynamic `tabindex`) raise `a11y_no_noninteractive_tabindex`. The list container is a role-less `<div>`, and its `onkeydown` raises `a11y_no_static_element_interactions`. Add a `svelte-ignore` with a one-line reason (roving-focus list) for each of those two, on the element that raises it, and for any other name `pnpm check` reports on these elements. `focusin` raises no warning. Keep the text span's existing ignore: the span keeps its click, and the row is its keyboard path. Do not add `aria-pressed` to the Status, Due, Priority and Tag triggers: they are dropdown triggers, and PRD A8's toolbar-toggle line is superseded.
- **Palette command** in `getBuiltInCommands` (`src/lib/app/commands.ts`), next to `tasks:toggle`, category `Navigation` like it:
  - `tasks:status-filter`: label `Tasks: Show all statuses` when `tasksStore.quick.show` is `open` and `statuses` is empty, else `Tasks: Show open only` (the store is read while the list is built, as `railGoToCommands` does). Empty means `undefined`: Issue 111's setters never store `[]`.
  - The action makes the same store call as choosing All or Open in Issue 111's Status menu radio group (`setQuick({ show, statuses: undefined })`), so Issue 239's Reset and `Filters (n)` (through Issue 111's `isQuickFieldDefault`) treat the result exactly as a menu pick. It then calls `openTasksTab()` so the change is visible.
  - "Toggle Tasks View" keeps its behavior. No other Tasks command is added.
