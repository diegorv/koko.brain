# 112: Group the Tasks list by note, folder, due, priority or status

**Origin:** `tasks-view` Issue 08, moved here on 2026-11-08 and rewritten on 2026-11-12 from the Tasks view UX research (`.scratch/tasks-view-ux/research/`, `critique.md` D4, D6 and D8), then the deep dive of 2026-11-12 (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md`, `refute-112.md`, `dossier-112.md`, `cross-state-chain.md` H2, M4, M6, L3). Collapse and the 50-row cap moved to Issue 240. Its PRD stays in `.scratch/archived/tasks-view/`. Issue numbers in this text keep the open-itens numbering: the Tasks view Issues live in `.scratch/tasks-view-ux/issues/`, the others (030, 085, 151, 198, 204, 205 and the rest) in `.scratch/open-itens/issues/`.

**What to build:** Tasks are grouped only by note. Add a Display menu with one grouping level (PRD A3), so "what is overdue" or "what is high priority" reads at a glance.

- **Types.** `task-query.logic.ts` (Issue 111) exports:
  ```ts
  type TaskGroupKey = 'note' | 'folder' | 'due' | 'priority' | 'status';
  type TaskSortKey = 'due' | 'priority' | 'path';
  const DEFAULT_TASK_SORT: TaskSortKey[] = ['due', 'priority', 'path'];
  type GroupedRow = VisibleRow & { breadcrumb?: string };
  interface TaskGroup {
  	key: string;
  	label: string;
  	rows: GroupedRow[];
  	count: number;
  	// Note groups only:
  	filePath?: string;
  	folder?: string;
  	modifiedAt?: number;
  	total?: number;
  	open?: number;
  }
  ```
  `TaskGroupKey` is the name the PRD model and Issue 118 use; 118 extends the union, so `groupTaskRows` stays one function with one switch.
- **Display menu:** a `DropdownMenu` trigger `Display` at the end of the pane toolbar, after the search box (Issue 239), holding a `DropdownMenu.Label` "Group by" and a radio group: Note (default), Folder, Due date, Priority, Status (item values `note`, `folder`, `due`, `priority`, `status`). The trigger is `shrink-0`: Issue 239's narrow rules hide the count first and then shrink the search box, never the Display trigger. Its padding classes go on the button, not on the `pane-toolbar` element (`pane-toolbar.test.ts` forbids `h-`, `p*-`, `gap-`, `border-` other than `border-b`, and `flex-wrap` there). The radio group's `onValueChange` yields a `string`; one `as TaskGroupKey` cast at that boundary is fine. Re-picking the checked item calls `onValueChange` again (bits-ui's `MenuRadioGroup` has no equality check), so `setGroupBy` with the current value must change nothing.
- **Store.** `tasksStore` gains `groupBy: TaskGroupKey` (default `'note'`) with `setGroupBy`, and `sort: TaskSortKey[]`, fixed at a copy of `DEFAULT_TASK_SORT`, with a getter and no setter. This Issue adds no sort control; `sort` is in the store so Issue 124 (saved views) can store it and Issue 126 can compare it. `reset()` restores both. The field is `groupBy`, not `group`, so it does not sit next to `groups` and `fileTaskGroups` with a near-identical name.
- **Groups**, from `groupTaskRows`, empty groups left out. Keys are raw, with no grouping prefix (Issue 240 adds `groupBy:` in front for its collapse keys):
  - Note: one group per note, key `filePath`, label `noteTitle`, in the order the rows arrive (path order since Issue 234). Rows keep document order, and dimmed parents (Issue 111) stay. A Note group also carries `filePath`, `folder`, `modifiedAt`, `total` and `open`, read from its first row: `folder` and `modifiedAt` are the row fields, `total` is the row's `noteTaskCount` and `open` its `noteOpenCount` (both added to `TaskRow` by Issue 111 through Issue 236's `noteTaskCounts`). Issue 236's header reads N from `open` and M from `total`. N is never `count`: under Status > All, `count` includes closed rows. `groupTaskRows` keeps its four parameters; never compute `total` from `rows.length`, which lacks the rows `applyQuickFilters` dropped.
  - Folder: key and label the row's `folder` (Issue 111 fills it through Issue 236's `noteFolder`), label `Vault root` for `''`. Vault root first, then folders in `compareTaskPaths` order (Issue 234, `tasks.logic.ts`).
  - Due date, from `metadata.dueDate`, compared as `YYYY-MM-DD` strings, with today + N computed by `formatDateWithOffset(today, 'YYYY-MM-DD', 'YYYY-MM-DD', n)` (`#lib/utils/date.js`, an allowed import for a `.logic.ts`): Overdue (before today), Today, Tomorrow, This week (today + 2 days through today + 7 days, the part of Issue 238's "Next 7 days" window after Tomorrow), Later, No date, in that order. Keys `overdue`, `today`, `tomorrow`, `week`, `later`, `none`. No validation of `dueDate`: Rust sends `YYYY-MM-DD`.
  - Priority: Highest, High, Medium, No priority, Low, Lowest, in that order. Keys are the `TaskPriority` values; `none` holds both `'none'` and a row with no `priority` field.
  - Status: one group per status in Issue 110's `TASK_STATUSES` order (`task-status.logic.ts`: todo, in-progress, question, important, forwarded, done, cancelled), labelled Todo, In progress, Question, Important, Forwarded, Done, Cancelled (the `statusGlyph` word with its first letter in upper case). Keys are the `TaskStatus` values.
- **Headers.** Note groups keep Issue 236's header (file icon, title button, folder subtitle, "N of M open") and its hooks (`data-task-group`, `data-task-group-title`, `data-task-group-subtitle`, `data-task-group-count`), fed from the Note group's fields. Every other group's header shows only its label and its row count ("Overdue  3"), with no icon, no subtitle and no "open" word: under Show all or in the Done group most rows are not open. It carries `data-task-group` on the wrapper, `data-task-group-label` on the label and `data-task-group-count` on the count, whose text is exactly `count`. Every group wrapper also carries `data-task-group-key={group.key}`. Tests find headers and counts through these hooks, never by text: Overdue, Today and High are also item text in the Due and Priority menus, and a closed bits-ui menu can stay in the jsdom DOM. Keep the header one block (a snippet) so Issue 240 adds its chevron in one place.
- **Rows in groups other than Note** are flat: rows with `dimmed: true` are dropped, and rows are sorted by the `sort` keys in order: due date ascending with undated rows last, then priority in the order above, then `relPath` with `compareTaskPaths` (Issue 234), then `lineNumber`. After the `sort` keys, ties always fall back to `relPath` then `lineNumber`, so any `sort` array gives one order. A row whose `parentLine` points at another task of the same note gets `breadcrumb` set to `taskDisplayText(parent)` (Issue 109): only the immediate parent, looked up in the rows `groupTaskRows` was given (dimmed ones included), set in every flat grouping even when the parent sits in the same group, never in Note groups. A `parentLine` with no matching row gives no breadcrumb. The view shows it as a muted `text-xs` line above the row's text. Flat rows get no indent padding (the breadcrumb carries the hierarchy); Note groups keep the indent from `row.indent`.
- **Lists and keys.** Every group's row container keeps Issue 113's `role="list"`, with `aria-label` set to the group's `label` (113 gives it only to note groups). Rows are keyed `filePath:lineNumber`, since a flat group mixes notes.
- **Keyboard.** Issue 113's roving focus works across groups in DOM order. The `order` that Issue 113's `nextCurrentRow` and `tabStopRow` take (`tasks-keys.logic.ts`, keyed `filePath:lineNumber`) becomes the flattened `tasksStore.groups` rows, so after a refetch removes the current row, the next current row is the next one on screen: under a flat grouping the next row in note order can sit in another bucket.
- **Focus follows a row that changes group.** Under Status grouping with Status > All, Space or a circle click on a todo row moves it to the Done group. Svelte recreates its element in the other group's keyed `{#each}`, so focus would fall to `<body>`. The current row is unchanged, so Issue 113's focus-follow (which moves focus only when the current row changed) does nothing. Extend that effect: when `order` changes, the current row is unchanged and still rendered, and after the DOM update `document.activeElement` is `<body>`, focus moves to the current row's new element (found by Issue 113's `data-task-key`).
- `timeSync('TASK-PROFILE', 'groupTaskRows', ...)` (`#lib/utils/debug.js`) wraps the `groupTaskRows` call inside the store's `$derived`, never inside `task-query.logic.ts`: `pure-logic.test.ts` forbids `utils/debug.ts` as an import of a `.logic.ts`. This is the log the PRD's "Why not Rust" reads. `debug()` reads `settingsStore`, so `groups` also recomputes on a settings write; accept that, and do not wrap the call in `untrack`, which would also untrack `visibleRows`, `groupBy` and `sort`. Many test files mock `#lib/utils/debug.js` without `timeSync` (among them `tasks.service.test.ts` and `app-lifecycle.service.test.ts`): add `timeSync: (_t, _l, fn) => fn()` to each such mock whose test reads `tasksStore.groups` or mounts `TasksView`.

**Logic.** `groupTaskRows(rows: VisibleRow[], groupBy: TaskGroupKey, sort: TaskSortKey[], today: string): TaskGroup[]` in `task-query.logic.ts`. It replaces Issue 111's `rowsByNote`, which is deleted once `grep -rn rowsByNote src` shows no caller. `count` is the number of rows with `dimmed: false`; in a flat grouping it equals `rows.length`. The store exposes the result as a `groups` getter over a module-level `$derived` of `visibleRows`, `groupBy`, `sort` and today (`formatNow('YYYY-MM-DD')`, `#lib/utils/date.js`) (ADR-0034), with a test. A pane left open past midnight keeps the old buckets until rows, grouping or sort change; accepted, as in Issues 109 and 238.

**Tests that change on purpose** (name them in the commit): Issue 111's `rowsByNote` cases in `task-query.logic.test.ts` move onto the Note group of `groupTaskRows` (the `total` case reads `noteTaskCount`, the open case `noteOpenCount`) and are not dropped.
