# 242: The Tasks section filter takes several tags

**Origin:** owner request, 2026-11-12, during the Tasks view UX review: keep the `#to-list` filter, and allow more tags instead of listing every task. Reviewed by the 2026-11-12 deep dive (`.scratch/tasks-view-ux/research/deep-dive/dossier-242.md`, `refute-242.md`, `SUMMARY.md`). Issue numbers in this text keep the open-itens numbering: the Tasks view Issues live in `.scratch/tasks-view-ux/issues/`, the others (030, 085, 151, 198, 204, 205 and the rest) in `.scratch/open-itens/issues/`.

**What to build:** The section tag textbox accepts several tags, for example `#to-list #work`. A task is listed when at least one of the tags, applied alone with today's heading rule, lists it. The default stays `#to-list`.

- **Input.** The textbox keeps one string in `tasksStore.sectionTag`. A pure `parseSectionTags(text: string): string[]` in `tasks.logic.ts` splits the text on whitespace and commas, drops empty tokens, adds a leading `#` to a token that lacks one, drops a token that is only `#`, and removes exact duplicates after the `#` is added, keeping the first-typed order. `work` and `#work` are one tag; `#Work` and `#work` stay two, because the match is case-sensitive. A lone `#` is dropped because it would match every tagged heading, and the 400 ms debounce can fire while the user is typing `#to-list #`. An empty result means no section filter: every task is listed through `get_all_tasks_v2`, as an empty box does today.
- **Rust scan.** In `src-tauri/src/vault/parsing.rs`, add `pub fn extract_tasks_from_sections(content: &str, section_tags: &[String]) -> Vec<Task>`. Its result is the union of the single-tag results: a task is kept when at least one tag, applied alone with today's rule, keeps it, each task at most once, in line order.
  - Do not share one `in_matching_section` / `section_level` state across tags. Today a heading that contains the tag re-anchors the section level, so a shared state ends an outer tag's section early. Example: `# A #to-list`, `## B #work`, `- [ ] t1`, `## C`, `- [ ] t2`. `#to-list` alone keeps t1 and t2 (`## C` does not close a level-1 section); a shared state re-anchors at `## B` and drops t2 at `## C`.
  - Keep one state per tag inside a single line loop, with one push per task line (a line inside two active sections is listed once). Do not concatenate per-tag scans either: a task listed twice duplicates a `lineNumber` key, and the view's task `{#each}` is keyed on `task.lineNumber`.
  - Each tag keeps today's rule unchanged: the `#` added when missing (untrimmed `starts_with('#')`, as `extract_tasks_from_section` does), case-sensitive substring of the heading text, fenced code skipped.
  - Tags that are blank after trimming are dropped. An empty or all-blank list returns every task (`extract_tasks`), as an empty `section_tag` does today. The TS side never sends one.
  - `extract_tasks_from_section(content, section_tag: &str)` stays, as the one-tag case of the new scan (a thin wrapper), so its inline tests and the oracle test keep their meaning.
- **Rust command.** In `src-tauri/src/commands/vault.rs`, `tasks_in_section` takes `section_tags: &[String]` in place of `section_tag: &str` and calls `extract_tasks_from_sections`. `get_tasks_in_section_v2` takes `section_tags: Vec<String>` (Tauri exposes it as `sectionTags`). One pass over the candidate notes still reads each note from disk once. Groups keep their current shape and order. No `#[ts(export)]` type changes, so no binding is regenerated. Swap the `extract_tasks_from_section` import in `vault.rs` for the plural one after a grep confirms `tasks_in_section` is its only caller there.
- **Typed command map.** In `src/lib/contracts/commands.ts`, the `CommandMap` entry for `get_tasks_in_section_v2` takes `args: { sectionTags: string[] }` (write `string[]`, not `Array<string>`: `ipc-parity.test.ts` compares the type text against Rust's `Vec<String>`), and its `COMMAND_ARGS` entry becomes `['sectionTags']`.
- **E2E mock.** `e2e/mocks/tauri-core.ts` passes `args.sectionTags`. `e2e/mocks/vault-index.ts` `getTasksInSection(sectionTags: string[])` is rewritten to apply the heading rule. Today it compares the lowercased tag, `#` kept, with the note's tags, which are stored without `#`, so every `#`-prefixed tag returns nothing and headings are ignored. For each group from `getAllTasks()`, read the file with `virtualFS.readFileSafe`, keep the tasks whose `lineNumber` falls inside a section matching any tag (per-tag state as in Rust, case-sensitive substring, `#` added when missing, a lone `#` and blank tags dropped, fenced lines skipped as the mock's `parseTasks` does), and drop empty groups. Keep it minimal: Issue 121 deletes it. `~~~` fences and frontmatter need no handling.
- **Service.** `buildTaskIndex` calls `get_tasks_in_section_v2` with `{ sectionTags: parseSectionTags(tasksStore.sectionTag) }` when the list is not empty, else `get_all_tasks_v2`. Issue 108's `hasLoaded` handling in the same function stays as it is.
- **Rule sentence, empty state, Clear tag** (Issue 108). `describeTaskRule` and `explainEmptyTasks` keep their `sectionTag: string` parameter (Issues 111 and 243 build on it) and run `parseSectionTags` on it internally. With zero parsed tags (for example `''` or `' , '`) they behave as Issue 108's no-tag case ("from every note", "No tasks in this vault yet", no Clear tag action), matching the service, which then calls `get_all_tasks_v2`. One tag reads as today. Several tags join with ` or ` for any count: ` under headings containing #to-list or #work`, and stage 1 says "No task sits under a heading containing #to-list or #work". The view shows Issue 108's Clear tag button only when the parsed list is not empty.
- **Textbox.** The placeholder becomes `#tag #tag`; the accessible name stays "Section tag" (Issue 108's `aria-label`). Before changing the placeholder, confirm that `aria-label="Section tag"` is on the input: every e2e locator finds the box by `/section tag/i`, and without the label the name comes only from the placeholder. The input widens from `w-28` to `w-40` so two tags fit. The decorative `Hash` icon inside the input stays (Issue 108 keeps it). Add no classes to the `.pane-toolbar` element (`src/tests/lib/pane-toolbar.test.ts` forbids overrides).
- **Comments that go stale.** Update the doc comments that name one tag: the `get_tasks_in_section_v2` entry in `commands.ts`, the `@ts-expect-error sectionTag is required` comment in `src/tests/lib/contracts/ipc.test.ts` (the case itself stays), `tasks_in_section` and `get_tasks_in_section_v2` in `vault.rs`, `extract_tasks_from_section` in `parsing.rs`, the `sectionTag` state in `tasks.store.svelte.ts`, and `buildTaskIndex` and `updateSectionTagFilter` in `tasks.service.ts`.
- `help/documentation/10-tasks-and-todoist.md` (the Filters table row for the section tag, as Issue 108 leaves it) says the field takes several tags, separated by spaces or commas, and lists a task when its heading contains any of them. Extend Issue 108's text; do not rewrite it.
