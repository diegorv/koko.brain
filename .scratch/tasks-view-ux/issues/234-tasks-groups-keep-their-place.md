# 234: The Tasks list keeps your place, and a failed refresh says so

**Origin:** Tasks view UX research, 2026-11-12 (`.scratch/tasks-view-ux/research/`, `synthesis.md` T03 and T07 as corrected by `critique.md` D6, D7 and D18) and its review, then the ticket deep dive (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md`, `dossier-234.md`, `refute-234.md`). It absorbs Issue 235, merged on the owner's approval the same day. Issue numbers in this text keep the open-itens numbering: the Tasks view Issues live in `.scratch/tasks-view-ux/issues/`, the others (030, 085, 151, 198, 204, 205 and the rest) in `.scratch/open-itens/issues/`.

**What to build:** Ticking a task in the fifth note leaves that note fifth, leaving the Tasks tab and coming back puts you where you were, and a refresh that fails says so instead of showing a stale or empty list in silence.

**Keep your place.** Today three things lose it:
- Rust returns note groups newest mtime first, and a toggle rewrites the note on disk, so the ticked note jumps to the top on the refetch.
- `TasksView` unmounts whenever another tab is active (`EditorView.svelte` renders it inside `{#if isTasksTab}`), so the scroll position is lost on return.
- A section tag typed less than 400 ms before the view unmounts is dropped: `onDestroy` clears the debounce timer without applying it. The textbox also holds its own copy of the tag (`sectionTagInput`), so a change made outside it (a store reset, Issue 243's load) is not shown.

Build:
- **Path order.** `tasks.logic.ts` exports `compareTaskPaths(a: string, b: string): number`: one module-level `Intl.Collator(undefined, { numeric: true, sensitivity: 'base' })` (the same order as `localeCompare` with those options, built once instead of per comparison), with ties broken by raw code-unit order (`a < b ? -1 : a > b ? 1 : 0`). Without the tie-break, `A.md`/`a.md` or `resume.md`/`résumé.md` compare equal, the stable sort keeps the incoming mtime order, and the two swap after a toggle. `buildTaskIndex` sorts the groups by `filePath` with it before `setFileTaskGroups`, after both the `get_all_tasks_v2` and the `get_tasks_in_section_v2` branches. Paths stay absolute (indexing rule 9); every indexed note shares the vault root prefix, so this is the vault-relative path order. Issues 111, 112 and 244 reuse `compareTaskPaths` rather than writing their own comparator; `.logic.ts` files cannot import the service, which is why it lives in logic.
- **Scroll offset.** `TasksView` binds the `ScrollArea` viewport (`viewportRef` is bindable in `src/lib/components/ui/scroll-area/scroll-area.svelte`; no other file uses it yet). A passive `scroll` listener on the viewport, added in an `$effect` that reads `viewportRef` and removed in its cleanup, writes the viewport's `scrollTop` into `tasksStore.scrollOffset` through `tasksStore.setScrollOffset(n)`. Do not read `scrollTop` in `onDestroy`: Svelte removes the `{#if}` branch's DOM before the component's teardowns run (`node_modules/svelte/src/internal/client/reactivity/effects.js`, `destroy_effect`), a detached element reports `scrollTop` 0, and the bits-ui ref is already null by then. jsdom stores `scrollTop` as a plain field, so a destroy-time read passes in vitest and saves 0 in the app.
- `scrollOffset` is a plain module `let`, not `$state`: no component renders it, so scrolling causes no reactive churn. Its JSDoc says it is not reactive.
- **Restore once per mount**, in an `$effect` that runs when `viewportRef` is set and the list has rows, reading `tasksStore.scrollOffset` with `untrack` and assigning it to the viewport's `scrollTop`. Effects run after the DOM update, so the rows exist. jsdom has no layout, so whether the webview clamps the value before layout settles (and needs a `requestAnimationFrame`) is checked only by the e2e criterion below, in Chromium.
- **Store field, not `tab-view-state`.** Use the store field, not `core/markdown-editor/tab-view-state.ts`: that map is keyed by tab path, needs `scrollLeft` and `cursorPos`, and `closeTab` deletes its entry. `tasksStore.reset()` must clear the offset, which Issue 244 relies on. With the store field the offset also survives closing and reopening the Tasks tab (Cmd+Shift+T) until a vault switch, like the groups do.
- **Debounce flush on destroy.** On destroy, a pending debounce applies its value (`updateSectionTagFilter`) instead of being dropped, unless `resetTasks()` ran since the view mounted. On a vault switch `teardownVault` (`app-lifecycle.service.ts`) calls `resetEditor()` and then `resetTasks()` in the same synchronous block, and the view unmounts at the next Svelte flush, after `resetTasks()`. A flush would then write vault A's tag into vault B's store and start a fetch.
- **Reset generation.** `tasks.service.ts` exports `getTasksResetGeneration(): number`, a module counter that `resetTasks()` increments. The view captures it when it mounts and compares it in `onDestroy`. Issue 241's Undo reuses it from service code, so it stays in the service when Issue 245 removes the textbox.
- **Textbox follows the store.** The textbox shows the typed text while a debounce is pending, and `tasksStore.sectionTag` otherwise, so a change from outside shows at once unless an edit is pending. Issue 108's Clear tag cancels the pending edit.

**A failed refresh says so.** Today `buildTaskIndex` logs the error with `error('TASKS', ...)` and leaves the store as it was: the user sees an empty state or an old list with no hint (CLAUDE.md "Error Handling": user-facing errors need an inline state or a toast).
- The Tasks store gains `error: string | null` (`$state`, getter `tasksStore.error`, setter `setError`), holding a fixed message, never the raw error text (the raw error goes to the log). `buildTaskIndex` sets it when the latest request fails and clears it when the latest request succeeds. A request superseded by a newer call or by `resetTasks()` never sets or clears it (the existing `latestTaskIndexRequest` guard). The error clears only on a success, not when a request starts. The groups are not touched on failure (CLAUDE.md: no partial data in stores).
- The alert sits directly under the rule sentence and above the count line and the list. It says "Tasks could not be refreshed. The log has the details." with a Retry button that calls `buildTaskIndex()`. The list stays, even when the failed refresh followed a section tag change: the alert says the list is stale.
- When `tasksStore.fileTaskGroups` is empty (a failed first fetch, or a failure after a fetch that returned nothing), the alert takes the empty state's place: the rule sentence stays, Issue 108's empty message and its action do not render. When `fileTaskGroups` has groups but the filters hide them all, Issue 108's empty state renders under the alert. `hasLoaded` is not the test: Issue 108 sets it after a failed fetch too. Issue 111 later changes this check to `rows`.
- While `tasksStore.isLoading` is true (a Retry or any other refetch), the alert stays and the Retry button is `disabled`.
- Use plain markup copied from the `role="alert"` block in `CollectionView.svelte` (`rounded-md border border-destructive/50 bg-destructive/10 p-3 text-row text-destructive`): theme tokens only, no raw palette classes. Moving it onto `InlineAlert` is a follow-up after Issues 204 and 241.

`tasksStore.reset()` clears the saved scroll offset and the error, so a vault switch opens vault B at its own top with no stale error.

`help/documentation/10-tasks-and-todoist.md` says notes are listed in path order, with numbers compared as numbers (it says modification date today).
