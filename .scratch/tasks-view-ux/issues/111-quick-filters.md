**Origin:** `tasks-view` Issue 07, moved here on 2026-11-08 and rewritten on 2026-11-12 from the Tasks view UX research (`.scratch/tasks-view-ux/research/`, `critique.md` D2, D4 and D13) and its review, then corrected the same day by the deep dive (`.scratch/tasks-view-ux/research/deep-dive/SUMMARY.md`, `refute-111.md`, `cross-state-chain.md` H2, H3, M1, M2, M8, L9). Its PRD stays in `.scratch/archived/tasks-view/`. Issue numbers in this text keep the open-itens numbering: the Tasks view Issues live in `.scratch/tasks-view-ux/issues/`, the others (030, 085, 151, 198, 204, 205 and the rest) in `.scratch/open-itens/issues/`.

**What to build:** The only status control is the hide-completed eye (titled "closed" since Issue 110), an icon whose meaning you have to guess. Replace it with a Status menu that says what is shown, start the row model the later filters share, and give the filters their own row so the toolbar can hold the title.

**Before editing, on the branch:** `grep -rn "hideCompleted\|setHideCompleted\|showCompleted\|Show closed\|filterCompleted\|computeTaskStats\|filterByDate\|describeTaskRule\|explainEmptyTasks\|fileTaskGroups\|noteFolder\|noteTaskCounts\|TASK_STATUSES" src e2e help`. Predecessors (108, 242, 110, 234, 236, 109) shaped these names; adapt to what landed, and move text verbatim where this Issue says "move".

**Layout**
- The pane toolbar holds the title "Tasks" (`min-w-0 truncate text-title`, as `FilesNavigator.svelte` titles its pane), the count (moved from the list body, `shrink-0 text-meta text-muted-foreground`) and Issue 108's refresh spinner. The title truncates first. Add no class to the `pane-toolbar` element itself (`pane-toolbar.test.ts` forbids overrides).
- The count reads "N open in M notes" when the status filter is at its default (`isQuickFieldDefault(quick, 'status')`, below), else "N tasks in M notes". N counts visible rows that are not dimmed; M counts the notes with at least one such row. Singular forms: "1 open in 1 note", "1 task in 1 note". The count shows once `tasksStore.hasLoaded` (Issue 108) is true, also in the empty state ("0 open in 0 notes"), and is absent before the first load.
- A filter row under the toolbar holds the Status menu, the date pills (until Issue 238) and the section tag textbox, with the date pills and textbox markup moved unchanged. It is a plain row, not a second `pane-toolbar` element: `pane-toolbar.test.ts` allows one per file.

**Status menu** (a `DropdownMenu` from `#lib/components/ui/dropdown-menu/`)
- Trigger text `Status: <value>`, where the value is `open`, `closed`, `all` or the chosen statuses' words (`statusGlyph(s).word`, Issue 110, for example `in progress`) joined with `, `. The trigger's accessible name must start with "Status" (no `title` or `aria-label` that says otherwise; icons `aria-hidden`).
- A radio group Open (default) / Closed / All sets `show` and clears `statuses`. While `statuses` is set, the group's `value` is `''`, so no radio shows as checked. bits-ui calls `onValueChange` on every pick, including the current value, so picking the displayed radio still clears `statuses`.
- Below a separator, one checkbox item per entry of `TASK_STATUSES` (Issue 110 defines it in `task-status.logic.ts`, open statuses first: todo, in progress, question, important, forwarded, done, cancelled), labelled with its word. Each toggles its status in `statuses` and passes `closeOnSelect={false}` so several can be picked in one go. Pass `checked` from the store and write the store in `onCheckedChange`; never bind the item to local state.
- A non-empty `statuses` wins over `show`. `statuses` is always kept in `TASK_STATUSES` order, whatever the click order, so the trigger, the sentence and tests read the same.
- No `ml-*`, `mr-*` (except `*-auto`) or `text-xs` on or inside any item (`menu-item-anatomy.test.ts`).

**Logic.** Start `src/lib/features/tasks/task-query.logic.ts` (pure: it may import `./tasks.types`, `./task-status.logic`, `./tasks.logic` and `#lib/utils/`, never a store or service, so `vaultPath` is a parameter):
- `TaskRow` is a `TaskItem` (every field: `text`, `checked`, `indent`, `lineNumber`, `status`, `metadata`) plus `filePath`, `relPath`, `folder`, `noteTitle`, `open`, `modifiedAt: number` (ms), `noteTaskCount: number`, `noteOpenCount: number` and `parentLine?: number` (the line of the nearest earlier task in the same note with a smaller indent; never taken from another note). Keeping the `TaskItem` fields means `toggleTask`, `taskChips`, `taskDisplayText`, `stripTaskTrailers` and `usesRawTaskText` (Issue 109) take a row unchanged; filters read dates, priority and tags from `metadata`. The snapshot fields of the PRD model (`noteType`, `noteTags`, lifecycle flags, `properties`, `headings`) come in Issue 244 (115b). Do not add a `key` field and do not name any type `Task` (`ipc-mirrors.test.ts`).
- `buildTaskRows(groups: FileTaskGroup[], vaultPath: string | null): TaskRow[]` keeps the group order and document order. `filePath` stays absolute and is the only path passed to IPC, `openFileInEditor` and `toggleTask`; `relPath` is for display and sorting only (indexing rule 9). `relPath` is `vaultRelativeKey(vaultPath, filePath)` (`#lib/utils/path.js`) when `vaultPath` is set and the note is inside the vault, else `filePath`. `folder` is `noteFolder(vaultPath, filePath)` (Issue 236, `tasks.logic.ts`): `''` at the vault root, outside the vault and with no vault open. `noteTitle` is `group.fileName`, `open` is `isTaskOpen(status)`, `modifiedAt` is the group's. `noteTaskCount` and `noteOpenCount` come from `noteTaskCounts(group.tasks)` (Issue 236) over the whole group, so they count the note's tasks before any quick filter or date cutoff, within what the section tag fetched.
- `export type TaskQuickFilters = { show: 'open' | 'closed' | 'all'; statuses?: TaskStatus[] }` in this Issue. Issues 238 and 239 add `due`, `priorities`, `tags` and `search` (PRD "One query model"); Issue 116's `TaskQuery.quick` is this type. `export const DEFAULT_QUICK: TaskQuickFilters = { show: 'open' }`.
- One rule for "at its default": `isQuickFieldDefault(quick: TaskQuickFilters, field: QuickFilterField): boolean` with `type QuickFilterField = 'status'` here; `'status'` is default when `show` is `open` and `statuses` is absent or empty. Issue 238 adds `'due'`, Issue 239 adds `'priority' | 'tag' | 'search'` and uses it for Reset and `Filters (n)`. Every setter writes `undefined` for an empty list, never `[]`: the checkbox toggle goes through a pure `toggleQuickStatus(statuses: TaskStatus[] | undefined, status: TaskStatus): TaskStatus[] | undefined`, which keeps `TASK_STATUSES` order and returns `undefined` when the list empties. Tests compare `quick` with `toEqual`.
- `applyQuickFilters(rows: TaskRow[], quick: TaskQuickFilters): VisibleRow[]`, where `VisibleRow = TaskRow & { dimmed: boolean }`. A row passes when `statuses` is non-empty and holds its status, or else by `show`: `open` keeps `row.open`, `closed` keeps `!row.open`, `all` keeps every row. A row that fails stays, with `dimmed: true`, when a later row of the same note in its subtree passes (its subtree is the rows after it with a larger indent, up to the next row whose indent is not larger). That is today's `filterCompletedTasks` parent rule, applied to every quick filter. Passing rows have `dimmed: false`. Return new objects; never mutate store rows.
- Until Issue 238 replaces them, the date pills still work: `applyEditedCutoff(rows: TaskRow[], dateFilter: TaskDateFilter, now: number): TaskRow[]` drops rows whose `modifiedAt` falls outside the last 7 or 30 days, with `filterByDate`'s arithmetic, and returns the input for `all`. Every row of a note shares `modifiedAt`, so the cutoff and `applyQuickFilters` commute.
- `rowsByNote(rows: VisibleRow[])` returns `{ filePath, noteTitle, folder, modifiedAt, total, open, rows }[]` in first-appearance order. `total` and `open` are read from the note's first row (`noteTaskCount`, `noteOpenCount`). A note with no visible row is not returned. The view keeps the per-note layout and the path order of Issue 234. Issue 112 replaces it with `groupTaskRows`, which reads the same row fields.
- Two small pure helpers the view and tests pin: the trigger value (`statusFilterLabel(quick)`) and the toolbar count text (`taskCountText(rows: VisibleRow[], quick)`), with the wording above.
- `describeTaskRule` and `explainEmptyTasks` (Issue 108, edited by 242 and 110) move from `tasks.logic.ts` to `task-query.logic.ts` with their tests. They keep the `sectionTag: string` parameter (Issue 242 parses it internally) and take `quick` instead of `hideCompleted`: `describeTaskRule({ sectionTag, quick, dateFilter })` and `explainEmptyTasks({ rows, sectionTag, quick, dateFilter, now })`, where `rows` is the unfiltered `tasksStore.rows`. The sentence starts with `Open tasks`, `Closed tasks`, `All tasks`, or `Tasks that are <the statuses' words, in TASK_STATUSES order, joined with ' or '>` (for example `Tasks that are in progress or done`), then the heading part and the date part as in Issue 108.
- `explainEmptyTasks` checks in this order and returns the first stage that applies:
  1. `rows` is empty: Issue 108's and 242's section-tag stage, unchanged (`clearTag` action, or the no-tag wording).
  2. The status stage, only when `applyQuickFilters(rows, quick)` returns no row (date cutoff not applied). "All N tasks are closed" ("The only task is closed" when N is 1, N = `rows.length`) when the status filter is at its default, else "No task has the chosen status". Both carry `{ kind: 'showAllStatuses', label: 'Show all' }`, which sets `show: 'all'` and clears `statuses`. It is not a reset: `resetQuick()` would put `show` back to `open`. `showAllStatuses` replaces the `showCompleted` kind, which leaves the action type.
  3. Otherwise the date stage, with Issue 108's `{ kind: 'allTime', label: 'All time' }` (Issue 238 replaces it): "No open task is in a note edited in the last 7 days" (or 30) when the status filter is at its default, "No note with tasks was edited in the last 7 days" (or 30) when `show` is `all` and no status is chosen, and "No task with the chosen status is in a note edited in the last 7 days" (or 30) otherwise. With `dateFilter: 'all'` the view never reaches stage 3; keep Issue 108's fallback for it.
