# 01: Canvas edits persist to the canvas's own tab, never to the tab active after a switch or close

**What to build:** Two user-facing fixes. (1) A canvas edit made just before switching or closing tabs (typing in a card, a color change, a selection) is saved into that canvas's .canvas file and never into the tab that becomes active. (2) Switching from canvas A to canvas B within the debounce window keeps A's last edit. Fix location: give each canvas file its own instance by wrapping CanvasView in {#key editorStore.activeTab.path} in src/lib/app/EditorView.svelte, as the collection branch already does. Pass the tab path in (a `path` prop) and bind persistence to it: onJsonChange becomes a path-scoped writer, e.g. a new editor.service function onContentChangeForPath(path, content) that calls editorStore.updateTabContentOnly(path, content) plus scheduleAutoSave('body'). The onDestroy flush in src/lib/features/canvas/CanvasInner.svelte must also build its JSON from data captured for its own file (the last synced/parsed canvas data), not from the jsonContent/canvasData prop. At destroy time that prop evaluates the new active tab's content. Keep the flush itself: it is what saves the last edit on quit.

## Notes

- **Source:** audit 2026-11-04 (`.scratch/audit-2026-11-04/findings.md`), deep dive by an opus verifier the same day. Wave 1 of the parallel plan.
- **Finding `canvas-destroy-flush`:** real, critical. Root cause: CanvasInner persists through onJsonChange = onContentChange, which calls editorStore.updateContent and writes tabs[activeIndex], the tab active at call time. The onDestroy flush runs after setActiveIndex/removeTab has already moved activeIndex, so a pending 300 ms debounce lands in whatever tab is now active and autosave writes it to that file.
  Evidence: src/lib/features/canvas/CanvasInner.svelte:230-234 (onDestroy calls persistChanges when pendingPersist is set). :104-108 persistWithoutHistory calls onJsonChange(json). src/lib/app/EditorView.svelte:80-81 wires onJsonChange={onContentChange} inside an {#if isCanvasTab} branch that is torn down once activeTab changes. src/lib/core/editor/editor.service.ts:229-232 onContentChange calls editorStore.updateContent and then scheduleAutoSave('body'). src/lib/core/editor/editor.store.svelte.ts:84-88 updateContent writes tabs[activeIndex].content. switchTab (editor.service.ts:257-262) and closeTab/removeTab (editor.service.ts:290, store :71-82) change activeIndex synchronously, before the branch teardown. Arming paths: TextNode.svelte:40 updateNodeData on every keystroke, and handleSetNodeColor at CanvasInner.svelte:394-398. Both persist only through the debounce at :212-226, and bind:nodes (:580) means selection changes also arm it. closeTab's dirty prompt (editor.service.ts:276) does not fire because the canvas tab's content is not yet updated. persistWithoutHistory also reads the canvasData prop (:71, :105), which at destroy time evaluates editorStore.activeTab.content of the new tab.
- **Finding `canvas-switch-drop`:** real, high. Root cause: Every canvas tab shares one CanvasInner instance: the canvas branch has no {#key}, unlike the collection branch. A prop-driven sync to canvas B re-runs the debounce effect. Its cleanup cancels A's pending timer, then it returns early on syncing=true without clearing pendingPersist. A's last edit is lost, and the stale pendingPersist feeds the active-tab onDestroy flush later.
  Evidence: src/lib/app/EditorView.svelte:80-81 (CanvasView not keyed; compare :84 {#key editorStore.activeTab.path} for CollectionView). src/lib/features/canvas/CanvasView.svelte:15-17 passes props through. CanvasInner.svelte:85-98: the sync effect sets syncing=true, assigns nodes = B's nodes, and resets syncing in a microtask. :212-226: the debounce effect cleanup (:225) clears A's timer, then `if (syncing) return;` (:218) runs before the timer is re-armed. pendingPersist is cleared only inside the timer callback (:223). Text edits reach the tab only through this timer (TextNode.svelte:40 updateNodeData), so A's typed text never reaches tabs[A].content.
- Shared root cause: the persist callback targets tabs[activeIndex] at call time, and all canvas tabs share one unkeyed CanvasInner. Keying alone does not fix it: the keyed instance's onDestroy still runs after activeIndex has moved, so the path binding is required. Mounting SvelteFlow in jsdom likely needs ResizeObserver/DOMMatrix stubs (infrastructure stubs, not store mocks; not verified). Not verified: whether bind:nodes receives `measured` updates right after mount, which would arm the debounce on every canvas open and widen the window. Check it while writing the test. Per CLAUDE.md, trace the onDestroy flush and the debounce before changing them, and keep the quit-time flush. Sibling sites from the sweep, out of scope (blur-driven, need WebKit blur-on-removal, unverified): KanbanLane.svelte:253 / KanbanCard.svelte:195 to KanbanView.svelte:89 onContentChange, CollectionView.svelte:429 commitTabRename to onYamlChange, and PropertyField.svelte:52-58. If the path-scoped writer lands, consider moving KanbanView to it in a follow-up.
