# 12: Composer reports saved only after the capture note is written, and keeps the text on failure

**What to build:** In the floating composer, Cmd+Enter flashes 'saved' and dismisses only after the main window has written the capture note. If the template or write fails, or the Rust call itself errors, the composer stays open with the typed text and shows an inline error. Today it dismisses in every case and resetForShow clears the text. Fix in three places. (1) src/routes/composer/+page.svelte:28-51: do not call dismiss() after a failed submit, and keep the text. (2) A completion signal from the main window. handleDetectedCapture (src/lib/plugins/quick-capture/quick-capture.service.ts:83-103) reports success or failure for composer-originated payloads. For example, Rust tags the payload with a request id in submit_composer_capture (src-tauri/src/quick_capture/commands.rs:459-474), the main window answers with a new qc:composer-capture-result event or command, and the composer waits for that answer with a timeout. (3) executeAction (deep-link.service.ts:180-211) currently swallows the error, so the capture path needs a variant that rethrows, or a result value, so the outcome reaches the reply. (4) Unsent text survives a closed or dismissed composer: the composer keeps its text in a draft (composer localStorage, every read and write wrapped in try/catch so the composer still works without storage), resetForShow restores that draft instead of clearing it, and the draft is cleared only on a reported success.

## Notes

- **Source:** audit 2026-11-04 (`.scratch/audit-2026-11-04/findings.md`), deep dive by an opus verifier the same day. Wave 1 of the parallel plan.
- **Finding `composer-early-ok`:** real, medium. Root cause: submit_composer_capture is fire-and-forget: it returns Ok once app.emit succeeds, before the main window has checked for a vault or written the note, and nothing reports back to the composer. The composer also calls dismiss() after its catch, so it drops the text even when the Rust call itself rejects. resetForShow clears the text on the next summon. Correction to the finding: the main-window failures are not only logged. handleDetectedCapture toasts 'Open a vault before capturing', and executeAction toasts 'Failed to execute deep link action: capture'. But those toasts appear in the main window, which may be hidden behind the app the user captured from, and the typed text cannot be recovered.
  Evidence: src-tauri/src/quick_capture/commands.rs:459-474: submit_composer_capture builds the payload and returns app.emit(...).map_err, with no acknowledgement. src/routes/composer/+page.svelte:41 calls await call('submit_composer_capture'), :42-44 shows the 'saved' flash, the catch at :45-46 only does console.error, and :50 runs await dismiss() unconditionally. :61 resetForShow sets text = ''. Main window: src/lib/plugins/quick-capture/quick-capture.service.ts:87-92 handles no vault with a toast and return. :102 calls executeAction, which at deep-link.service.ts:207-211 catches and toasts. The write itself happens in deep-link-actions.ts:133-221 (mkdir, writeTextFile at :211). The composer tests (src/tests/routes/composer-page.test.ts) cover only the theme.
- **Owner decision (2026-11-04):** D10 (b)+(c). (b) Full round-trip ack from the main window with a timeout (about 3 s); on timeout keep the text and say the result is unknown. (c) Persist unsent composer text and restore it on the next summon; clear it only on a reported success. No dedicated handling for a capture with no vault open: the owner never uses the app without a vault. If it happens, the composer takes the timeout path and keeps the text. Known trade-off: after a timeout whose write did succeed, resubmitting the kept text creates a second capture.
- Correction to the audit: main-window failures are not only logged. quick-capture.service.ts:91 and deep-link.service.ts:210 toast, but in the main window, which may be hidden while the composer floats over another app. The clipboard-shortcut path (lib.rs:81) emits the same event with no composer, so the ack must apply only to composer-originated payloads. Keep the per-capture queue serialization (quick-capture.service.ts:53-64).
