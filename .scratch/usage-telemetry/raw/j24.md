## Findings the scouts missed

**M1, medium. The privacy CI gate cannot see a telemetry library added as a dependency.** `privacy.yml` scans only `src/**/*.ts` and `src-tauri/src/**/*.rs` source patterns (`privacy.yml:40-120`). A Rust crate such as `tauri-plugin-aptabase`, or the existing `sentry` crate (`Cargo.toml:72`), makes its HTTP calls inside the dependency, and the scan never sees them. The PRIVACY.md claim that "any new external call ... will fail the build" (`PRIVACY.md:20`) does not hold for dependency-based telemetry. Any third-party option would rely on review, not on the gate.

**M2, medium. A user-chosen endpoint (self-hosted or OTLP) does not fit a static CSP or HTTP scope.** Sentry works because its ingest hosts are fixed wildcards (`tauri.conf.json:29`). The HTTP plugin scope is a static URL list (`capabilities/default.json:227-263`). An arbitrary user host needs one of two things:
- widen `connect-src` to `https:`, which weakens the CSP for every vault, or
- send from Rust with a new HTTP client, which is a new dependency, and the privacy gate's `reqwest` pattern would flag it.

s18 rated OTLP "clean, cheap to emit" and missed this.

**M3, info. The strongest third-party candidate was not evaluated: Aptabase.** It has an official Tauri v2 plugin (`tauri-plugin-aptabase` 1.3.0, published 2026-10-16 per the crates.io API, so past the two-week quarantine). It is MIT, explicit `trackEvent` only, and enriches events with OS and app version (https://github.com/aptabase/tauri-plugin-aptabase). It is the cheapest SaaS path. But it is built for aggregate app analytics across many installs. For one user it still needs an account, a fixed host in CSP or scope, a PRIVACY.md rewrite, and the registry diff below to answer "never used". I did not verify free-tier retention or PostHog cloud retention: the pricing page fetch failed.

**M4, medium (design). Four seams cover nearly all usage, and the event id should be the command id.**
1. `CommandPalette.svelte:28` (palette).
2. The `global-keybindings.ts:224` map, keeping `binding.command` instead of discarding it (shortcuts).
3. `selectRailItem` (`rail-navigation.ts:14`) for rail clicks that don't go through the palette.
4. `settingsPanelStore.setSection` for settings sections.

Use the `AppCommand.id` as the feature key everywhere a command exists. Strip the suffix of `rail:open-view:*` and `rail:go-to:view:*` / `type:*` to the prefix. Add feature-level events only where no command exists. That avoids the s11 double count.

**M5, info. "What do I never use" needs no hand-kept registry.** The denominator already exists at runtime:
- the palette command list (`app/commands.ts`)
- rail navigators (`railRegistryStore`)
- the `SettingsSection` union (`settings.types.ts:331`)

The diff is registered ids minus ids with a count above zero. This answers s18 open Q3.

**M6, info. The data is tiny, so a per-day counter beats an event log.** About 100 ids × 365 days is at most around 36k rows a year in `usage_counts(day TEXT, feature TEXT, count INTEGER, PRIMARY KEY(day, feature))`, written by UPSERT on a timer. That needs no retention job at all. An append-only event log (s18 F5, "timestamp and count") adds volume and has no question it would answer better.

**M7, low. Per-vault storage matches the existing opt-in model.** Settings and the Sentry opt-in live in `{vault}/.kokobrain/settings.json`, and the vault DB sits next to them. Per-vault counters are consistent with that, but they split across vaults. The owner reportedly uses no external sync, so the vault DB stays on the machine.

**M8, low (doc drift, outside my area).** `PRIVACY.md`'s network table omits Todoist, though it is in CSP `connect-src` (`tauri.conf.json:29`) and the HTTP scope (`default.json:227`).

## Verdict

For a single owner who wants to learn their own usage over months, no third party beats local stats.

Every third-party path has these costs:
- It breaks `PRIVACY.md:8` ("No analytics, no tracking").
- It needs CSP or HTTP-scope edits, and a user-chosen host doesn't fit at all (M2).
- It slips past the privacy CI gate when it comes as a dependency (M1).
- It still needs local work for the "never used" diff (M5).

Sentry Logs is out because its query window is 30 days at most. Self-hosting is out because PostHog asks for 4 vCPU and 16 GB, unsupported. Aptabase is the only credible SaaS, and its strengths (dashboards across many installs) don't matter for an audience of one.

Recommended design:
- **Storage:** a `usage_counts` per-day counter table in the existing vault DB.
- **Seams:** the four in M4, keyed by command id with path suffixes stripped.
- **Toggle:** a Settings switch, off by default, next to Sentry.
- **Views:** a small Settings view with top and never-used lists, and optionally `kb.usage()` for QueryJS charts (Chart.js is already bundled).

It needs no new dependency, no network and no PRIVACY.md change beyond one line. Expect about 2 days plus the ts-rs bindings gate.
