## Summary

- The Sentry tests cover the main gates well: opt-in default, DSN validation, queued reconfiguration, and the integration whitelist checked against the SDK's real default names (`sentry.service.test.ts:84-96`).
- The biggest gap is that `@sentry/browser` is fully mocked in `sentry.service.test.ts`, so `beforeSend` is only tested by calling the function directly. No test shows the SDK's event pipeline ever runs the scrubbing.
- The scrubbing also does not cover `message` or `exception` values, and handled errors with non-Error arguments can forward arbitrary strings (possibly note paths) to Sentry. No test covers this, and `debug.test.ts` mocks the forwarding boundary.
- The Rust tests check only an invalid DSN and an explicit opt-out. Neither covers an enabled client, the scrub-related client options, or closing a previous client.
- The e2e test covers only the UI gate and the "not active" branch. It does not cover a successful test event, DSN persistence, or the absence of network traffic.

## Findings

**F1. medium. Scrubbing covers only four fields; message and exception text leave the machine untouched.**
- Claim: `removeSensitiveEventData` drops `breadcrumbs`, `extra`, `request`, and `user`, but keeps `message` and `exception.values[].value`. Any non-Error last argument to `error()` is forwarded as the exception.
- Evidence: `/Users/diegorv/Dev/pet-projects/koko/brain/src/lib/core/settings/sentry.service.ts:28-36` (scrub), `:84` (`beforeSend`); `/Users/diegorv/Dev/pet-projects/koko/brain/src/lib/utils/debug.ts:31` (`captureSentryException(tag, args.find(Error) ?? args.at(-1))`). Settings text (`SentrySection.svelte`, last paragraph) admits "Error messages can still include technical details", so this may be a known trade-off, but no test pins it. The scrub test feeds only breadcrumbs, extra, request, and user (`sentry.service.test.ts:98-109`).
- Test gap: the scrub test would still pass if `message` carried a vault path. The debug test (`debug.test.ts:130-141`) only covers the Error branch; the `args.at(-1)` branch is untested.
- Fix: decide the policy (strip or redact `message` and `exception` values, or require callers to pass Errors with no paths). Then add a test with a path in `message` and a string last-arg, asserting what reaches `Sentry.captureException`. Grep found 151 `error(` call sites; I checked only the first ~12 path-related hits, so the exhaustive check is UNVERIFIED.

**F2. medium. The SDK is mocked, so the real beforeSend and dataCollection behavior is never exercised.**
- Claim: the tests assert the options object literal, not what the SDK does with it. A `beforeSend` that never runs, or `dataCollection` keys the SDK ignores, would still pass.
- Evidence: `sentry.service.test.ts:3-9` (full `@sentry/browser` mock), `:63-72` (literal `toMatchObject`), `:98-109` (direct call). Key names are type-checked: `@sentry/core@11.9.0` declares `dataCollection?: DataCollection` (`node_modules/.pnpm/@sentry+core@11.9.0/node_modules/@sentry/core/build/types/types/options.d.ts:346`), so `pnpm check` catches typos but not no-ops. The integration-name test (`:84-96`) is the one that uses real SDK code.
- Fix: add one test that runs the real `@sentry/browser` with a stub transport (option existence UNVERIFIED in this session) and a synthetic error, then asserts the transmitted payload has no breadcrumbs, request, user, or extra. This is the test that would catch the case the owner asked about.

**F3. medium. Rust tests do not cover the enabled path or the options that protect privacy.**
- Claim: `error_monitoring_test.rs` has two tests. Neither enables a client, asserts `send_default_pii(false)` or `max_breadcrumbs(0)`, or checks that an invalid DSN after a valid one closes the previous client.
- Evidence: `/Users/diegorv/Dev/pet-projects/koko/brain/src-tauri/tests/error_monitoring_test.rs:3-21`. Implementation: `/Users/diegorv/Dev/pet-projects/koko/brain/src-tauri/src/error_monitoring.rs:36-40` (close previous), `:46-48` (parse), `:49-55` (init options). The "disabled" test passes on a no-op because the default state is already inactive.
- Fix: add (a) valid DSN sets `is_sentry_active` true, (b) enable then disable makes it false, (c) valid then invalid makes it false, and (d) a way to observe the options (for example a small pure builder function returning `ClientOptions` that the test inspects).

**F4. medium. The Rust side has no host allowlist, and no test documents that.**
- Claim: `configure_sentry` accepts any DSN that parses. The only host check is TypeScript (`sentry.logic.ts:13-27`). The CSP `connect-src` (`src-tauri/tauri.conf.json:29`) applies to the webview, and I believe it does not constrain the Rust HTTP transport (UNVERIFIED against Tauri docs in this session).
- Failure scenario: a future caller passes an arbitrary DSN to the `configure_sentry` command, and Rust panics are sent to that host.
- Fix: enforce the same host allowlist in Rust (or document the single-caller assumption) and add a test that a non-Sentry host returns `Err`.

**F5. medium. The privacy scan allowlists Sentry and does not inspect the Rust crate.**
- Claim: `privacy.yml` lists `@sentry/browser` and `ingest(\.us|\.de)?\.sentry\.io` under `known`, so any Sentry use passes whether or not it is opt-in gated. The Rust patterns do not include the `sentry` crate, and `.test.ts` files are skipped.
- Evidence: `/Users/diegorv/Dev/pet-projects/koko/brain/.github/workflows/privacy.yml` (`patterns`, `skip`, `known` blocks for both TypeScript and Rust scans).
- Fix: keep the allowlist but add a check that the Sentry import sits only in the `sentry.service.ts` boundary, and add the `sentry::` crate to the Rust patterns with its own known entry.

**F6. medium-low. The e2e test covers only the UI gate and the "not active" branch.**
- Claim: `settings.spec.ts:46-61` verifies the switch default, DSN field visibility, the alert, and "Sentry is not active". It does not cover "Test event sent", the "pending" message, DSN persistence, or the absence of outbound traffic. The Rust side is mocked (`e2e/mocks/tauri-core.ts:393`, returns `null`).
- Fix: add an e2e case that enters a valid-format DSN, asserts the saved settings contain it, and intercepts network requests to confirm nothing reaches an ingest host (the mock could also stub the success path).

**F7. low. The lifecycle tests mock Sentry entirely and miss rejection paths.**
- Claim: `app-lifecycle.service.test.ts:106-109` mocks `configureSentry` and `disableSentry`, so only call order is asserted. `app-lifecycle.service.ts:154` and `:585` call `void disableSentry()`, which drops a rejection. The init call site has try/catch (`:202-206`), but no test forces it to reject.
- Fix: add a case where `configureSentry` rejects and assert `debug.error` is called, and one where `disableSentry` rejects at teardown, to make the unhandled-rejection path explicit.

**F8. low. Tags and IPC failure are not asserted.**
- Claim: the `source` tag (`sentry.service.ts:115`) and the `synthetic` tag (`:128-129`) are never asserted. There is no test that an `invoke('configure_sentry')` rejection propagates (`:50-54`) or that a Rust client survives a failed TS disable. In that case `activeDsn` is already `null` (`:45-47`), so TypeScript reports inactive while Rust may still be reporting.
- Fix: assert the tags with the `withScope` mock's `setTag`, and add a test where the invoke rejects.

**F9. low. The release-string assertion is weak.**
- Claim: `expect.stringMatching(/^kokobrain@/)` also matches `kokobrain@unknown`, and `sentry.service.test.ts` does not set `__BUILD_INFO__`.
- Fix: set `__BUILD_INFO__` in the test and assert the exact release.

**F10. low. The logic test does not guard the CSP domain list.**
- Claim: the allowlist in `sentry.logic.ts:1-6` must match the CSP (`tauri.conf.json:29`), but nothing checks that they agree. `sentry.logic.test.ts` covers the three regions and rejections but not ports, queries, or fragments.
- Fix: a test that parses `tauri.conf.json` and asserts each `SENTRY_INGEST_DOMAINS` entry appears in `connect-src`.
