## Findings

1. **major** `src/tests/lib/features/type-definitions/TypeNameDialog.svelte.test.ts:198` The double-Enter test passes without the `busy` guard in `confirm()`. The shared `onConfirm` (`:52-56`) adds the saved name to `taken`, so after the first Enter `validate` returns "already exists" and the second Enter returns on `error !== null`; the click on "Updating notes..." is a no-op because the button is disabled. In the app the store gains the name only after `renameItem` / `createFile` finish, so a fast second Enter before that is exactly the case the test should cover. Fix: in this test, make `onConfirm` leave `taken` alone (for example a `$state` flag `registersName` that the shared `onConfirm` checks, set false here), then assert `confirmed` is `['Area']`. Verified with a probe: with an `onConfirm` that does not touch `taken`, the guarded code gives one call and the unguarded code gives two (`+ "Zeta"`).
2. **nit** `src/lib/features/type-definitions/TypeNameDialog.svelte:88` The input stays editable while busy. Typing during the save changes the field, while the frozen line keeps describing the name being saved and the dialog then closes with the typed text discarded. The Issue does not ask to lock the input and the build report flags it as undecided; leave it unless the owner wants `disabled={busy}` (check the focus trap and Escape still work if so).
