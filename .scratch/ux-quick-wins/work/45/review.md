## Findings

1. minor, `src/tests/routes/composer-page.test.ts` (test "Discard empties the editor and the stored draft and keeps focus in the editor"): the `document.activeElement === contentDOM` assertion passes without the refocus. Probe: deleting `view?.focus()` from `discard()` (`+page.svelte:206`) leaves all 49 tests green, because jsdom's `.click()` moves no focus and the editor was focused at mount. Fix: move focus off the editor first (`discardButton()!.focus()` before `.click()`, or blur the content DOM), so the test fails when the refocus is missing.
2. minor, `src/routes/composer/+page.svelte:230` / test file: the `next !== text` guard in `onDocChange` has no test (probe: replacing it with an unconditional `restored = false` keeps all tests green). The build report says no test can fail without it; that is not right. It matters on the late-confirmed path: a save confirmed after Esc and a summon runs `setText(withoutWritten(text, body))` at `:138` in the new show; when text was typed after the submit, the tail is non-empty, and without the guard the `setComposerText` echo would clear the note on a draft that is still restored. Fix: add a variant of "drops the note when a late confirmed save empties the restored text" where text is typed after the submit (`type('an idea, more')` while waiting) and assert the note stays over `', more'`.
3. nit, `src/routes/composer/+page.svelte:159`: after the hold, `setText(withoutWritten(text, body))` also runs in a new show (summoned during the hold). The stored draft was already trimmed at `:151`, so the new show's text normally no longer starts with `body`, and the strip does nothing. When it does start with `body` (the person retyped the same capture within the hold, or the tail itself begins with the body), the strip removes unsaved text. This also covers the Issue's accepted Risk (a keystroke during the hold rewrites the full text, and the strip trims it in the new show), so restricting it to `show === savedShow` would trade one rare case for the other. No change asked; noted for the record, since the Issue's Risk section names "withoutWritten on the wrong body" as the data-loss path.
