## Findings

1. **blocker** `src/lib/plugins/kanban/KanbanCard.svelte:135-142` - the editor does not grow on open, only on typing (What to build 5: "set on input and on open"). On open, the focus effect (`:127-133`) writes `editText = item.text`. The grow effect then measures in the same flush, before the `bind:value` render effect has put that value into the textarea, so it measures the old (empty) value. It does not run again after the DOM updates, because `editText` has not changed since it ran. The code comment ("A user effect runs after the `bind:value` render effect") holds only when the DOM already has the value, which is the case when the user types. Probe (a temporary test file, deleted afterwards): with the test's stub (`value.length > 20 ? 60 : 20`), opening the card "a very long card text that certainly wraps" gives `textarea.value` = the full text and `style.height` = `20px`, where 60px was expected. A long card therefore opens as one clipped line (now `overflow-hidden`, so it cannot even scroll) until the first keystroke. The existing test misses this because "plain card" is under the 20-character threshold, so the empty value and the real value both give 20px. `typeInto` also sets `textarea.value` itself, so it cannot catch the same ordering bug on a programmatic `editText` change (a wikilink insert, `handleWikilinkSelect` `:103-110`). Fix: measure after the DOM update, for example `await tick()` before reading `scrollHeight`, or call one `autosize()` from `oninput` and from the open effect after `tick()`. Tests: open a card longer than the stub threshold and expect 60px on open, and add one case where `editText` changes programmatically (a wikilink suggestion select).
2. **major** `src/lib/plugins/kanban/KanbanView.svelte:521` - after Enter or Escape, the newly focused board root shows the browser focus ring around the whole view. The root has no `outline-none`, and the base layer (`src/app.css:495`, `outline-ring/50`) only sets the colour. Probe with Playwright 1.64.1 (headless WebKit and Chromium; scratchpad script): focus moved programmatically from a textarea to a `tabindex="-1"` div makes the div match `:focus-visible`, with computed `outline-style: auto`, in both engines. Before this branch nothing focused the root programmatically. The precedent for the same pattern, `EventCalendarView.svelte:229-232` (a `tabindex="-1"` root focused from code), carries `outline-none`. Fix: add `outline-none` to the root's class, and a test (DOM class or source) that pins it.
3. **minor** `src/tests/lib/plugins/kanban/KanbanView.test.ts` ("Enter commits once and focuses the board root ...") - the build report says, and the code path confirms, that the M27 no-op guard swallows a second identical write, so `getPersistCount() === 1` still holds if the focus moves before the commit. The criterion's literal assertion is there; the guard it is meant to protect is not tested. Fix, optional: also assert that `document.activeElement` is still the textarea (or that the root is not focused) synchronously right after `press(textarea, 'Enter')` and before `settle()`, so focusing early fails the test.
4. **nit** `src/tests/lib/plugins/kanban/KanbanView.test.ts` ("the linked-note preview is clamped ...") - `vi.mocked(loadLinkedFileContent).mockResolvedValue(...)` is never reset, so every later test in this describe renders the linked card with that preview. Harmless today, but it is order-dependent. Fix: reset it in the describe's `afterEach` (`vi.mocked(loadLinkedFileContent).mockReset()` plus restoring the `null` default), or use `mockResolvedValueOnce`.
