# Todoist two-way sync: design (after opus validation, 2026-11-09)

Evidence: `wave1-notes.md` (scouts). This file folds in three adversarial opus reviews (data safety, API semantics, scope/slicing). Owner decisions were answered on 2026-11-09 (all four recommended defaults, plus the state location); they are marked **[decided]**.

## Goal (owner, 2026-11-09)

What is created or changed in the brain shows up in Todoist, and the reverse. Projects and labels sync too, at least in a basic form. A local SQLite store is allowed.

## Hard rules (each one answers a found failure)

1. **Identity is recoverable from either side.** Each synced line carries an anchor; a brain-born task's Todoist description ends with the line `kokobrain:td-<value>` (description is not otherwise synced). A Todoist-born task uses its Todoist id as the anchor value. When the store is missing or empty but anchors or remote items exist, the engine runs in rebuild mode: pair a line with an item by `td-<todoist id>` or by the description's `kokobrain:` line, create nothing, log the unmatched. (Store loss, restored backup, new machine otherwise duplicate everything.)
2. **Anchor before create.** A brain-born task gets its anchor written to the line and a link row with `todoist_id NULL` and a stored `pending_uuid` before `item_add` is sent. Before inserting a pulled task, match it against pending adds by its description's `kokobrain:` line (content + project only as a fallback). A lost `item_add` response never yields a second task or a second line.
3. **Two bases per link.** `remote_base` = raw Todoist values last seen; `local_base` = values parsed from the line as last written/seen. Local change = parse(line) vs `local_base`; remote change = item vs `remote_base`. Push only local changes, write only remote changes. When both sides already agree, just move the bases. Bases move in the same transaction as the `sync_token`. Brain -> Todoist projection is lossy (parser strips `#tags`, priority/date emoji, `🆔`, collapses spaces), so never compare the raw content.
4. **Field patches, never whole-line rewrites.** Writes change one token at a time: status char, the `📅` token, the priority emoji, tags inserted before the anchor, the description text only when the line has nothing in mid-sentence that would be lost (else log a conflict). "Mid-sentence" = any tag, link or unmapped signifier that sits between the first and the last word of the description text; one before the first word (e.g. `- [ ] #todoist Call Bob`) stays in place and does not block [decided 2026-11-09]. Preserve `⏳ 🛫 ➕ ⛔ 🏁`, links, and anything not mapped.
5. **Status from the status char, not `checked`.** `checked` is `char != ' '` (parsing.rs:1633), so `[/] [?] [!] [>]` look checked. Closed = `x`/`X` (and `-`, **[decided]** yes). A remote reopen never overwrites an open non-space status with a space; a remote close keeps `-` if present.
6. **Completion through `/sync` `item_close` with a uuid**, never `item_complete` (archives recurring tasks for good) and never REST `closeTask` (SDK retries network errors, no uuid, a recurring date can advance twice). `item_close` is missing from the SDK's typed command map; build it by hand. Each cycle pulls before it pushes; if remote `due` moved since the base, drop the pending close. A command response carries only `sync_status` and `temp_id_mapping`, so after an ack the engine runs an incremental pull and rewrites the line from it (recurring: `[ ]` + new `📅`). A pending close or reopen lives in the link's `pending_cmd` column (uuid + type) until acknowledged. Verified live (`live-check.md`): `item_close` rolls a plain recurring rule forward, but completes for good a rule whose string contains `starting <date>`; such Todoist-made rules are closed anyway and the outcome logged.
7. **Recurring tasks:** Todoist owns the rule; the `🔁` text is never parsed into a Todoist update. A bare `📅` change on an item with `is_recurring` drops the rule (verified live), so a due push is always `{date, string: remote_base string, lang}`. Creation sends `due: {date: <📅>, string: <🔁 text>, lang: "en"}` (or `{string}` without a `📅`), never `"<rule> starting <date>"`, which ends on the first close (verified live). Keep the time part of datetimes.
8. **Labels:** a label becomes a tag only when the whole name matches the tag rule (today ASCII `[A-Za-z0-9_][A-Za-z0-9_-]*`, parsing.rs:1577). Others are kept in `remote_base.unmapped_labels` and always re-sent (`item_update.labels` replaces the list). Compare case-insensitively. The scope tag, `defaultLabel` and the context labels `Work` and `personal` stay out of the mapping: never written as tags, never removed by a push (kept like unmapped labels). `autoParseLabels: false` on add.
8b. **Vault context [decided 2026-11-09]:** a per-vault setting `syncContext: 'work' | 'personal'` (default `'work'`). The owner's webhook server (`koko-personal-webhooks`, rule "Default new tasks to 'Work' unless labeled 'personal' or 'kokobrain'") adds `Work` to every new Todoist task. A brain-born task in a `work` vault is sent with no context label, so the webhook adds `Work`; in a `personal` vault it is sent with the label `personal`, so the webhook leaves it alone. The sync does not add `defaultLabel` (that setting belongs to the old send popover). The webhook's later label edit arrives as a normal remote change and only touches the preserved labels.
8c. **Each vault syncs one Todoist project tree [decided 2026-11-09, replaces the label filter].** Setting `syncRootProjectId`: the vault syncs that project and every project nested under it, at any depth (the owner's roots: `Work` = `6hxGCqmrqCMqj7mj` for the work vault, `Personal` = `6hxGCqqw9pjvv9MF` for the personal one, created 2026-11-09). Adoption needs no label check: every open task in the tree is synced. The Todoist Inbox belongs to no tree; setting `syncIncludeInbox` (default off) adds it to one vault (the owner turns it on in one vault only). A task or project moved out of the tree in Todoist is detached (line or note kept, logged); one moved into the tree is adopted. With no root chosen, the sync stays off.
9. **Safety brakes.** Start only after `vaultStore.indexReady`; capture `vaultStore.path` at cycle start, recheck it before every write, and pass the vault root to every sync IPC command, which refuses a mismatch; abort a cycle when the anchored lines seen fall under ~50% of active links (or zero). Caps per cycle (creates 25, close/reopen 25, field pushes 50, detaches 10); over a cap, pause and ask. First run is a preview. "Pause and ask" = on a manual cycle, a confirm dialog naming the counts: yes runs this cycle uncapped, no aborts with bases untouched. Automatic cycles never ask: they skip the over-cap action class, show one toast, and never run before `first_run_done`. Never act on a single missing observation; detach only after N consecutive misses or on `is_deleted`.
10. **Duplicate anchors freeze.** Build anchor -> occurrences each cycle (copy-line-down, paste, templates duplicate anchors). Two or more occurrences: no pushes, no creates for that link; log it.
11. **Excluded always:** templates folder (`_system/templates` default, settings.store:98), `_system/`, `.view`, code blocks (already skipped by the parser), `.kokobrain/` (hidden).
12. **Writes into notes:** notes without an open tab go through a Rust guarded write located by unique anchor + expected text (not line number), vault-relative path joined with the vault root in Rust; then `markRecentSave` + the after-task-write steps (the 'task' source from open ticket 114, moved out of `features/tasks` into a core module so the sync can call them without importing `features/tasks`). A new note is created through `create_note` + `applyNoteChange({source:'create'})`, never the 'task' source. The active tab gets a guarded CodeMirror transaction; a background tab (plain string, no view) gets a string patch through the tab content update; autosave persists both, the background job never saves the user's tab, and both paths return the new content. The engine prefers open-tab content over disk when diffing. Read tasks with `get_all_tasks_v2` directly, not the throttled entries snapshot; notes written in this cycle use the write's returned content.
13. **API facts to respect:** 100 commands/request, 1000 partial / 100 full syncs per 15 min; read `retry_after` from `responseData.error_extra`; 400 command errors are terminal (mark, stop retrying); SDK 16 `TodoistSyncError` drops the pull's `sync_token`, so send command batches separately from pulls or re-pull with the old token; content <= 500 chars and no newlines (check before queueing); minimum 30 s between cycles.

## Architecture

- **Code:** new `src/lib/features/todoist-sync/` (engine `.service.ts`, pure diff/merge/projection in `.logic.ts`, store for UI state). The SDK client, the plugin-http fetch adapter and the priority map move there from `features/tasks`; the old Send popover imports them from there until it is retired. Settings use flat keys in `TodoistSettings`: `syncEnabled`, `syncFolder`, `syncIntervalMinutes` (the settings merge is shallow). It reads tasks through contracts (`get_all_tasks_v2`), never imports `features/tasks` (avoids a feature cycle when the Tasks view later shows sync state). Lifecycle wiring in `app/`. Settings stay in `core/settings` (`TodoistSettings`).
- **HTTP:** TS, SDK `sync()` over the existing plugin-http adapter (scope, CSP and privacy.yml already allow todoist.com in TS; a Rust client would fail privacy.yml).
- **State [decided]:** new tables in the existing `<vault>/.kokobrain/kokobrain.db`, created in the schema module, accessed through the existing `with_db` / `with_db_transaction` (sync writes are small and background, so waiting behind a semantic batch is harmless; the FTS connection is the precedent if a dedicated connection is ever needed). Code never deletes this file (only FTS tables are rebuilt on a version bump), and rule 1's rebuild mode covers its loss. Tables: `todoist_kv` (sync_token, user_id, vault_id, first_run_done), `todoist_sync_log`, and `todoist_task_link(anchor, todoist_id, note_rel_path, local_base, remote_base, pending_uuid, pending_cmd, miss_count, frozen)`. Projects are identified by note frontmatter `todoist_project: <id>`; sections by heading text within the project note plus a small `todoist_section_link(todoist_section_id, project_id, heading)` table when sections land. `todoist_sync_log` keeps the newest 1000 rows. One transactional IPC per step.
- **Project model [decided]:** one note per Todoist project of the vault's tree (rule 8c), root included, in a folder (default `Todoist/`), frontmatter id; with `syncIncludeInbox`, the project with `inbox_project: true` -> `Todoist/Inbox.md`. Flat: nested projects become sibling notes, nesting ignored; name collision gets a suffix; illegal filename chars cleaned. The note's filename is the project name (no H1 or frontmatter title). Project rename in Todoist renames the file through the rename-with-links path; archived project stops syncing its note.
- **Sections:** `##` headings in the project note. A line under no section heading has `section_id: null`. Section order is not synced.
- **Scope [decided]:** (b): every task line in notes under the sync folder, plus lines tagged `#todoist` anywhere else (those land in the root project and stay in their note). Alternatives: (a) folder only; (c) whole vault (rejected: templates, archives, thousands of old tasks).
- **Anchor [decided]: `🆔`.** `🆔 <id>` (already parsed anywhere on the line and stripped from `description`, no parser/DTO change; visible; collides with Obsidian Tasks dependency meaning) vs `^td-<id>` (hidden by live preview off-cursor; needs a parser change: `blockId` field (DTO), strip from `description` and from the recurrence text, which today swallows it; breaks when text is typed after it). Format: `🆔 td-<value>`. A Todoist-born task uses `td-<todoist id>` (rebuild needs no push); a brain-born task uses `td-` plus 8 random base36 chars, checked unique against the vault. A line that already carries a user `🆔` without the `td-` prefix is out of the sync (logged): the parser keeps only one id.
- **Sync log:** the bounded `todoist_sync_log` table (conflict losers, detaches, frozen anchors, skipped lines, terminal command errors), viewable through a palette command.
- **Conflicts [decided]:** fixed rule, Todoist wins, losing value written to the sync log.
- **Deletion [decided]:** detach on either side, never delete, logged. Alternative: propagate deletes with caps.
- **Triggers:** manual "Todoist: Sync now" command first; later interval (default 5 min), app focus, debounced after save of a note with linked tasks. One cycle at a time; vault-switch guard.
- **Old send/sync:** the popover Send is hidden for in-scope lines once brain-side creation lands; the old send/sync code and `todoist-sent.json` polling are retired after that. Migration of `todoist-sent.json`: none by default (file kept).
